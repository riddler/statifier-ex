# Evaluator and the macrostep context - Implementation Plan

## Overview

Lands the evaluation half of `docs/datamodel.md`'s evaluation contract: one
module with one `evaluate` function over `Statifier.Machine.expr()`, one
per-site predicator context carrying spec 5.10's system variables and the
`In(stateId)` predicate, and the two `datamodel["_event"] = ...` writes
Appendix D's `mainEventLoop` performs. Nothing in a document evaluates yet
after this bead - `cond` gating is st-af3.2, `<log>`/`<donedata>` evaluation
is st-af3.7 - but every one of those beads calls the function this bead
lands, so it lands first. Bead: st-af3.1.

Three new modules, one new `MachineState` writer, one new
`%Statifier.ExecutableContent.Context{}` field, and two comment seams in
`Statifier.Interpreter` replaced with real calls.

## Current State Analysis

Everything upstream of evaluation exists; nothing evaluates.

- **Compilation is done.** `Statifier.Compiler.Expressions.compile/3`
  (`lib/statifier/compiler/expressions.ex:63`) already produces
  `{:compiled, %Predicator.Compiled{}, source}` through
  `Predicator.compile_with_spans/1`, and `static/1` produces
  `{:static, value}`. `Statifier.Machine.expr/0`
  (`lib/statifier/machine.ex:82`) is the sum type both arms belong to.
  Predicator is pinned `~> 4.0` (`mix.exs:41`) and locked at 4.0.0
  (`mix.lock:17`), so ADR-0014's span shape is available with no stopgap.
- **Nothing consumes a compiled expression.** Two sites carry an
  unevaluated one with an explanatory comment:
  `Statifier.Machine.Content.Log`'s `value/1`
  (`lib/statifier/machine/content/log.ex:54-65`) and
  `ExitEntry.static_donedata/2`. Both are st-af3.7's, not this bead's.
- **`condition_match/2` is a deliberate stub.**
  `lib/statifier/interpreter/selection.ex:252-255` returns
  `{:error, {:unsupported, :cond}}` for a written `cond`. Its moduledoc
  (`selection.ex:29-42`) records that `select_transitions/2` and
  `select_eventless_transitions/1` already thread `{machine_state,
  transitions}` so the replacement is a body change only. That replacement
  is st-af3.2's.
- **The `_event` seams are comments.** `lib/statifier/interpreter.ex:210-212`
  (`handle_event/2`, external event) and `lib/statifier/interpreter.ex:388-389`
  (`internal_round/1`, internal event) each name st-af3 in place of the
  pseudocode's assignment. A third comment at `interpreter.ex:156-158`
  (`initialize/2`) covers early `<datamodel>` binding and
  `executeGlobalScriptElement` - st-af3.3's and permanently-out-of-scope
  respectively, not this bead's.
- **The datamodel slot exists and is empty.**
  `MachineState.datamodel :: map()` defaults to `%{}` and is settable via
  `MachineState.new/2`'s `:datamodel` option
  (`lib/statifier/machine_state.ex:116,131,170`). Nothing writes it after
  construction.
- **The macrostep-context slot is reserved but unfilled.**
  `Statifier.ExecutableContent.Context`
  (`lib/statifier/executable_content/context.ex:16-28`) has a whole
  moduledoc section stating that the memoized evaluation context arrives as
  a new field on that struct and explicitly never as a third `execute/3`
  argument. `@enforce_keys [:machine_state, :owner]`; the only constructor
  is `Statifier.Interpreter.Content.execute_block/3`
  (`lib/statifier/interpreter/content.ex:77`).
- **`uxid ~> 2.9` is already a dependency** (`mix.exs`), so `_sessionid`
  needs no new dep (ADR-0008).

### What predicator 4.0.0 actually offers (verified against `deps/predicator/`)

- `Predicator.evaluate/3` accepts a `%Predicator.Compiled{}` as its first
  argument and threads `compiled.positions` itself
  (`deps/predicator/lib/predicator.ex:163-180`). Passing a `:positions`
  option alongside a `%Compiled{}` raises `ArgumentError` - we never pass
  one (ADR-0014 item 2).
- `Predicator.Context.new(data, functions: ..., on_unbound: ...)`
  (`deps/predicator/lib/predicator/context.ex:79-94`) builds a reusable
  bound context. `:on_unbound` accepts `:undefined` (default) or `:error`;
  anything else raises `ArgumentError`.
- Custom host functions are a plain map
  `%{name => {arity, fun}}` where `fun` is `fn args, raw_context -> {:ok,
  value} | {:error, binary()} end`
  (`deps/predicator/lib/predicator/evaluator.ex:82-89,1184-1227`). An
  exception raised inside a host function is caught by predicator and
  converted to an error tuple.
- `Context.new/2` **normalizes `nil` to `:undefined` recursively**
  (`context.ex:190-237`), and dotted `.` access on a non-map yields
  `:undefined` rather than an error
  (`evaluator.ex:1104-1137`). Together these give `_event.data` the
  undefined semantics `conf:emptyEventData` needs, with no host special
  casing.
- Errors are `%Predicator.Errors.{EvaluationError,TypeMismatchError,
  UndefinedVariableError,ParseError}{}`; the first three carry both
  `:position` and `:span` (`deps/predicator/lib/predicator/errors.ex:41-56`).
- `on_unbound: :error` is a **root-only** policy: a missing nested member
  stays `:undefined` regardless (`context.ex:30-34`).

### Key Discoveries

- **A strictly per-macrostep context is provably wrong.**
  `docs/datamodel.md:41` says the context is built "once per macrostep".
  Two of its inputs change *within* a macrostep: `_event` is rewritten on
  every internal-event round (`internal_round/1` dequeues many per
  macrostep), and `In(stateId)` reads a configuration that changes at every
  microstep. This plan therefore builds the context **once per evaluation
  site** - one per executable-content block, later one per selection round -
  which keeps the actual commitment ("never once per expression") and adds
  freshness the per-macrostep reading cannot provide. The wording in
  `docs/datamodel.md` and in `ExecutableContent.Context`'s moduledoc is
  amended on this branch to say so, with the reason. This is a prose
  amendment, not an ADR change: no accepted ADR states the interval.
- **The context must be a value the caller builds, not a memo on
  `MachineState`.** `ExecutableContent.Context`'s moduledoc
  (`context.ex:18-25`) already argues the memo is neither machine_state nor
  node-local. A `MachineState` memo field would additionally need an
  invalidation story at every configuration change; a per-site build cannot
  go stale.
- **No statifier-side wrapper struct around the predicator context.**
  ADR-0014 item 2 settled the identical question for the compiled envelope
  ("the envelope is upstream's, not a statifier-side wrapper"); the same
  reasoning applies here, so `Statifier.Evaluator.context/1` returns a
  `%Predicator.Context{}` and the new struct field is typed
  `Predicator.Context.t()`.
- **System variables belong in `machine_state.datamodel`.** Appendix D
  writes `datamodel["_event"] = ...`; spec 5.10 places `_sessionid`,
  `_name`, and `_ioprocessors` in the datamodel as well. Storing them there
  makes `Statifier.Evaluator.context/1` a near pass-through and makes the
  `_event` seam a literal port. `machine_state.datamodel` stops being "the
  author's data only" - `test/statifier/machine_state_test.exs:104-107`
  asserts `ms.datamodel == %{}` today and changes with this bead.
- **`condition_match/2` and `Log.value/1` are deliberately untouched here**
  (st-af3.2 and st-af3.7 own them), so nothing this bead lands is reachable
  from a corpus document. `FeatureDetector` keeps
  `conditional_transitions: :unsupported`
  (`test/support/feature_detector.ex:68`), and `Statifier.Case` flunks -
  never skips - a document using it (`test/support/case.ex:99-117`).
- **`mix adr.check`** scans `def`/`defp` names under
  `lib/statifier/interpreter` for near-misses of the Appendix D name list
  (`lib/mix/statifier/adr_guard.ex:52-70`). No phase adds a function there,
  so no escape comment is needed.

## Desired End State

`Statifier.Evaluator.evaluate/2` evaluates either arm of
`Machine.expr()` against a context built by `Statifier.Evaluator.context/1`,
returning `{:ok, value} | {:error, %Statifier.Evaluator.Error{}}` and never
raising. That context resolves `_event`, `_sessionid`, `_name`,
`_ioprocessors`, and `In(stateId)`. An event with no data makes
`_event.data` evaluate as predicator's `:undefined`, not `%{}`.
`machine_state.datamodel["_event"]` is written for both the external and the
internal round at the pseudocode's own positions.
`%Statifier.ExecutableContent.Context{}` carries the built context in a new
`datamodel_context` field, populated once per block by
`Interpreter.Content.execute_block/3`.

Verified by: a full `mix quality` green on each phase, the unit tests each
phase adds (every one of them sabotaged per `docs/testing.md:78-134`), and
`mix test.regression` unchanged - no conformance test moves in either
direction, because nothing in a document reaches the evaluator yet.

## What We're NOT Doing

- **Not wiring `cond`.** `Selection.condition_match/2` keeps returning
  `{:error, {:unsupported, :cond}}`; st-af3.2 replaces that body.
- **Not evaluating `<log expr>` or `<donedata>`.**
  `Machine.Content.Log`'s `value/1` and `ExitEntry.static_donedata/2` keep
  their "compiled but not yet evaluated" comments; st-af3.7 finishes them.
- **Not parsing or binding `<datamodel>`/`<data>`** (st-af3.3), and not
  implementing `<assign>` (st-af3.4), `<if>` (st-af3.5), or `<foreach>`
  (st-af3.6). `initialize/2`'s early-binding comment stays.
- **Not touching `FeatureDetector`, the exclusions files, or
  `test/passing_tests.json`.** Flipping datamodel features and splitting the
  `<content>` detector is st-af3.8. No conformance test can move on this
  bead, so there is nothing to ratchet.
- **Not building the `Statifier.Session`.** `_sessionid` is supplied via a
  `MachineState.new/2` option with a generated default; Phase 4 (st-cmq)
  replaces the generator with the session's own id and extends
  `_ioprocessors` past the minimal single-entry map.
- **No `nil`-to-`:undefined` normalization function for event data.** The
  one normalization function `docs/datamodel.md` promises (shared by
  `<param>`, `<content>`, `namelist`, `<donedata>`) is st-af3.7's; this bead
  relies on `Predicator.Context.new/2`'s own recursive normalization
  (`deps/predicator/lib/predicator/context.ex:190-237`) and does not
  pre-empt that function's design.
- **No changelog fragment.** Per `changelog.d/README.md`'s narrower rewrite
  rule, a fragment is for where v2 differs from v1, and v1 already had
  system variables and expression evaluation. The one genuine difference - a
  `_sessionid` stable for the session's lifetime rather than regenerated per
  evaluation (ADR-0008) - is not observable through the public API until
  st-af3.2/st-af3.7 make an expression in a document evaluate, so the
  fragment belongs to whichever of those lands first, not here.
- **No memo field on `MachineState` for the built context**, and no
  invalidation protocol - see Key Discoveries.

## Implementation Approach

Build inward-out: the evaluator first, with no caller but its own tests
(Phase 1); then the datamodel content it reads and the two interpreter
writes that produce it (Phase 2); then the seam that hands it to executable
content (Phase 3). Each phase leaves the tree green on its own and each is a
separate commit.

Naming: `Statifier.Evaluator` mirrors `Statifier.Compiler.Expressions` - one
module per side of the compile/evaluate seam. Its moduledoc must state the
three-`Context` naming hazard the way `MachineState`'s moduledoc states the
`MachineState`/`Machine.State` one: `Predicator.Context` (the value this
module builds), `Statifier.ExecutableContent.Context` (the protocol's second
argument, which carries one), and `Statifier.Validator.Context` (unrelated,
validation-time).

## Phase 1: The evaluator and its span-carrying error

### Overview

One module with one `evaluate` function over both `Machine.expr()` arms, one
`context/1` builder that binds the datamodel plus the `In(stateId)` host
function, and the error value ADR-0014 item 4 describes. No caller in `lib/`
yet.

### Changes Required:

#### 1. The error value

**File**: `lib/statifier/evaluator/error.ex` (new)
**Changes**: A small struct carrying ADR-0014 item 4's committed fields
minus the owner - the owner is added by the raise site
(`Interpreter.Content.raise_execution_error/4` already stamps
`{:content, c_index, owner}`), so the evaluator never needs one passed in.

```elixir
defmodule Statifier.Evaluator.Error do
  @enforce_keys [:source, :error]
  defstruct [:source, :error, :span]

  @type t :: %__MODULE__{
          source: String.t(),
          error: struct(),
          span: term() | nil
        }

  @spec new(source :: String.t(), error :: struct()) :: t()
  def new(source, error) do
    %__MODULE__{source: source, error: error, span: Map.get(error, :span)}
  end
end
```

`Map.get/2` rather than `error.span` because `ParseError` has no `:span`
field; a nil span is ADR-0014 item 4's own "nil when predicator cannot
attribute one".

#### 2. The evaluator

**File**: `lib/statifier/evaluator.ex` (new)
**Changes**: `context/1` and `evaluate/2`.

```elixir
@spec context(machine_state :: MachineState.t()) :: Predicator.Context.t()
def context(%MachineState{} = machine_state) do
  Predicator.Context.new(machine_state.datamodel,
    functions: %{"In" => {1, in_function(machine_state)}},
    on_unbound: :error
  )
end

@spec evaluate(context :: Predicator.Context.t(), expr :: Machine.expr()) ::
        {:ok, term()} | {:error, Error.t()}
def evaluate(%Predicator.Context{}, {:static, value}), do: {:ok, value}

def evaluate(%Predicator.Context{} = context, {:compiled, %Predicator.Compiled{} = compiled, source}) do
  case Predicator.evaluate(compiled, context) do
    {:ok, value} -> {:ok, value}
    {:error, error} -> {:error, Error.new(source, error)}
  end
end
```

Points the implementation must honor:

- **`{:static, v}` returns `v` untouched** - no predicator normalization. A
  static value came from the document as a literal and has no expression to
  evaluate (`Compiler.Expressions.static/1`).
- **No `:positions` option, ever** - the `%Compiled{}` carries its own span
  table and passing both raises (ADR-0014 item 2,
  `deps/predicator/lib/predicator.ex:246-273`).
- **`on_unbound: :error` and `functions:` are baked into the context**, not
  passed per call: `Predicator.evaluate/3` routes a *bare map* through
  `Context.new/2` with the call's opts, but a prebuilt `%Predicator.Context{}`
  is used as given. The Phase 1 tests below assert `In/1` and the unbound
  error both fire through the prebuilt-context path, which is what pins this
  down. If that assertion fails, the fallback is one line: keep the built
  value but pass `functions:`/`on_unbound:` on every `Predicator.evaluate/3`
  call as well.
- **`In/1` never raises and never errors**: `Machine.index/2` returns
  `:error` for an unknown id, which becomes `{:ok, false}` - an `In()` on a
  state the document does not declare is false, not an evaluation failure.
  The closure captures `machine_state.machine` and
  `machine_state.configuration`, which is why a context is a position
  snapshot and is rebuilt per site rather than per macrostep.
- **The membrane rule**: this module returns `{:ok, _} | {:error, _}` and
  never raises; only the interpreter turns an error into `error.execution`
  (`docs/architecture.md` principle 3, `Interpreter.Content`'s moduledoc).

#### 3. Tests

**File**: `test/statifier/evaluator_test.exs` (new)

- `{:static, v}` returns `v` for a value predicator would otherwise coerce
  (a nil, a map, a bare atom).
- A `{:compiled, _, _}` arm compiled through
  `Compiler.Expressions.compile/3` evaluates true and false against a
  datamodel bound on `MachineState.new/2`'s `:datamodel` option.
- An unbound root variable returns
  `{:error, %Error{error: %UndefinedVariableError{variable: "score"}}}` with
  a non-nil `span` (ADR-0014 items 4-5).
- A type mismatch returns `{:error, %Error{error: %TypeMismatchError{}}}`.
- `In("s1")` is true for a state in the configuration, false for one that is
  not, and false for an id the machine never declared. These are three
  separate tests on purpose: the private `in_function/1` closure has two
  branches (`Machine.index/2` returning `{:ok, index}` and returning
  `:error`), and the third case is the only one that reaches the second
  branch. Skipping it leaves a private clause uncovered and the coverage
  floor is the thing that finds out.
- Evaluating against a machine_state whose configuration has moved gives a
  different `In/1` answer only after `context/1` is called again - the
  snapshot property, pinned so the per-site build rule is not silently
  relaxed later.
- `evaluate/2` never raises: a deliberately hostile expression (division by
  zero / a wrong-arity `In()` call) returns an error tuple.

Every test above asserts `lib/` behavior and therefore carries a sabotage
line in `docs/testing.md:106-107`'s format
(`# sabotage: <what was broken> -> red`).

## Phase 2: System variables in the datamodel, and the two `_event` writes

### Overview

Spec 5.10's four system variables land in `machine_state.datamodel`, and
Appendix D's `datamodel["_event"] = ...` assignments replace the two
comments that stand in for them.

### Changes Required:

#### 1. System-variable construction

**File**: `lib/statifier/evaluator/system_variables.ex` (new)
**Changes**: Two functions, so that neither `MachineState` nor
`Interpreter` grows spec 5.10 knowledge of its own.

```elixir
@scxml_event_processor "http://www.w3.org/TR/scxml/#SCXMLEventProcessor"

@doc "The three session-lifetime system variables (spec 5.10)."
@spec initial(machine :: Machine.t(), session_id :: String.t()) :: map()
def initial(%Machine{} = machine, session_id) do
  %{
    "_sessionid" => session_id,
    "_name" => machine.name,
    "_ioprocessors" => %{
      @scxml_event_processor => %{"location" => session_id}
    }
  }
end

@doc "`_event`'s value for `event` - spec 5.10.1's fields."
@spec event(event :: Event.t()) :: map()
def event(%Event{} = event) do
  %{
    "name" => event.name,
    "type" => Atom.to_string(event.type),
    "sendid" => nil,
    "origin" => nil,
    "origintype" => nil,
    "invokeid" => nil,
    "data" => event.data
  }
end
```

`nil` is deliberate for every absent field, `"data"` above all: predicator's
`Context.new/2` normalizes `nil` to `:undefined` recursively
(`deps/predicator/lib/predicator/context.ex:190-237`), so `_event.data`
evaluates as undefined and `_event.data.foo` also as undefined - the
`conf:emptyEventData` requirement `tools/corpus/scxml_w3/exclusions.exs:7-11`
records as the condition for leaving test343/488/528 unexcluded. Writing
`%{}` there is precisely the outcome that comment forbids. `_name` is `nil`
when `<scxml>` wrote no `name` attribute, which normalizes the same way.
`sendid`/`origin`/`origintype`/`invokeid` are `nil` because
`Statifier.Event` deliberately does not carry them yet (its own moduledoc);
they become real when `<send>`/`<invoke>` land.

#### 2. `MachineState`: seeding and the single `_event` writer

**File**: `lib/statifier/machine_state.ex`
**Changes**:

- `new/2` gains a `:session_id` option, defaulting to
  `UXID.generate!(prefix: "sess")` (`deps/uxid/lib/uxid.ex:89-104`). This is
  the **first** `UXID.` call site in `lib/` - `<send>` and `<invoke>` are
  unimplemented, so there is no `send_`/`inv_` precedent to match and
  ADR-0008's prefix table is the source of truth, not repo convention.
  It merges `SystemVariables.initial/2` **over** the `:datamodel` option's
  map, so an author-supplied datamodel can never shadow a system variable.
- A new `put_event/2`, the single writer of `datamodel["_event"]`, in the
  style of the counter contract's single-writer rule:

```elixir
@doc """
`datamodel["_event"] = event` (Appendix D) - the one and only writer of
the `_event` system variable (spec 5.10.1). Both of `mainEventLoop`'s
assignments, the external one and the internal one, go through here.
"""
@spec put_event(machine_state :: t(), event :: Event.t()) :: t()
def put_event(%__MODULE__{datamodel: datamodel} = machine_state, %Event{} = event) do
  %{machine_state | datamodel: Map.put(datamodel, "_event", SystemVariables.event(event))}
end
```

- The moduledoc gains a short section stating that `datamodel` holds spec
  5.10's system variables alongside the author's data, that `_sessionid`,
  `_name`, and `_ioprocessors` are written exactly once by `new/2`, and that
  `_event` is written only by `put_event/2` - the same "exactly one writer"
  discipline the counter contract already states, and the same
  enforced-by-review status.
- The `:session_id` option is documented on `new/2` beside `:trace` and
  `:datamodel`. `Statifier.initialize/2` and `Interpreter.initialize/2`
  already pass `opts` straight through and need no change
  (`lib/statifier/interpreter.ex:149`, `lib/statifier.ex:90-93`).

**ADR-0002 note to write inline**: seeding the three session-lifetime
variables in `new/2` rather than in `initialize/2` is a mechanical
deviation from `interpret`'s ordering, not a semantic one -
`Interpreter.initialize/2` calls `MachineState.new/2` as its first
statement, so the variables are bound before anything can read them, and
`new/2` is the only writer of the struct's initial fields.

#### 3. The two interpreter seams

**File**: `lib/statifier/interpreter.ex`
**Changes**: replace the two stand-in comments with the calls, keeping each
at the pseudocode's own position.

- `handle_event/2` (`interpreter.ex:210-213`): the comment becomes
  `machine_state = MachineState.put_event(machine_state, event)` placed
  immediately before `Selection.select_transitions/2`, exactly where
  `datamodel["_event"] = externalEvent` sits in `mainEventLoop`. The
  remaining half of that comment (the invoke `finalize`/`autoforward`
  passes, st-cmq) stays.
- `internal_round/1` (`interpreter.ex:388-389`): the comment becomes the
  same call on the dequeued event, before `Selection.select_transitions/2`
  and after the `EventDequeued` trace - the pseudocode's own order.
- Neither call changes a signature, an arity, or the effect list. The
  eventless probe writes no `_event`: the pseudocode assigns `_event` only
  when it has an event, and an eventless round has none, so the previous
  round's `_event` remains bound. That is the spec's behavior and must be
  stated in a comment rather than left to be rediscovered.

#### 4. Tests

**Files**: `test/statifier/evaluator/system_variables_test.exs` (new);
additions to `test/statifier/machine_state_test.exs` and
`test/statifier/interpreter/microstep_test.exs` (or a sibling under
`test/statifier/interpreter/`).

- `SystemVariables.event/1` maps `Event.external/2` with no data to a map
  whose `"data"` is `nil`, and the end-to-end assertion that matters:
  `Predicator.evaluate` of `_event.data` against
  `Statifier.Evaluator.context/1` returns `{:ok, :undefined}`, and

## Phase 3: The reserved slot on `ExecutableContent.Context`

### Overview

Fills the field `Statifier.ExecutableContent.Context`'s moduledoc has been
reserving, populated once per block by the block runner, and corrects the
two places that describe the context's rebuild interval.

### Changes Required:

#### 1. The new field

**File**: `lib/statifier/executable_content/context.ex`
**Changes**: `datamodel_context` joins the struct and `@enforce_keys`.

```elixir
@enforce_keys [:machine_state, :owner, :datamodel_context]
defstruct [:machine_state, :owner, :datamodel_context]

@type t :: %__MODULE__{
        machine_state: MachineState.t(),
        owner: Content.owner(),
        datamodel_context: Predicator.Context.t()
      }
```

Enforced rather than optional: there is exactly one constructor
(`Interpreter.Content.execute_block/3`), it can always build one, and an
optional field would let a future node read `nil` and quietly evaluate
nothing - the rescue-to-default failure `docs/architecture.md` principle 3
names.

The moduledoc's "Where the datamodel context goes" section is rewritten from
future tense to present: the slot is filled, it holds a
`%Predicator.Context{}` (upstream's envelope, no statifier wrapper, the same
call ADR-0014 item 2 made), it is built once per **block** rather than once
per macrostep, and the reason is that `_event` changes per internal round
and `In/1` reads a configuration that changes per microstep, so a
macrostep-scoped snapshot would be stale by construction. The "never a third
`execute/3` argument" paragraph stays exactly as written - it is the
decision this change honors.

#### 2. The block runner builds it

**File**: `lib/statifier/interpreter/content.ex`
**Changes**: one line in `execute_block/3`:

```elixir
context = %Context{
  machine_state: machine_state,
  owner: owner,
  datamodel_context: Evaluator.context(machine_state)
}
```

The early-return clause `execute_block(machine_state, _owner, [])` stays
first and untouched, so an empty block still builds nothing - the untraced,
un-evaluated hot path keeps its current cost.

The moduledoc gains a paragraph: the context is built once here and shared
by every node in the block, which is `docs/datamodel.md`'s "never per
expression" commitment at the tightest interval that stays correct. A node
that mutates the datamodel (st-af3.4's `<assign>`) will have to rebuild or
rebind before the next node reads it; naming that here is what stops
st-af3.4 from discovering it at debugging time.

#### 3. Documentation amendments

**File**: `docs/datamodel.md`
**Changes**: the evaluation-contract bullet currently reading "The
evaluation context is built once per macrostep, not per expression" becomes
the per-site rule plus its two-clause reason (`_event` per internal round,
`In/1` per configuration change). The upstreaming section's item 1
("Persistent bound context") gains a sentence noting that
`Predicator.Context.bind/3` is the cheap-rebind API that would let the
interval widen again, which is the seam that entry was written about.

#### 4. Tests

**File**: `test/statifier/interpreter/content_test.exs` (extend), plus a
recording node under `test/support/`.

Because no shipped node reads the field yet, the assertion needs a node that
does: a small struct in `test/support/` with a
`defimpl Statifier.ExecutableContent` whose `execute/2` returns the received
`datamodel_context` as a log effect (or stashes it via a returned effect the
test inspects). A hand-built `%Machine{}` can hold it in `contents`, which is
how the block runner reaches it. That support file states its own coverage
position - `test/support/` is excluded from coverage
(`docs/testing.md:229-242`) - and the sabotage line goes on the *test*, not
on the support struct.

- The context reaching a node evaluates `In(...)` correctly for the
  configuration at the time the block ran.
- Every node in a two-node block receives the *same* context value (the
  once-per-block property, pinned so a later refactor cannot quietly move
  the build inside the fold).
- A block whose owner is a transition and one whose owner is an
  `<onentry>` both get a context - the field is not owner-dependent.
- Sabotage lines on each.

## Performance Considerations

`Predicator.Context.new/2` deep-normalizes its data map on every call
(atom keys to string keys, `nil` to `:undefined`, recursively through nested
maps and lists - `deps/predicator/lib/predicator/context.ex:190-237`). At
one build per executable-content block over corpus-sized datamodels this is
not measurable, and correctness (a context that cannot be stale) is worth
more than the allocation. The documented widening path, when it is ever
needed, is `docs/datamodel.md`'s upstreaming seam 1: keep one bound context
and use `Predicator.Context.bind/3` for the O(1) rebind of `_event` and of
assigned locations, rebuilding only the `In/1` closure when the
configuration moves. Nothing in this plan forecloses that - it is a change
inside `Statifier.Evaluator.context/1` and its callers, with no signature
movement.
