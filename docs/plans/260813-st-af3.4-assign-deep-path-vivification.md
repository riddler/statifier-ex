# `<assign>`: auto-vivifying deep-path assignment - Implementation Plan

## Overview

Add `<assign>` as an executable-content element: a new `Statifier.Document.Assign`
node, a lowering builder, a `Statifier.Machine.Content.Assign` struct with its
`Statifier.ExecutableContent` implementation in the same file, and the runtime
write that resolves a deep `location` path, auto-vivifies intermediate
containers, writes into `machine_state.datamodel`, and rebuilds the block's
datamodel context so the next node in the same block sees the new value. Every
failure - an unresolvable location, an undeclared root, a system-variable
target, a bad value expression - becomes `error.execution` through the block
runner's existing single conversion site.

Beads issue: `st-af3.4`. Research: `docs/research/260813-st-af3.4-assign-deep-path-vivification.md`.

## Current State Analysis

Everything this bead needs already exists as a seam that was designed for it,
and three places in the source name the bead by number.

- The parser is element-agnostic; the allowlist is one map at
  `lib/statifier/lowering.ex:53-69`. `<assign>` parses today and is rejected one
  layer later as `{:unsupported_element, "assign"}`.
- `lib/statifier/machine/content.ex:11-15` states that each new element gets its
  own struct plus its own `defimpl` in the same file, "never a clause added to
  this module", and names `<assign>` first.
- `lib/statifier/interpreter/content.ex:49-52` names the rebuild seam in prose:
  "A node that mutates the datamodel (`<assign>`, st-af3.4) will have to rebuild
  or rebind that context before the next node in the same block reads it."
- `lib/statifier/compiler.ex:657-682` (`build_content_node/2`) is the one site
  that dispatches on Document node struct type. Its `@spec` is
  `DRaise.t() | DLog.t()`, and `acc()`'s `contents_acc` (`lib/statifier/compiler.ex:123`)
  carries the same union - which is why the Document-side union cannot widen in
  a phase that leaves the compiler untouched (see "Implementation Approach").
- `machine_state.datamodel` has exactly four writers today
  (`lib/statifier/machine_state.ex:257`, `:326`,
  `lib/statifier/interpreter/datamodel.ex:146`, `:201`). `<assign>` becomes the
  fifth.
- Nothing guards system-variable writes at write time. The only protection is
  the construction-time `Map.merge/2` ordering at
  `lib/statifier/machine_state.ex:257`. There is no named list of the four
  system-variable names anywhere - they exist only as literal keys in
  `Statifier.Evaluator.SystemVariables.initial/2`.
- `Statifier.Machine.Content.Log` does not evaluate its compiled `expr` at all
  yet (`lib/statifier/machine/content/log.ex:62-65` returns `nil` for the
  `{:compiled, ...}` arm). `<assign>` is therefore the **first content node that
  evaluates a compiled expression against the block's datamodel context**.
- 82 generated corpus files require `assign_elements`; exactly 6 name no other
  feature still registered `:unsupported`.

## Desired End State

A document containing `<assign location="..." expr="..."/>` (or with child
content) compiles, runs, and writes the evaluated value into
`machine_state.datamodel` at the resolved path, creating intermediate maps and
lists as predicator's `ContextLocation.put/3` does; a later node in the same
block reads the new value; and each of the failure modes below raises exactly
one `error.execution` platform event with cause origin
`{:content, c_index, owner}` and the block halting at that node.

Verification: the three new internal test files added by these phases
(`test/statifier/document/assign_test.exs`,
`test/statifier/machine/content/assign_test.exs`,
`test/statifier/validator/checks/assign_test.exs`) pass alongside the four
existing test files these phases extend, the six
corpus files listed under "Corpus/Ratchet Notes" pass with
`assign_elements: :supported`, and `mix test.regression` is green with those six
in `test/passing_tests.json`.

### Key Discoveries

- **`<assign expr>` must defer compile failures to runtime.** Verified against
  the installed predicator 5.0.0: `Predicator.compile_with_spans("{p1: 'v1'")`
  returns `{:error, "Expected '}' but found end of input..."}`, and
  `test/scion_tests/assign/assign_invalid_test.exs` requires that document to
  run and produce `error.execution`. Rejecting at load time would fail the whole
  document instead. This is the exact `<data expr>` asymmetry
  `docs/datamodel.md:53-71` already records as deliberate, with the
  `{:invalid, error}` mechanism at `lib/statifier/machine/data.ex:36-40` and
  `lib/statifier/compiler.ex:816`.
- **`location` cannot be resolved at compile time even in principle**, and
  parse-checking it at compile time would break `test286`. Verified:
  `Predicator.context_location("foo.bar.baz ", %{})` returns
  `{:ok, ["foo", "bar", "baz"]}` - the trailing space is not the failure
  test286 is about.
- **test286's failure is the undeclared root, not the path syntax.** Verified:
  `Predicator.ContextLocation.put(%{}, ["foo","bar","baz"], 1)` succeeds and
  vivifies. So predicator's vivification alone does not satisfy test286; the
  root-segment rule in Decision 4 below is what does.
- **`expr="return"` compiles and fails at evaluation**, not at compile:
  `{:error, %Predicator.Errors.UndefinedVariableError{span: {{1,1},{1,7}}}}`.
  That struct carries a `:span`, so `Statifier.Evaluator.Error.new/2` lifts a
  real span for test487/test312's failures.
- **`Predicator.Context.new/2` deep-normalizes `nil` to `:undefined`**
  (`deps/predicator/lib/predicator/context.ex:326-337`), and nothing in `lib/`
  reads `context.data` back out today. Decision 2 keeps it that way.
- **Growing the ratchet needs no ledger entry.** Verified against
  `Mix.Statifier.GateGuard.removed_patterns/3`
  (`lib/mix/statifier/gate_guard.ex:206-236`): a finding is produced only when
  `base -- head` is non-empty. Adding patterns produces nothing. ADR-0011.
- **`test/passing_tests.json`'s `internal_tests` already globs
  `test/statifier/**/*_test.exs`**, so new internal test files are ratcheted
  automatically with no registry edit.
- **Conformance suites are excluded by default** (`test/test_helper.exs`:
  `ExUnit.start(exclude: [:scion, :scxml_w3, ...])`), so flipping
  `assign_elements: :supported` cannot redden `mix quality`'s Tests stage; only
  `mix test.regression` runs corpus files, and only those in the registry.
- Constraints: ADR-0002 (no Appendix D body for `executeContent`; 5.4's prose is
  the source), ADR-0003 and `docs/architecture.md:104-114` (a new element is a
  struct plus a `defimpl`, **never a change to the runner**), ADR-0004
  (predicator is the datamodel), ADR-0011 (the ratchet only grows), ADR-0012
  constraints 1 and 4 (`%MachineState{}` stays a resumable position; the
  motivating diagnostic is literally an `<assign>` error), ADR-0014 items 1-4
  (compiled-expression shape and error identity).

## Decisions

The research recorded seven open questions and no human was available to answer
them. Each is decided here, with its rationale, so nothing is left for the
implementer to discover.

**Decision 1 - the predicator entry point.** Use
`Predicator.context_location/3` to resolve the path, then
`Predicator.ContextLocation.put/3` to write, rather than
`Predicator.context_assign/4` or `Predicator.Context.assign/3`. Rationale:
`context_assign/4` is literally those two calls composed
(`deps/predicator/lib/predicator.ex:1144-1147`), so the vivification semantics
`docs/datamodel.md:104-109` commits to are byte-identical either way, but
splitting them lets the *resolve* run against the normalized context and the
*write* run against the raw `machine_state.datamodel`. That split is what makes
Decision 2 possible, and it is also what gives the root-segment check in
Decision 4 a resolved path to inspect. **This deviates from the bead
description's naming of `Predicator.context_assign/4`**: the deviation is
mechanical (same two functions, same semantics), not semantic, and is recorded
here rather than left implicit.

**Decision 2 - the `nil` versus `:undefined` round trip.** Never write
`context.data` back into `machine_state.datamodel`. Resolve the path against
`context.datamodel_context.data` (the normalized view, so a bracket key like
`items[i]` reads `i` exactly as an expression would), and apply
`ContextLocation.put/3` to `machine_state.datamodel` (the raw map, `nil`s
intact). Rationale: `machine_state.datamodel` is the resumable truth under
ADR-0012 constraint 1, and `test/statifier/interpreter/datamodel_test.exs`'s
`assert ms.datamodel["Var1"] == nil` is a live assertion that a normalizing
round trip would break. `ContextLocation.put/3` treats `nil` and `:undefined`
identically for vivification (`deps/predicator/lib/predicator/context_location.ex:381-393`),
so writing into the raw map loses nothing. A `:undefined` may still *enter* the
datamodel as list padding past the end of a list - that is predicator's
documented sentinel and the corpus spelling settled by st-unt, and is intended.

**Decision 3 - where the rebuild seam goes.** Inside `<assign>`'s own
`execute/2`, which returns
`%{context | machine_state: ms, datamodel_context: Evaluator.context(ms)}`. The
block runner is not touched. Rationale: `docs/architecture.md:112-114` requires
"never a change to the runner", and the protocol already permits a node to
return an updated context (`lib/statifier/executable_content.ex:19-21`).
**`test/statifier/interpreter/content_test.exs:316-341` stays green exactly as
written and its sabotage note is unchanged** - that test drives
`Statifier.ContextRecorder`, which deliberately mutates the datamodel *without*
rebuilding, so it asserts the runner's behavior rather than `<assign>`'s. Two
moduledocs go stale and are corrected in Phase 1:
`lib/statifier/interpreter/content.ex:49-52` (the seam is now taken, in the
node) and `test/support/context_recorder.ex:12-20` (its "no shipped node
rebuilds that field either" clause becomes false).

**Decision 4 - the root segment must already exist.** After resolving the path,
if `List.first(path)` is not a key of `machine_state.datamodel`, return
`{:error, {:unbound_location, location_source}}` without attempting the write.
Rationale: spec 5.9.2 requires `error.execution` when a location expression
"cannot be evaluated to yield a valid location", and
`test/scxml_tests/mandatory/assign/test286_test.exs` requires exactly that for
`location="foo.bar.baz "` in a document with no `<datamodel>`. Predicator's
`put/3` would happily vivify `foo`, so this rule is what makes test286 pass.
It is also faithful to the scope commitment: `docs/datamodel.md:28-30` promises
"auto-vivification of **intermediate** maps", not creation of undeclared
top-level variables, and it matches ECMAScript strict-mode assignment to an
undeclared identifier. A `<data>` id is seeded (`Map.put_new(_, id, nil)`,
`lib/statifier/interpreter/datamodel.ex:146`) under both bindings before any
content runs, so a declared id always passes this check even when unbound.

**Decision 5 - how far spec 5.10's protection extends.** Test the *resolved root
segment* for a leading `"_"` rather than checking membership in a list of four
names. Rationale: 5.10 says "Variable names beginning with '_' are reserved for
system use", requires platform variables under an `_x` root that this engine
does not yet create, and says "A conformant SCXML document MUST NOT contain ids
beginning with '_' in the `<data>` element" - so a prefix test can never collide
with legitimate author data, covers `_x.foo` and any future system variable for
free, and needs no new list to be invented and kept in sync. Testing the
resolved root rather than the raw attribute string handles `_event.name` and
`_event['name']` uniformly. This is both narrower in code and broader in
coverage than the bead's four-name list; the deviation is recorded here.
`test/scxml_tests/mandatory/system_variables/test346_test.exs` exercises all
four names. This check runs **before** Decision 4's root-existence check, so
`_undeclared` reports as a system-variable violation rather than an unbound
location.

**Decision 6 - `location` is resolved entirely at runtime; `expr` compiles at
Machine-build time but defers its failure.** `location` is carried as a raw
`String.t()` on both the Document and Machine structs and resolved by
`context_location/3` at `execute/2` time - it cannot be resolved earlier even in
principle, since a bracket key reads the pre-assignment datamodel, and
parse-checking it at load time would reject test286's document instead of
letting it raise. `expr` goes through `Statifier.Compiler.Expressions.compile/3`
like every other expression, but a compile failure is captured as
`{:invalid, error}` on the Machine struct instead of failing
`Statifier.Compiler.compile/1` - the exact `<data expr>` mechanism
(`lib/statifier/machine/data.ex:36-40`, Decision 2 of the st-af3.3 plan),
required by `assign_invalid_test.exs`. `<assign>` therefore joins `<data expr>`
on the deferring side of the asymmetry `docs/datamodel.md:53-71` names as
deliberate; that document's prose is updated in Phase 4 to say so.

**Decision 7 - what `error.execution`'s `data:` carries.** Three shapes, each
matching an existing precedent:

- an `expr` evaluation failure: the `%Statifier.Evaluator.Error{}` that
  `Statifier.Evaluator.evaluate/2` already returns (source = the expression,
  span lifted from predicator's struct). Unchanged from every other evaluation
  site.
- a deferred compile failure: the captured `%Statifier.Compiler.Error{}`,
  passed through as `Interpreter.Datamodel.bind_value/4` does for
  `{:invalid, error}`.
- a location failure - `%Predicator.Errors.LocationError{}` from
  `context_location/3` or `put/3`: wrapped as
  `Statifier.Evaluator.Error.new(location_source, error)`. `LocationError` has
  no `:span` field, so `new/2`'s `Map.get(error, :span)` yields `nil`, which
  ADR-0014 item 4 explicitly permits ("nil when predicator cannot attribute
  one"). The `<assign>`'s own document span travels separately on the Machine
  struct's `location_location` field, which is what ADR-0012 constraint 4's "the
  `<assign>` at line 42" diagnostic reads.
- the two engine-originated failures carry bare tagged tuples,
  `{:unbound_location, location_source}` and `{:system_variable, root}`,
  following the bare-tuple precedent already in
  `lib/statifier/interpreter/datamodel.ex:196` (`{:src, uri}`).

## What We're NOT Doing

- **Not flipping `conditional_transitions` to `:supported`.**
  `test/support/feature_detector.ex:68` still reads `:unsupported` even though
  st-af3.2 landed `cond` and is closed, and it is the single largest co-blocker
  among the 76 corpus files `<assign>` alone does not unblock. Flipping it is
  real, separable work with its own baseline run and its own ratchet delta, and
  it is not `<assign>`. **File it as a follow-up bead** (`/wurk:issue`,
  `area:test-harness` + `area:corpus`) rather than widening this one. This is
  the research's open question 4, decided deliberately.
- Not implementing `<script>` (permanently unsupported, ADR-0004) or the other
  executable-content elements (`<if>`, `<foreach>`, `<send>`, `<cancel>`,
  `<invoke>`).
- Not creating the `_x` platform-variable root that spec 5.10 requires.
  Decision 5's prefix test already protects it against author writes; creating
  and populating it is separate work with no corpus file driving it today.
- Not emitting a trace effect for a datamodel write.
  `docs/observability.md:57-68`'s minimum trace vocabulary is a closed table
  with no datamodel-write row, and `Trace.ContentExecuted` already covers
  `<assign>` generically through its `c_indexes` - the same reasoning
  `lib/statifier/interpreter/datamodel.ex:104-113` gives for `<data>` binding.
- Not benchmarking or optimizing the per-assign context rebuild. See
  "Performance Considerations"; st-sdh owns that question.
- Not changing `Statifier.Interpreter.Content`'s code. Only its moduledoc
  changes (Decision 3).

## Implementation Approach

Four phases. Phase 1 is a full vertical slice rather than a
lowering-then-compiler split, and that is deliberate: widening
`Statifier.Document`'s `content_node` union without adding the matching
`build_content_node/2` clause and widening `acc()`'s `contents_acc`
(`lib/statifier/compiler.ex:123,657`) leaves a Document node type flowing into a
function whose `@spec` excludes it, which dialyzer reports and which would make
an intermediate commit's gate red. The skill's rule applies: combine rather than
split when the intermediate gate cannot be green.

This is a deliberate exception to the parser-vs-interpreter-vs-corpus-tooling
split `.claude/wurk/plan.md` asks this project's plans to prefer, not an
unstated deviation from it: the union-widening problem crosses that very
boundary, since the Document-side type and the compiler `@spec` that consumes it
sit on opposite sides of it and cannot move independently. Phases 2 through 4
do respect the boundary - two interpreter-side rules and one corpus-tooling
phase - so the parallelization property `docs/workflow.md` wants is only given
up for the first slice.

Phases 2 and 3 each add one independently-testable rule on top of the slice.
Phase 4 is the corpus-tooling boundary the project's `.claude/wurk/plan.md`
names, and is separable because conformance tests are excluded from `mix test`.

Every new test asserting `lib/` behavior carries a sabotage note per
`docs/testing.md:80-136`. Suggested mutations are given per phase so the
implementer does not have to invent one.

## Phase 1: The `<assign>` element, end to end, with `expr`

### Overview

`<assign location="..." expr="..."/>` parses, lowers, compiles, and at runtime
resolves the path, vivifies intermediates, writes into
`machine_state.datamodel`, rebuilds the block's datamodel context, and returns
`{:error, reason}` on every predicator failure.

### Changes Required

#### 1. Document node

**File**: `lib/statifier/document/assign.ex` (new)
**Changes**: The Document struct, modeled on `lib/statifier/document/log.ex` for
the optional-attribute shape and `lib/statifier/document/data.ex` for the
multi-source value. `location` is required, so it is `@enforce_keys`'d alongside
the node's own `Parser.Location` (which is *not* the same thing - name the
fields so the two cannot be confused; the moduledoc must say so explicitly).

```elixir
@enforce_keys [:location, :node_location]
defstruct [:location, :node_location, expr: nil, text: nil, attribute_locations: %{}]
```

Use whatever field naming the implementer finds least confusable, but the
SCXML `location` attribute and the document `Parser.Location` span must be
distinguishable at a glance; `location` / `node_location` above is the
suggestion. `text` is present from this phase and stays `nil` until Phase 3
populates it, exactly as `Statifier.Document.Content` holds both
representably so the validator can report the pair.

**File**: `lib/statifier/document.ex:100`
**Changes**: `@type content_node :: Raise.t() | Log.t() | Assign.t()`.

#### 2. Lowering

**File**: `lib/statifier/lowering.ex:53-69`
**Changes**: add `"assign" => &Builders.build_assign/2` to `@dispatch`.

**File**: `lib/statifier/lowering/builders.ex`
**Changes**: `build_assign/2` following `build_raise/2`'s required-attribute
shape for `location` (returning `{nil, [Error.missing_attribute("assign",
"location", element.location)]}` when absent) and `build_log/2`'s
`Attributes.put_location/4` recording for `location` and `expr`. Add the third
`content_node_name/1` clause (`:543-545`), `%Assign{} -> "assign"`, and widen
its `@spec`.

#### 3. Compiler and Machine struct

**File**: `lib/statifier/compiler.ex`
**Changes**: `DAssign`/`MAssign` aliases; widen `acc()`'s `contents_acc` union
(`:123`) and `build_content_node/2`'s `@spec` (`:657`); add two
`build_content_node/2` clauses mirroring the `%DLog{}` pair - a no-`expr` clause
and an `expr` clause - except the `expr` clause captures a compile failure as
`{:invalid, error}` rather than returning `{:error, error}` (Decision 6). Widen
`expr_location/1` to accept `DAssign.t()` as well, or add a sibling; either is
fine, name the choice in the commit.

**File**: `lib/statifier/machine/content/assign.ex` (new)
**Changes**: the struct plus its `defimpl Statifier.ExecutableContent`, in one
file (`docs/architecture.md:112-114`).

```elixir
@enforce_keys [:c_index, :location, :node_location]
defstruct [:c_index, :location, :node_location, value: {:static, nil},
           location_location: nil, expr_location: nil]

@type value :: Machine.expr() | {:invalid, Compiler.Error.t()}
```

`execute/2`, in order:

1. `evaluate_value/2` - `{:invalid, error}` short-circuits to
   `{:error, error}`; anything else goes through
   `Statifier.Evaluator.evaluate(context.datamodel_context, value)`.
2. `Predicator.context_location(node.location, context.datamodel_context.data)` -
   pass `.data`, never the `%Predicator.Context{}` struct itself, which would
   satisfy `context_location/3`'s `is_map/1` guard and then look up the wrong
   keys. On `{:error, error}` return
   `{:error, Evaluator.Error.new(node.location, error)}`.
3. Decision 4's root check against `context.machine_state.datamodel`.
4. `Predicator.ContextLocation.put(machine_state.datamodel, path, value)`; on
   `{:error, error}` wrap as in step 2.
5. On success, build `ms = %{machine_state | datamodel: new_datamodel}` and
   return
   `{:ok, %{context | machine_state: ms, datamodel_context: Evaluator.context(ms)}, []}`.

No effect is emitted, and nothing here raises or builds a `Statifier.Event` -
`test/statifier/interpreter/content_acceptance_test.exs`'s structural AC globs
`lib/statifier/machine/content/*.ex` and will sweep this new file in
automatically.

**File**: `lib/statifier/machine/content.ex:11-15,49`
**Changes**: widen `@type t` to include `Assign.t()`; drop `<assign>` from the
moduledoc's list of *future* nodes.

#### 4. Moduledoc corrections (Decision 3)

**File**: `test/support/context_recorder.ex:12-20`

**File**: `test/statifier/machine/content/assign_test.exs` (new) - the protocol

**File**: `test/statifier/interpreter/datamodel_test.exs` - one regression test

Sabotage suggestion: have `execute/2` write `assigned_context.data` back into
`machine_state.datamodel` instead of putting into the raw map -> the unrelated
id becomes `:undefined` -> red.

## Performance Considerations

Every successful `<assign>` calls `Statifier.Evaluator.context/1`, which
`Predicator.Context.new/2` implements as a deep normalization of the whole
datamodel (`lib/statifier/evaluator.ex:63-72`). A block of *n* `<assign>` nodes
therefore normalizes the datamodel *n* times rather than once. That is accepted
here for correctness and shape: the cheap alternative, `Predicator.Context.bind/3`,
is O(1) only for a top-level key and does not express a deep-path write, and the
`Predicator.Context.assign/3` alternative would force Decision 2's normalizing
round trip back into `machine_state.datamodel`. Nothing evaluates in a hot path
yet, so there is nothing to measure; **st-sdh** already owns the benchmarking
question and the px-8ii `FunctionProvider`/`host:` seam is the upstream escape
hatch if it ever matters. Do not pre-optimize this in these phases.

  including the `{:invalid, _}` deferral and the `inline_value/1` fold
- `test/statifier/machine/content/assign_test.exs` - the protocol leaf, where
  the vivification and error matrix lives
- `test/statifier/validator/checks/assign_test.exs` - spec 5.4.2's exclusion
- `test/statifier/interpreter/content_test.exs` - through the real block runner:
  a later node sees the write; a failure raises one `error.execution` and halts
  the block
- `test/statifier/interpreter/datamodel_test.exs` - Decision 2's `nil` regression

Key edge cases, all at the leaf: deep vivification of maps and of lists; list
index past the end padding with `:undefined`; negative index; scalar collision
mid-path; integer segment against an existing map (allowed - predicator's own
rule, `context_location.ex:169-170`); undeclared root; non-assignable location;
system-variable root, bare and nested; a value expression that fails to
evaluate; a value expression that failed to compile.

Every one of these tests carries a sabotage note per `docs/testing.md:80-136` -
one line directly above the `test` line and above any `@tag`, naming a mutation
a reasonable person could make by mistake. Per-phase suggestions are given
inline above. Generated corpus files are exempt and get no notes.
