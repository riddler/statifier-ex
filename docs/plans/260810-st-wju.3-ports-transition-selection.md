# Transition selection - Implementation Plan

## Overview

Ports the Appendix D transition-selection block function-for-function
(ADR-0002): `select_transitions`, `select_eventless_transitions`,
`remove_conflicting_transitions`, `compute_exit_set`, `get_transition_domain`,
`get_effective_target_states`, `find_lcca`, plus the spec 3.13 event
descriptor matcher and the `cond` evaluation seam. Everything here is a pure
query over plain values, unfused, so `select_transitions(machine_state, event)`
in `iex` answers "what would happen if event X arrived" without stepping -
`docs/observability.md` constraint 5, which this bead is the one that ticks.

Nothing here steps a machine. This bead produces no effect and emits no trace:
the `transitions selected` trace point belongs to st-wju.6, which calls these
queries from `microstep/1`. Exiting and entering states is st-wju.4; executable
content is st-wju.5.

Bead: st-wju.3. No research document exists; the bead's description and
acceptance criteria are the specification, read alongside ADR-0002 (literal
port), ADR-0005 (full configuration, interned indexes), ADR-0012 /
`docs/observability.md` (constraint 5), and the two landed sibling plans
(`docs/plans/260809-st-wju.1-compile-document-to-interned-machine.md`,
`docs/plans/260809-st-wju.2-machine-state-event-effects-vocabulary.md`).

**A note on the word "phase".** The project roadmap numbers its own phases -
Phase 1 is the core engine (this epic, `st-wju`), Phase 3 is the datamodel
(`st-af3`), Phase 4 is sessions and invoke (`st-cmq`). This plan numbers its
four implementation phases independently. Every reference to a roadmap phase
below names the bead too ("the datamodel bead, st-af3"); a bare "Phase N"
always means a phase of *this* plan.

No human was available while this plan was written. Every question the bead
left open is settled below under "Decisions", each stated as an assumption a
reviewer may overturn; the three most reversible are listed again under "Open
Questions" so a reviewer can find them without reading the whole document.

### What v1 got wrong here, and why it matters to the tests

`../statifier` (read-only reference) is the source of the two named regression
tests the bead asks for. Both were confirmed against the v1 tree:

- **The parallel-region conflict bug.** v1's
  `resolve_transition_conflicts/2` (`../statifier/lib/statifier/interpreter/transition_resolver.ex:83`)
  never computes a per-transition exit set in the spec's sense. It reduces the
  exit set to a boolean "does this transition leave its nearest parallel
  ancestor" (`:167-184`), groups transitions into "exits parallel" versus
  "stays inside" (`:205-220`), and when both groups are non-empty **collapses
  the entire microstep to a single transition** - the earliest in document
  order - discarding every other enabled transition, including ones in
  completely unrelated parallel states whose exit sets are disjoint
  (`:142-156`). ADR-0002's context calls this out ("conflict resolution
  discarded non-conflicting transitions from parallel regions"). The port's
  regression test is: two parallel regions, one transition enabled in each,
  both survive.
- **`foo.*` did not match `foo`.** v1's `matches_wildcard_prefix?`
  (`../statifier/lib/statifier/event.ex:88-93`) requires *strictly more* event
  tokens than prefix tokens, so `event="foo.*"` matched `foo.bar` but not
  `foo`. `docs/architecture.md:95` names this exact case. v1 also did not
  handle a trailing dot (`"foo."` matched nothing) and only honored a bare `*`
  when it was the entire attribute value, not as one of several descriptors.
  All four are named tests here.

## Desired End State

Two new modules under `lib/statifier/interpreter/`, fully documented, fully
tested, and consumed by nothing yet:

1. `Statifier.Interpreter.NameMatch` - the spec 3.13 descriptor matcher,
   `name_match?/2`, over compile-time token lists.
2. `Statifier.Interpreter.Selection` - `select_transitions/2`,
   `select_eventless_transitions/1`, `remove_conflicting_transitions/2`,
   `compute_exit_set/2`, `get_transition_domain/2`,
   `get_effective_target_states/2`, `find_lcca/2`, and `condition_match/2`.

Verification that the end state is reached: `mix quality` is green with
coverage at or above the floor; `mix adr.check` (the `ADR guard` stage) is clean
without a single naming citation being needed for a ported function;
`test/statifier/interpreter/selection_acceptance_test.exs` asserts every line of
the bead's acceptance criteria a test can decide; and
`docs/observability.md`'s checklist has its "Appendix D query functions
take/return plain values, unfused" box ticked naming this module.

The behavioral end state, stated so a reviewer can check it without the
pseudocode in hand:

- For each atomic state in the configuration in document order, the walk goes
  self-first then outward through `proper_ancestors/2`; the first transition
  (in the state's own document order) whose event descriptor matches and whose
  `cond` passes is enabled for that atomic state, and the walk for that atomic
  state stops there - a child preempts its ancestor.
- The same transition selected by two atomic states appears once, at its first
  selection position.
- Two transitions conflict iff their computed exit sets intersect; on conflict
  the transition from the earlier atomic state wins, except one whose source is
  a descendant of the other's source preempts it.
- A targetless transition has no domain, contributes an empty exit set, and
  therefore conflicts with nothing.
- An `:internal` transition whose source is compound and all of whose effective
  targets are proper descendants of the source has domain = source; every other
  transition has domain = `find_lcca([source | effective_targets])`.

## What We're NOT Doing

- **No exiting or entering states.** `exit_states`, `compute_entry_set`,
  `add_descendant_states_to_enter`, `add_ancestor_states_to_enter`,
  `enter_states`, `in_final_state?`, history *recording*, and `done.state.*`
  are st-wju.4. This bead computes the exit *set*; it never removes a state
  from the configuration.
- **No microstep, no macrostep, no interpreter entry point.** st-wju.6.
- **No executable content.** A selected transition's `content` list is carried
  through untouched; running it is st-wju.5.
- **No trace emission and no effects.** `select_transitions` returns
  transitions, not effects; st-wju.6 owns the `TransitionsSelected` trace point
  (its bead description says so explicitly) and is the only place a
  machine_state and a trace gate meet in the selection path. Emitting here
  would fuse a pure query to an effect list, which constraint 5 forbids.
- **No `cond` evaluation.** Decision 7 fixes the seam's shape; the predicator
  call and the `error.execution` raise are the datamodel bead, st-af3.
- **No `FeatureDetector` change and no conformance ratchet movement.** Every
  feature stays `:unsupported`; no document can be executed until st-wju.6/7,
  so `test/passing_tests.json`'s conformance lists stay empty. See
  "Corpus/Ratchet Notes".
- **No changelog fragment.** Nothing here is reachable from a public API until
  st-wju.7 (`changelog.d/README.md` - most changes need none).
- **No compile-time normalization of `*` and trailing-dot descriptors.**
  Decision 4 keeps that in the matcher at runtime rather than reaching back
  into st-wju.1's compiler; the cost is bounded and the alternative is
  recorded under "Performance Considerations".
- **No rename of `Statifier.Machine`'s helper functions.** Decision 2 keeps
  `lcca/2`, `child_indexes/2`, `proper_ancestors/2` exactly as st-wju.1 named
  them.
- **No `getChildStates`/`getProperAncestors` re-port.** They exist on `Machine`
  under st-wju.1's names and are called as-is; the ADR-0002 diff for a function
  that calls them is unaffected, and st-wju.1's plan explicitly recorded those
  names as "the spec operation it serves" with the `@doc` cross-reference that
  keeps the diff mechanical.

## Implementation Approach

Four phases, in dependency order, each adding code together with its own tests
so no phase leaves an untested module behind to sink the coverage floor:

1. The spec 3.13 matcher - a standalone, string-and-token-level module with no
   dependency on `Machine` or `MachineState` at all.
2. The domain half of the Appendix D block - `find_lcca`,
   `get_effective_target_states`, `get_transition_domain`, `compute_exit_set`.
   These are what `remove_conflicting_transitions` is written against, and they
   are the half st-wju.4 consumes.
3. The selection half - `condition_match`, the two `select_*` walks, and
   `remove_conflicting_transitions`.
4. The acceptance test, the documentation tick, and the cross-bead notes.

Phases 2 and 3 both touch `Statifier.Interpreter.Selection`; they are split
because each half is independently gate-verifiable with its own tests and the
domain half is the one another bead consumes, so landing it first shortens
st-wju.4's dependency. They do not parallelize across worktrees, which is fine:
`docs/workflow.md`'s parallelism is across beads, not within one.

Every design question is settled below before any code is written, because
st-wju.4 and st-wju.6 both read these signatures.

## Decisions

**Decision 1 - the modules and their paths.**
`Statifier.Interpreter.NameMatch` in `lib/statifier/interpreter/name_match.ex`;
`Statifier.Interpreter.Selection` in `lib/statifier/interpreter/selection.ex`.

The directory is not a free choice: `Mix.Statifier.AdrGuard`'s
`@interpreter_pattern` is `~r{^lib/statifier/interpreter}`
(`lib/mix/statifier/adr_guard.ex:50`), so ADR-0002's naming check only sees
interpreter code that lives there. Putting the port anywhere else would
silently disable a gate stage that exists for this exact code.

One module per bead within that namespace (`Selection` here, st-wju.4's exit
and entry sets next, st-wju.5's content runner, st-wju.6's `Statifier.Interpreter`
entry point) keeps each bead's diff to one file, which is what makes the epic's
worktrees mergeable. The matcher is a second module rather than private
functions in `Selection` because spec 3.13 is not Appendix D - it is a
string-level rule with its own six-case acceptance criterion, and it is the
one piece here that needs neither a `Machine` nor a `MachineState` to test.

**Decision 2 - `find_lcca` is a `defdelegate` to `Statifier.Machine.lcca/2`;
nothing is renamed and nothing is reimplemented.**

The bead asks for a spec-named `find_lcca(state_list)`, and
`Statifier.Machine.lcca/2` already is that port, body for body
(`lib/statifier/machine.ex:224-231`). Three options were weighed:

| Option | Verdict |
|---|---|
| Rename `Machine.lcca/2` to `Machine.find_lcca/2` | Rejected. st-wju.1's plan deliberately named `Machine`'s query helpers after *the spec operation they serve* rather than after the spec function - `lcca/2` for `findLCCA`, `child_indexes/2` for `getChildStates`, `proper_ancestors/2` for `getProperAncestors` - and made that a manual-verification item of its own Phase 2. Renaming one of the three breaks a convention a landed plan chose, and leaves the spec-named port sitting in a non-interpreter module where `mix adr.check` does not even look. |
| Reimplement `find_lcca` in `Selection` | Rejected outright. Two implementations of one function is precisely the divergence this codebase's "make invalid states unrepresentable" principle exists to prevent, and `Machine.lcca/2`'s body already handles the ancestor-target subtlety its `@doc` documents. |
| **`defdelegate find_lcca(machine, indexes), to: Statifier.Machine, as: :lcca`** | **Chosen.** One implementation, the spec name present at the interpreter's port surface where ADR-0002 and `mix adr.check` want it, `Machine`'s helper convention intact, and a `@doc` on the delegate that names the pseudocode block and points at the body. `defdelegate` is also the promotion path `docs/observability.md:122` already blesses for exactly this situation. |

Cost: one line, plus a cross-reference line added to `Machine.lcca/2`'s `@doc`
naming `Selection.find_lcca/2` as its spec-named entry point, so a reader
arriving from either direction finds the other. The delegate's argument is the
`Machine`, not the `MachineState` - `findLCCA` is pure topology and needs
neither the configuration nor history.

**Decision 3 - every query takes `machine_state` (or `machine`) first, and
that is a mechanical deviation with a comment.** The pseudocode reads
`configuration` and `historyValue` as globals. Reifying them onto
`%MachineState{}` is the deviation `docs/observability.md:44-45` sanctions and
st-wju.2 already took; here it shows up as an extra first parameter on
`select_transitions/2`, `select_eventless_transitions/1`,
`remove_conflicting_transitions/2`, `compute_exit_set/2`,
`get_transition_domain/2`, and `get_effective_target_states/2`. It also matches
this project's own convention (CLAUDE.md: "functions taking a state/session put
it as the first argument"). Each function's `@doc` says which globals its first
argument stands in for; the module's own moduledoc states the rule once so the
six `@doc`s do not each re-argue it.

`find_lcca/2` and `name_match?/2` take no machine_state: neither reads a global.

**Decision 4 - the 3.13 matcher normalizes descriptor tokens, and one rule
covers `*`, `foo.*`, and `foo.`.**

`Machine.Transition.events` is `[[String.t()]]` - each descriptor already
dot-split (`transition.ex:28-34`). Spec 3.13 then says a descriptor matches an
event name iff the descriptor's tokens are a prefix of the event's tokens *on
token boundaries*, that a trailing `.*` is equivalent to the descriptor without
it, and that `*` alone matches every event. All three fall out of one
normalization plus a prefix test:

```
normalize: drop a trailing "*" token and a trailing "" token
  ["*"]            -> []            (bare * -> empty prefix -> matches all)
  ["foo", "*"]     -> ["foo"]       (foo.* matches foo AND foo.bar)
  ["foo", ""]      -> ["foo"]       (trailing dot, spec-equivalent to foo)
  ["error"]        -> ["error"]     (matches error.execution, not errors.execution)

match: normalized == Enum.take(event_tokens, length(normalized))
```

The event name is split on `"."` **once per selection round**, not once per
transition: `select_transitions/2` tokenizes `event.name` and passes the token
list down. This is a mechanical hoist, not a semantic change - `nameMatch`'s
result is identical - and it is why `name_match?/2`'s signature is
`(descriptors :: [[String.t()]], event_tokens :: [String.t()])` rather than the
pseudocode's `(descriptorList, eventName)`. Both facts get an inline comment.

A `*` that is *not* the last token (`"foo.*.bar"`) is matched literally - spec
3.13 defines the wildcard only as a trailing element, so there is nothing to
port for the interior case, and inventing a rule would be a semantic deviation.
The `@doc` says so.

Empty `events` (`[]`) means an eventless transition and is never handed to the
matcher: `select_transitions/2` considers only transitions with `events != []`,
`select_eventless_transitions/1` only those with `events == []`. That is the
pseudocode's `t.event` / `!t.event` test, spelled for a pre-split list.

**Decision 5 - `get_effective_target_states` is ported here, in full, including
history resolution.** Appendix D's `getTransitionDomain` calls
`getEffectiveTargetStates`, which resolves a `:history` target to its recorded
value or, when nothing is recorded, to its default transition's targets. The
domain math cannot be ported without it, so this bead ports it rather than
stubbing it - st-wju.4's acceptance criteria already anticipate this
("getEffectiveTargetStates ported if the domain/history math needs it"), and
Phase 4 records the resolved boundary on that bead.

Both branches are testable today even though st-wju.4 writes the history
values: `history_values` is a plain map on `%MachineState{}` that a test seeds
by hand, and `Machine.State.history_default` is populated by st-wju.1. So Phase
2 tests the recorded branch (seeded map) and the unrecorded branch (empty map,
falls through to the default transition's targets) with no dependency on
st-wju.4.

Recursion: the unrecorded branch recurses through the default transition's own
targets, which the pseudocode does too (`getEffectiveTargetStates(s.transition)`).
A history default targeting another history state is pathological but
representable; the port recurses as written and the `@doc` notes it.

**Decision 6 - `compute_exit_set/2` returns a `MapSet` of indexes; ordering is
the caller's job.** The pseudocode's `OrderedSet` serves two consumers with
different needs: `remove_conflicting_transitions` wants set intersection, and
st-wju.4's `exit_states` wants exit order. A `MapSet.t(non_neg_integer())`
gives the first directly and the second through the `Machine.exit_order/2` that
already exists for it (`machine.ex:251`). Returning a list in exit order would
force the conflict filter to sort-then-intersect on every pair, which is both
slower and further from the pseudocode's own set semantics. The `@doc` states
that st-wju.4 pipes the result through `Machine.exit_order/2` rather than
expecting order here, and Phase 4 records it on st-wju.4.

Two literal-port details that must survive review:

- The guard is `if t.target` - i.e. `targets == []`, the *written* targets, not
  the effective ones. A transition with written targets whose effective target
  set resolves empty still enters the loop; its domain is then `nil` and it
  contributes nothing. The port keeps the pseudocode's guard and handles the
  `nil` domain explicitly with a comment, rather than "simplifying" the two
  tests into one.
- `descendant?/3` is proper, so the domain itself is never in the exit set.
  That is the whole reason `Machine.descendant?/3`'s strictness was chosen
  (`machine.ex:117-137`); a self-inclusive test here would exit the domain and
  break every internal transition.

**Decision 7 - `condition_match/2` is the one `cond` seam, and an error
disables the transition without raising.**

```elixir
@spec condition_match(machine_state :: MachineState.t(), transition :: Transition.t()) ::
        {:ok, boolean()} | {:error, term()}
def condition_match(%MachineState{}, %Transition{cond: nil}), do: {:ok, true}
def condition_match(%MachineState{}, %Transition{}), do: {:error, {:unsupported, :cond}}
```

A written `cond` returns an error rather than `{:ok, true}` because silently
treating an unevaluated condition as satisfied is the "rescue-to-default at a
leaf" failure `docs/architecture.md:28-33` names as a v1 defect - a document
whose `cond` we cannot yet evaluate must not quietly behave as if it were
`true`. It is unreachable from the corpus (`FeatureDetector` flunks any
`cond`-bearing document, `feature_detector.ex:53`,`:133`) and reachable from an
internal test, which is what makes the seam testable now.

The selection walk treats `{:ok, true}` as enabling and both `{:ok, false}` and
`{:error, _}` as not-enabling, with an inline comment citing st-af3 for the
`error.execution` raise that will accompany the error case. st-af3 replaces
this function's *body* and adds the raise; it changes no signature and no
selection logic, which is the bead's own requirement.

**Decision 8 - `select_transitions/2` and `select_eventless_transitions/1`
return `{machine_state, [Transition.t()]}`.** The inner queries
(`remove_conflicting_transitions/2`, `compute_exit_set/2`,
`get_transition_domain/2`, `get_effective_target_states/2`, `find_lcca/2`,
`condition_match/2`, `name_match?/2`) all return plain values with no
machine_state, because none of them can raise.

The two entry points thread the machine_state because st-af3 must enqueue
`error.execution` when a `cond` fails, and the bead requires that st-af3
"replaces the stub, not the selection logic". With a bare-list return, st-af3
would have to change both entry points' return types and every caller in
st-wju.6 - which is changing the selection logic. Threading it now costs one
tuple and matches the `{machine_state, [effect]}` shape st-wju.6 already
returns from `microstep/1`.

In this bead the machine_state comes back unchanged from both functions, and a
Phase 3 test asserts exactly that (so the day it stops being true, the test
that changes is a deliberate st-af3 edit). Constraint 5's REPL story is
unharmed: `{_ms, transitions} = Selection.select_transitions(ms, event)` still
answers "what would happen if event X arrived" without stepping.

Reversible: if a reviewer prefers a bare list, deleting the tuple is a one-line
change per function plus the assertion above, and st-af3 inherits the problem.

**Decision 9 - the loop decomposition, and how it stays diffable.** Credo caps
cyclomatic complexity at 9 and nesting at 2 (`.credo.exs:153`,`:169`), so
Appendix D's two nested loops become named private helpers. The decomposition
is fixed here so it is not re-invented per function:

- The selection walk's labelled `break loop` becomes `Enum.find_value/2` over
  `[state | Machine.proper_ancestors(machine, state)]`, returning the first
  state that yields an enabled transition. "Stop at the first hit, walking
  self-first then outward" is exactly the labelled break's meaning.
- The per-state inner loop becomes a private
  `first_matching_transition/4` returning `Transition.t() | nil` -
  `Enum.find/2` over the state's `transitions` mapped through
  `Machine.transition/2`, in the order stored (document order).
- The atomic-state outer loop becomes `Enum.flat_map/2` over
  `machine_state |> MachineState.active_leaf_states() |>
  Machine.document_order(...)`, wrapping each atomic state's `find_value`
  result as `[]` or `[transition]` so there is something to flatten - the
  per-state walk yields `Transition.t() | nil`, and `flat_map` needs an
  enumerable per element. Then a dedupe by `t_index` preserving first
  occurrence (Decision 10).
- `remove_conflicting_transitions`'s outer loop becomes `Enum.reduce/3` over
  the enabled list with the accumulator being the pseudocode's
  `filteredTransitions` (a list in insertion order), and its inner loop plus
  `t1Preempted` / `transitionsToRemove` becomes a private
  `resolve_against_filtered/3` returning `{:preempted, filtered}` or
  `{:keep, filtered_without_removed}`. The pseudocode's `break` on preemption
  is `Enum.reduce_while/3`.

Each helper carries a one-line comment naming the pseudocode lines it covers,
so "diff the function against the pseudocode" still works at the helper
boundary. None of these helper names is flagged by `mix adr.check`; the
implementer runs the stage and, if a future helper name does trip it, adds the
ADR-citing comment the guard's escape hatch expects rather than renaming to
something less clear.

**Decision 10 - the enabled set is deduplicated by `t_index`, preserving first
occurrence.** Appendix D's `enabledTransitions` is an `OrderedSet`, and its
`toList` "sorts the transitions in the order of the states that selected them".
One transition can be selected by two atomic states - two parallel regions
whose atomic states both walk up to a common ancestor's transition - and a
plain Elixir list would hold it twice. The duplicate would in fact be dropped
by the conflict filter (identical exit sets, neither source a descendant of the
other, so the second is preempted), but relying on that is relying on a
coincidence rather than porting the data structure. The port dedupes on
`t_index` at the end of the walk, keeping the first occurrence, and a Phase 3
test asserts the shared-ancestor-transition case yields exactly one entry.

**Decision 11 - the returned element type is `Transition.t()`, not `t_index`.**
Every consumer (`remove_conflicting_transitions` here, `exit_states` and
`compute_entry_set` in st-wju.4, the content runner in st-wju.5) immediately
needs `source`, `targets`, `type`, or `content`, and the pseudocode's
`OrderedSet` holds transitions. `t_index` is a field on the struct, so
st-wju.6's `TransitionsSelected` trace effect maps to indexes with
`Enum.map(transitions, & &1.t_index)` - the constraint-3 rule that *trace
effects* carry indexes (`docs/observability.md:73-74`) is about what crosses the
effect boundary, not about what a pure query returns internally.

## Testing Strategy

### Unit Tests:

- `test/statifier/interpreter/name_match_test.exs` - the spec 3.13 matrix over
  literal token lists: full name, boundary prefix, non-boundary non-match,
  trailing `.*` matching both the bare prefix and a longer name, trailing dot,
  bare `*`, multi-descriptor including a `*` alongside a specific descriptor,
  and a descriptor longer than the event name.
- `test/statifier/interpreter/selection_domain_test.exs` - effective target
  states (plain, recorded history, unrecorded history, multi-target); the
  domain's five branches including the internal-versus-external difference on
  one source/target pair; exit sets including targetless, internal, and
  disjoint parallel regions.
- `test/statifier/interpreter/selection_test.exs` - the selection walk (self
  first, child preempts ancestor, sibling document order, eventless versus
  event-bearing, the `cond` seam, no match, machine_state unchanged, shared
  ancestor transition deduped) and conflict resolution (parallel regions keep
  non-conflicting transitions, descendant preempts ancestor, document-order
  priority, targetless conflicts with nothing, a preempted transition removes
  nothing).
- `test/statifier/interpreter/selection_acceptance_test.exs` - the bead's
  criteria, driven from XML through the real pipeline, plus the
  standalone-callability assertion.

Key edge cases, each its own named test: an empty configuration selects nothing;
a configuration whose only atomic state has no transitions; a transition whose
source is the `:scxml` root; a self-transition on a compound state (external
type - it exits and re-enters); a history target whose recorded value is an
empty `MapSet` (distinct from no key at all, per st-wju.2's Decision 9); and a
document with two parallel states where a transition leaves one and another
stays inside the other, which is the precise shape v1 collapsed.

Fixtures follow `test/statifier/machine_test.exs:10-71`: a triple-quoted
heredoc at 4-space base indentation through `Parser -> Lowering -> Validator ->
Compiler`, preceded by a hand-drawn depth-first index comment, with a pinned
`@indexes` map and `idx/1` so assertions read in state ids. No `%Machine{}` or
`%Machine.Transition{}` literals - a hand-built Machine can drift from what the
compiler actually emits. `%MachineState{}` values *are* built by hand
(`MachineState.new/2` then a configuration and, where needed, `history_values`
set directly), because nothing can enter states until st-wju.4; that is the
deliberate exception and each test says which configuration it is asserting
against.

Every test asserting `lib/` behavior carries its sabotage line per
`docs/testing.md:78-134`. The mutations named in the phases above are the
intended ones; an implementer who finds a listed mutation does not redden the
test must fix the test rather than weaken the mutation. Two mutations are worth
watching for the "one mutation reddens twenty tests" signal
`docs/testing.md:114-117` describes: breaking `Machine.descendant?/3` and
breaking the atomic-state document-order sort will each redden much of the
domain and selection suites respectively, which is expected - those are genuine
shared foundations, not twenty doors onto one assertion.

## Corpus/Ratchet Notes

This bead cannot move conformance results: no document can be executed until
st-wju.6, and the corpus suites stay excluded and flunking on `FeatureDetector`
until st-wju.7 flips the Phase 1 features. So:

- No `test/passing_tests.json` change in any phase. The conformance lists stay
  empty; the internal-test glob picks up the new test files automatically,
  which is why `mix test.regression` is a listed criterion in Phase 4 even
  though nothing conformance-related moved.
- No `mix test.baseline add` in any phase. Running `mix test.baseline` here
  would report nothing newly passing, at the cost of a full conformance run.
- **No `test/support/feature_detector.ex` change.** `conditional_transitions`,
  `wildcard_events`, `internal_transitions`, `targetless_transitions`, and
  `eventless_transitions` all stay `:unsupported`. Flipping a feature claims
  the engine *runs* documents using it, which will not be true until st-wju.7;
  flipping one early would let a corpus test masquerade as passing, which is
  the one thing the flunk-don't-skip rule exists to prevent
  (`docs/testing.md:216-219`).
- No corpus regeneration, no exclusion-manifest edit.
- No gate-guard ledger entry (`docs/quality-gate-changes.md`): no phase touches
  `.quality.exs`, `.credo.exs`, `coveralls.json`, `.sobelow-conf`, a
  gate-relevant `mix.exs` line, adds a `@tag :skip`, or shrinks
  `test/passing_tests.json`. An implementer who wants one has gone outside the
  phase's scope.

## Performance Considerations

- **`compute_exit_set/2` is called O(n^2) times inside
  `remove_conflicting_transitions/2`** - once per `(t1, t2)` pair, as the
  pseudocode writes it. `n` is the number of transitions enabled in one
  microstep, which is bounded by the number of atomic states and is single
  digits for essentially every real document. Memoizing per `t_index` would be
  a fusion the pseudocode does not have, and ADR-0002 makes the literal port the
  default; if a corpus document ever makes this measurable, the memo is a local
  change inside one function with a mechanical-reason comment. Recorded here so
  the decision is visible rather than rediscovered.
- **Descriptor normalization runs per (transition, event) pair** rather than at
  compile time (Decision 4). Each descriptor is a two- or three-element list and
  the normalization is a single tail inspection, so this is cheaper than the
  `Machine` lookup that precedes it. Hoisting it into st-wju.1's compiler is the
  available optimization; it is not taken because it would make
  `Transition.events` no longer a faithful record of what the document wrote,
  which the trace and diagnostics story leans on.
- **The event name is tokenized once per selection round**, not once per
  transition (Decision 4) - the one hoist that is taken, because it is O(states
  x transitions) otherwise and costs nothing in fidelity.
- **The configuration is a `MapSet` of integers and every topology test is an
  integer range comparison** (ADR-0005), so exit sets and domain tests allocate
  nothing beyond the result set.
- `MachineState.active_leaf_states/1` is documented as an O(n) API-boundary
  view, not a per-microstep path (`machine_state.ex:180-182`). The selection
  walk calls it once per selection round, which is the pseudocode's own
  `configuration.toList().filter(isAtomicState)` and is exactly one pass; this
  is consistent with that `@doc` rather than in tension with it, and the
  moduledoc says so.

## Appendix D Deviations

Per ADR-0002 and `.claude/wurk/plan.md`'s Appendix D rule, these are the only
deviations this bead makes. Every one is mechanical, and every one carries an
inline comment at its site:

1. **`machine_state` is the first argument of every query that reads a global**
   (Decision 3). The pseudocode reads `configuration` and `historyValue` as
   globals; ADR-0012 constraint 1 reifies them onto the struct. Semantics
   unchanged.
2. **`select_transitions/2` and `select_eventless_transitions/1` return
   `{machine_state, transitions}`** (Decision 8). The extra element exists so
   st-af3 can enqueue `error.execution` from a failed `cond` without changing
   the selection logic. In this bead the machine_state is returned unchanged
   and a test asserts it. No transition's selection depends on it.
3. **`computeExitSet` returns a `MapSet` rather than an `OrderedSet`**
   (Decision 6). Both consumers are served: intersection here, and
   `Machine.exit_order/2` for st-wju.4. Membership is identical.
4. **`nameMatch` takes pre-split token lists** (Decision 4). st-wju.1's
   compiler already dot-split every descriptor; the event name is split once
   per selection round. Identical results, no runtime string splitting.
5. **The two nested loops are decomposed into named private helpers**
   (Decision 9), and `OrderedSet` is an explicit dedupe on `t_index` preserving
   first occurrence (Decision 10). Elixir has neither a labelled break nor an
   ordered set; both are shape, and each helper names the pseudocode lines it
   covers.

`findLCCA` is *not* a deviation: `Statifier.Machine.lcca/2` is the port, and
`Selection.find_lcca/2` is a `defdelegate` giving it the spec name at the
interpreter's surface (Decision 2). One implementation, two names, no drift.

Nothing here alters which transitions are selected, in what order, or what
their domains and exit sets are.

## Open Questions

None outstanding. Every question the bead raised is settled above as a numbered
Decision. Three are assumptions a human may overturn without invalidating the
phase structure, listed here so a reviewer can find them quickly:

1. **Decision 2** - `find_lcca/2` is a `defdelegate` to `Machine.lcca/2` rather
   than a rename of `Machine.lcca/2` to `Machine.find_lcca/2`. The bead
   explicitly asked for this call to be made and recorded. If a reviewer
   prefers the rename, it is mechanical today (`Machine.lcca/2` has no callers
   in `lib/`, only `test/statifier/machine_test.exs:213-247`) and gets more
   expensive with every later bead - but it also reverses a naming convention
   st-wju.1's plan chose deliberately for all three of `lcca/2`,
   `child_indexes/2`, and `proper_ancestors/2`, so reversing it for one of them
   alone is the part to think about.
2. **Decision 8** - the two `select_*` entry points return
   `{machine_state, transitions}` and the machine_state is unchanged in this
   bead. The alternative (a bare list, and st-af3 widens it later) is one line
   simpler now and moves a signature change into a bead that will already have
   two callers in st-wju.6.
3. **Decision 7** - a written `cond` returns `{:error, {:unsupported, :cond}}`
   rather than `{:ok, true}`. The bead's wording ("stubbed to `{:ok, true}` for
   nil cond") is compatible with either reading; this plan chose the error
   because an unevaluated condition silently behaving as `true` is the
   rescue-to-default failure `docs/architecture.md:28-33` names. Nothing in the
   corpus can reach either branch until st-af3.
