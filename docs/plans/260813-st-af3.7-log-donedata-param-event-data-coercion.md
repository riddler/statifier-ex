# Log, donedata, `<param>`, and one event-data coercion function

## Overview

st-af3.7 finishes the two evaluation sites the codebase deliberately left
unevaluated, adds `<param>` under `<donedata>`, and discharges
`docs/datamodel.md`'s standing commitment to a single event-data
normalization function. Bead: st-af3.7.

Four things land:

1. `Log.value/1` evaluates a `{:compiled, ...}` expr against the block's
   already-built `datamodel_context`; a failure returns `{:error, reason}`
   to the block runner, which raises `error.execution`.
2. Both donedata call sites evaluate the `{:compiled, ...}` arm -
   `raise_completion_events/2`'s `done.state.*` data and
   `exit_interpreter/1`'s `Effect.Done` / `Trace.Done` donedata.
3. `<param>` under `<donedata>` lowers (`name` + `expr`/`location`),
   compiles, evaluates at done time, and merges into the done event's data
   map, shaped for `<send>`/`<invoke>` reuse in the epic's Phase 4 (st-cmq).
4. `Statifier.EventData.coerce/1` - one function, defined rules, used by
   `<param>` and `<content>` here and extended (not reinvented) by
   namelist / `<send>` / `<invoke>` later.

The research document
`docs/research/260813-st-af3.7-log-donedata-param-event-data-coercion.md`
left eight open questions. No human was available to resolve them, so each
is decided below under "Decisions" with the normative clause quoted and the
tension, where one exists, stated rather than hidden.

## Current State Analysis

Everything this bead needs to call already exists.

- `Statifier.Evaluator.context/1` (`lib/statifier/evaluator.ex:98-103`) and
  `Statifier.Evaluator.evaluate/2` (`lib/statifier/evaluator.ex:123-133`)
  are the single evaluation seam. Five sites already use it (`<data>`,
  `<assign>`, `<if>`, `<foreach>`, transition `cond`).
- `Statifier.Interpreter.Content` (`lib/statifier/interpreter/content.ex`)
  already carries the fatal `{:error, reason}` channel, the non-fatal
  `pending_errors` channel, and the one `raise_execution_error/4` both
  converge on (`content.ex:229-239`). The `ExecutableContent` protocol's
  `result/0` (`lib/statifier/executable_content.ex:73-76`) already admits
  the error shapes; `Log`'s `defimpl` simply never returns one.
- `Log.value/1` (`lib/statifier/machine/content/log.ex:62-65`) returns `nil`
  for the compiled arm, with a comment saying so.
- `ExitEntry.static_donedata/2`
  (`lib/statifier/interpreter/exit_entry.ex:869-878`) does the same, and is
  `def` rather than `defp` because `Interpreter.exit_interpreter/1`
  (`lib/statifier/interpreter.ex:676-719`) is its second caller.
- The two donedata sites differ structurally.
  `raise_parent_completion/3` (`exit_entry.ex:782-807`) threads a
  `MachineState` and already calls `MachineState.raise_platform/4`.
  `exit_interpreter/1` folds donedata inside an `Enum.reduce` over the exit
  set that also threads a `MachineState` (`ms`), but the event loop has
  already stopped and `status: :done` is set on the next line, so nothing
  ever dequeues from there.
- `<param>` is genuinely absent: no `"param"` key in `Lowering`'s
  `@dispatch` (`lib/statifier/lowering.ex:53-74`), no `Document.Param`, no
  `Machine.Param`, no `place/3` clause. `Document.Donedata` and
  `Machine.Donedata` each have a single content slot, not a list.
- No shared coercion function exists. The nearest analogue is
  `Statifier.Compiler.Expressions.inline_value/1`
  (`lib/statifier/compiler/expressions.ex:119-131`), a parse-or-string
  ladder for `<data>` inline content that runs at **compile** time.
- `Evaluator.evaluate/2`'s `{:static, value}` arm returns `value` untouched
  by design (st-af3.1), so `<content>21</content>` is the string `"21"`
  today, while W3C test529 requires the integer `21`.

## Desired End State

- A `<log expr="...">` in any executed block logs the evaluated value; a
  failed evaluation emits no `{:log, _}` effect, halts the block, and
  produces one `error.execution` naming the `<log>`'s `c_index`.
- A `<final>` with `<donedata><content expr="..."/>` raises
  `done.state.<parent>` whose `data` is the evaluated value; with
  `<donedata><content>21</content>` the `data` is the integer `21`; with a
  failing `expr` the `data` is `nil` and one `error.execution` is on the
  internal queue.
- A `<final>` with one or more `<param>` children raises
  `done.state.<parent>` whose `data` is a string-keyed map of the params
  that evaluated successfully; each failure contributes one
  `error.execution` and no key; an all-failed or empty map is `nil`, not
  `%{}`.
- The same values reach `Effect.Done` / `Trace.Done` at
  `exit_interpreter/1`, with evaluation errors enqueued on the internal
  queue of the returned (terminal) `MachineState`.
- `Statifier.EventData.coerce/1` exists as the single documented
  normalization function, and `docs/datamodel.md` names it.
- Verification: full `mix quality` green on each phase, plus
  `mix test.regression` green (the ratchet's 87 SCION + 10 W3C files
  contain `<log expr>` and are the widest blast radius in this bead).

### Key Discoveries

- `lib/statifier/interpreter/content.ex:150-158` already builds
  `datamodel_context` once per block, so `<log>` needs no new context
  construction - only `Evaluator.evaluate(context.datamodel_context, expr)`.
- Neither donedata site sits inside an executable-content block
  (`<donedata>` payload is not executable content -
  `lib/statifier/machine/content.ex:25-28`), so both must build their own
  context via `Evaluator.context/1` from the `MachineState` they hold.
- `exit_interpreter/1`'s reduce already threads `ms`, so enqueuing an
  `error.execution` there is mechanically free (`interpreter.ex:684-706`).
- `Machine.Donedata.expr`'s `{:static, _}` arm can **only** come from
  `<content>`'s text body (`Compiler.build_content_expr/2`,
  `lib/statifier/compiler.ex:1041-1047`), never from an attribute. That is
  what makes "static means raw document text" a safe local rule.
- Three sibling beads already own work this bead could otherwise absorb:
  **st-oq4** (flip `conditional_transitions`), **st-af3.8** (split the
  `send_content_elements` / `send_param_elements` detector regexes by parent
  and ratchet), **st-hyx** (reject `<donedata>` carrying both `<content>`
  and `<param>` - whose own description says it "should land with"
  `<param>` support).
- **Verified against a live predicator 5.0 during planning**, not assumed:
  against `Predicator.Context.new(%{}, on_unbound: :error)`,
  `compile_with_spans/1` + `evaluate/2` give `"21" -> 21`, `"true" -> true`,
  `"\"hi\"" -> "hi"`, `"[1,2]" -> [1, 2]`, while `"foo"` errors
  (`UndefinedVariableError`) and `"a b"` fails to parse - so the literal-parse
  rung falls through to the string exactly where Decision 2 needs it to.
  A datamodel of `%{"_event" => %{"data" => %{"Var1" => 1}}}` answers
  `_event.data["Var1"] == 1` true (string keys work), and
  `%{"_event" => %{"data" => nil}}` answers `_event.data === undefined` true
  (predicator's deep `nil -> :undefined` normalization), which is what makes
  Decision 1's `nil` donedata satisfy `conf:emptyEventData`.
- ADR-0002 (literal Appendix D port), ADR-0003 (effects out, only the block
  runner raises), ADR-0004 (predicator is the datamodel), ADR-0005 (interned
  indices; `<param>`'s `name` is a document-facing string key, not an index),
  ADR-0012 (a `MachineState` is a complete inspectable position),
  ADR-0014 item 2 (spans on evaluation errors) all bound this work and are
  cited rather than re-argued.

## Decisions

Each is one of the research document's eight open questions, resolved.

### Decision 1: a failed `<content expr>` under `<donedata>` yields no data

**Decided: the done event carries `nil` data (predicator `undefined`), plus
one `error.execution`. Not the empty string.**

The tension is real and is recorded here rather than papered over. Spec 5.6
says, of `<content>` generally:

> When the SCXML Processor evaluates the `<content>` element, if the 'expr'
> value expression is present, the Processor MUST evaluate it and use the
> result as the output of the `<content>` element. If the evaluation of
> 'expr' produces an error, the Processor MUST place error.execution in the
> internal event queue and use the empty string as the value of the
> `<content>` element.

Read literally, a failed `<content expr>` under `<donedata>` would make
`_event.data` the empty string. Three things outweigh that reading:

1. **A mandatory W3C conformance test asserts otherwise.**
   `test/scxml_tests/mandatory/content/test528_test.exs` is exactly this
   document (`<content expr="return"/>` under `<donedata>`), and its guard
   transition reads `cond="_event.data === undefined"`. That spelling is
   the W3C `conf:emptyEventData` macro, recorded as a deliberate emission
   choice in `tools/corpus/scxml_w3/exclusions.exs:8-13`, not a rewrite
   artifact. Following 5.6's letter reddens a mandatory test forever.
2. **Spec 5.10.1 states the opposite outcome for the event's `data` field**:
   "If the conversion is not possible, the Processor MUST leave the field
   blank and MUST place an error 'error.execution' in the internal event
   queue." That is a normative clause about `data` specifically, where 5.6
   is a normative clause about `<content>`'s *output* generically - and
   `<content>`'s primary context in 5.6 is a payload passed to an external
   service (`<send>`/`<invoke>`), where an output value is required and
   `""` is the safe one.
3. **5.5 routes through B.2.8.1, which has no empty-string rung.** B.2.6:
   "When `<content>` is a child of `<donedata>`, the Processor MUST
   interpret its value as defined in B.2.8.1 _event.data."

The deviation from 5.6's letter is deliberate, is scoped to the
`<donedata>` context only, and gets an inline comment at the fold site
citing 5.6 against 5.10.1 and test528. When `<send>`'s `<content>` lands in
the epic's Phase 4 (st-cmq), 5.6's empty-string rule applies there unchanged - the two contexts
are allowed to differ because 5.6 itself says "the use of the `<content>`
element depends on the context in which it occurs".

### Decision 2: which rungs of B.2.8.1 the one function implements, and when it runs

**Decided: three rungs, at event time, in `Statifier.EventData.coerce/1`.**

B.2.8.1's ladder is: indicated format -> key-value pairs -> JSON -> XML DOM
-> space-normalized string literal. The rungs this project implements:

| B.2.8.1 rung | Implemented? | Reason |
|---|---|---|
| Indicated format ("SHOULD") | No | No content-type channel exists; nothing delivers one until the BasicHTTP processor (epic Phase 4+, st-cmq). It is a SHOULD, not a MUST. |
| Key-value pairs ("MUST") | **Yes** | `<param>` "consists unambiguously of key-value pairs" (B.2.8.1's own parenthetical). Produces a string-keyed map. |
| JSON ("MUST, if the Processor supports JSON") | Substituted | The clause is conditional on JSON support; this engine's value space is predicator's (ADR-0004), not ECMAScript's. The predicator literal grammar covers the same ground for this corpus (numbers, booleans, strings, lists, maps), so the rung is implemented as a **predicator literal-parse** rung rather than a JSON parse. No new dependency, and no second value space. |
| XML DOM ("MUST, if interpretable as XML") | No | `Statifier.Document.Content`'s moduledoc already settled this: preserving non-text markup would put a DOM subtree inside a Document struct, crossing the layer boundary the rewrite is organized around, and lowering errors on an element child inside `<content>` instead. Nothing in either corpus needs it. |
| Space-normalized string literal ("MUST") | **Yes** | The fallback. |

**Event time, not compile time.** A `<param expr>`'s value is only known at
event time, so the key-value rung cannot be a compile-time fold; splitting
the ladder across two times would produce exactly the two normalization
functions `docs/datamodel.md` forbids. The compiler therefore keeps
producing `{:static, raw_text}` for `<content>`'s text body unchanged, and
the interpreter coerces at the raise site. The re-parse cost per done event
is negligible and st-sdh already owns the "measure the evaluation seam"
question.

`Expressions.inline_value/1` stays exactly as it is and is **not** merged
into the new function. It implements **B.2.1** (datamodel initialization
from `<data>` inline content), a different normative clause from B.2.8.1
(`_event.data` population), and it runs at compile time because a `<data>`
body is static by construction. Merging them would either drag `<data>`
binding into this bead's blast radius or force `<param>` to be folded at
compile time, which is impossible. A one-line comment on `inline_value/1`
points at `Statifier.EventData` and says why the two ladders coexist.

The shape - one function, three tagged inputs, so `<send>`, `<invoke>` and
`namelist` extend rather than invent:

```elixir
@type input ::
        {:value, term()}
        | {:text, String.t()}
        | {:params, [{String.t(), term()}]}

@spec coerce(input()) :: term() | nil
```

- `{:value, v}` -> `v`, unchanged. An evaluated expression already produced
  a legal data value (spec 5.9.3), so re-running the text ladder over it
  would be a second interpretation of a value that was never text. This is
  the rung that keeps `<content expr="'21'"/>` a string while
  `<content>21</content>` is an integer.
- `{:text, t}` -> trim `t`; if the trimmed text compiles under predicator
  **and** evaluates against an empty `Predicator.Context.new(%{},
  on_unbound: :error)` context, that value; otherwise the space-normalized
  string (trim, then collapse internal whitespace runs to a single space,
  per B.2.8.1's "space-normalized string literal"). Whitespace-only or
  empty text -> `nil`, matching `Checks.Content`'s existing rule that
  whitespace-only `<content>` text "is source formatting, not a payload".
- `{:params, pairs}` -> a `%{String.t() => term()}` map folded in document
  order; an empty result -> `nil` (see Decision 5).

The empty-context trick is the same one `inline_value/1` documents: `foo`
compiles to an identifier load that errors against a context holding
nothing, so it falls through to the string `"foo"` rather than silently
becoming a datamodel read.

### Decision 3: `{:static, v}` from `<content>` text does go through coercion

**Decided: yes, via the `{:text, _}` input.**

W3C test529 (`<content>21</content>` with `cond="_event.data == 21"`) is
mandatory and requires the integer. B.2.6 requires `<donedata>`'s
`<content>` to be interpreted per B.2.8.1, whose bottom rungs are exactly a
parse-then-string ladder. `Evaluator.evaluate/2`'s `{:static, v}` bypass is
untouched - it is still correct that a static value never passes through
predicator's *value normalization*; the coercion happens **after**
`evaluate/2` returns, at the donedata fold, and only for the `<content>`
text arm. `Machine.Donedata.expr`'s `{:static, _}` can only originate from
`<content>`'s text body (`Compiler.build_content_expr/2`), so the fold can
tell text from value by the arm alone, with no new tagging.

Tests that change, and why each is a fix rather than a weakened check:

| Test | Today | After | Why it is a fix |
|---|---|---|---|
| `test/statifier/interpreter/termination_test.exs:127-148` - "static donedata rides the terminal effect" | `%Effect.Done{donedata: "42"}` | `%Effect.Done{donedata: 42}` | The assertion becomes strictly *more* specific (an integer literal, which `"42"` would not match). B.2.6 + B.2.8.1 require the interpretation; the string was the un-coerced intermediate. |
| `test/statifier/interpreter/exit_entry_enter_test.exs:424-437` - "a final with static donedata carries it as the raised event's data" | `event.data == "42"` | `event.data == 42` | Same clause, same reasoning; this is the `_event.data` half 5.5 names explicitly. |

Its sabotage note is updated in the same edit (the mutation still redden it:
`static_donedata`'s static arm returning `nil` still loses the value).

Two tests the research flagged that do **not** change, because the coercion
runs at event time and not in the compiler:

- `test/statifier/machine/content_test.exs:305-311` asserts
  `%Machine.Donedata{expr: {:static, "done text"}}` - compiler output,
  unchanged.
- `test/statifier/machine/content_test.exs:333-354` asserts the compiled
  arm - unchanged.

### Decision 4: `<param location>` lands in this bead

**Decided: in scope, implemented as a value-expression read.**

Spec 5.7 gives `location` and `expr` the *same* failure result:

> If the 'location' attribute does not refer to a valid location in the data
> model, or if the evaluation of the 'expr' produces an error, the SCXML
> Processor MUST place the error 'error.execution' on the internal event
> queue and MUST ignore the name and value.

Under the predicator datamodel a location expression (5.9.2) is a syntactic
subset of a value expression (5.9.3): `Var1`, `foo.bar.baz`. Reading one is
therefore `Expressions.compile/3` plus `Evaluator.evaluate/2` against the
same context, with `on_unbound: :error` turning an unresolvable root into
the error 5.7 demands. `test/scxml_tests/mandatory/param/test298_test.exs`
(`location="foo.bar.baz "` must raise `error.execution`) and `test343`
(`_event.data === undefined`) are both satisfied by that path.

Deferring instead would leave `<param location>` lowering to a slot nothing
reads, which is a worse intermediate state than one honest read path. The
`kind` field (`:expr | :location`) is kept on the compiled struct anyway, so
when `<assign>`-style `Predicator.context_location/3` grows a read-only
sibling (the epic's Phase 4, with `<send>` - st-cmq.3), this one call site switches over without
touching lowering, the Document struct, or the validator.

Two consequences stated so the implementer does not rediscover them:

- Deep-path **write** vivification (st-af3.4) is not involved. This is a
  read.
- A `location` or `expr` source that will not *compile* is a document-load
  error through the existing `Expressions.compile/3` path, not a runtime
  `error.execution`. Spec 5.9.4 explicitly permits either, and
  `docs/datamodel.md` records that this engine rejects at load time
  everywhere except `<data expr>` and `<assign expr>`. `<param>` joins the
  load-time majority; no new asymmetry is introduced.

### Decision 5: params merge in document order, last key wins, empty means no data

**Decided: fold in document order into a string-keyed map with `Map.put`
semantics (last occurrence of a duplicate name wins); an empty result is
`nil`, not `%{}`.**

B.2.8.1: "In the case of duplicate keys, the behavior is platform-specific."
This is the project's call. Last-wins is what a left-to-right fold over
document order yields with no extra machinery, and matches how an
ECMAScript object literal - the datamodel B.2.8.1 was written for - resolves
duplicate properties. It is written into `Statifier.EventData`'s moduledoc as
a stated rule, not left implicit in a `Map.put`.

The empty case is not a free choice: `test488` has a single failing
`<param>` and asserts `_event.data === undefined`, and st-af3.8's own bead
text already flags "the conf:emptyEventData trio test343/488/528 requiring
absent event data to be undefined, not `%{}`". So an all-failed param set,
and a `<donedata>` with no usable children at all, both produce `nil`.

Failed params are skipped entirely per 5.7's "MUST ignore the name and
value", and each contributes exactly one `error.execution`; a failure does
not abort the remaining params, because 5.7 scopes the consequence to that
param's own name and value.

### Decision 6: the 5.5 `<content>`-xor-`<param>` check lands here

**Decided: yes, as a new arm of `Statifier.Validator.Checks.Donedata`, plus
a new `Statifier.Validator.Checks.Param` for 5.7's expr-xor-location rule.**

Bead **st-hyx** owns this rule and its own description settles the timing:
"Moot in [epic] Phase 1 because lowering rejects `<param>` as
`{:unsupported_element, "param"}` ... It becomes live the moment `<param>`
is supported ([epic] Phase 3), and should land with it rather than being
rediscovered then." This bead is what makes it live, so it is what lands it.
This plan's Phase 3 commit references st-hyx alongside st-af3.7; the orchestrator
closes st-hyx per the repo's authority table (merged to `origin/main`,
verified against the remote), not this plan.

The split follows the existing Content/Donedata precedent exactly - each
rule lives where the spec states it:

- 5.5 states "either a single `<content>` element or one or more `<param>`
  elements as children of `<donedata>`, but not both" **on `<donedata>`** ->
  an arm of `Checks.Donedata` (which is already the `<donedata>` shape
  check).
- 5.7 states "MUST specify either the 'expr' attribute of `<param>` or the
  'location' attribute, but MUST NOT specify both" **on `<param>`** -> a new
  `Checks.Param`, mirroring `Checks.Content`, whose moduledoc already
  explains that it walks `<donedata>` today and "grows an arm" when `<send>`
  gains a `<content>` child. `Checks.Param` gets the identical note.

Lowering keeps both fields nilable and simultaneously representable, per the
`<data>` `expr`/`src` and `<content>` `expr`/`text` precedents - the
validator reports the shape, lowering does not refuse to build it
(`docs/architecture.md` principle 4).

### Decision 7: the FeatureDetector registry and `test/passing_tests.json` are untouched

**Decided: this bead changes neither file. No corpus file moves into the
ratchet.**

Two sibling beads already own that work, and taking it here would duplicate
their scope:

- **st-oq4** - "Flip `conditional_transitions` to `:supported` in the
  feature registry", with its own ratchet run. All seven donedata/param
  corpus files carry `:conditional_transitions`, still `:unsupported` at
  `test/support/feature_detector.ex:68`, and `Statifier.Case`'s
  `validate_features!/2` **flunks** rather than skips - so none of the seven
  can pass while that atom is unsupported, no matter what this bead
  implements.
- **st-af3.8** - "Corpus: flip datamodel features, split the content
  detector, ratchet", whose description already names this exact gap: "the
  `send_content_elements` pattern (feature_detector.ex:151) cannot tell
  `<send>`'s `<content>` from `<donedata>`'s. Fix by stripping
  `<donedata>...</donedata>` blocks from the source before the send-flavored
  element patterns run ... Same consideration for `<param>` under
  `<donedata>` vs `send_param_elements`." It also carries the ratchet run
  for everything the epic's Phase 3 unblocks, per `docs/testing.md`'s "a feature PR
  that makes tests pass adds them in the same PR" applied at the epic's
  closer.

So this bead proves its behavior with **internal tests only**, and every
phase still runs `mix test.regression` to prove it has not *lost* a
ratcheted file - which is the live risk, since `<log expr>` appears in 172
corpus files and 97 files are in the ratchet today.

`test/passing_tests.json` is never shrunk, so no `docs/quality-gate-changes.md`
ledger entry is needed or written; a ledger entry is a human's call on the
record (ADR-0011) and this plan does not propose an action that would
require one.

### Decision 8: `exit_interpreter/1` enqueues the error anyway

**Decided: enqueue `error.execution` on the internal queue of the returned
`MachineState`, exactly as site 1 does. No new effect type, no drop.**

Spec 5.6 and 5.7 both say the Processor MUST place `error.execution` in the
internal event queue. Placing it satisfies the MUST literally. That nothing
ever dequeues it is Appendix D's own consequence - `exitInterpreter` runs
after the event loop has stopped - and not a deviation this port introduces
(ADR-0002: the pseudocode is silent on when donedata is evaluated, so 5.5's
prose is the port source, and 5.6/5.7's error rule is unqualified).

The alternatives were weighed and rejected:

- **A new effect** (`{:error, ...}` or similar) would add a member to the
  effect vocabulary (ADR-0003) for one unobservable case, and would make the
  two donedata sites report the same failure through two different channels
  - the exact divergence `interpreter.ex:661-668` already argues against for
  `Trace.Done` and `Effect.Done`.
- **Dropping it** would be a rescue-to-default at a leaf, which
  `docs/architecture.md` principle 3 and `.claude/wurk/codebase.md` both
  name as a finding.

It is observable, which is what makes it testable: ADR-0012 constraint 1
makes the returned `%MachineState{}` a complete inspectable position, so
`MachineState.internal_events/1` on the terminal state shows the
`error.execution`, and Phase 2 asserts exactly that. The `Effect.Done`
`donedata` is `nil` alongside it.

## What We're NOT Doing

- **Not touching `test/support/feature_detector.ex` or
  `test/passing_tests.json`** (Decision 7). st-oq4 and st-af3.8 own them.
- **Not evaluating `<param>`/`<content>` under `<send>` or `<invoke>`.**
  Those elements do not exist yet (st-cmq.3, st-cmq.6). `EventData.coerce/1`
  and the `Document.Param` / `Machine.Param` shapes are built for that reuse
  and nothing more.
- **Not implementing `namelist`.** It is named in `docs/datamodel.md`'s
  commitment as a future consumer of the same function, not a subject of
  this bead.
- **Not implementing B.2.8.1's JSON or XML-DOM rungs** (Decision 2), and not
  adding a JSON dependency.
- **Not merging or changing `Expressions.inline_value/1`** or any `<data>`
  binding behavior (Decision 2). Only a pointer comment is added.
- **Not changing `Evaluator.evaluate/2`'s `{:static, v}` bypass**
  (Decision 3). Coercion happens after evaluation, at the donedata fold.
- **Not adding a read-only location-resolve helper over

## Implementation Approach

Four phases, split along the pipeline's module boundaries
(`.claude/wurk/plan.md`): one interpreter-only phase for `<log>`, one
evaluator+interpreter phase for `<content>` donedata and the coercion
function, then lowering+validator and compiler+interpreter for `<param>`.

Each phase is independently committable and leaves a green full `mix
quality`. Phase 3's structures (`Document.Param`, `Checks.Param`, the
`Checks.Donedata` arm) are exercised by lowering and validator tests within
that phase, so it is not the "structure added in one phase, consumed in the
next, with nothing in between" shape the plan skill says to combine - it
changes observable lowering and validation behavior on its own, and existing
tests pin that behavior today and are rewritten in that phase.

**Appendix D deviations** (`.claude/wurk/plan.md`'s rule): this bead adds no
new deviation. The pseudocode names `s.donedata` as an argument to
`returnDoneEvent` and to `new Event("done.state." + parent.id, s.donedata)`
without saying when it is evaluated (`appendix-d.txt:169-178`, `326-330`),
so 5.5's prose is the port source, and both sites already fold at the raise
point with the mechanical reason in a comment. The grandparent event stays
dataless, matching `new Event("done.state." + grandparent.id)` verbatim -
do not "fix" it by symmetry.

**What the gate expects from every new module.** `.doctor.exs` holds 100% on
every axis with empty `ignore_modules`/`ignore_paths`, and `coveralls.json`
sets `minimum_coverage: 90`. Each new module in this plan
(`Statifier.EventData`, `Statifier.Document.Param`, `Statifier.Machine.Param`,
`Statifier.Validator.Checks.Param`) therefore lands with a moduledoc, a
`@doc` and `@spec` on every public function, and tests in the same phase -
not as a follow-up. Neither guarded file is edited, so no
`docs/quality-gate-changes.md` entry is involved (ADR-0011).

A single changelog fragment `changelog.d/st-af3.7.md` is created in Phase 1
and extended by each later phase (user-visible: `<log expr>` values, real
donedata, `<param>` support).

```elixir
@spec execute(node :: Log.t(), context :: Context.t()) ::
        {:ok, Context.t(), [{:log, Effect.Log.t()}]} | {:error, term()}
def execute(%Log{} = node, %Context{} = context) do
  case value(node, context) do
    {:ok, value} ->
      # build %Effect.Log{...} exactly as today, with `value: value`
      {:ok, context, [{:log, log_effect}]}

    {:error, reason} ->
      {:error, reason}
  end
end

# spec 5.9.3/5.9.4: a value expression that fails to evaluate raises
# error.execution at the point of evaluation. 4.7's "<log> MUST have no
# side-effects on document interpretation" governs the logging mechanism
# (how the message is displayed), not the error model - an unevaluatable
# expression is an error wherever it sits, and the block runner is the

@spec value(node :: Log.t(), context :: Context.t()) :: {:ok, term()} | {:error, term()}

defp value(%Log{expr: expr}, %Context{datamodel_context: datamodel_context}),
  do: Evaluator.evaluate(datamodel_context, expr)
```

## Phase 2: `Statifier.EventData` and donedata `<content>` evaluation

### Overview

### Changes Required

#### 1. The coercion function

**File**: `lib/statifier/event_data.ex` (new)
**Changes**: `Statifier.EventData.coerce/1` per Decision 2, with a moduledoc
that states each rung, quotes B.2.8.1, names the rungs deliberately not
implemented and why, and states the duplicate-key rule (Decision 5) as a
rule rather than leaving it implicit in `Map.put`.

```elixir
@type input :: {:value, term()} | {:text, String.t()} | {:params, [{String.t(), term()}]}

@spec coerce(input()) :: term() | nil
def coerce({:value, value}), do: value
def coerce({:text, text}), do: from_text(text)
def coerce({:params, pairs}), do: from_params(pairs)

# B.2.8.1's bottom two rungs. The predicator-literal rung stands in for the
# JSON rung (Decision 2 of the plan on this module): the clause is
# conditional on JSON support, and this engine's value space is
# predicator's (ADR-0004). The empty, on_unbound: :error context is the
# same guard `Expressions.inline_value/1` documents - `foo` compiles to an
# identifier load that errors against a context holding nothing, so it
# falls through to the string literal instead of becoming a datamodel read.
defp from_text(text) do
  case String.trim(text) do
    "" ->
      nil

    trimmed ->
      empty_context = Predicator.Context.new(%{}, on_unbound: :error)

      with {:ok, %Predicator.Compiled{} = compiled} <- Predicator.compile_with_spans(trimmed),
           {:ok, value} <- Predicator.evaluate(compiled, empty_context) do
        value
      else
        _failure -> space_normalize(trimmed)
      end
  end
end

# B.2.8.1: "the Processor MUST treat the content as a space-normalized
# string literal" - trim, then collapse internal whitespace runs.
defp space_normalize(trimmed), do: String.replace(trimmed, ~r/\s+/, " ")

# B.2.8.1's key-value rung. Document order, last duplicate key wins
# ("In the case of duplicate keys, the behavior is platform-specific" -
# this is the project's call). An empty map is no data, not %{}.
defp from_params([]), do: nil
defp from_params(pairs) do
  Enum.reduce(pairs, %{}, fn {name, value}, acc -> Map.put(acc, name, value) end)
end
```

## Phase 3: `<param>` lowering and validation

### Overview

`<param>` stops being an unsupported element: it lowers into a
`Document.Param` on a new `Donedata.params` list, and two validator checks
report the shapes spec 5.5 and 5.7 forbid. Nothing evaluates it yet; the
compiler still ignores it, which is why this phase is committable on its own
and why its tests are lowering and validator tests.

### Changes Required

#### 1. Document layer

**File**: `lib/statifier/document/param.ex` (new)
**Changes**:

```elixir
@enforce_keys [:location]
defstruct [:location, name: nil, expr: nil, param_location: nil, attribute_locations: %{}]
```

`param_location` is the SCXML `location` **attribute** (a raw path string).
`<param>` hits the same name collision `Document.Assign` documents under
"Two spans that are not the same thing"
(`lib/statifier/document/assign.ex:6-22`), and **resolves it the opposite
way** - the moduledoc must say so plainly rather than claiming to repeat
`Assign`'s choice, because the two are mirror images and a reader who
assumes otherwise will build the fields backward:

| | `location` holds | element span held by |
|---|---|---|
| `Document.Assign` | the raw path string (required, `@enforce_keys`) | `node_location` |
| `Document.Param` | the `Parser.Location.t()` element span | `location` (the ordinary convention) |

Two reasons for the inversion, both specific to `<param>`:

1. On `<assign>` the `location` attribute is **required** (spec 5.4.2), so
   the raw path is the field a reader reaches for first. On `<param>` it is
   **optional** and mutually exclusive with `expr` (spec 5.7), so making the
   always-present parser span the oddly-named field would be the worse
   trade.
2. `place_children/3`'s generic catch-all does
   `Map.fetch!(value, :location)` and hands the result to
   `Error.misplaced/3`, which pattern-matches `%Location{}`
   (`lib/statifier/lowering/builders.ex:846-850`). `Assign` needs a
   dedicated earlier `place/3` clause purely to avoid crashing that match on
   a binary. Keeping `location` as the span means `{:param, _}` needs no
   such clause.

The moduledoc also says that `expr` and `param_location` are both nilable
and simultaneously representable so `Checks.Param` can report the violation
(the `<data>` `expr`/`src` precedent).

## Testing Strategy

### Unit Tests

- `test/statifier/event_data_test.exs` - one test per stated rule of
  `coerce/1`, including the two that exist only to prove a boundary: a
  `{:value, "21"}` that stays a string (no double interpretation) and a
  `{:params, []}` that is `nil` rather than `%{}`.
- `test/statifier/executable_content_test.exs` - `<log>`'s evaluated value
  and its error return, with no `{:log, _}` effect on failure.
- The block-runner test file - a failing `<log expr>` producing exactly one
  `error.execution` at the right `c_index` and halting the block.
- `test/statifier/lowering/donedata_test.exs` - `<param>` lowering, document
  order, missing `name`.
- `test/statifier/validator/checks/param_test.exs` and
  `.../donedata_test.exs` - the three new reasons and the passing shapes.
- `test/statifier/interpreter/exit_entry_enter_test.exs` - the
  `done.state.*` half of 5.5: content value, content failure, param map,
  param failure, duplicate keys.
- `test/statifier/interpreter/termination_test.exs` - the "return the data
  to the environment" half: `Effect.Done` / `Trace.Done` agreement, and the
  Decision 8 error visible on the terminal `MachineState`.

Key edge cases: whitespace-only `<content>` text; a `<content expr>` whose
value is itself a string that would parse as a number; a param name that
duplicates another; every param failing; `<donedata>` present but empty.

Every test asserting `lib/` behavior follows the project's sabotage
convention (`docs/testing.md`): break the covered code, confirm red, revert,
and record the mutation in a one-line comment above the test. Generated
corpus files are exempt and none is authored here.

### Manual Testing Steps

1. Load a document with `<log expr="Var1 + 1">` under a bound datamodel
   through the public API and confirm the `Effect.Log` carries the evaluated
   number.
2. Change that expr to reference an undeclared identifier and confirm one
   `error.execution` appears and the rest of the block does not run.
3. Run a document whose `<final>` has `<donedata><content>21</content>` and
   confirm `_event.data` is the integer `21` in a following transition's
   `cond`.
4. Run a document whose `<final>` has two `<param>` children and confirm the
   `done.state.*` event's data is the expected string-keyed map.
5. Run a top-level `<final>` with a failing `<content expr>` and confirm
   `Effect.Done`'s `donedata` is `nil` while the returned `MachineState`'s
   internal queue holds the `error.execution`.

## Corpus/Ratchet Notes

**No corpus file moves into `test/passing_tests.json` in this bead, and no
corpus file is regenerated.** Decision 7 records why: all seven donedata and
param corpus files require `:conditional_transitions`, which
`test/support/feature_detector.ex:68` still marks `:unsupported` and which
**st-oq4** owns; and the `send_content_elements` / `send_param_elements`
regexes flag `<content>`/`<param>` regardless of parent, which **st-af3.8**
owns along with the epic-closing ratchet run.
`Statifier.Case.validate_features!/2` flunks rather than skips, so none of
the seven can pass here regardless of what this bead implements.

`test/passing_tests.json` is therefore never shrunk and never grown, and no
`docs/quality-gate-changes.md` entry is required (ADR-0011). The live risk
runs the other way: `<log>` appears in 172 corpus files and the ratchet
holds 97 (2 internal, 87 SCION, 10 W3C), so `mix test.regression` is an
Automated Verification item on **every** phase, not just the first.
