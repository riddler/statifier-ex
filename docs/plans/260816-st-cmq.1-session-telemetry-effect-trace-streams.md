# Session telemetry for the effect and trace streams Implementation Plan

## Overview

`Statifier.Session` gains a `:telemetry` bridge over the effect/trace stream it
already fans out to subscriber pids, discharging `docs/observability.md`
constraint 6's "once it exists" hedge. The pure core never calls `:telemetry`:
the trace effects *are* the instrumentation stream and this is one more
interpreter of them (ADR-0003), enforced mechanically by `Mix.Statifier.AdrGuard`.
Bead: st-cmq.1.

## Current State Analysis

Everything the bridge needs is already in place; nothing about the core changes.

- **One fan-out point, total and ordered.** `Statifier.Session.Effects.plan/2`
  (`lib/statifier/session/effects.ex:111-114`) emits `{:notify, effect}` as the
  head of every effect's instruction list, and `perform_instruction/3`
  (`lib/statifier/session.ex:801-809`) hands it to `notify/2`
  (`lib/statifier/session.ex:1250-1255`). Two more envelopes ride the same
  function: `{:unroutable, effect}` (`:920-923`) and `{:halted, reason}`
  (`:925-931`).
- **The counters are already stamped on every effect.** All nine core effect
  structs carry `macrostep`/`microstep`; the nine `Effect.Trace.*` structs and
  `Effect.BudgetExhausted` also carry `round` (ADR-0020).
- **Constraint-3 identities ride as bare integers** (`state_index`, `t_index`,
  `c_index`, `owner`, `invoke_id`, `invoke_index`). Source locations are *not*
  on the effects; they are reached through `Machine.at/2` (`lib/statifier/machine.ex:168`),
  `Machine.transition/2` (`:177`) or `Machine.content/2` (`:186`) and reading
  `.location`. The session holds the `Machine` at dispatch time via
  `state.machine_state.machine`, so no new plumbing is needed.
- **The trace gate is in the core, not at the bridge.** `Effect.trace/3`
  (`lib/statifier/effect.ex:163-173`) is a `defmacro` that expands to a
  zero-or-one element list on `machine_state.trace`. With `trace: false` the
  core produces no trace effect at all.
- **Four core-driving paths plus one bypass.** `init/1` -> `Interpreter.initialize/2`
  (`:492`), `drain_event/2` -> `handle_event/2` (`:776`), `drain_cancel/1` ->
  `cancel/1` (`:762`), `deliver_internal/6` -> `deliver_internal/5` (`:1216`,
  ADR-0039). `handle_cast({:interpret, effects}, _)` (`:673-676`) reaches
  `perform/3` without touching the core at all (ADR-0029).
- **No clock anywhere.** `session.ex` contains no `System.monotonic_time/0`;
  `Statifier.Session.Recording`'s moduledoc (`lib/statifier/session/recording.ex:56-65`)
  states its clock-freedom as deliberate (ADR-0034).
- **`:telemetry` is absent** from `mix.exs`, `mix.lock`, `deps/`, `lib/` and
  `test/`. The only occurrences are prose (`lib/statifier/machine.ex:101`,
  `docs/observability.md:151` and `:196`).
- **The enforcement hook exists.** `Mix.Statifier.AdrGuard`'s
  `@effect_call_pattern` (`lib/mix/statifier/adr_guard.ex:97-102`) is applied by
  `effects_findings/1` (`:263-273`) to added diff lines under
  `lib/statifier/`, exempting `@effect_interpreter_paths` (`:78`, today
  `session.ex` and `supervisor.ex`). Adding `:telemetry\.` is a one-alternation
  edit that reuses the existing `adr_guard` gate stage (`.quality.exs:94-101`).

## Desired End State

After this plan:

1. `{:telemetry, "~> 1.3"}` is a runtime dependency, present in `mix.exs` and
   `mix.lock`.
2. `Statifier.Session.Telemetry` exists, its `@moduledoc` is the authoritative
   reference for all 25 public event names with their measurement and metadata
   shapes, and `events/0` returns that same list so a metrics consumer can
   attach to every one without hand-copying names.
3. `Statifier.Session` emits those events from the seams named in Phase 3, and
   nothing under `lib/statifier/` other than the two ADR-0003 effect-interpreter
   paths (`session.ex` and the new `session/telemetry.ex`) may call
   `:telemetry` without an ADR escape comment - checked by `mix adr.check`.
4. `docs/observability.md` constraint 6 no longer says "once it exists".
5. ADR-0040 records the contract, the trace-off policy, and the one new clock
   read.

Verification: `mix quality` is green on every phase; `mix adr.check --format json`
reports the new pattern; the telemetry handler tests in
`test/statifier/session/telemetry_test.exs` pass with `trace: false` and
`trace: true`; `Statifier.Session.Telemetry.events/0` and the moduledoc table
agree (asserted by a test, not by eye).

### Key Discoveries:

- `Effects.plan/2` guarantees `{:notify, effect}` first, in core order
  (`lib/statifier/session/effects.ex:111-114`) - one seam sees every effect.
- `notify/2` already carries `state.session_id` (`lib/statifier/session.ex:1250-1255`).
- `Trace.MacrostepStable` is emitted only on the `:quiescent` branch
  (`lib/statifier/interpreter.ex:986-994`); `Effect.BudgetExhausted` is emitted
  *instead* on exhaustion (`:996-1008`). A macrostep event built on
  `MacrostepStable` would therefore be missing exactly the runs an operator
  most wants to see.
- `.doctor.exs:22-35` holds 100% thresholds on every axis with
  `ignore_modules: []` - a new module needs `@moduledoc`, and every public
  function needs `@doc` *and* `@spec`.
- `Credo.Check.Warning.UnsafeToAtom` (`.credo.exs:200`) forbids building event
  name segments with `String.to_atom/1`; every segment must be a literal atom
  or an atom already carried by the effect tuple.
- ADR-0029: core-derived and `interpret/2`-injected effects are
  indistinguishable *on the stream*. ADR-0034: `Statifier.Replay` is a pure
  fold with no session, so replay structurally cannot fire telemetry.
- `docs/adr/README.md` closing line: "New ADRs: next number" - 0039 is the
  highest today, so this plan claims **0040**.
- st-cmq.1 already `DEPENDS ON` st-cmq.4 (closed) in beads, so the bead's last
  acceptance criterion ("Dependency on the Session GenServer bead wired when
  Phase 4 is broken down") is already satisfied; no `bd dep add` is needed.

## What We're NOT Doing

- **No OpenTelemetry bridge, no `:telemetry_metrics` definitions, no
  reporter.** st-cmq.2 builds on these events and is a separate bead.
- **No `[..., :exception]` span half.** `Statifier.Session` does not rescue;
  a raising core call takes the GenServer down and the supervisor's own
  telemetry (if any) is the observer. Adding a rescue purely to emit an
  exception event would change failure semantics to serve instrumentation.
- **No telemetry from `Statifier.Replay`.** ADR-0034 makes it a pure fold with
  no process; there is nothing to emit from, and emitting would make replay
  observably different from the run it reproduces.
- **No telemetry for validator findings.** ADR-0033 already decided that
  `validate/2`'s return and `Machine.warnings` are the whole channel
  (`docs/observability.md:194-198`).
- **No change to the subscriber pid stream.** Its shape was st-cmq.4's
  commitment; this plan adds a second consumer of the same seam and modifies
  neither the message shape nor the ordering.
- **No resolution of a location per index for the list-carrying trace effects.**
  See Decision 4 - `ExitSet`, `EntrySet`, `TransitionsSelected`,
  `ContentExecuted` and `InvokePass` carry index lists whose length is
  unbounded by the document; resolving each would put an O(configuration)
  `Machine` walk on every microstep. The indexes are in metadata and a
  consumer that wants locations has the same `Machine.at/2` the session does.
- **No `Effect.trace?/1`-based filtering at the bridge.** The split is in the
  event *name* (Decision 5), which is cheaper for a subscriber than a metadata
  test and is what `:telemetry.attach_many/4` is built for.
- **No ratchet or corpus movement.** Nothing here touches the interpreter or
  the parser; `test/passing_tests.json` is untouched. (See "Corpus/Ratchet
  Notes".)
- **No agent-written ledger entry.** See Decision 6 and Phase 4.

## Implementation Approach

The research document ended with nine open questions. Each is decided below;
the phases implement the decisions.

### Decision 1 (research Q1): the session reads a monotonic clock, and that does not contradict ADR-0034

**Decision.** `Statifier.Session` reads `System.monotonic_time()` at the head
of each core-driving path and emits `duration` (in `:native` units) on the
macrostep stop event. `%State{}` gains one integer field, `macrostep_started_at`.

**Rationale.** ADR-0034's clock-freedom is a property of
`Statifier.Session.Recording` and `Statifier.Replay`: a recording that carried
wall-clock timestamps would either replay them (making replay a simulation of
timing, which it is not) or discard them (making them dead weight). Neither
argument reaches telemetry, because telemetry is a *live-session-only* channel
that by ADR-0034's own construction replay cannot fire. The recording is still
built from `Recording.put_*` calls that read no clock, and no telemetry
measurement is ever written into it. `duration` is emitted in `:native` units
per `:telemetry`'s own convention, leaving unit conversion
(`System.convert_time_unit/3`) to the consumer.

**Cost.** Two `System.monotonic_time/0` calls per core-driving path (~20ns
each on OTP 27), paid whether or not a handler is attached. This is the only
unconditional cost the bridge adds; every `:telemetry.execute/3` call is a
single ETS lookup that returns immediately when no handler is attached.

### Decision 2 (research Q2): the macrostep boundary is observed at the core call's return, never from `Trace.MacrostepStable`

**Decision.** The macrostep span is opened immediately before each
`Interpreter.*` call in the session and closed immediately after it returns,
reading the counters off the returned `machine_state`.

**Rationale.** Three properties the `Trace.MacrostepStable` route does not
have: (a) it works with `trace: false`, which the bead's own trace-off policy
requires; (b) it fires on budget exhaustion, where `MacrostepStable` is
suppressed in favor of `Effect.BudgetExhausted` (`lib/statifier/interpreter.ex:986-1008`);
(c) it is one seam per path rather than a scan of the returned effect list.
The outcome is still distinguishable: the stop event carries an `outcome`
metadata key derived from the returned `machine_state` and the session's own
halt bookkeeping - `:quiescent | :budget_exhausted | :done | :cancelled`.

### Decision 3 (research Q3): all four core-driving paths are macrosteps and are distinguished by `trigger`; `interpret/2` is not a macrostep

**Decision.** `init/1`, `drain_event/2`, `drain_cancel/1` and
`deliver_internal/6` each emit a macrostep span, with metadata
`trigger: :initialize | :event | :cancel | :internal`.
`handle_cast({:interpret, effects}, _)` emits its own
`[:statifier, :session, :interpret]` event carrying `effect_count`, and its
effects then flow through the ordinary per-effect events with **nothing
distinguishing them from core-derived ones**.

**Rationale.** All four call the core and each one advances `macrostep` (or, in
`deliver_internal/5`'s case, re-enters the same one per ADR-0039), so they are
the same kind of thing and a `trigger` key is the honest discriminator.
`interpret/2` calls no core function, so calling it a macrostep would put a
span around something that moves no counter. Naming the *call* is not the same
as distinguishing the *effects*: ADR-0029's point is that a consumer of the
effect stream cannot tell a re-derived effect from an injected one, and that
stays exactly true here - the injected effects are indistinguishable, and only
the `interpret/2` call itself is named. This is deliberate: a recorder built
on these events would still have to record the four inputs ADR-0029 names, not
the effect stream.

### Decision 4 (research Q4): locations are resolved for single-index effects only, and carried as the `%Location{}` struct

**Decision.**

- An effect that carries exactly one resolvable index gets
  `metadata.location`, resolved at emission:
  `c_index -> Machine.content/2`, `state_index -> Machine.at/2`,
  `t_index -> Machine.transition/2`, then `.location`.
- The value is the `%Statifier.Parser.Location{}` struct verbatim, not
  flattened into `line`/`column` keys. Flattening invents a key set the
  library does not otherwise have, and it silently drops whatever
  `Location` gains later.
- `cond_location` is **not** resolved. No effect in the vocabulary is emitted
  from a guard evaluation, so it would always be the location of a condition
  that did not produce this effect.
- An effect with no index carries `location: nil`. This includes an effect
  whose index field is present but `nil` - `Effect.Log`'s `c_index` is
  `non_neg_integer() | nil` (`lib/statifier/effect/log.ex:24-33`, nil for a
  global `<script>`), so the resolver must match on `nil` before it indexes a
  tuple rather than letting `Machine.content/2` raise.
- An effect carrying a *list* of indexes carries the list in metadata and its
  length as a measurement, and carries `location: nil`. See "What We're NOT
  Doing".

**Rationale.** One tuple read per event is genuinely cheap and removes the need
for a subscriber to hold a `Machine` handle, which is the bead's stated goal.
N tuple reads per microstep is not, and the list-carrying effects are exactly
the ones a high-volume trace run produces most of.

### Decision 5 (research Q5): `{:halted, _}` and `{:unroutable, _}` both get events

**Decision.** `[:statifier, :session, :halt]` and
`[:statifier, :session, :unroutable]`.

**Rationale.** Both already ride `notify/2`, so the seam costs nothing.
`{:halted, reason}` is the single most operationally interesting thing a
session does, and `{:unroutable, effect}` is a silent-failure surface that
today has no channel but a subscriber pid - exactly the kind of thing a metrics
pipeline exists to alert on.

### Decision 6 (research Q6): the guard is amended on this branch; the ledger entry is the human's

**Decision.** Phase 4 adds `:telemetry\.` to `@effect_call_pattern` **and**
adds `lib/statifier/session/telemetry.ex` to `@effect_interpreter_paths` - the
two are one change, because the pattern would otherwise flag the emitters the
same branch just wrote (`AdrGuard` diffs against `merge-base(main, HEAD)`, so
it re-reads the whole branch's added lines, not just the current commit). It
also
writes the *recommended text* of a `docs/quality-gate-changes.md` entry into
this plan, and stops there. No agent writes the entry into the ledger.

**Rationale.** ADR-0027's reasoning is explicit that riding a pattern gap
instead of amending the guard "would be the hole the guard's own comment
disclaims", and the two prior amendments to `adr_guard.ex` each took a
*voluntary* ledger entry (`docs/quality-gate-changes.md:16-46`, `:73-112`) even
though `mix gate.check` would have stayed green. ADR-0011 and the ledger's own
preamble put writing the entry on a human. Because `adr_guard.ex` is not a
guarded path, Phase 4's automated gate is green either way - the entry is a
merge precondition, not a phase gate, which is why this plan can complete
without a human present and still leave the decision where it belongs.

### Decision 7 (research Q7): `{:telemetry, "~> 1.3"}`

**Decision.** `{:telemetry, "~> 1.3"}` as a plain runtime dependency in
`deps/0`, with no `application/0` change.

**Rationale.** `~> 1.3` admits every 1.x from 1.3.0 and excludes a future 2.0,
which is the constraint `:telemetry_metrics` and the OpenTelemetry Erlang
bridges publish and the one an embedder is most likely to already have
resolved. `application/0` (`mix.exs:30-34`) has no `:applications` key, so Mix
infers the dependency automatically. The `telemetry` application also ships
`:telemetry_test`, which the Phase 3 tests use.

### Decision 8 (research Q8): the contract lives in the module doc; `docs/observability.md` links to it

**Decision.** `Statifier.Session.Telemetry`'s `@moduledoc` is the single
authoritative event reference and ships in ExDoc. `docs/observability.md`
constraint 6 is rewritten in Phase 3 to state that the bridge exists and to
point at that module in one sentence, with no second copy of the table.

**Rationale.** The bead says "module doc or docs/" without choosing. Two copies
of a 25-row table drift; the ExDoc-visible one is the one a library consumer
actually reaches, and `docs/observability.md` is a constraints document rather
than a reference.

### Decision 9 (research Q9): a new module, and it pays the Doctor bar

**Decision.** `Statifier.Session.Telemetry`, with a small public surface -
`events/0` plus one emitter per event family - each carrying `@doc` and
`@spec`, and the module carrying the `@moduledoc` from Decision 8.

**Rationale.** `session.ex` is already ~1300 lines; adding 25 event shapes and
a location resolver to it fights `Credo.Check.Refactor.Nesting` and buries the
contract. A separate module is also what makes Decision 8's "the moduledoc is
the reference" possible. The 100% Doctor bar is a cost, not an obstacle: the
module is documentation-first by construction.

### The event contract

Prefix `[:statifier, :session, ...]`. Measurements are numbers only; every
identity is metadata, including identities that happen to be integers
(`state_index`, `t_index`, `c_index`, `invoke_index`) - putting a state index
in measurements would invite `:telemetry_metrics` to average it.

**Configurations are state ids, not indexes.** Wherever a `configuration`
appears in metadata it is translated from the `MapSet.t(non_neg_integer())` the
effect carries into a list of state id strings, using the same
`translate_configuration/2` `build_status/1` already applies
(`lib/statifier/session.ex:1307-1309`, called at `:1278`). That helper is
private to `session.ex`, and `Statifier.Session.Telemetry.effect/3` receives
the `Machine` anyway, so the telemetry module does its own translation over the
public `Machine.id/2` (`lib/statifier/machine.ex:349-350`) rather than
promoting a private session function. Two small implementations of the same
one-liner is the cheaper trade than a new cross-module seam. This is the same "resolve at emission"
rule as Decision 4: a subscriber should not need a `Machine` to read a
configuration.

**Note on the bead's wording.** The bead says both "metadata carries ... the
step counters" and "numbers in measurements, identity in metadata per
`:telemetry` convention". These conflict. This plan resolves it in favor of the
convention the bead itself names as governing: the counters are numbers and go
in **measurements**. The bead's acceptance criterion "measurements numeric,
identity in metadata per :telemetry convention" is the one the tests assert.

**Lifecycle and span events (7), emitted regardless of `trace`:**

| Event | Measurements | Metadata |
|---|---|---|
| `[:statifier, :session, :init]` | `system_time` | `session_id`, `machine_name`, `trace`, `invoked_by` |
| `[:statifier, :session, :halt]` | `macrostep`, `microstep`, `round` | `session_id`, `reason` (`:done \| :cancelled \| :budget_exhausted`), `configuration` (state ids) |
| `[:statifier, :session, :terminate]` | `macrostep`, `microstep`, `round` | `session_id`, `reason` (the GenServer reason), `status` |
| `[:statifier, :session, :macrostep, :start]` | `system_time` | `session_id`, `trigger`, `macrostep`, `event_name` |
| `[:statifier, :session, :macrostep, :stop]` | `duration` (native), `macrostep`, `microsteps`, `rounds` | `session_id`, `trigger`, `outcome`, `event_name`, `configuration` |
| `[:statifier, :session, :interpret]` | `effect_count` | `session_id`, `macrostep`, `microstep` |
| `[:statifier, :session, :unroutable]` | `macrostep`, `microstep` | `session_id`, `effect`, `target`, `send_id`, `location` |

`[:statifier, :session, :unroutable]` is a lifecycle event rather than a member
of the `[..., :effect, _]` family on purpose: it names a *routing failure the
session detected*, not an effect the core produced, and it is emitted from the
`{:unroutable, effect}` instruction (`lib/statifier/session.ex:920-923`), which
is the session's own construct. A consumer alerting on it wants one name to
attach to, not a filter across nine effect names.

`[:statifier, :session, :terminate]` fires from `terminate/2` and is therefore
subject to the GenServer contract: it does not fire on a brutal kill. The
moduledoc says so; `:halt` is the event to build a "session finished" metric
on.

**Core effect events (9), emitted regardless of `trace`:**

`[:statifier, :session, :effect, kind]` for
`kind in [:send, :send_delayed, :cancel, :invoke, :cancel_invoke, :autoforward, :budget_exhausted, :done, :log]`.

- Measurements: `macrostep`, `microstep`; plus `round` and `budget` for
  `:budget_exhausted` only (it is the one core effect ADR-0020 stamps with a
  round, `lib/statifier/effect/budget_exhausted.ex:38`); plus `delay_ms` for
  `:send_delayed` (`lib/statifier/effect/send_delayed.ex:25-46`).
- Metadata: `session_id`, `effect` (the struct itself), `location` per
  Decision 4, and the family's identities - `send_id`, `target`, `c_index`,
  `owner` for the send family; `invoke_id`, `state_index`, `invoke_index` for
  the invoke family; `label` for `:log`.

**Trace effect events (9), emitted only under `trace: true`:**

`[:statifier, :session, :trace, kind]` for
`kind in [:event_dequeued, :transitions_selected, :exit_set, :content_executed, :entry_set, :macrostep_stable, :done, :invoke_pass, :finalize_autoforward]`.

- Measurements: `macrostep`, `microstep`, `round`; plus a `size` for the
  list-carrying families (`exit_set`, `entry_set`, `transitions_selected`,
  `content_executed`, `invoke_pass`).
- Metadata: `session_id`, `effect`, the index lists as carried, `location: nil`.

`kind` is derived by a multi-clause private function pattern-matching each
`Effect.Trace.*` struct to a literal atom - never `Module.split/1` plus
`String.to_atom/1`, which `Credo.Check.Warning.UnsafeToAtom` forbids and which
would make `events/0` unable to enumerate the set.

**Trace-off emission policy.** Everything above except the
`[:statifier, :session, :trace, _]` family fires with `trace: false`. The trace
family vanishes **in the core**, not at the bridge: `Effect.trace/3`
(`lib/statifier/effect.ex:163-173`) produces no effect, so the session has
nothing to forward. The bridge contains no `if trace` of its own, and Phase 3
tests that in both directions.

### Overview

Make "no `:telemetry` in the pure core" mechanical, which is the bead's third

```elixir
    use\s+GenServer\b | GenServer\. | Process\.(send|send_after|exit|monitor)\( |
    :timer\. | :telemetry\. | Logger\.\w+\( | IO\.(puts|write|inspect)\( |
    File\.\w+!?\( | System\.cmd\( | Node\.\w+\( | :ets\. | Agent\.\w+!?\( |
    Task\.(start|async)\( | \bspawn\w*\( | \breceive\s+do\b
  /x
```

#### 2. The exemption

**File**: `lib/mix/statifier/adr_guard.ex`
**Changes**: `@effect_interpreter_paths` (`:78`) gains
`"lib/statifier/session/telemetry.ex"`.

This is required, not optional, and it is the counterpart to the pattern above.
The `:telemetry.execute/3` call sites live in the Phase 2 module, not in
`session.ex` - `session.ex` only calls `Telemetry.*`. `AdrGuard` diffs against
`merge-base(main, HEAD)`, so it re-reads every line the whole branch added, not
just the current commit; without the exemption, the moment the pattern lands
every emitter in `telemetry.ex` becomes a live ADR-0003 finding and this phase's
own "`mix adr.check` is clean" criterion fails.

ADR-0027 is explicit that a new exempt path is "a smell to be argued, not
defaulted", so the argument, in one line: `Statifier.Session.Telemetry` is not a
second effect interpreter - it is the emission half of the one ADR-0003 names,
split out of `session.ex` only because `.doctor.exs`'s 100% bar makes the event
contract belong in a `@moduledoc` (Decision 9). It holds no state, drives no
core function, and is called from nowhere but `session.ex`. The alternative -
an `ADR-0003` escape comment above each of ~10 `:telemetry.execute/3` call
sites - is the same exemption spelled 10 times with no record, which is exactly
what ADR-0027 calls riding the gap.

## Testing Strategy

### Unit Tests:

- `test/statifier/session/telemetry_test.exs` (new, `async: false`) is the

  with hand-built effects and real compiled machines); Phase 3 fills its

  - `trace: false` vs `trace: true`, asserted in both directions;
  - zero handlers attached (the production default) - the session must behave
    identically;
  - an effect with no resolvable index (`location: nil`);
  - a list-carrying trace effect (`size` measurement, no location);
  - `interpret/2`-injected effects indistinguishable from core-derived ones
    (ADR-0029);
  - `terminate/2` firing on `Session.stop/2`.

## Performance Considerations

- **Unconditional cost**: two `System.monotonic_time/0` reads per core-driving
  path (Decision 1). Nothing else is paid before the `:telemetry` handler
  lookup.
- **Per-event cost when no handler is attached**: `:telemetry.execute/3` is a
  single ETS lookup that returns `:ok`. Measurements and metadata are built
  eagerly at each call site, which is the one place a hot untraced run pays for
  the bridge. If profiling later shows this matters, the fix is
  `:telemetry.execute/3`'s existing lazy-metadata idiom or an
  `Application.compile_env` kill switch - deliberately not built now, because
  a compile-time switch would make the events unattachable for an embedder and
  `Credo.Check.Warning.ApplicationConfigInModuleAttribute` (`.credo.exs:179`)
  points the same way.
- **Location resolution**: one `elem/2` on a tuple per single-index effect
  (Decision 4). The list-carrying trace effects are explicitly excluded, which
  bounds the per-microstep cost at O(1) rather than O(configuration).
- **Trace runs**: the trace family doubles the per-effect work on a traced run
  (one subscriber `send/2` plus one `:telemetry.execute/3`). Traced runs are a
  debugging mode, not a production path, and the core gate
  (`Effect.trace/3`) still means an untraced run allocates nothing.
