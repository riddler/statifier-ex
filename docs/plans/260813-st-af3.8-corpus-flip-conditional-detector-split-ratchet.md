# Corpus: flip conditional_transitions, split the send-child detector, ratchet

## Overview

The closer for epic Phase 3. Three harness-only changes, in order: teach
`Statifier.FeatureDetector` to tell `<donedata>`'s `<content>`/`<param>` from
`<send>`'s, flip `conditional_transitions` to `:supported`, then run the full
conformance suites and ratchet every newly passing file into
`test/passing_tests.json`. Nothing under `lib/` changes.

Bead: st-af3.8

Seven corpus files carry `<donedata>`; six of them are gated exactly this way.

## What We're NOT Doing

- **Not touching anything under `lib/`.** Every change is in `test/support/`,
  `test/statifier/`, and `test/passing_tests.json`. The Appendix D rule and
  the `docs/adr/` interpreter constraints have no surface here.
- **Not regenerating the corpus** (`mise run corpus`). It needs network access
  and Saxon, and the only thing it would change is the informational
  `@tag required_features:` lines on the seven `<donedata>` files. Those tags
  are read by nothing; the next routine regeneration picks them up. Leaving
  them stale is a deliberate, recorded choice, not an oversight.
- **Not fixing the six feature-clean failures.** They get beads. Fixing them
  is engine work in `lib/`, which is a different bead's scope and a different
  review.
- **Not adding a detector atom for `<data src=...>`.**
  `test/scxml_tests/mandatory/data/test552_test.exs` fails because `src` is
  never fetched, and the detector has no atom that would gate it. Adding one
  here would convert a visible failure into a silent skip on the same branch
  that discovered it - the shape ADR-0011 exists to prevent. It goes on the
  bead instead, for a human to decide.
- **Not re-attributing `<invoke>`'s `<content>`/`<param>`.** They keep
  reporting `send_content_elements`/`send_param_elements`, as today. Any
  document with `<invoke>` already trips `invoke_elements`, which is
  `:unsupported`, so the misattribution is unobservable. Splitting it would be
  churn with no corpus payoff.
- **Not flipping `event_expressions` or `target_expressions`.** They are
  `<send>` attributes and stay Phase 4 (st-cmq), per the bead.
- **Not treating test298 as payoff or as a regression.** See above.

## Implementation Approach

Three phases, ordered so each one's diff is reviewable on its own terms:
harness regex logic, then registry policy, then the ratchet that consumes
both.

Phases 1 and 2 are kept apart even though neither unblocks a corpus file by
itself. Each is independently gate-green and each has its own verifiable
assertion - Phase 1's is a set of new detector unit tests plus a change in
*which feature* the six files flunk on; Phase 2's is the roster test. Merging
them would produce one commit mixing a regex refactor with a support-policy
decision, and would lose the intermediate state where the six files are proven
to be blocked on nothing but `conditional_transitions`. Phase 3 depends on
both and must come last.

## Phase 1: Attribute `<content>` and `<param>` away from `<donedata>`

### Overview

Run the two send-flavored element patterns over a copy of the document with
`<donedata>...</donedata>` blocks removed, leaving every other pattern -
including the one that detects `<donedata>` itself - on the untouched source.

### Changes Required:

#### 1. The detector

**File**: `test/support/feature_detector.ex`

**Changes**: remove the `:send_content_elements` and `:send_param_elements`
rows from `@element_features` (lines 156-157), add a separate
`@send_child_features` table run over the stripped source, and add the strip
step to the `detect_features/1` pipeline.

```elixir
def detect_features(xml) when is_binary(xml) do
  MapSet.new()
  |> detect_elements(xml)
  |> detect_send_children(xml)
  |> detect_attributes(xml)
end
```

```elixir
# <content> and <param> are legal under <send>, <invoke>, and <donedata>.
# Only the <send> flavour is gated on send support - <donedata>'s children
# landed with st-af3.7 - so these two run over a copy with the <donedata>
# blocks removed. Every other pattern, <donedata> included, still sees the
# untouched source.
@send_child_features [
  {~r/<content(\s|>|\/>)/, :send_content_elements},
  {~r/<param(\s|>|\/>)/, :send_param_elements}
]

# <donedata> holds only <param> and <content>, so it never nests and the
# non-greedy run to the first close tag is exact. The lookbehind keeps a
# self-closing <donedata/> - which has no children to strip - from opening a
# span that swallows everything up to some later </donedata>.
@donedata_block ~r{<donedata\b[^>]*(?<!/)>.*?</donedata\s*>}s

defp detect_send_children(features, xml) do
  add_matches(features, String.replace(xml, @donedata_block, ""), @send_child_features)
end
```

The `@moduledoc` is left alone in this phase; Phase 2 rewrites the stale
paragraph about datamodel features once the registry actually matches it.

#### 2. Detector tests

**File**: `test/statifier/feature_detector_test.exs`

**Changes**: add a describe block covering the new attribution. The existing
`@samples` entries need no edit - the `donedata_elements` sample
(`feature_detector_test.exs:107-109`) still yields `donedata_elements`, and the
`send_content_elements`/`send_param_elements` samples (lines 86-91) use
`<send>` children with no `<donedata>` anywhere. Each new test carries the
file's existing exemption line, since `FeatureDetector` is harness code under
`test/support/` and has no `lib/` behavior to sabotage.

Cases to cover:

- `<final><donedata><content expr="1"/></donedata></final>` yields
  `donedata_elements` and **not** `send_content_elements`.
- The same for `<param>` and `send_param_elements`.
- A document with both `<send><content/></send>` and
  `<donedata><content/></donedata>` yields both atoms.
- Two `<donedata>` blocks in one document are both stripped - the shape of
  `test/scxml_tests/mandatory/donedata/test294_test.exs`, which has a `<param>`
  block and a `<content>` block.
- A self-closing `<donedata/>` earlier in the document does not swallow a
  later `<send><param/></send>`. This is the case the `(?<!/)` lookbehind
  exists for; without it the test goes red.

### Overview

**File**: `test/support/feature_detector.ex`


feature gate. Naming it here would claim a registry authority that does not
exist and would read as an instruction to add the atom this plan declines to

#### 3. The two moduledocs the flip invalidates

**Files**: `test/statifier/statifier_if_test.exs`,
`test/statifier/statifier_foreach_test.exs`

**Changes**: prose only. Both moduledocs currently say
