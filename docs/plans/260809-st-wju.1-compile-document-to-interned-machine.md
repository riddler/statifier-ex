# Compile the Document to an interned Machine - Implementation Plan

## Overview

Stands up `Statifier.Compiler`, the pass between the validator and the
interpreter, and `Statifier.Machine`, the type it produces. A validated
`%Statifier.Document{}` goes in; a Machine comes out in which every state is an
integer index into a flat tuple, every state carries its parent index and a
contiguous self-inclusive descendant range, every transition and every
executable-content node carries a dense document-order index, every source
location survives, and every expression is compiled once into the single
`expr()` sum type. After this pass, ancestor tests, descendant tests, LCCA,
document-order sorting, and exit-set computation are integer or range
comparisons (ADR-0005).

Beads issue: st-wju.1. Research:
`docs/research/260809-st-wju.1-compile-document-to-interned-machine.md`.

The research recorded seven open questions and no human was available. Open
question 1 was subsequently decided by the user on 2026-08-09: predicator 4.0.0
has shipped, so this bead builds against 4.0's documented shape and the pin bump
is in scope (Phase 1). The remaining six are decided below under "Decisions",
each marked as an assumption a reviewer may overturn. One genuinely
human-gated question, discovered while planning and belonging to a later bead,
is recorded at the end; it does not block any phase here.

## Current State Analysis

`lib/statifier/` has `parser/`, `lowering/`, `document/` and `validator/`.
There is no `Statifier.Compiler`, no `Statifier.Machine`, and no
`lib/statifier/machine/` or `lib/statifier/compiler/` directory - the layer is
empty. `docs/architecture.md:47-51` places it between Validator and Machine, and
principle 4 (`docs/architecture.md:33-36`) is why the Machine must be a distinct
type rather than an enriched Document: the interpreter accepts a Machine and
nothing else.

The input side is complete and deliberately bare:

- `%Statifier.Document{}` is nine structs of pure syntax. No struct carries a
  `parent`, `depth`, `index`, `document_order`, or any lookup map
  (`lib/statifier/document.ex:7-10`). Document order is list order everywhere,
  guaranteed by `reverse_lists/1`
  (`lib/statifier/lowering/builders.ex:456-482`).
- Every node carries a six-field `Statifier.Parser.Location` span
  (`lib/statifier/parser/location.ex:13-37`) plus an `attribute_locations` map
  of per-attribute *value* spans that exists only for attributes the author
  actually wrote (`lib/statifier/document.ex:31-39`). `cond`'s span lives at
  `attribute_locations[:cond]`, not on a field of `Transition`.
- `<scxml>` is deliberately not a `%State{}`; the compiler synthesizes its
  index-0 root from the root struct's fields
  (`lib/statifier/document.ex:58-87`).
- `Transition.event` and `Transition.target` are already whitespace-split
  lists; the second-level split of a descriptor into dot-separated tokens is
  explicitly this bead's job (`lib/statifier/document/transition.ex:6-18`).
- The validator hands back the caller's own document unmodified
  (`lib/statifier/validator.ex:19-23`). It resolves no `initial`, resolves no
  target, compiles no expression, assigns no index, and widens no `kind`. Its
  `Statifier.Validator.Context` computes parent/ancestor/descendant relations
  in an ephemeral value whose moduledoc forbids the compiler from reusing it
  (`lib/statifier/validator/context.ex:1-8`).

Nothing under `lib/` calls predicator today; this pass is its first consumer.
`mix.exs:41` pins `{:predicator, "~> 3.8"}` and `mix.lock` holds 3.8.0, but
4.0.0 shipped to hex on 2026-08-09 and is the version every design document
describes.

## Desired End State

`Statifier.Compiler.compile/1` takes a validated `%Statifier.Document{}` and
returns `{:ok, %Statifier.Machine{}} | {:error, [Statifier.Compiler.Error.t()]}`,
where the only reachable error is a failed expression compilation. On the
Machine:

- `states` is a tuple of `%Statifier.Machine.State{}` in document order, index 0
  being the synthesized `:scxml` root. Each state carries `index`, `id`, `kind`,
  `parent`, `last` (the highest index in its subtree; the low end is `index`
  itself), `children`, resolved `initial` indexes, its selectable transitions'
  `t_index` list, `onentry`/`onexit` blocks of `c_index` lists,
  `history_children`, `history_type`, `history_default`, `donedata`, and
  `location`.
- `transitions` is a tuple of `%Statifier.Machine.Transition{}` indexed by
  `t_index`, dense over every `<transition>` element in the document.
- `contents` is a tuple of `%Statifier.Machine.Content{}` indexed by `c_index`,
  dense over every executable-content node in the document.
- `id_to_index` maps every written state id to its index; the reverse direction
  is `elem(states, i).id`, already total-with-nils, and is exposed as a function
  rather than a second map.
- Every `cond`, every `<log expr=...>`, every `<content expr=...>` and every
  `<content>` text body is one `expr()` value:
  `{:static, term()} | {:compiled, %Predicator.Compiled{}, source :: String.t()}`.

Verification that the end state holds:

- `mix quality` green with the new test modules under
  `test/statifier/compiler/` and `test/statifier/machine/`.
- A full-pipeline integration test drives a nontrivial SCXML document from a
  heredoc through `Parser -> Lowering -> Validator -> Compiler` and asserts every
  acceptance criterion on the bead directly: ranges contiguous and
  self-inclusive, parent/child agreement, document order matching source order,
  id maps round-tripping, `t_index`/`c_index` dense and ordered from zero,
  locations non-nil on every compiled state / transition / content node, and
  every expression slot holding an `expr()` value.
- `grep -rn "compiled_" lib/statifier/machine/` returns nothing: no
  `x`/`x_expr`/`compiled_x_expr` triple exists anywhere.

### Key Discoveries:

- Document order is already list order in every child list
  (`lib/statifier/lowering/builders.ex:456-482`), so a single depth-first walk
  assigns every index this pass needs; nothing has to sort.
- `attribute_locations[:cond].start_offset` is the base offset ADR-0014's
  arithmetic adds a within-expression span to, convertible back with
  `Location.at_offset/2` (`lib/statifier/parser/location.ex:7-10`).
- The validator owns every non-expression failure mode exclusively (checks 1-11
  at `lib/statifier/validator.ex:47-59`), so the compiler's error union has
  exactly one member. An unresolvable id in the compiler is a bug in the
  validator, not a user error.
- predicator 4.0's `compile_with_spans/1` returns `{:ok, %Predicator.Compiled{}}`
  but `{:error, binary()}` - a *formatted string*, never a `%ParseError{}`.
  Read directly from the 4.0.0 hex package on 2026-08-09
  (`lib/predicator.ex:690-693` for `compile_with_spans/1`, and its private
  `build_compiled_result/1` at `:751-760`, whose error clause formats
  `"#{message} at line #{line}, column #{column}"`). Structured
  `{line, column}` is reachable only through `Predicator.parse/2`
  (`lib/predicator.ex:777-784`), which returns
  `{:error, message, line, column}`. Re-confirm this against the installed dep
  once Phase 1 lands, since `deps/predicator` still holds 3.8.0 today.
- `Predicator.Errors.ParseError` at 4.0 has exactly `[:message, :position]`, both
  enforced; `:line` and `:column` are gone.
- `Credo.Check.Readability.PredicateFunctionNames` is enabled and `strict: true`
  (`.credo.exs:125`, `.quality.exs:26-28`). Probed empirically on 2026-08-09: it
  flags **both** `def is_compound_state` and `def is_compound_state?`. This
  constrains the naming of predicate functions added here (Decision 5).
- `mix gate.check`'s `mix.exs` guard matches by line content, not by path, and
  its pattern does not include `:predicator` (`lib/mix/statifier/gate_guard.ex:43`),
  so the Phase 1 pin bump needs no ledger entry.
- Binding ADRs, cited rather than re-argued: ADR-0005 (flat document-order
  array, parent pointers, descendant ranges, both index directions), ADR-0012
  item 3 (locations retained, document-order indexes assigned), ADR-0014 (the
  expression sum type, spans always on, what a failure names), ADR-0004
  (predicator permanently), ADR-0002/ADR-0003 (the Machine is plain data).

## What We're NOT Doing

- **No evaluation.** Nothing here evaluates an expression. `on_unbound: :error`
  (ADR-0014 item 5) and the `error.execution` payload (item 4) are st-af3's, not
  this bead's. This pass compiles and stores only.
- **No interpreter.** No Appendix D function is ported here. `get_transition_domain`,
  `compute_exit_set`, `select_transitions` and the rest land in st-wju.3 and
  consume this layout.
- **No `FeatureDetector` change.** `conditional_transitions: :unsupported`
  (`test/support/feature_detector.ex:53`) stays as it is; cond-bearing corpus
  documents keep out of the runtime until the epic's Phase 3. The compiler is
  complete for them now so that later flip is a switch, not a revisit.
- **No corpus regeneration.** `tools/corpus/scxml_w3/conf_predicator.xsl`
  already emits `==`/`===` throughout, and the checked-in generated tests already
  use them. See Corpus/Ratchet Notes.
- **No re-derived hierarchy cache.** v1's 376-line `HierarchyCache` with an
  O(n^2) LCCA matrix, `ancestor_paths`, `descendant_sets` and a
  `validate_cache/2` consistency checker is the thing ADR-0005 exists to
  delete. Ranges replace all of it.
- **No `depth` field.** v1 wrote it and never read it. It is
  `length(proper_ancestors(machine, index))` when something actually needs it.
- **No reuse of `Statifier.Validator.Context`**, per its own moduledoc
  (`lib/statifier/validator/context.ex:1-8`). The compiler builds its own
  relations in its own walk.
- **No edit to ADR-0004's text.** Its Decision line still reads `~> 3.5`. An
  accepted ADR records a decision as of its date; the live pin is `mix.exs`, and
  `docs/datamodel.md` is the living document that gets corrected (Decision 11).
- **No Credo or `.quality.exs` change.** The ADR-0002-versus-Credo collision on
  `is_in_final_state` is real but belongs to st-wju.3, and resolving it means
  editing gate config, which ADR-0011 makes a human's call with a ledger entry.
  Recorded at the end; nothing here needs it.
- **No `bd` action on st-2pj.** Phase 1 subsumes its acceptance criteria. A note
  on st-wju.1 says so; a human decides st-2pj's fate.

## Implementation Approach

The compiler is one depth-first walk over the document in source order,
followed by two resolution passes that need the walk's output:

1. **Numbering walk.** Depth-first, source order, synthesizing the root at index
   0. Assigns state indexes, `t_index` to every `<transition>` element
   encountered (including `<initial>` and history default transitions, in the
   position they occupy in the source), and `c_index` to every executable-content
   node. Builds `parent`, `children`, `last`, `history_children` and
   `id_to_index` on the way out of each subtree - `last` is the largest index
   handed out inside the subtree, which is exactly the recursion's return value,
   so contiguity is a property of the traversal rather than something asserted
   afterwards.
2. **Reference resolution.** With `id_to_index` complete, turn every
   `Transition.target` token list, every `initial` attribute token list, every
   `<initial>` element target and every history default target into index lists,
   and resolve the spec 3.3 first-child default for a compound state with no
   `initial` in either form. Every id here is guaranteed present by validator
   checks 2 and 3.
3. **Expression compilation.** With `t_index`/`c_index` assigned, compile every
   `cond`, `expr`, and `<content>` text into an `expr()`, collecting failures as
   `Statifier.Compiler.Error` values sorted by `location.start_offset`, mirroring
   `Statifier.Lowering.finalize/2` (`lib/statifier/lowering.ex:137-141`).

Phases follow the data rather than the passes, so each one lands a complete
slice of the Machine with its own tests: layout, then the expression seam, then
transitions, then executable content. The expression seam comes before the two
phases that consume it so neither has to land a raw-string field and then
change its type - a churn the ADR-0014 judge would have to read twice.

## Decisions

Each is a decision this plan makes, not a fact the codebase already states. A
reviewer may overturn any of them; the reasoning is recorded so overturning one
is cheap.

**1. predicator `~> 4.0`, not ADR-0014's 3.8 stopgap.** *(Open question 1 -
decided by the user on 2026-08-09.)* 4.0.0 shipped, so ADR-0014 item 1's own
conditional resolves in favour of spans and the stopgap is not taken. The
compiled arm is literally `{:compiled, %Predicator.Compiled{}, source}`, which
is what `docs/architecture.md:78`, `docs/datamodel.md:36`,
`docs/observability.md:82`, ADR-0014 item 2 and `lib/statifier/document.ex:18`
all already say. This subsumes st-2pj.

**2. The `<scxml>` root is state index 0, `kind: :scxml`.** The spec treats
`<scxml>` as a state for LCCA and transition-domain purposes, so including it
removes the special case from `get_transition_domain` rather than adding one.
`parent` is `nil` and `id` is `nil` (the root struct has `name`, not `id`), which
is itself the proof that the index-to-id direction must tolerate `nil`.

**3. Descendant ranges are self-inclusive, and only the high end is stored.**
`first == index` by construction, so storing it would be a duplicated fact - the
`depth`-written-and-never-read hazard v1 shipped. Each compiled state stores
`last` only, and `descendant?(machine, d, a)` is
`a.index <= d and d <= a.last`. Self-inclusive matches the spec's
descendant-or-self usage in entry sets; the one place it matters gets an inline
comment.

**4. `kind` stays the element kind; atomic/compound is derived.** The compiled
`kind` is `:scxml | :state | :parallel | :final | :history`. No `:atomic` /
`:compound` discriminator is stored: it is `children == []`, which is O(1) on a
list, and storing it is the second encoding of one fact that produced v1's
`:final`-is-not-`:atomic` divergence
(`lib/statifier/document/state.ex:25-34` records that history).

**5. Layout query functions use ordinary Elixir predicate names.**
`descendant?/3`, `ancestor?/3`, `atomic?/2`, `compound?/2`, `parallel?/2`,
`final?/2`, `history?/2`, `child_indexes/2`, `proper_ancestors/2`, `lcca/2`,
`document_order/2`, `exit_order/2` - not `is_atomic_state`/`is_atomic_state?`.
All twelve land in Phase 2 and are tested there; none of them is reserved for a
later bead, because each one is a two-line reader over the layout Phase 2
builds and leaving any of them out would mean st-wju.3 adds a function to this
module rather than only calling it. Two reasons for the naming: Credo's `PredicateFunctionNames` is on and strict and rejects both
`is_` forms (probed, see Key Discoveries), and ADR-0002's Decision names
fourteen functions, every one an interpreter function and none of them in this
bead. The `mix adr.check` similarity guard is over those fourteen names; none of
the names above is within its 0.84 threshold of any of them, and a bare
`mix quality` proves it.

**6. A cond compile failure is a collected compiler error carrying the
predicator `%ParseError{}` verbatim, in predicator's own coordinate space.**
*(Open question 2.)* The compile path is `Predicator.compile_with_spans/1`
(ADR-0014 item 1). It returns `{:error, binary()}` on failure - a formatted
string, no struct - so on that branch only, the compiler calls
`Predicator.parse(source, spans: true)` to recover `{message, line, column}` as
data and builds `Predicator.Errors.ParseError.new(message, line, column)`. The
re-parse costs one extra parse on the failure path and touches only public API,
which is why it beats scraping the message or reaching into
`Predicator.Compiler`. Coordinates are stored as predicator reports them
(expression-relative `{line, column}`) alongside the document `Location` of the
attribute value; the translation into document columns happens at *reporting*
time, not compile time. ADR-0014's consequences quote a message in document
terms but do not mandate translating early, and translating early would discard
the expression-relative position that a caret under the expression source needs.

**7. `Content.text` folds into the `expr()` sum type.** *(Open question 3.)*
`<content expr="...">` compiles to `{:compiled, ...}` and `<content>text</content>`
to `{:static, text}`, in one field. `docs/architecture.md:80-82` says every
foo/fooexpr pair stores one `expr` value evaluated by one function, and
`Content` is the only Phase 1 node with a static/expression alternative.
Validator check 9 already guarantees the two are never both present
(`lib/statifier/validator.ex:47-59`), so the sum type cannot lose information.
The static arm's diagnostic points at the `Content` node's own `location`,
because `Content.text` has no span of its own by design
(`lib/statifier/document/content.ex:17-21`).

**8. `<donedata>` content gets no `c_index`.** *(Open question 4.)* ADR-0012
item 3 assigns indexes to *executable content*, and donedata's `<content>` is
not executable content: it is not a `content_node()` in the Document's type
(`lib/statifier/document.ex:101`), it never appears in a block, and no
`execute_block` ever runs it. Putting it in the `c_index` space would stop
`c_index` meaning "the nth executable-content node", which is the property trace
effects rely on. It is reached through its owning final state's index, and its
own `location` and its `<content>` node's location are both retained, so nothing
about diagnostics is lost. When Phase 2 gives `<donedata>` `<param>` children,
that bead revisits this rather than inheriting it silently.

**9. `<initial>` and history default transitions do get a `t_index`.** *(Open
question 5.)* One dense document-order numbering over every `<transition>`
element in the document. They are real source elements whose executable content
runs (spec 3.3 for the `<initial>` transition, 3.6 for a history default), so
trace effects must be able to name them and tooling must be able to map the
index back to a location - which is exactly what ADR-0012 item 3 assigns indexes
for. Selectability is a property of *where a transition is stored*, not of its
index: `select_transitions` walks `state.transitions`, which holds only
selectable ones, while these live in `state.initial_transition` and
`state.history_default`. So no filtering is needed and no separate discriminator
field is stored.

**10. `id_to_index` is partial; the reverse direction is a field, not a map.**
*(Open question 6.)* `id_to_index :: %{String.t() => non_neg_integer()}` holds an
entry only for a state with a non-nil, non-empty id - mirroring `Checks.Ids`,
which excludes exactly those from its uniqueness set, so every entry it admits
is unique by validation. There is no `index_to_id` map: `elem(states, i).id` is
already that function, total with `nil`s, and a second map duplicating a field
on an O(1)-indexed tuple is v1's `state_lookup`-beside-the-tree anti-pattern.
ADR-0005's "the Machine keeps both directions" is satisfied at the API:
`Machine.index/2` and `Machine.id/2`.

**11. The `~> 3.5` drift is fixed in `docs/datamodel.md` only.** *(Open question
7.)* `docs/datamodel.md:3-4` becomes `~> 4.0`. ADR-0004's Decision line stays as
written; see "What We're NOT Doing".

**12. No top-level `initial` field on the Machine.** The bead's design suggests
one, but the root state at index 0 already carries resolved `initial` indexes,
and Decision 2 exists precisely so the root needs no special case. A second copy
would be the same duplicated fact Decision 3 rejects. `Machine.initial/1` reads
it off index 0.

## Phase 2: Interns states into the flat document-order layout

### Overview

Lands `Statifier.Machine`, `Statifier.Machine.State`, and
`Statifier.Compiler.compile/1` producing a states-only Machine: the numbering
walk, the id map, resolved `initial` indexes, and the layout query API that is
the whole point of ADR-0005. Transitions, executable content and expressions are
not yet compiled; the compiled state's slots for them arrive in Phases 4 and 5.

### Changes Required:

#### 1. The Machine and its query API
**File**: `lib/statifier/machine.ex`
**Changes**: the struct, the `expr()` type declaration (per
`docs/architecture.md:69-82` the sum type is a Machine `@type`, even though the
function that builds one lives in the compiler), and the layout queries.

```elixir
defstruct [:states, :id_to_index, :transitions, :contents,
           :name, :datamodel, :binding, :location]

@type expr :: {:static, term()} | {:compiled, Predicator.Compiled.t(), source :: String.t()}

@spec descendant?(t(), descendant :: non_neg_integer(), ancestor :: non_neg_integer()) :: boolean()
# Self-inclusive: `first` is the ancestor's own index by construction, so a
# state is its own descendant - which is the shape Appendix D's entry sets use
# (ADR-0005, plan Decision 3).
def descendant?(machine, d, a) do
  %{last: last} = at(machine, a)
  a <= d and d <= last
end

@spec ancestor?(t(), ancestor :: non_neg_integer(), descendant :: non_neg_integer()) :: boolean()
@spec lcca(t(), [non_neg_integer()]) :: non_neg_integer()
@spec proper_ancestors(t(), non_neg_integer()) :: [non_neg_integer()]
@spec child_indexes(t(), non_neg_integer()) :: [non_neg_integer()]
@spec atomic?(t(), non_neg_integer()) :: boolean()
@spec compound?(t(), non_neg_integer()) :: boolean()
@spec parallel?(t(), non_neg_integer()) :: boolean()
@spec final?(t(), non_neg_integer()) :: boolean()
@spec history?(t(), non_neg_integer()) :: boolean()
@spec index(t(), String.t()) :: {:ok, non_neg_integer()} | :error
@spec id(t(), non_neg_integer()) :: String.t() | nil
@spec document_order(t(), Enumerable.t()) :: [non_neg_integer()]
@spec exit_order(t(), Enumerable.t()) :: [non_neg_integer()]
```

All twelve of Decision 5's query functions land here, not just the ones spelled
out above: `atomic?/2` is `children == []`, `compound?/2` is its complement
restricted to `:state`/`:scxml`, and the remaining three kind predicates are
`kind` comparisons (Decision 4 - derived, never stored).

`transitions` and `contents` are present as empty tuples in this phase so the
struct shape does not change under later phases; they are populated in Phases 4
and 5.

#### 2. The compiled state
**File**: `lib/statifier/machine/state.ex`
**Changes**: the struct, with a kind-scoped field table in the moduledoc
following the precedent at `lib/statifier/document/state.ex:42-53`. Fields
landed in this phase: `index`, `id`, `kind`, `parent`, `last`, `children`,
`initial`, `history_type`, `history_children`, `location`. Fields declared but
left at their empty default until Phases 4-5: `transitions`, `onentry`,
`onexit`, `initial_transition`, `history_default`, `donedata`.

#### 3. The compiler pass and its error type
**File**: `lib/statifier/compiler.ex`
**Changes**: `compile/1`, the numbering walk, and reference resolution. Returns
`{:ok, Machine.t()} | {:error, [Compiler.Error.t()]}`. The walk returns the
highest index issued inside each subtree, which *is* the subtree's `last`, so

**File**: `lib/statifier/compiler/error.ex`

## Phase 3: Compiles expressions into the `expr()` sum type

### Overview

Lands the expression seam on its own, before either consumer, so neither Phase 4
nor Phase 5 has to land a raw-string field and change its type afterwards. This
is the ADR-0014 phase and the one `mix adr.judge` reads hardest at
`--profile merge`.

### Changes Required:

#### 1. Expression compilation
**File**: `lib/statifier/compiler/expressions.ex`
**Changes**: one public function, plus the failure-path re-parse of Decision 6.

```elixir
@spec compile(source :: String.t(), owner :: owner_ref(), location :: Location.t()) ::
        {:ok, Machine.expr()} | {:error, Compiler.Error.t()}
def compile(source, owner, location) do
  # ADR-0014 item 1: spans, not point positions. predicator 4.0's
  # compile_with_spans/1 returns the table with the instructions (item 2), so
  # nothing here can drop it - it is inside the value we store.
  case Predicator.compile_with_spans(source) do
    {:ok, %Predicator.Compiled{} = compiled} ->
      {:ok, {:compiled, compiled, source}}

    {:error, _formatted} ->
      # compile_with_spans/1 formats its parse error into a bare string, so the
      # structured position is recovered from parse/2 on the failure path only.
      {:error, parse_error(source, owner, location)}
  end
end

@spec static(term()) :: Machine.expr()
def static(value), do: {:static, value}
```

`owner_ref` is `{:transition, t_index} | {:content, c_index} | {:donedata, state_index}`,
so the error names the owning node's ADR-0012 constraint-3 identity as well as
the source and the position (ADR-0014 item 4).

## Testing Strategy

### Unit Tests:

Every test drives the full pipeline from an XML heredoc, using the local
helper shape the validator tests already established
(`test/statifier/validator_test.exs:9-13`), extended by one step:

```elixir
defp compile!(xml) do
  {:ok, root} = Parser.parse(xml)
  {:ok, document} = Lowering.lower(root)
  {:ok, document} = Validator.validate(document, xml)
  {:ok, machine} = Compiler.compile(document)
  machine
end
```

The bead's fallback ("until then, construct Document structs literally") is no
longer needed - lowering and the validator have both landed.

What to test, and where:

- `test/statifier/machine_test.exs` - the query API: `descendant?/3` on self, on
  a child, on a sibling, across a parallel boundary; `lcca/2` for two siblings,
  for a state and its own ancestor, for states in different parallel regions;
  `document_order/2` and `exit_order/2` as exact inverses; `index/2` and `id/2`
  round-tripping and both failing shapes (unknown id, nameless index);
  `child_indexes/2` in source order; and each of `atomic?/2`, `compound?/2`,
  `parallel?/2`, `final?/2`, `history?/2` on a state of its own kind and on one
  of another, including the case Decision 4 exists for - a `:final` is atomic
  and is not compound.
- `test/statifier/compiler_test.exs` - the numbering walk and `initial`
  resolution, including all three `initial` sources and the atomic/final/history
  empty cases.
- `test/statifier/compiler/expressions_test.exs` - the three `expr()` outcomes
  and the failure shape.
- `test/statifier/machine/transition_test.exs`,
  `test/statifier/machine/content_test.exs` - `t_index`/`c_index` density and
  ordering, target resolution, descriptor tokenizing, block and donedata shape.
- `test/statifier/compiler/acceptance_test.exs` - one test per bead acceptance
  criterion.

Key edge cases: a document that is a single atomic state (root plus one, ranges
degenerate); a nameless state (absent from `id_to_index`, present in `states`);
a targetless transition; a state whose only child is a history state combined
with an explicit `initial` (legal - validator check 7 only rejects the *default*
case); two bad conds in one document, so error collection rather than
short-circuiting is proved; `event=""` versus an absent `event`, which lowering
renders identically as `[]` and only `attribute_locations` distinguishes.

Sabotage discipline (`docs/testing.md:85-127`): one
`# sabotage: <what was broken> -> red` line above every `test` line that asserts
`lib/` behavior, above any `@tag`. Deleting a function body does not count. The
bead names the model mutation: swap two children's numbering and watch the range
assertions go red.

## Performance Considerations

- `states`, `transitions` and `contents` are tuples rather than lists or maps, so
  index lookup is `elem/2` and constant-time. That is the whole reason for
  interning; a map from integer to struct would give up the property ADR-0005
  was adopted for.
- Descendant and ancestor tests are two integer comparisons against a single
  stored `last`, replacing v1's `HierarchyCache` with its O(n^2) LCCA matrix,
  materialized `descendant_sets`, and cache-validity checker.
- `lcca/2` walks up from the first state's parent and stops at the first ancestor
  whose range covers every index in the list, which is O(depth) with no
  allocation beyond the ancestor walk, and no precomputation.
- The compiler is one depth-first pass plus two linear resolution passes over
  already-collected node lists. Nothing sorts: document order is list order out
  of lowering.
- The permanent memory cost is locations and index tables, which ADR-0012 already
  accepts, plus one `%Predicator.Compiled{}` per expression. There are no
  duplicated facts to keep consistent: `first`, `depth`, a reverse id map, and a
  second copy of the top-level `initial` are all deliberately absent
  (Decisions 3, 10, 12).
