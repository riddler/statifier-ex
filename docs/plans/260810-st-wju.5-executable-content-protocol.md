# Executable content protocol with raise and log - Implementation Plan

## Overview

Defines the one `Statifier.ExecutableContent` protocol - `execute(node, context)`
returning `{:ok, context, [effect]} | {:error, reason}` - implements it for the
two datamodel-free nodes (`<raise>`, `<log>`), and lands the block runner that
executes a list of content nodes in document order, stops on the first error,
converts that error into `error.execution` on the internal queue, and wraps the
whole block in a gated `Trace.ContentExecuted` effect. The runner replaces the
private no-op `execute_block/3` stub st-wju.4 left in
`lib/statifier/interpreter/exit_entry.ex:245`, so all four existing call sites
(`<onexit>`, `<onentry>`, an `<initial>` transition's content, default history
content) begin actually running content with no change to where or in what
order blocks run.

The deliverable that outlives this bead is the *contract*: st-af3's `<assign>`,
`<if>`/`<elseif>`/`<else>`, `<foreach>`, `<script>` and st-cmq's `<send>` /
`<cancel>` / `<invoke>` implement the protocol for their own node structs and
never touch the interpreter (`docs/architecture.md:101-105` - "No central
dispatcher with per-struct clauses and a parallel summary function to keep in
sync").

Bead: st-wju.5. No research document exists; the bead's description, its
acceptance criteria, and its 2026-08-09 note are the specification, read
alongside ADR-0002 (literal port), ADR-0003 (pure core with effects), ADR-0012 /
`docs/observability.md` (constraints 2, 3, 4), `docs/datamodel.md` (the
evaluation-context seam Phase 3 needs), and the landed sibling plans - in
particular `docs/plans/260810-st-wju.4-ports-exit-and-entry-sets.md` (which
created the seam this bead fills) and
`docs/plans/260809-st-wju.2-machine-state-event-effects-vocabulary.md` (the
effect and cause vocabulary).

**A note on the word "phase".** The project roadmap numbers its own phases -
Phase 1 is the core engine (this epic, `st-wju`), Phase 3 is the datamodel
(`st-af3`), Phase 4 is sessions and invoke (`st-cmq`). This plan numbers its
four implementation phases independently. Every reference to a roadmap phase
below names the bead too ("the datamodel bead, st-af3"); a bare "Phase N" always
means a phase of *this* plan.

No human was available while this plan was written. Every question the bead left
open is settled below under "Decisions", each stated as an assumption a reviewer
may overturn; the five least settled are listed again under "Open Questions" so
a reviewer can find them without reading the whole document.

## Current State Analysis

Nothing in `lib/` executes any content node today, and no protocol exists
anywhere in the repo (`grep -r defprotocol lib test` returns nothing).

What exists and must be consumed rather than duplicated:

- **The seam.** `Statifier.Interpreter.ExitEntry.execute_block/3`
  (`lib/statifier/interpreter/exit_entry.ex:240-245`) is private and returns
  `{machine_state, []}` unconditionally. Its four call sites already pass the
  `Machine.Content.owner()` identity the runner needs: `run_onexit_blocks/2`
  (`:224-233`) passes `{:onexit, state_index, ordinal}`, `run_onentry_blocks/2`
  (`:637-646`) passes `{:onentry, state_index, ordinal}`, and
  `run_transition_content/3` (`:702-710`) passes `{:transition, t_index}` for
  both the `<initial>` transition's content (via
  `run_initial_transition_content/3`, `:692-697`) and the default history
  transition's content (via `run_default_entry/3`, `:662-681`) - two owners, one
  code path. `default_history_content` deliberately stores a `t_index` rather
  than a `[c_index]` (st-wju.4 Decision 5) precisely so that owner survives to
  here.
- **`Statifier.Machine.Content`** (`lib/statifier/machine/content.ex`) - **one**
  struct for both node kinds, discriminated by a `kind :: :raise | :log` field,
  with a moduledoc table (`:15-22`) listing which of `event` / `label` / `expr` /
  `expr_location` is meaningful on which kind. It also owns `owner/0` (`:39-56`),
  the block-identity type `Statifier.Effect.Trace.ContentExecuted` aliases and
  `Statifier.Event.Cause.origin/0` embeds. **This single struct is the central
  obstacle to protocol dispatch** - see Decision 1.
- **`Statifier.Machine.content/2`** (`lib/statifier/machine.ex:114-115`) -
  `elem(contents, c_index)` over a dense tuple; `@spec` already returns
  `Content.t()`, so a union type is a drop-in.
- **`Statifier.Compiler`** - `build_content_node/2`
  (`lib/statifier/compiler.ex:539-565`) already has three clauses (raise; log
  without `expr`; log with `expr`, compiled through `Expressions.compile/3` with
  owner tag `{:content, c_index}`). `%MContent{}` is constructed *only* here;
  `assign_content_nodes/2` (`:339-354`) assigns dense document-order `c_index`es.
- **`Statifier.MachineState`** - `raise_internal/4` (`:240-249`), whose `@doc`
  already names this bead's `<raise>` as its caller and specifies the
  `{:content, c_index, owner}` origin; `raise_platform/4` (`:266-281`), added by
  st-wju.4, which is what `error.execution` wants (spec 5.10.1 and
  `Statifier.Event`'s moduledoc both classify `error.*` as `:platform`).
  Neither writes the counters, so a whole block executes at one
  `(macrostep, microstep)` stamp.
- **`Statifier.Effect`** - the `trace/3` macro (`:146-156`, single evaluation,
  lazy fields), `trace?/1` (`:130-131`), and the vocabulary table which already
  assigns the `:log` row (`:30`) and the `Trace.ContentExecuted` row (`:34`) to
  this bead and to nothing else.
- **`Statifier.Effect.Log`** (`lib/statifier/effect/log.ex`) - `label`, `value`,
  `c_index`, `macrostep`, `microstep`. Built by struct literal today; it has no
  `new/2` and **no `owner` field** (Decision 6).
- **`Statifier.Effect.Trace.ContentExecuted`** - `new/2`-built, `owner` +
  `c_indexes` + counters, `c_indexes` documented as "the run content nodes'
  identities, in execution order".
- **`Statifier.Event.Cause`** - `origin` is
  `{:content, c_index, Content.owner()} | {:state, state_index}`; the

### The obstacle this bead has to clear first

`Statifier.Machine.Content` is a single struct with a `kind` tag. An Elixir
protocol dispatches on the *struct module*, so `defimpl Statifier.ExecutableContent,
for: Statifier.Machine.Content` can only be **one** implementation that then
switches on `kind` - which is exactly the central dispatcher with per-kind
clauses that `docs/architecture.md:101-105` and the bead's own first sentence
reject, and which would force st-af3 to add a `kind` value and a clause to a
shared struct for every new element. Decision 1 splits the struct.

## Desired End State

Five new modules and one replaced stub:

- `Statifier.ExecutableContent` (`lib/statifier/executable_content.ex`) - the
  protocol, `execute(node, context)`.
- `Statifier.ExecutableContent.Context`
  (`lib/statifier/executable_content/context.ex`) - the threaded context struct,
  `machine_state` + `owner`.
- `Statifier.Machine.Content.Raise` and `Statifier.Machine.Content.Log`
  (`lib/statifier/machine/content/raise.ex`, `log.ex`) - the two compiled node
  structs, each with its `defimpl` in the same file.
- `Statifier.Interpreter.Content`
  (`lib/statifier/interpreter/content.ex`) - the block runner,
  `execute_block/3`.
- `Statifier.Machine.Content` keeps its module name and its `owner/0` type but
  stops being a struct; it gains `@type t :: Raise.t() | Log.t()`.
- `Statifier.Interpreter.ExitEntry.execute_block/3`'s body becomes a call to
  `Statifier.Interpreter.Content.execute_block/3`. No call site moves.

The behavioral end state, stated so a reviewer can check it without the spec in
hand:

- **Dispatch.** `ExecutableContent.execute(node, context)` dispatches on the node
  struct. A struct defined entirely outside `lib/` that implements the protocol
  runs through the block runner unmodified - proven by a test-only node in
  `test/support/`.
- **Block semantics (spec 3.9 / 4.x).** A block's nodes run in document order,
  threading one context. On `{:error, reason}` from a node, the remainder of that
  block does not run, `error.execution` goes onto the internal queue (type
  `:platform`, cause `{:content, c_index, owner}`, `data: reason`), and the
  block returns. Effects produced by nodes that already ran are kept, in order.
  Other blocks are unaffected - two `<onentry>` elements on one state are two
  separate blocks, and the second still runs after the first errored.
- **`<raise>`.** Enqueues an `:internal` event named by its literal `event`
  attribute, FIFO, via `MachineState.raise_internal/4` with origin
  `{:content, c_index, owner}` and the machine_state's counters. Emits **no**
  effect.
- **`<log>`.** Emits exactly one `{:log, %Effect.Log{}}` carrying `label`,
  `value`, `c_index`, `owner`, and the counters. `value` is the static value when
  the compiled `expr` is `{:static, term}`, and `nil` when it is
  `{:compiled, _, _}` (unevaluated until st-af3) or absent. Changes no
  machine_state.
- **Trace.** After a non-empty block finishes, one gated
  `Trace.ContentExecuted` is appended carrying the block's `owner` and the
  `c_indexes` that actually executed, in execution order. An empty block emits
  nothing at all. Trace off produces zero `Effect.trace?/1` members.
- **The four exit/entry call sites now run content.** Entering a state with
  `<onentry><raise event="foo"/></onentry>` puts `foo` on the internal queue;
  exiting one with `<onexit><log label="bye"/></onexit>` returns a `:log` effect.

Verification: `mix quality` green with coverage at or above the floor;
`mix gate.verify` confirming the run was full and unscoped; `mix adr.check`
clean; `test/statifier/interpreter/content_acceptance_test.exs` asserting every
acceptance-criteria line a test can decide.

## What We're NOT Doing

- **No expression evaluation.** `<log expr="...">` carries its compiled
  expression unevaluated; `value` is the static value or `nil`, with an inline
  comment naming st-af3 - the same treatment st-wju.4 Decision 10 gave
  `<donedata>`. This is not a rescue-to-default at a leaf: nothing failed, the
  value simply has not been evaluated yet, and `FeatureDetector` flunks any
  document with a datamodel expression.
- **No `<assign>`, `<if>`/`<elseif>`/`<else>`, `<foreach>`, `<script>`,
  `<send>`, `<cancel>`, `<invoke>`.** They are the beads (st-af3, st-cmq) the
  protocol exists to serve. This bead adds no node struct, no lowering builder,
  and no validator check for them.
- **No `microstep`, no `macrostep`, no interpreter entry point.** st-wju.6. This
  bead calls neither `begin_macrostep/1` nor `begin_microstep/1`, so every node
  in a block stamps the same counters.
- **No change to where or in what order blocks run.** st-wju.4 owns that, and
  the stub's four call sites and their `owner` arguments are consumed exactly as
  landed. In particular this bead does not reorder onentry-then-default-entry-
  then-default-history, and does not add a fifth call site.
- **No `Trace.ContentExecuted` from `ExitEntry`.** The emission belongs to the
  runner, per st-wju.4's own note and `lib/statifier/effect.ex:34`.
- **No structural error type.** `{:error, reason}` carries a bare `term()`;
  `error.execution`'s `data` is that term. Turning `reason` into a struct with a
  message, a location, and a predicator span is st-af3's work, when there is a
  real failure to describe (ADR-0014). The protocol's return type does not
  change when that happens.
- **No new lowering, validator, or document-layer work.** `Statifier.Document.Raise`
  and `Statifier.Document.Log` already exist and are already validated; the
  split in Decision 1 is entirely below the Document layer.
- **No `FeatureDetector` change and no conformance ratchet movement.** See
  "Corpus/Ratchet Notes".
- **No changelog fragment.** Nothing here is reachable from a public API until
  st-wju.7 (`changelog.d/README.md` - most changes need none).
- **No `Effect.Log.new/2` constructor.** Considered, for symmetry with the trace
  payloads' `new/2`. Rejected: `Effect.Log` is a *core* effect, and the trace
  `new/2` convention exists specifically so the counters cannot be forgotten
  behind the `trace/3` gate. `Log` has exactly one producer in the whole
  codebase (the `<log>` impl), so a constructor would be a module to keep in sync
  with one call site. Recorded here because a reviewer may reasonably ask.
- **No caching or memoization of `Machine.content/2` lookups.** See "Performance
  Considerations".

## Implementation Approach

Four phases, in dependency order, each adding code together with its own tests
so no phase leaves an untested function behind to sink the coverage floor:

1. **Split the compiled node struct** (Decision 1). A pure refactor with no
   behavior change: `Machine.Content` becomes a namespace holding `owner/0` and a
   `t()` union, `Content.Raise` and `Content.Log` become the structs, and the
   compiler builds the right one. Green on its own, and it de-risks everything
   after it - if this is wrong, it is wrong before any protocol exists.
2. **The protocol, the context, and the two implementations.** Dispatch is
   testable directly (`ExecutableContent.execute(node, context)`) with no runner
   and no interpreter, which is what makes this a phase rather than half of one.
   The test-only node lands here too, since open extension is a property of the
   protocol, not of the runner.
3. **The block runner, the error conversion, the trace, and the seam.** The one
   phase that changes observable interpreter behavior: `ExitEntry`'s stub starts
   running content.
4. **The acceptance test, the documentation, and the cross-bead notes.**

Phases 1 and 2 are separable along a real boundary (the Machine layer versus the
protocol layer) and neither leaves an intermediate gate red: Phase 1's split is
consumed by the existing compiler and its existing tests, and Phase 2's protocol
is consumed by its own tests. Phase 3 is where they meet. Phases do not
parallelize across worktrees; `docs/workflow.md`'s parallelism is across beads.

Every design question is settled below before any code is written, because
st-af3 and st-cmq both implement against these signatures.

## Decisions

**Decision 1 - `Statifier.Machine.Content` splits into one struct per node kind.**

```elixir
# lib/statifier/machine/content.ex - no longer a struct
defmodule Statifier.Machine.Content do
  alias Statifier.Machine.Content.Log
  alias Statifier.Machine.Content.Raise

  @type owner ::
          {:onentry, non_neg_integer(), non_neg_integer()}
          | {:onexit, non_neg_integer(), non_neg_integer()}
          | {:transition, non_neg_integer()}

  @type t :: Raise.t() | Log.t()
end

# lib/statifier/machine/content/raise.ex
defmodule Statifier.Machine.Content.Raise do
  @enforce_keys [:c_index, :event, :location]
  defstruct [:c_index, :event, :location]
end

# lib/statifier/machine/content/log.ex
defmodule Statifier.Machine.Content.Log do
  @enforce_keys [:c_index, :location]
  defstruct [:c_index, :location, label: nil, expr: nil, expr_location: nil]
end
```

This is the load-bearing decision of the bead, and it is forced rather than
chosen. An Elixir protocol dispatches on the struct module. With one struct and a
`kind` tag there is exactly one possible `defimpl`, whose body must switch on
`kind` - the central dispatcher with per-struct clauses that
`docs/architecture.md:101-105` names as the v1 mistake this rewrite exists to fix,
and that the bead's own first sentence rejects. It also makes st-af3's job
"add a `kind` value and a clause to a struct shared with every other element",
which is the parallel-summary-function failure mode one step removed.

Three further arguments, none of them decisive alone:

- `Machine.Content`'s own moduledoc already carries a "Fields that are
  kind-scoped" table (`:15-22`) - an admission in the module's own words that
  four of its seven fields are meaningless on one kind or the other. The split
  deletes the table instead of extending it with a row per st-af3 element.
- The Document layer already has per-element structs (`Statifier.Document.Raise`,
  `Statifier.Document.Log`). The union struct is an asymmetry introduced at the
  Machine layer, not a codebase-wide convention.
- `@enforce_keys` becomes meaningful again: `Raise.event` is mandatory (the
  lowering builder already errors without it,
  `lib/statifier/lowering/builders.ex:210-232`), which the shared struct could
  not express.

Blast radius, verified by grep: `%MContent{}` is constructed in exactly one
place (`lib/statifier/compiler.ex:539-565`, three clauses, one per shape);
`Content.t()` appears in one `@spec` (`lib/statifier/machine.ex:114-115`) and is
satisfied by the union unchanged; `Content.owner()` is referenced by
`Statifier.Event.Cause` and `Statifier.Effect.Trace.ContentExecuted` and does not
move; four `Effect.*` moduledocs mention `%Statifier.Machine.Content{}` in prose
and get a wording fix. Two test files assert on the struct:
`test/statifier/machine/content_test.exs` (the field assertions), and
`test/statifier/compiler/acceptance_test.exs:298-329`, whose "no compiled struct
has a `compiled_` field" test calls `mod.__struct__()` over a hardcoded list of
five `Statifier.Machine.*` modules including `Content` - it raises
`UndefinedFunctionError` the moment `Content` stops being a struct, so Phase 1
replaces that entry with the two new node structs rather than dropping it (the
test's own property - no `compiled_` field, no `x`/`x_expr` pair - applies to
them just as it did to the union struct).

The alternative - one `defimpl` for `Machine.Content` switching on `kind` -
would be a smaller diff today and would fail the bead's first acceptance
criterion ("no central dispatcher") on the day st-af3 adds its first node. It is
recorded under "Open Questions" as the reversible half of this call.

**Decision 2 - the protocol is `Statifier.ExecutableContent`, with one function.**

```elixir
defprotocol Statifier.ExecutableContent do
  alias Statifier.Effect
  alias Statifier.ExecutableContent.Context

  @type result :: {:ok, Context.t(), [Effect.t()]} | {:error, term()}

  @spec execute(node :: t(), context :: Context.t()) :: result()
  def execute(node, context)
end
```

No `@fallback_to_any`: a node struct reachable from a `c_index` that does not
implement the protocol is a compiler bug, and `Protocol.UndefinedError` naming
the struct is a better diagnosis than any fallback could be. This is the
`Machine`-is-valid-by-construction principle (`docs/architecture.md:34-37`)
applied to content nodes.

**Decision 3 - `context` is a struct, not a bare `MachineState`.**

```elixir
defmodule Statifier.ExecutableContent.Context do
  @enforce_keys [:machine_state, :owner]
  defstruct [:machine_state, :owner]

  @type t :: %__MODULE__{
          machine_state: MachineState.t(),
          owner: Content.owner()
        }
end
```

The bead asks for this decision to be recorded "with the Phase 3 datamodel
threading in view", so here is the reasoning in full:

- **A bare `MachineState` cannot work today.** `<raise>` needs
  `{:content, c_index, owner}` for its cause, and `owner` is a property of the
  *block*, not of the node or of the machine_state. With a two-argument protocol
  function there is nowhere else to put it.
- **A struct is where st-af3's per-macrostep evaluation context goes.**
  `docs/datamodel.md:41` commits to building the predicator context once per
  macrostep rather than per expression. That memoized context is neither
  machine_state (it is derived, and rebuilt when the datamodel changes) nor
  node-local. Adding a field to this struct is how it arrives, and it changes no
  protocol signature and no implementation that does not read it.
- **Adding a *third* protocol argument later would change every implementation.**
  The struct is the versionable slot; the arity is not.

`machine_state` stays a full `MachineState.t()` rather than a projection of it:
`<send>` and `<invoke>` (st-cmq) read the configuration and the machine, and
narrowing now would be a guess about which fields a future node needs.

**Decision 4 - the return shape is `{:ok, context, [effect]} | {:error, reason}`.**

The bead writes "`{context, [effect]}` or an error". A bare two-tuple beside
`{:error, reason}` is unambiguous (a `%Context{}` first element cannot be
`:error`), but the tagged form is what CLAUDE.md's own rule asks for - "evaluations
return `{:ok, v} | {:error, e}`" - and what every other result-shaped function in
this codebase uses. The deviation from the bead's literal wording is
presentational, and it is named here so a reviewer does not read it as a missed
requirement.

`reason` is a bare `term()` (see "What We're NOT Doing"). The runner is what
turns it into an event, so no implementation ever constructs an `Event`, and
"only the interpreter raises `error.execution`" (ADR-0003's error model, the
bead's third acceptance criterion) holds structurally rather than by convention.

**Decision 5 - the block runner is `Statifier.Interpreter.Content.execute_block/3`,
and `ExitEntry`'s private stub delegates to it.**

```elixir
@spec execute_block(
        machine_state :: MachineState.t(),
        owner :: Content.owner(),
        c_indexes :: [non_neg_integer()]
      ) :: {MachineState.t(), [Effect.t()]}
def execute_block(machine_state, owner, c_indexes)
```

The signature is st-wju.4's stub signature verbatim, so its four call sites are
untouched. `ExitEntry`'s private `execute_block/3` keeps its name and its
`@spec` and gains a one-line body; the alternative (deleting it and calling the
runner at four sites) trades one changed body for four changed call sites in a
module this bead does not own.

The module lives under `lib/statifier/interpreter/` because it is interpreter
code and `Mix.Statifier.AdrGuard`'s `@interpreter_pattern`
(`lib/mix/statifier/adr_guard.ex:50`) is what subjects interpreter code to the
ADR-0002 naming stage; a runner outside that directory would silently escape it.
Naming note for the implementer: `ExitEntry` currently does
`alias Statifier.Machine.Content` (`:74`) solely to write `Content.owner()` in
one `@spec`. That alias is dropped in favour of `Machine.Content.owner()`
(`Machine` is already aliased), freeing the bare `Content` name for
`alias Statifier.Interpreter.Content`.

**Decision 6 - `Effect.Log` gains an `owner` field.** The bead asks for the log
effect to "carry the `c_index` and counters so a session-side subscriber can
correlate it (cheap now, annoying to retrofit)", and its acceptance criterion
says "label, identity fields, counters". A bare `c_index` is exactly the identity
`Statifier.Event.Cause`'s post-review correction found insufficient
(`lib/statifier/event/cause.ex:28-42`): it resolves to the node's own `Location`
but names nothing about which `<onentry>`/`<onexit>` block or transition the node
sits in. The runner knows the owner - it is an argument - so the same correction
is applied here rather than left for a later bead to retrofit onto a struct with
consumers. Additive: `owner` is a new nilable field with a `@typedoc` pointing at
`Machine.Content.owner/0`, exactly as `ContentExecuted` does.

**Decision 7 - `<raise>` emits no effect, and `<log>` changes no machine_state.**
Straight from the bead. `<raise>`'s queued event is core state, not an effect
(`MachineState.raise_internal/4`, which builds the cause from the origin and the
counters so no call site can forget it). `<log>`'s output is an effect and
nothing else - ADR-0003's whole point is that the core does not log, it returns
log entries. Two named tests pin the negative halves: a `<raise>` block returns
an empty effect list, and a `<log>` block returns a machine_state equal to the
one it was given.

**Decision 8 - stop-on-error is implemented now, including the `error.execution`
raise, and is tested with a test-only failing node.**

The bead's parenthetical - "Phase 3 wires the actual raising - Phase 1 nodes
cannot fail" - reads at first as "defer the raise". It is read here as "Phase 3
supplies nodes that can actually fail", because the bead's own acceptance
criteria demand the behavior in this bead: "Errors-are-events conversion in the
runner, not in leaf nodes" and "Sabotage: runner continuing past an error turns
the stop-on-error test red". A stop-on-error path with no conversion could not
satisfy either. So:

- On `{:error, reason}` from node `c_index`, the runner stops, calls
  `MachineState.raise_platform(ms, "error.execution", {:content, c_index, owner},
  data: reason)`, and returns.
- `raise_platform/4` rather than `raise_internal/4`: spec 5.10.1 and
  `Statifier.Event`'s moduledoc (`:8-17`, `:76-81`) both classify `error.*` as a
  platform event, and st-wju.4's Decision 8 already established that `type` must
  not be stamped `:internal` for platform-raised events. The origin is still
  `{:content, c_index, owner}` - the platform raised it, *about* a content node.
- Nodes that already ran keep their effects, in order. The failing node
  contributes none (it returned an error, not a partial success).

**Decision 9 - `Trace.ContentExecuted` is emitted last, carries the nodes that
actually executed, and an empty block emits nothing.**

Unlike `Trace.ExitSet` / `Trace.EntrySet` - computed before acting and therefore
emitted first (st-wju.4 Decision 13) - `ContentExecuted` reports what ran, which
is only known afterwards, and its own `@doc` says `c_indexes` are "the run
content nodes' identities, in execution order". So it is appended after the
block's effects. The `@doc` on the runner states this difference explicitly so a
consumer reading a mixed effect list is not surprised.

On error, the trace is still emitted, and the `c_indexes` list *includes* the
node that returned the error - it executed, it just failed - so the list is a
prefix of the block. The failing node is identified by the `error.execution`
event's cause, not by absence from the trace.

An empty block (`<onentry/>`, or a transition with no content) returns
`{machine_state, []}` immediately, before the trace gate: nothing ran, so there
is nothing to report, and the untraced hot path keeps the cheapest possible
shape for the common case. Named test.

**Decision 10 - `<log>`'s `value` is the static value or `nil`.**

```elixir
# st-af3 evaluates a compiled expr; until then `value` is the static value or
# nil. Not a rescue-to-default - nothing failed, the expression simply has not
# been evaluated yet (`docs/datamodel.md`), and FeatureDetector flunks any
# document carrying one.
defp value(%Log{expr: nil}), do: nil
defp value(%Log{expr: {:static, term}}), do: term
defp value(%Log{expr: {:compiled, _compiled, _source}}), do: nil
```

Exactly the shape and the reasoning st-wju.4's `static_donedata/2` used
(`lib/statifier/interpreter/exit_entry.ex:817-825`), so the two places that
carry an unevaluated expression until st-af3 look the same and are found by the
same grep.

**Decision 11 - the test-only node is one struct in `test/support/`, data-driven.**

```elixir
defmodule Statifier.TestContent do
  defstruct [:c_index, :label, fail: false]
end

defimpl Statifier.ExecutableContent, for: Statifier.TestContent do
  # succeeds with one marker :log effect, or returns {:error, {:test_content, label}}
end
```

One struct covers both jobs the acceptance criteria need: it proves open
extension (a node defined entirely outside `lib/` runs through the runner
untouched) and it is the failing node the stop-on-error criterion requires. It
lives in `test/support/` because `elixirc_paths(:test)` compiles that directory
into the app only under `MIX_ENV=test` (`mix.exs:36-37`), so the impl
consolidates in the test env and cannot reach `dev`/`prod`. No `mix.exs` change,
therefore no ADR-0011 ledger entry.

Getting it in front of the runner: the runner resolves nodes through
`Machine.content/2`, so a test compiles a real document and then substitutes
`%{machine | contents: put_elem(machine.contents, i, %TestContent{...})}`. That
is a Machine built by the compiler with one cell replaced, not a `%Machine{}`
literal, so it stays inside st-wju.4's fixture rule. The technique is stated in
"Testing Strategy" so it is not reinvented per test.

**Decision 12 - the runner threads the context; the counters do not move.**
`execute_block/3` builds one `%Context{machine_state: ms, owner: owner}`, folds
the `c_indexes` through it, and unwraps `context.machine_state` at the end. Since
neither `begin_macrostep/1` nor `begin_microstep/1` is called anywhere in this
bead, every node in a block - and every event and log effect it produces - stamps
the same `(macrostep, microstep)` pair. A named test asserts that two `<raise>`
nodes in one block produce two causes with identical counters, so st-wju.6
cannot quietly change it later without a red test.

## Phase 3: Runs blocks, converts errors, and fills the exit/entry seam

### Overview

`Statifier.Interpreter.Content.execute_block/3`: document order, stop-on-error
with the `error.execution` conversion, effect-order preservation, and the gated
`Trace.ContentExecuted` wrap - then `ExitEntry`'s stub delegates to it and the
interpreter starts actually running content.

### Changes Required:

#### 1. The runner

**File**: `lib/statifier/interpreter/content.ex` (new)
**Changes**: the module and `execute_block/3` of Decision 5. Body:

1. `[]` returns `{machine_state, []}` immediately (Decision 9 - empty block, no
   trace).
2. Build `%Context{machine_state: machine_state, owner: owner}`.
3. Fold `c_indexes`, resolving each through
   `Machine.content(context.machine_state.machine, c_index)` and calling
   `Statifier.ExecutableContent.execute/2`, accumulating effects in order and
   accumulating the executed `c_indexes` in order. `{:error, reason}` halts the
   fold (`Enum.reduce_while/3`) with the failing `c_index` recorded.
4. On halt: `MachineState.raise_platform(ms, "error.execution",
   {:content, failed_c_index, owner}, data: reason)` (Decision 8).
5. Append `Effect.trace(machine_state, Effect.Trace.ContentExecuted, owner: owner,
   c_indexes: executed)` - `machine_state` here is the *final* one, since the
   counters are identical either way (Decision 12) and the final one is what the
   effect list is being built from. The `@doc` records st-wju.4 Decision 13's
   hygiene note: `trace/3` binds its own `machine_state` inside a hygienic quote,
   so a local of the same name is not shadowed.
6. Return `{context.machine_state, effects ++ trace_effects}`.

document order, stop-on-error, "other blocks are unaffected", where the trace
sits in the list and why it differs from `ExitSet`/`EntrySet`, and that
`error.execution` is raised here and only here so leaves never do.

**How a test-only node reaches the runner.** The runner resolves nodes through
`Machine.content/2`, so a test compiles a real document and substitutes one cell:
`%{machine | contents: put_elem(machine.contents, idx, %Statifier.TestContent{...})}`.
That is a compiler-built Machine with one cell replaced, not a `%Machine{}`
literal, so it stays inside st-wju.4's fixture rule; the substituted index is
named in a comment in each test that uses it. The alternative - a real node that
can fail - does not exist until st-af3, which is exactly why the bead asks for a
test-only node.

**What a sabotage of the stop-on-error test must show.** The bead names this one
explicitly: "runner continuing past an error turns the stop-on-error test red".
The mutation is `Enum.reduce_while/3` -> `Enum.reduce/3` with the error ignored,
and the failure must be about the *third* node's effects appearing, not about a
crash - a crash would mean the test was asserting on the error path rather than
on the stopping.

Key edge cases, each its own named test: a block of one node; a block whose only
node errors (no effects at all, still one trace, still one `error.execution`); a
block where the *first* node errors and the second would have raised (the queue
holds only `error.execution`); two `<onentry>` blocks on one state where the
first errors; a transition's content block, which has no wrapping element and so
exercises the `{:transition, t_index}` owner; and a `<log>` with neither `label`
nor `expr` (one effect, both fields `nil` - the element is legal).

Fixtures follow `test/statifier/machine/content_test.exs:1-55` and
`test/statifier/interpreter/selection_acceptance_test.exs:1-80`: a triple-quoted
heredoc at 4-space base indentation through the real pipeline, preceded by a
hand-drawn document-order index comment, with a pinned `@indexes` map so
assertions read in ids rather than integers.

Every test asserting `lib/` behavior carries its sabotage line per
`docs/testing.md:78-134`. `test/support/test_content.ex` states its exemption
(`# sabotage: n/a - harness plumbing, asserts no lib/ behavior`) rather than
omitting the line.

## Performance Considerations

- **Protocol dispatch versus a `case` on `kind`.** Consolidated protocol dispatch
  is a module lookup on the struct's `__struct__` field - the same cost class as
  a multi-clause function head, and consolidation is on by default in every env
  (`mix.exs` sets no `consolidate_protocols`). The dispatch is per content node,
  i.e. bounded by the document's content, not by the configuration size.
- **One `Machine.content/2` per node per execution**, an `elem/2` on a tuple.
  Memoizing resolved nodes per block was considered and rejected: the lookup is
  O(1), a block is short, and a cache would be a second copy of Machine data with
  an invalidation story ADR-0005 deliberately avoids everywhere else.
- **Effect accumulation appends.** `effects ++ new_effects` per node is the same
  shape `ExitEntry` already uses for blocks and states, and is quadratic in the
  block length. Blocks are short (single digits in every corpus document), and
  matching the surrounding code is worth more than a reversed accumulator here;
  if a pathological document ever makes it measurable, the fix is a
  prepend-and-reverse inside one helper with a mechanical-reason comment.
- **Trace off allocates nothing**: `Effect.trace/3` reads one boolean field and
  returns `[]` without evaluating its `fields` expression, so no
  `ContentExecuted` payload and no executed-index list is materialized into a
  struct when tracing is off. The executed-index list itself is accumulated
  regardless, because it is one cons per node on a list the fold is already
  building.
- **An empty block short-circuits before the context is built** (Decision 9), so
  a state with an empty `<onentry/>` costs one list match.

## Appendix D Deviations

Per ADR-0002 and `.claude/wurk/plan.md`'s Appendix D rule, these are the only
deviations this bead makes to the pseudocode. Every one is mechanical, and every
one carries an inline comment at its site:

1. **`executeContent(block)` returns `{machine_state, [effect]}` rather than
   performing I/O and mutating globals** (Decision 5). ADR-0003. `<log>`'s output
   becomes a returned effect; `<raise>`'s enqueue becomes a returned
   machine_state. Semantics unchanged.
2. **Dispatch is a protocol, not a type switch** (Decisions 1 and 2). The
   pseudocode does not say how a processor decides what an element does;
   `docs/architecture.md:101-105` does. No semantic content.
3. **A gated `Trace.ContentExecuted` effect is appended to every non-empty
   block** (Decision 9). Not in the pseudocode at all - it is ADR-0012 constraint
   2's "content executed" row, and it is inert when `trace: false`.
4. **The error path is explicit rather than ambient.** Spec 3.9 / 4.x already
   require that an error in executable content places `error.execution` on the
   internal queue and stops the rest of the block; the pseudocode leaves it to
   the processor's error model. Implementing it as a returned `{:error, reason}`
   converted in one place (Decision 8) is ADR-0003's error model, not a change to
   what the spec requires.
5. **`error.execution` is enqueued through `MachineState.raise_platform/4`**
   rather than a bare `internalQueue.enqueue`, so the event carries spec
   5.10.1's `:platform` type and ADR-0012 constraint 4's cause metadata. Same
   queue, same order, same name - identical in shape to st-wju.4's Decision 8 for
   `done.state.*`.
6. **`<log>`'s `expr` is not evaluated** (Decision 10). A deferral, not a
   divergence: the value is `nil` until st-af3, with an inline comment, and no
   document that could reach the branch is executable today.

Nothing here alters which content runs, in what order, what a `<raise>` puts on
the queue, or when a block stops.

## Open Questions

No human was available while this plan was written, so nothing here blocks
implementation: every question below is settled in the Decisions section and the
assumption is recorded so a reviewer can overturn it cheaply. These five are the
ones most worth a second opinion.

1. **Decision 1 - splitting `Statifier.Machine.Content` into per-kind structs.**
   This is the largest and least reversible call in the plan, and it changes a
   struct three landed beads already reference. The assumption made: a protocol
   dispatches on the struct module, so a single struct with a `kind` tag admits
   exactly one implementation, which is the central dispatcher
   `docs/architecture.md:101-105` and the bead's own first sentence reject. If a
   reviewer prefers one `defimpl` for `Machine.Content` that switches on `kind`,
   Phase 1 disappears and Phase 2 shrinks - the cost is that st-af3 adds a `kind`
   value and a clause to a shared struct for every new element, which is the
   failure mode this bead exists to prevent. Reversing later is a mechanical
   refactor, but one that touches every node struct written in the meantime.
2. **Decision 8 - the `error.execution` raise lands in this bead, not in
   st-af3.** The bead's parenthetical "Phase 3 wires the actual raising" is read
   here as "Phase 3 supplies nodes that can actually fail", because two of the
   bead's own acceptance criteria (errors-are-events conversion in the runner;
   the stop-on-error sabotage) cannot be satisfied by a runner that stops without
   converting. If a reviewer intended the narrower reading, the change is
   deleting one helper and one test; the cost is a landed stop-on-error path that
   nothing verifies end to end.
3. **Decision 6 - adding `owner` to `Statifier.Effect.Log`.** Additive to a
   struct st-wju.2 landed, on the same argument that drove the `Event.Cause`
   post-review correction: a bare `c_index` names the node but not its block. The
   assumption made: the bead's "cheap now, annoying to retrofit" sentence covers
   exactly this. If a reviewer disagrees, dropping the field is one line in the
   struct and one in the `<log>` implementation, and the acceptance criterion
   "log effect carries label, identity fields, counters" is then satisfied by
   `c_index` alone.
4. **Decision 9 - `Trace.ContentExecuted` is appended after the block's effects,
   and an empty block emits none.** Both differ from `ExitSet`/`EntrySet`, which
   are emitted first and unconditionally. The assumption made: `c_indexes` is
   documented as the nodes that *ran*, which is only knowable afterwards, and a
   trace for a block that did nothing is noise a tooling consumer would filter.
   A reviewer who wants a uniform trace-first rule gets it by emitting the
   block's declared `c_indexes` up front and losing the "which ones actually ran"
   information on the error path.
5. **Decision 4 - `{:ok, context, effects}` rather than the bead's literal
   `{context, [effect]}`.** Presentational, and chosen for CLAUDE.md's
   `{:ok, v} | {:error, e}` rule. Flagged only because it is a visible departure
   from the bead's own words, and because the protocol's return type is the one
   thing in this bead that st-af3 and st-cmq both encode against.
