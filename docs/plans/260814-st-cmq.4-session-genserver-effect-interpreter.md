# Statifier.Session: the GenServer Effect Interpreter Implementation Plan

## Overview

Build `Statifier.Session`, the OTP runtime layer that owns Appendix D's outer
`while running` loop, the external event queue, `isCancelEvent`, and the timers
for delayed sends, driving the pure core through
`Statifier.Interpreter.initialize/2` and `handle_event/2` and interpreting the
effects the core hands back. Bead: st-cmq.4.

This is the first process this library has ever started. Three of the four
modules it adds are pure values with no OTP in them at all; the fourth is the
single file the quality gate exempts from the ADR-0003 side-effect ban.

> Base note: this branch is cut from `st-af3.17-script-statement-bodies`, not
> `origin/main`. A `/wurk:refresh` onto `origin/main` is expected once that base
> lands, before this work is published.

## Current State Analysis

**What exists.** The pure core is complete for everything this layer drives:

- `Statifier.Interpreter.initialize/2` (`lib/statifier/interpreter.ex:171-230`)
  returns an untagged `{machine_state, [effect]}` and cannot fail;
  `handle_event/2` (`lib/statifier/interpreter.ex:331-351`) returns
  `{:ok, machine_state, [effect]}` or `{:error, :not_running}`.
- `Statifier.Interpreter.exit_interpreter/1` is already **public** with a
  `@spec` (`lib/statifier/interpreter.ex:769`), and sets `status: :done` - but
  it does not touch `running`.
- The effect vocabulary is complete and typed (`lib/statifier/effect.ex`), with
  `Effect.Send`, `Effect.SendDelayed`, `Effect.Cancel`, and `Effect.Invoke`
  defined and documented as having no producer yet
  (`lib/statifier/effect.ex:41-44`).
- `MachineState.new/2` already generates the `sess_` UXID and seeds
  `_sessionid`, `_name`, `_ioprocessors` through
  `Evaluator.SystemVariables.initial/2`
  (`lib/statifier/machine_state.ex:265-285`,
  `lib/statifier/evaluator/system_variables.ex:50-60`). The session's job is
  *ownership* of the id, not creation of the mechanism.
- `MachineState` is a plain serializable value - no pid, ref, port, or fun -
  so a snapshot-returning `GenServer.call` is a term copy and nothing more.

**What is missing.** There is no OTP anywhere: `mix.exs` declares no `mod:`
(`mix.exs:30-34`), there is no `config/` directory, and there is not one
`GenServer`, `Registry`, `start_link`, or `Process.send_after` under
`lib/statifier/`. The external queue is deliberately absent from `MachineState`
(`lib/statifier/machine_state.ex:21-31`), `isCancelEvent` has no implementation
and `Statifier.Event` has no cancel notion, and `MachineState` has no public
writer for `running`.

**The constraint that shapes the file layout.**
`Mix.Statifier.AdrGuard`'s `@effect_call_pattern`
(`lib/mix/statifier/adr_guard.ex:87-92`) fails the gate on `use GenServer`,
`GenServer.`, `Process.send_after(`, `:timer.`, `Logger.*(`, `:ets.` and more,
for every path under `lib/statifier/` except the single entry in
`@effect_interpreter_paths` (`lib/mix/statifier/adr_guard.ex:65-68`):

    @effect_interpreter_paths ["lib/statifier/session.ex"]

So the GenServer must be `Statifier.Session` at exactly `lib/statifier/session.ex`,
and every helper module beside it must be pure. That is not a workaround - it is
the design this plan follows deliberately: the decisions (which timer to cancel,
what to enqueue, when to stop) are pure values in helper modules, and
`session.ex` only *performs* them.

**What cannot be tested through a document.** `<send>`, `<cancel>`, and
`<invoke>` have no parser support, no `Document` struct, no `Machine.Content`
node, and no lowering builder; `test/support/feature_detector.ex:106-113` marks
them all `:unsupported`. No document can make the core emit a `:send`,
`:send_delayed`, or `:cancel` effect until st-cmq.3. Every test of the session's
interpretation of those effects therefore constructs the effect struct directly.

## Desired End State

Four new modules, and one new public function on the interpreter:

| Module | Path | Kind |
|---|---|---|
| `Statifier.Session.Inbox` | `lib/statifier/session/inbox.ex` | pure value: the external queue and `isCancelEvent` |
| `Statifier.Session.Timers` | `lib/statifier/session/timers.ex` | pure value: the `send_id -> [ref]` timer table |
| `Statifier.Session.Effects` | `lib/statifier/session/effects.ex` | pure function: `[effect] -> [instruction]` |
| `Statifier.Session` | `lib/statifier/session.ex` | the GenServer that performs the instructions |
| `Statifier.Interpreter.cancel/1` | `lib/statifier/interpreter.ex` | the core half of Appendix D's cancel path |

Verified by: `Session.start_link/2` runs a chart to quiescence and answers
snapshot queries; a `:send_delayed` effect handed to a live session fires its
event after the delay and a matching `:cancel` stops it; `:done` and every trace
effect reach subscribers in order; `Session.cancel/1` terminates the chart
through `exit_interpreter`; terminating the session discards outstanding timers.

- `lib/mix/statifier/adr_guard.ex:65-68` - the one exempt path. Helpers beside
  it are not exempt, so they must be pure.
- `lib/statifier/interpreter.ex:769` - `exit_interpreter/1` is already public,

## Decisions

The research document (`docs/research/260814-st-cmq.4-session-genserver-effect-interpreter.md`)
recorded eight plan-stage questions. All eight are settled here. Each decision
names its revisit trigger so a later bead does not have to re-derive it.

**1. No application callback, no supervision tree, no registry in this bead.**
`mix.exs` keeps its `application/0` with no `mod:`, and `Statifier.Session`
ships `start_link/2` plus a `child_spec/1`, so an embedder places it in their
own supervision tree. The `use` line is written
`use GenServer, restart: :transient` explicitly: Elixir's generated
`child_spec/1` defaults to `restart: :permanent`, which would have an
embedder's supervisor restart a session that halted normally on `:done` or
stopped on `:cancelled` - the opposite of Decision 2. `start_link/2` accepts `:name`, passed through to `GenServer.start_link/3`
unchanged, so an embedder who already runs a `Registry` uses
`{:via, Registry, _}` today with no code here. This follows the repo's standing
rule against mechanism without a caller - the same rule that keeps
`states_to_invoke` off `MachineState` (`lib/statifier/machine_state.ex:33-41`)
and `origin`/`sendid` off `Event` (`lib/statifier/event.ex:32-35`). *Revisit
trigger*: st-cmq.5 needs a registry to resolve `#_scxml_<sessionid>` targets and
st-cmq.7 needs a parent to own children; whichever lands first introduces the
`DynamicSupervisor` + `Registry` pair, with the application callback question
decided there against a real caller.

**2. `:done` idles the session; it does not stop it.** The process stays alive
with the terminal `%MachineState{}` and the retained `%Effect.Done{}` in hand,
so `snapshot/1` and `status/1` still answer. Stopping is the caller's move
(`Session.stop/2`), or the supervisor's. Rationale: `Effect.Done` carries the
full configuration precisely so the terminal position is observable without
tracing (`lib/statifier/effect/done.ex:6-12`); a session that exits on `:done`
throws that away for any owner that was not already subscribed, and under a
plain link it would take the linked owner with it. Further events are queued but
never drained, and `status/1` reports `:done`.

**3. One stream, no separate owner.** There is no `:owner` concept. Subscribers
are a monitored set; `start_link/2` takes `:subscribers` (default `[]`), and
`subscribe/2`/`unsubscribe/2` manage it afterwards. Every effect the core
returns is forwarded to every subscriber, in order, as
`{:statifier, session_id, {:effect, effect}}` - trace effects included, since
they are ordinary list members and not a side channel
(`lib/statifier/effect.ex:59-63`); a consumer filters with `Effect.trace?/1`.
One lifecycle message follows the effects that caused it:
`{:statifier, session_id, {:halted, :done | :cancelled | :budget_exhausted}}`.
A subscriber that dies is dropped on its `:DOWN`. st-cmq.1 builds the telemetry
bridge on this stream, so the stream shape is this bead's commitment and
telemetry event names are not.

**4. A cancel event is a queue entry, not an event name.** `Session.cancel/1`
enqueues the atom `:cancel` onto the same external inbox that carries events, so
`Statifier.Session.Inbox.cancel_event?/1` is a structural match rather than a
name comparison. This keeps the input path single and capturable
(`docs/observability.md` constraint 6): a cancellation is recorded in the same
ordered queue as every event, which an out-of-band `GenServer.call(:stop)` would
not be. It also avoids reserving an event name a document could raise, and needs
no fourth `Event.type`. Appendix D's own comment at the dequeue
(`<git-common-dir>/spec-cache/appendix-d.txt:145-147`) calls the mechanism
"platform specific" and the special event an assumption - "The mechanism for
this is platform specific, but here we assume it's a special event we receive" -
so a platform choice here is a port, not a deviation. Draining a `:cancel` entry calls `Statifier.Interpreter.cancel/1`
(Phase 2), which is Appendix D's `running = false; continue` followed by the
loop's own `exitInterpreter()`.

**5. `#_internal` is resolved core-side and never escapes as an effect.** An
internal-target send is executable content running *inside* a microstep, and the
internal queue is drained within that same macrostep; by the time an effect
reaches the session, `handle_event/2` has already folded to quiescence, so
enqueuing there would place the event a macrostep too late. The correct
resolution is `MachineState.enqueue_internal/2` from inside `<send>`'s own
`execute/2`, which is st-cmq.3's work. This bead's session therefore routes
exactly one target - absent (`nil`), which
`Statifier.Event.internal/3`'s own `@doc` puts on the sending session's external
queue (`lib/statifier/event.ex:63-69`). Every other target, `#_internal`
included, plans as `{:unroutable, effect}`: forwarded to subscribers as a
`{:unroutable, effect}` lifecycle message and otherwise dropped, with no guess
and no crash. *Revisit trigger*: st-cmq.5 owns target routing and replaces the
`:unroutable` default clause with real resolution.

**6. `:budget_exhausted` halts the session and keeps the position.** The effect
is forwarded, `status/1` reports `:budget_exhausted`, queued events stay queued
and are not drained, and the resumable `%MachineState{}` stays readable through
`snapshot/1` (ADR-0019's returned position is resumable by construction,
`lib/statifier/effect/budget_exhausted.ex:25-27`). The session neither retries
with a larger budget nor stops itself: a retry policy is an embedder's
judgment, and stopping would destroy the position ADR-0019 built. `cancel/1`
still works from a budget-halted session, since the inbox's cancel entry is
checked before any drive of the core.

**7. The timer table is `send_id -> [ref]`.** Spec 6.3's "If multiple delayed
events have this sendid, the Processor will cancel them all" is only reachable
with a list, and an author-supplied `<send id>` on a state entered twice reaches
it. A `SendDelayed` with `send_id: nil` is scheduled and tracked for termination
cleanup but is not cancellable - there is no id to name it by. v1's flat
`send_id -> ref` map (`../statifier/lib/statifier/state_machine.ex:66`) silently
lost the first ref; this is the argument against copying it.

**8. Both snapshot shapes, as two functions.** `snapshot/1` returns the whole
`%MachineState{}` - constraint 1's complete, resumable, inspectable position,
which tooling and replay need. `status/1` returns a small projection
(`session_id`, `status`, `configuration` as string ids, the three counters,
queued-event and pending-timer counts) for a caller polling in a loop, since
`snapshot/1` copies the entire compiled `machine` on every call. For a halted
session, the projection's `configuration` comes from the retained
`Effect.Done.configuration`, mirroring the restore `test/support/case.ex:23-32`
already performs.

**9. `Session.interpret/2` is a public seam, not a test hook.** The session
accepts a list of `Effect.t()` values produced by any driver of the pure core
and interprets them on the same code path its own drives use. ADR-0003's
Consequences list "Embedders can supply their own effect interpreter", and the
inverse - an embedder driving the core themselves and handing the effects to a
session for timer and routing service - is the same seam read the other way. It
is also what makes `:send_delayed`/`:cancel` testable end-to-end before
st-cmq.3 produces them. It funnels through the same `handle_cast` path as
`send_event/2`, so it does not open a side door around the inbox.

It does, however, *widen what a recording has to contain*, and the moduledoc
must say so. Constraint 6's replay tuple is "(machine, initial data, external
event log)", which reconstructs a run only when every effect the session
interpreted came from the core. An `interpret/2` call hands the session effects
that no `initialize/2` or `handle_event/2` produced, so replaying such a run
needs the `interpret/2` calls recorded alongside the event log. That is a
statement about the recording's contents, not a leak in the boundary - the
calls are still ordered, still observable, still on the one input path - but
`interpret/2`'s `@doc` states it plainly rather than leaving a reader to infer
that the three-part replay tuple still covers everything. *Revisit trigger*:
once st-cmq.3 makes documents produce `:send`/`:cancel` effects, the ordinary
path stops needing `interpret/2` at all, and whether it stays public is a fair
question for the bead that builds the replay recorder.

## What We're NOT Doing

- **No `<send>`, `<cancel>`, or `<invoke>` element support.** No parser,
  lowering, `Document`, `Machine.Content`, or validator work. Those are
  st-cmq.3 and st-cmq.6. This bead interprets the effect *structs*, which
  already exist.
- **No target routing beyond the absent target.** `#_internal`, `#_parent`,
  `#_scxml_<sessionid>`, and external URI targets are st-cmq.5 (Decision 5).
- **No `_ioprocessors` change.** The minimal map
  `Evaluator.SystemVariables.initial/2` writes today stays as it is; st-cmq.5
  replaces it.
- **No child sessions, `autoforward`, or `<finalize>`.** st-cmq.6/st-cmq.7. The
  three skipped invoke passes in `main_event_loop/1`
  (`lib/statifier/interpreter.ex:680-691`) and the `cancelInvoke` skip in
  `exit_interpreter/1` (`:780-781`) stay skipped and keep their comments.
- **No `:telemetry` dependency and no telemetry event names.** st-cmq.1 builds
  that bridge on the subscriber stream this bead exposes.
- **No `Registry`, `DynamicSupervisor`, application callback, or `mod:` in
  `mix.exs`** (Decision 1).
- **No corpus or ratchet movement.** Nothing here changes what any conformance
  document does; `test/passing_tests.json` is not touched.
- **No new `origin`/`sendid` fields on `Statifier.Event`.** They are documented
  as arriving with `<send>`/`<invoke>` round-tripping
  (`lib/statifier/event.ex:32-35`), which is st-cmq.3/st-cmq.5, not this bead.
- **No fix to `Statifier.initialize/2`'s option list**, which omits
  `:session_id` (`lib/statifier.ex:82-85`). That gap is pre-existing and was
  deliberately left alone once already
  (`docs/plans/260812-st-sd1-macrostep-round-budget.md:137-141`); touching it
  here would be an unrelated change in the commit.

## Implementation Approach

Push every decision into a pure value or a pure function, and leave
`session.ex` performing instructions. Three consequences follow, and they are
why the phases are ordered as they are:

1. **The gate allows it.** Helper modules beside `session.ex` are not exempt
   from the ADR-0003 check, so they must be pure anyway. The constraint and the
   good design point the same way.
2. **The hard parts are unit-testable with no processes**, which is exactly what
   ADR-0003 promises ("Tests interpret effects directly, no processes
   required"). Cancel-all semantics, cancel-of-an-already-fired-send,
   routing, and the halt decisions are all pure-function tests.
3. **Each phase is independently green.** Phases 1 and 3 add fully tested pure
   modules with no caller yet; Phase 2 adds a public interpreter function with
   its own tests; Phase 4 is the only phase that introduces a process, and by
   then it is wiring rather than logic.

### The Appendix D rule for this plan

Two deviations, both mechanical (ADR-0002), both already half-documented in the
core:

- **`isCancelEvent` and the external queue live outside `MachineState`.** The
  reason is written at the port site already
  (`lib/statifier/interpreter.ex:693-702`) and in `MachineState`'s moduledoc
  (`:21-31`): the core takes one external event per call, so the waiting events
  and the cancel check move to the driver. Phase 1 restates that reason at
  `Inbox`'s own site; Phase 2 rewrites the `main_event_loop/1` comment's closing
  sentence to name where `isCancelEvent` went. That rewrite must **restate**
  the fact rather than move the `st-cmq` ID onto a new line (ADR-0018).
- **`running = false; continue` becomes a function call.** Appendix D reaches
  `exitInterpreter()` by falling out of the `while running` loop. With the loop
  driven by the caller there is no loop to fall out of, so
  `Statifier.Interpreter.cancel/1` performs the same two steps in the same
  order, and says so in its own `@doc`. No semantics change: the states exited,
  the `<onexit>` blocks run, the donedata collected, and the `{:done, _}` effect
  produced are all `exit_interpreter/1`'s, untouched.

Everything else is a straight port: the drain loop is the pseudocode's
`while running:` with `externalQueue.dequeue()` replaced by the inbox, and each
iteration's body is `Interpreter.handle_event/2`.

## Phase 1: The pure external queue and timer table

### Overview

Two pure value modules with no caller yet: the external event queue with
Appendix D's `isCancelEvent` check, and the `send_id -> [ref]` timer table.
Neither contains any OTP call - the caller in Phase 4 performs the
`Process.send_after` and `Process.cancel_timer`; these modules only decide.

### Changes Required:

#### 1. The external inbox

**File**: `lib/statifier/session/inbox.ex` (new)
**Changes**: A `:queue`-backed FIFO of entries, where an entry is either an
event or the cancel marker.

```elixir
defmodule Statifier.Session.Inbox do
  @moduledoc """
  The waiting external events, plus Appendix D's `isCancelEvent` check.

  ADR-0002 mechanical deviation, ADR-0003: Appendix D's `mainEventLoop` owns
  both queues and blocks on `externalQueue.dequeue()`, checking
  `isCancelEvent/1` on what it dequeues. `Statifier.MachineState` owns only the
  internal queue, so the waiting external events and the cancel check live
  here, in the driver. The semantics of processing one external event are
  unchanged; only the storage of the waiting ones moves.

  Appendix D's `isCancelEvent` is described by spec 6.4 as platform specific
  ("here we assume it's a special event we receive"). This platform makes the
  cancel a distinct *queue entry* rather than a reserved event name, so no
  document can raise one by writing that name, and `cancel_event?/1` is a
  structural match.
  """

  @type entry :: {:event, Statifier.Event.t()} | :cancel
  @opaque t :: %__MODULE__{queue: :queue.queue(entry())}

  @spec new() :: t()
  @spec enqueue_event(t(), Statifier.Event.t()) :: t()
  @spec enqueue_cancel(t()) :: t()
  @spec next(t()) :: {:ok, entry(), t()} | :empty
  @spec cancel_event?(entry()) :: boolean()
  @spec pending_events(t()) :: [Statifier.Event.t()]
  @spec size(t()) :: non_neg_integer()
end
```

`pending_events/1` is the `internal_events/1`-shaped inspection view
(`lib/statifier/machine_state.ex:334-335`): no code outside this module touches
`:queue` directly, and `==` on two inboxes is not a position test for the same
reason.

#### 2. The timer table

**File**: `lib/statifier/session/timers.ex` (new)
**Changes**: A pure table mapping a `send_id` to every live timer reference
scheduled under it, plus the flat set of live references for termination.

```elixir
defmodule Statifier.Session.Timers do
  @moduledoc """
  The pending delayed-send timers, as a value.

  Spec 6.3: "If multiple delayed events have this sendid, the Processor will
  cancel them all" - so a send id maps to a *list* of references, in
  scheduling order, not to one. A send scheduled with no id is tracked for
  termination cleanup but cannot be cancelled: `<cancel>` names a sendid, and
  there is none to name.

  Spec 6.2 requires that a session terminating before a delay elapses discard
  the message without delivering it, which is what `refs/1` exists for: the
  caller cancels every reference it returns.

  Nothing here calls `Process.send_after/3` or `Process.cancel_timer/1`. This
  module decides which references are affected; `Statifier.Session` performs
  the cancellation.
  """

  @opaque t :: %__MODULE__{by_id: %{String.t() => [reference()]}, live: MapSet.t(reference())}

  @spec new() :: t()
  @spec put(t(), send_id :: String.t() | nil, ref :: reference()) :: t()
  # Removes and returns every reference under `send_id`, in scheduling order.
  # An unknown id returns `{[], timers}` - spec 6.3 makes that a no-op, not an
  # error.
  @spec take(t(), send_id :: String.t()) :: {[reference()], t()}
  # Drops a reference that has already fired.
  @spec forget(t(), ref :: reference()) :: t()
  @spec refs(t()) :: [reference()]
  @spec count(t()) :: non_neg_integer()
end
```

#### 3. Tests

**Files**: `test/statifier/session/inbox_test.exs`,
`test/statifier/session/timers_test.exs` (new)
**Changes**: Every test asserting `lib/` behavior carries its one-line sabotage
note (`docs/testing.md`). Cases to cover: FIFO order across mixed event and
cancel entries; `next/1` on an empty inbox; `cancel_event?/1` true only for
`:cancel`; two refs under one send id both returned by `take/2` in scheduling
order; `take/2` on an unknown id; `forget/2` removing a fired ref from both
maps; a `nil` send id appearing in `refs/1` but reachable by no `take/2`.

## Phase 2: `Statifier.Interpreter.cancel/1`

### Overview

The core half of Appendix D's cancel path: set `running` false and run
`exit_interpreter/1`, in that order. Independently useful and independently
tested - a caller can cancel a chart with no session involved at all, which is
what keeps this phase's tests process-free.

### Changes Required:

#### 1. The cancel entry point

**File**: `lib/statifier/interpreter.ex`
**Changes**: A new public function beside `handle_event/2`, mirroring its return
shape.

```elixir
@doc """
`mainEventLoop`'s cancel path (Appendix D) - `running = false`, then
`continue`, which ends the `while running` loop and reaches
`exitInterpreter()`.

ADR-0002 mechanical deviation: the outer loop is driven by the caller
(`handle_event/2`), so there is no loop here to fall out of; the two steps
the pseudocode reaches by falling out are performed directly, in the same
order. Nothing about the exit itself changes - the states exited, the
`<onexit>` blocks run, the `<donedata>` collected, and the `{:done, _}`
effect produced are all `exit_interpreter/1`'s.

Rejects an already-terminated machine_state with `{:error, :not_running}`,
matching `handle_event/2`: Appendix D would not be inside the loop to check
`isCancelEvent` at all.
"""
```

## Phase 3: The pure effect planner

### Overview

`[Effect.t()] -> [instruction]`, with no process, no clock, and no state beyond
the effect list. This is where every routing and halting decision in the bead
actually lives, and it is where the `:send`/`:send_delayed`/`:cancel` semantics
get their real test coverage, against hand-built effect structs, because no
document can produce them yet.

### Changes Required:

#### 1. The planner

**File**: `lib/statifier/session/effects.ex` (new)
**Changes**:

```elixir
defmodule Statifier.Session.Effects do
  @moduledoc """
  Turns the effect list the pure core returns into an ordered list of
  instructions for `Statifier.Session` to perform (ADR-0003). Deciding is
  here, where it is a pure function of the effect list; performing is there,
  where the process is.

  Every effect produces a `{:notify, effect}` instruction in its original
  position, so a subscriber sees the whole stream in order - trace effects
  included, since they are ordinary list members and not a side channel.
  Effects that also mean something to the session emit their action
  immediately after their own `:notify`.
  """

  @type instruction ::
          {:notify, Statifier.Effect.t()}
          | {:enqueue_event, Statifier.Event.t()}
          | {:schedule, send_id :: String.t() | nil, delay_ms :: non_neg_integer(),
             Statifier.Event.t()}
          | {:cancel_timers, send_id :: String.t()}
          | {:unroutable, Statifier.Effect.t()}
          | {:halt, :done | :budget_exhausted}

  @spec plan(effects :: [Statifier.Effect.t()]) :: [instruction()]
end
```

The clauses, one per vocabulary tag:

| Effect | Instructions emitted |
|---|---|
| `{:send, %Send{target: nil}}` | `{:notify, e}`, `{:enqueue_event, Event.external(send.event, data: send.data)}` |
| `{:send, %Send{target: _}}` | `{:notify, e}`, `{:unroutable, e}` (Decision 5) |
| `{:send_delayed, %SendDelayed{target: nil}}` | `{:notify, e}`, `{:schedule, send_id, delay_ms, event}` |
| `{:send_delayed, %SendDelayed{target: _}}` | `{:notify, e}`, `{:unroutable, e}` |
| `{:cancel, %Cancel{send_id: id}}` | `{:notify, e}`, `{:cancel_timers, id}` |
| `{:invoke, _}` | `{:notify, e}`, `{:unroutable, e}` (st-cmq.6 owns invoke) |
| `{:done, _}` | `{:notify, e}`, `{:halt, :done}` |
| `{:budget_exhausted, _}` | `{:notify, e}`, `{:halt, :budget_exhausted}` |
| `{:log, _}`, `{:trace, _}` | `{:notify, e}` only |

The event a `:send` becomes is `type: :external` and `cause: nil`, per
`Statifier.Event.external/2` and the reasoning in `Event.internal/3`'s `@doc`

## Phase 4: `Statifier.Session`, the GenServer

### Overview

**Why this phase is not split further** (a review finding, declined
deliberately, recorded here for whoever implements it): Phase 4 is the largest
of the four - the GenServer, six control-flow paths, the subscriber lifecycle,
real timers, and eleven categories of test - and a reviewer reasonably asked
whether it should be two phases, lifecycle/drain/snapshot then
subscribers/timers/cancel. It stays one because the split would not be
independently gate-verifiable in the way the phase rule means: a session that
drives the core but interprets no `:send_delayed` is a session whose effect loop
is half-written, and `Statifier.Session.Effects` (Phase 3) would sit with a
caller for some instructions and none for others across a commit boundary. The
file-level AdrGuard exemption also means both halves land in the same file, so
the split buys a smaller diff rather than a smaller unit of verification. If the
loop stalls here in practice, splitting at the subscriber/timer line is the
place to cut.

The one file allowed to do I/O. It holds the machine_state, the inbox, the timer
table, and the subscriber set; it drives the core; and it performs the
instructions Phase 3 plans. Plus the moduledoc, the changelog fragment, and the
architecture-doc line that stops saying "not yet implemented".

### Changes Required:

#### 1. The GenServer

**File**: `lib/statifier/session.ex` (new - the exact path
`@effect_interpreter_paths` exempts; a different path or a different module name
fails the gate)
**Changes**:

```elixir
defmodule Statifier.Session do
  @moduledoc """
  The GenServer effect interpreter (ADR-0003): the outer `while running` loop,
  the waiting external events, the delayed-send timers, and the fan-out of the
  effect stream to subscribers. The pure core decides; this module performs.

  This is the one module under `lib/statifier/` allowed to do I/O, which is
  why the deciding half lives in `Statifier.Session.Inbox`,
  `Statifier.Session.Timers`, and `Statifier.Session.Effects` - pure values and
  a pure function, testable with no process at all - and only the performing
  half lives here.
  ...
  """

  # `:transient` is explicit: the generated `child_spec/1` defaults to
  # `:permanent`, which would restart a session that halted normally.
  use GenServer, restart: :transient

  # -- client ---------------------------------------------------------------
  @spec start_link(machine :: Machine.t(), opts :: keyword()) :: GenServer.on_start()
  @spec session_id(server()) :: String.t()
  @spec send_event(server(), Event.t() | String.t()) :: :ok
  @spec interpret(server(), [Effect.t()]) :: :ok
  @spec cancel(server()) :: :ok
  @spec snapshot(server()) :: MachineState.t()
  @spec status(server()) :: status()
  @spec subscribe(server(), pid()) :: :ok
  @spec unsubscribe(server(), pid()) :: :ok
  @spec stop(server(), reason :: term()) :: :ok
end
```

- `start_link/2` options: `:name` (passed to `GenServer.start_link/3` verbatim,
  so `{:via, Registry, _}` works today), `:session_id`, `:subscribers`, and
  `MachineState.new/2`'s own `:trace`, `:datamodel`, `:max_macrostep_rounds`.
  The session generates the `sess_` UXID once, through `MachineState.new/2`'s
  own `:session_id` default rather than by calling `UXID` itself - the guard's
  ad-hoc-identifier check is **not** lifted for `session.ex`
  (`lib/mix/statifier/adr_guard.ex:96-100`) - and keeps its own copy for
  routing and message tagging, since there is no `session_id` field on
  `%MachineState{}`.
- `init/1` runs `Interpreter.initialize/2`, plans and performs the resulting
  effects, then continues into the drain.
- The drain (`handle_continue(:drain, state)`) is Appendix D's `while running:`
  with the inbox in place of the blocking dequeue: while not halted, `next/1`
  the inbox; a `:cancel` entry calls `Interpreter.cancel/1` and halts
  `:cancelled`; an event calls `Interpreter.handle_event/2`. Both plan and
  perform their effects. A `{:error, :not_running}` from a race halts without
  crashing.
- `handle_info({:statifier_delayed_send, ref, send_id, event}, state)` is the
  fired timer: `Timers.forget/2`, then the same enqueue path any event takes,
  then drain. This is the single recordable input path
  (`docs/observability.md` constraint 6) - a caller's `send_event/2`, a
  self-targeted send re-enqueued from an effect, and a fired timer all reach the
  core through the same inbox.
- `handle_info({:DOWN, _, :process, pid, _}, state)` drops a dead subscriber.
- Performing `{:schedule, id, ms, event}` is the one `Process.send_after/3` call
  in the library; `{:cancel_timers, id}` is `Timers.take/2` then
  `Process.cancel_timer/1` per ref. Cancelling a ref for a send that already
  fired or never existed is a no-op (spec 6.3).
- `terminate/2` cancels every ref `Timers.refs/1` returns - spec 6.2's "If the
  SCXML session terminates before the delay interval has elapsed, the SCXML
  Processor MUST discard the message without attempting to deliver it."
- `Statifier.Session.State` is a nested `@moduledoc false` struct in this same
  file (so it stays inside the exempt path and needs no Doctor entry).

Key edge cases: a cancel queued behind events; a `<cancel>` for an
already-fired send; two live delayed sends under one id; an event arriving after
`:done`; a livelocked chart; a subscriber that dies mid-run; termination with
timers outstanding.

Sabotage discipline: every test asserting `lib/` behavior gets its one-line
mutation note above it (`docs/testing.md`), verified by breaking the covered

### Manual Testing Steps:

1. In `iex -S mix`, compile a small chart, `Statifier.Session.start_link/2` it
   with `trace: true` and `subscribers: [self()]`, and `flush()` to read the
   initialization effect stream in order.
2. `Statifier.Session.send_event/2` an event that fires a transition; confirm
   `status/1` shows the new configuration and the counters advanced.
3. `Statifier.Session.interpret(pid, [{:send_delayed, %Statifier.Effect.SendDelayed{...delay_ms: 3_000}}])`,
   then `status/1` to see one pending timer, then wait and confirm the event was
   processed.
4. Repeat, and `interpret/2` a matching `%Effect.Cancel{}` inside the window;
   confirm the timer count drops to zero and nothing is delivered.
5. Repeat, and `Statifier.Session.stop/2` inside the window; confirm nothing is
   delivered (spec 6.2).
6. Drive a chart to a top-level final; confirm the process is alive, `status/1`
   reports `:done` with the terminal configuration, and further sends change
   nothing.
7. `Statifier.Session.cancel/1` a mid-run chart; confirm the `<onexit>` `<log>`
   effects arrive in exit order before the `{:done, _}`.
