# Committed SCION Exclusion Manifest Implementation Plan

## Overview

Record the SCION corpus's ECMAScript-irreducible tests and its duplicate copy
of the W3C IRP suite in a committed manifest with reasons, wired into the
SCION emitter so excluded cases never reach the generated corpus and their
count is reported. Beads issue: st2-00p.8.

W3C already has this mechanism (`tools/corpus/scxml_w3/exclusions.exs`, landed
under st2-00p.7); this plan brings SCION to parity and adds the count
reporting the acceptance criteria requires for both suites.

## Current State Analysis

- `mise.toml`'s `corpus:fetch:scion` task deletes
  `checkout/test/w3c-ecma{,-in-review,-modified}` unconditionally, with a
  one-line comment ("dropping its ecma-only trees") and no per-test reason.
  Investigation (shallow-cloning `jbeard4/scxml-test-framework` to inspect)
  shows only `test/w3c-ecma` currently exists upstream (189 `.json` cases);
  the `-in-review`/`-modified` variants are dead globs. That directory is not
  a native SCION suite - it is SCION's own untransformed mirror of the W3C
  IRP suite (`datamodel="ecmascript"`, same test numbers as the W3C corpus,
  no predicator XSL ever applied to it). `tools/corpus/scxml_w3` already
  generates the real W3C corpus from the primary IRP source, so this tree is
  a duplicate, not an exclusion candidate on ECMAScript grounds per se.
- After that deletion, 127 native SCION cases remain and **all 127 currently
  emit unfiltered** (`tools/corpus/scion/cases.exs` has no exclusion
  mechanism at all - confirmed by reading the file in full).
- Four native locations are irreducibly `<script>`-dependent (predicator has
  no statement layer, ADR-0004) and are emitted anyway, doomed to fail
  forever once an engine exists:
  - `script/` - all 3 cases (`test0`, `test1`, `test2`) use inline `<script>`.
  - `script-src/` - all 4 cases (`test0`-`test3`) use external
    `<script src="...">`.
  - `error/` - its single case (`error`) uses `<script>` for an intentional
    semantic-error scenario.
  - `assign-current-small-step/` - only `test0` of its 5 cases uses
    `<script>` (`onentry` assignment); `test1`-`test4` do not and must stay
    included. This is the one case where directory-level exclusion is wrong.
  - Confirmed via `grep -rl "<script" test --include="*.scxml"` against the
    live checkout, cross-referenced against each directory's `.json` count.
- These four locations are already committed as generated test files:
  `test/scion_tests/script/{test0,test1,test2}_test.exs`,
  `test/scion_tests/script_src/{test0,test1,test2,test3}_test.exs`,
  `test/scion_tests/error/error_test.exs`,
  `test/scion_tests/assign_current_small_step/test0_test.exs`. Each carries
  `@tag required_features: [..., :script_elements, ...]`. None are in
  `test/passing_tests.json` (the SCION/W3C ratchet lists start empty - v2 has
  no engine yet), so removing them is a zero-impact ratchet change.
- `tools/corpus/scxml_w3/cases.exs` already loads `exclusions.exs` and skips
  matches (`Map.has_key?(exclusions, name)`), but prints no count and never
  checks whether an exclusion entry matched anything.
- `tools/corpus/scxml_w3/check_exprs.exs` (a related but distinct mechanism -
  validates transformed predicator expressions compile, not corpus emission)
  already has the pattern this plan follows: `report.files_skipped`,
  `report.stale_allowlist`, `System.halt(1)` on an unexpected result,
  `IO.puts` summary at the end. `test/corpus/check_exprs_test.exs` sabotage-
  tests that logic; it is the closest in-repo precedent for "manifest entry
  that matches nothing is a hard failure."

### Key Discoveries

- `test/w3c-ecma`'s 189 cases share numbering with the primary W3C corpus
  (e.g. `test302`, `test525` - both also appear in
  `scxml_w3/exclusions.exs`), confirming it is a duplicate embed, not an
  independent test set.
- `tools/corpus/normalize.exs` (`Cases.Normalize.identifier/1`) is explicitly
  shared by both emitters "so the two generators can't drift" - the new
  exclusion-matching logic in `scion/cases.exs` should key on the *raw*
  `spec_dir`/`name` (pre-normalization), matching how `scxml_w3/cases.exs`
  keys its own exclusions on the raw W3C `name` (`"test302"`, not a
  normalized form).
- `.formatter.exs` includes `tools/**/*.exs`, so `mix quality`'s Format stage
  covers every file this plan touches even though Credo's `included` list
  (lib/, src/, test/, web/, apps/\*) does not reach `tools/` - no Credo
  IoPuts concern for the new `IO.puts` calls.
- ADR-0004's decision text says "W3C tests that irreducibly require
  ECMAScript are excluded..." - written before a SCION-side manifest existed.
  The principle (predicator is the datamodel; ECMAScript-only tests get a
  reasoned, committed exclusion) applies identically to SCION; only the
  ADR's illustrative wording was W3C-specific. Per project convention, ADRs
  are not re-litigated - this plan cites ADR-0004 for the SCION `:needs_script`
  reason without editing the ADR, and extends `docs/testing.md`'s prose
  instead (which is where the W3C-specific paragraph already lives).

## Desired End State

- `tools/corpus/scion/exclusions.exs` is committed: a map from either a bare
  spec directory (whole-tree exclusion) or `"spec/name"` (single-case
  exclusion) to `{reason_atom, description}`, covering `w3c-ecma`, `script`,
  `script-src`, `error`, and `assign-current-small-step/test0`.
- `tools/corpus/scion/cases.exs` loads that manifest, skips every matching
  input before emission, and after the run prints
  `emitted <N> SCION case(s), excluded <M>`. If any manifest entry matches
  zero inputs, the script halts non-zero naming the stale entry(ies) - a
  manifest entry that silently stops firing is a bug, not a no-op.
- `tools/corpus/scxml_w3/cases.exs` gets the same treatment for parity:
  `emitted <N> W3C case(s), excluded <M>` plus the same stale-entry check.
- `mise.toml`'s `corpus:fetch:scion` no longer deletes any `test/w3c-ecma*`
  tree - the whole upstream checkout is kept, and exclusion happens once, at
  emit time, via the manifest (matching how W3C's fetch keeps every `.txml`
  and filters at emit).
- `test/scion_tests/script/`, `test/scion_tests/script_src/`,
  `test/scion_tests/error/`, and
  `test/scion_tests/assign_current_small_step/test0_test.exs` are deleted (no
  longer generated).
- Regenerating with `mise run corpus` reproduces exactly this state (idempotent).
- `docs/testing.md` and `tools/corpus/README.md` describe the SCION manifest
  alongside the W3C one, with corrected case counts.
- Verify: `mise run corpus:emit` prints both count lines; `git status` after a
  full `mise run corpus` shows no unexpected diff in `test/scion_tests/` or
  `test/scxml_tests/` beyond the four removed directories/file; `mix quality`
  is green.

## What We're NOT Doing

- Not touching `scxml_w3/exclusions.exs`'s existing 14 entries or their
  reasons - only adding count/stale-check plumbing around the existing
  mechanism.
- Not adding a SCION equivalent of `check_exprs.exs` (predicator-expression
  validation against the transformed `.scxml`) - SCION cases never go
  through `conf_predicator.xsl`, so that check has no SCION analogue. Out of
  scope for this issue.
- Not editing ADR-0004's text.
- Not adding entries for tests that merely *use* ECMAScript-flavored syntax
  predicator can already evaluate (e.g. `cond-js/`'s literal `true`/`false`
  conditions) - those stay in and either pass or fail loudly on their own
  merits per the unsupported-feature-fails-not-skips policy
  (`docs/testing.md`).
- Not ratcheting any newly-passing test - there is no engine yet, so nothing
  in this corpus passes regardless of exclusion.
- Not changing `internal-transitions/test0.scxml`'s `sed` patch in
  `corpus:fetch:scion` (root-transition support gap, unrelated to ADR-0004
  exclusions).

## Implementation Approach

Single phase: the manifest, its wiring into both emitters, the fetch-task
change, the stale generated-file cleanup, and the doc updates are one
logically atomic change - none of them is independently meaningful without
the others (a manifest nobody reads, an emitter change with no manifest to
read, or docs describing a count nothing prints, are each half a feature).
`mix quality` gates the whole thing at once.

## Phase 1: SCION exclusion manifest, emitter wiring, and doc parity

### Overview

Add the committed manifest, wire both emitters to read/count/validate their
respective exclusion files, stop the blind fetch-time deletion, remove the
now-stale generated SCION test files, and update the two docs that describe
this mechanism.

### Changes Required

#### 1. `tools/corpus/scion/exclusions.exs` (new file)

Committed manifest, modeled on `scxml_w3/exclusions.exs`'s header-comment
style but documenting the two-level key scheme:

```elixir
# SCION scxml-test-framework cases with no predicator equivalent, or that
# duplicate the separately-generated W3C corpus. A key is either a bare spec
# directory ("script") to exclude every case under it, or "spec/name"
# ("assign-current-small-step/test0") to exclude one case within an
# otherwise-included spec.
#
# Reasons:
#   :needs_script          - <script>/statements; permanently out (ADR-0004)
#   :duplicates_w3c_corpus - SCION's own untransformed mirror of the W3C IRP
#                            suite (datamodel="ecmascript", no predicator XSL
#                            applied); tools/corpus/scxml_w3 generates the
#                            real W3C corpus from the primary IRP source

%{
  "w3c-ecma" =>
    {:duplicates_w3c_corpus,
     "SCION framework's embedded copy of the W3C IRP suite; duplicates tools/corpus/scxml_w3's output with no predicator transform applied"},
  "script" => {:needs_script, "conf:script - predicator has no statement layer"},
  "script-src" =>
    {:needs_script, "external <script src> - same statement-layer gap as inline <script>"},
  "error" => {:needs_script, "conf:script - predicator has no statement layer"},
  "assign-current-small-step/test0" =>
    {:needs_script, "onentry <script> assignment - predicator has no statement layer"}
}
```

#### 2. `tools/corpus/scion/cases.exs`

**File**: `tools/corpus/scion/cases.exs`
**Changes**: load the exclusions manifest; extract the existing per-case body
into a private `emit_case/4`-style function; replace the `Enum.each` with a
reduction that tallies emitted/excluded counts and the set of manifest keys
that actually matched something; after the loop, halt non-zero naming any
manifest entry that matched nothing, otherwise print the summary line.

```elixir
exclusions_path = Path.join(__DIR__, "exclusions.exs")
{exclusions, _bindings} = Code.eval_file(exclusions_path)

[out_root, in_root | inputs] = System.argv()

{matched, emitted, excluded} =
  Enum.reduce(inputs, {MapSet.new(), 0, 0}, fn input, {matched, emitted, excluded} ->
    rel = Path.relative_to(input, in_root)
    spec_dir = Path.dirname(rel)
    name = Path.basename(rel, ".json")

    cond do
      Map.has_key?(exclusions, spec_dir) ->
        {MapSet.put(matched, spec_dir), emitted, excluded + 1}

      Map.has_key?(exclusions, "#{spec_dir}/#{name}") ->
        {MapSet.put(matched, "#{spec_dir}/#{name}"), emitted, excluded + 1}

      true ->
        emit_case(out_root, in_root, input)
        {matched, emitted + 1, excluded}
    end
  end)

stale = Map.keys(exclusions) -- MapSet.to_list(matched)

if stale != [] do
  IO.puts(:stderr, "stale scion exclusions.exs entries (matched nothing): #{Enum.join(stale, ", ")}")
  System.halt(1)
end

IO.puts("emitted #{emitted} SCION case(s), excluded #{excluded}")
```

(`emit_case/4` is the current `Enum.each` body, unchanged, just lifted to a
named function so the reduction above can call it from one branch.)

#### 3. `tools/corpus/scxml_w3/cases.exs`

**File**: `tools/corpus/scxml_w3/cases.exs`
**Changes**: same treatment for parity - the current `Enum.each` body's
`if Map.has_key?(exclusions, name) do :skip else ... end` becomes a reduction
tallying emitted/excluded/matched-keys, followed by the same stale-check and
summary print (`emitted <N> W3C case(s), excluded <M>`). No change to which
tests are excluded or why - purely additive counting/validation around the
existing logic.

#### 4. `mise.toml`

**File**: `mise.toml`
**Changes**: `corpus:fetch:scion` task -

```toml
[tasks."corpus:fetch:scion"]
description = "Clone the SCION scxml-test-framework"
shell = "bash -c"
run = '''
set -euo pipefail
if [ -d "$CORPUS_SCION_CASES" ]; then exit 0; fi
scion_root="$(dirname "$CORPUS_SCION_CASES")"
rm -rf "$scion_root"
mkdir -p "$scion_root"
git clone --depth 1 "$CORPUS_SCION_SUITE" "$scion_root/checkout"
mv "$scion_root/checkout/test" "$CORPUS_SCION_CASES"
rm -rf "$scion_root/checkout"
# The root transition is not supported.
sed -i.bak -e '25,28d' "$CORPUS_SCION_CASES/internal-transitions/test0.scxml"
rm -f "$CORPUS_SCION_CASES/internal-transitions/test0.scxml.bak"
'''
```

Removes the `rm -rf .../w3c-ecma{,-in-review,-modified}` line and the old
"dropping its ecma-only trees" description; exclusion now happens once, at
emit time, via the manifest - matching how the W3C fetch task keeps every
`.txml` and filters downstream.

## Testing Strategy

### Unit Tests

None added. The exclusion-matching logic in `cases.exs` is generator tooling
under `tools/corpus/`, not `lib/` behavior - consistent with the existing
precedent that `scxml_w3/cases.exs`'s own (already-shipped) exclusion
filtering carries no dedicated test, and with `docs/testing.md`'s stated
sabotage exemption for harness/generator plumbing. `Cases.Normalize` is the
one piece of corpus tooling that does get unit-tested
(`test/corpus/normalize_test.exs`), precisely because its per-character
edge cases are non-obvious; the spec-or-spec/name matching added here is a
two-branch `cond`, not that kind of logic.

### Conformance Tests

None newly ratcheted - no engine exists yet, so nothing in either corpus
passes regardless of this change. The four excluded SCION locations simply
stop being generated (they were never in `passing_tests.json`).

### Manual Testing Steps

1. Regenerate the corpus end to end (`mise run corpus`, or `corpus:emit`
   against a pre-populated `scratch/` tree) and confirm the printed counts
   from the manual-verification checklist above.
2. Diff `test/scion_tests/` and `test/scxml_tests/` against the pre-change
   tree; the only changes should be the four deleted SCION locations.
3. Confirm `tools/corpus/scion/exclusions.exs` is loaded by both re-running
   `mise run corpus:emit` twice in a row (idempotent - no diff on the second
   run) and by the stale-entry negative test above.

## Corpus/Ratchet Notes

No `passing_tests.json` changes - the SCION/W3C ratchet lists are still
empty (v2 has no engine yet). Deleting the four stale generated locations
under `test/scion_tests/` has no ratchet impact.
