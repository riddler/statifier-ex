# Real `condition_match/2`: cond gates selection, errors become `error.execution` Implementation Plan

## Overview

Replace the stub body of `Statifier.Interpreter.Selection.condition_match/2`
with a real datamodel evaluation through `Statifier.Evaluator`, and reshape the
private selection walk so that a `cond` that fails to evaluate enqueues an
`error.execution` platform event on the internal queue - catchable in the same
macrostep - without changing any public signature in `Selection` or
`Statifier.Interpreter`. Beads issue: `st-af3.2`.

## Current State Analysis

`condition_match/2` (`lib/statifier/interpreter/selection.ex:252-255`) is two
clauses of stub:

```elixir
def condition_match(%MachineState{}, %Transition{cond: nil}), do: {:ok, true}
def condition_match(%MachineState{}, %Transition{}), do: {:error, {:unsupported, :cond}}
```

Everything the replacement needs already exists:

- **The evaluation seam.** `Statifier.Evaluator.context/1` and
  `Statifier.Evaluator.evaluate/2` (`lib/statifier/evaluator.ex:98`, `:123`)
  are the one module over both arms of `Machine.expr()`, built on predicator
  5.0.0 with `on_unbound: :error` and the `In/1` host function. `evaluate/2`
  returns `{:ok, term()} | {:error, Statifier.Evaluator.Error.t()}` and never
  raises (`docs/architecture.md` principle 3).
- **The compiled cond.** `Statifier.Machine.Transition` carries `cond ::
  Machine.expr() | nil` and `cond_location :: Location.t() | nil`, both non-nil
  together (`lib/statifier/machine/transition.ex:34-40`). The compiler already
  builds them (`lib/statifier/compiler.ex:517-535`), compiling through
  `Compiler.Expressions.compile/3` with owner `{:transition, t_index}`.
- **The raise seam.** `MachineState.raise_platform/4`
  (`lib/statifier/machine_state.ex:332`) builds a `Cause` from an origin plus
  the counters as they stand and enqueues an `Event.platform/3` on the internal
  queue. `Statifier.Interpreter.Content.raise_execution_error/4`
  (`lib/statifier/interpreter/content.ex:168-172`) is the established call
  shape: `raise_platform(ms, "error.execution", origin, data: reason)`.
- **The threaded machine_state.** `select_transitions/2` and
  `select_eventless_transitions/1` already return `{MachineState.t(),
  [Transition.t()]}` (`selection.ex:270-306`), and `Interpreter` already
  continues with the returned machine_state at all three selection sites
  (`interpreter.ex:215`, `:289`, `:397`) - documented at `interpreter.ex:96-101`
  as existing precisely so this bead is a body change.

What is missing, and what makes this more than a two-line edit:

1. **`Cause.origin/0` has no transition arm.** It is
   `{:content, c_index, Content.owner()} | {:state, state_index}`
   (`lib/statifier/event/cause.ex:47-49`). A failed `cond` is not a content node
   and has no `c_index`. Note that `{:transition, t_index}` already exists as a
   `Content.owner()` value (`lib/statifier/machine/content.ex:43-46`) nested
   *inside* a `{:content, _, _}` origin - a top-level transition origin is a
   genuinely new third arm. Nothing in `lib/` destructures an origin by shape
   (verified: `raise_internal/4` / `raise_platform/4` take it opaquely and pass
   it to `Cause.new/3`; construction sites are `content/raise.ex:39`,
   `interpreter/content.ex:169`, `exit_entry.ex:774,814`), and no formatter or
   `Inspect` impl renders one, so a new arm breaks no exhaustive match.
2. **The private walk is a chain of pure boolean predicates.** Between the two
   entry points and `condition_match/2` sit `selected_for_atomic_state/3`
   (`Enum.find_value`, `selection.ex:331-339`), `first_matching_transition/4`
   (`Enum.find`, `:350-356`), and `transition_enabled?/3` (a bare boolean
   comparing `condition_match(...) == {:ok, true}`, `:368-379`). None of them
   thread anything out. Enqueuing on a failed cond requires reshaping this walk.
   These helpers were decomposed for exactly Credo's cyclomatic-complexity and
   nesting limits (`selection.ex:42-49`), so the reshape must not re-fuse them.
3. **Two module docs and two tests describe the stub as current.** The moduledoc
   paragraph at `selection.ex:29-41` and the `@doc` at `:236-251` both narrate
   the stub and say the day it changes is a deliberate edit. Two existing tests
   assert the stub's *inverted* behavior and will go red on Phase 1 unless
   rewritten, because both fixtures write `cond="true"`, which now evaluates to
   `{:ok, true}` and therefore now *does* select:
   - `test/statifier/interpreter/selection_test.exs:247` -
     `test "a transition with a written cond is not selected"` (fixture
     `condfail`, `selection_test.exs:73`).
   - `test/statifier/interpreter/selection_acceptance_test.exs:386` -
     `test "condition_match/2 is the one cond seam: nil cond -> {:ok, true}, written cond -> {:error, _}"`
     (fixture `cond_holder`, `:108`).

   The two `test "the machine_state comes back unchanged"` tests
   (`selection_test.exs:284-295` and `:352-363`) both use cond-free transitions
   and stay green through every phase; they keep their value as "unchanged when
   nothing fails" and are joined, not replaced, by a new "changed when a cond
   fails" test in Phase 2.

**Predicator's actual return values**, probed against the pinned 5.0.0 with
`on_unbound: :error` (this settles the coercion question below):

| cond source | `Predicator.evaluate/2` |
|---|---|
| `true` | `{:ok, true}` |
| `x > 3` (x bound to 5) | `{:ok, true}` |
| `1` | `{:ok, 1}` |
| `x` (x bound to 5) | `{:ok, 5}` |
| `x > 'a'` (type mismatch) | `{:ok, :undefined}` |
| `nope` (unbound) | `{:error, %Predicator.Errors.UndefinedVariableError{}}` |

So a written cond can come back a non-boolean without predicator calling it an
error, and this plan has to decide what that means.

## Desired End State

`condition_match/2` evaluates a written `cond` through `Statifier.Evaluator`
and returns `{:ok, true}` (enable), `{:ok, false}` (do not enable), or
`{:error, reason}` (do not enable, and the selection round enqueues
`error.execution`). Both entry points keep their signatures and return a
machine_state that carries any cond errors raised during that round. An
`error.execution` raised by a failing cond is dequeued and selected on in the
same macrostep, so a `<transition event="error.execution">` catches it.

Verify with: full `mix quality` green; the new tests in
`test/statifier/interpreter/selection_test.exs`,
`test/statifier/interpreter/selection_acceptance_test.exs`, and
`test/statifier/interpreter_test.exs`; and by hand, `Statifier.compile/1` on a
document with a failing cond followed by `Statifier.send_event/2` landing in the
catcher state.

### Decisions this plan makes (so the implementer does not re-open them)

**D1. A non-boolean `{:ok, value}` is an error, not a falsy value.** Only
`{:ok, true}` enables and only `{:ok, false}` does not; anything else -
`{:ok, 1}`, `{:ok, 5}`, `{:ok, :undefined}` - becomes
`{:error, {:non_boolean_cond, value}}` and therefore an `error.execution`.
Reason: `docs/architecture.md` principle 3 forbids rescue-to-default at a leaf,
and this module's own `@doc` (`selection.ex:238-242`) already refuses to treat
an un-evaluated cond as satisfied for that reason; collapsing an unexpected
value to `false` is the same mistake one step later. ADR-0004 rules out
importing ECMAScript truthiness - predicator is the datamodel, and it has no
truthiness rules to borrow. `docs/datamodel.md:88-96` records that the corpus
XSL was deliberately changed to emit strict `=== undefined` precisely because
non-strict comparison propagates `:undefined` instead of returning a boolean, so
`:undefined`-as-error is consistent with a decision already taken.
This decision is reversible in one clause if st-af3.8's full conformance run
turns up a corpus document relying on a truthy non-boolean cond; that run, not
this bead, is where such a counterexample can appear (see Scope Boundary).

**D2. The walk accumulates cond errors, not machine_state.** Of the shapes
weighed:

- *Accumulating fold over machine_state* - every private helper returns
  `{machine_state, result}`. Rejected: it makes `machine_state` an in-and-out
  value in helpers the moduledoc (`selection.ex:22-27`, `:36-38`) explicitly
  keeps as pure queries returning plain values, and it invites a later helper to
  make an unrelated machine_state write mid-walk. It also does not actually buy
  anything - counters do not move during selection, so an enqueue at the point
  of failure and an enqueue at the end of the round produce identical `Cause`
  stamps and identical queue order.
- *Pre-pass: evaluate every candidate cond up front into a memo, enqueue, then
  run the existing boolean walk against the memo.* **Rejected as a semantic
  deviation.** Appendix D evaluates `conditionMatch` only on the transitions the
  walk actually reaches - it breaks out of both loops at the first enabled
  transition - so a pre-pass would raise `error.execution` for conds the spec
  never evaluates. ADR-0002 makes that a semantic bug with no mechanical
  justification.
- **Chosen: collect-errors-then-enqueue.** The three private helpers thread a
  `[{Transition.t(), reason}]` accumulator through their returns; each entry
  point folds that list onto its machine_state with `raise_platform/4` before
  returning. Document order of the walk is the order of the list is the order of
  the queue. The accumulator is strictly smaller than a machine_state, every
  helper stays standalone-callable per `docs/observability.md` constraint 5, and
  the enqueue lands in exactly the two functions the moduledoc already
  designated for it.

**D3. The two entry points stay duplicated.** The reshape does *not* factor a
shared private `select/3` out of `select_transitions/2` and
`select_eventless_transitions/1`. The moduledoc (`selection.ex:284-291`) records
that the pseudocode writes these as two functions rather than one parameterized
by "is there an event", that this port keeps them that way, and that
`Credo.Check.Design.DuplicatedCode` is disabled in `.credo.exs` for exactly this
reason. Factoring them together now would be that parameterization.

**D4. `condition_match/2` keeps its arity-2 `(machine_state, transition)`
signature and builds its own context; the walk calls a private
`evaluate_cond/2` over a prebuilt context.** `condition_match/2` is the
Appendix D name at the port surface, where `mix adr.check` and ADR-0002 expect
it, and `docs/observability.md` constraint 5 wants it callable standalone in
`iex` from a machine_state alone. Building one context per *round* rather than
per *call* is what `lib/statifier/evaluator.ex:33-35` asks for, so the walk
needs a context-taking entry; the public function delegates to it after building
a context of its own. This is a mechanical decomposition of one pseudocode
function, in the same spirit as `transition_domain/3` (`selection.ex:173`), and
gets an inline comment saying so.

## What We're NOT Doing

- **Not flipping `conditional_transitions` in the feature detector.** See Scope
  Boundary below. st-af3.8 owns it.
- **Not closing st-mp4.** The richer positions-into-diagnostics work - rendering
  a `Cause` and an `Evaluator.Error` into a human message like "columns 22-27 of
  `user.age > 18 AND score > 5` loaded an unbound `score`" - stays open. This
  bead makes the ingredients present and structurally reachable
  (`origin -> Machine.transition/2 -> cond_location`, and `data.span`); no
  formatter is written here, and none exists today.
- **Not guarding against the eventless cond-error livelock.** A cond that
  deterministically errors on an *eventless* transition makes the macrostep
  fold non-terminating: each round's eventless probe evaluates the cond, enqueues
  `error.execution`, and `internal_round/1` dequeues it and selects on it (which
  never re-evaluates that eventless cond, since an event-matched selection round
  short-circuits `%Transition{events: []}` before reaching the cond), leaving
  the queue empty for the next probe to refill. Appendix D contains no guard and
  SCXML already permits non-terminating macrosteps for ordinary eventless
  self-loops, so inventing one here would be a semantic deviation with no
  mechanical reason (ADR-0002). It is filed as **st-sd1** ("Macrostep step
  budget: an erroring eventless cond livelocks the fold"), which owns the
  general engine-level bound, and no test in this plan constructs one - Phase 3's
  end-to-end test uses an **event-matched** cond, which terminates cleanly. This
  hazard is flagged forward to st-af3.8, whose full conformance run is the first
  place a corpus document could hang the suite on it.
- **Not touching `remove_conflicting_transitions/2` or the domain half of the
  module.** Neither can raise; both keep returning plain values with no
  machine_state, per `selection.ex:36-38`.
- **Not adding `<assign>`, `<if>`, `<foreach>`, or `<data>` seeding.** Those are
  st-af3.3 / st-af3.4 and later.
- **Not caching the built context on `MachineState`.** Ruled out on two grounds
  at `lib/statifier/evaluator.ex:39-61`; st-sdh owns the performance question.

## Scope Boundary: the feature detector flip belongs to st-af3.8, not here

`FeatureDetector` (`test/support/feature_detector.ex`) marks
`conditional_transitions` `:unsupported`, so no generated corpus document
carrying a cond-bearing transition reaches selection today. **st-af3.8 ("Corpus:
flip datamodel features, split the content detector, ratchet") owns that flip**
- its description names `conditional_transitions` explicitly among the six atoms
it flips, and its acceptance criteria bind the flip, the detector-test table
update, the full conformance run, and the `mix test.baseline add` ratchet into
one PR, per `docs/testing.md`'s "a feature PR that makes tests pass adds them in
the same PR". st-af3.8 depends on this bead. Splitting the flip out of it would
break that atomicity for no gain.

Consequences for this plan, stated so nothing is left ambiguous:

- No phase here touches `test/support/feature_detector.ex`,
  `test/statifier/support/feature_detector_test.exs`, or
  `test/passing_tests.json`.
- No phase here runs `mix test --include scion --include scxml_w3` as a gate, and
  no phase can move a conformance result. There is therefore **no
  `## Corpus/Ratchet Notes` section** in this plan and no `mix test.regression` /
  `mix test.baseline add` criterion in any phase - the project extension asks for
  those "whenever a phase can move conformance results", and none can.
- Every test in this plan therefore builds its own machine from hand-written XML
  through the local `compile!/1` pipeline helper, exactly as the current
  `condition_match/2` `@doc` describes ("Reachable, and tested, from a
  machine_state and transition built by hand"). Note this is stronger than
  literally hand-constructing structs: the detector gates only the *generated*
  corpus suites, so a hand-written XML heredoc with a `cond` compiles and runs
  end to end today. Phase 3 depends on that.

## Implementation Approach

Three phases, each independently committable and gate-verifiable:

1. **Make `condition_match/2` real** - a body change plus its two docs and its
   tests. After this phase a failing cond correctly does not enable a transition;
   it just does not announce itself yet. Nothing about the walk changes, so both
   `machine_state comes back unchanged` tests still pass untouched.
2. **Make the failure announce itself** - add the `Cause.origin` transition arm,
   reshape the private walk to accumulate cond errors, and fold them onto the
   machine_state in each entry point. The new type arm arrives with its producer
   in the same phase, so there is no intermediate commit with a dead union
   member.
3. **Prove same-macrostep catchability** - an end-to-end test through
   `Statifier.compile/1` / `Interpreter.handle_event/2` that a `cond` failure's
   `error.execution` is caught by a transition in the same macrostep, plus the
   changelog fragment.

Phases 1 and 2 both touch `selection.ex`, so they do not parallelize across
worktrees; they are sequential increments on one branch.

## Phase 1: Real evaluation in `condition_match/2`

### Overview

Replace the stub body with an `Evaluator` call and settle the boolean
discipline (D1). No walk changes, no enqueue, no `Cause` changes.

### Changes Required:

#### 1. The function body

**File**: `lib/statifier/interpreter/selection.ex`
**Changes**: Add `alias Statifier.Evaluator`. Keep the public `condition_match/2`
signature and `@spec` exactly as they are; delegate to a private
`evaluate_cond/2` over a prebuilt `Predicator.Context.t()` (D4).

```elixir
  @spec condition_match(machine_state :: MachineState.t(), transition :: Transition.t()) ::
          {:ok, boolean()} | {:error, term()}
  def condition_match(%MachineState{} = machine_state, %Transition{} = transition) do
    evaluate_cond(Evaluator.context(machine_state), transition)
  end

  # `conditionMatch`'s body over a context the caller already built - the
  # selection walk builds one per round (`Statifier.Evaluator`'s "once per
  # evaluation site" contract), while `condition_match/2` above builds one per
  # call so the spec-named port stays callable from a machine_state alone
  # (docs/observability.md constraint 5). ADR-0002 mechanical decomposition of
  # one pseudocode function, not a second one.
  @spec evaluate_cond(context :: Predicator.Context.t(), transition :: Transition.t()) ::
          {:ok, boolean()} | {:error, term()}
  defp evaluate_cond(_context, %Transition{cond: nil}), do: {:ok, true}

  defp evaluate_cond(context, %Transition{cond: cond}) do
    case Evaluator.evaluate(context, cond) do
      {:ok, true} -> {:ok, true}
      {:ok, false} -> {:ok, false}
      # D1: a cond that evaluates to a non-boolean is a type failure, not a
      # falsy value - collapsing it to `false` would be the rescue-to-default
      # at a leaf docs/architecture.md principle 3 forbids. ADR-0004: predicator
      # is the datamodel and has no ECMAScript truthiness to borrow.
      {:ok, other} -> {:error, {:non_boolean_cond, other}}
      {:error, %Evaluator.Error{} = error} -> {:error, error}
    end
  end
```

#### 2. The `@doc` on `condition_match/2`

**File**: `lib/statifier/interpreter/selection.ex:236-251`
**Changes**: Rewrite. It must now say: `nil` cond passes; a written cond is
evaluated through `Statifier.Evaluator` against a context built per call here
and per round in the walk; `{:ok, true}` enables, `{:ok, false}` and
`{:error, _}` do not; a non-boolean result is an error (D1, with its reason);
and that the `{:error, _}` path's `error.execution` enqueue lives in the
entry points, not here. Keep the standing note that a compiled corpus document
cannot reach this yet (FeatureDetector, st-af3.8) and that it is reachable and
tested from hand-written XML.

The moduledoc paragraph at `:29-41` is **not** touched in this phase - it
describes the entry points' machine_state, which is still genuinely unchanged
until Phase 2.

#### 3. Rewrite the two inverted tests

**File**: `test/statifier/interpreter/selection_test.exs:243-252`
**Changes**: `test "a transition with a written cond is not selected"` asserts
the stub's behavior on a `cond="true"` fixture and inverts. Replace the
`condfail` fixture state's transition with one whose cond genuinely evaluates
false (`cond="false"`), rename the test to
`"a transition whose cond evaluates false is not selected"`, and update the
document-order comment at `:28` and any `@indexes` entry that shifts. Add a
sibling test that a `cond="true"` transition **is** selected. Both get sabotage
lines.

**File**: `test/statifier/interpreter/selection_acceptance_test.exs:380-394`
**Changes**: The AC comment quotes the *old* acceptance criterion ("cond seam is
one stubbed function..."). Rewrite the test and its AC comment against this
bead's criterion ("cond gates selection"): `nil` cond -> `{:ok, true}`;
`cond="true"` -> `{:ok, true}`; `cond="false"` -> `{:ok, false}`; a cond naming
an unbound variable -> `{:error, %Evaluator.Error{}}`. Add the needed fixture
states beside `cond_holder` / `nocond_holder` and update the index comment block
and `@indexes` map. Keep the existing "all eight spec-named functions exist" and
"callable standalone" checks (`:174-192`, `:406-428`) passing unchanged - the
public arity is deliberately preserved.

#### 4. New unit coverage for `condition_match/2`

**File**: `test/statifier/interpreter/selection_test.exs`
**Changes**: Add a `describe "condition_match/2"` block (the file has none
today). Each test gets a sabotage line naming the exact clause mutated and the
assertion that reddens. Cases:

- `cond: nil` returns `{:ok, true}` with an empty datamodel.
- `cond="true"` returns `{:ok, true}`; `cond="false"` returns `{:ok, false}`.
- A cond over bound data (`machine_state` built with
  `MachineState.new(machine, datamodel: %{"x" => 5})`) - `x > 3` is
  `{:ok, true}`, `x > 9` is `{:ok, false}`.
- A cond naming an unbound variable returns
  `{:error, %Evaluator.Error{source: "nope", error: %Predicator.Errors.UndefinedVariableError{}}}`,
  and its `span` is non-nil - the ADR-0014 item 4 payload, asserted structurally.
- A non-boolean cond (`cond="1"`) returns `{:error, {:non_boolean_cond, 1}}` (D1).
- A cond calling `In('someState')` answers against the machine_state's
  configuration - true for a state in the configuration, false for one that is
  not, and false for an id the document never declared
  (`lib/statifier/evaluator.ex:136-151`).

## Phase 2: `error.execution` on a failed cond

### Overview

Add the `{:transition, t_index}` arm to `Cause.origin/0`, reshape the private
selection walk to accumulate cond errors (D2), and fold them onto the
machine_state in each entry point (D3). The new type arm and its producer land
together, so no intermediate commit carries a dead union member.

### Changes Required:

#### 1. `Cause.origin/0` gains a transition arm

**File**: `lib/statifier/event/cause.ex:31-49`
**Changes**: Add the third arm and its `@typedoc` bullet.

```elixir
  @type origin ::
          {:content, non_neg_integer(), Content.owner()}
          | {:state, non_neg_integer()}
          | {:transition, non_neg_integer()}
```

The `@typedoc` bullet must say: the platform raised the event about a
transition's own `cond`, with no content node behind it; `t_index` resolves
through `Statifier.Machine.transition/2`, and the transition it names carries
`cond` and `cond_location`, which is how an ADR-0014 item 4 diagnostic reaches
the expression's span in the document without this cause duplicating the

node living in a transition's block), and that the moduledoc's own history note
(`:14-23`) refers to that older, different shape.

#### 2. The walk reshape

**File**: `lib/statifier/interpreter/selection.ex`
**Changes**: The three private helpers gain a `cond_errors` accumulator in and
out. Nothing public changes.

```elixir
  @typep cond_error :: {Transition.t(), term()}

  # `Enum.find_value` becomes `Enum.reduce_while` for the same labelled `break
  # loop`, threading the cond-error accumulator out alongside the result.
  # Structure is unchanged; only the accumulator is new. ADR-0002.
  @spec selected_for_atomic_state(
          machine_state :: MachineState.t(),
          context :: Predicator.Context.t(),
          state_index :: non_neg_integer(),
          event_tokens :: [String.t()] | nil,
          cond_errors :: [cond_error()]
        ) :: {[Transition.t()], [cond_error()]}
  defp selected_for_atomic_state(
         %MachineState{machine: machine} = machine_state,
         context,
         state_index,
         event_tokens,
         cond_errors
       ) do
    [state_index | Machine.proper_ancestors(machine, state_index)]
    |> Enum.reduce_while({[], cond_errors}, fn s, {[], errors} ->
      case first_matching_transition(machine_state, context, machine, s, event_tokens, errors) do
        {nil, errors} -> {:cont, {[], errors}}
        {transition, errors} -> {:halt, {[transition], errors}}
      end
    end)
  end
```

`first_matching_transition/6` turns its `Enum.find` into the same
`Enum.reduce_while` over `{nil, errors}`. `transition_enabled?/3` becomes
`transition_enabled/5` returning `{boolean(), [cond_error()]}`, keeping its four
clauses one-to-one with today's (`events: []` + `nil` tokens;
`events: []` + tokens; non-empty events + `nil` tokens; non-empty events +
tokens), with the two cond-reaching clauses delegating to one small helper:

```elixir
  @spec cond_enabled(
          context :: Predicator.Context.t(),
          transition :: Transition.t(),
          cond_errors :: [cond_error()]
        ) :: {boolean(), [cond_error()]}
  defp cond_enabled(context, transition, cond_errors) do
    case evaluate_cond(context, transition) do
      {:ok, true} -> {true, cond_errors}
      {:ok, false} -> {false, cond_errors}
      # Not enabling *and* recording: docs/architecture.md principle 3 - the
      # error becomes an event, it is never swallowed into a bare `false`.
      {:error, reason} -> {false, cond_errors ++ [{transition, reason}]}
    end
  end
```

Credo watch: each reshaped helper keeps one `case` and no added nesting level;
`cond_enabled/3`'s existence is what keeps `transition_enabled/5`'s clauses flat
(`selection.ex:42-49`'s stated reason for the decomposition).

#### 3. The two entry points enqueue

**File**: `lib/statifier/interpreter/selection.ex:272-306`
**Changes**: Each builds one context per round, folds the walk with
`Enum.flat_map_reduce/3`, and raises the collected errors before the conflict
filter. Kept as two duplicated bodies, deliberately (D3).

```elixir
  def select_transitions(%MachineState{} = machine_state, %Event{name: name}) do
    event_tokens = NameMatch.tokenize(name)
    context = Evaluator.context(machine_state)

    {enabled, cond_errors} =
      machine_state
      |> atomic_states_in_document_order()
      |> Enum.flat_map_reduce(
        [],
        &selected_for_atomic_state(machine_state, context, &1, event_tokens, &2)
      )

    machine_state = raise_cond_errors(machine_state, cond_errors)
    enabled = Enum.uniq_by(enabled, & &1.t_index)

    {machine_state, remove_conflicting_transitions(machine_state, enabled)}
  end
```

`select_eventless_transitions/1` is the same body with `event_tokens = nil` and
no `tokenize/1`.

```elixir
  # The errors-are-events conversion for a failed `cond`, in document order -
  # `raise_platform/4` not `raise_internal/4` because spec 5.10.1 classifies
  # `error.*` as a platform event, exactly as
  # `Statifier.Interpreter.Content.raise_execution_error/4` does for a failed
  # content node; spec 3.12.2 is what puts it on the internal queue at all.
  # The origin names the transition, whose `cond_location` an ADR-0014 item 4
  # diagnostic resolves through `Machine.transition/2`.
  @spec raise_cond_errors(machine_state :: MachineState.t(), cond_errors :: [cond_error()]) ::
          MachineState.t()
  defp raise_cond_errors(machine_state, cond_errors) do
    Enum.reduce(cond_errors, machine_state, fn {transition, reason}, ms ->
      MachineState.raise_platform(ms, "error.execution", {:transition, transition.t_index},
        data: reason
      )
    end)
  end
```

Nilability note for the implementer: `Transition.t_index` is typed
`non_neg_integer() | nil` (`lib/statifier/machine/transition.ex:69`), while the
new `Cause.origin/0` arm is `{:transition, non_neg_integer()}`. At runtime the
`nil` case cannot reach here - `nil` names only the synthesized initial
transition, which lives in `initial_transition` / `history_default` and never in
`State.transitions`, so `first_matching_transition/6` never walks it (that
struct's own moduledoc, `:11-18`). If Dialyzer nonetheless flags the contract,
the fix is a local guard or pattern match at `raise_cond_errors/2` narrowing
`t_index` to the non-nil case - **not** widening `Cause.origin/0` to accept
`nil`, which would make a meaningless origin representable.

Counter note for the implementer: the cause is stamped with the counters as they
stand during selection, i.e. **before** `run_selected/3` calls
`begin_microstep/1`. That is the same "one microstep behind" stamping
`interpreter.ex:72-80` already documents for `Trace.TransitionsSelected`, and it
is correct - no exit or entry has happened yet.

Key edge cases, each pinned by a test:

1. A cond on a transition the walk never reaches must **not** be evaluated and
   must **not** raise (the anti-pre-pass pin).

3. `:undefined` from a type-mismatched comparison is a non-boolean result and
   therefore an error.
4. Two failing conds in one round enqueue two errors, in document order.
5. `cond: nil` never touches the evaluator at all.
6. `In('x')` inside a cond reads the configuration the round started with.
7. An uncaught `error.execution` from a cond reaches quiescence and does not hang.

Every test asserting `lib/` behavior carries a `# sabotage:` line immediately
above it, in the repo's established shape - backtick-quoted function/clause, the
