# Invoke type=scxml child sessions Implementation Plan

## Overview

Give `{:invoke, _}`, `{:cancel_invoke, _}` and `{:autoforward, _}` a performer.
st-cmq.6 landed the whole pure-core half: the element lowers, compiles, and
produces all three effects in the Appendix D positions, and `<finalize>`
already *executes* inside the core. st-cmq.5 landed the target vocabulary, the
registry, and `Statifier.Supervisor`. What is missing is one layer: the parent
session has no invocation table, so all three effects terminate at
`Session.Effects`'s `{:unroutable, effect}`, and `#_parent` resolves
unconditionally to `error.communication`.

This plan lands the **session-side protocol** ADR-0027 decision 3 specifies:
the parent-held invocation table, child sessions started on
`Statifier.SessionSupervisor` with 6.4.3 name-matched datamodel seeding,
`#_parent` routing, `done.invoke.<invokeid>` with donedata, autoforward
delivery, cancel-invoke, and the 6.4.3 discard of a cancelled invocation's
queued events.

It does **not** land inline `<content><scxml>` compilation or `src`
dereferencing. Both are real gaps against the bead's acceptance criteria, both
are argued in full under "What We're NOT Doing" and Decisions 1 and 2, and
neither costs this bead a single conformance test, because `Statifier.Case`
never starts a `Session` and every invoke corpus file is blocked on st-cmq.9
regardless.

Bead: st-cmq.7

## Current State Analysis

Everything below is established fact from
`docs/research/260815-st-cmq.7-invoke-scxml-child-sessions.md`, re-verified at
this commit.

**The three effects arrive and stop.** `Session.Effects.plan_one/2` plans
`{:invoke, _}`, `{:cancel_invoke, _}` and `{:autoforward, _}` as
`[{:notify, effect}, {:unroutable, effect}]`
(`lib/statifier/session/effects.ex:98-108`), and `Session.perform_instruction/3`
turns `{:unroutable, _}` into a subscriber message and nothing else
(`lib/statifier/session.ex:642-645`). The clause list is total over a closed
union with no fallback, so a new instruction tag is a compile-visible,
test-visible addition rather than a silent one.

**`Session.State` has no invocation field.** Its struct is `machine_state,
session_id, done_effect, inbox, timers, timer_refs, subscribers, halted,
recording` (`lib/statifier/session.ex:158-185`). `deliver/5`'s `:parent` and
`{:invoke, _}` clauses both fall to `communication_error/4` unconditionally
with the comment "no invocation table yet"
(`lib/statifier/session.ex:703-709`); `communication_error/4` (`:750-765`) is
the single private resolver a table changes.

**`Effect.Invoke` carries no `invoke_index`.** Its fields are `invoke_id,
type, src, params, content, autoforward, state_index, macrostep, microstep`
(`lib/statifier/effect/invoke.ex:36-56`). `invoke_one/6` has `invoke_index` in
hand at build time (`lib/statifier/interpreter.ex:1324-1359`) and drops it.
`Cause.origin()`'s `{:invoke, state_index, invoke_index}` arm
(`lib/statifier/event/cause.ex:99-113,140`) is the shape the core already uses
for a failed argument evaluation, and the session cannot name a failing
`<invoke>` in an origin without the second index.

**The runtime exists and is embedder-placed.** `Statifier.Supervisor`
(`lib/statifier/supervisor.ex`) holds `{Registry, keys: :unique, name:
Statifier.Registry}` then `{DynamicSupervisor, name:
Statifier.SessionSupervisor}` under `:rest_for_one`.
`Statifier.start_session/2` (`lib/statifier.ex:176-196`) builds the child spec
by hand (`%{id: Session, start: {Session, :start_link, [machine, opts]},
restart: :temporary}`) and calls `DynamicSupervisor.start_child/2`, returning
its `{:ok, pid} | {:error, term}` - `{:error, _}` including the case where
`Statifier.SessionSupervisor` was never started. `Session.register_session/1`
(`:400-408`) rescues every registration failure into a no-op, so a bare
`start_link/2` session is legal and unregistered.

**The datamodel seam for a child is already anticipated.**
`MachineState.new/2` merges system variables *over* the caller's `:datamodel`
(`lib/statifier/machine_state.ex:436`), and
`Statifier.Interpreter.Datamodel` captures `env_ids` from
`Map.keys(machine_state.datamodel)` before seeding
(`lib/statifier/interpreter/datamodel.ex:237`), skipping any top-level
`<data>` whose id is already an `env_id` (`:295-303`) and guarding
`state_index == 0` out of late binding for exactly this reason (`:364-372`,
`:406`) - its moduledoc names the invoked-child case by hand. Top-level
`<data>` ids on a compiled `Machine` are
`Machine.at(machine, 0).data |> Enum.map(&Machine.data(machine, &1).id)`
(`lib/statifier/machine/state.ex:33,67`, `lib/statifier/machine.ex:195-196`).

**Termination idles, it does not stop.** `{:done, _}` plans to
`[{:notify, effect}, {:halt, :done}]`; the session retains `%Effect.Done{}`
in `done_effect` (with `donedata`) and stays alive
(`lib/statifier/session.ex:45-57,581-584,647-652`). A cancelled session halts
`:cancelled` through the same `exit_interpreter/1` walk, which is what runs
6.4.3's mandated `<onexit>` handlers.

**The inbox is FIFO with no keyed discard.** `Session.Inbox`
(`lib/statifier/session/inbox.ex`) exposes `new/0`, `enqueue_event/2`,
`enqueue_cancel/1`, `next/1`, `cancel_event?/1`, `pending_events/1`, `size/1`.
The only existing keyed discard anywhere is `Timers.take/2` by send id.

**Replay is a closed fold.** `Statifier.Replay.perform_instruction/3` has a
clause for every member of `Effects.instruction()` and no catch-all
(`lib/statifier/replay.ex:327-393`), per ADR-0034; a new tag is a
`FunctionClauseError` at the first test that produces one.

**The corpus cannot move.** Thirty-five W3C mandatory files declare
`required_features: [:invoke_elements]`; `FeatureDetector` marks
`invoke_elements` and `finalize_elements` `:unsupported`
(`test/support/feature_detector.ex:112-113`); and `Statifier.Case.test_scxml/4`
drives the pure four-function API and never starts a `Session`
(`test/support/case.ex:77-98`). Twenty-five of the twenty-seven files under
`test/scxml_tests/mandatory/invoke/` carry a `<content>` element, and
`build_content/2` rejects every element child of `<content>` as
`{:misplaced_element, _, "content"}` (`lib/statifier/lowering/builders.ex:356-373`),
which `Lowering.finalize/2` makes fatal (`lib/statifier/lowering.ex:164-168`).

**A defect discovered while reading the records, not caused by this bead.**
`docs/adr/` contains two files numbered 0037:
`0037-session-detected-send-failures-re-enter-the-core.md` and
`0037-unbound-spelled-undefined-at-the-writer.md`, and `docs/adr/README.md`
lists only one at that number. This plan claims **0038** for its own record and
does not renumber either existing file - a renumber rewrites citations across
the tree and is its own change. Phase 1 files a bead for it.

## Desired End State

An `<invoke type="scxml">` whose child document is available as markup starts a
real child `Statifier.Session` on `Statifier.SessionSupervisor`, seeded with
exactly those `<param>`/namelist values whose names match a top-level `<data>`
id of the child, with the parent monitoring the child and the child monitoring
the parent. The child's `<send target="#_parent">` reaches the parent's
external queue with `invokeid` stamped on it, so the core's existing finalize
pass runs the right `<finalize>` before selection. When the child reaches a
top-level final it puts `done.invoke.<invokeid>` carrying its donedata on the
parent's external queue; when it is cancelled it runs its `<onexit>` handlers
and puts nothing. Every external event the parent removes from its queue is
forwarded verbatim to each autoforwarding invocation. Exiting the invoking
state cancels the child and discards every queued event from that invocation,
and a `Replay` of the same recording reaches the same configuration.

Verified by: full unscoped `mix quality` green at every phase; new unit and
integration tests under `test/statifier/`; `test/passing_tests.json` unchanged
(see Corpus/Ratchet Notes); `mix gate.verify` at the end of the branch.

### Key Discoveries

- **`<finalize>` is already implemented.** `apply_invoke_passes/2` runs inside
  `Interpreter.handle_event/2` at `lib/statifier/interpreter.ex:447`, after
  `put_event/2` and before `Selection.select_transitions/2` - Appendix D's own
  position. This bead delivers an event carrying the right `invokeid`; it does
  not implement finalize (`lib/statifier/interpreter.ex:527-579,693-750`).
- **Appendix D defines no pseudocode for `invoke`, `cancelInvoke`,
  `applyFinalize`, `returnDoneEvent` or `isCancelEvent`** - the REC declares
  each platform-specific. Every call site is already ported. This bead's
  Appendix D obligation is therefore to leave the ported call sites untouched,
  not to port new ones (ADR-0002).
- Spec 6.4.2 puts autoforward "at the point at which it removes it from the
  external event queue of the invoking session for processing" and finalize
  "right before it removes the event from the event queue for processing" -
  both are inside the one synchronous `drain_event/2` -> `handle_event/2`
  turn, before the next `Inbox.next/1`.
- Spec 6.4.3: a cancelled session "MUST exit at the end of the next
  microstep. The Processor MUST execute the `<onexit>` handlers for all active
  states in the invoked session, but it MUST NOT generate the done.invoke.id
  event." `Session.cancel/1` -> `Interpreter.cancel/1` -> `exit_interpreter/1`
  is exactly that walk, and halts `:cancelled` rather than `:done`.
- Spec 3.12.2 is the only clause that assigns an error class to a failed
  `<invoke>`: `error.communication` covers "errors occurring while trying to
  communicate with external entities, **such as those arising from `<send>`
  and `<invoke>`**". Nothing in 6.4 names an error for a service that fails to
  start (Decision 4).
- Spec 6.4.4's prose spells the parent target `'_parent'` while C.1 spells it
  `#_parent` - the same disagreement `Target.parse/1` already resolves for
  `_internal`/`#_internal` by accepting both (Decision 8).
- ADR-0027 forecloses links and a supervisor-per-parent by name; monitors plus
  a parent-held table is the decided protocol, and the queued-event discard is
  explicitly "inbox work, not process work".
- `Mix.Statifier.AdrGuard`'s `@effect_interpreter_paths` is exactly
  `["lib/statifier/session.ex", "lib/statifier/supervisor.ex"]`
  (`lib/mix/statifier/adr_guard.ex:78`), and ADR-0027 pre-argues a third entry
  as "a smell to be argued, not defaulted". This plan needs no third entry
  (Decision 6), so it carries **no ADR-0011 ledger obligation** and no human
  approval gate.

## What We're NOT Doing

- **No inline `<content><scxml>...</scxml></content>` compilation.** This is
  the bead's acceptance criterion this branch cannot meet, and it is stated
  plainly rather than dropped. See Decision 1. Follow-up bead filed in Phase 1.
- **No `src` dereferencing inside the library.** The library never fetches;
  resolution is the embedder's, per ADR-0024's posture and ADR-0031's explicit
  hand-off. See Decision 2. The bead's "starts from src" criterion is met in
  the sense the engine can honor - an embedder-resolved `src` starts a child -
  and not in the sense of the corpus's `'file:test216sub1.scxml'`, which needs
  both a fetcher and the sub-document fixtures that were deliberately filtered
  out of corpus emission (st-rbp).
- **No `<dep>` sub-document fixtures.** They are filtered from emission by
  design and absent from the tree; putting them back is corpus tooling
  (`area:corpus`), not interpreter work, and buys nothing while st-cmq.9 is
  open.
- **No `FeatureDetector` reclassification and no ratchet movement.**
  st-cmq.6's plan predicted this bead would flip `invoke_elements` and
  `finalize_elements`; that prediction is wrong now for a reason st-cmq.6
  itself named. See Decision 7 and Corpus/Ratchet Notes.
- **No `<send target="#_invokeid">` resolution.** That is st-xcgr, filed by
  st-cmq.5 and blocked on this bead for the table. This plan builds the shared
  resolver `deliver({:invoke, id}, ...)` will use and deliberately leaves that
  one `deliver/5` clause on `communication_error/4`, so st-xcgr is a one-clause
  change plus its own tests. Autoforward does **not** wait on it: it carries
  `invoke_id` on the effect and resolves the table directly, which is what
  Appendix D's `send(inv.id, externalEvent)` means here (research question 4).
- **No BasicHTTP Event I/O Processor and no non-SCXML invoke types.** An
  unsupported invoke `type` raises `error.execution` and starts nothing.
- **No handler-registry invoke as an extension.** That is the epic's separate
  bead.
- **No multiple named runtime instances.** ADR-0027 defers them; a child
  always lands on the one `Statifier.SessionSupervisor`.
- **No renumbering of the duplicate ADR-0037 files.** Recorded above and
  filed as its own bead in Phase 1; renumbering rewrites citations across
  `lib/`, `docs/` and tests and does not belong in a feature branch.
- **No `Statifier.Case` harness change.** st-cmq.9 owns starting a `Session`
  under the corpus harness; st-cmq.5's plan already assigned it there.

## Implementation Approach

Six phases, each independently committable and gate-verifiable with a full
unscoped `mix quality`. The split follows the session's own module boundaries -
pure planner and pure value modules first, then the performing clauses, one
protocol obligation at a time - so that no phase leaves a structure in the tree
without a caller and a test.

The ordering is forced in one place only: the invocation table (Phase 2) must
exist before `#_parent`, autoforward, or cancel can resolve anything. Phases 3,
4 and 5 are independent of each other given Phase 2 and could be reordered or
parallelized across worktrees.

Every phase that edits an existing comment carries the same gate hazard
st-cmq.6's plan documented: `Mix.Statifier.AdrGuard`'s `adr-0018-bead-id`
check fails on a bead ID on an *added* diff line in a comment, moduledoc, doc,
typedoc or test description. Several of the comments this plan rewrites
currently say "a later bead"; the replacements cite ADR numbers, never bead
IDs.

`Statifier.Session` is the only module in this plan that starts a process,
monitors one, or sends to one. Every new value module is pure.

### Decision 1: inline `<content><scxml>` is deferred, with its reason

The bead asks for a child session started "from `<content>` (an inline
document)". Today `Statifier.Lowering.Builders.build_content/2` reports every
element child of `<content>` as `{:misplaced_element, name, "content"}` and
`Lowering.finalize/2` makes that fatal, so the twenty-five corpus files that
write `<content><scxml>...` do not compile at all - the failure is in the
parser layer, three layers below anything this bead touches.

`Statifier.Document.Content`'s moduledoc records why: preserving markup "would
mean holding a DOM subtree inside a Document struct, crossing the layer
boundary this rewrite is organized around, and nothing in the conformance
corpus needs it". The second clause is now false. The first is still true, and
choosing among the three available answers - hold a DOM subtree, keep the raw
source span and re-parse later, or re-serialize the subtree to XML at lowering
- is a layer-boundary decision of exactly the kind `docs/adr/` exists for.

**This branch does not decide it.** Three things make deferral the careful
call rather than the convenient one:

1. It is `area:parser` work in an `area:interpreter` bead. The change is in
   `lowering/builders.ex` and `document/content.ex`; nothing in it needs the
   session runtime, and nothing in the session runtime needs it to be designed
   first.
2. It buys **zero** conformance movement here. `Statifier.Case` never starts a
   `Session` (`test/support/case.ex:77-98`), so even a perfectly compiling
   `<content><scxml>` would still fail every one of the twenty-five files on
   its assertions. Both halves are blocked on st-cmq.9 either way.
3. Deciding it inside a plan whose subject is the session protocol is how a
   load-bearing decision gets made by accident in the module least suited to
   hold it - the precise failure st-cmq.10 was raised to prevent, one bead
   earlier in this same epic.

What this branch does instead: `Statifier.Invoke.Source` accepts a `content`
that is **markup in a binary** and compiles it with `Statifier.compile/1`. A
`<content>` holding XML as text already reaches the session that way today, so
the inline-document path is implemented and tested end to end; only the
lowering of *element* children remains closed. Phase 1 files the follow-up bead
with this analysis attached, so the next planner starts from a recorded
decision rather than rediscovering the blocker.

### Decision 2: `src` is resolved by the embedder, never fetched by the library

ADR-0031 routed this here by name: "whether anything downstream fetches the
resolved URI, and under what security posture, is st-cmq.7's call." ADR-0024
answered the sibling question for `<data src>` with "never fetched, at any
binding time", and explicitly declined to extend that answer to `<invoke>`,
which "sits at the effect boundary where a fetch may genuinely be
expressible".

**The library does not fetch.** A `src` reaches
`Statifier.Invoke.Source.resolve/2` and, with no embedder resolver configured,
returns `{:error, :src_not_resolved}`, which the session turns into
`error.communication` on the parent (Decision 4). An embedder that wants
`file:`, `http:`, or an application-specific scheme supplies
`invoke_source: fun` when it starts the parent session; the function takes the
resolved URI string and returns `{:ok, %Machine{}} | {:error, term}`.

The reasoning is ADR-0004's security posture, unchanged in kind by the effect
boundary: a document-named URI dereferenced by the engine is the engine
fetching whatever the document says, and a library that ships this on by
default hands every embedder a request-forgery surface they did not choose.
Handing the embedder the decision costs one option and matches what this
project already decided once, in ADR-0024, for the same shape of question. It
is recorded as ADR-0038 rather than as a plan sentence because ADR-0031 asked
for a record, and because "does the engine fetch URLs" is not a detail a future
reader should have to reconstruct from a resolver's default argument.

The resolver is also the seam a future `src`-fetching bead extends rather than
redesigns: shipping a default fetcher later means adding one implementation, not
moving the decision point.

### Decision 3: the invocation table is a pure value module; the process work stays in `session.ex`

`Statifier.Session.Invocations` is a struct over `%{invoke_id =>
%Entry{session_id, pid, monitor_ref, autoforward}}` with a `pid -> invoke_id`
reverse index, in the same shape and the same directory as `Session.Inbox` and
`Session.Timers`: pure data, pure functions, testable with no process at all.
`Session` holds one in its state and makes every `start_child`, `monitor`,
`demonitor` and `send` call itself.

This is what keeps `Mix.Statifier.AdrGuard.@effect_interpreter_paths` at two
entries. ADR-0027 pre-argued a third path as "a smell to be argued, not
defaulted", and the argument is unnecessary here because the split the module
already uses - "the deciding half lives in `Inbox`/`Timers`/`Effects` ... only
the performing half lives here", `Session`'s own moduledoc - covers this case
without modification. **This plan therefore carries no `.quality.exs`,
`.credo.exs` or `adr_guard.ex` change, no `docs/quality-gate-changes.md` entry,
and no human approval gate.** If an implementer finds themselves reaching for a
third exempt path, that is a signal the split has been drawn wrong, not a
signal to widen the guard.

### Decision 4: a child that cannot start raises `error.communication`

ADR-0027 left this open by name: "what error an `<invoke>` raises when the
runtime supervisor is not running is st-cmq.7's detail to settle against spec
6.4's error clauses." 6.4 has no such clause. 3.12.2 does:

> Two error events are defined in this specification: 'error.communication' and
> 'error.execution'. The former cover errors occurring while trying to
> communicate with external entities, such as those arising from `<send>` and
> `<invoke>`, while the latter category consists of errors internal to the
> execution of the document, such as those arising from expression evaluation.

Starting a child session is communicating with an external entity, and the
sentence names `<invoke>` outright. So **every runtime failure to start the
child raises `error.communication`** on the parent's internal queue, through
ADR-0039's `deliver_internal/5` door, with origin
`{:invoke, state_index, invoke_index}`: `Statifier.SessionSupervisor` not
running, `DynamicSupervisor.start_child/2` returning `{:error, _}`, a `src`
with no embedder resolver, a resolver returning `{:error, _}`, and a
`<content>` binary that does not compile.

The one exception is an **unsupported `type`**, which is `error.execution`: it
is a property of the document rather than of the world, no communication is
attempted, and it is the same class `Session.Effects` already assigns to an
unsupported `<send>` type under 6.2.5. Nothing in the invoke corpus asserts
either error, so this is decided on the spec text and on internal consistency,
and it is cheap to reverse if a test ever constrains it.

Either way the invocation is abandoned and no entry is written to the table -
6.4's "terminate the processing of the element without further action", which
ADR-0031 already applies to the argument-evaluation half of the same element.

### Decision 5: the child returns `done.invoke`, and cancellation is what suppresses it

The child session carries `invoked_by: {parent_pid, invoke_id}`, given to it as
a `start_link/2` option by the parent at start. It serves both obligations:

- `deliver(:parent, ...)` resolves to `parent_pid` and casts the event onto the
  parent's inbox, with `invokeid` stamped per 5.10.1 ("If this event is
  generated from an invoked child process, the SCXML Processor MUST set this
  field to the invoke id of the invocation that triggered the child process").
- On `{:halt, :done}` the child places `done.invoke.<invoke_id>` on the
  parent's **external** queue, carrying `done_effect.donedata` as the event
  data. `exitInterpreter`'s own prose puts `returnDoneEvent` in the terminating
  session, and 6.4.3 says "external", which is why this does not go through
  ADR-0039's internal-queue seam - that door is for routing failures only.

Suppression on cancel falls out of the existing halt reasons: a cancelled child
halts `:cancelled`, not `:done`, so the `{:halt, :done}` clause is the only one
that returns the done event, and 6.4.3's "MUST NOT generate the done.invoke.id
event" needs no separate flag. The parent's own discard (Decision 7 below) is
the second line of defence against a done event that raced the cancel.

The parent is deliberately **not** subscribed to the child's effect stream.
Subscribing would flood the parent with every log, trace and send effect the
child produces to read one field off one of them, and the subscriber channel is
an observability seam, not a transport (ADR-0012).

### Decision 6: the queued-event discard keys off the table, not off a cancelled-id set

6.4.3 requires that after cancelling, the parent "MUST ignore any events it
receives from that session. In particular it MUST NOT not insert them into the
external event queue of the invoking session" (the doubled "not" is verbatim in
the REC). ADR-0027 assigns this to the parent's inbox at drain time.

The research flagged that a set of cancelled invokeids has no obvious
retirement point. It does not need one: **the live table is already the
predicate**. At drain, an `{:event, %Event{invokeid: id}}` with a non-`nil`
`id` that is not a key of `Invocations` is discarded and the drain continues to
the next entry. Cancelling removes the key, so every event from that invocation
- queued before the cancel or arriving after it - is dropped, and nothing
accumulates.

The residual case is an author-written `id` on an `<invoke>` in a state that is
exited and re-entered: the second invocation re-adds the same key, so an event
still queued from the first is delivered to the second's finalize. Ids
generated by the core are counter-based and never collide (ADR-0008 as
amended); this is only reachable when an author writes a fixed `id` on an
`<invoke>` in a re-entrant state, and the alternative - a monotonically growing
cancelled-id set that is never retired - trades a rare aliasing case for an
unbounded one. Recorded here rather than left to be discovered.

Replay honours the same rule by re-deriving it. `Statifier.Replay` holds no
invocation state today; Phase 5 adds it. What makes that cheap is the property
`Replay` *does* already have: it re-drives the core, so it sees the same
`{:invoke, _}` and `{:cancel_invoke, _}` effects in the same order the live
session did. Phase 5 has it maintain the same live-invokeid set from them and
apply the identical predicate to recorded events. That keeps ADR-0034
whole - a discarded event is recorded (the tap is on the input side, before
planning) and is skipped identically on replay, rather than the recording and
the live run disagreeing about what the core saw.

### Decision 7: the feature atoms do not flip here

st-cmq.6's plan says "st-cmq.7 flips it, and `mix test.baseline add` runs
there". That was written before st-cmq.5's plan assigned the
`Statifier.Case`-starts-a-Session change to st-cmq.9, and it is wrong now for
the reason st-cmq.6's own plan gave against flipping early: "Flipping the atom
to `:partial` would let 27 files past the feature gate only to fail on their
assertions instead" - a worse signal for the same red.

Flipping here would admit thirty-five files, of which twenty-five cannot
compile at all (Decision 1) and none of which reaches an effect performer,
since the harness drives the pure four-function API. `invoke_elements` and
`finalize_elements` stay `:unsupported`, `test/passing_tests.json` is
untouched, and st-cmq.9 flips them when the harness can actually exercise them.

### Decision 8: `_parent` is accepted alongside `#_parent`

C.1 spells the parent target `#_parent`; 6.4.4's prose spells it `'_parent'`
("it can use `<send>` with the special target '_parent' and type 'scxml'").
This is the same self-contradiction `Target.parse/1` already resolves for
`_internal`/`#_internal` by accepting both spellings, on the recorded ground
that a superset fails no test. The same answer applies here for the same
reason, and the corpus writes the `#_` form either way.

## Phase 1: The invoke type vocabulary and the child-source resolver

### Overview

The pure, process-free groundwork, with an observable behavior change of its
own: an `<invoke>` with an unsupported `type` now raises `error.execution`
instead of being notified as unroutable. Lands ADR-0038, `Effect.Invoke`'s
`invoke_index`, and `Statifier.Invoke.Source`.

### Changes Required:

## Phase 5: Cancel-invoke, and discarding a cancelled invocation's events

### Overview

Exiting the invoking state stops the child and silences it. Lands the

### Changes Required:

#### 1. Planner

#### 2. Performer

**File**: `lib/statifier/session.ex`

every one of them. The child is left to idle `:cancelled` exactly as any
cancelled session does; the parent is no longer monitoring it and no longer
holds its id, so it is silent by construction. A miss is a no-op.

Popping the entry before the cancel is what makes the discard correct: any
event this child already delivered is now un-keyed.

#### 3. The discard

**File**: `lib/statifier/session.ex`
**Changes**: `handle_continue(:drain, state)` gains a clause between the halted

:drain}}`). Comment cites 6.4.3's MUST-NOT-insert sentence and ADR-0027's
"drops, at drain time, every queued entry originating from a cancelled
invokeid", and Decision 6's reason for keying off the live table.

`Session.Inbox` needs **no** new function: the predicate is applied at
`next/1`'s result, not inside the queue. Keeping the discard in the drain loop
rather than in `Inbox` is what keeps `Inbox` ignorant of invocations.

#### 4. Parent termination

**File**: `lib/statifier/session.ex`
**Changes**: `terminate/2` cancels every live child alongside the existing
timer cancellation, so an orderly parent stop leaves no orphans. The child-side
parent monitor from Phase 2 covers the disorderly case.

## Performance Considerations

One new map lookup per drained external event (the discard predicate) and one
per autoforward effect. Both are `Map.has_key?`/`Map.fetch` on a map whose size
is the number of live invocations of one session - single digits in every
document in the corpus.

The parent deliberately does not subscribe to its children (Decision 5), which
is the one place this design could have become O(child effects) in parent
message volume.
