# `<script>` as predicator statement programs - Implementation Plan

## Overview

Implement `<script>` per ADR-0026: a body is a predicator *statement program*,
compiled with `Predicator.compile_program_with_positions/1` and run with
`Predicator.execute/3` against the session datamodel. Errors keep the partial
context and raise `error.execution`; `<script src>` is rejected at load; a
`<script>` child of `<scxml>` runs at document load time; and the corpus
`:needs_script` exclusions are re-decided file by file.

Beads issue: `st-af3.17`. Direction artifact: ADR-0026 (accepted, uncommitted in this
tree along with the ADR-0004 amendment note, the ADR README row, and the
rewritten `docs/datamodel.md` "Statement sequences and `<script>`" section -
all four ride in Phase 1's commit).

## Current State Analysis

Ground truth is `docs/research/260814-st-af3.17-script-statement-bodies.md`.
The load-bearing facts:

- **The element pattern is closed and mechanical.** `<assign>` (st-af3.4) left
  every seam a datamodel-mutating executable-content element needs open for a
  second occupant. Nothing in `Statifier.ExecutableContent`, the block runner
  (`lib/statifier/interpreter/content.ex`), `Machine.content/2`, or the
  interpreter changes for a `<script>` node.
- **The program path is a new sibling of the expression path, not a third arm
  of `Machine.expr()`** (`lib/statifier/machine.ex:90`).
  `Predicator.evaluate/3` never accepts statement nodes; `parse_program/2` /
  `compile_program_with_positions/1` / `execute/3` are a separate API
  (`deps/predicator/lib/predicator.ex:404-415`, `:757-797`, `:865-871`).
- **The parser needs no change.** `Statifier.Parser.Handler` already retains
  character data verbatim and untrimmed
  (`lib/statifier/parser/handler.ex:110-143`); `Statifier.Parser.DOM.text/1`
  (`lib/statifier/parser/dom.ex:44-55`) is the shared body reader three
  builders already use. It is *lowering* that rejects `<script>` today, via a
  `@dispatch` miss (`lib/statifier/lowering.ex:53-75`, `:151-152`).
- **Neither `Document` nor `Machine` has a slot for a top-level `<script>`**
  (`lib/statifier/document.ex:111-123`, `lib/statifier/machine.ex:71-81`).
- **`Evaluator.context/1` runs `undefine_nils/1`**
  (`lib/statifier/evaluator.ex:105-133`), rewriting every `nil` in the
  datamodel to `:undefined`. `Predicator.execute/3` hands back a whole
  context, so a naive write-back would convert every `nil` in the datamodel to
  `:undefined`, permanently, for ids the script never touched. `<assign>`
  sidesteps this by writing through the *raw* datamodel map
  (`lib/statifier/machine/content/assign.ex:175-193`); a program cannot.
- **Two `<assign>` invariants a script cannot inherit.** `check_root/3`
  (`assign.ex:162-173`) refuses to create a new top-level root and
  `check_system_variable/1` (`assign.ex:143-153`) refuses a `_`-prefixed
  write. Predicator's `store` instruction does neither
  (`deps/predicator/lib/predicator/evaluator.ex:1491-1523`).
- **Corpus sources are cloned, not vendored.** `mise run corpus:fetch` has now
  been run in this worktree and the bodies read; the ceiling is measured, not
  guessed (see Corpus/Ratchet Notes).

## Desired End State

A document may use `<script>` anywhere the spec allows it:

- As executable content in `<onentry>`, `<onexit>`, a transition, an `<if>`
  branch, or a `<foreach>` body - compiled at load, executed in document order
  by the existing block runner, mutating the session datamodel.
- As a child of `<scxml>` - compiled at load, executed at load time before the
  initial state is entered, at Appendix D `interpret`'s
  `executeGlobalScriptElement(doc)` position.
- With `src` - rejected at load with a named unsupported error.

A body that fails mid-program retains prior writes and raises
`error.execution`. A body that does not parse defers to runtime and raises
`error.execution` when reached.

Verification: SCION `script/test0`, `script/test1`, `script/test2` and W3C
`test302`, `test303`, `test304` are generated, pass, and are in
`test/passing_tests.json`; the `:needs_script` reason string exists nowhere in
`tools/corpus/`; full `mix quality` is green with no shrinkage of the ratchet.

### Key Discoveries

- `Predicator.execute/3` returns `{:error, error, %Context{}}` for a **parse**
  failure as well as an execution failure
  (`deps/predicator/lib/predicator.ex:530-539`), so deferring a compile
  failure to runtime costs no extra error-shape handling.
- The returned context is `%{input_context | data: final.context}`
  (`deps/predicator/lib/predicator.ex:554-564`), so the `In/1` host function
  `Evaluator.context/1` installs survives a program run.
- `Statifier.ExecutableContent`'s three-element error arm
  (`lib/statifier/executable_content.ex:73-76`) already means "keep
  `new_context`" in `run_nodes/2`
  (`lib/statifier/interpreter/content.ex:172-193`) - exactly ADR-0026
  decision 1, with no protocol change.
- Predicator's `if`/`while` are fully implemented statements, not merely
  reserved words (`deps/predicator/lib/predicator/parser.ex:16-22`,
  `:565-575`). The sharp constraint on ECMAScript bodies is that `;` is the
  mandatory separator and that `var`, compound assignment (`*=`), object
  literals, `typeof`, and function definitions do not parse.
- `raise_platform/4` (`lib/statifier/machine_state.ex:398-413`) is available
  at `initialize/2`'s script position and stamps the current
  macrostep/microstep, and `main_event_loop/1`
  (`lib/statifier/interpreter.ex:207`) dequeues it in the initialization
  macrostep - so a load-time `error.execution` needs no new machinery.
- `validate_features/1` (`test/support/feature_detector.ex:121-136`) treats
  `:partial` identically to `:supported`, and `Statifier.Case.test_scxml/4`
  **flunks** rather than skips - so the detector flip and the exclusion
  re-recording must land in one commit.
- Constraints: ADR-0026 (governing), ADR-0004 (amended in part), ADR-0024
  (`<data src>`; deliberately *not* the shape used here), ADR-0014
  (compile/evaluate split, spans not positions), ADR-0012 (context never
  cached on `MachineState`), ADR-0003 (pure core; the runner owns the sole
  `error.execution` conversion), ADR-0002 (Appendix D fidelity), ADR-0011
  (gate-guard ledger for any ratchet shrinkage).

## What We're NOT Doing

- **No external fetch.** `<script src>` is rejected, never downloaded
  (ADR-0026 decision 2). st-322 owns the external-fetch question.
- **No ECMAScript.** Bodies that need `var`, `*=`, object literals, `typeof`,
  or function definitions stay out of the corpus, re-recorded under ADR-0004's
  ECMAScript-dependence reason.
- **No document rejection for a failing top-level script.** ADR-0026's own
  open question stays open; a load-time inline-body failure queues
  `error.execution`. Escalating that is an ADR amendment, not a plan edit.
- **No change to `validate_features/1`.** `:partial` keeps its existing
  "allowed to run" meaning; this bead is its first user, not its redefinition.
- **No `mix.exs` / predicator pin change.** st-5ma already moved it to
  `~> 7.0`.
- **No rollback semantics** and no flag for them (ADR-0026 decision 1).
- **No new trace event for a datamodel write.** `docs/observability.md`'s
  vocabulary is closed and `Trace.ContentExecuted` already covers any content
  node by `c_index`; the load-time script is outside that vocabulary by
  construction and emits nothing, matching `Datamodel.initialize/1`.
- **`conf:incrementArray`, `conf:scriptGoodSrc`, `conf:scriptBadSrc` stay
  stubbed.** No `.txml` in the IRP suite references any of them; only their
  stale ADR-0004 reason comments are corrected. Building an unused template
  would be untestable by construction.

## Implementation Approach

Four phases, split along this project's module boundaries (evaluator/compiler,
parser+lowering+machine, interpreter, corpus tooling). Each ends with a working
engine and a green full gate.

The eleven open questions the research recorded are decided here. Each decision
is stated once, in the phase that owns it, and is repeated in the module or
moduledoc comment the phase writes so it survives outside this document.

Two gate facts every phase inherits: `.doctor.exs` holds 100% thresholds on
every axis, so each new module needs a `@moduledoc` and each new public
function a `@doc` and a `@spec` (a `defimpl` block takes `@moduledoc false`,
as `assign.ex:60` does); and coverage is measured only by a bare `mix quality`,
never by `--profile loop`.

### Decision 1 (research OQ 1): an unparseable body defers to runtime

Compilation happens at load (`compile_program/3`, Phase 1). On failure the
node stores `{:invalid, Compiler.Error.t()}` - the exact deferral shape
`<assign expr>` (`lib/statifier/compiler.ex:860-876`) and `<data expr>`
(`:1199`) already use - and `execute/2` short-circuits it into
`{:error, error}` (the two-element arm: nothing ran, so there is no partial
context to keep), which the runner converts to `error.execution`.

Why deferral rather than load rejection: `docs/datamodel.md` records that if
the split is ever unified it unifies *toward* deferral; load rejection would
make every ECMAScript-bodied `<script>` document unloadable, which turns the
detector flip into a wall of red for documents whose other features are fully
supported; and `execute/3` returns the same error shape for a parse failure
anyway, so deferral costs nothing in handling.

### Decision 2 (research OQ 2): a `<script>` may create a new top-level root

`<assign>`'s `check_root/3` stands unchanged, and `<script>` deliberately does
not get an equivalent. The asymmetry has a stated reason: `<assign>`'s
`location` attribute is a *reference* to a location the document must already
have (spec 5.9.2's "cannot be evaluated to yield a valid location"), while a
predicator assignment *statement* is a declaration and a write in one - which
is what W3C test302 and test304 assert, since `Var1` appears in no
`<datamodel>` in either. This must be written into
`Statifier.Machine.Content.Script`'s moduledoc, next to a pointer at
`assign.ex:162-173`, so the next reader does not read it as an oversight.

### Decision 3 (research OQ 7, the blocking one): write back only changed roots

`Evaluator.execute/2` never writes `context.data` into
`machine_state.datamodel` wholesale. It diffs the post-run `context.data`
against the pre-run `context.data` at the **top level only**, and merges just
the changed and newly-added roots into the *raw* datamodel map:

```elixir
changed =
  for {key, value} <- after_data,
      Map.get(before_data, key, :__absent__) !== value,
      into: %{},
      do: {key, value}

Map.merge(raw_datamodel, changed)
```

Every root the program did not touch keeps its raw value, so a seeded-but-
unbound `<data>` still reads `nil` and not `:undefined`. This is the same
property `<assign>`'s "write through the raw map" comment
(`assign.ex:175-193`) protects, reached differently because a program returns
a whole context rather than one path.

Top-level granularity is deliberate: predicator's `store` writes through
`ContextLocation.put/3` from a root segment, so any nested write changes its
root's value and is caught. A root the program assigns a value equal to its
pre-run *normalized* form (`x = undefined` over a `nil`-valued `x`) is not
merged, which is correct - the two spell the same thing.

`store` never deletes, so there is no removal case to handle. State that in the
function comment rather than writing dead code for it.

### Decision 4 (research OQ 3): system variables are enforced by the same diff

The changed-root set from Decision 3 is the hook spec 5.10 needs. Roots
beginning with `_` are partitioned out: they are **not** merged, and their
presence makes the call return an error whose reason is
`{:system_variable, root}` - the same reason tuple `<assign>` produces
(`assign.ex:143-153`), so `error.execution`'s `data:` reads identically
whichever element attempted the write. Non-system changed roots still merge:
that is 4.9's stop-and-keep model, applied to the one statement that failed the
check.

Known and accepted gap, to be written into the function comment: a program that
writes a system variable and then writes it back to its original value is
unobservable to a diff, and therefore not caught. A pre-execution scan of
assignment targets was rejected because it cannot see a computed bracket key,
which would make the protection *look* complete while being bypassable; the
diff is bypassable only by a write with no effect. This closes st-af3.4's open
question 5 for both claimants.

### Decision 5 (research OQ 4): lowering rejects `<script src>`

Lowering owns it, because ADR-0026 says "rejected at load" and lowering is
where this engine already refuses to build an unloadable document; the
validator has no notion of a valid-but-unsupported construct and no warning
concept (`lib/statifier/validator/error.ex:68-75`).

`Statifier.Lowering.Error`'s closed `reason` union
(`lib/statifier/lowering/error.ex:21-28`) gains one member,
`{:unsupported_attribute, element_name, attribute_name}`, with a constructor
`unsupported_attribute/3`. It is deliberately distinct from
`unexpected_attribute/3`, whose message ("takes no such attribute") would be
false of `<script src>` in the spec: this one means "the spec defines it; this
engine does not implement it", and its message cites ADR-0026.

`<script src>` plus child text is **not** a second error. Spec 5.8.2 forbids
the pair, but the document is already rejected on `src` alone, so a second
error would add noise without adding information. Report one error and build no
struct.

### Decision 6 (research OQ 6): the error is wrapped as `Evaluator.Error`

`Predicator.execute/3` returns a bare `%EvaluationError{}` /
`%TypeMismatchError{}` / `%UndefinedVariableError{}` / `%ParseError{}`.
`Evaluator.execute/2` wraps it with `Statifier.Evaluator.Error.new(source,
error)`, `source` being the script body text - so `error.execution`'s `data:`
carries the same `{source, error, span}` shape the expression path already
produces, and a consumer never has to branch on which path failed. This closes
st-af3.4's open question 7.

### Decision 7 (research OQ 5): a new field on `Document` and on `Machine`

`Document` gains `scripts: [Document.Script.t()]` and `Machine` gains
`global_scripts: [Machine.program()]`, both in document order, both defaulting
to `[]`. `datamodel_element` is the exact precedent: a document-level,
non-block slot for a load-time construct.

The alternative - routing the top-level script through the `c_index`-addressed
`contents` tuple - is rejected: `contents` is the block runner's address space,
and a node that no block ever runs does not belong in it. `Machine`'s moduledoc
reluctance to add fields is about fields *derivable from elsewhere*; this one is
not derivable from anything.

A list rather than a single slot, because spec 5.8 says "any `<script>` element
that is a child of `<scxml>`" without limiting the count.

### Decision 8 (research OQ 8): the detector flip and the exclusions are one commit

`script_elements` moves `:unsupported -> :partial` in Phase 4, in the same
commit that resolves every `:needs_script` exclusion. Because
`validate_features/1` admits `:partial` and `Statifier.Case` flunks rather than
skips, any other ordering is a red suite. The registry comment states what
`:partial` means for this entry: the element is implemented, and bodies outside
predicator's statement grammar are kept out at corpus-generation time rather
than at detection time.

### Decision 9 (research OQ 9): the fetch is a phase step, already performed

`mise run corpus:fetch` has been run in this worktree during planning and the
bodies are read (see Corpus/Ratchet Notes). Phase 4 re-runs the full
`mise run corpus` pipeline; the fetch is named as its first step because a
fresh clone starts with an empty `tools/corpus/scratch/`.

### Decision 10 (research OQ 10): the W3C half is in scope

`conf:script` emits `<script>Var1 = 1</script>` - verified to compile. The
three W3C exclusions are removed. The three other stubbed templates stay
stubbed (see "What We're NOT Doing").

### Decision 11 (research OQ 11): ADR-0026's open question stays open

A top-level script's evaluation error queues `error.execution`; it never
rejects the document. No corpus file observes otherwise, and test302 would
observe only the queued form. Recorded, unchanged, as an open question below.

## Phase 1: The program compile/execute seam

### Overview

Add the program half of the compile/evaluate split (ADR-0014) with no consumer
yet: `Statifier.Compiler.Expressions.compile_program/3` and
`Statifier.Evaluator.execute/2`, the latter carrying Decisions 3, 4 and 6. This
phase also carries the direction artifacts already sitting uncommitted in the
tree.

Independently committable: two new public functions with full unit coverage and
no caller. Independently gate-verifiable: `mix quality` exercises them through
their own tests, and Doctor's 100% thresholds are met by their `@doc`/`@spec`.

### Changes Required

#### 1. The uncommitted direction artifacts

**Files**: `docs/adr/0026-script-as-predicator-statement-programs.md` (new),
`docs/adr/0004-predicator-as-the-datamodel.md`, `docs/adr/README.md`,
`docs/datamodel.md`
**Changes**: none - they are already written and correct. They ride in this
phase's commit because ADR-0026 is the record the code cites and must not land
after it.

#### 2. Program compilation

**File**: `lib/statifier/compiler/expressions.ex`
**Changes**: add `compile_program/3`, mirroring `compile/3`'s shape and error
recovery.

```elixir
@spec compile_program(source :: String.t(), owner :: owner_ref(), location :: Location.t()) ::
        {:ok, Machine.program()} | {:error, Error.t()}
def compile_program(source, owner, %Location{} = location)
    when is_binary(source) and is_tuple(owner) do
  case Predicator.compile_program_with_positions(source) do
    {:ok, %Predicator.Compiled{} = compiled} -> {:ok, {:program, compiled, source}}
    {:error, _formatted_message} -> {:error, program_parse_error(source, owner, location)}
  end
end
```

The failure path recovers `{line, column}` with a second call to
`Predicator.parse_program/2`, which returns the structured 4-tuple
`{:error, message, line, column}` directly
(`deps/predicator/lib/predicator.ex:865-871`) - simpler than `compile/3`'s
`Predicator.parse/2` detour, and the moduledoc must say so rather than leaving
the asymmetry to be read as an accident.

#### 3. The program type

**File**: `lib/statifier/machine.ex`
**Changes**: add `@type program :: {:program, Predicator.Compiled.t(), source :: String.t()}`
beside `expr()`, with a typedoc stating that it is a *sibling* of `expr()` and
never an arm of it, because `Predicator.evaluate/3` rejects statement programs
outright (`deps/predicator/lib/predicator.ex:213-217`).

#### 4. Program execution

**File**: `lib/statifier/evaluator.ex`
**Changes**: add `execute/2`, taking a `MachineState` (per the project's
state-first argument convention) and a `Machine.program()`, and returning
`{:ok, MachineState.t()} | {:error, MachineState.t(), Error.t()}` - the
three-element error arm carrying the machine state with the partial writes
already merged.

Steps: build the context via `context/1`; keep `before_data`; call
`Predicator.execute(compiled, context)`; on either outcome, partition the
changed roots into system and non-system per Decisions 3 and 4; merge the
non-system roots into `machine_state.datamodel`; return `{:ok, machine_state}`
when the program succeeded and no system root was attempted, otherwise
`{:error, machine_state, Error.new(source, error)}` with the merge already
applied.

Add the moduledoc section this module's "three `Context`s" prose implies:
`evaluate/2` reads, `execute/2` writes, and both build the same context.

## Phase 2: `<script>` as executable content

### Overview

Wire `<script>` end to end through lowering, validation, compilation, and the
executable-content protocol, and reject `<script src>` at load. After this
phase a document with `<onentry><script>x = 1</script></onentry>` runs.

Independently committable and gate-verifiable: the feature is complete and
observable from `Statifier.compile/1` plus `Statifier.Interpreter.initialize/2`
in an internal test.

### Changes Required

#### 1. The document node

**File**: `lib/statifier/document/script.ex` (new)
**Changes**: `%Statifier.Document.Script{}` with `text` (verbatim body from
`DOM.text/1`), `node_location` (named as on `Document.Assign`, for the same
reason), `src`, and `attribute_locations`. Moduledoc cites spec 5.8 and
ADR-0026.

#### 2. The lowering builder and dispatch

**Files**: `lib/statifier/lowering/builders.ex`, `lib/statifier/lowering.ex`,
`lib/statifier/lowering/error.ex`
**Changes**:
- `build_script/2`, modelled on `build_assign/2`
  (`builders.ex:472-501`): reads `DOM.text/1`, reports any element child as
  `misplaced_element`, and on a written `src` reports
  `Error.unsupported_attribute("script", "src", location)` and builds nothing
  (Decision 5).
- `@dispatch` gains `"script" => &Builders.build_script/2`.
- `place/3` gains a `%Script{}` clause **before** the generic `:content_node`
  catch-all, for the same `node_location`-vs-`location` reason the `%Assign{}`
  clause has (`builders.ex:883-885`), plus a clause placing a `%Script{}` into
  `Document.scripts` when the parent is `scxml` (Phase 3 consumes that slot;
  the field is added here so placement has somewhere to put it and a top-level
  `<script>` is not a `misplaced_element` in the interim).
- `content_node_name/1` gains `defp content_node_name(%Script{}), do: "script"`
  **and** its own `@spec`'s five-member union (`builders.ex:899`) gains
  `| Script.t()`.
- `Lowering.Error` gains the `{:unsupported_attribute, element, attribute}`
  reason and its constructor.

**The two closed unions a new content node must join.** Both are hard-coded
five-member lists today and dialyzer will flag a `%Script{}` flowing through
either:
- `Statifier.Document.content_node` (`lib/statifier/document.ex:100`) - what
  `Document.Block.content`, `Document.Transition.content`,
  `Document.If.Branch.content`, and `Document.Foreach.content` are all typed
  as.
- `Statifier.Machine.Content.t` (`lib/statifier/machine/content.ex:57`) - the
  compiled counterpart.

Both gain `| Script.t()` in this phase, alongside the `content_node_name/1`
`@spec` above.

#### 3. The document struct

**File**: `lib/statifier/document.ex`
**Changes**: add `scripts: []` (Decision 7), with the field comment naming
`datamodel_element` as the precedent for a document-level, non-block slot.

#### 4. The validator check

**File**: `lib/statifier/validator/checks/script.ex` (new), registered in
`lib/statifier/validator.ex`'s `@checks`
**Changes**: spec 5.8.2's mutual exclusion is unreachable through lowering
(`src` already rejects), so this check has exactly one job: a `<script>` with
neither `src` nor non-blank text is an empty script. Per 5.8.2 a conformant
document MUST specify one or the other, so report it.

`Statifier.Validator.Error`'s `reason` union
(`lib/statifier/validator/error.ex:33-67`) is closed and its moduledoc requires
"a constructor per reason rather than reopening the type", so this addition is
explicit, at the same level of detail Decision 5 gives the lowering error: the
reason is `{:script_no_src_or_text}` (nullary, matching `{:empty_id}` and
`{:if_duplicate_else}` - a `<script>` has no id and no attribute value to name
it by) with a constructor `script_no_src_or_text/1` taking the node's own span,
and a message citing spec 5.8.2. Reuse the `blank?/1`
convention (`checks/assign.ex:118-119`) - whitespace-only text is not text -
and the `descend/1` recursion through `%DIf{}` branches and `%DForeach{}`
bodies (`checks/assign.ex:97-103`), plus `document.scripts` for the top-level
occurrences the state walk cannot reach.

#### 5. Compilation to a machine node

**File**: `lib/statifier/compiler.ex`
**Changes**: a `build_content_node/2` clause for `%Document.Script{}`,
compiling the body with `Expressions.compile_program/3` and storing
`{:invalid, error}` on failure (Decision 1). The `assign_content_node/2`
numbering pass is already generic and needs no change.

#### 6. The machine node and its protocol implementation

**File**: `lib/statifier/machine/content/script.ex` (new)
**Changes**: `%Statifier.Machine.Content.Script{}` (`c_index`, `program`,
`node_location`) plus `defimpl Statifier.ExecutableContent` in the same file.
`execute/2`:

```elixir
def execute(%Script{program: {:invalid, error}}, %Context{}), do: {:error, error}

def execute(%Script{program: program}, %Context{} = context) do
  case Evaluator.execute(context.machine_state, program) do
    {:ok, machine_state} ->
      {:ok, rebind(context, machine_state), []}

    {:error, machine_state, error} ->
      {:error, rebind(context, machine_state), error}
  end
end
```

where `rebind/2` sets both `machine_state` and

the node's own responsibility, never the runner's
(`lib/statifier/executable_content/context.ex:16-31`). The three-element error
arm is ADR-0026 decision 1: `run_nodes/2` keeps the returned context and the
runner raises `error.execution`. The moduledoc carries Decision 2's stated
reason for the root-creation asymmetry with `<assign>`.

`lib/statifier/machine/content.ex`'s moduledoc line naming `<script>` as a
future member is updated to name it as a present one.

## Phase 3: The top-level `<script>` load-time path

### Overview

Execute a `<script>` child of `<scxml>` at document load time, at Appendix D
`interpret`'s `executeGlobalScriptElement(doc)` position. Phase 2 already
lowers and places it; this phase compiles it onto `Machine` and runs it.

Independently committable and gate-verifiable: observable through
`Statifier.Interpreter.initialize/2` in an internal test.

### Changes Required

#### 1. The machine slot

**File**: `lib/statifier/machine.ex`
**Changes**: add `global_scripts: []` holding
`[Machine.program() | {:invalid, Compiler.Error.t()}]` in document order
(Decision 7). The moduledoc's "No top-level `initial`" section
(`lib/statifier/machine.ex:55-62`) is the place that argues against adding a
field derivable from elsewhere; a short sibling paragraph beside it says why
this field is not derivable from `contents`.

#### 2. Compilation

**File**: `lib/statifier/compiler.ex`
**Changes**: compile `document.scripts` with `Expressions.compile_program/3`
into `machine.global_scripts`, using a new `owner_ref` arm
`{:global_script, non_neg_integer()}` (position in document order) added to
`Statifier.Compiler.Expressions.owner_ref` - a top-level script has no
`c_index`, `t_index`, or state index to name it by, and reusing one would put a
false index into the ADR-0012 index space.

#### 3. The interpreter call site

**File**: `lib/statifier/interpreter.ex`
**Changes**: in `initialize/2`, between `Datamodel.initialize(machine_state)`
and `ExitEntry.enter_states/2`, fold `machine.global_scripts` in document
order. Appendix D's `interpret` prose is explicit about the position:

> Initialize the global data structures, including the data model. If binding
> is set to 'early', initialize the data model. Then execute the global
> `<script>` element, if any. Finally call enterStates on the initial
> configuration...

**No ADR-0002 deviation is required or taken**: this lands exactly where the
pseudocode puts it. The only note the comment must carry is that Appendix D
says "element" singular while spec 5.8 says "any `<script>` element that is a
child of `<scxml>`", so the fold is over a list - a plural where the pseudocode
is singular, not a reordering.

Each script runs through `Evaluator.execute/2` directly - no block runner, no
`ExecutableContent.Context` (ADR-0026 decision 3). On `{:error, machine_state,
error}` the partial writes stand and the interpreter calls
`MachineState.raise_platform(machine_state, "error.execution", {:global_script,
n}, data: error)`. This is the one place outside
`Statifier.Interpreter.Content` that converts an evaluation error into
`error.execution`; the comment must say why - there is no block runner on this
path to own it, and `Statifier.Interpreter.Datamodel.bind_value/4` is the
existing precedent for a load-time raise outside the runner.

The `executeGlobalScriptElement(doc)` seam comment
(`lib/statifier/interpreter.ex:200-201`) is replaced by the implementation.

## Open Questions

These are recorded rather than resolved. No human was available during
planning; each is a decision this plan deliberately does not make, with the
owner named.

1. **Should a top-level `<script>` evaluation error ever escalate to document
   rejection?** ADR-0026's own open question, unchanged. This plan queues
   `error.execution` (Decision 11). No corpus file observes otherwise. Owner:
   a future ADR amendment, triggered by a mandatory test that observes
   rejection - not any phase here.
2. **Does the system-variable diff want closing for the write-then-restore
   case?** Decision 4 accepts the gap knowingly (a write with no observable
   effect). Owner: st-af3.4's open question 5 lineage; if a corpus file ever
   observes it, the fix is a pre-execution scan *added to* the diff, not
   replacing it.
3. **Should `Machine.expr()` and `Machine.program()` ever unify?** They cannot
   today - `Predicator.evaluate/3` rejects statement programs. If predicator
   ever unifies them upstream, this plan's sibling-type choice is the thing to
   revisit. Owner: a future predicator bump bead, not this one.
