# Branch Naming Decision Implementation Plan

## Overview

Decide, and record, whether worktree branches keep their `<bead-id>-<slug>` names
now that a branch may carry several beads. The decision is **keep the prefix**,
with the name reclassified as a creation-time label rather than a source of
truth, and with `/commit`'s bead detection re-ranked so an explicitly known bead
beats the branch name. Beads issue: st2-qww.7.

## Current State Analysis

### Where the branch name is actually load-bearing

Only two places derive a bead from it:

- `.claude/skills/commit/SKILL.md:142-147` - Step 1.5 strategy 1 reads
  `git branch --show-current` and takes the prefix as the issue ID. That ID
  becomes the `Refs:` trailer (Step 2, `SKILL.md:238-242`).
- `.claude/skills/merge-request/SKILL.md:45-51` - step 2 resolves one bead from
  the branch prefix, for validation and for the `bd note` in step 7.

`/new-worktree` and `/next-issue`/`/next-issues` *construct* the name
(`new-worktree/SKILL.md:25-30`, `next-issue/SKILL.md:89-92`,
`next-issues/SKILL.md:107`) but derive nothing from it afterwards.
`/cleanup-worktrees` matches its tmux window on the worktree **directory name
plus path** (`cleanup-worktrees/SKILL.md:117-124`), which is a string identity
check, not a bead lookup.

### The close-on-merge path is already name-independent

`/cleanup-worktrees` step 4.5 (`SKILL.md:250-289`) closes beads from the
`^Refs:` trailers in the merged PR's commits, explicitly *because* "the branch
name carries only one ID, so keying on it silently drops every other bead a
multi-commit branch closed". The acceptance criterion "whichever lands,
`/cleanup-worktrees` still closes every bead a branch carries" is therefore
already satisfied and is not at risk from any option considered here.

### What actually went wrong on PR #10

The bead's description reports the worktree created as
`st2-qww.6-upstream-check-fix` with the branch renamed to
`st2-qww.4-close-on-merge` mid-work. `/commit` reads
`git branch --show-current`, so it saw the *renamed* branch and got the right
bead. What went stale was the **directory** name, which nothing derives a bead
from. The incident is a readability problem, not a correctness one.

### The correctness hole that does exist

A branch may deliberately carry several beads as separate commits, one bead per
commit (`docs/workflow.md:65-75`, `merge-request/SKILL.md:176-180`). The branch
prefix names the branch, not the commit, so on such a branch's second commit the
prefix supplies the *wrong* `Refs:` trailer - and Step 1.5 ranks it first, above
the bead the session was actually seeded with.

`/new-worktree` step 5 (`SKILL.md:133-155`) puts the bead ID in the seeded
prompt twice: once in the seed command (`/create-plan st2-00p.3`) and once in
the fixed finishing clause ("refuses if the tree carries changes unrelated to
`<id>`"). The session already knows its bead explicitly; Step 1.5 just prefers a
weaker signal.

### Constraints

- ADR-0010 fixes the name as `<beads-id>-<slug>`
  (`docs/adr/0010-worktree-parallel-development.md:19-20`), so any change here
  amends it. Per `docs/workflow.md:11-13`, ADR changes are direction-level
  (Fable) review.
- `mix adr.check` (`lib/mix/tasks/adr.check.ex`) guards ADR-0002/0003/0004 code
  patterns only; a docs-and-skills branch does not interact with it.
- No mechanical check can distinguish "commit 2 of a grouped branch" from
  "commit 2 of a single-bead branch" using the branch alone - in both cases the
  existing trailers equal the prefix. This is why the fix is a re-ranking, not a
  new detector.

## Desired End State

1. ADR-0010 records that bead-prefixed names are kept, that the name is a
   creation-time label naming the primary bead at cut time, and that it is never
   renamed when the grouping shifts.
2. `docs/workflow.md` states the same rule where the naming convention already
   lives, and says explicitly that a stale name is expected and harmless because
   `Refs:` trailers are what close beads.
3. `/commit` Step 1.5 ranks an explicitly known bead above the branch prefix,
   and refuses in auto mode when the only signal is a branch prefix naming an
   already-closed bead.
4. `/merge-request` resolves the beads a branch carries from its commits'
   `Refs:` trailers, with the branch prefix as a fallback, and names all of them
   in the PR body.

Verification: `grep -rn` over `.claude/skills/` and `docs/` finds no remaining
claim that the branch name is the authoritative bead source; the branch's own
diff review passes (`/commit` Step 0 carve-out - no Elixir touched).

### Key Discoveries

- `/cleanup-worktrees` already uses `Refs:` trailers, anchored on `^Refs:`
  (`cleanup-worktrees/SKILL.md:262-276`) - the acceptance criterion is met
  before this plan starts.
- The seeded prompt is a stronger bead signal than the branch name and is
  already present in every `/new-worktree`-created session
  (`new-worktree/SKILL.md:133-155`).
- The bead's own DESIGN note rejects "infer from claimed `in_progress` beads" as
  ambiguous across parallel worktrees. That rejection stands; the seeded prompt
  is not that inference - it names one bead, in this session, unambiguously.

## What We're NOT Doing

- **Not adopting topical names** (e.g. `merge-automation`) for grouped branches.
  They remove the signal `/commit --auto` falls back on without fixing the
  staleness that motivated them, and they add a naming judgment call at cut time.
- **Not adding a worktree-local bead pointer file** (gitdir file, tracked file,
  or `git config --worktree`). It is new state restating what the seeded prompt
  already carries, and an unmaintained pointer is stale *invisibly*, which is
  worse than a stale directory name you trip over in `ls`.
- **Not renaming any existing branch, worktree, or directory.** The rule being
  written down is precisely that these are not renamed.
- **Not changing `/cleanup-worktrees`.** Its detection is already correct.
- **Not touching `mix gate.check` / `mix adr.check` or any Elixir.**

## Implementation Approach

Two phases, both docs-and-skills only, each independently committable and
reviewable on its diff:

1. Record the decision where the convention is defined (ADR-0010,
   `docs/workflow.md`). This stands alone as a coherent change - it is the half
   of the acceptance criteria that reads "a decision to keep bead-prefixed
   names, recorded with its reasoning".
2. Make the skills match the recorded decision - `/commit`'s detection order and
   auto-mode refusal, `/merge-request`'s trailer-first resolution, and the
   one-line label note in the three name-constructing skills.

Phase 1 before Phase 2 so the skill edits can cite the amended ADR rather than
asserting the rule on their own authority.

## Phase 1: Record the decision

### Overview

Amend ADR-0010 and `docs/workflow.md` so the naming rule, its reasoning, and the
never-rename consequence are on the record.

### Changes Required:

#### 1. ADR-0010 amendment

**File**: `docs/adr/0010-worktree-parallel-development.md`
**Changes**: Extend the Decision section's naming sentence and add the
consequence. Keep the existing three-section format and the file's hyphen
punctuation.

Decision section, after the existing `named <beads-id>-<slug>` clause, add:

```markdown
The branch and worktree name is a **label fixed at creation**: it names the bead
the worktree was cut for, and it is not re-derived afterwards. A branch that
grows to carry several beads keeps its original name, and neither the branch nor
the worktree directory is renamed when the grouping shifts. Nothing downstream
reads the name as an authority: `/cleanup-worktrees` closes beads from the
`Refs:` trailers in the merged PR's commits, and `/commit` prefers the bead its
session was seeded with over the branch prefix.
```

Consequences section, add:

```markdown
- A name that no longer matches the beads on the branch is expected, not a
  defect to repair. Renaming would break the worktree-directory match
  `/cleanup-worktrees` uses to find the tmux window, and would fix nothing:
  the trailers, not the name, are what close beads.
```

#### 2. Workflow doc

**File**: `docs/workflow.md`
**Changes**: In "Worktrees and parallel agents", extend the "One worktree, one
branch - usually one issue" bullet (currently `docs/workflow.md:65-75`) with the
label rule, replacing the trailing sentence "When one does, its name reflects
the primary issue."

```markdown
  The name is a label fixed at creation - it names the bead the worktree was
  cut for. When a branch grows to carry several beads, it keeps that name;
  neither the branch nor the worktree directory is renamed. A stale-looking
  name is the expected outcome, because the `Refs:` trailers are what close
  beads (ADR-0010).
```

## Phase 2: Make the skills match the decision

### Overview

Re-rank `/commit`'s bead detection, add the one auto-mode refusal that is
mechanically checkable, switch `/merge-request` to trailer-first resolution, and
note the label rule in the three skills that construct names.

### Changes Required:

#### 1. `/commit` bead detection

**File**: `.claude/skills/commit/SKILL.md`
**Changes**: Rewrite Step 1.5's strategy list (currently lines 136-171) so the
branch prefix is the last mechanical signal rather than the first, and add the
stale-name refusal.

New strategy order:

```markdown
1. **An explicit ID** - `$ARGUMENTS`, if one was given. Validate with `bd show`
   and use it; the other strategies do not run.

2. **The bead this session was seeded with.** `/new-worktree` names the bead
   twice in every seeded prompt - in the seed command (`/create-plan st2-abc`)
   and in the fixed finishing clause ("unrelated to st2-abc"). That is one bead,
   in this session, stated by whoever started it. It is a stronger signal than
   anything derived from the branch, and on a branch carrying several beads it
   is the only signal that names the bead *this commit* is for.

   This is not the same as inferring from claimed `in_progress` beads, which is
   ambiguous across parallel worktrees (st2-qww.7) and is not a strategy here.

3. **A plan document in the diff.**
   ```bash
   git diff main...HEAD --name-only | grep 'docs/plans/'
   ```
   Plan filenames carry the issue ID: `YYMMDD-<issue-id>-*.md`. Commit-specific,
   so it outranks the branch name.

4. **The branch prefix** - last, and a hint rather than an authority.
   ```bash
   git branch --show-current
   ```
   Worktree branches are named `<beads-id>-<slug>`, but ADR-0010 fixes that name
   at creation: it names the bead the worktree was cut for, not necessarily the
   bead this commit is for. On a branch carrying several beads the prefix names
   the first one and is wrong for every later commit.

   **Validate the status, not just the existence.** `bd show <id>` on a prefix-
   derived ID that comes back `closed` means the name outlived its bead - the
   stale-name case ADR-0010 says to expect. Interactive mode asks which bead
   this commit is for; **auto mode refuses and reports**, naming the branch and
   the closed bead. Writing a `Refs:` line pointing at a closed bead would have
   `/cleanup-worktrees` close nothing and leave the real bead open.

5. **Fallback to user prompt** - unchanged, and auto mode still stops rather
   than committing without a `Refs:` line.
```

Also add to the Step 4 report (`SKILL.md:331-338`) the strategy that supplied
the bead, so a prefix-derived ID is visible as such:

```
Issue: st2-xxx (from seeded prompt; left in_progress - it closes on merge)
```

And add to the auto-mode refusal list at the top (`SKILL.md:27-40`):

```markdown
- the only bead signal was the branch prefix and `bd show` says that bead is
  already closed - the name outlived its bead (ADR-0010), and auto mode has
  nobody to ask which bead this commit is for
```

#### 2. `/merge-request` bead resolution

**File**: `.claude/skills/merge-request/SKILL.md`
**Changes**: Replace step 2 (lines 45-51) so it resolves the beads the branch
actually carries, matching how `/cleanup-worktrees` will close them.

```markdown
2. **Resolve the beads.** From `$ARGUMENTS` if given. Otherwise read the
   trailers the branch's own commits carry - the same anchored match
   `/cleanup-worktrees` closes on, so the PR body and the eventual closes agree:
   ```bash
   git log origin/main..HEAD --pretty=%B \
     | grep -E '^Refs:' \
     | grep -oE 'st2-[a-z0-9]+(\.[0-9]+)?' | sort -u
   ```
   Fall back to the branch prefix only when that finds nothing (a branch whose
   commits predate the `Refs:` convention). The prefix is a creation-time label
   and names at most one bead (ADR-0010), so a branch carrying several would
   otherwise reach the PR body naming only the first.

   Validate each with `bd show <id>`. STOP if none resolves.
```

Then step 6's PR body (lines 126-131) names every resolved bead:

```markdown
   - The bead references: `Closes st2-xxx` for **every** bead the branch's
     trailers name, one per line (and the epic, if they share one)
```

And step 7's `bd note` runs once per resolved bead.

#### 3. Label note in the name-constructing skills

**Files**: `.claude/skills/new-worktree/SKILL.md`,
`.claude/skills/next-issue/SKILL.md`, `.claude/skills/next-issues/SKILL.md`
**Changes**: One line each, at the point where the name is computed, so the
convention is not silently re-derived later:

```markdown
The name is fixed at creation and never renamed afterwards, even if the branch
grows to carry more beads (ADR-0010).
```
