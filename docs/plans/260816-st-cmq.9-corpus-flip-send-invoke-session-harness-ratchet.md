# Corpus: flip the send/invoke atoms, drive them through a Session, ratchet

## Overview

The Phase 4 corpus closer, the same shape as Phase 3's st-af3.8. Three
harness-and-data changes, in order: flip the ten send/invoke feature atoms to
`:supported` and move every mirror that asserts the supported set; teach
`Statifier.Case` to drive a document through `Statifier.Session` when it needs
real delivery, timers, or child sessions; then run both conformance suites in
full and ratchet every newly passing file into `test/passing_tests.json`.

Bead: st-cmq.9

Everything under `lib/` that this bead depends on has already landed. The only
`lib/` edits here are moduledoc prose: a sentence in
`lib/statifier/supervisor.ex` that this plan's own test-helper change makes
false, and a paragraph in `lib/statifier/session.ex` that st-xcgr made false
and that this bead ratchets the disproof of. `docs/architecture.md` carries
that same stale paragraph and is fixed alongside it. No behavior in `lib/`
changes.

**The corpus asserts configurations that only a running session reaches.**
`test/scxml_tests/mandatory/cancel/test208_test.exs` passes **no events at

`delayexpr="'1.5s'"` send fires. `test/scion_tests/delayed_send/send1_test.exs`

delayed send lands - and `["d"]` after `t2`, which requires that same send to
have landed first. `test233` needs an invoked child session, `#_parent`
delivery, and a `<finalize>` handler.

**Timers are real wall-clock.** `Session` calls `Process.send_after/3`
directly (`lib/statifier/session.ex:932-947`); `Session.Timers` deliberately
performs nothing. There is no clock-injection seam anywhere in the repo, and
this bead does not add one. Corpus delay values split cleanly into two
clusters with nothing between them: `1ms`, `2ms` and `10ms` (7 occurrences),
and `.5s` upward (72). The short cluster is the only one that ever has to fire
*between two events of the same test*. The long cluster is mostly guard sends
(`<send event="timeout" delay="5s"/>`) that a passing run must never let fire,
plus a handful a test genuinely waits on with no further event to send -
`test208`'s `'1.5s'`, `test175`'s dynamic `'1s'`.

**The session runtime is globally named.** `Statifier.Supervisor`
(`lib/statifier/supervisor.ex`) is module-based with fixed child names
`Statifier.Registry` and `Statifier.SessionSupervisor`, never started
automatically (ADR-0027 decision 1). Eight existing test files
(`session_runtime_test.exs`, `supervisor_test.exs`, and six under
`test/statifier/session/invoke_*`) call `start_supervised!(Statifier.Supervisor)`
across ~30 call sites and are all `async: false` for exactly that reason.
Generated corpus tests are `use Statifier.Case, async: true` unconditionally.

**Growing the ratchet is unguarded.** `test/passing_tests.json` is absent from
`GateGuard`'s `@guarded_paths` (`lib/mix/statifier/gate_guard.ex:36`);
`ratchet_findings/1` (`:206-219`) fires only on a set-difference *removal*. No
`docs/quality-gate-changes.md` entry is needed for this bead's ratchet growth.
`GateGuard` does scan `test/` for newly added `@tag :skip` (`:196-203`), which
is ADR-0011's mechanical half.

**Unratcheted corpus failures cannot redden the gate.** `mix test` excludes
`:scion` and `:scxml_w3` (`test/test_helper.exs`), and the `Regression ratchet`
stage runs only what `test/passing_tests.json` expands to. That is what lets
Phase 1 land a flip that starts ~106 files running, most of them failing, on a
green gate - the same property st-af3.8 relied on.

### Resolutions of the research document's eight open questions

Each was a design question the plan had to settle rather than pass through.

1. **What routes a corpus test to the session path?** The detected feature set
   already computed at `test/support/case.ex:101`. A document detecting any of
   the ten flipped atoms takes the session path; every other document keeps
   the synchronous four-function path byte-for-byte unchanged. No generator
   change, no corpus regeneration, and zero risk to the 174 already-ratcheted
   files - none of them detects any of the ten. Rejected: routing on the
   emitted `@tag required_features:` list (invisible to `test_scxml/4`, and
   would need a generator change), and running *every* corpus test through a
   session (would put all 174 ratcheted files on a new code path for no
   payoff).

2. **What does "quiescent" mean for the harness?** No single quiescence
   predicate satisfies both of `send1`'s assertions, so the harness uses two
   different rules at two different moments:

   - **Asserting a configuration**: poll until the observed leaf set *equals*
     the expectation, and stop early when the session can no longer change -
     `status != :running`, or `queued_events == 0 and pending_timers == 0` -
     or when a 4000ms deadline expires. Then assert equality. `send1`'s
     `["b"]` matches on the first poll, before the 10ms timer; `test208`'s
     `["pass"]` matches after 1.5s; a genuinely wrong configuration in a chart
     with no pending work fails immediately rather than burning the deadline.
   - **Between one assertion and the next event**: if `pending_timers > 0`,
     wait up to a 100ms settle window for it to reach 0. `send1`'s 10ms send
     lands inside that window, so `t2` arrives in `c` and reaches `d`; the
     `500ms`-and-up guard timers do not fire and cost the full 100ms only on
     the tests that carry them.

   The 100ms threshold sits in the gap between the corpus's two delay
   clusters, counted at this commit: `1ms`/`2ms`/`10ms` (7 occurrences) and
   `.5s` upward (72). Only the first cluster ever has to fire between two
   events of the same test, which is all the settle window is for; a longer
   delay a test waits on with no further event to send - `test208`'s 1.5s,
   `test175`'s dynamic `'1s'` - is covered by the deadline instead. The
   4000ms deadline clears the
   longest load-bearing delay (1.5s) with margin while staying under the
   shortest guard that a stuck test would let fire (3s guards exist, so a
   stuck test may observe a `timeout` event before the deadline - that is a
   failure either way, and the observed configuration in the flunk message
   names it).

   The residual risk this accepts, recorded so it is not discovered later:
   poll-until-match accepts a configuration the chart passes through
   transiently. A chart that reaches the expected leaves and then leaves them
   still passes that step. This is the standard shape for an asynchronous
   conformance harness and is the only rule that satisfies `send1`; the
   alternative (a quiet-window rule) fails `send1`'s first assertion outright.

3. **How do `async: true` invoke corpus files coexist with a globally-named
   supervisor?** `test/test_helper.exs` places `Statifier.Supervisor` once for
   the whole run, before `ExUnit.start/1`, and the ~30
   `start_supervised!(Statifier.Supervisor)` call sites in the eight existing
   files are removed. One node-wide runtime is safe to share: sessions are
   `restart: :temporary`, registered under UXID session ids that cannot
   collide, and each corpus test stops its own session before returning.
   Rejected: emitting `async: false` for invoke files (needs a corpus
   regeneration, which needs network and Saxon), and a lazily-started tolerant
   helper (`Supervisor.start_link/1` links to the calling test process, so the
   runtime would die with whichever test happened to start it).

4. **What does the wall-clock delay cost the gate?** Measured in Phase 3 and
   recorded in Corpus/Ratchet Notes rather than guessed here. The design keeps
   it bounded: the settle window costs nothing for a document with no pending
   timer, the assertion poll exits early whenever the session cannot change,
   and the corpus runs `async: true`.

5. **What replaces the `:unsupported` examples?** Synthetic names, and no new
   registry atom. `validate_features/1` already treats an atom absent from the
   registry as unsupported (`feature_detector.ex:134`), which the adjacent
   `:not_a_real_feature` test already exercises, so
   `feature_detector_test.exs:316` becomes a two-atom synthetic set. The
   `case_test.exs` flunk test cannot survive in its current form at all:
   `detect_features/1` can only emit atoms the registry knows, and after the
   flip every one of them is `:supported` or `:partial`, so **no real document
   can flunk the gate**. It is replaced by a test that asserts exactly that -
   every atom the detector can emit is supported or partial - which states the
   vacuity deliberately and goes red the day a new `:unsupported` atom is
   added. Rejected: keeping a placeholder `:unsupported` atom purely so the
   gate has something to catch (a fabricated gate), and adding a `data_src`
   atom (st-af3.8 declined it on the record, and it would convert test552's
   visible failure into a silent skip - the exact shape ADR-0011 exists to
   prevent).

6. **What is the exact corpus denominator?** 281 files, counted at this commit
   (119 + 159 + 3). `docs/testing.md:215-216` says 118 SCION + 159 W3C and
   omits `optional/` entirely; the bead description says 282. Phase 3
   recounts and corrects that sentence. `docs/testing.md` is not a guarded
   path.

7. **Which stale prose is in scope?** In: the `FeatureDetector` moduledoc and
   the `@send_child_features` comment (Phase 1), `lib/statifier/supervisor.ex`'s
   "Tests `start_supervised!` the same module" sentence, which this plan makes
   false (Phase 2), and the claim that `#_<invokeid>` resolves to
   `error.communication` unconditionally, which st-xcgr changed and this bead
   ratchets the proof of - it appears **twice**, at
   `docs/architecture.md:150-153` and word for word in
   `lib/statifier/session.ex:109-114`, and both are fixed in one pass
   (Phase 3). Out:
   `.quality.exs:60-81`'s "still empty" comment, because `.quality.exs` is
   ADR-0011 guarded and a guarded edit needs a human's ledger entry; `st-0y0`
   already exists for a different stale comment in that file, and Phase 3
   files a bead for this one rather than editing it.

8. **The 2026-08-11 survey** in the bead description exists only in the bead
   text. Its figures do not reconcile with the counts above, which were taken
   from the tree. This plan uses the counted figures throughout.

## Desired End State

`test/support/feature_detector.ex` marks all ten atoms `:supported` and holds
no `:unsupported` entry at all; `test/support/case.ex` drives a document
detecting any of the ten through `Statifier.Session`, keeping every other
document on the unchanged four-function synchronous path; `test/test_helper.exs`
places the session runtime once for the run; and `test/passing_tests.json`
holds every corpus file that passes, with none removed.

Verify with: `mix gate.verify` exits 0 (proving an unscoped, unprofiled,
unskipped full green), `mix test.regression` passes, `mix test.baseline` run a
second time reports zero newly passing, and `mix test --include scion --include
scxml_w3` shows no failure in any file listed in `test/passing_tests.json`.

### Key Discoveries:

- The ten registry rows are contiguous at `test/support/feature_detector.ex:80-81`
  and `:106-113`; the flip follows the established `# st-cmq.9` provenance-comment
  convention.
- `test/support/case.ex:101` already computes the detected feature set, so
  routing needs no generator change and no corpus regeneration.
- `Session.status/1` returns the **full** configuration as string ids
  (`lib/statifier/session.ex:315-324`), not the leaf view, so the harness reads
  leaves off `Session.snapshot/1`'s `%MachineState{}` and uses `status/1` only
  for the `queued_events` / `pending_timers` / `status` counters.
- A terminated session's `snapshot/1` configuration is empty by construction
  (`exit_interpreter/1`, Appendix D). The terminal position rides the
  `{:done, %Effect.Done{}}` effect, which the session delivers to
  `subscribers:`. The existing `observed_state_chart/2`
  (`test/support/case.ex:139-144`) already performs exactly that restore and is
  reused unchanged by both paths.
- `Statifier.start_session/2` (`lib/statifier.ex:176-196`) starts an
  unlinked, registered session on `Statifier.SessionSupervisor`; it does not
  die with the test process, so the harness must stop it itself.
  `Session.stop/2`'s `terminate/2` cancels outstanding delayed-send timers, so
  stopping is also what keeps a 5s guard timer from outliving its test.
- Growing `test/passing_tests.json` trips no `mix gate.check` finding
  (`lib/mix/statifier/gate_guard.ex:206-236`); only shrinking does.
- ADR-0011 and `docs/testing.md`: the ratchet only moves forward, a feature PR
  adds the tests it makes pass in the same PR, and a remaining red is a bead,
  never a `@tag :skip` and never a corpus exclusion.
- **ADR-0006's four-function contract now reads per path, not corpus-wide.**
  That ADR calls `compile/1`, `initialize/2`, `send_event/2` and
  `active_leaf_states/1` "a hard API constraint on the v2 surface", for the
  corpus as a whole. After this bead the ~106 session-routed files couple to
  five functions in a different module instead - `Statifier.start_session/2`,
  `Session.send_event/2`, `Session.snapshot/1`, `Session.status/1`,
  `Session.stop/2` - while `compile/1` and `active_leaf_states/1` stay shared
  and unchanged. That is a change in what the ADR's contract covers, not a
  demonstration that it is untouched, and this plan states it as such rather
  than arguing it away. `Statifier.Session` is already public API with its own
  ADRs (0027, 0029), so nothing undocumented is being exposed; what moves is
  the *scope* of ADR-0006's constraint. Phase 3 files a bead proposing the
  addendum, which is a direction-level call, not a plan's to make.
- **ADR-0027 decision 1 prescribes `start_supervised!` in tests; this plan
  deviates.** That ADR says "Tests `start_supervised!` the same supervisor",
  and `lib/statifier/supervisor.ex`'s moduledoc repeats it. `start_supervised!`
  binds the runtime's lifetime to one test process, so no two `async: true`
  corpus files can share it, and the generated corpus is `async: true`
  unconditionally. Phase 2 therefore places one run-scoped runtime in
  `test/test_helper.exs` instead. The ADR's principle is untouched - the
  embedder places the runtime, the library never does, and nothing in `lib/`
  starts a process - but its stated mechanism is not, and this is named here as
  a deviation rather than left for a reader to find in the diff. Phase 3 files
  it with the ADR-0006 addendum above.
- No changelog fragment. `changelog.d/README.md` excludes test harness, corpus
  tooling, and conformance fixtures, and this bead is nothing else.

## What We're NOT Doing

- **Not adding a clock-injection seam.** Timers stay real wall-clock. A fake
  clock would be a `lib/` design change (ADR-0003 territory) with its own bead
  and its own review, and the two bounded waits in Phase 2 make the corpus pass
  without one.
- **Not regenerating the corpus** (`mise run corpus`). It needs network access
  and Saxon, and nothing it would change is read at run time - the
  `@tag required_features:` lines are informational and the feature gate
  recomputes from the document. Same deliberate choice st-af3.8 recorded.
- **Not renaming `send_content_elements` / `send_param_elements`.** The
  `@send_child_features` comment (`feature_detector.ex:168-182`) defers its own
  rename to this bead, and this plan declines it. The names are emitted into
  every generated file's `@tag required_features:` list, so a rename means a
  corpus regeneration for a cosmetic gain; and with `<send>` and `<invoke>` now
  both `:supported`, the lumping the comment worried about can no longer change
  any outcome. Phase 1 rewrites the comment to say that instead.
- **Not adding a `data_src` atom, and not touching test552.** st-af3.8 declined
  it on the record and `st-bnr` owns it. Gating it here would silence a visible
  failure on the branch that inherited it.
- **Not editing `.quality.exs`.** Its "conformance lists are still empty"
  comment is stale, and the file is ADR-0011 guarded. Phase 3 files a bead.
- **Not fixing the engine failures the run turns up.** They get beads, one per
  distinct root cause. Fixing them is `lib/` work with a different review.
- **Not supplying the harness an `:invoke_source` resolver.** ADR-0038 puts
  `src` resolution with the embedder and says the library never fetches. An
  `<invoke src="...">` corpus file therefore stays red here; making it pass by
  teaching the harness to fetch would have the corpus answer a question the
  library is documented not to answer.
- **Not making the existing `async: false` session tests async.** Phase 2
  removes their `start_supervised!` calls because the runtime is now placed
  globally, and nothing else about them changes. Several read `:sys.get_state`
  and assert on process-global effects; flipping them is unrelated risk.
- **Not adding a shared `wait_for_status/3` to `test/support/`.** Six existing
  session test files copy-paste their own poller. Consolidating them is a real
  cleanup and a real diff, and it is not this bead's; the corpus harness's two
  waits live in `test/support/case.ex` where the corpus uses them.

## Implementation Approach

Three phases, ordered so each one's diff is reviewable on its own terms and
each leaves the gate green on its own: registry policy, then the harness that
consumes it, then the ratchet that consumes both.

The flip comes **first**, before the session harness, which inverts the order a
reader might expect. It is the order that makes each phase verifiable. After
Phase 1 the ~106 blocked files start running and mostly fail - which cannot
redden the gate, since they are not in the ratchet and `mix test` excludes both
suites - and that failure set is Phase 1's own measurable assertion: every one
of them now fails on an assertion or a compile, and none on the feature gate.
Phase 2's new harness tests then need `<send>` and `<invoke>` documents to run
through `test_scxml/4`, which is only possible once the gate lets them through.
Sequencing the harness first would produce a phase whose central mechanism
nothing could exercise - the case the skill's sizing rule says to combine or
reorder rather than ship.

Phase 3 depends on both and must come last.

```elixir
  # The ten atoms st-cmq.9 flipped are exactly the ones whose semantics need a
  # running session: delivery to an external queue, wall-clock timers, and
  # child sessions. Every other document reaches the same configuration
  # through the four-function synchronous path, which stays the default - the
```

#### 3. The session driving path

**File**: `test/support/case.ex`

**Changes**: a new private path. It reuses `parse_document/1`,
`observed_state_chart/2`, `assert_every_leaf_named/2` and `active_leaf_states/1`
unchanged - only `initialize` and `send_event` are replaced.

```elixir
  # A corpus document that needs a session needs the *registered* runtime:
  # `<invoke>` starts children through `Statifier.start_session/2` and
  # `#_scxml_<sessionid>` targets resolve through `Statifier.Registry`.
  # Sessions started this way are unlinked and `restart: :temporary`, so the
  # harness stops each one itself - which is also what cancels any guard timer
  # still pending when the test ends (`terminate/2`, spec 6.2's
  # discard-on-termination).
  defp drive_through_session(xml, expected_initial_config, events) do
    machine = parse_document(xml)
    {:ok, session} = Statifier.start_session(machine, subscribers: [self()])

    try do
      assert_configuration_eventually(session, expected_initial_config)

      Enum.each(events, fn {%{"name" => name}, expected_states} ->
        settle_short_timers(session)
        :ok = Statifier.Session.send_event(session, name)
        assert_configuration_eventually(session, expected_states)
      end)
    after
      Statifier.Session.stop(session)
    end

    :ok
  end
```

The two waits, each a named constant with the reasoning inline:

```elixir
  # The corpus's delay values fall into two populations: load-bearing
  # intermediate delays (1ms, 2ms, 10ms) that a later assertion depends on
  # having fired, and guard sends (`<send event="timeout" delay="5s"/>`) that a
  # passing run must never let fire. 100ms separates them cleanly, so waiting
  # out a pending timer before the *next* event drains the first population and
  # never the second. Costs nothing when no timer is pending, which is most of
  # the corpus.
  @settle_window_ms 100

  # The longest load-bearing delay in the corpus is 1.5s
  # (mandatory/cancel/test208). 4s clears it with margin. This bounds only the
  # wrong answer: a chart that cannot change again exits the poll immediately.
  @configuration_deadline_ms 4_000
  @poll_interval_ms 5
```

`assert_configuration_eventually/2` polls `Session.status/1` for the counters
and `Session.snapshot/1` for the `%MachineState{}` the leaf read needs,
draining any `{:statifier, _sid, {:effect, {:done, done}}}` message from the
mailbox so a terminated chart's configuration is restored by the *same*
`observed_state_chart/2` the synchronous path uses. It stops on the first of:
the observed leaf set equalling the expectation; the session being unable to
change again (`status != :running`, or `queued_events == 0 and pending_timers
== 0`); or the deadline. It then performs the ordinary
`assert_every_leaf_named/2` plus set-equality assertion, so a failure message
is identical in shape to the synchronous path's.

`settle_short_timers/1` returns immediately when `status.pending_timers == 0`,
and otherwise polls until it reaches 0 or `@settle_window_ms` elapses.

The moduledoc gains a section stating the two-path contract explicitly: the
four-function requirement on `Statifier` is unchanged and is what the
synchronous path exercises; the session path replaces two of the four
(`initialize`, `send_event`) with `Statifier.start_session/2` and
`Session.send_event/2` while `Statifier.compile/1` and
`Statifier.active_leaf_states/1` stay exactly as they were, so the corpus still
cannot widen the library surface (ADR-0006).

## Open Questions Discovered During Implementation

- **test192 and test233 cannot pass through the session harness**, contrary
  to Phase 2's and Phase 3's automated verification lists. Root cause
  (confirmed by direct reproduction against both a bare `Session.start_link`
  and `Statifier.start_session`): each document's inline
  `<invoke><content><scxml>` child carries no `xmlns`, and
  `Invoke.Source.resolve/2` recompiles that slice as a standalone top-level
  document at invoke time, which `Validator.Checks.Boilerplate` rejects with
  `{:bad_namespace, nil}` per ADR-0041's amendment. `error.communication`
  then routes test192 to its wildcard-less stuck-at-`s01` timeout and test233
  to its `event="*" target="fail"` wildcard. This is exactly the gap
  `st-ybuj` tracks; ADR-0042 (branch `st-ybuj-namespaceless-content-child`,
  commit `b5250f2`) records the decided fix but its own note says
  "Implementation not done". A `blocked-by` dependency link from `st-cmq.9`
  to `st-ybuj` was added during this run. Phase 2's two boxes for these files
  are left unchecked rather than force-checked; Phase 3 treats both files as
  expected reds pending `st-ybuj` and files/reuses the existing bead instead
  of ratcheting them. This is a human-visible mismatch between the plan's
  literal success criteria and what this bead can deliver before `st-ybuj`
  lands - flagged here rather than silently worked around.
- **A `Statifier.start_session/2` + `DynamicSupervisor` deadlock** was found
  in Phase 2: if a session's own `init/1` synchronously starts a child
  `<invoke>`, both `start_child` calls contend the same busy
  `DynamicSupervisor` and hang forever. Not filed as its own bead yet because
  it is unreachable in the corpus today - every initial-state `<invoke>` in
  the corpus hits the `st-ybuj` namespace gap first and never reaches
  `DynamicSupervisor` for the grandchild. Worth its own bead once `st-ybuj`
  lands and this deadlock becomes reachable; noted here so it is not lost.
