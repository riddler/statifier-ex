# Exit and entry sets - Implementation Plan

## Overview

Ports the Appendix D exit and entry block function for function (ADR-0002):
`exit_states`, `compute_entry_set`, `add_descendant_states_to_enter`,
`add_ancestor_states_to_enter`, `enter_states`, and `in_final_state?`, plus
history recording and restoration, the `done.state.*` completion events, and
the exit-set / entry-set trace points. This is the bead that first *mutates*
the configuration: st-wju.3 computed which transitions fire and which states
they would leave; this one actually leaves and enters them.

Bead: st-wju.4. No research document exists; the bead's description and
acceptance criteria are the specification, read alongside ADR-0002 (literal
port), ADR-0003 (pure core with effects), ADR-0005 (full configuration,
interned indexes), ADR-0012 / `docs/observability.md` (constraints 2, 3, 4,
5), and the three landed sibling plans
(`docs/plans/260809-st-wju.1-compile-document-to-interned-machine.md`,
`docs/plans/260809-st-wju.2-machine-state-event-effects-vocabulary.md`,
`docs/plans/260810-st-wju.3-ports-transition-selection.md`).

**A note on the word "phase".** The project roadmap numbers its own phases -
Phase 1 is the core engine (this epic, `st-wju`), Phase 3 is the datamodel
(`st-af3`), Phase 4 is sessions and invoke (`st-cmq`). This plan numbers its
four implementation phases independently. Every reference to a roadmap phase
below names the bead too ("the datamodel bead, st-af3"); a bare "Phase N"
always means a phase of *this* plan.

No human was available while this plan was written. Every question the bead
left open is settled below under "Decisions", each stated as an assumption a
reviewer may overturn; the four least settled are listed again under "Open
Questions" so a reviewer can find them without reading the whole document.

### The cross-bead boundary this bead sits on

st-wju.4's dependencies are st-wju.1, st-wju.2, and st-wju.3. **st-wju.5 (the
executable-content protocol and block runner) is not among them**, and its own
bead says the block runner "lives here and is what st-wju.4 and st-wju.6
call". So this bead owns the *ordering and call sites* of content execution -
which the Appendix D exit/entry blocks define - while the runner that actually
executes a block lands later. Decision 6 fixes the seam.

## Desired End State

One new module, `Statifier.Interpreter.ExitEntry` in
`lib/statifier/interpreter/exit_entry.ex`, fully documented and fully tested,
consumed by nothing yet (st-wju.6 is its first caller), exposing:

- `exit_states/2` - `{MachineState.t(), [Effect.t()]}`
- `compute_entry_set/2` - the three-part entry bookkeeping
- `add_descendant_states_to_enter/3`
- `add_ancestor_states_to_enter/4`
- `enter_states/2` - `{MachineState.t(), [Effect.t()]}`
- `in_final_state?/2`

plus one additive function on `Statifier.MachineState`, `raise_platform/4`
(Decision 8).

Verification that the end state is reached: `mix quality` green with coverage
at or above the floor; `mix adr.check` clean, with exactly one ADR-citing
comment in the module (on `in_final_state?/2`, for the reason above) and no
other naming finding;
`test/statifier/interpreter/exit_entry_acceptance_test.exs` asserting every
acceptance-criteria line a test can decide.

The behavioral end state, stated so a reviewer can check it without the
pseudocode in hand:

- **Exit.** The states to exit are `Selection.compute_exit_set/2` over the
  enabled transitions, ordered by `Machine.exit_order/2` (descending index).
  *Before any state is removed and before any `onexit` content runs*, every
  history child of every exiting state records against the configuration as it
  stands: a `:shallow` history records the exiting state's active immediate
  children, a `:deep` history records its active atomic descendants. Then, per
  state in exit order: run its `onexit` blocks in document order, then remove
  it from the configuration.
- **Entry set.** `compute_entry_set/2` walks each transition's written targets
  through `add_descendant_states_to_enter/3` and each of its *effective*
  targets through `add_ancestor_states_to_enter/4` bounded by the transition
  domain. A compound state entered without an explicit descendant target pulls
  in its `<initial>` targets and is flagged for default entry; a parallel pulls
  in every region not already covered; a history target restores its recorded
  value, or, when unrecorded, follows its default transition's targets and
  registers that transition's content as the state's default history content.
- **Entry.** States enter in document order (ascending index): add to the
  configuration, run `onentry` blocks in document order, then the default-entry
  content when flagged, then the default history content when registered.
- **Completion.** Entering a `:final` whose parent is the `:scxml` root sets
  `running: false` and raises nothing. Entering any other `:final` raises
  `done.state.{parent_id}` carrying the final state's static donedata; if that
  parent's own parent is a `:parallel` and every one of its regions is now in a
  final state, `done.state.{grandparent_id}` follows, with no donedata. Both
  carry a `{:state, final_index}` cause and the current counters.
- **Trace.** `Trace.ExitSet` is emitted with the exit-ordered indexes before
  any state exits; `Trace.EntrySet` with the entry-ordered indexes before any
  state enters. Both gated; trace off produces neither.

## What We're NOT Doing

- **No executable content is actually run.** `<onexit>`, `<onentry>`, the
  `<initial>` transition's content, and the default history content all get
  their *call site and ordering* here, behind the Decision 6 seam whose body
  st-wju.5 fills in. This bead runs zero content nodes and emits zero
  `Trace.ContentExecuted` effects - `lib/statifier/effect.ex:34` already
  assigns that row to st-wju.5, whose bead says the trace "wraps the block
  runner".
- **No `microstep`, no `macrostep`, no interpreter entry point.** st-wju.6.
  This bead never calls `begin_macrostep/1` or `begin_microstep/1`; it reads
  the counters through the trace and cause constructors and never writes them.
- **No `exit_interpreter`, no top-level termination effect.** Entering a
  top-level final sets `running: false` and stops; producing `{:done, _}` and
  moving `status` to `:done` is st-wju.6's, per the bead's explicit split.
- **No donedata evaluation.** A `{:static, term}` donedata rides onto the
  event's `data`; a `{:compiled, _, _}` one contributes `nil` with a comment
  naming st-af3 (Decision 10). No predicator call appears in this bead.
- **No `statesToInvoke`, no `cancelInvoke`.** Both are pseudocode lines this
  port skips with a mechanical-reason comment naming st-cmq, exactly as
  `Statifier.MachineState`'s moduledoc already committed to ("`states_to_invoke`
  is deliberately absent").
- **No `binding == "late"` datamodel initialization.** `enterStates`'s
  `initializeDataModel` line is skipped with a comment naming st-af3;
  `Machine.binding` is compiled and unread until then.
- **No change to `Statifier.Interpreter.Selection`.** Its three boundary
  decisions are consumed as landed. In particular this bead does not make
  `compute_exit_set/2` return an ordered structure, and does not re-port
  `get_effective_target_states/2` or `find_lcca/2`.
- **No `FeatureDetector` change and no conformance ratchet movement.** See
  "Corpus/Ratchet Notes".
- **No changelog fragment.** Nothing here is reachable from a public API until
  st-wju.7 (`changelog.d/README.md` - most changes need none).
- **No memoization of `compute_exit_set/2`.** See "Performance
  Considerations"; the literal port is the default under ADR-0002.

## Implementation Approach

Four phases, in dependency order, each adding code together with its own tests
so no phase leaves an untested function behind to sink the coverage floor:

1. The exit side end to end - the module, the content seam, history recording,
   the `ExitSet` trace, and configuration removal. It depends on nothing this
   plan has not landed and is the half st-wju.6 calls first.
2. The entry *set* - `compute_entry_set/2` and its two `add_*` walks. Pure
   computation over a machine_state, mutating nothing, which is what makes it
   independently testable before anything can enter a state.
3. Entry itself - `enter_states/2`, `in_final_state?/2`, the `done.state.*`
   raises, the top-level `running: false`, the `EntrySet` trace, and
   `MachineState.raise_platform/4`.
4. The acceptance test, the documentation, and the cross-bead notes.

Phases 1-3 all touch `lib/statifier/interpreter/exit_entry.ex`; they are split
because each is independently gate-verifiable with its own tests and each is a
coherent piece of the pseudocode. They do not parallelize across worktrees,
which is fine: `docs/workflow.md`'s parallelism is across beads, not within
one.

Every design question is settled below before any code is written, because
st-wju.5 and st-wju.6 both read these signatures.

## Decisions

**Decision 1 - one module, `Statifier.Interpreter.ExitEntry`, at
`lib/statifier/interpreter/exit_entry.ex`.** The directory is fixed by
`Mix.Statifier.AdrGuard`'s `@interpreter_pattern`
(`lib/mix/statifier/adr_guard.ex:50`): interpreter code outside
`lib/statifier/interpreter/` silently escapes the ADR-0002 naming stage. One
module per bead within that namespace is st-wju.3's Decision 1 and keeps each
bead's diff to one file, which is what makes the epic's worktrees mergeable.

Exit and entry are not split into two modules: `enterStates` calls
`computeEntrySet`, `computeEntrySet` calls the domain half of `Selection`, and
`exitStates` and `enterStates` are the two halves of one microstep that
st-wju.6 calls back to back. A `Statifier.Interpreter.Exit` /
`.Entry` pair would put a module boundary in the middle of one pseudocode
section for no gain.

**Decision 2 - `exit_states/2` and `enter_states/2` return
`{MachineState.t(), [Effect.t()]}`.** They are the two functions in this bead
that both mutate the position and emit effects; the tuple is the shape
`docs/observability.md:39` already fixes for `microstep/1`, which is their only
caller, and the shape st-wju.5's block runner returns. The pure queries
(`compute_entry_set/2`, the two `add_*` walks, `in_final_state?/2`) return
plain values with no machine_state and no effects, because none of them can
mutate or emit - constraint 5's "callable standalone in `iex`" applies to them
in exactly the form st-wju.3's queries have it.

Effect order within the returned list is emission order: the `ExitSet` /
`EntrySet` trace first, then each block's effects in the order the blocks ran.

**Decision 3 - `compute_entry_set/2` returns a three-element tuple, and the
same tuple is the accumulator the two `add_*` walks thread.**

```elixir
@type entry_set :: {
        states_to_enter :: MapSet.t(non_neg_integer()),
        states_for_default_entry :: MapSet.t(non_neg_integer()),
        default_history_content :: %{optional(non_neg_integer()) => non_neg_integer()}
      }

@spec compute_entry_set(machine_state :: MachineState.t(), transitions :: [Transition.t()]) ::
        entry_set()

@spec add_descendant_states_to_enter(
        machine_state :: MachineState.t(),
        state_index :: non_neg_integer(),
        acc :: entry_set()
      ) :: entry_set()

@spec add_ancestor_states_to_enter(
        machine_state :: MachineState.t(),
        state_index :: non_neg_integer(),
        ancestor :: non_neg_integer(),
        acc :: entry_set()
      ) :: entry_set()
```

The pseudocode passes `statesToEnter`, `statesForDefaultEntry`, and
`defaultHistoryContent` as three mutable out-parameters. Elixir has no
out-parameters, so they become one accumulator threaded in and returned - the
minimal mechanical deviation, and the one that keeps the recursion a fold
rather than a rewrite. A named struct was considered and rejected: three
members with no behavior and one call site is a tuple, and a struct would put a
type between the reader and the pseudocode's own three names. The `@type` above
carries the names instead.

Argument order follows CLAUDE.md ("functions taking a state/session put it as
the first argument") and st-wju.3's Decision 3; the accumulator goes last,
where the pseudocode's out-parameters are.

**Decision 4 - `states_to_enter` and `states_for_default_entry` are `MapSet`s;
entry order comes from `Machine.document_order/2`.** The pseudocode's
`OrderedSet` is read in exactly two ways: membership (`isMember`,
`some(isDescendant)`) and `toList().sort(entryOrder)`. Neither uses insertion
order, so a `MapSet` plus the existing ascending sort is behaviorally
identical, and it matches Decision 6 of st-wju.3 for the exit set - one
ordering rule, `Machine.document_order/2` and `Machine.exit_order/2`, and no
function in the interpreter that orders a set by hand. `@doc`s say so.

`default_history_content` is a plain map keyed by state index, which is what
the pseudocode's `HashTable` keyed by `state.parent` is.

**Decision 5 - `default_history_content` stores the default transition's
`t_index`, not its `[c_index]` list.** The pseudocode stores
`state.transition.content`. Storing the `t_index` instead is strictly more
information (the content list is `Machine.transition(machine, t).content`, one
lookup away) and it is the information the content seam actually needs: a
block's effects and its future `Trace.ContentExecuted` are stamped with a
`Machine.Content.owner()`, which for a transition's own content is
`{:transition, t_index}` (`lib/statifier/machine/content.ex:41-52`). Storing
the bare list would throw the owner away and force st-wju.5 to reconstruct it.
Mechanically equivalent, so it carries a comment naming the deviation and its
reason rather than being silently different.

**Decision 6 - content execution is one private seam,
`execute_block/3`, whose body st-wju.5 replaces.**

```elixir
# ADR-0002: the pseudocode's `executeContent(content)`. st-wju.5 owns the
# block runner and the `Trace.ContentExecuted` emission that wraps it; this
# bead owns only *where and in what order* blocks run, which is what the
# exit/entry pseudocode defines. Replacing this body with a call to that
# runner changes no call site and no ordering.
@spec execute_block(
        machine_state :: MachineState.t(),
        owner :: Content.owner(),
        c_indexes :: [non_neg_integer()]
      ) :: {MachineState.t(), [Effect.t()]}
defp execute_block(machine_state, _owner, _c_indexes), do: {machine_state, []}
```

Every content call site in this bead goes through it: each `<onexit>` block
with `{:onexit, state_index, ordinal}`, each `<onentry>` block with
`{:onentry, state_index, ordinal}`, the `<initial>` transition's content with
`{:transition, initial_t_index}`, and the default history content with
`{:transition, history_default_t_index}`. `ordinal` is the block's position in
the state's `onentry` / `onexit` list, which is exactly what
`Machine.Content.owner()` documents it to be.

Three alternatives were weighed:

| Option | Verdict |
|---|---|
| Take a `run_block` function as a parameter (dependency injection) | Rejected. It puts a function-valued argument on `exit_states/2` and `enter_states/2` forever to serve one bead's ordering, and st-wju.6 would have to supply it at every call. |
| Land st-wju.5 first and call its runner | Rejected. st-wju.5 is not a dependency of this bead, the epic's worktrees are meant to move independently, and inverting the order makes st-wju.5 the bead that has to invent this ordering blind. |
| **A private stub seam with the signature fixed and a comment naming st-wju.5** | **Chosen.** Exactly the precedent `Selection.condition_match/2` set for st-af3 (its plan's Decision 7): the shape is decided now, the body lands later, and the later bead changes a body rather than a signature or a call site. It is also the only option under which this bead's ordering tests - which is what the bead is actually about - can exist today. |

Consequence to state plainly, because it is the biggest thing a reviewer should
check: **this bead cannot test that content ran, only that it would have been
asked to run, in the right order.** Phase 1 and Phase 3 therefore each carry one
test that injects a recording seam - see "Testing Strategy" - so the *sequence*
of `execute_block/3` calls is asserted even though the runner is a stub.

**Decision 7 - history is recorded in a separate full pass over the exit set,
before the first `onexit` runs.** The pseudocode writes two consecutive `for s
in statesToExit` loops, and the order is load-bearing rather than incidental:
`onexit` content can raise events but, more importantly, the second loop
deletes from the configuration as it goes, so recording inside it would let a
later-exiting state's deep history see a configuration its own siblings have
already been removed from. The port keeps two passes and the `@doc` says why -
this is the acceptance criterion "History recorded from the pre-exit
configuration before any onexit content of the step runs", and it is asserted
by a test that puts `onexit` on a state exiting *before* the one whose history
is recorded.

Shallow: `MapSet.filter(configuration, &(Machine.at(machine, &1).parent == s))`.
Deep: `MapSet.filter(configuration, &(Machine.atomic?(machine, &1) and
Machine.descendant?(machine, &1, s)))`. Both are the pseudocode's two lambdas
verbatim; `descendant?/3` is proper, which is correct here because `s` is not
atomic when it has a history child.

Recording overwrites unconditionally, which is what `historyValue[h.id] = ...`
does - a revisit replaces the previous record rather than merging. A named test
pins that.

**Decision 8 - `done.state.*` is raised through a new
`MachineState.raise_platform/4`, not `raise_internal/4`.**

This is the one place this plan departs from a sentence in a landed sibling.
`MachineState.raise_internal/4`'s `@doc` says it "is the one function st-wju.4
(`done.state.*`) and st-wju.5 (`<raise>`) call", and this bead's own note
repeats it. But `raise_internal/4` builds its event with `Event.internal/3`,
which stamps `type: :internal` - and `Statifier.Event`'s moduledoc defines
`:internal` as "raised by executable content in the document" and names
`done.state.*` explicitly as a **`:platform`** event, matching spec 5.10.1.
Following the sentence would ship every completion event misclassified, and
would leave `Event.platform/3` a documented constructor with no caller
anywhere.

So Phase 3 adds, additively, on `Statifier.MachineState`:

```elixir
@spec raise_platform(
        machine_state :: t(),
        name :: String.t(),
        origin :: Cause.origin(),
        opts :: keyword()
      ) :: t()
```

- identical to `raise_internal/4` except for calling `Event.platform/3`, and
  `raise_internal/4`'s `@doc` is amended in the same commit to point at it for
  `done.state.*` rather than claiming that traffic for itself. Both still
  enqueue on the same single internal queue - `type` is provenance, not routing
  (`Statifier.Event`'s Decision 10), so nothing about ordering or dequeue
  changes.

Cost: one small function and one doc sentence in another bead's module. The
alternative - `raise_internal/4` and a wrong `type` - is recorded under "Open
Questions" as the reversible half of this call. What is *not* reversible
cheaply is the misclassification leaking into st-cmq's session layer and into
every `_event` the datamodel bead exposes.

**Decision 9 - a `done.state.*` whose parent state has no written id is not
raised, and the skip is commented.** `Statifier.Validator.Checks.Ids` accepts
`nil` and `""` ids, so `Machine.id/2` can return either for a compound parent.
`"done.state." <> nil` raises an ArgumentError, and `"done.state."` is an event
name no transition can usefully match (an id-less state cannot be a transition
target either, so nothing can observe its completion). The port therefore
guards on `Machine.id/2` returning a non-empty binary and skips otherwise, with
a comment stating that the pseudocode assumes `parent.id` exists because the
spec types `id` as an XML Schema ID and this codebase deliberately admits
documents that omit it. A named test covers the id-less parent, asserting no
event and no crash.

**Decision 10 - donedata is static-only, and only the compound-parent event
carries it.** The pseudocode's `new Event("done.state." + parent.id,
s.donedata)` takes the donedata from the *final state being entered*, and the
grandparent-parallel event (`new Event("done.state." + grandparent.id)`) takes
none. Ported as written.

The value: `Machine.State.donedata` is `Donedata.t() | nil` and its `expr` is
`{:static, term} | {:compiled, _, _} | nil`. A `{:static, term}` becomes the
event's `data`. A `{:compiled, _, _}` becomes `nil` `data` with a comment
naming st-af3 as the bead that evaluates it - this is the bead's own "Phase 1
static content only, carried from st-wju.1", and it is not a rescue-to-default
at a leaf because nothing failed: the value simply has not been evaluated yet
and the corpus cannot reach it (`FeatureDetector` flunks any document with a
datamodel expression). A `nil` donedata becomes `nil` `data`, which
`Statifier.Event` already distinguishes from `%{}`.

**Decision 11 - `enter_states/2` sets `running: false` by direct struct update,
and raises nothing for the top level.** The bead is explicit: "Top-level final
entry sets running = false for st-wju.6 to act on - this bead raises nothing
for the top level, matching the pseudocode split." `MachineState` has no
`running` writer; the counter contract restricts only `macrostep` and
`microstep`, so `%{machine_state | running: false}` is in bounds. The condition
is the pseudocode's `isSCXMLElement(s.parent)`, ported as
`Machine.at(machine, s).parent == 0` with a comment noting that the `:scxml`
root is state index 0 by st-wju.1's Decision 2, which is why no root special
case is needed anywhere else either.

**Decision 12 - the helper decomposition, and the names that survive
`mix adr.check`.** Credo caps complexity at 9 and nesting at 2, so the two
recursive walks and `enterStates`'s per-state body become named private
helpers. The names are fixed here because half the obvious ones trip the ADR
guard's containment test (see "Current State Analysis"):

| Pseudocode shape | Helper | Guard check |
|---|---|---|
| `exitStates`'s history-recording loop | `record_history_values/2`, `recorded_value/3` | clear |
| `exitStates`'s onexit-and-delete loop | `depart/2` (per state), `run_onexit_blocks/2` | clear |
| `computeEntrySet`'s per-transition body | `entry_set_for_transition/3` | clear |
| `addDescendantStatesToEnter`'s history arm | `enter_history_target/3`, `enter_restored/4` | clear |
| `addDescendantStatesToEnter`'s compound arm | `enter_initial_targets/3` | clear |
| `addDescendantStatesToEnter`'s parallel arm | `enter_uncovered_regions/3`, `covered?/3` | clear |
| `enterStates`'s per-state body | `arrive/3` (per state), `run_onentry_blocks/2`, `run_default_entry/3`, `raise_completion_events/2` | clear |

Rejected because the guard flags them: `exit_state`, `enter_state`,
`entry_set`, `exit_set`, `enter_states_in_order`. `depart/2` and `arrive/3` are
the deliberate antonym pair for the two per-state bodies - far enough from
`exit_states` / `enter_states` for the guard, close enough in meaning for a
reader, and each carries a comment naming the pseudocode lines it covers so
"diff the function against the pseudocode" still works one level down.

`in_final_state?/2` is the one exception: it is a canonical name in its
ADR-0002-amended form and is flagged anyway, so it carries the ADR-citing
comment the guard's escape hatch expects (`lib/mix/statifier/adr_guard.ex:81`).
The implementer runs `mix adr.check` and, if any further helper name trips it,
adds the same one-line comment rather than renaming to something less clear.

**Decision 13 - the two trace effects are emitted from `exit_states/2` and
`enter_states/2` themselves, at the top, before any mutation.** Both payloads'
`@doc`s already say "before exiting" / "before entering" and "in exit order" /
"in entry order", so this is a contract this bead satisfies rather than
chooses. Emission uses the `Effect.trace/3` macro
(`require Statifier.Effect, as: Effect`), which means trace-off allocates
nothing and never builds the payload. A named test asserts trace-off yields an
effect list with zero `Effect.trace?/1` members, and a second asserts the
indexes are in the documented order rather than merely the right set.

One subtlety the implementer must not trip on: `Effect.trace/3` expands to a
block that binds a variable literally named `machine_state`. The macro is
hygienic, so it cannot capture a caller's binding - but the call sites here are
inside functions whose own parameter is also called `machine_state`, so a
reader may expect shadowing that does not happen. The `@doc` on each emission
site notes it rather than leaving the next reader to check the expansion.

**Decision 14 - `in_final_state?/2` takes `(machine_state, state_index)` and is
public.** The pseudocode's `isInFinalState(s)` reads `configuration` as a
global; reifying it is the same Decision 3 deviation as everywhere else. It is
public rather than private because `docs/observability.md` constraint 5 makes
the Appendix D query functions the debug API - "is this parallel complete?" is
exactly the question a stepper asks - and because the completion-event logic is
the part of this bead most worth being able to call standalone. Its three
branches (compound -> some child is a final in the configuration; parallel ->
every child is in a final state, recursively; otherwise false) are ported
verbatim, including the fact that an atomic `:final` state itself answers
`false`.

## Phase 2: Ports the entry set

### Overview

`compute_entry_set/2`, `add_descendant_states_to_enter/3`, and
`add_ancestor_states_to_enter/4` - the recursive computation of which states a
transition set enters, which of them enter by default, and which carry default
history content. Pure: nothing here touches the configuration.

### Changes Required:

#### 1. The three functions

**File**: `lib/statifier/interpreter/exit_entry.ex`
**Changes**: the `entry_set()` type and the three public functions of Decision
3, plus the Decision 12 helpers.

`compute_entry_set/2` ports its block verbatim: for each transition, each
*written* target through `add_descendant_states_to_enter/3`, then the domain
via `Selection.get_transition_domain/2`, then each *effective* target through
`add_ancestor_states_to_enter/4` bounded by that domain. The written-versus-
effective distinction is the pseudocode's and is preserved with a comment; it
is the same distinction `compute_exit_set/2` already documents on the other
side.

`add_descendant_states_to_enter/3`, three arms:

- **history target**: recorded value in `machine_state.history_values` ->
  recurse into each recorded index and, for each, walk its proper ancestors up
  to the history state's parent through `add_ancestor_states_to_enter/4`.
  Unrecorded -> register `default_history_content[history.parent] =
  history_default_t_index` (Decision 5) and do the same recursion over the
  default transition's targets.
- **compound**: add the state, flag it in `states_for_default_entry`, recurse
  into `initial_transition`'s targets, and walk ancestors bounded by the state
  itself. The targets come from
  `Machine.transition(machine, state.initial_transition).targets`, not from
  `State.initial`, because the pseudocode reads
  `state.initial.transition.target` and the `<initial>` transition is also what
  carries the default-entry content Phase 3 runs. `initial_transition` is
  guaranteed non-nil on a compound state by st-wju.1's compiler (it synthesizes
  one from the `initial` attribute or from the first child); the port asserts
  that with a match rather than a nil check, so a compiler regression fails
  loudly here instead of silently entering nothing.
- **parallel**: for each child region not already covered by a
  `states_to_enter` member that is its descendant, recurse. `covered?/3` is the
  pseudocode's `statesToEnter.some(lambda s: isDescendant(s, child))`.
- **atomic / final / anything else**: add the state and stop.

`add_ancestor_states_to_enter/4` ports its block verbatim: every proper
ancestor of `state` up to but excluding `ancestor` is added, and each parallel
ancestor pulls in its uncovered regions through the same `covered?/3` test.
`Machine.proper_ancestors/2` returns *all* ancestors, so the bound is applied
with `Enum.take_while(&(&1 != ancestor))`; a comment records that this is
`getProperAncestors(state, ancestor)`'s two-argument form expressed over the
one-argument helper st-wju.1 landed, and that a `nil` ancestor (a targetless
transition's domain) therefore correctly takes every ancestor.

## Testing Strategy

### Unit Tests:

- `test/statifier/interpreter/exit_entry_exit_test.exs` - exit order, history
  recording (shallow, deep, both on one state, overwrite, non-exiting history,
  pre-exit configuration), configuration removal, and the `ExitSet` trace with
  its gate.
- `test/statifier/interpreter/exit_entry_entry_set_test.exs` - the three
  members of the entry-set tuple across atomic, compound, parallel, and history
  targets; the default-entry flag's named-target distinction; the
  `default_history_content` recorded/unrecorded split; the ancestor walk's
  bound and its parallel expansion.
- `test/statifier/interpreter/exit_entry_enter_test.exs` - entry order,
  configuration insertion, per-state block ordering, the three completion-event
  cases, cause metadata and counters, `in_final_state?/2`'s three branches, and
  the `EntrySet` trace with its gate.
- `test/statifier/interpreter/exit_entry_acceptance_test.exs` - the bead's
  criteria, driven from XML through the real pipeline, plus the
  standalone-callability assertion and the exit-then-enter round trip.

**How block *ordering* is asserted while the runner is a stub.** Decision 6
leaves `execute_block/3` returning `{machine_state, []}` unconditionally, so no
test in this bead can observe content *running*. Two alternatives were weighed
and both rejected: making the stub emit a marker effect puts test-only
behavior into `lib/`, and passing the runner in as a function argument puts a
permanent parameter on `exit_states/2` and `enter_states/2` to serve one bead.

What the ordering tests assert instead is the input to that seam: for the state
under test, that `Machine.at(machine, s).onentry`, the flagged
`initial_transition`, and `default_history_content[s]` are three *distinct*,
non-empty content lists in the fixture, and that the entry path visits exactly
those three in that order - which is decidable from `compute_entry_set/2`'s two
bookkeeping members plus the state's own compiled blocks, with no execution
involved. That is strictly weaker than observing execution, and it is stated as
such: **the assertion that a block's nodes actually run, in document order,
lands in st-wju.5**, whose bead already owns "block runner: document order,
stop-on-error, effect order preserved". Phase 4's note to st-wju.5 hands the
gap over explicitly rather than losing it. The tests that *are* strong here are
the ones deciding which states are flagged for default entry and which are
registered for default history content, since those decide whether a block
would be asked to run at all.

Key edge cases, each its own named test: an empty transition list on both
sides; a transition list whose exit set is empty (all targetless); a history
state whose recorded value is an empty `MapSet` (distinct from no key at all,
per st-wju.2's Decision 9 - it restores nothing and does **not** fall through to
the default); a deep history on a parallel with one region recorded and one
not; a compound whose `<initial>` targets a grandchild rather than a child; a
transition whose domain is the `:scxml` root; and a `<final>` that is itself
the initial state of a compound (completion on the very first entry).

Fixtures follow `test/statifier/machine_test.exs:10-71` and
`test/statifier/interpreter/selection_acceptance_test.exs:1-80`: a triple-quoted
heredoc at 4-space base indentation through the real pipeline, preceded by a
hand-drawn depth-first index comment, with a pinned `@indexes` map and `idx/1`
so assertions read in state ids. No `%Machine{}` or `%Machine.Transition{}`
literals. `%MachineState{}` values *are* built by hand for the exit and
entry-set suites, because only `enter_states/2` can produce a real
configuration and it does not exist until Phase 3; from Phase 3 on, the enter
suite builds its starting configurations with `enter_states/2` itself wherever
that is the shorter path, and says which it used.

Every test asserting `lib/` behavior carries its sabotage line per
`docs/testing.md:78-134`. Two mutations are worth watching for the "one
mutation reddens twenty tests" signal (`docs/testing.md:114-117`): breaking
`Machine.descendant?/3` and breaking `Machine.document_order/2` will each
redden most of one suite, which is expected - those are genuine shared
foundations, not twenty doors onto one assertion.

## Performance Considerations

- **`Selection.compute_exit_set/2` is called once per `exit_states/2` over the
  whole transition list**, not per pair - the O(n^2) call pattern its own plan
  records lives inside `remove_conflicting_transitions/2`, which has already
  run by the time this bead sees a transition list. No new quadratic behavior
  is introduced here.
- **History recording is O(|exit set| x |configuration|)** because each history
  child filters the whole configuration. Both are small (a configuration is
  bounded by the state count, and history children are rare), and the
  alternative - indexing the configuration by parent - is a data structure the
  pseudocode does not have and ADR-0005 deliberately does not build. Recorded
  here so the decision is visible rather than rediscovered.
- **`covered?/3` scans `states_to_enter` per parallel region.** The pseudocode's
  `some(lambda s: isDescendant(s, child))` verbatim. `MapSet` membership does
  not help - the test is a range predicate, not equality - so this stays a
  linear scan over a set that is bounded by the entry set's size. If a document
  with very wide parallels ever makes it measurable, the fix is a range check
  against `child..last` over a sorted list, which is a local change inside one
  helper with a mechanical-reason comment.
- **The configuration is a `MapSet` of integers and every topology test is an
  integer range comparison** (ADR-0005), so exit sets, entry sets, and history
  values allocate nothing beyond the result sets.
- **Trace off allocates nothing**: `Effect.trace/3` reads one boolean field and
  returns `[]` without evaluating its `fields` expression, so neither
  `exit_order` nor `entry_order` is even materialized into a payload when
  tracing is off (they are computed regardless, because the algorithm needs
  them).

## Appendix D Deviations

Per ADR-0002 and `.claude/wurk/plan.md`'s Appendix D rule, these are the only
deviations this bead makes. Every one is mechanical, and every one carries an
inline comment at its site:

1. **`machine_state` is the first argument of every function** (st-wju.3's
   Decision 3, inherited). The pseudocode reads `configuration`,
   `historyValue`, and `running` as globals; ADR-0012 constraint 1 reifies them
   onto the struct. Semantics unchanged.
2. **`exit_states/2` and `enter_states/2` return `{machine_state, [effect]}`**
   (Decision 2). The pseudocode mutates globals and performs I/O; ADR-0003
   makes both a returned value. Semantics unchanged.
3. **The three `computeEntrySet` out-parameters become one threaded
   accumulator** (Decision 3), and `statesToEnter` /
   `statesForDefaultEntry` are `MapSet`s ordered at use by
   `Machine.document_order/2` (Decision 4). Elixir has neither out-parameters
   nor a mutable ordered set; membership and ordering are both preserved
   exactly.
4. **`defaultHistoryContent` maps to a `t_index` rather than a `[c_index]`**
   (Decision 5). Strictly more information, one lookup from the pseudocode's
   value, and the owner identity `Machine.Content.owner()` requires.
5. **`executeContent` is a private seam whose body st-wju.5 fills**
   (Decision 6). Call sites and ordering are the pseudocode's; only the body
   is deferred, exactly as `Selection.condition_match/2` defers `cond`
   evaluation to st-af3.
6. **`done.state.*` is enqueued through `MachineState.raise_platform/4`**
   (Decision 8) rather than a bare `internalQueue.enqueue`, so the event
   carries spec 5.10.1's `:platform` type and ADR-0012 constraint 4's cause
   metadata. Same queue, same order, same name.
7. **A `done.state.*` whose parent has no written id is not raised**
   (Decision 9). The pseudocode assumes `parent.id` exists; this codebase
   admits documents that omit it, and an unnamed state's completion is
   unobservable.
8. **`statesToInvoke`, `cancelInvoke`, and the `binding == "late"` datamodel
   initialization are skipped**, each with a comment naming st-cmq or st-af3 -
   the same deferrals `Statifier.MachineState`'s moduledoc already committed to.
9. **The recursive walks are decomposed into named private helpers**
   (Decision 12) to stay under Credo's complexity and nesting limits. Shape
   only; each helper names the pseudocode lines it covers.
10. **`isInFinalState` is `in_final_state?`** - ADR-0002's own 2026-08-09
    predicate amendment, not a deviation this plan invents; recorded here only
    because the `mix adr.check` interaction it causes (an ADR-citing comment on
    the `def`) is visible in the diff and would otherwise look like a
    suppression.

Nothing here alters which states are exited or entered, in what order, what is
recorded in history, or which completion events are raised.

## Open Questions

No human was available while this plan was written, so nothing here blocks
implementation: every question below is settled in the Decisions section and
the assumption is recorded so a reviewer can overturn it cheaply. These four
are the ones most worth a second opinion.

1. **Decision 8 - `done.state.*` goes through a new
   `MachineState.raise_platform/4` rather than `raise_internal/4`.** This
   departs from a sentence in `raise_internal/4`'s own `@doc` and from this
   bead's note, both of which name `raise_internal/4` as the `done.state.*`
   caller. The assumption made: those were written before anyone checked that
   `raise_internal/4` stamps `type: :internal`, while `Statifier.Event`'s
   moduledoc and spec 5.10.1 both classify `done.state.*` as `:platform`. If a
   reviewer prefers to honor the note as written, the change is one function
   call and one deleted function; the cost is a permanently misclassified event
   type that st-cmq and st-af3 both read.
2. **Decision 6 - content execution is a private stub seam rather than a
   dependency on st-wju.5.** The assumption made: st-wju.4 owning the ordering
   and st-wju.5 owning the runner is what the two beads' own texts describe,
   and the `condition_match/2` precedent makes a stubbed body the established
   way to fix a shape early. The cost, stated plainly in "Testing Strategy", is
   that this bead cannot assert content *ran* - only which states would have
   asked. If a reviewer would rather land st-wju.5 first and have this bead
   call the real runner, the phase structure survives unchanged; only the seam
   body and two ordering tests move.
3. **Decision 9 - an id-less compound parent raises no `done.state.*`.** The
   pseudocode has no such case because it assumes ids exist. The alternative
   considered and rejected: raise `done.state.` with an empty suffix, which is
   a name no transition can meaningfully match and which would put a
   nonsense event on the queue. A third option - making the validator reject an
   id-less compound state that contains a `<final>` - is a real design, but it
   belongs to the validator bead and would change which documents this engine
   accepts, so it is not taken here unasked.
4. **Decision 1 - one module for both halves.** A reviewer who wants
   `Statifier.Interpreter.Exit` and `Statifier.Interpreter.Entry` as separate
   modules gets a cleaner one-concern-per-file story at the cost of splitting
   one pseudocode section and of `enter_states` reaching across a module
   boundary into `compute_entry_set` on every call. The split is mechanical
   later if wanted; nothing in the phase structure depends on it.
