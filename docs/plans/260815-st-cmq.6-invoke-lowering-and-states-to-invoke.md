# `<invoke>` lowering and the statesToInvoke passes Implementation Plan

## Overview

Give `<invoke>` a producer. Today the element is a vocabulary without one:
`Statifier.Effect.Invoke` exists and is typed into the effect union, the
session already plans it, and five interpreter seams sit commented in the
pseudocode's own position - but nothing in `lib/` builds a `Document.Invoke`,
no `Machine.Invoke` exists, `<invoke>` is rejected as
`{:unsupported_element, "invoke"}`, and `states_to_invoke` is deliberately
absent from `%MachineState{}`.

This plan lands the **pure-core half**: document and machine shapes, lowering
and validation, `states_to_invoke` and the runtime invocation table on
`MachineState`, the Appendix D invoke passes inside `main_event_loop/1`,
cancel-invoke effects on both exit walks, `Effect.Invoke` (its field is
`state_index`, never `source`), and core-side finalize/autoforward selection.
Child sessions, `#_parent` routing, and actual delivery are st-cmq.7.

Beads issue: st-cmq.6

## Desired End State

A document containing `<invoke>` lowers, validates, and compiles. Entering a
state adds it to `machine_state.states_to_invoke`; exiting removes it. At the
end of every macrostep, `main_event_loop/1` walks `states_to_invoke` in entry
order and each state's invocations in document order, evaluates their
arguments, assigns each a spec-6.4.1-shaped invokeid, records it in
`machine_state.active_invocations`, and returns one
`{:invoke, %Effect.Invoke{}}` per invocation; then it clears
`states_to_invoke` and, if invoking left the internal queue non-empty,
re-enters the loop. Exiting a state - on a transition or at
`exit_interpreter/1` - returns one `{:cancel_invoke, %Effect.CancelInvoke{}}`
per live invocation of that state and forgets it. An external event carrying
an `invokeid` runs exactly the matching invocation's `<finalize>` inside the
core before transition selection, and every autoforwarding invocation gets a
`{:autoforward, %Effect.Autoforward{}}` carrying the event verbatim.

Verified by: `mix quality` green at every phase; new unit tests under
`test/statifier/` covering each of the above; `test/passing_tests.json`
unchanged (see Corpus/Ratchet Notes).

### Key Discoveries

- Appendix D puts `if not running: break` **before** the invoke pass
  (`appendix-d.txt:128-144`), so the pass belongs inside `main_event_loop/1`'s
  `running` branch, before the return.
- `statesToInvoke.sort(entryOrder)` is **in the pseudocode**, so storing a
  `MapSet` and sorting with `Machine.document_order/2` at the pass is a
  literal port, not a deviation - the same thing `enter_states/2` already does
  at `lib/statifier/interpreter/exit_entry.ex:600`.
- W3C mandatory test224 (`test/scxml_tests/mandatory/invoke/test224_test.exs`)
  asserts `starts_with(Var1, 's0.')` on an `idlocation`-generated invokeid.
  That is mechanical evidence for the composite id format (Decision 1).
- Spec 6.4 has a clause that overrides 5.6's generic empty-string rule for
  this context: "When the `<invoke>` element is executed, if the evaluation of
  its arguments produces an error, the SCXML Processor MUST terminate the
  processing of the element without further action."
- Spec 6.4 also collapses two of the four data channels: invoked services
  "MUST treat values specified by `<param>` and namelist identically" and
  "MUST also treat values specified by 'src' and `<content>` identically".
- ADR-0019's budget is scoped to `macrostep/1`'s fold; the post-invoke
  `continue` is a second, currently unbounded loop (Decision 8).
- ADR-0027 assigns the parent-held `invokeid -> {child_session_id, pid,
  monitor_ref}` table to st-cmq.7. The `active_invocations` map this plan adds
  is not that table - it is Appendix D's `inv.invokeid` hoisted off compiled
  data, holding no process identity at all.
- The validator has no warning tier (`lib/statifier/validator.ex` contract 3),
  which decides what 6.5's authoring constraints can and cannot become here.

## What We're NOT Doing

- **No child sessions.** No process starts, nothing is delivered, no
  `done.invoke.<id>` is generated, no `#_parent` or `#_invokeid` routing.
  st-cmq.7, planned against ADR-0027 decision 3.
- **No `<send>` or `<cancel>` element support.** st-cmq.3 / st-cmq.5.
- **No fetching of `src`/`srcexpr`.** The core resolves the URI to a string
  and carries it on the effect. Whether anything dereferences it is st-cmq.7's
  call; ADR-0031 says so explicitly rather than leaving ADR-0024's scope limit
  hanging.
- **No 6.5 "`<send>` and `<raise>` MUST NOT occur inside `<finalize>`"
  check.** The validator has no warning tier, so expressing this would mean
  rejecting documents - a conformance constraint on *authors* turned into an
  engine refusal. Recorded here rather than silently skipped; revisit if a
  warning tier ever lands.
- **No duplicate-child check** for a second `<content>` or `<finalize>` under
  one `<invoke>`. `place/3` overwrites, exactly as it already does for a
  second `<content>` under `<donedata>`; parity with the existing precedent
  beats a new one-off check.
- **No new trace effect** for the invoke pass. ADR-0012 constraint 2 would
  permit a `Trace.InvokeSet` row, but `Effect.Invoke` is a *core* effect and
  is therefore already visible with `trace: false`; a trace row would be
  additive observability with no caller. Out of scope by choice, not oversight.
- **No `FeatureDetector` reclassification** and no ratchet movement. See
  Corpus/Ratchet Notes.
- **No injectable invokeid generator.** The invoke pass calls
  `UXID.generate!/1` inside the core, exactly as `MachineState.new/2` already
  does for `sess_`, so the ADR-0003 purity story is unchanged in kind. It does
  make one thing newly non-deterministic that ADR-0029's replay cares about:
  with `idlocation`, the generated id lands in the datamodel where a `cond`
  can read it (W3C test224 does precisely that), so re-driving the core from
  an event log re-derives a *different* id. The fix has the same shape as the
  one already in place for `_sessionid` - an option on `MachineState.new/2`
  that a recorder pins - but adding it now would be mechanism with no caller,
  and there is no recorder until st-dtm. Named here so st-dtm inherits a
  recorded gap rather than discovering a silent one.
- **No `origin`/`sendid` on `Statifier.Event`.** `invokeid` gets added because
  this bead is its first reader; the other two still have no caller and stay
  out under the same standing rule.

## Implementation Approach

Nine phases, split along the pipeline's module boundaries (parser/lowering ->
compiler -> interpreter), each independently committable and gate-verifiable
with a full unscoped `mix quality`.

The four questions the research document flagged as possibly ADR-shaped are
answered here, with the two that genuinely need a record scoped into Phase 1
rather than decided in passing.

**One gate hazard applies to every phase that edits an existing seam
comment.** All five seams currently end in "st-cmq.", and
`Mix.Statifier.AdrGuard`'s `adr-0018-bead-id` check fails on a bead ID added
to a comment, `@moduledoc`, `@doc`, `@typedoc` or test description on an
*added* diff line. Rewriting a seam comment re-adds it as a new line, so every
rewritten comment must drop the bead ID and cite an ADR number instead
(ADR-0018's rule that ADR numbers are the durable citation form). The same
applies to the new tests' descriptions and to every sabotage line.

**Each phase's manual criteria carry the extension's spec-conformance
judgment.** For Phases 5-8 that is Appendix D line for line, as the extension
states. For Phases 2-4, which touch `lib/statifier/` at points Appendix D does
not describe at all - lowering, compilation, the `<assign>` write - the
normative clause stands in for the pseudocode and is named per phase.

### Decision 1: the generated invokeid is `"<stateid>." <> UXID(inv)`

Spec 6.4.1: "The automatically generated identifier MUST have the form
stateid.platformid, where stateid is the id of the state containing this
element and platformid is automatically generated. platformid MUST be unique
within the current session." Spec 3.14 adds that for `<invoke>` the processor
generates it "not at load time but each time the element is executed".

W3C mandatory test224 asserts exactly this against a `predicator`
`starts_with(Var1, 's0.')`, so a bare `inv_01J...` would leave a mandatory
test permanently red - the same shape of evidence ADR-0021 weighted first.

**The invokeid is `state.id <> "." <> UXID.generate!(prefix: "inv")`**, and
the bare `inv_` UXID when the state has no `id` (this engine leaves
`Machine.State.id` `nil` for an anonymous state rather than synthesizing one
at load time; there is then no `stateid` for the composite and uniqueness is
all that remains of the MUST). An author-written `id` attribute is used
verbatim and never composed - ADR-0008's "document-authored IDs are always
respected".

This is a narrow amendment to ADR-0008, which reads "All generated
identifiers are UXIDs with a stable prefix per kind": an invoke's is a UXID
with a state-id qualifier in front of it. It also needs ADR-0008's "generated
once at the owning entity's creation and immutable for its lifetime" read
against 3.14: the owning entity of an invokeid is the **invocation**, not the
`<invoke>` element, so a state entered twice invokes twice and gets two ids,
each immutable for its own invocation's life. Phase 1 writes that amendment
in place, in the same dated form ADR-0002 and ADR-0030 already use.

### Decision 2: argument-evaluation failure aborts the invocation (ADR-0031)

ADR-0021's scope limit is explicit that `<content>` under `<invoke>` "must
answer the 5.6 question for their own context rather than inherit this
answer, and the default expectation there is the opposite" - 5.6's empty
string. ADR-0024's scope limit says the same about fetching `src`.

Spec 6.4 answers both with a clause neither ADR considered: "When the
`<invoke>` element is executed, if the evaluation of its arguments produces an
error, the SCXML Processor MUST terminate the processing of the element
without further action." That is neither ADR-0021's `nil` nor 5.6's `""` - the
question of what value a failed `<content>` contributes does not arise,
because there is no invocation to contribute it to. 5.9.1/5.9.3 still require
`error.execution` on the internal queue, and Appendix D's own comment on the
post-invoke re-check ("Invoking may have raised internal error events and we
iterate to handle them") confirms that is the intended interaction.

**So: any failure while evaluating `typeexpr`, `srcexpr`, `idlocation`, a
`<param>` expr or location, a namelist location, or `<content expr>` raises
`error.execution` via `MachineState.raise_platform/4` with origin
`{:invoke, state_index, invoke_index}`, and no `Effect.Invoke` is produced for
that invocation.** Sibling invocations of the same state are unaffected -
6.4's MUST is scoped to "the element". This is a third answer to ADR-0021's
open question, not the amendment it anticipated, so it gets its own record
(ADR-0031) that also closes ADR-0024's `<invoke>`-shaped scope limit by
stating that the core never dereferences `src` and that st-cmq.7 owns whether
anything else does.

### Decision 3: the cancel-invoke effect

**A new core effect, `{:cancel_invoke, %Statifier.Effect.CancelInvoke{}}`,
one per live invocation**, with `@enforce_keys [:invoke_id, :state_index,
:macrostep, :microstep]` and exactly those four fields.

- One per invocation, not one per state carrying a list: Appendix D is
  `for inv in s.invoke: cancelInvoke(inv)`, one call per invocation, and every
  other effect in the vocabulary is one-per-action.
- `invoke_id` and `state_index` both: the session resolves the child by
  invokeid (ADR-0027 decision 3), and `state_index` is the constraint-3
  identity every other state-attached effect carries.
- **No `round` field.** No core effect has one; all seven trace payloads do.
  Consistency with the half of the vocabulary this belongs to.
- Not `Effect.Cancel`: that struct is spec 6.3's `<cancel sendid>`, its
  moduledoc says so, and its session plan drives `Timers.take/2` on a table
  keyed by `send_id` that has no notion of an invocation.

`Session.Effects.plan_one/1` gains `[{:notify, effect}, {:unroutable,
effect}]`, matching what `:invoke` already gets, and `lib/statifier/session.ex:52`'s
list of what `:unroutable` covers grows two members. st-cmq.7 replaces both
plans with real work.

### Decision 4: invocations are structs on `Machine.State`, attached in the post-interning pass

`Document.State` gains `invoke: [Document.Invoke.t()]` and `Machine.State`
gains `invoke: [Machine.Invoke.t()]` - inline structs, mirroring `donedata`,
not interned indexes. Nothing outside the owning state ever refers to an
invocation by index, which is the criterion ADR-0005 uses.

Attachment mirrors `with_donedata/2`: a `with_invoke/2` in the same `Enum.map`
over `0..root_last`. The one difference from donedata, and the reason to note
it in a comment: an invocation's `<finalize>` is executable content, so its
`Machine.Block` must be built by `assign_blocks/2` **during** `walk_siblings/4`
where the `c_index` accumulator is threaded. So `Machine.Invoke` structs are
built complete in the walk (the state's own index is in hand there) and
accumulated into `acc.invoke_acc`; `with_invoke/2` only attaches them.

### Decision 5: `states_to_invoke` is an unconditional `MapSet` of state indexes

Appendix D declares `statesToInvoke = new OrderedSet()`, adds unconditionally
in `enterStates` (`statesToInvoke.add(s)` with no test for `s.invoke`),
deletes in `exitStates` before the exit set is sorted, and **sorts by entry
order at the pass itself**.

Because the sort is in the pseudocode, a `MapSet.t(non_neg_integer())` plus
`Machine.document_order/2` at the pass is the literal port - the same pattern
`configuration` uses everywhere and `enter_states/2` uses at
`lib/statifier/interpreter/exit_entry.ex:600`. **This is not an ADR-0002
deviation and needs no record.**

Population is unconditional, for `entered_states`'s stated reason: a field
whose contents depend on whether the document happens to carry `<invoke>`
children has a meaning a reader cannot state without the document in hand,
and ADR-0012 constraint 1 wants an inspectable position. The cost of a state
with no invocations is one `MapSet` member and one empty inner loop, which is
where Appendix D already puts it.

### Decision 6: finalize runs inside the pure core; autoforward is an effect

Appendix D's pass runs `applyFinalize(inv, externalEvent)` and
`send(inv.id, externalEvent)` in the same loop, in `handle_event/2`'s
position, before `selectTransitions`.

These two halves fall on opposite sides of ADR-0003's line and are split
accordingly:

- **`applyFinalize` runs in the core.** `<finalize>` contains ordinary
  executable content, which this core already runs purely via
  `Interpreter.Content.execute_block/3`; 6.5 bans `<send>` and `<raise>`
  inside it, so nothing impure can appear there in a conformant document, and
  its whole purpose is to mutate the datamodel *before* transition selection -
  a mutation the session cannot perform on a `%MachineState{}` it does not
  own. Deferring it would change observable transition selection, which is a
  semantic deviation with no mechanical reason. It executes with
  `Content.owner()` arm `{:finalize, state_index, invoke_index}` and ADR-0028's
  one-context-per-block contract, unchanged.
- **`send(inv.id, externalEvent)` is an effect.** A new
  `{:autoforward, %Statifier.Effect.Autoforward{}}` carrying `invoke_id`,
  `state_index`, the `event` verbatim, and the counters. It is deliberately
  *not* an `Effect.Send` with `target: "#_" <> invoke_id`: 6.4 requires an
  exact copy - "All the fields specified in 5.10.1 ... MUST have the same
  values in the forwarded copy" - and `Effect.Send` describes an event to be
  *built* from `<send>` attributes, which would lose `sendid`, `origin` and
  `invokeid` on the way through. Carrying the event verbatim is the only shape
  that can satisfy the MUST.

**Neither half needs a new ADR**; both follow from ADR-0002 (port the loop as
written), ADR-0003 (the pure/effect line), and ADR-0028 (block context).

Two literal properties of the pseudocode loop the port must keep: it iterates
the **full** configuration (which `MachineState.configuration` already is,
ADR-0005), and the `autoforward` test is **not** in the `else` of the
invokeid test - an invocation that matches *and* autoforwards does both.

### Decision 7: `active_invocations` is `inv.invokeid` hoisted off compiled data

The finalize pass needs `inv.invokeid`, and the cancel walks need the live
invokeid of each of an exiting state's invocations. Appendix D stores that on
the invocation object; `Machine.Invoke` is immutable compiled data, so it is
hoisted onto `%MachineState{}` as

```elixir
active_invocations: %{{state_index, invoke_index} => invoke_id}
```

keyed to match the pseudocode's own access pattern - `for inv in s.invoke`
walks the compiled list in document order and looks each one up, so document
order comes from the compiled list and never from map iteration. Entries are
written by the invoke pass and deleted by the cancel walks.

This is an ADR-0002 mechanical deviation of exactly the shape `entered_states`
already declares (`lib/statifier/machine_state.ex:43-66`), and its moduledoc
section cites that precedent rather than re-arguing it. It is **not**
ADR-0027 decision 3's parent-held table: it holds no pid, no monitor ref, and
no child session id, and the session's table keyed by invokeid is built on top
of it in st-cmq.7.

It is added in Phase 6, with its first writer, not in Phase 5 alongside
`states_to_invoke` - the same standing rule that kept `states_to_invoke` off
the struct until this bead applies to it.

### Decision 8: the round budget spans the invoke re-entry (ADR-0032)

Appendix D's post-invoke `continue` re-enters the outer `while running` body.
In this port `main_event_loop/1` **is** that body, so `continue` is a
self-call - and a self-call re-enters `macrostep/1`, which today starts a
fresh `max_macrostep_rounds` budget every time.

That reopens exactly the hole ADR-0019 closed. Two states whose `<invoke>`
arguments deterministically error can hand each other control forever:
each macrostep terminates within budget, each invoke pass raises
`error.execution`, the re-check sees a non-empty internal queue and loops, and
the pure core has no external entity to cancel it - ADR-0019's Context
verbatim, one loop further out.

**The budget is therefore spent across the whole `main_event_loop/1` call**,
threaded through a new private `main_event_loop/3` exactly as it is already
threaded through the private `macrostep/3`, with `{:budget_exhausted,
%Effect.BudgetExhausted{}}` on exhaustion. Nothing else about ADR-0019 changes:
the field, the default, `:infinity`, the effect, and the "a later
`handle_event/2` starts fresh" rule all stand.

ADR-0019's Decision says "each `microstep/1` call within one fold consumes one
round" and its consequences say a later `handle_event/2` gets a fresh budget -
both true of a single fold, and both silent about a second fold inside one
call. Narrowing "per fold" to "per `main_event_loop/1` call" is an amendment,
so Phase 1 writes ADR-0032 in the house's amends-in-part form rather than
editing ADR-0019's Decision silently.

### Decision 9: `Effect.Invoke` gains `content`; namelist folds into params

`Effect.Invoke`'s moduledoc already reserves the right ("The
not-yet-implemented invoke/session support may add fields to this payload once
it exists"). It gains exactly one field, `content`, because 6.4 makes
`<content>` and `src` two forms of the same channel ("MUST also treat values
specified by 'src' and `<content>` identically") and they cannot share one
field: `src` is a URI to dereference, `content` is markup or a value already
in hand.

`namelist` gets **no** effect field. 6.4 says the two must be treated
identically ("these services MUST treat values specified by `<param>` and
namelist identically"), and 6.5's empty-finalize rule treats a namelist item
and a `<param location>` identically too. So each namelist entry lowers to a
`Machine.Param{kind: :location}` and both lists coerce through the one shared
`Statifier.EventData.coerce({:params, pairs})` ladder into `params`. They stay
two fields on `Machine.Invoke` only so the validator can enforce 6.4.1's
"namelist Must not occur with the `<param>` element" and so the empty-finalize
auto-assign can find the write targets.

## Phase 1: The three architecture decisions

### Overview

Write the two new records and the one in-place amendment the rest of the plan
depends on, correct the bead's stale line numbers, and change no Elixir. This
is direction-level work per `docs/workflow.md`; the records are drafted here
and their acceptance is a human's call, which is why nothing downstream reads
them mechanically.

### Changes Required:

#### 1. ADR-0031

**File**: `docs/adr/0031-invoke-argument-failure-aborts-the-invocation.md`
**Changes**: New record in the house's three-section form. Context quotes
6.4's "terminate the processing of the element without further action",

budget (Decision 8 / ADR-0032):

```elixir
defp main_event_loop(machine_state, effects, budget) do
  {outcome, machine_state, macrostep_effects, budget} =
    macrostep(machine_state, [], budget)

  if machine_state.running do
    # for state in statesToInvoke.sort(entryOrder):
    #     for inv in state.invoke.sort(documentOrder): invoke(inv)
    # statesToInvoke.clear()   (Appendix D)
    {machine_state, invoke_effects} = run_invoke_pass(machine_state)
    effects = effects ++ macrostep_effects ++ invoke_effects

    # if not internalQueue.isEmpty(): continue (Appendix D). This port's
    # loop body is a function, so `continue` is a self-call; ADR-0032 is
    # why the budget crosses it instead of restarting.
    cond do
      MachineState.internal_queue_empty?(machine_state) ->
        {machine_state, effects ++ terminal_effects(machine_state, outcome)}

      budget == 0 ->
        {machine_state, effects ++ terminal_effects(machine_state, :budget_exhausted)}

      # `continue` (Appendix D)
      true ->
        main_event_loop(machine_state, effects, budget)
    end
  else
    ...
  end
end
```

Three mechanical changes make that work, stated precisely because the
existing exhaustion machinery has to move rather than be duplicated:

1. **The private `macrostep/3`'s return grows a fourth element.**
   `{outcome, machine_state, effects}` becomes
   `{outcome, machine_state, effects, rounds_left}`. Nothing else about the
   fold changes: it still spends one round per `microstep/1` call and still
   returns `:quiescent`, `:done` or `:budget_exhausted`.
2. **Public `macrostep/1` keeps its arity, signature and behavior**, by
   discarding the new element:
   `{outcome, ms, effects, _rounds_left} = macrostep(ms, [], ms.max_macrostep_rounds)`
   then `{ms, effects ++ terminal_effects(ms, outcome)}`. Every existing
   caller and every existing test is untouched.
3. **`terminal_effects/2` moves from the fold to the loop: exactly one
   terminal effect per `main_event_loop/1` call.** `main_event_loop/3` calls
   the private `macrostep/3` directly with the budget it is carrying, and
   appends `terminal_effects/2` **once**, when it stops looping - from the
   last fold's `outcome`, or from `:budget_exhausted` when the loop wanted to
   re-enter and `rounds_left` was `0`. Intermediate folds contribute no
   terminal row.

That third change is what keeps ADR-0019's "the three macrostep outcomes
(stable, done, budget-exhausted) stay mutually exclusive per macrostep"
true across a re-entry, and it answers the two cases the arrangement raises:

- **A fold that reaches `:quiescent` on the very round the budget runs out,
  with the internal queue left non-empty by invoking.** The loop wants to
  re-enter and cannot, so the one terminal effect is
  `{:budget_exhausted, _}` and no `Trace.MacrostepStable` is emitted - the
  configuration did not stabilize, it ran out of road, which is ADR-0019's
  own stated reason for suppressing that row.
- **What `Effect.BudgetExhausted.budget` reports.** Unchanged:
  `machine_state.max_macrostep_rounds`, the budget that was granted. Its
  meaning is not edited by ADR-0032 - only its scope, from "per fold" to
  "per `main_event_loop/1` call", which is the amendment itself.

For a document with no `<invoke>` the loop runs exactly one fold and emits
exactly one terminal effect, which is byte-identical to today's behavior;
that equivalence is what the existing macrostep and budget suites prove when
they pass unchanged.

`MachineState` gains an `internal_queue_empty?/1` predicate (the current
public reader is `internal_events/1`, which materializes a list).

`run_invoke_pass/1` per invocation, in
`ExitEntry.evaluate_donedata_params/3`'s idiom - one `Evaluator.context/1`
built for the pass and threaded:

1. Resolve `type` and `src` (static or compiled).
2. Resolve `params` and `namelist` and coerce with
   `EventData.coerce({:params, pairs})`; resolve `content` with
   `EventData.coerce({:value, v})` or `{:text, t}`.
3. Any `{:error, reason}` in steps 1-3 raises `error.execution` via
   `MachineState.raise_platform(machine_state, "error.execution", {:invoke,
   state_index, invoke_index}, data: reason)` and produces **no effect for
   this invocation** - ADR-0031, cited in the comment rather than re-argued.
4. Otherwise: `invoke_id` is the author's `id`, or
   `"#{state.id}.#{UXID.generate!(prefix: "inv")}"`, or the bare UXID when the

## Performance Considerations

Two loops run per event on documents that contain no `<invoke>` at all:

- The invoke pass walks `states_to_invoke`, which is every entered state. Its
  inner loop is over `state.invoke`, empty for every such state, so the cost
  is one `MapSet` sort per macrostep - the same shape `enter_states/2` already
  pays.
- The finalize/autoforward pass walks the full configuration per external
  event. This one is short-circuited when `active_invocations` is empty
  (Phase 8), which is observationally identical rather than an optimization
  that changes behavior, and is commented as such.

Neither is on a path that grows with document size beyond what the existing
entry and exit walks already do.
