# SCION Emitter: v2 Test Shape Implementation Plan

## Overview

Rewrite `tools/corpus/scion/cases.exs` so it emits `test/scion_tests/` modules in
the v2 shape (`Statifier.Case`) instead of the current v1/`ex_statechart`
(`Test.StateChart.Case`) shape. This is the last blocker before `mise run corpus`
is safe to run end to end - the W3C emitter side already produces v2-shaped
modules (st2-00p.7/`47f4a25`); the SCION side still does not compile against v2.

Beads issue: st2-00p.6.

## Current State Analysis

- `tools/corpus/scion/cases.exs` (28 lines) emits `Test.StateChart.Scion.*`
  modules using `use Test.StateChart.Case`, `@tag :scion`, `@tag spec:` - the
  ex_statechart shape, seeded verbatim and never updated (file header even says
  so at line 9-10).
- Input: `<in_root>/<spec>/<name>.json` + sibling `.scxml`, where `<in_root>` is
  the SCION `scxml-test-framework` checkout (`CORPUS_SCION_CASES`,
  `mise.toml:35`). JSON shape (confirmed against
  `jbeard4/scxml-test-framework` sources, mirrored in
  `../ex_statechart/test/scion/cases/**/*.json`):

  ```json
  {
    "initialConfiguration": ["a"],
    "events": [
      {"event": {"name": "t"}, "nextConfiguration": ["b"]},
      {"after": 100, "event": {"name": "t2"}, "nextConfiguration": ["e"]}
    ]
  }
  ```

  `event` is already a `%{"name" => ...}` map - the exact shape
  `Statifier.Case.test_scxml/4`'s `events :: [{map(), [String.t()]}]` wants, so
  the existing `Enum.map(events, fn %{"event" => e, "nextConfiguration" => conf}
  -> {e, conf} end)` extraction needs no change. A map pattern with only
  `"event"`/`"nextConfiguration"` matches fine against entries that also carry
  `"after"` - delayed-send timing is silently dropped today and that is a
  pre-existing scope limit, not something this issue fixes (see "What We're NOT
  Doing").
- Upstream directory/file names are not always valid Elixir identifiers:
  `more-parallel`, `hierarchy+documentOrder`, `deep-initial` all appear
  (confirmed via `../ex_statechart/test/scion/cases`, which mirrors the same
  upstream). The current code only replaces `-` in the *spec* dir
  (`String.replace(spec_dir, "-", "_")`) and never normalizes `name`, so
  `Macro.camelize("deep-initial")` produces the invalid identifier
  `Deep-initial`, which `ex_statechart`'s own output confirms
  (`misc/deep-initial_test.exs` defines `defmodule :"Elixir...Deep-initial"`) -
  a bug we are not inheriting.
- **Reference for the target shape**: `../statifier/test/scion_tests/` (v1's
  committed, already-v2-shaped output - e.g.
  `../statifier/test/scion_tests/misc/deep_initial_test.exs`,
  `../statifier/test/scion_tests/more_parallel/test6b_test.exs`). This is the
  literal target to match: module `SCIONTest.<Spec>.<Name>Test`, file
  `<spec_underscored>/<name_underscored>_test.exs`, `use Statifier.Case`,
  `@tag :scion` (v1's; this repo's W3C emitter and the bd acceptance criteria
  use `@moduletag :scion` instead - functionally equivalent for
  `ExUnit.start(exclude: [:scion, :scxml_w3])` in `test/test_helper.exs:1`, and
  the form to follow here), `@tag required_features: [...]`, `@tag spec:
  "<original_spec_dir>"`, inline XML heredoc with the **raw source `.scxml`
  content unmodified, each line prefixed by the 4-space heredoc base indent**
  (no xmerl re-serialization - unlike the W3C emitter, SCION's `.scxml` sources
  are already clean), and `test "<original name>" do ... test_scxml(xml, "",
  config, events) end` where the *test name* keeps the original hyphenated
  name (`"deep-initial"`) even though the *module/file* name is normalized.
- `tools/corpus/scxml_w3/cases.exs` (st2-00p.7, done) is the sibling precedent
  for every v2-specific piece needed here:
  - `Code.require_file(Path.join([__DIR__, "..", "..", "..",
    "test/support/feature_detector.ex"]))` - required because this repo's
    `test/support/` is only compiled under `MIX_ENV=test`, and the SCION
    emitter is invoked via `mix run` (`mise.toml:145`), which defaults to
    `MIX_ENV=dev`. `mix run` still loads `lib/` normally, so
    `Statifier.FeatureDetector` (test/support-only) is the only piece missing;
    plain `elixir` (the W3C emitter's approach) is not needed here since SCION
    parsing needs no `xmerl`.
  - `Statifier.FeatureDetector.detect_features/1` -> sorted, `inspect`-joined
    list for `@tag required_features: [...]`.
  - `Code.format_string!/1` piped through `IO.iodata_to_binary/1` and a
    trailing newline, matching the "mix format clean" acceptance criterion
    without a separate `mix format` pass.
- `Statifier.FeatureDetector.feature_registry/0` currently marks every feature
  `:unsupported` (test/support/feature_detector.ex:44-78), so `test_scxml/4`
  flunks on `validate_features!/2` for essentially every case regardless of the
  document's declared `datamodel`. SCION `.scxml` sources declare
  `datamodel="ecmascript"` (confirmed in `test6b.scxml` etc.), which the
  project's predicator commitment (docs/datamodel.md) does not accept - but
  that mismatch is invisible to the emitter and to `mix quality` today: the
  feature gate flunks first. No W3C-style datamodel filter or
  `exclusions.exs` is needed for the SCION side; the bd acceptance criteria
  does not ask for one, and there is no per-case datamodel variant to filter
  the way txml's `conf:` transforms produce for W3C.
- `tools/corpus/scratch/` is gitignored and not present in this worktree; the
  first verification run needs `mise run corpus:fetch:scion` (and the deps it
  needs - none beyond the SCION clone).

### Key Discoveries

- `Statifier.Case.test_scxml/4` spec (test/support/case.ex:54-59) already
  matches the SCION JSON's per-event shape one-for-one; the rewrite is purely
  about the emission side (module/file naming, tags, XML heredoc format), not
  the JSON parsing/extraction logic.
- The identifier-normalization gap (hyphens/`+` in spec and name) is the one
  correctness bug in the current script beyond the shape itself, and v1's
  committed output (`more_parallel`, `hierarchy_documentOrder`,
  `deep_initial_test.exs`) is direct evidence of the expected normalization:
  replace every run of non-alphanumeric characters with `_` in both `spec_dir`
  and `name` before building the module and the output path, but keep the
  original (unnormalized) string for the `@tag spec:` value and the `test`
  block's description string.

## Desired End State

`tools/corpus/scion/cases.exs` emits one `Statifier.Case`-based module per
SCION JSON case, matching `../statifier/test/scion_tests/` in shape byte-for-byte
modulo the `@moduletag`/`@tag` choice noted above. Running:

```bash
mise run corpus:fetch:scion
find "$CORPUS_SCION_CASES" -type f -iname '*.json' -print0 | sort -z | xargs -0 \
  mix run tools/corpus/scion/cases.exs test/scion_tests "$CORPUS_SCION_CASES"
```

populates `test/scion_tests/<spec>/<name>_test.exs` for all ~127 SCION cases,
every file `mix format`-clean, every module compiling under v2 (tests run and
flunk on undetected/unsupported features via `Statifier.Case`, they do not
raise `UndefinedFunctionError` or fail to compile). At that point `mise run
corpus` (the full fetch+transform+emit pipeline, W3C and SCION together) runs
end to end without error - the current blocker noted in
`tools/corpus/README.md`'s Status section is resolved.

Verify with:

1. `mise run corpus:emit` (or the manual command above) completes with no
   crash and file count matches JSON case count.
2. `mix quality` is green (format, compile, credo, dialyzer, deps audit, full
   suite - the new/regenerated files must not break `mix format` or `mix
   compile --warnings-as-errors` if configured).
3. `mix test --include scion` runs every emitted module and every one flunks
   cleanly on `Statifier.FeatureDetector`-named unsupported features (none
   raise, none silently pass) - expected, since the engine does not exist yet.
4. Spot-diff a handful of emitted files against
   `../statifier/test/scion_tests/` for shape (module name, tags, XML
   indentation, `test_scxml/4` call).

## What We're NOT Doing

- Not fixing delayed-send (`"after"`) timing semantics in
  `Statifier.Case`/`test_scxml/4` - the JSON's `after` field stays unread, same
  as today's script. That is an engine/harness capability gap (delayed send
  isn't implemented), not an emitter shape problem.
- Not adding a datamodel filter or `exclusions.exs` equivalent for SCION - see
  Current State Analysis; the feature-detector gate already makes every case
  flunk safely regardless of `datamodel="ecmascript"`, and no bd acceptance
  criterion asks for a filter.
- Not touching `tools/corpus/scxml_w3/*` - it already emits the v2 shape
  (st2-00p.7).
- Not implementing the actual Phase 1/2 engine (`Statifier.parse/1`, etc.) -
  `test/support/case.ex`'s four helpers stay `flunk`-stubs; this issue only
  makes SCION test files exist and compile in the v2 shape.
- Not building the committed exclusion manifest with reasons (st2-00p.8) or
  the snake_case/PascalCase path normalization issue (st2-yo4) - both are
  downstream of this one and out of scope here, though the identifier
  normalization this plan adds is exactly what st2-yo4 will build on, not
  duplicate.
- Not running `mix test.baseline add` to ratchet any SCION tests into
  `test/passing_tests.json` - nothing can pass yet (feature registry is all
  `:unsupported`), so the ratchet stays empty for this suite until an engine
  phase lands.

## Implementation Approach

Single-file rewrite of `tools/corpus/scion/cases.exs`, modeled directly on the
already-landed `tools/corpus/scxml_w3/cases.exs` for every v2-specific piece
(feature-detector loading, tag/heredoc emission, `Code.format_string!`), and on
`../statifier/test/scion_tests/*` for the exact target shape. One phase is
enough - this is a single self-contained script with no library-side surface
and no interpreter/parser work, so there is no natural module boundary to
split it across.

## Phase 1: Rewrite the SCION emitter

### Overview

Replace the ex_statechart-shaped emission in `tools/corpus/scion/cases.exs`
with the v2 `Statifier.Case` shape, add identifier normalization for spec/name,
and update `tools/corpus/README.md`'s Status section to reflect the change.

### Changes Required:

#### 1. `tools/corpus/scion/cases.exs`

**File**: `tools/corpus/scion/cases.exs`
**Changes**: Full rewrite. Key pieces:

- Drop the stale header comment (lines 9-10) noting the shape is still
  ex_statechart's.
- `Code.require_file(Path.join([__DIR__, "..", "..", "..",
  "test/support/feature_detector.ex"]))` at the top, matching
  `scxml_w3/cases.exs:26`.
- Normalize both `spec_dir` and `name` for the module/path: a small helper
  (e.g. `normalize/1`) that replaces every run of non-alphanumeric characters
  with `_`, then `Macro.camelize/1`s the result for the module segment. Keep
  the *un*-normalized `spec_dir` and `name` around for the `@tag spec:` value
  and the `test` description string, respectively.
- Build `module = Module.concat(["SCIONTest", Macro.camelize(normalized_spec),
  Macro.camelize(normalized_name) <> "Test"])` (note: `scxml_w3/cases.exs`
  does not append `Test` to the module name - confirm against
  `../statifier/test/scion_tests` which does: `SCIONTest.Misc.DeepInitialTest`
  - so the SCION emitter's module suffix differs from the W3C one
  intentionally, matching the reference).
- Read the JSON exactly as today (`initialConfiguration`, `events` extraction
  unchanged - see Current State Analysis, no logic change needed there).
- Read the sibling `.scxml` file's raw content, and build the heredoc body by
  prefixing every line with 4 spaces (`String.split(xml, "\n") |>
  Enum.map_join("\n", &("    " <> &1))`), no xmerl parsing. Guard the same
  `\` / `#{` escaping the W3C emitter does (`scxml_w3/cases.exs:141-142`) in
  case any SCION fixture contains those characters literally in a `log expr`
  or similar.
- Compute `features = xml |> Statifier.FeatureDetector.detect_features() |>
  Enum.sort() |> Enum.map_join(", ", &inspect/1)` over the raw (unindented)
  source XML.
- Emit via a `source = """ ... """` string (not `quote`/`Macro.to_string`,
  matching `scxml_w3/cases.exs`'s approach so the heredoc/formatting is
  under direct control rather than going through `Macro.to_string`'s
  reformatting of heredocs):

  ```elixir
  defmodule #{inspect(module)} do
    use Statifier.Case

    @moduletag :scion
    @tag required_features: [#{features}]
    @tag spec: #{inspect(spec_dir)}
    test #{inspect(name)} do
      xml = \"\"\"
  #{xml_body}\"\"\"

      test_scxml(xml, "", #{inspect(conf)}, #{inspect(events)})
    end
  end
  ```

  (adjust escaping/formatting details to match `scxml_w3/cases.exs`'s working
  pattern exactly; use `Code.format_string!/1` afterward so exact spacing of
  the tuple/list literals is not hand-maintained.)
- Write via `File.write!(out, Code.format_string!(source) |>
  IO.iodata_to_binary() |> Kernel.<>("\n"))`, matching
  `scxml_w3/cases.exs:166`.
- Output path: `Path.join([out_root, normalized_spec, normalized_name <>
  "_test.exs"])`.

## Testing Strategy

### Unit Tests:
None planned - this is a code-generation script with no `lib/` surface and no
sabotage-testable behavior of its own (its correctness is verified by
inspecting its generated output, per the Automated/Manual Verification above).
No new `test/statifier/` file is warranted.

### Conformance Tests:
No SCION test enters `test/passing_tests.json` in this phase - the feature
registry marks everything `:unsupported`, so nothing can pass yet. Once an
engine phase lands and some SCION tests start passing, `mix test.baseline add`
ratchets them in at that time, not here.

### Manual Testing Steps:
1. Run `mise run corpus:fetch:scion`, then the emit command from Desired End
   State, and confirm the file count and shape as listed under Success
   Criteria.
2. Diff a sample of emitted files against `../statifier/test/scion_tests/`.
3. Run `mix test --include scion` and read the failure output to confirm every
   failure names an unsupported feature (no crashes, no compile errors, no
   unexpected passes).

## Performance Considerations

None - this is a one-time/regenerate-on-demand code generator over ~127 small
JSON+XML files; runtime is not a concern.

## Corpus/Ratchet Notes

No `passing_tests.json` changes in this phase (see Testing Strategy). The
`tools/corpus/README.md` Status section update (Phase 1, change 2) is the only
corpus-documentation change.
