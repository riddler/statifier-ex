# `<if>`/`<elseif>`/`<else>` - Implementation Plan

## Overview

Add `<if>`/`<elseif>`/`<else>` as an executable-content element: a new
`Statifier.Document.If` node whose children lowering partitions into ordered
branches, a `Statifier.Machine.Content.If` struct with its
`Statifier.ExecutableContent` implementation in the same file, dense
document-order `c_index`es for the nodes *inside* the partitions, and a runtime
that evaluates branch conds in document order and runs the first true branch's
partition through the same protocol dispatch the block runner uses.

One thing this element needs that no shipped element needed: spec 5.9.1 makes a
failed `cond` **non-fatal** - the expression is treated as `false` *and*
`error.execution` is queued, and the `<if>` keeps scanning. The current
executable-content contract has only a fatal channel (`{:error, reason}` halts
the block). Phase 1 adds the missing non-fatal channel to the protocol, the
context, and the runner, as a general mechanism rather than an `<if>`-shaped one;
`<foreach>` (st-af3.6) and the `<send>` family will reuse it.

Beads issue: `st-af3.5`. There is no research document for this bead; the
research this plan rests on is st-af3.4's
(`docs/research/260813-st-af3.4-assign-deep-path-vivification.md`), which
documents the whole executable-content pipeline, plus the direct reading
recorded under "Key Discoveries".

## Current State Analysis

- The parser is element-agnostic; the allowlist is one map at
  `lib/statifier/lowering.ex:53-69`. `<if>`, `<elseif>` and `<else>` parse today
  and are rejected one layer later as `{:unsupported_element, _}`.
- `lib/statifier/machine/content.ex:11-20` names `<if>`/`<elseif>`/`<else>`
  first among the future nodes and states the contract: each gets "its own
  struct here too, and its own `Statifier.ExecutableContent` implementation,
  never a clause added to this module". `lib/statifier/executable_content.ex:9-12`
  says the same.
- `docs/architecture.md:104-114`: "`Statifier.Interpreter.Content` is the block
  runner [...] and is the only place that converts a node's `{:error, _}` into
  `error.execution`. A new element is a new `Statifier.Machine.Content.*` struct
  plus a `defimpl` in the same file - never a change to the runner or the
  interpreter."
- **`c_index` assignment is flat today.** `Compiler.assign_content_nodes/2`
  (`lib/statifier/compiler.ex:460-476`) walks a list of `%DRaise{}`/`%DLog{}`/
  `%DAssign{}` and never recurses; `contents_acc`
  (`lib/statifier/compiler.ex:125`) maps `c_index` to a raw Document node with no
  room for a per-node index list, unlike `transitions_acc`
  (`lib/statifier/compiler.ex:396-408`) which already carries
  `%{transition: ..., source: ..., content: content_indexes}`.
- **A transition's `cond` compiles at load time and a compile failure fails the
  document** (`Compiler.build_cond/2`, `lib/statifier/compiler.ex:622-628`;
  `docs/datamodel.md:53-71` records `<data expr>` and `<assign expr>` as the two
  deliberate exceptions).
- **`Interpreter.Selection` already ports spec 5.9.1 for a transition's `cond`**
  (`lib/statifier/interpreter/selection.ex:294-311`, the `D1` comment), including
  the `{:error, {:non_boolean_cond, other}}` arm, and raises one
  `error.execution` per failed cond in walk order via `raise_cond_errors/2`
  (`:522-533`). It can do that because it is interpreter-layer. A leaf node
  cannot - `test/statifier/interpreter/content_acceptance_test.exs:158-170` is a
  structural acceptance test that globs `lib/statifier/machine/content/*.ex` and
  asserts no file there contains the literal `"error.execution"` or `"Event"`.
- `Statifier.ExecutableContent.result` is
  `{:ok, Context.t(), [Effect.t()]} | {:error, term()}`
  (`lib/statifier/executable_content.ex:51`). `{:error, _}` halts the block and
  discards the node's context, so there is no way for a node to say "I kept
  going, but the platform still owes an `error.execution`".
- `Statifier.ExecutableContent.Context` has exactly three fields, all
  `@enforce_keys`'d (`lib/statifier/executable_content/context.ex:41-42`).
- `lib/statifier/validator/checks/assign.ex:50-74` collects `<assign>` nodes from
  `state.onentry`, `state.onexit`, `state.transitions` and `<initial>`'s
  transitions with `Enum.filter(&match?(%DAssign{}, &1))` over each block's
  **flat** `content` list. Once `<if>` exists, an `<assign>` inside an `<if>`
  partition is invisible to that check.
- Feature registry: `if_elements: :unsupported`
  (`test/support/feature_detector.ex:89`), `conditional_transitions: :unsupported`
  (`:68`). `assign_elements` was flipped by st-af3.4 (`:supported`, with a
  `# st-af3.4` provenance comment - the convention every flipped entry follows).

## Desired End State

A document containing `<if cond="...">`, with any number of `<elseif cond="..."/>`
partitions and at most one trailing `<else/>`, compiles and runs: branch conds
evaluate in document order, the first `{:ok, true}` branch's partition runs
through the same protocol dispatch and in the same document order as any other
block content, a cond that errors or returns a non-boolean is treated as `false`
with one `error.execution` queued, a partition that fails halts the *enclosing*
block, and nested `<if>`s work to arbitrary depth.

Verification: the five new/extended internal test files listed under "Testing
Strategy" pass; `test/statifier/statifier_if_test.exs` (Phase 4) drives the exact
XML of the five corpus documents named under "Corpus/Ratchet Notes" through
`Statifier.compile/1` + `initialize/2` + `send_event/2` and reaches the same final
configurations those files assert, *without* going through the feature gate; and
`mix quality` plus `mix test.regression` are green throughout.

### Key Discoveries

- **Spec 4.3.2 defines `<if>` by partitions, and 4.5.1 defines `<else>` as an
  `<elseif>` whose cond is always true.** Quoted from
  `spec-cache/scxml-rec.html`:

  > The behavior of `<if>` is defined in terms of partitions of executable
  > content. The first partition consists of the executable content between the
  > `<if>` and the first `<elseif>`, `<else>` or `</if>` tag. Each `<elseif>` tag
  > defines a partition that extends from it to the next `<elseif>`, `<else>` or
  > `</if>` tag. The `<else>` tag defines a partition that extends from it to the
  > closing `</if>` tag. In a conformant SCXML document, a partition MAY be
  > empty. In a conformant SCXML document, `<else>` MUST occur after all
  > `<elseif>` tags.

  > When the `<if>` element is executed, the SCXML processor MUST execute the
  > first partition in document order that is defined by a tag whose 'cond'
  > attribute evaluates to true, if there is one. Otherwise, it MUST execute the
  > partition defined by the `<else>` tag, if there is one. Otherwise it MUST NOT
  > execute any of the executable content.

  > `<else>` is an empty element that partitions the content of an `<if>`. It is
  > equivalent to an `<elseif>` with a "cond" that always evaluates to true.

  4.3.2 also states: "The other children of `<if>` consist of executable content.
  Note that since `<if>` itself is executable content, nested `<if>` statements
  are allowed." 4.3.1's attribute table makes `cond` `required="true"` on `<if>`;
  4.4.1 makes `<elseif>` "an empty element that partitions the content of an
  `<if>`, and provides a condition"; 4.5.2 gives `<else>` no attributes.

- **Spec 5.9.1 makes a failed cond non-fatal, and this is the whole reason
  Phase 1 exists:**

  > Conditional expressions are used inside the 'cond' attribute of
  > `<transition>`, `<if>` and `<elseif>`. If a conditional expression cannot be
  > evaluated as a boolean value ('true' or 'false') or if its evaluation causes
  > an error, the SCXML Processor MUST treat the expression as if it evaluated to
  > 'false' and MUST place the error 'error.execution' in the internal event
  > queue.

- **Spec 4.9 is what a partition failure has to answer to:**

  > if transition t takes the state machine from atomic state S1 to atomic state
  > S2, there are three blocks of executable content executed: the one in the
  > `<onexit>` handler of S1, the one inside t, and the one inside the
  > `<onentry>` handler of S2. The SCXML processor MUST execute the elements of a
  > block in document order. If the processing of an element causes an error to
  > be raised, the processor MUST NOT process the remaining elements of the
  > block. (The execution of other blocks of executable content is not affected.)

  4.9 enumerates blocks by their *container element* - `<onexit>`, the
  transition, `<onentry>` - never by nesting of executable content. An `<if>`
  partition is therefore part of the enclosing block, not a block of its own,
  which is what Decision 3 rests on. Note also 4.9's closing sentence, "error
  events will not be removed from the queue and processed until all events
  preceding them in the queue have been processed" - the relevance is Decision 5.

- **Appendix D has no `executeContent` procedure body.** The five hits at
  `appendix-d.txt:173,271,296,315,319` are all call sites, and `elseif` /
  `conditional` return zero matches in that file. So ADR-0002's Appendix D rule
  applies vacuously to `<if>`, exactly as st-af3.4 recorded for `<assign>`: 4.3's
  prose is the port source. There is no pseudocode to deviate from, and this plan
  names no deviation from Appendix D.

- **Every one of the eight `if_elements` corpus files also names
  `conditional_transitions`**, because `test/support/feature_detector.ex:160`'s
  `~r/\bcond\s*=/` fires on `<if cond=...>` itself. Flipping `if_elements` alone
  unblocks **zero** files. See "Corpus/Ratchet Notes".

- **`conditional_transitions`, `if_elements` and the corpus ratchet already
  belong to an existing open bead, `st-af3.8`** ("Corpus: flip datamodel
  features, split the content detector, ratchet"), whose description names
  `datamodel, data_elements, conditional_transitions, assign_elements,
  if_elements, foreach_elements` explicitly and owns the full conformance run and
  `mix test.baseline add`. This settles st-af3.4's "file it as a follow-up bead"
  note - the bead exists and predates it. This plan does not do st-af3.8's work.

- **`test/passing_tests.json` tracks none of the eight `if_elements` files**, and
  its `internal_tests` key already globs `test/statifier/**/*_test.exs`, so new
  internal test files are ratcheted automatically with no registry edit.

- **SCION `if_else/test0` is the hardest single document** and exercises, in one
  file: `<if>` with no `<elseif>`/`<else>`, `<if>` with `<else/>` as the first
  child (an empty first partition), a multi-node partition, an `<if>` nested
  inside another `<if>`'s partition, and - decisively for Decision 2 - an
  `<assign>` inside a partition whose write must be visible to a `<log>` *after*
  the `<if>` in the same `<onentry>` block.

- Constraints: ADR-0002 (Appendix D port; no `executeContent` body), ADR-0003
  (pure core, effects out, the runner is the sole `error.execution` conversion
  site), ADR-0004 (predicator is the datamodel), ADR-0011 (the ratchet only
  grows; a guarded-path change needs a ledger entry), ADR-0012 constraints 3 and
  4 (`c_index` and locations on the Machine; a diagnostic names the failing
  node), ADR-0014 items 1-4 (compiled-expression shape, spans, error identity).

## Decisions

No human was available while this plan was written. Every question this bead
raises is decided here, with its rationale, so nothing is left for the
implementer to discover. Decision 1 is the one the bead names explicitly.

**Decision 1 - the `<if>` defimpl walks its own children; it does NOT call
`Statifier.Interpreter.Content.execute_block/3`.** Four independent reasons, the
first mechanical and corpus-verifiable:

1. `execute_block/3` returns `{MachineState.t(), [Effect.t()]}` - it does not
   return the `Context`. It builds a *fresh* `Evaluator.context/1` for the nested
   call (`lib/statifier/interpreter/content.ex:106-111`) and throws it away on
   return, so an `<assign>` inside a partition could not thread its rebuilt
   `datamodel_context` back to the enclosing block. SCION `if_else/test0`
   requires exactly that (`<if>` assigns `x`, then `<log expr="x"/>` after the
   `</if>` in the same `<onentry>`), so recursion is not merely inelegant here,
   it is wrong.
2. `execute_block/3` *is* the `error.execution` conversion site. Recursing would
   convert a partition node's failure into `error.execution` and then return
   success to the outer block, which would keep running - contradicting 4.9's
   "MUST NOT process the remaining elements of the block" under the reading
   Decision 3 settles. It would also make a file under
   `lib/statifier/machine/content/` the indirect raiser, which
   `content_acceptance_test.exs:158-170` exists to prevent.
3. `execute_block/3` emits one `Trace.ContentExecuted` per call, carrying an
   `owner`. An `<if>` is not a block owner and has no `owner` value of its own to
   pass; a per-`<if>` trace event is not in `docs/observability.md:57-68`'s
   minimum vocabulary.
4. It inverts the layering: `lib/statifier/machine/content/if.ex` would depend on
   `lib/statifier/interpreter/`, making the runner reentrant through the very
   protocol it dispatches.

   Instead, the defimpl folds the selected partition's `c_index` list itself,
   resolving each through `Statifier.Machine.content/2` and dispatching through
   `Statifier.ExecutableContent.execute/2` - the same two lines
   `Interpreter.Content.execute_one/2` runs (`:156-160`), accumulating
   `effects ++ node_effects` in document order and halting on the first
   `{:error, _}`. Document order and effect accumulation are identical to the
   runner's fold by construction, which is what the bead asks for. The ~12 lines
   of fold are deliberately duplicated rather than extracted: extracting them
   would put a shared helper *somewhere*, and every candidate home either
   re-creates reason 4's layering inversion or makes `Interpreter.Content` export
   a function whose only caller is a leaf.

**Decision 2 - partition nodes get their own dense `c_index`es.** ADR-0012 item 3
makes `c_index` "a dense document-order identity assigned to **every**
executable-content node" (`lib/statifier/machine/content.ex:22-29`), and the
alternative - inlining child Machine structs inside the `%MIf{}` - would make a
node inside a partition unaddressable by `Machine.content/2`, unnameable in a
`Trace.ContentExecuted`, and unnameable in an `error.execution` cause origin.
`assign_content_nodes/2` therefore recurses: it assigns the `<if>`'s own
`c_index` first (the `<if>` open tag precedes its children in document order),
then walks each branch's content list in order. `contents_acc`'s value type
widens to carry the assigned branch index lists alongside the raw node, exactly
as `transitions_acc` already does (`lib/statifier/compiler.ex:396-408`).

**Decision 3 - a partition failure halts the enclosing block.** The `<if>`
propagates the child's `{:error, reason}` upward rather than absorbing it.
Rationale: 4.9's own example enumerates blocks by container element
(`<onexit>` / the transition / `<onentry>`), never by nesting of executable
content, so a partition is part of the enclosing block and 4.9's "MUST NOT
process the remaining elements of the block" reaches past the `</if>`. No corpus
file distinguishes the two readings today.

**Decision 4 - a partition failure keeps the inner node's identity.** The `<if>`
returns `{:error, {:nested_content, inner_c_index, reason}}` rather than the bare
`reason`. Rationale: the runner stamps the cause origin with the *`<if>`'s*
`c_index`, so an unwrapped reason would silently give up ADR-0012 constraint 4's
"the `<assign>` at line 42" diagnostic the moment an element is nested. The
protocol already types `reason` as a bare `term()`
(`lib/statifier/executable_content.ex:20-28`), so a tagged wrapper needs no
protocol change and no runner change; the tuple nests naturally for an `<if>`
inside an `<if>`. The `Trace.ContentExecuted` for the enclosing block still lists
only the `<if>`'s own `c_index` and not the partition's - accepted, recorded in
"What We're NOT Doing", because the trace list is built by the runner's fold from
what *it* dispatched and there is no channel for a node to contribute to it.

**Decision 5 - the non-fatal cond-error channel, and where it is drained.**
`Statifier.ExecutableContent.Context` gains a fourth field, `pending_errors: []`
(a default, not an `@enforce_key`, so every existing construction site is
untouched), and `Statifier.ExecutableContent.result` gains a third form,
`{:error, Context.t(), term()}`. `Interpreter.Content.run_nodes/2` drains
`pending_errors` on **both** return paths, in order, through the existing
`raise_execution_error/4`, then clears the list. The three-arity error form
exists solely so that the failure path does not discard cond errors already
recorded before the partition ran; leaf nodes keep returning the two-tuple and
are unaffected.

This is a change to the runner and to the protocol, which
`docs/architecture.md:112-114` says never happens when an element is added. It is
justified as a change to the **error model**, not as an element clause: the model
had only a fatal channel because every shipped element's failure is fatal and the
one non-fatal error the engine already implements (a transition's `cond`, spec
5.9.1) is evaluated in `Interpreter.Selection`, which can raise directly. An
`<if>` cond is the same clause evaluated in a leaf, and the leaf cannot raise
(ADR-0003, and `content_acceptance_test.exs:158-170` mechanically). The runner
stays the sole conversion site; `<foreach>` and the `<send>` family inherit the
channel. Phase 1 lands it on its own, with its own tests, before `<if>` exists.

**Known ordering caveat, recorded rather than hidden.** Because the runner drains
after the node returns, a cond error is queued *after* any event the selected
partition itself raised, where the spec's reading is that it is queued at the
moment the cond is evaluated - i.e. before. Getting the order right would require
either the leaf to raise (ADR-0003) or a second protocol round-trip per node. The
window is narrow: it needs a cond that errors, *and* a later branch that is
selected, *and* that partition to queue an event, *and* the chart to distinguish
the queue order. None of the eight `if_elements` corpus files has an erroring
cond at all. The implementer writes this caveat as an inline comment on the drain
site citing 5.9.1 and 4.9's "error events will not be removed from the queue and
processed until all events preceding them" sentence. Revisit if a corpus file
ever distinguishes it.

**Decision 6 - `cond` compiles at Machine-build time and a compile failure fails
the document.** Same as `<transition cond>` (`Compiler.build_cond/2`,
`lib/statifier/compiler.ex:622-628`), under the existing
`{:content, c_index}` owner ref (`lib/statifier/compiler/expressions.ex:31-35`) -
no new arm. `<if>`/`<assign>` deliberately part company here: `docs/datamodel.md:53-71`
names `<data expr>` and `<assign expr>` as the *only* deferring sites, and both
defer because a corpus file requires a specific document to run and fail at
runtime. Nothing analogous exists for a `cond`, and `<transition cond>` already
sets the load-time precedent for exactly this expression kind.

**Decision 7 - branch ordering is a validator error, not a lowering error.**
Lowering partitions greedily and always produces a well-formed
`[%Branch{}]`; an `<elseif>` after an `<else>`, or a second `<else>`, is
representable and reported by `Statifier.Validator.Checks.If`. This is the
division of labour `lib/statifier/document/content.ex:23-30` states and
`checks/content.ex` / `checks/assign.ex` implement: lowering builds what the
source says, the validator reports what the spec forbids. The two conditions -
"a nil-cond branch that is not last" and "more than one nil-cond branch" - are
both decidable from the partitioned form alone, so no extra field is needed to
preserve the raw child order. Missing `cond` on `<if>`/`<elseif>`, a stray
`<elseif>`/`<else>` outside an `<if>`, and an attribute on `<else>` stay lowering
errors, the same way `<assign>`'s missing `location` does.

**Decision 8 - `Statifier.Document.If.Branch` is a struct, not a tuple.** The
bead sketches `[{cond_expr, block} ...]`. A branch needs three things a bare pair
cannot carry: its own `Parser.Location` (the `<if>`/`<elseif>`/`<else>` tag's
span, which is where Decision 7's validator error must be reported), an
`attribute_locations` entry for `cond` (ADR-0014 item 4's span), and a `cond`
that is `nil` for `<else>` without that `nil` being ambiguous. This is a
mechanical deviation from the bead's wording, recorded rather than left implicit.
`%MIf{}`'s branches are `[{compiled_cond | nil, [c_index]}]` plus the branch's
`cond_location` - a small `Statifier.Machine.Content.If.Branch` struct there too,
so the two sides stay parallel.

## What We're NOT Doing

- **Not flipping `conditional_transitions`, not running the full conformance
  suites, and not touching `test/passing_tests.json`.** Bead **st-af3.8** owns
  all three by name, including `if_elements` itself. Phase 4 flips `if_elements`
  only, because flipping it costs nothing (zero files unblock either way, since
  all eight also trip `conditional_transitions`) and leaving the registry lying
  about a landed feature is worse. If st-af3.8 has already flipped it by the time
  this phase runs, Phase 4's registry edit is a no-op and the phase drops it -
  say so in the commit rather than reverting anything.
- Not making `Trace.ContentExecuted` report the nodes inside a selected
  partition (Decision 4). The trace list is the runner's record of what *it*
  dispatched, and a consumer resolves a partition through `Machine.content/2`
  from the `<if>`'s own `c_index`. Adding an "executed" accumulator alongside
  `pending_errors` would double Phase 1's surface for an observability nicety no
  ADR commits to.
- Not adding `<elseif>`/`<else>` atoms to `Statifier.FeatureDetector`'s registry.
  `@element_features`' `~r/<if(\s|>|\/>)/` (`test/support/feature_detector.ex:144`)
  does not match `<elseif`, and there is no separate atom for either element -
  they ride inside `if_elements`. That is the existing design; changing the
  detector's shape is st-af3.8's declared territory (its description names a
  detector fix of its own).
- Not implementing `<foreach>`, `<send>`, `<cancel>`, `<invoke>`, or `<script>`
  (permanently unsupported, ADR-0004), even though Phase 1's channel is built for
  the first of those.
- Not extracting the child-node fold shared between
  `Interpreter.Content.run_nodes/2` and the `<if>` defimpl into a common helper
  (Decision 1, closing paragraph).
- Not fixing the cond-error queue-ordering caveat under Decision 5. It is
  documented in code and here; closing it needs a protocol shape this bead does
  not justify.

## Implementation Approach

Four phases, split along the boundaries `.claude/wurk/plan.md` names.

Phase 1 is interpreter-side and lands the error-model change alone, with no
`<if>` in sight, so the model change is reviewed and gated on its own. It is
independently gate-verifiable because `Statifier.TestContent` (`test/support/`)
is the existing harness node for exercising protocol shapes no shipped element
produces - the same role it already plays for `fail: true`.

Phase 2 is the parser/compiler vertical slice, and it is deliberately not split
into a lowering phase and a compiler phase. Widening `Statifier.Document`'s
`content_node` union without adding the matching `build_content_node/2` clause
and widening `acc()`'s `contents_acc` (`lib/statifier/compiler.ex:125,660`)
leaves a Document node type flowing into a function whose `@spec` excludes it,
which dialyzer reports and which would make the intermediate commit's gate red.
This is the same exception st-af3.4's Phase 1 took, for the same mechanical
reason, and the skill's own rule applies: combine rather than split when the
intermediate gate cannot be green.

Phase 3 is validator-side and separable: it adds a check and widens two existing
checks' traversal, with nothing in Phase 2 depending on it.

Phase 4 is the corpus-tooling/documentation boundary - the feature flag, the
conformance-shaped internal tests, the changelog fragment - and is separable
because the conformance suites are excluded from `mix test` by default
(`test/test_helper.exs`) and this phase does not touch the ratchet at all.

Every new test asserting `lib/` behavior carries a sabotage note per
`docs/testing.md:80-136` - one line directly above the `test` line and above any
`@tag`. Suggested mutations are given per phase so the implementer does not have
to invent one.

## Phase 1: The non-fatal error channel

### Overview

A node can report a spec-5.9.1 error it recovered from, and the runner converts
it to `error.execution` without halting the block. No element uses it yet.

### Changes Required

#### 1. The context field

**File**: `lib/statifier/executable_content/context.ex`
**Changes**: a fourth field, defaulted so no construction site changes.

```elixir
@enforce_keys [:machine_state, :owner, :datamodel_context]
defstruct [:machine_state, :owner, :datamodel_context, pending_errors: []]
```

Moduledoc: a `## Non-fatal errors` section stating what the field is for -
spec 5.9.1's "MUST treat the expression as if it evaluated to 'false' **and**
MUST place the error 'error.execution' in the internal event queue", quoted -
that entries are bare `term()` reasons in the order the node produced them, that
the node never converts them itself (ADR-0003), and that the runner drains and
clears the list after every node. Say explicitly that this is *not* the fatal
channel: a node with `pending_errors` still ran to completion.

#### 2. The protocol

**File**: `lib/statifier/executable_content.ex`
**Changes**: widen `result` and document the third form.

```elixir
@type result ::
        {:ok, Context.t(), [Effect.t()]}
        | {:error, term()}
        | {:error, Context.t(), term()}
```

Moduledoc contract section gains the third bullet: `{:error, context, reason}` -
"the node failed, and state it had already legitimately produced (queued events,
datamodel writes, `pending_errors`) must not be discarded with it. A leaf node
returns the two-element form; a *composite* node - one that runs child content -
returns this one so that work done before the failure survives." Keep the
existing "never constructs a `Statifier.Event` and never raises" sentence
untouched: it governs both error forms.

#### 3. The runner

**File**: `lib/statifier/interpreter/content.ex`
**Changes**: `run_nodes/2` gains the third-form clause and the drain. Sketch:

```elixir
case execute_one(context, c_index) do
  {:ok, new_context, node_effects} ->
    new_context = drain_pending(new_context, c_index)
    {:cont, {new_context, effects ++ node_effects, executed ++ [c_index], nil}}

  {:error, new_context, reason} ->
    new_context = drain_pending(new_context, c_index)
    {:halt, {new_context, effects, executed ++ [c_index], {c_index, reason}}}

  {:error, reason} ->
    {:halt, {context, effects, executed ++ [c_index], {c_index, reason}}}
end
```

`drain_pending/2` folds `context.pending_errors` through
`raise_execution_error/4` in order - the same function the fatal path already
uses, so the origin stamp stays `{:content, c_index, owner}` and there is still
exactly one site in the tree that names `"error.execution"` for content - and
returns `%{context | machine_state: ms, pending_errors: []}`.

Note the `{:error, new_context, reason}` arm halts with `new_context`, not
`context`: that is the whole point of the third form. `execute_block/3`'s
existing `case error do {failed_c_index, reason} -> raise_execution_error(...)`
then runs on top of the drained machine_state, so a drained cond error precedes
the fatal one on the queue.

## Corpus/Ratchet Notes

Eight generated corpus files carry `:if_elements`. **All eight also carry
`:conditional_transitions`**, which `test/support/feature_detector.ex:68` still
registers `:unsupported` - the `~r/\bcond\s*=/` attribute detector (`:160`) fires
on `<if cond=...>` and `<elseif cond=...>` just as it does on
`<transition cond=...>`. Flipping `if_elements` alone therefore unblocks **zero**
files, and `test/passing_tests.json` tracks none of the eight today.

Assuming both atoms flip - which is **st-af3.8**'s job, not this bead's - five
would newly pass:

| File | What it exercises |
|---|---|
| `test/scion_tests/if_else/test0_test.exs` | the hardest single document: bare `<if>`, `<else/>` as first child, multi-node partitions, two levels of nesting, and an `<assign>` inside a partition read by a `<log>` after the `</if>` |
| `test/scxml_tests/mandatory/if/test147_test.exs` | 4.3.2's "first partition in document order whose cond is true", with `<if cond="false">` / `<elseif cond="true"/>` / `<else/>` and a `<raise>` after the `</if>` |
| `test/scxml_tests/mandatory/if/test148_test.exs` | same clause, `<else>` selected |
| `test/scxml_tests/mandatory/if/test149_test.exs` | same clause, no branch selected |
| `test/scxml_tests/mandatory/system_variables/test319_test.exs` | `<if cond="_event !== undefined">` with `<else/>` - `_event` unbound at initialization |

The remaining three stay blocked on a feature neither this bead nor st-af3.8's
`if`/`foreach` reach touches:
`test/scxml_tests/mandatory/foreach/test153_test.exs` (`foreach_elements`), and
`test/scxml_tests/mandatory/selecting_transitions/test409_test.exs` and
`test411_test.exs` (`send_elements`, `send_delay_expressions`).

Phase 4's `test/statifier/statifier_if_test.exs` is how this bead proves the five
documents behave correctly without touching the ratchet. `Statifier.Case.test_scxml/4`
flunks rather than skips (`test/support/case.ex:41-46`), so a still-blocked
generated file cannot silently pass either way.

**Residual risk**, recorded rather than hidden: this plan asserts that the five
documents pass, from reading them, not from running them - the feature gate
prevents running them until st-af3.8. If one of them turns out to fail in Phase
4, do **not** weaken anything to make it pass and do **not** drop it from the
internal test file: record which one and why in the commit body and as a note on
st-af3.5, and fix the engine.

## Performance Considerations

An `<if>` adds one `Predicator.evaluate/3` call per branch cond scanned (at most
once per branch, short-circuiting at the first true one) and no context rebuild
of its own - it reuses `context.datamodel_context` as given, and only an
`<assign>` inside a partition rebuilds, which is st-af3.4's already-accepted cost
(that plan's "Performance Considerations", owned by st-sdh). The partition fold
allocates one list per executed partition. Nothing here evaluates in a hot path
yet, so there is nothing to measure; do not pre-optimize in these phases.

## Testing Strategy

### Unit Tests

One file per pipeline layer, matching the `<raise>`/`<log>`/`<assign>` layout:

- `test/statifier/document/if_test.exs` (new) - `@enforce_keys`, defaults, branch
  defaults, `attribute_locations`
- `test/statifier/lowering/content_test.exs` - four new `<if>` describes:
  partitioning, empty first partition, missing `cond` on `<if>` and `<elseif>`,
  misplaced `<elseif>`, nested `<if>`
- `test/statifier/machine/content_test.exs` - the compiled `%MIf{}`, its branch
  index lists, `c_index` density and document order across nesting, and a bad
  `cond` failing `compile/1`
- `test/statifier/machine/content/if_test.exs` (new) - the protocol leaf, where
  the branch-selection and cond-error matrix lives
- `test/statifier/validator/checks/if_test.exs` (new) - 4.3.2's `<else>` ordering
- `test/statifier/validator/checks/assign_test.exs` - the nested-traversal
  regression
- `test/statifier/interpreter/content_test.exs` - Phase 1's non-fatal channel
  through the real runner, and Phase 2's three end-to-end block behaviors
- `test/statifier/executable_content_test.exs` - the defaulted `pending_errors`
- `test/statifier/statifier_if_test.exs` (new) - the five corpus documents,
  end to end through the public API

Key edge cases, most at the leaf: an empty partition; every cond false with and
without `<else>`; a later true branch that must not win; a cond that errors
followed by a branch that is selected; a non-boolean cond; two failing conds
accumulating in order; a partition node that fails, with pending errors already
recorded; two levels of `<if>` nesting; an `<assign>` inside a partition read
after the `</if>`; an `<elseif>` after an `<else>`; two `<else>`s; a stray
`<elseif>` outside any `<if>`.

Every one of these tests carries a sabotage note per `docs/testing.md:80-136` -
one line directly above the `test` line and above any `@tag`, naming a mutation a
reasonable person could make by mistake. Per-phase suggestions are given inline
above. Generated corpus files are exempt and get no notes;
`test/support/test_content.ex`'s existing
`# sabotage: n/a - harness plumbing, asserts no lib/ behavior` line covers its new
modes.

### Manual Testing Steps

1. In `iex -S mix`, build a chart with
   `<onentry><if cond="false"><log label="a" expr="1"/><elseif cond="true"/><log label="b" expr="2"/><else/><log label="c" expr="3"/></if></onentry>`
   and confirm exactly one `Effect.Log` comes back, labelled `b`.
2. Repeat with an `<assign location="x" expr="10"/>` inside the selected
   partition and a `<log expr="x"/>` **after** the `</if>` in the same
   `<onentry>`, confirming the log reads `10` - Decision 1's mechanical reason,
   by hand.
3. Repeat with `cond="undefined_var"` on the first branch and a true `<elseif>`,
   confirming one `error.execution` on the internal queue **and** that the
   `<elseif>` partition ran.
4. Nest an `<if>` two deep with a failing `<assign>` at the bottom, confirming
   the enclosing block halts and the `error.execution`'s `data` unwraps to name
   the innermost `c_index` through the `{:nested_content, _, _}` chain.
5. Run the five corpus documents through `Statifier.compile/1` + `initialize/2`
   by hand, or by
   temporarily flipping `conditional_transitions` locally and running
   `mix test <file> --include scion --include scxml_w3` - **do not commit that
   flip**; it is st-af3.8's.
