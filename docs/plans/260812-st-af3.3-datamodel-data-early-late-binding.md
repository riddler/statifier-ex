# `<datamodel>`/`<data>` Early and Late Binding Implementation Plan

## Overview

Land `<datamodel>`/`<data>` end to end - DOM lowering, validator checks,
Machine compilation, and both binding modes - so that a declared `<data>` id
is present in `MachineState.datamodel` from document initialization onward and
carries its initial value at the time spec 5.3.3 requires. Bead: st-af3.3.

The producer is the whole job. Every consumer already exists and works:
`Statifier.Evaluator.context/1` builds a real `Predicator.Context` with
`on_unbound: :error` ([`lib/statifier/evaluator.ex:98-103`](../../lib/statifier/evaluator.ex)),
`Selection.condition_match/2` evaluates conds and raises `error.execution`, and
`Interpreter.Content` does the same for content nodes. Nothing writes the
author's half of `MachineState.datamodel`.

## Current State Analysis

Read `docs/research/260812-st-af3.3-datamodel-data-early-late-binding.md` end
to end before starting; this section states only what the plan turns on.

**Nothing about `<datamodel>` or `<data>` exists in `lib/` today beyond two
root attributes.** `<scxml datamodel="...">` and `<scxml binding="early|late">`
lower onto `%Statifier.Document{}` (`lib/statifier/lowering/builders.ex:52`,
`:61-62`) and are copied unchanged onto `%Statifier.Machine{}`
(`lib/statifier/compiler.ex:180-181`). Nothing reads either one. The
`<datamodel>` and `<data>` *elements* miss the 13-entry lowering dispatch map
(`lib/statifier/lowering.ex:53-67`), so any document containing them fails to
lower with `{:unsupported_element, "datamodel"}` before validation runs.

`MachineState.datamodel` has exactly two writers - `new/2`
(`lib/statifier/machine_state.ex:220`) and `put_event/2` (`:289`). `new/2`
merges the `:datamodel` option's map *under* `SystemVariables.initial/2`'s four
system variables, so an author map can never shadow a system variable.

Both binding hooks are already commented at their exact pseudocode positions:
`interpret`'s preamble (`lib/statifier/interpreter.ex:163-165`) and
`enterStates`' per-state step (`lib/statifier/interpreter/exit_entry.ex:619-623`).
`arrive/3` (`:624-644`) does configuration-add, `run_onentry_blocks/2`,
`run_default_entry/3`, `raise_completion_events/2` in that order; the
late-binding step belongs between the configuration add and the onentry run.
**There is no first-entry tracking anywhere** - Appendix D's `s.isFirstEntry`
has no counterpart, and `states_for_default_entry` is not a substitute
(history restoration re-enters a state without default entry).

Three corpus facts settle three of the plan's decisions and were verified
directly against the installed predicator 5.0.0, not recalled:

| probe | result |
|---|---|
| `Predicator.compile_with_spans("return")` (test277) | `{:ok, %Compiled{instructions: [["load", "return"]]}}` - compiles |
| evaluating that against `on_unbound: :error` | `{:error, %UndefinedVariableError{variable: "return"}}` |
| `Predicator.compile_with_spans("{p1: 'v1'")` (`data_invalid`) | `{:error, "Expected '}' but found end of input..."}` - does **not** compile |
| `Predicator.compile_with_spans("[1,2,3]")` (test551) | `{:ok, %Compiled{instructions: [["lit", [1, 2, 3]]]}}` |
| `Predicator.Context.new(%{"Var1" => nil})` | normalizes to `%{"Var1" => :undefined}` |

And two corpus counts, verified in this repo:

- `datamodel="ecmascript"` appears in **111** corpus files; **86 of them are
  the entire SCION half of `test/passing_tests.json`**. Erroring on that value
  would regress the whole ratchet.
- No corpus file has a `<data id>` that collides with a state id, and no
  `<data>` id begins with `_`, so both uniqueness rules below are safe to
  enforce today.

## Desired End State

After this plan, for any document the pipeline accepts:

1. Every declared `<data>` id - top-level and state-scoped, under `early` and
   under `late` - is **present** as a key in `MachineState.datamodel` from the
   moment `Statifier.Interpreter.initialize/2`'s preamble finishes, bound to
   `nil` when it has no value yet. `Var1 === undefined` and
   `Var1 !== undefined` therefore evaluate rather than raising
   `UndefinedVariableError`.
2. Under `binding="early"`, every `<data>` in the document carries its value
   before `enter_states/2` runs. Under `binding="late"`, top-level `<data>`
   carries its value at initialization and a state-scoped `<data>` carries it
   at that state's first entry, before any `<onentry>` markup.
3. A `<data>` whose value cannot be produced - an unparseable `expr`, an
   `expr` that fails at evaluation, or a `src` - leaves its id bound to `nil`
   and raises `error.execution` on the internal queue with a
   `{:data, d_index}` cause.
4. Values supplied through `MachineState.new/2`'s `:datamodel` option override
   the document's own top-level `<data>` values.
5. `mix quality` is green, and `datamodel` / `data_elements` are `:supported`
   in the feature registry with every newly-passing corpus file ratcheted in.

**How to verify**: `mix quality` green; `mix test.regression` green; the three
corpus files whose entire unsupported set is `{datamodel, data_elements}`
(`test/scion_tests/data/data_obj_literal_test.exs`,
`test/scion_tests/data/data_invalid_test.exs`,
`test/scxml_tests/mandatory/evaluationof_executable_content/test158_test.exs`)
pass and are in `test/passing_tests.json`.

### Key Discoveries

- **`initializeDatamodel` has no Appendix D body.** Case-insensitive grep over
  `spec-cache/appendix-d.txt` returns exactly two hits, both call sites -
  `:102` `initializeDatamodel(datamodel, doc)` and `:312`
  `initializeDataModel(datamodel.s,doc.s)`. `new Datamodel(doc)` is never
  defined either. **The ADR-0002 port obligation here is the two call sites
  and the `isFirstEntry` flag; the body's semantics come from clause 5.3 and
  B.2.2, not from Appendix D.** Every module this plan adds under
  `lib/statifier/interpreter/` must say so in its own moduledoc.
- **Spec 5.3.3 makes seeding mandatory under both bindings**, verbatim: "When
  'binding' is assigned the value \"late\", the SCXML Processor MUST create the
  data elements at document initialization time, but MUST assign the specified
  initial value to a given data element only when the state that contains it is
  entered for the first time, before any `<onentry>` markup." Creation is
  unconditional; only assignment is deferred.
- **Spec 5.3.2 puts the environment ahead of the document**, verbatim: "The
  SCXML Processor MUST use any values provided by the environment at
  instantiation time in place of those contained in the top-level `<data>`
  elements. (Top-level data elements are those that are children of the
  `<datamodel>` element that is a child of `<scxml>`)." The rule is scoped to
  top-level, and 6.4 states the same override for an `<invoke>`
  `<param>`/`namelist`.
- **Spec 5.9.4 permits either failure timing**, verbatim: "The SCXML Processor
  MAY reject documents containing syntactically ill-formed expressions at
  document load time, or it MAY wait and place 'error.execution' in the
  internal event queue at runtime when the expressions are evaluated."
- **Spec 5.3.2's failure clause names the wrong half of the bead's citation.**
  Verbatim: "If the value specified for a `<data>` element (by 'src', children,
  or the environment) is not a legal data value, the SCXML Processor MUST raise
  place error.execution in the internal event queue and MUST create an empty
  data element in the data model with the specified id." ("MUST raise place" is
  the REC's own typo.) It names `src`/children/environment, **not `expr`** - an
  `expr` failure reaches `error.execution` through 5.9.3 instead: "If a value
  expression does not return a legal data value, the SCXML Processor MUST place
  the error 'error.execution' in the internal event queue."
- **Spec 3.14 makes the id namespace session-wide and shared**, verbatim: "In a
  conformant SCXML document, the values of all attributes of type \"id\" MUST be
  unique within the session." `<data>`'s `id` is type `ID` and Required = true
  (5.3.1).
- **Spec 5.10 reserves the `_` prefix**, verbatim: "A conformant SCXML document
  MUST NOT contain ids beginning with '_' in the `<data>` element."
- **Spec 3.2.1 does not enumerate `datamodel`'s values closed.** Required =
  false, Type = NMTOKEN, Default = "platform-specific", Valid Values = `"null",
  "ecmascript", "xpath" or other platform-defined values`. Appendix B's intro
  adds "Conformant SCXML processors MUST support the null data model, and MAY
  support other data models" and **states no rule at all** for what a processor
  does when handed a datamodel it does not implement.
- **`<datamodel>` occurs 0-or-1 times under `<scxml>`, `<state>`, and
  `<parallel>`, and nowhere else** - the identical children-list sentence
  appears in 3.2.2, 3.3.2, and 3.4.2 only. Not under `<final>`, `<initial>`, or
  `<history>`.
- **B.2.2 forbids ordering dependencies between `<data>` elements**: "Ordering
  dependencies between `<data>` elements are not permitted. In the case of
  early binding, the SCXML Processor MUST evaluate all `<data>` elements at
  initialization time but MAY do so in any order it chooses." This is what
  makes one evaluation context per binding pass correct rather than one per
  `<data>`.
- **Constraints on the new structs.** Nothing under `lib/statifier/document/`
  may reference `Predicator` (`lib/statifier/document.ex:14-20`);
  `attribute_locations` holds value spans only, and an entry exists only for an
  attribute actually written (`:22-39`). `Statifier.Document.Content` is the
  precedent for representing an illegal shape rather than refusing to build it
  (`lib/statifier/validator/checks/content.ex:6-10`).
- **ADR-0014 item 5** (`on_unbound: :error`) is what makes seeding versus
  absence observably different, and **ADR-0012 constraint 1** is what bounds
  how first-entry tracking may be stored.

## What We're NOT Doing

- **Not fetching `src`.** Lowering, validation, and compilation handle the
  attribute; no HTTP or file read happens anywhere. A `<data src=...>` binds
  its id to `nil` and raises `error.execution` at its binding time, which is
  exactly what spec 5.3.2's failure clause prescribes for a value that cannot
  be produced. `test552` therefore takes its `fail` branch and does not enter
  the ratchet. The doc-versus-spec contradiction about *when* a fetch would
  happen (research open question 1) is not settled here, because with no fetch
  there is no timing to be wrong about.
- **Not changing `cond` or `<log expr>` failure timing.** Those keep failing at
  `Compiler.Expressions.compile/3` and failing the whole document compile. Only
  `<data>` defers to runtime, for the reason given under Decision 2. Spec 5.9.4
  permits the choice per expression class; a plan that widened the deferral to
  every expression would be re-deciding `cond` behavior that st-af3.2 already
  landed, and no corpus test asks for it.
- **Not implementing `<assign>`** (st-af3.4), `<foreach>` item/index bindings
  (st-af3.6), or `<invoke>` `<param>`/`namelist` seeding of a child session
  (st-cmq.6/st-cmq.7). test150's `Var4` and test151's `Var5` come from
  `<foreach>` and stay unbound after this bead.
- **Not flipping `conditional_transitions` in the feature registry.** It is
  still `:unsupported` (`test/support/feature_detector.ex:68`) even though
  st-af3.2 landed real cond evaluation; flipping it is st-af3.8's job, and
  doing it here would pull 79 files this bead cannot make pass into scope. This
  is why 102 of the 105 datamodel-blocked files do not move within this bead.
- **Not adding a `binding=` feature-detector pattern.** The detector has none
  today, so a `binding="late"` document produces no feature atom. Adding one
  now would create an atom that is `:supported` from birth, which can never
  gate anything - a detector entry that cannot fail is noise. Recorded here
  rather than left as a silent omission.
- **Not adding a trace effect for datamodel binding.**
  `docs/observability.md`'s minimum trace vocabulary is a closed table and
  datamodel binding is not in it ("shapes settled at implementation, the set is
  the commitment"). The one observable event a binding pass can produce -
  `error.execution` - already travels as an internal event with a full
  `Statifier.Event.Cause`.
- **Not revisiting `_event`'s seeding.** The spec agent surfaced 5.10's "The
  SCXML Processor MUST NOT bind _event at initialization time until the first
  event is processed", which sits in tension with
  `SystemVariables.initial/2`'s `"_event" => nil` seed and its test319
  argument. That is a standing decision in a module this bead does not
  otherwise touch; re-opening it here would be a direction-level change smuggled
  into a feature branch.
- **Not raising the coverage floor or touching any gate-guarded file.**

## Implementation Approach

Six phases along the pipeline's own module boundaries (lowering, validator,
compiler, interpreter, corpus), so they can parallelize across worktrees per
`docs/workflow.md`. Each phase lands tested behavior of its own and is green on
a full `mix quality` by itself.

The eight decisions below are settled here so no implementer re-litigates them.
Each cites the clause it rests on.

### Decision 1: the environment wins, for top-level `<data>` only

Spec 5.3.2 is explicit and scoped: values provided by the environment at
instantiation time replace those in the **top-level** `<data>` elements.

`MachineState.new/2` writes exactly two things into `datamodel`: the
`:datamodel` option's map, and `SystemVariables.initial/2`'s four system
variables merged over it. So at the first instruction of
`Interpreter.initialize/2`, **key presence in `machine_state.datamodel` is
definitionally "provided by the environment at instantiation time"** - the
spec's own phrase. That is the whole mechanism; no new `MachineState` field is
needed, and the environment key set never outlives `initialize/2`.

Concretely, `Statifier.Interpreter.Datamodel.initialize/1`:

1. captures `env_ids = MapSet.new(Map.keys(machine_state.datamodel))` **first**;
2. seeds - `Map.put_new(datamodel, id, nil)` for every declared `<data>` id in
   the whole machine, which is itself the environment-wins rule for seeding;
3. binds, skipping any **top-level** `<data>` whose id is in `env_ids`.

A *state-scoped* `<data>` whose id happens to match an environment key is
**not** skipped: 5.3.2 scopes the override to top-level, and a state-scoped
`<data>` is the document asserting a value at a point in the run the
environment could not have known about. A system variable can never be
shadowed either, since `_`-prefixed `<data>` ids are rejected by the validator
(spec 5.10) - so the top-level skip cannot be reached by a system variable.

### Decision 2: a bad `<data expr>` fails at runtime, not at load time

Spec 5.9.4 permits either. The corpus does not:

`test/scion_tests/data/data_invalid_test.exs` declares
`<data id="o1" expr="{p1: 'v1'"/>` - which predicator refuses to compile
(`{:error, "Expected '}' but found end of input at line 1, column 10"}`) - and
asserts a final configuration of `["pass"]`, reached through a
`<transition event="error.execution" target="pass"/>`. Rejecting at load time
makes `Statifier.compile/1` return `{:error, _}`, the harness never reaches
`initialize/2`, and the test is unpassable. `test277`'s `expr="return"` is the
milder case: it compiles to `[["load", "return"]]` and fails only at evaluation
under `on_unbound: :error`, so it needs nothing special - but `data_invalid`
decides the question on its own.

So: a `<data>` value expression is still compiled once at Machine-build time,
but a **compile failure is captured onto the compiled node** rather than
failing `Compiler.compile/1`. `%Statifier.Machine.Data{}`'s `value` field is:

```elixir
@type value ::
        Statifier.Machine.expr()
        | {:invalid, Statifier.Compiler.Error.t()}
        | {:src, uri :: String.t()}
```

At binding time, `{:invalid, error}` and `{:src, uri}` both take the failure
branch - id stays `nil`, `error.execution` raised. `Statifier.Compiler.Expressions`
needs no new function for this; the data pass calls the existing `compile/3`
and stores whichever result it gets.

This does not weaken "the Machine is valid by construction"
(`docs/architecture.md` principle 4). A `<data>` with an ill-formed expression
is a *document-legal* shape whose failure the spec routes through the event
queue; representing it is the same division of labour `Statifier.Document.Content`
already has with the validator.

### Decision 3: seeding, and what "empty data element" means

Every declared `<data>` id is bound to `nil` before any value is evaluated.
`Predicator.Context.new/2` normalizes `nil` to `:undefined` recursively, so
`Var1 === undefined` returns `{:ok, true}` and `Var1 !== undefined` returns
`{:ok, false}` - verified against predicator 5.0.0. This is
`SystemVariables.initial/2`'s `"_event" => nil` precedent applied verbatim, and
its moduledoc (`lib/statifier/evaluator/system_variables.ex:31-48`) already
argues the case at length.

Because seeding runs before every evaluation, spec 5.3.2's "MUST create an
empty data element in the data model with the specified id" on failure is
satisfied by *not writing* on the error branch, rather than by writing `nil`
after the error. Research open question 7's sub-question - "whether the id is
bound to `nil` before the error is raised or after" - therefore does not arise:
it is always before, for every `<data>`, failing or not.

The caveat st-unt recorded stands and is not closable here:
`Context.new/2` normalizes `nil` recursively, so a `<data>` holding a genuine
null is indistinguishable from unbound under `=== undefined`. No corpus test
assigns a null.

### Decision 4: where `<data>` lives on the Machine

Both, because the two bindings want different views and one storage serves
both:

- `%Statifier.Machine{data_elements: tuple()}` - dense, `d_index`-keyed,
  document order, read by `Statifier.Machine.data/2` (mirroring `at/2`,
  `transition/2`, `content/2`). This is the ADR-0012 constraint-3 index space a
  cause and a diagnostic name a `<data>` by, and it is exactly the sequence
  early binding folds over.
- `%Statifier.Machine.State{data: [non_neg_integer()]}` - the `d_index`es this
  state's own `<datamodel>` declares. Late binding reads
  `Machine.at(machine, index).data` at first entry.

The synthesized root state at index 0 holds the top-level `<datamodel>`'s
`d_index`es, so "is this `<data>` top-level" is
`d_index in Machine.at(machine, 0).data` - which is what Decision 1's skip
tests. Giving the root a real index is already what removes the root's special
case everywhere else in this codebase (`lib/statifier/machine.ex:8-20`).

### Decision 5: `<data>` ids share one namespace with state ids

Spec 3.14: all `id`-typed attribute values MUST be unique within the session,
and `<data>`'s `id` is type `ID` (5.3.1). So `Statifier.Validator.Checks.Ids`
widens to collect `<data>` ids alongside state ids into **one** uniqueness set
in document order; a `<data id="s1">` colliding with `<state id="s1">` is a
`:duplicate_id` error at the `<data>`'s own `id` span. `id=""` on a `<data>` is
`:empty_id`, same as on a state. Verified safe: no corpus file has such a
collision.

A **missing** `id` is a different layer's problem. 5.3.1 marks it Required =
true, so `build_data/2` follows `build_raise/2`'s pattern
(`lib/statifier/lowering/builders.ex:212-232`) and returns
`{nil, [Error.missing_attribute("data", "id", location)]}` - lowering, not
validation.

An id beginning with `_` is `{:data_reserved_id, id}` per spec 5.10.

### Decision 6: first-entry tracking is a `MapSet` on `MachineState`

Appendix D mutates `s.isFirstEntry` on the state itself. A compiled
`%Machine.State{}` is immutable compile-time data in this port, so the flag
moves to the runtime struct - **an ADR-0002 mechanical deviation, and
`arrive/3` must carry a comment saying exactly that**, in the same shape as
`MachineState`'s existing external-queue and `states_to_invoke` deviation notes.

`%MachineState{entered_states: MapSet.t(non_neg_integer())}`, defaulting to
`MapSet.new()` in `new/2`. `arrive/3` tests membership **before** adding, then
adds unconditionally. It satisfies ADR-0012 constraint 1 - plain data, no
closure, survives a round trip, diffable - and `history_values` is the existing
precedent for a MapSet-valued field on this struct.

Considered and rejected: populating the set only when
`machine.binding == :late`. That saves one `MapSet.put` per state entry under
early binding, at the cost of making the field's meaning conditional on the
document - which is precisely the "not a complete, inspectable position"
failure ADR-0012 constraint 1 exists to prevent. ADR-0012's Consequences
section already accepts "modest permanent weight" for exactly this trade.

Not `states_for_default_entry`: history restoration re-enters a state without
default entry, so the two sets diverge.

### Decision 7: top-level `<data>` binds at initialization under both bindings

Spec 5.3.3 defers assignment to "when the state that contains it is entered for
the first time". A top-level `<data>` is contained in no state. Appendix D
makes the same split structurally: `initializeDatamodel(datamodel, doc)` in
`interpret` is whole-document, while `initializeDataModel(datamodel.s,doc.s)`
in `enterStates` is per-state and iterates `statesToEnter`, which never
contains the `<scxml>` root. B.2.2 says it directly: "the processor MUST assign
the specified initial values to data elements only when the state containing
them is first entered".

So under `late`, deferring a top-level `<data>` would defer it to an entry that
never happens, leaving it permanently unassigned. It binds at initialization
instead. `test280` does not discriminate (its root `<data id="Var1"/>` has no
value), so this rests on the spec text rather than on a corpus assertion.

The structural consequence, spelled out in Phase 4 because it is the one place
this plan departs from Appendix D's literal shape: the pseudocode's
`if doc.binding == "early":` guard **moves off the call site and into**
`Datamodel.initialize/1`. Seeding and top-level binding run under both
bindings; the guard decides only which `d_index`es get bound.

Under `early`, *every* `<data>` binds at initialization, state-scoped ones
included, even for states that are never entered - `test551` asserts exactly
that: `binding="early"`, `<data id="Var1">[1,2,3]</data>` inside a never-entered
`s1`, and `s0`'s `cond="Var1 !== undefined"` must be true.

### Decision 8: child content is constant-folded at compile time

Spec 5.3.2: "The children of the `<data>` element represent an **in-line
specification of the value** of the data object" - a value, not an expression
that reads the datamodel. B.2.1 gives the ECMAScript datamodel a
parse-then-fall-back-to-string ladder ("if the content is a valid JSON... create
the corresponding ECMAScript object... Otherwise the Processor MUST treat the
content as a space-normalized string literal").

The predicator analogue, one rung shorter (predicator's literal syntax replaces
JSON; there is no XML rung, ADR-0004):

`Statifier.Compiler.Expressions.inline_value/1` takes the raw child text and
returns a `{:static, value}` always:

1. trim the text; compile it with `Predicator.compile_with_spans/1`;
2. on success, evaluate it **at compile time** against
   `Predicator.Context.new(%{}, on_unbound: :error)`;
3. on `{:ok, value}`, return `{:static, value}`;
4. on any failure at either step, return
   `{:static, space_normalized_text}`.

Step 2 is what makes the fold safe: `<data id="x">hello</data>` compiles to
`[["load", "hello"]]`, fails on the empty context, and correctly falls back to
the string `"hello"` rather than becoming a datamodel read. `[1,2,3]` folds to
the list `[1, 2, 3]`, which is what `test551` needs and what `<foreach>`
(st-af3.6) will need over test150's `Var3`.

Consequences worth stating: child content is **never** a `{:compiled, ...}`
arm, so it can never raise `error.execution` at binding time, and 5.3.2's
failure clause is vacuous for children under this datamodel - the string
fallback means there is no illegal child value. The fold lives in `Expressions`
rather than in `Compiler` so `Statifier.Compiler` grows no `Predicator`
knowledge of its own.

### Decision 9: the `datamodel` attribute allow-list is the spec's list plus ours

The bead asks for `predicator` accepted, `elixir` aliased, and "other values
are a validator error". **Taken literally that regresses 86 of the ratchet's 91
entries**: `datamodel="ecmascript"` appears in 111 corpus files, and 86 of them
are the whole SCION half of `test/passing_tests.json`.

The spec does not support the literal reading either. 3.2.1 gives `datamodel`
Type = NMTOKEN, Default = "platform-specific", Valid Values = `"null",
"ecmascript", "xpath" or other platform-defined values`, and Appendix B's intro
states **no** rule for what a processor does with a datamodel it does not
implement.

So the allow-list is `["predicator", "elixir", "null", "ecmascript", "xpath"]` -
the three the spec names plus statifier's two - reported as
`{:scxml_bad_datamodel, raw}` through `Checks.Enums`'s existing `out_of_range/5`
helper. What that check actually catches is a **typo** (`datamodel="predicater"`,
`datamodel="javascript"`), which is what a validator check on an enumerated
NMTOKEN is good for. It does not, and must not, claim the engine implements
ECMAScript or XPath: which datamodel this engine runs is ADR-0004's answer and
the corpus tooling's, not this attribute's. An absent `datamodel` attribute is
predicator, which is this platform's documented default (3.2.2: "Platforms
SHOULD document their default data model" - `docs/datamodel.md:3-7` does).

This is recorded under "Decisions Taken Without a Human" below, because it
deliberately reads the bead's acceptance criterion against its evident intent.

## Phase 1: Lower `<datamodel>` and `<data>`

### Overview

Add the Document-layer structs and the two builders, so a document containing
`<datamodel>`/`<data>` lowers instead of failing with
`{:unsupported_element, ...}`. Nothing downstream reads the new slots yet;
lowering's own tests are what exercise this phase.

### Changes Required:

#### 1. Two new Document structs

**File**: `lib/statifier/document/data.ex` (new)

```elixir
defmodule Statifier.Document.Data do
```

## Phase 4: Seed the datamodel and bind early

### Overview

The `interpret` preamble hook. This is the phase that makes
`Var<n> === undefined` conds evaluate, which is what st-unt's finding 3 is
waiting on.

### Changes Required:

#### 1. The binding module

**File**: `lib/statifier/interpreter/datamodel.ex` (new)

Its moduledoc must open by stating the ADR-0002 position: `initializeDatamodel`
and `initializeDataModel` have **no procedure body anywhere in Appendix D** -
only the two call sites, `appendix-d.txt:102` and `:312`, which even disagree
on spelling and argument shape - so this module's semantics come from clause
5.3.2, 5.3.3, and B.2.2, quoted there, not from pseudocode. Without that note a
future reader will look for a pseudocode block to diff against and find none.

```elixir
@spec initialize(machine_state :: MachineState.t()) :: MachineState.t()
```

1. `env_ids = MapSet.new(Map.keys(machine_state.datamodel))` - captured first,
   per Decision 1.
2. Seed: `Map.put_new(datamodel, id, nil)` over every
   `%Machine.Data{}` in `machine.data_elements`.
3. Build **one** `Evaluator.context/1` for the whole pass - B.2.2's "Ordering
   dependencies between `<data>` elements are not permitted" is what licenses
   this, and it belongs as a comment at the build site, since
   `docs/datamodel.md`'s "once per evaluation site" rule would otherwise read
   as prohibiting it.
4. Bind, in ascending `d_index` order: under `:early` every `d_index`, under
   `:late` only `Machine.at(machine, 0).data`. Skip a top-level `d_index` whose
   id is in `env_ids`.

Returns a bare `MachineState.t()`, not `{machine_state, [effect]}`: binding
produces no effect today (no trace vocabulary entry per "What We're NOT
Doing"), and a permanently-empty list at two call sites would be a shape
invented for symmetry rather than for a caller. Note the reason at the spec.

The failure branch: `{:invalid, error}` and `{:src, uri}` short-circuit to the
error path without evaluating; a `{:compiled, _, _}` goes through
`Evaluator.evaluate/2` and takes the error path on `{:error, _}`. Either way
the id keeps its seeded `nil` and
`MachineState.raise_platform(machine_state, "error.execution", {:data, d_index}, data: reason)`
runs - `raise_platform/4` rather than `raise_internal/4` because spec 5.10.1
classifies `error.*` as a platform event, matching the two existing raise sites
(`lib/statifier/interpreter/content.ex:162-172`,
`lib/statifier/interpreter/selection.ex:527-534`).

#### 2. The cause arm

**File**: `lib/statifier/event/cause.ex`
**Changes**: `origin` gains `{:data, non_neg_integer()}`, documented in the same
shape as the `{:transition, t_index}` arm (`:44-55`): the index resolves through
`Statifier.Machine.data/2`, and the resolved `%Machine.Data{}` carries `id`,
`value`, `location`, and `value_location`, so the cause never duplicates the
location itself. This is ADR-0014 item 4's committed field set reached without
a new struct.

#### 3. The call site

**File**: `lib/statifier/interpreter.ex`
**Changes**: replace the `# interpret's skipped preamble` comment at `:163-165`
with the real call, keeping `executeGlobalScriptElement` named as still-skipped.

**The call is unconditional - `Appendix D`'s `if doc.binding == "early":` gate
moves *inside* `Datamodel.initialize/1`.** This is the one deviation from the
pseudocode's literal structure in this phase, and it needs an inline comment
naming itself as such, because a reader diffing against
`spec-cache/appendix-d.txt:101-102` will otherwise read a missing guard as a
port bug:

```
datamodel = new Datamodel(doc)
if doc.binding == "early":
    initializeDatamodel(datamodel, doc)
```

The deviation is not mechanical in ADR-0002's usual sense (effects, storage of
loop variables) - it is a **semantic** reading of an incomplete pseudocode
block, licensed by three facts that must be stated together at the call site:

1. `initializeDatamodel` has **no procedure body anywhere in Appendix D**, so
   there is no definition of what the guard is guarding. What the guard means
   is decided by prose, not by pseudocode.
2. Spec 5.3.3 makes *creation* unconditional under both bindings ("When
   'binding' is assigned the value \"late\", the SCXML Processor MUST create the
   data elements at document initialization time"), so seeding cannot sit behind
   an early-only guard without violating a MUST.
3. Under `late`, top-level `<data>` has no state entry to defer to - the root is
   never in `statesToEnter` - so binding it here is the only place it can happen
   at all (Decision 7).

So the guard survives, moved: `Datamodel.initialize/1` seeds unconditionally and
binds every `d_index` under `:early`, only the root's under `:late`. Keeping the
guard at the call site instead would leave every top-level `<data>` permanently
unbound in a `binding="late"` document - a bug no corpus test catches, since
`test280`'s root `<data id="Var1"/>` has no value to lose. Phase 4's own
late-binding unit test is the only thing standing between that bug and the
ratchet.

The call sits after `begin_microstep/1` and before `enter_states/2` - so an
`error.execution` raised during binding is stamped macrostep 1, microstep 1,
the same microstep as the initial entry, and lands on the internal queue
*ahead* of anything `<onentry>` raises. That ordering is what `test277` depends
on: its `error.execution` transition must win over the `foo` its `<onentry>`
raises.

## Decisions Taken Without a Human

This plan was produced unattended. Every item below is **decided** - nothing in
it blocks implementation - but each rests on an assumption a human may want to
overturn, and each is recorded here so the assumption is visible rather than
buried in the phase that acts on it.

1. **The `datamodel` attribute allow-list contradicts the bead's literal
   wording.** The bead's acceptance criterion says non-`predicator`/`elixir`
   values "are a validator error". Decision 9 accepts `null`, `ecmascript`, and
   `xpath` as well. *Assumption*: the bead's author did not intend to regress 86
   of the ratchet's 91 entries, and would prefer the check catch typos rather
   than declare 111 corpus files invalid. If the intent really was strict
   rejection, the corpus tooling must rewrite SCION's `datamodel="ecmascript"`
   first, which is its own bead.
2. **`src` is never fetched.** *Assumption*: shipping a conformant failure
   (`error.execution` + empty data element, spec 5.3.2) is better than shipping
   a fetch whose correct timing is disputed between `docs/datamodel.md:22-23`
   and spec 5.3.2, especially since ADR-0003 makes a runtime fetch an effect and
   the one corpus file using `src` names a file the corpus does not contain.
   Research open question 1 stays open; Phase 6 writes it into
   `docs/datamodel.md` rather than resolving it.
3. **Top-level `<data>` binds at initialization even under `binding="late"`**
   (Decision 7). *Assumption*: the spec means what B.2.2 says and Appendix D
   structurally implies, rather than intending top-level data to stay unassigned
   forever under late binding. No corpus test discriminates, so this rests on
   spec reading alone.
4. **`<data>` is the only expression class that defers its compile failure to
   runtime** (Decision 2). *Assumption*: keeping `cond` and `<log expr>` at
   load-time rejection is right because no corpus test asks otherwise and
   changing them would re-decide st-af3.2's landed behavior. If a later bead
   finds a corpus test asserting runtime `cond` failure, that is a separate
   decision, not a bug in this one.
5. **`entered_states` is populated unconditionally**, not only under `late`
   binding (Decision 6). *Assumption*: ADR-0012 constraint 1's "complete,
   inspectable, resumable position" outweighs one `MapSet.put` per state entry.
   A human who disagrees would gate it on `machine.binding`, at the cost of a
   field whose meaning depends on the document.
6. **No `binding=` feature-detector pattern is added.** *Assumption*: an atom
   that is `:supported` from the moment it is introduced cannot gate anything,
   so adding one is noise. A human who wants the detector to be a complete
   inventory of SCXML surface rather than a gate would add it.
7. **A state-scoped `<data>` overrides an environment-supplied key of the same
   id** (Decision 1). *Assumption*: spec 5.3.2 scopes the environment override
   to top-level deliberately. No corpus test exercises the collision.
8. **`_event`'s existing seeding is left alone** despite spec 5.10's "MUST NOT
   bind _event at initialization time until the first event is processed".
   *Assumption*: that is a standing decision with its own recorded reasoning
   (test319) in a module this bead does not otherwise touch, and reopening it
   inside a feature branch would be a direction-level change made invisibly.
