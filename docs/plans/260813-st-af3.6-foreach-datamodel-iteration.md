# `<foreach>` - Implementation Plan

## Overview

Add `<foreach>` as an executable-content element: a new
`Statifier.Document.Foreach` node holding a flat child-content list, a
`Statifier.Machine.Content.Foreach` struct with its
`Statifier.ExecutableContent` implementation in the same file, dense
document-order `c_index`es for the nodes *inside* it, and a runtime that
validates `item`/`index` and `array` before any iteration, declares the loop
variables, and then runs the child block once per element of a value captured
before the loop began.

This is the last Phase 3 executable-content element, and it is deliberately the
*second* composite one. `<if>` (st-af3.5, commits 25dacfd..3e132c4) already paid
every structural cost this element would otherwise have to pay: the recursive
`c_index` assignment (`Statifier.Compiler.assign_content_node/2`), the widened
`contents_acc` entry shape, the three-element `{:error, context, reason}` result
form that keeps a composite node's partial work, the runner's drain, and the
validator's descent-into-partitions helper. `<foreach>` reuses all of it and
adds no protocol change, no runner change, and no ADR-level decision of its own.

Beads issue: `st-af3.6`. There is no research document for this bead; the plan
rests on `docs/plans/260813-st-af3.5-if-elseif-else-conditional-executable-content.md`
(the direct shape template, whose Decisions 1-8 this plan follows rather than
re-argues), on st-af3.4's research
(`docs/research/260813-st-af3.4-assign-deep-path-vivification.md`, the
executable-content pipeline end to end), and on the direct reading recorded
under "Key Discoveries".

## Current State Analysis

- **`<foreach>` parses and is rejected one layer later.** The parser is
  element-agnostic; the allowlist is one map at `lib/statifier/lowering.ex:53-73`,
  which now carries `"if"`, `"elseif"` and `"else"` but not `"foreach"`.
- **The composite-node contract is fully built.**
  `Statifier.ExecutableContent.result` already includes
  `{:error, Context.t(), term()}` (`lib/statifier/executable_content.ex`), and
  `Statifier.Interpreter.Content.run_nodes/2`
  (`lib/statifier/interpreter/content.ex:174-193`) halts on it while keeping the
  node's own `new_context` - which is exactly what "an error inside an iteration
  stops the loop, keeping mutations already made" needs.
  `docs/architecture.md:106-124` states the widened signature.
- **`Statifier.Machine.Content.If`'s `run_partition/2`
  (`lib/statifier/machine/content/if.ex:171-186`) is the fold to copy.** It
  resolves each `c_index` through `Statifier.Machine.content/2`, dispatches
  through `Statifier.ExecutableContent.execute/2`, accumulates effects in
  document order, and halts wrapping the failure as
  `{:nested_content, c_index, reason}`. Its moduledoc's four reasons for not
  recursing through the block runner apply verbatim to `<foreach>`.
- **`c_index` assignment already recurses.** `Compiler.assign_content_node/2`
  (`lib/statifier/compiler.ex:505-528`) has a `%DIf{}` clause that takes the
  composite's own `c_index` first and then walks its children;
  `contents_acc`'s value type (`lib/statifier/compiler.ex:137-142`) already
  carries a composite entry shape, `%{if: DIf.t(), branches: [[c_index]]}`.
- **The validator's nested-content gap is already closed for `<if>`, and the
  helper says `<foreach>` is next.** `lib/statifier/validator/checks/assign.ex:76-100`
  is `descend/1`, with a comment stating "`<foreach>` will be the next composite
  executable-content element; when it lands, it gets a clause here alongside
  `%DIf{}` rather than a second walk elsewhere", and enumerating exactly which
  other checks do *not* need it.
  `lib/statifier/validator/checks/if.ex:90-97` has its own `collect_ifs/1` with
  the same shape and the same gap.
- **`<assign>` already owns the datamodel-write seam.**
  `lib/statifier/machine/content/assign.ex:76-91` writes into the raw
  `machine_state.datamodel` and rebuilds `Evaluator.context(machine_state)` so a
  later node in the same block sees the write - the "context invalidation" the
  bead names. It also refuses to create an undeclared top-level root
  (`check_root/3`, `:167-173`) and refuses a `_`-prefixed root
  (`check_system_variable/1`, `:145-153`).
- **Feature registry**: `foreach_elements: :unsupported`
  (`test/support/feature_detector.ex:91`); the detector regex
  `{~r/<foreach(\s|>|\/>)/, :foreach_elements}` (`:151`) already exists.
  `conditional_transitions:` (`:68`) is still `:unsupported`.
- **Eight generated corpus files carry `:foreach_elements`** - seven W3C
  (`test150`, `151`, `152`, `153`, `155`, `156`, `525`) and one SCION
  (`foreach/test1`). **All eight also carry `:conditional_transitions`.**
- `changelog.d/` contains no `st-af3.5.md`: the `<if>` branch decided no
  fragment was owed for a re-implemented v1 feature.

## Desired End State

A document containing `<foreach array="..." item="..." [index="..."]>` compiles
and runs: an illegal `item`/`index` name or a non-iterable `array` fails the
element *and the enclosing block* with `error.execution` before a single child
node runs; `item` (and `index`) are declared in the datamodel if absent and stay
bound after the loop; the loop iterates a value captured before the first
iteration, so a write to the array's own source inside the body does not change
the iteration; each iteration writes `item` (and the 0-based `index`) through the
same raw-datamodel-write-plus-context-rebuild path `<assign>` established, so the
body and the next iteration both see it; a child failure stops the loop and the
enclosing block while keeping every mutation already made; and `<foreach>` nests
with `<if>` in both directions.

Verification: the six new/extended internal test files listed under "Testing
Strategy" pass; `test/statifier/statifier_foreach_test.exs` (Phase 3) drives the
exact XML of the seven W3C corpus documents named under "Corpus/Ratchet Notes"
through `Statifier.compile/1` + `initialize/2` + `send_event/2` and reaches the
same final configurations those files assert, *without* going through the feature
gate; and `mix quality` plus `mix test.regression` are green throughout.

### Key Discoveries

- **Spec 4.6.2's attribute table** (quoted from `spec-cache/scxml-rec.html`):

  > **array** / required `true` / Value expression / A value expression that
  > evaluates to an iterable collection. The `<foreach>` element will iterate
  > over a shallow copy of this collection.
  >
  > **item** / required `true` / `xsd:string` / Any variable name that is valid
  > in the specified data model. A variable that stores a different item of the
  > collection in each iteration of the loop.
  >
  > **index** / required `false` / `xsd:string` / Any variable name that is
  > valid in the specified data model. A variable that stores the current
  > iteration index upon each iteration of the foreach loop.

- **Spec 4.6.3 is the whole runtime, in three paragraphs**:

  > The children of `<foreach>` consist of one or more items of executable
  > content. (Note that they are considered to be part of the same block of
  > executable content as the parent `<foreach>` element.)

  > The SCXML processor MUST declare a new variable if the one specified by
  > 'item' is not already defined. If 'index' is present, the SCXML processor
  > MUST declare a new variable if the one specified by 'index' is not already
  > defined. If 'array' does not evaluate to a legal iterable collection, or if
  > 'item' does not specify a legal variable name, the SCXML processor MUST
  > terminate execution of the `<foreach>` element and the block that contains
  > it, and place the error error.execution on the internal event queue.

  > The SCXML processor MUST act as if it has made a shallow copy of the
  > collection produced by the evaluation of 'array'. Specifically,
  > modifications to the collection during the execution of `<foreach>` MUST NOT
  > affect the iteration behavior. The SCXML processor MUST start with the first
  > item in the collection and proceed to the last item in the iteration order
  > that is defined for the collection. (This order depends on the data model in
  > use.) For each item in turn, the processor MUST assign it to the item
  > variable. (Note that the assigned value MAY be null or undefined if the
  > collection contains a null or undefined item.) After making the assignment,
  > the SCXML processor MUST evaluate its child executable content. It MUST then
  > proceed to the next item in iteration order. If the evaluation of any child
  > element causes an error, the processor MUST cease execution of the
  > `<foreach>` element and the block that contains it.

  Two clauses in that block are load-bearing here and easy to skim past: the
  parenthetical "considered to be part of the same block of executable content
  as the parent `<foreach>` element", which settles Decision 4 the way `<if>`'s
  Decision 3 had to be *argued* from 4.9's example; and "cease execution of the
  `<foreach>` element **and the block that contains it**", which says the same
  thing again for the failure path.

- **Spec 4.9's block rule is unchanged and still governs the enclosing block**:

  > The SCXML processor MUST execute the elements of a block in document order.
  > If the processing of an element causes an error to be raised, the processor
  > MUST NOT process the remaining elements of the block. (The execution of
  > other blocks of executable content is not affected.)

- **Appendix D has no `foreach` and no `executeContent` procedure body.**
  `grep -i foreach` over `spec-cache/appendix-d.txt` returns **zero** hits, and
  the five `executeContent` hits (`:173,271,296,315,319`) are all call sites. So
  ADR-0002's Appendix D rule applies vacuously, exactly as st-af3.4 and st-af3.5
  each recorded: 4.6's prose is the port source, and this plan names no deviation
  from Appendix D.

- **`<foreach>` produces no *non-fatal* errors at all.** Every failure 4.6.3
  names is fatal to the element and to its block. Spec 5.9.1's non-fatal channel
  (`context.pending_errors`) exists and is drained by the runner, but `<foreach>`
  never *adds* to it - it only has to forward what a nested `<if>` put there,
  which the three-element error form does for free. This element therefore needs
  **no protocol change and no runner change**, unlike st-af3.5's Phase 1.

- **The corpus pins every semantic this plan decides**, which is the material
  difference from st-af3.5 (where several decisions had no corpus witness):

  | Document | Pins |
  |---|---|
  | `test150` | `item` declared when absent; still bound after the loop (`Var4 !== undefined`) |
  | `test151` | same for `index` (`Var5 !== undefined`) |
  | `test152` | non-iterable `array` (`7`) and illegal `item` (`'continue'`) each raise `error.execution` **and halt the enclosing block** - the `<raise>` after the `</foreach>` must not fire - **and run zero iterations** (`Var1==0`) |
  | `test153` | iteration order, item assignment, and an `<if>` nested inside a `<foreach>` |
  | `test155` | an `<assign>` in the body accumulates across iterations (`Var1==6` over `[1,2,3]`) - so a write in iteration *n* must be visible in iteration *n+1* |
  | `test156` | a mid-loop child error stops the loop and the block **keeping prior mutations** (`Var1==1`) - the corpus proof of the three-element error form st-af3.5 had to justify without one |
  | `test525` | the shallow copy: appending to the array's own source variable in the body must not extend the iteration (`Var2==3`) |
  | SCION `foreach/test1` | 0-based `index` (`indexSum === 10` over five elements), and a second `<foreach>` with no `index` at all |

- **`index` is 0-based**, and SCION `foreach/test1` is the only witness:
  `myArray = [1,3,5,7,9]`, `indexSum` accumulates `index` over five iterations,
  and the transition's cond requires `indexSum === 10` - which is `0+1+2+3+4`,
  not `1+2+3+4+5`. This is also what "the iteration order that is defined for the
  collection" means for a list under the ECMAScript-shaped datamodel predicator
  models (ADR-0004).

- **`<foreach>` with no children is legal in practice.** 4.6.3 says "one or more
  items of executable content", but the W3C's own `test150` and `test151` both
  write `<foreach item="Var1" index="Var2" array="Var3" />` self-closed. Their
  entire point is that the declaration MUST still happen. So the empty case is a
  first-class supported shape, not an error - see Decision 6.

- **`<assign>`'s root-existence rule and `<foreach>`'s declaration MUST are not
  in tension.** `Statifier.Machine.Content.Assign`'s `check_root/3`
  (`lib/statifier/machine/content/assign.ex:167-173`) refuses to create an
  undeclared top-level variable, because 5.9.2 requires an unresolvable location
  to fail and `test286` pins it. 4.6.3 separately and explicitly *requires*
  `<foreach>` to declare `item`/`index`. Two different clauses about two
  different elements; `<foreach>` declares directly rather than routing through
  `<assign>`'s checks (Decision 2).

- **Predicator 5.0.0 has what the corpus needs**: `concat/2`
  (`deps/predicator/lib/predicator/functions/system_functions.ex:93`, used by
  `test525`), `===`/`!==` (`deps/predicator/lib/predicator/lexer.ex:287,302`)
  and `&&`/`||` (`:337,347`, used by SCION `test1`), and the `undefined` literal
  (st-unt, `docs/datamodel.md:121-131`) the `!== undefined` boundness conds in
  `test150`/`test151` rely on.

- Constraints: ADR-0002 (Appendix D port; no `foreach`, no `executeContent`
  body), ADR-0003 (pure core, effects out, the runner is the sole
  `error.execution` conversion site), ADR-0004 (predicator is the datamodel),
  ADR-0011 (the ratchet only grows; a guarded-path change needs a ledger entry),
  ADR-0012 constraints 3 and 4 (`c_index` and locations on the Machine; a
  diagnostic names the failing node), ADR-0014 items 1-4 (compiled-expression
  shape, spans, error identity).

## Decisions

No human was available while this plan was written. Every question this bead
raises is decided here, with its rationale, so nothing is left for the
implementer to discover. Decisions inherited unchanged from st-af3.5 are named
rather than restated.

**Inherited without change, and not re-argued here** (see that plan for the full
accounting): its Decision 1 (a composite node folds its own children rather than
calling `Statifier.Interpreter.Content.execute_block/3` - all four reasons apply
verbatim, and reason 1 is *more* binding here, since `test155` requires a write
in iteration *n* to be visible in iteration *n+1* within one `<foreach>`); its
Decision 2 (children get their own dense `c_index`es, and the `contents_acc`
entry carries the assigned index list); its Decision 4 (a child failure keeps the
inner node's identity through a `{:nested_content, c_index, reason}` wrapper);
and its Decision 6 (an expression attribute compiles at Machine-build time and a
compile failure fails the document).

**Decision 1 - `item` and `index` legality is a *runtime* check, not a lowering
or validator error.** Both are plain `xsd:string` attributes known at parse time,
so a validator check is technically possible and is nonetheless wrong: `test152`
writes `<foreach item="'continue'" index="Var3" array="Var5">` in a document that
MUST still compile, still run, and still reach `pass` by way of the
`error.execution` the illegal name produces at runtime. A validator error would
fail the whole document and make that test unreachable. 4.6.3 is explicit about
the mechanism too - "MUST terminate execution of the `<foreach>` element ... and
place the error error.execution on the internal event queue" is a runtime
sentence, not a conformance-of-the-document sentence.

The legality test is `~r/\A[A-Za-z_][A-Za-z0-9_]*\z/` applied to the attribute
string, plus the `_`-prefix rejection `<assign>` already performs for the same
5.10 reason (`lib/statifier/machine/content/assign.ex:145-153`), reported with
the same `{:system_variable, name}` reason so a diagnostic consumer sees one
vocabulary. Rationale for that particular regex: it is the intersection of the
ECMAScript identifier grammar (minus `$` and Unicode, neither of which any corpus
document or predicator identifier uses) and predicator's own bare-identifier
shape, and it rejects `'continue'` for the reason 4.6.3 means - a quoted string
literal is a *value*, not a variable name. A dotted path such as `foo.bar` is
also rejected: 4.6.2 says "variable name", `<assign location>` is the element for
writing into a path, and nothing in the corpus writes one. The reason atoms are
`{:illegal_item_name, item}` and `{:illegal_index_name, index}`, distinct so a
diagnostic names which attribute was wrong.

**Decision 2 - `<foreach>` declares and writes `item`/`index` itself, with
`Map.put_new/3` and `Map.put/3` on the raw `machine_state.datamodel`, not through
`<assign>`'s path machinery.** `item` is a bare variable name by Decision 1, so
there is no path to resolve and `Predicator.context_location/3` +
`ContextLocation.put/3` would buy nothing. More importantly, `<assign>`'s
`check_root/3` would *refuse* the very write 4.6.3 requires - the whole point of
`test150`/`test151` is that an undeclared `item`/`index` gets created. The
declaration is `Map.put_new(datamodel, name, nil)` (the same shape
`Statifier.Interpreter.Datamodel.seed/2` uses for `<data>` with no value,
`lib/statifier/interpreter/datamodel.ex:143-146`, so an undeclared-then-declared
variable reads exactly like `<data id="x"/>`); the per-iteration write is
`Map.put/3`.

What *is* shared with `<assign>` - and this is the half of the bead's "same
datamodel-write path" sentence that matters - is the seam around the write:
every mutation lands on the **raw** `machine_state.datamodel` (never on the
normalized `%Predicator.Context{}`, whose `:undefined` normalization would round
-trip `nil` wrongly - st-af3.4's Decision 2), and the block's
`datamodel_context` is rebuilt with `Evaluator.context(machine_state)` afterward.
Without that rebuild `test155` fails: iteration 2's `Var1 + Var2` would read
iteration 1's stale context.

**Decision 3 - the rebuild happens once per iteration, not once per write.** An
iteration writes `item`, optionally `index`, and then runs the body. Writing both
and rebuilding once is one `Evaluator.context/1` call per iteration rather than
two, and no observer can tell the difference: nothing runs between the two writes.
The declaration pass before the loop rebuilds once more, so an empty array still
leaves the block's context aware of the newly declared names. Total rebuilds:
`1 + length(collection)` per `<foreach>`, plus whatever `<assign>` nodes in the
body do on their own. See "Performance Considerations".

**Decision 4 - a child failure halts the enclosing block, and `<foreach>` returns
the three-element error form.** Unlike st-af3.5's Decision 3, this needs no
argument from 4.9's example: 4.6.3 says it twice in its own words ("considered to
be part of the same block of executable content as the parent `<foreach>`
element"; "MUST cease execution of the `<foreach>` element **and the block that
contains it**"). The three-element `{:error, context, reason}` form is what keeps
the mutations already made - `test156` is the corpus proof, requiring `Var1==1`
after the loop aborts mid-iteration. The two-element form would discard them and
turn `test156` red, so this is mechanically forced, not stylistic.

The wrapper is `{:nested_content, failing_c_index, reason}` - byte-identical to
`<if>`'s. The alternative considered and rejected was a `<foreach>`-specific
`{:foreach_iteration, iteration_index, c_index, reason}` carrying which pass
failed: it would split the nested-content vocabulary across composite elements
for a diagnostic detail nothing consumes today, and the iteration is already
recoverable from the datamodel's own `index` variable when the author declared
one.

**Decision 5 - `array` is evaluated exactly once, before the first iteration, and
the resulting value is the iteration source.** This is 4.6.3's shallow copy, and
in an immutable language it costs nothing: an Elixir list *is* a snapshot, so
"modifications to the collection during the execution of `<foreach>` MUST NOT
affect the iteration behavior" is satisfied by not re-evaluating `array` per
iteration. `test525` is the witness - its body appends to `Var1`, the array's own
source variable, and the loop must still run exactly three times. The
implementation comment must say *why* this is free rather than leaving a reader to
wonder whether a copy was forgotten.

"A legal iterable collection" is `is_list/1` and nothing else. Predicator's value
types (ADR-0004) give lists as the only ordered collection with a defined
iteration order; a map has no order the spec's "iteration order that is defined
for the collection" could name, and no corpus document iterates one. A non-list
value returns `{:error, {:not_iterable, value}}` - `test152`'s `array="Var4"` with
`Var4 = 7`.

**Decision 6 - validation order is item, then index, then array; and an empty
`<foreach>` is legal.** The order is unobservable in the corpus (`test152`'s two
states isolate each failure), so it is chosen for cheapness: the two name checks
are pure string tests needing no evaluation. Declaration happens *after* all three
checks pass, so a `<foreach>` that fails validation declares nothing - which
matches "MUST terminate execution of the `<foreach>` element" reading the
termination as covering the declaration too, and is unobservable either way since
the block dies with it.

On the empty case: 4.6.3's "one or more items of executable content" is
contradicted by the W3C's own `test150`/`test151`, which self-close `<foreach>`
precisely to isolate the declaration MUST. No lowering error, no validator error,
no warning. An empty `content` list folds to `{:ok, context, []}` per iteration,
so an empty `<foreach>` over `[1,2,3]` is three declarations-and-writes and
nothing else - and leaves `item` bound to the last element, which is exactly what
`test150` asserts.

**Decision 7 - no new validator check module.** Everything 4.6 forbids is either
a lowering error (a missing required `array` or `item`, following
`build_if/2`'s required-attribute shape) or a runtime error (Decision 1). There is
no ordering constraint among children, no cardinality rule that survives
Decision 6, and no cross-element rule. Phase 2 therefore extends the two existing
checks that walk executable-content *nodes* rather than adding a third file. The
`<if>` element needed `Statifier.Validator.Checks.If` because 4.3.2 has a
document-level MUST (`<else>` after all `<elseif>`s) with no runtime counterpart;
4.6 has none.

**Decision 8 - `Statifier.Document.Foreach` carries a flat `content` list, not a
branch struct.** `<if>` needed `Statifier.Document.If.Branch` because a partition
carries its own `cond`, its own span, and its own `attribute_locations`
(st-af3.5's Decision 8). `<foreach>` has exactly one child block and three
attributes that all belong to the `<foreach>` element itself, so `content` is
`[Document.content_node()]` directly and the Machine node's is `[c_index]`
directly. The `contents_acc` entry is correspondingly `%{foreach: DForeach.t(),
content: [non_neg_integer()]}` - the same *shape* as the `<if>` entry, one nesting
level shallower.

## What We're NOT Doing

- **Not flipping `conditional_transitions`, not running the full conformance
  suites, and not touching `test/passing_tests.json`.** Bead **st-af3.8** owns
  all three by name, including `foreach_elements` itself. Phase 3 flips
  `foreach_elements` only, because flipping it costs nothing (zero files unblock
  either way, since all eight also trip `conditional_transitions`) and leaving
  the registry lying about a landed feature is worse. If st-af3.8 has already
  flipped it by the time this phase runs, Phase 3's registry edit is a no-op and
  the phase drops it - say so in the commit rather than reverting anything.
- Not adding a `Statifier.Validator.Checks.Foreach` module (Decision 7).
- Not widening the `Statifier.ExecutableContent` protocol, the
  `Statifier.ExecutableContent.Context` struct, or
  `Statifier.Interpreter.Content`. st-af3.5's Phase 1 built the composite-node
  error model; `<foreach>` is its second consumer and needs nothing new. If any
  phase here finds itself editing `lib/statifier/interpreter/`, that is a signal
  the design drifted, not a licence.
- Not making `Trace.ContentExecuted` report the nodes inside a `<foreach>` body,
  or the iteration count. Same reasoning as st-af3.5's identical exclusion: the
  trace list is the runner's record of what *it* dispatched, and a consumer
  resolves the body through `Machine.content/2` from the `<foreach>`'s own
  `c_index`. A per-iteration trace event is not in
  `docs/observability.md:57-68`'s minimum vocabulary.
- Not extracting the child-node fold now shared three ways
  (`Interpreter.Content.run_nodes/2`, `Machine.Content.If.run_partition/2`, and
  this element's own). st-af3.5's Decision 1 closing paragraph gives the reason -
  every candidate shared home either inverts the layering or makes a runner-only
  helper whose other callers are all leaves. A third instance strengthens the
  temptation without changing the argument; if a fourth composite element ever
  lands, revisit it as its own bead rather than inside an element's plan.
- Not guarding against an unbounded iteration. A `<foreach>` over a very large
  array is a document's own choice; `docs/adr/0019-*`'s macrostep round budget
  bounds livelock at the *round* level and does not apply inside one block, and
  SCION's `foreach/test1` comment explicitly frames loop termination as the
  application's responsibility.
- Not implementing `<send>`, `<cancel>`, `<invoke>`, or `<script>` (the last
  permanently unsupported, ADR-0004).

## Implementation Approach

Three phases, split along the boundaries `.claude/wurk/plan.md` names.

Phase 1 is the parser/compiler/runtime vertical slice, and it is deliberately not
split further, for the same mechanical reason st-af3.4's Phase 1 and st-af3.5's
Phase 2 each took: widening `Statifier.Document`'s `content_node` union
(`lib/statifier/document.ex:100`) without adding the matching
`build_content_node/2` clause and widening `acc()`'s `contents_acc`
(`lib/statifier/compiler.ex:137-142`) leaves a Document node type flowing into a
function whose `@spec` excludes it - which dialyzer reports and which would make
the intermediate commit's gate red. The skill's own rule applies: combine rather
than split when the intermediate gate cannot be green.

Phase 2 is validator-side and separable: it widens two existing checks'
traversal, with nothing in Phase 1 depending on it. It is independently
gate-verifiable because each widening comes with a test that is red before it and
green after.

Phase 3 is the corpus-tooling/documentation boundary - the feature flag, the
conformance-shaped internal tests, the changelog decision - and is separable
because the conformance suites are excluded from `mix test` by default
(`test/test_helper.exs`) and this phase does not touch the ratchet at all.

There is no interpreter-side phase, and that absence is the plan's main claim: if
one appears during implementation, stop and re-read "What We're NOT Doing".

Every new test asserting `lib/` behavior carries a sabotage note per
`docs/testing.md:80-136` - one line directly above the `test` line and above any
`@tag`. Suggested mutations are given per phase so the implementer does not have
to invent one.

## Phase 1: `<foreach>`, end to end

### Overview

`<foreach>` parses, lowers into a node with a flat child list, compiles with
dense body `c_index`es and a compiled `array` expression, and at runtime
validates, declares, and iterates per spec 4.6.3.

parenthetical, and state that `content` is the flat child list in document order
(no partitioning, unlike `<if>`).

defmodule Statifier.Document.Foreach do

## Performance Considerations

A `<foreach>` costs one `Predicator.evaluate/3` call for `array`, plus
`1 + length(collection)` `Evaluator.context/1` rebuilds (one for the declaration
pass, one per iteration - Decision 3), plus whatever the body's own nodes cost.
`Evaluator.context/1` deep-normalizes the whole datamodel on every call
(`lib/statifier/evaluator.ex`'s "Never scoped to a whole macrostep" section), so
a `<foreach>` over a large array against a large datamodel is the first
construct in this engine whose cost is *multiplicative* rather than additive -
worth naming even though nothing evaluates in a hot path yet and there is
nothing to measure.

The fix, when something needs measuring, is the seam already recorded in
`docs/datamodel.md:95-110` and owned by **st-sdh**: predicator 5.0.0's
`Context.bind/3` and `Context.put_host/2` are O(1) rebinds, so a per-iteration
rebuild could become a rebind rather than a rebuild. Do **not** take that seam in
this bead - it would change every context-building call site in the tree for a
benchmark nobody has run. Add a one-line pointer to st-sdh in the loop's comment
so the next reader finds the answer instead of inventing one.

- `test/statifier/machine/content_test.exs` - the compiled `%MForeach{}`, its

  `array` failing `compile/1`
- `test/statifier/machine/content/foreach_test.exs` (new) - the protocol leaf,
  where the validation/declaration/iteration matrix lives
- `test/statifier/validator/checks/assign_test.exs` and
  `test/statifier/validator/checks/if_test.exs` - the widened-traversal
  regressions
- `test/statifier/interpreter/content_test.exs` - the three end-to-end block
  behaviors through the real runner
- `test/statifier/statifier_foreach_test.exs` (new) - the seven W3C corpus
  documents, end to end through the public API

Key edge cases, most at the leaf: an illegal `item` (quoted literal, dotted path,
`_`-prefixed); an illegal `index`; a non-iterable `array`; an `array` expression
that errors; an empty collection (declaration still happens, body never runs); a
single-element collection; an omitted `index`; a body that writes the array's own
source variable; a body that writes the `item` variable itself; a body whose
second node fails on the first iteration; a body whose node fails on the *third*
iteration, with the first two iterations' mutations intact; an `<if>` inside a
`<foreach>` and a `<foreach>` inside an `<if>`; a `<foreach>` inside a
`<foreach>`.

Every one of these tests carries a sabotage note per `docs/testing.md:80-136` -
one line directly above the `test` line and above any `@tag`, naming a mutation a
reasonable person could make by mistake. Per-phase suggestions are given inline
above. Generated corpus files are exempt and get no notes.

### Manual Testing Steps

1. In `iex -S mix`, build a chart with
   `<datamodel><data id="a">[1,2,3]</data><data id="s" expr="0"/></datamodel>`
   and `<onentry><foreach array="a" item="i" index="n"><assign location="s" expr="s + i"/></foreach><log expr="s"/></onentry>`,
   and confirm the log reads `6` - accumulation across iterations, and the write
   visible after the `</foreach>` in the same block.
2. Confirm `i` reads `3` and `n` reads `2` after the loop - `item`/`index` stay
   bound, and `index` is 0-based.
3. Replace the body with `<assign location="a" expr="concat(a, [4])"/>` and a
   counter, confirming the counter reaches `3`, not `4` - the shallow copy.
4. Set `array` to a plain `7` and confirm one `error.execution` on the internal
   queue **and** that a `<raise>` written after the `</foreach>` never fires.
5. Set `item` to `'continue'` and confirm the same, with the body having run zero
   times.
6. Put a failing `<assign location="undeclared" expr="1"/>` as the body's second
   node and confirm the counter its first node increments reads `1` afterward -
   mutations survive the abort.
7. Nest a `<foreach>` inside an `<if>` inside a `<foreach>` and confirm the
   `c_index`es reported in a `Trace.ContentExecuted` for the enclosing block name
   only the outer `<foreach>`, with the inner nodes resolvable through
   `Machine.content/2`.

## Open Questions

None remain open in the sense of blocking implementation: every question this
bead raises is decided above, and the two that a human might have answered
differently are recorded here with the assumption taken, so a reviewer can
overturn either without re-deriving the context.

1. **How strict should "a legal variable name" be?** Decided in Decision 1 as
   `~r/\A[A-Za-z_][A-Za-z0-9_]*\z/` plus the `_`-prefix rejection. **Assumption
   taken**: rejecting `$` and Unicode identifiers is safe because the datamodel
   is predicator, not ECMAScript (ADR-0004), and no corpus document uses either.
   If a future corpus document writes `<foreach item="$x">`, widen the regex
   rather than special-casing that document.
2. **Should a map be an "iterable collection"?** Decided in Decision 5 as no -
   `is_list/1` only. **Assumption taken**: 4.6.3's "the iteration order that is
   defined for the collection" presupposes a defined order, and predicator maps
   have none. If a future document iterates a map, that is a new decision about
   which order, not a widening of this one.

Two things are recorded as accepted risks rather than open questions, because a
decision has been made and the reason is written down: the **residual risk** that
the seven W3C documents are asserted-from-reading rather than run
("Corpus/Ratchet Notes"), and the narrower risk that **SCION `foreach/test1`**'s
raw ECMAScript syntax does not evaluate under predicator (Phase 3, change 1).

One item is a **handoff, not a question**: whether `conditional_transitions`
flips before or after this branch lands is st-af3.8's call, and Phase 3 is
written to be correct either way.
