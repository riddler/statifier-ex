# Handler-registry invoke as an extension - Implementation Plan

## Overview

Give hosts a supported way to register `<invoke>` handlers for types beyond
`scxml`, so that "real computation belongs in the host application, reached
through `<invoke>` handlers" (`docs/datamodel.md:17`) names a seam that
actually exists. `type=scxml` becomes the built-in registered handler with
today's child-session mechanics behind that interface; an invoke whose
resolved type names no registered handler keeps raising `error.execution`;
and the seam gets a user-facing document plus a changelog fragment.

Bead: `st-cmq.8`.

## Current State Analysis

`<invoke>` is already split across two layers with a clean instruction seam
between them. The research document
(`docs/research/260818-st-cmq.8-handler-registry-invoke.md`) is the ground
truth for the shape; the load-bearing facts this plan builds on were
re-verified against the tree at `463fb45`.

**The pure core** decides *that* an invocation starts, is cancelled,
autoforwarded to, or finalized. `run_invoke_pass/1`
(`lib/statifier/interpreter.ex:1279-1312`) runs Appendix D's `statesToInvoke`
pass; `invoke_one/6` (`:1362-1418`) ports 6.4's `invoke(inv)`;
`generate_invoke_id/3` (`:1491-1512`) is the single mint site and reads
`machine_state.invoke_counter` (`lib/statifier/machine_state.ex:128-167`), a
deterministic counter rather than a UXID per ADR-0008 as amended. The core
emits `%Effect.Invoke{}`, `%Effect.CancelInvoke{}`, `%Effect.Autoforward{}`
and two trace effects. It never starts a process and never dereferences a URI.

**`Statifier.Session.Effects.plan/2`** is a *pure* planner turning those
effects into instruction tuples - `{:start_child, invoke, effect}`,
`{:stop_child, invoke_id}`, `{:forward, invoke_id, event}`,
`{:raise, :platform, "error.execution", origin, opts}`.
`Statifier.Session.perform_instruction/3` is one executor of that vocabulary;
`Statifier.Replay`'s no-op performers (`lib/statifier/replay.ex:453-492`) are
already a second. So "define the behaviour against the effect vocabulary, not
Session internals" (bead note 1) is a matter of naming an existing
planner/executor split as a contract, not of inventing a layer.

**The type gate is a hardcoded three-way string test.**
`Statifier.Send.Target.supported_invoke_type?/1`
(`lib/statifier/send/target.ex:129-132`) answers `true` for `nil`, `"scxml"`,
and the bare `http://www.w3.org/TR/scxml/` URI, `false` for everything else
including `#SCXMLEventProcessor`. It has exactly two callers:
`maybe_record_active_invocation/5` (`lib/statifier/interpreter.ex:1583-1596`,
core bookkeeping - an unsupported type is not recorded live) and
`plan_invoke/2` (`lib/statifier/session/effects.ex:208-218`, the actual
rejection). ADR-0047 decision 4 is why they cannot drift: "The two sites apply
one shared classifier, so they cannot drift."

**What is missing** is everything that makes a non-scxml type possible: no
project-authored `@callback` exists anywhere in `lib/`; there is no
`Application.get_env`, no `compile_env`, and no `config/` directory at all -
every option is threaded through `start_link/2` opts; `Statifier.Invoke.Source`
resolves to a `Machine.t()`, which is meaningful only for an SCXML-typed
service; `done.invoke.<id>` is constructed only from a child session's done
effect (`lib/statifier/session.ex:1393-1407`); and
`Statifier.Session.Invocations`' entry type (`session_id, pid, monitor_ref,
autoforward`, `lib/statifier/session/invocations.ex:46-59`) assumes a pid.

### Key Discoveries

- **Section 6.4 contains neither error name.** Flattening
  `spec-cache/scxml-rec.html` and slicing section 6.4 (11,256 characters,
  from "6.4 `<invoke>` [This section is normative.]" to "6.5 `<finalize>`")
  yields zero occurrences of `error.execution` and zero of
  `error.communication`. The bead's "per spec 6.4" citation has no referent.
  See "The error event, decided" below.
- **6.4's own type prose is permissive**, quoted from the cache: "Platforms
  MUST support http://www.w3.org/TR/scxml/ as a value for the 'type'
  attribute. ... Platforms MAY support additional values, but they SHOULD
  assign them the URI of a description of the relevant service. Processors MAY
  define short form notations as an authoring convenience". Registering
  additional types is the spec's own sanctioned extension, not a deviation.
- **6.4 makes `<param>`/namelist interpretation platform-specific for
  non-scxml types**, quoted from the cache: "For targets of other invoked
  service types, the interpretation of `<param>` and `<content>` elements and
  the 'src' and 'namelist' attributes is platform-specific. However, these
  services MUST treat values specified by `<param>` and namelist identically."
- **Appendix D declares the procedure itself platform-specific**
  (`spec-cache/appendix-d.txt:137-141`): "Here we invoke whatever needs to be
  invoked. The implementation of 'invoke' is platform-specific."
- **ADR-0048 already blessed the shape** for handing the core deployment
  state: a caller-declared, point-in-time *value* on `%MachineState{}`
  (`lib/statifier/send/routes.ex`, field at
  `lib/statifier/machine_state.ex:357`, stamp at `:759-761`), chosen over a
  resolver function on three grounds - a value cannot perform a lookup, so
  ADR-0003 stays structural; replay records one value instead of call-by-call
  answers; and a resolver's freshness advantage is illusory.
- **`MachineState.new/2` already takes `:routes` as an option**
  (`lib/statifier/machine_state.ex:430-431,471`) and
  `Statifier.Session.Recording`'s `@normalized_opts`
  (`lib/statifier/session/recording.ex:111`) already records
  `[:session_id, :trace, :datamodel, :max_macrostep_rounds, :routes]`. A
  per-session value needs no entry widening at all.
- **`:invoke_source` is the precedent for an embedder-supplied per-session
  handler** (`lib/statifier/session.ex:342,447-451,733,1313`): a plain
  function value on session state, `nil` default, contract in prose and a
  typespec, no behaviour wrapping it.
- **The whole internal suite is already ratcheted.**
  `test/passing_tests.json:3-6` holds `internal_tests` as a glob
  (`test/statifier/**/*_test.exs`), so every one of the ~100 invoke tests the
  research enumerates is enforced by `mix test.regression`. 20 of the 27
  mandatory invoke conformance files are ratcheted.
- **Constraint: ADR-0012** - if the registered-type set becomes core-visible
  it must be part of the resumable microstep position, which is exactly
  ADR-0048 decision 2's argument for `Routes` being a struct field.
- **Constraint: ADR-0024/ADR-0038** - the registry must not become a back door
  for the library to fetch `src`. A handler that fetches does so as embedder
  code under embedder policy.
- **Constraint: ADR-0029/ADR-0034** - `Session.interpret/2` is public and
  `Statifier.Replay` is catch-all-free, so any new instruction shape needs an
  explicit `Statifier.Replay` clause.
- **Constraint: ADR-0031** - handler resolution must happen *after* argument
  evaluation succeeds, per invocation.
- **Constraint: ADR-0040 plus a live downstream consumer** - see "The
  cross-repo obligation" below.

## Desired End State

A host writes a module implementing `Statifier.Invoke.Handler`, passes
`invoke_handlers: %{"myapp:enrich" => MyApp.EnrichHandler}` to
`Statifier.Session.start_link/2`, and an `<invoke type="myapp:enrich">` in a
document starts, cancels, autoforwards to, finalizes from, and completes
through that handler with the same core mechanics `type=scxml` uses. With no
`:invoke_handlers` passed, every observable behavior in the repo is
byte-identical to today.

Verified by: the full gate green at every phase; `mix test.regression` green
(the internal glob makes the ~100 existing invoke tests the regression net);
new tests driving a registered test handler end to end through a real session
and through `Statifier.Replay`; and `docs/extending.md` existing with
`docs/datamodel.md` pointing at it.

### The error event, decided

**An invoke whose resolved type names no registered handler raises
`error.execution`, which is today's behavior and does not change. The bead's
citation does.**

The bead's acceptance criterion says "an unknown type raises error.execution
per spec 6.4". The outcome is right; the citation is not, and this plan says
so plainly rather than editing the criterion. Section 6.4 has no
`error.execution` in it (measured above), so the requirement cannot be a 6.4
MUST. Two clauses do apply, both quoted from the local cache:

> Two error events are defined in this specification: 'error.communication'
> and 'error.execution'. The former cover errors occurring while trying to
> communicate with external entities, such as those arising from `<send>` and
> `<invoke>`, while the latter category consists of errors internal to the
> execution of the document, such as those arising from expression
> evaluation. (3.12.2)

> If the SCXML Processor does not support the type that is specified, it MUST
> place the event error.execution on the internal event queue. (6.2.5, for
> `<send>`)

The distinguishing question 3.12.2 poses is whether communication with an
external entity was attempted. For an unregistered type it was not: this
deployment implements no such service, so nothing was ever reached for. That
is the same fact pattern 6.2.5 assigns `error.execution` to for `<send>`, and
6.2.4 confirms the split on the `<send>` side in one sentence - unsupported or
invalid gets `error.execution`, "unable to dispatch" gets
`error.communication`. `<invoke>`'s genuine communication failure already
exists and already raises `error.communication`: `Statifier.Invoke.Source`
failing to resolve `src` (ADR-0038), where the handler *was* found and
reaching the service failed.

So the rule this plan implements, and ADR-0051 records:

| Failure | Event | Ground |
|---|---|---|
| Type names no registered handler | `error.execution` | 3.12.2's "internal to the execution of the document" plus 6.2.5's explicit analogue |
| A registered handler fails to reach its service | `error.communication` | 3.12.2's "trying to communicate with external entities" - already the `Invoke.Source` path |

Choosing `error.execution` also costs nothing in regression: st-5fbw pinned it
at five layers (`test/statifier/send/target_test.exs:99-145`,
`test/statifier/interpreter/invoke_pass_test.exs:485,524`,
`test/statifier/interpreter/cancel_invoke_test.exs:215`,
`test/statifier/session/effects_test.exs:530-571`,
`test/statifier/session/invoke_start_child_test.exs:496-578`), and every one of
those pins stays green.

**What a human should decide, and the plan does not:** whether to correct the
bead's `per spec 6.4` wording. The plan neither edits the acceptance criterion
nor pretends it is right; the implementer proceeds on the outcome, which is
unchanged either way.

### The registry location, decided

**The handler modules live on the session boundary as an `:invoke_handlers`
option; the *set of registered type strings* becomes a caller-declared value on
`%MachineState{}`, stamped once per session rather than once per drive.**

This is the central call, and ADR-0047 decision 5 names this bead as its own
reopen trigger:

> **5. The supported-type set stays static, so 6.2.5's check may run in the
> core.** ... The named reopen trigger: an embedder-registrable processor-type
> set. If that lands, the 6.2.5 check becomes deployment state and moves back
> to the boundary (or into a caller-supplied capability), and this decision is
> re-argued in that record.

Re-argued here, and the answer is a **split**, because decision 5 is about two
different type sets that happen to share a module:

1. **`<send>`'s Event I/O Processor set (6.2.5) stays static, and decision 5
   stands unamended for it.** This bead registers `<invoke>` handlers. It does
   not make `<send type>` registrable, does not add a second Event I/O
   Processor, and does not touch
   `Statifier.Send.Target.supported_type?/1`. Decision 5's trigger fires for
   the `<invoke>` half of `Statifier.Send.Target` only. `<send>`'s check stays
   in `Statifier.Machine.Content.Send.execute/2` where ADR-0047 decision 1 put
   it, and ADR-0047's supersession trigger ("wants the static check somewhere
   other than `execute/2`") does not fire.
2. **`<invoke>`'s type set becomes deployment state**, so
   `supported_invoke_type?/1` can no longer be the whole answer.

Decision 4's anti-drift property is the reason a session-only registry is not
enough. Its two sites are the core's `maybe_record_active_invocation/5` and
the planner's `plan_invoke/2`. If handlers were known only to the session, the
planner would start a registered `myapp:enrich` invocation that the core had
refused to record in `active_invocations` - and then `<finalize>` would never
run for it (`lib/statifier/interpreter.ex:560-564`), it would never be
autoforwarded to (`:621-638`), no `%Effect.CancelInvoke{}` would be emitted on
exit (`lib/statifier/interpreter/exit_entry.ex:330-338`), and
`Trace.InvokePass.invoke_ids` would omit it. That is precisely the drift
decision 4 forbids, and it would silently break the feature this bead exists
to add. So the core must be able to answer "is this type registered", which
means the answer has to reach it as a value.

The shape is ADR-0048's, for ADR-0048's own reasons: a value cannot perform a
lookup, so ADR-0003's purity stays structural rather than by convention; a
value is recordable, so ADR-0034's pure fold is untouched; and a resolver
function inside a core drive would be the first impure call in a drive, which
ADR-0048 decision 1 rejected explicitly.

**Where this plan diverges from ADR-0048, deliberately: the cadence.** `Routes`
is stamped per drive because session liveness changes between drives. The
registered handler set does not - it is a `start_link/2` option, fixed for the
session's lifetime, exactly like `:max_macrostep_rounds`. So it is passed to
`MachineState.new/2` as an option (joining `:routes` at
`lib/statifier/machine_state.ex:430-431,471`) and recorded once in
`Statifier.Session.Recording`'s `@normalized_opts`
(`lib/statifier/session/recording.ex:111`). No recorded entry widens, ADR-0029's
input set does not grow, and `Statifier.Replay` needs no new plumbing beyond
the opts it already replays. Same shape as ADR-0048, smaller blast radius,
because the fact it carries is per-session rather than per-drive.

This is also exactly bead note 4: per-session data rather than a global mutable
registry, multi-tenant hosts get a different palette per chart, and replay
determinism does not depend on handler presence at replay time because the set
is captured in the recording. The rejected alternatives:

- **Session-only opt with no core visibility** - rejected above on ADR-0047
  decision 4 grounds; it breaks finalize, autoforward, cancel, and trace for
  every registered non-scxml type.
- **Delete the core's type gate entirely and record every invocation live** -
  rejected: it un-does st-5fbw's four-layer pinning that an unsupported type is
  not live, and would make `active_invocations` claim invocations that never
  started. That is going green by weakening a check.
- **Global or compile-time registry** - rejected: bead note 4 disprefers it,
  and the repo has no precedent (no `config/`, no `Application.get_env` in
  `lib/`).

**This warrants an ADR**, written as Phase 1: ADR-0051.

### The handler contract, decided

Bead note 3 asks for either documented idempotency expectations or "start
shaped as returned instructions/data so the host owns the IO and the dedup".
This plan takes the second, because the repo already has that shape with two
executors, and it answers the first for free.

`Statifier.Invoke.Handler` defines three **pure planning** callbacks and one
optional **performing** callback:

```elixir
@callback start(invoke :: Effect.Invoke.t(), ctx :: map()) ::
            {:ok, [instruction()]} | {:error, term()}
@callback cancel(invoke_id :: String.t(), ctx :: map()) :: {:ok, [instruction()]}
@callback forward(invoke_id :: String.t(), event :: Event.t(), ctx :: map()) ::
            {:ok, [instruction()]}
@callback perform(instruction :: term(), ctx :: map()) :: :ok | {:error, term()}
@optional_callbacks perform: 2
```

**`ctx` is the plan context, not a new concept**, and its shape is decided
here rather than invented during coding, because it is the most host-visible
half of the contract:

```elixir
@type ctx :: %{
        session_id: String.t(),
        invoke_types: Statifier.Invoke.Types.t() | nil,
        invoke_handlers: %{String.t() => module()}
      }
```

It is the same map `Statifier.Session.Effects.plan/2` threads through its
fold (Phase 2's plan context plus Phase 3's one added key), handed to the
callback unchanged. Three properties the moduledoc must state: it carries
`session_id` because a handler addressing an external system usually needs to
say who is asking; it carries no pid, no `%MachineState{}`, and no session
struct, so a handler cannot reach into Session internals (bead note 1); and it
is a plain map rather than a struct so that adding a key later is additive for
every handler already written. A handler needing per-invocation identity reads
it off `%Effect.Invoke{}` - `invoke_id`, `state_index`, `invoke_index` - not
off `ctx`.

The instruction vocabulary gains exactly one opaque member,
`{:handler, module, term}`, which an executor routes back to `module.perform/2`.
The three planning callbacks stay pure, so a durable host that drives the pure
Interpreter directly (bead note 1, chartered as `st-q6xl`) gets the whole plan
with no process, and `Statifier.Replay` gets an explicit no-op clause for
`{:handler, _, _}` per ADR-0034.

**At-least-once and dedup (note 3), answered rather than deferred:** because
`start/2` is pure and `invoke_id` is a deterministic `%MachineState{}` counter
(ADR-0008 as amended), re-running a drive after a crash produces the byte-identical
instruction, so `invoke_id` is the natural idempotency key. The library performs
no dedup and cannot: it has no view of the host's durable store. The behaviour's
moduledoc states the contract - `perform/2` MAY be called more than once for the
same `invoke_id`, and a handler MUST be idempotent on it. That is the documented
expectation note 3 asks for, and it is honest about who owns it.

### `done.invoke` and `<donedata>` for a non-scxml handler, decided

The handler's host feeds it back through a public
`Statifier.Session.done_invocation/3`, which constructs
`done.invoke.<invoke_id>` with the supplied donedata, stamps `invokeid`, and
enqueues it on the session's external queue - generalizing what
`return_done_event/2` (`lib/statifier/session.ex:1393-1407`) does today for a
child session. The built-in scxml handler routes through the same function, so
there is one construction site rather than two. 6.4's MUST here is on the
*service* ("Once the external service has finished processing it MUST return a
special event 'done.invoke.id'"), not on this engine, so the engine's job is to
provide the door and document the event's shape - which `docs/extending.md`
does. A process-less durable host constructs the event itself against that
documented shape.

### `<finalize>` auto-assign for non-scxml handlers, decided

**It stays unconditional. No code changes; the choice gets written down.**

6.4 makes it platform-specific ("For targets of other invoked service types,
the interpretation of `<param>` and `<content>` elements and the 'src' and
'namelist' attributes is platform-specific"), so both readings conform.
`auto_assign_finalize/5` (`lib/statifier/interpreter.ex:728-759`) runs off the
*arriving event* regardless of type today. Keeping it that way wins on three
grounds: making it type-conditional would give the core a second reason to
consult the registered set, for a case with no consumer; `<finalize>` semantics
would then vary by deployment, which is a strictly worse debugging story under
ADR-0012; and an empty `<finalize/>` is the author's explicit request to
auto-assign, which is the least surprising thing to honor uniformly. Recorded in
ADR-0051 and in a comment above `auto_assign_finalize/5` citing it.

### Naming, decided

`Statifier.Registry` is taken (ADR-0027, session-id lookup), so nothing in this
work is called a Registry in code:

| Concept | Name | Sits beside |
|---|---|---|
| The behaviour | `Statifier.Invoke.Handler` | `Statifier.Invoke.Source` |
| The built-in scxml handler | `Statifier.Invoke.Handler.Scxml` | - |
| The core-visible type set + shared classifier | `Statifier.Invoke.Types` | `Statifier.Send.Routes` |
| The per-session handler map | the `:invoke_handlers` opt, a plain `%{type => module}` on session state | `:invoke_source` |

`docs/extending.md` names the collision in one sentence so a reader searching
for "registry" is not sent to the session-id `Registry`.

### The cross-repo obligation, restated correctly

**Bead note 6's premise does not hold.** It names "the statifier-ui golden
trace corpus" as the regression net for autoforward and finalize. That corpus
is a single two-state chart whose own moduledoc says it was "chosen
deliberately to avoid the `st-r6l9` reordering seam - **no `<invoke>`**"
(`~/repos/github/statifier-ui/test/statifier_ui/trace/golden_trace_test.exs`).
It does not cover invoke at all.

The real regression net is this repo's own: the ~100 internal invoke and
finalize tests the research enumerates, all of them enforced by
`mix test.regression` through `test/passing_tests.json:3-6`'s `internal_tests`
glob, plus the 20 ratcheted mandatory invoke conformance files.

The genuine cross-repo obligation is narrower and is a hard constraint on this
work: `statifier-ui:lib/statifier_ui/trace/normalizer.ex:279-301` reads `p.type`
straight off `%Effect.Invoke{}`. **`%Effect.Invoke{}` may only change
additively** - no field removed, renamed, or retyped - per ADR-0040's event
contract. This plan removes nothing from it and adds nothing to it. Per
CLAUDE.md's cross-repo table, this repo's files change so this repo owns the
decision; there is no paired bead in another tracker, so no `mirrors:` line is
owed.

## What We're NOT Doing

- **Not making `<send type>` registrable.** ADR-0047 decision 5 stands
  unamended for the 6.2.5 Event I/O Processor set; only its `<invoke>` half is
  re-argued. `supported_type?/1` and its placement in
  `Statifier.Machine.Content.Send.execute/2` are untouched.
- **Not adding an invoke-`type` flag to the feature detector.** The detector
  gates *corpus documents*, and no conformance document in the corpus names a
  non-scxml type (the W3C suite exercises only the mandated type). A new
  registry entry would gate a set of zero files, and
  `test/statifier/feature_detector_test.exs:318` asserts no registry entry is
  `:unsupported`, so an `:unsupported` entry would redden the suite and the only
  ways green would be to weaken that assertion or to add a vacuous
  `:supported` entry. No bead is filed: the reopen trigger is a corpus document
  naming a non-scxml type, which would arrive with its own bead, and ADR-0051
  records the trigger the way ADR-0047 and ADR-0048 record theirs.
- **Not deleting the core's type gate.** Recording every invocation live
  regardless of type would un-do st-5fbw's four-layer pinning; it is rejected
  above.
- **Not changing invoke id minting.** Bead note 2's "keep it that way" is
  already the accepted position (ADR-0008 as amended); `invoke_counter` stays a
  `%MachineState{}` counter and nothing here touches it.
- **Not letting a handler make the library fetch a URI.** ADR-0024 and
  ADR-0038 hold: `Statifier.Invoke.Source` becomes an implementation detail
  *of the built-in scxml handler*, not a general resolution path a handler
  inherits. A handler that fetches does so as embedder code.
- **Not shipping the Oban-backed handler base.** Chartered separately as
  `st-rsyx`, which already lists "the registry itself (st-cmq.8, core)" as
  outside its scope.
- **Not shipping the process-less durable stepper.** Chartered as `st-q6xl`.
  This plan makes the contract executable without a Session process; it does
  not build the second executor.
- **Not supporting mid-session handler re-registration.** The set is a
  `start_link/2` option, per bead note 4's per-session preference and per the
  "The registry location, decided" cadence argument. A host needing a different
  palette starts a different session.
- **Not rescuing handler exceptions into error events.** v1 did this
  (`../statifier/lib/statifier/actions/invoke_action.ex:157-166`); it is the
  rescue-to-default at a leaf CLAUDE.md forbids. A handler that raises crashes
  its executor, which is the host's supervision concern.
- **Not filing speculative beads for the deferrals above.** Each one either has
  a chartered bead already (`st-rsyx`, `st-q6xl`) or gets a named reopen
  trigger in ADR-0051, which is how ADR-0047 and ADR-0048 handle theirs.

## Implementation Approach

Five phases, ordered so that each one is green on its own and the previous
behavior never has a window of being wrong.

Phase 1 writes the record, because every subsequent phase cites it. Phase 2
makes the registered-type set core-visible with an empty registration set,
which is a pure refactor of the classifier call sites - every existing pin
stays green and that is the phase's own proof. Phase 3 introduces the behaviour
and the built-in scxml handler and routes *starting* through it. Phase 4
completes the lifecycle - cancel, forward, and `done.invoke` with donedata -
which is where `Statifier.Session.Invocations` learns about a pid-less entry.
Phase 5 is the user-facing document and the changelog fragment, which lands
last because it describes the finished seam.

Phases 3 and 4 are deliberately not merged: each is separately committable and
separately gate-verifiable, and merged they would be one very large phase.
Phase 3 leaves the seam startable but not completable; no changelog fragment
lands until Phase 5, so nothing half-finished is announced to users.

**Appendix D (per `.claude/wurk/plan.md`'s rule):** this plan introduces **no
deviation** from the Appendix D pseudocode. `run_invoke_pass/1`,
`invoke_one/6`, `apply_invoke_passes/2`, and `apply_finalize/5` keep their
structure line for line; the only core change is what
`maybe_record_active_invocation/5` consults, and that function is already an
acknowledged, comment-documented mechanical addition to Appendix D's `invoke`
(which the pseudocode itself declares platform-specific:
`spec-cache/appendix-d.txt:137-141`).

## Phase 1: ADR-0051, the invoke handler seam

### Overview

Write the decision record every later phase cites, and re-argue ADR-0047
decision 5 in it. Documentation only.

### Changes Required:

#### 1. The record
**File**: `docs/adr/0051-invoke-handlers-are-registered-per-session.md`
**Changes**: New accepted ADR. Status line notes it re-argues ADR-0047
decision 5 in part (scoped to `<invoke>`; the `<send>` 6.2.5 set is untouched)
and extends ADR-0048's snapshot shape to a second consumer at a per-session
cadence. Decisions, each with its ground:

1. An unregistered invoke type raises `error.execution`, on 3.12.2's
   internal-versus-communication split plus 6.2.5's explicit `<send>`
   analogue - **not** on a 6.4 MUST, which does not exist; 6.4 contains
   neither error name. A registered handler failing to reach its service
   raises `error.communication`, which is already the `Invoke.Source` path.
2. Handler modules are a per-session `:invoke_handlers` option; the registered

## Phase 3: the behaviour, the built-in scxml handler, and handler-planned starts

### Overview

Name the contract, move `type=scxml`'s start mechanics behind it, and let a
registered handler start an invocation. The seam is startable at the end of
this phase; cancel, forward, and `done.invoke` land in Phase 4.

### Changes Required:

#### 1. The behaviour
**File**: `lib/statifier/invoke/handler.ex` (new)
**Changes**: The `@callback` set from "The handler contract, decided", with a
moduledoc that states, in this order: that the three planning callbacks are
pure and are called from `Statifier.Session.Effects.plan/2`'s fold; that
`perform/2` is the impure half and MAY be called more than once for the same
`invoke_id`, so a handler MUST be idempotent on it; that `invoke_id` is a
deterministic `%MachineState{}` counter (ADR-0008 as amended), which is what
makes it a usable idempotency key across a crash; and that a handler must not
expect the library to fetch a URI on its behalf (ADR-0024, ADR-0038).

This is the repo's **first project-authored `@behaviour`** - the only two
`@behaviour` lines today implement dependency-owned behaviours
(`lib/statifier/evaluator/functions.ex:1-28`,
`lib/statifier/parser/handler.ex:58`) - so the moduledoc carries the weight a
later reader will need.

#### 2. The instruction vocabulary
**File**: `lib/statifier/session/effects.ex`
**Changes**: `t:instruction/0` gains `{:handler, module(), term()}`.

The plan context Phase 2 introduced gains **one key**, `:invoke_handlers`
(a `%{type_string => module()}`), so the signature does not churn a second
time. Both call sites - `lib/statifier/session.ex:1218` and
`lib/statifier/replay.ex:386` - put it into the context they already build.
The full context is then
`%{session_id: String.t(), invoke_types: Invoke.Types.t() | nil,
invoke_handlers: %{String.t() => module()}}`, and this same map is what the
behaviour's callbacks receive as `ctx`.

`plan_invoke/3` then becomes: if `Invoke.Types.registered?/2` says no, the
existing `error.execution` raise, unchanged; otherwise look the module up in
the handler map and call `module.start(invoke, ctx)`, splicing its returned
instructions into the plan. The built-in module is the default entry for the
built-in types, so no branch in the planner special-cases `scxml`.

**Replay parity depends on the map reaching `Replay` too.** If
`lib/statifier/replay.ex:386` passed an empty map, a type that was registered
during recording would be re-classified as unregistered on replay and
`plan_invoke` would raise `error.execution` where the live run started an
invocation - a silent parity break, and exactly the determinism bead note 4
asks to protect. So `:invoke_handlers` joins
`Statifier.Session.Recording`'s `@normalized_opts` alongside the
`:invoke_types` Phase 2 added, and `Statifier.Replay` rebuilds the same map
from it. Module names are atoms and record cleanly; ADR-0029's input set does
not grow, because this is a session option like `:max_macrostep_rounds`, not
a new recorded input kind. Replay still performs no handler IO: `plan/3` is
pure, and the `{:handler, _, _}` instruction has an explicit no-op clause
below.

Keep the two representations derived by **one constructor**: the
`Invoke.Types` snapshot the core is stamped with is built from the same
handler map the planner dispatches on, so ADR-0047 decision 4's anti-drift
property holds by construction rather than by discipline. The core still
holds only type strings, never modules - a module reference in the core would
be a latent lookup, which ADR-0003 keeps structurally impossible.

## Testing Strategy

### Unit Tests:

- `test/statifier/invoke/types_test.exs` - the shared classifier. The critical
  edge cases are the four-way answer with a `nil` snapshot (`nil`, `"scxml"`,
  the bare `http://www.w3.org/TR/scxml/` URI true;
  `http://www.w3.org/TR/scxml/#SCXMLEventProcessor` false) and that a declared
  set adds to the built-ins rather than replacing them.
- `test/statifier/invoke/handler/scxml_test.exs` - the built-in handler emits
  exactly the instructions the old hardcoded planner did.
- `test/statifier/session/invoke_handler_test.exs` - the end-to-end pin, in the
  idiom of `test/statifier/session/invoke_start_child_test.exs:496-578`: one
  document driven through a real session with everything asserted from a single
  drained stream, so a core-only and a session-only regression each redden a
  different assertion.
- Extensions to `invoke_pass_test.exs`, `effects_test.exs`,
  `invocations_test.exs`, `replay_test.exs`, and `replay_round_trip_test.exs`
  as listed per phase.

Edge cases that must be covered explicitly: a `typeexpr` resolving to a
registered type (resolution happens after argument evaluation, ADR-0031); a
`typeexpr` resolving to an unregistered type; an author-written `id` on a
handler-backed invoke (it does not advance `invoke_counter`); two handler-backed
invocations live in one state; a handler-backed and an scxml-backed invocation
live simultaneously; and a cancel naming a handler-backed invocation that has
already completed.

**Sabotage**: every new test asserting `lib/` behavior gets its mutation proven
and noted in one line above it, per `docs/testing.md`. Harness plumbing states
`# sabotage: n/a - ...` rather than omitting the line.

### Manual Testing Steps:

1. Start a session with `invoke_handlers: %{"test:echo" => TestHandler}` and a
   document containing `<invoke type="test:echo">`; confirm the handler's
   `start/2` ran and `Session.invocations/1` names the invocation.
2. Deliver an external event with the parent autoforwarding; confirm the
   handler's `forward/3` saw an exact copy with every 5.10.1 field preserved.
3. Call `Statifier.Session.done_invocation/3` with donedata; confirm
   `done.invoke.<id>` arrives with `invokeid` set and that a `<finalize>` block
   sees the donedata.
4. Exit the invoking state before completion; confirm the handler's `cancel/2`
   ran and no `done.invoke` is generated afterward.
5. Run the same document with `<invoke type="test:missing">` and confirm
   `error.execution`, no `active_invocations` entry, no
   `Trace.InvokePass.invoke_ids` entry, and no `Effect.CancelInvoke` on exit.
6. Record the session with `record: true`, replay it with `Statifier.Replay`,
   and confirm the effect streams match with no handler ever performing IO on
   the replay side.
