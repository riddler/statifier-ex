# Typed Document Structs Implementation Plan

## Overview

Define the `Statifier.Document` layer: the typed parse target that lowering
(st-l5k.4) produces and that both the validator (st-l5k.5) and the Machine
compiler (st-wju.1) consume. Structs only - no parsing, no lowering, no
validation, no predicator.

Beads issue: `st-l5k.2`. Source research:
`docs/research/260807-st-l5k.2-typed-document-structs.md`.

The research settled the hard question (one `State` struct with a `kind` atom,
not per-kind structs) and left eight open questions. This plan resolves all
eight, states what the single struct gives up and where each looseness is
caught, and sequences nine struct modules into three phases that each end on a
green gate.

## Current State Analysis

### What exists

- The parser layer landed under st-l5k.3 and is the local convention these
  structs must match: `lib/statifier/parser/location.ex`,
  `lib/statifier/parser/dom.ex`, and `lib/statifier/parser/dom/{element,text,attribute}.ex`.
- `lib/statifier/parser/location.ex:13-37` is the shared span:
  `start_line`, `start_column`, `start_offset`, `end_line`, `end_column`,
  `end_offset`. 1-based line/column counted in Unicode codepoints, 0-based byte
  offsets, exclusive end, `@enforce_keys` on all six.
- `lib/statifier/parser/dom/element.ex:28-38` is the struct-module template:
  `@enforce_keys`, `defstruct`, a `@type` alias for a heterogeneous child list,
  a `@type t` naming every field, and no functions in the module at all.
- `lib/statifier/parser/dom/attribute.ex:23-31` carries two spans per attribute
  (`location` for `name="value"`, `value_location` for the text inside the
  quotes). That is the upper bound on what lowering can copy forward.
- `lib/statifier/parser/markup.ex:32-45` is the in-repo precedent for a single
  struct with a `kind` atom over a discriminated union.
- There is no `lib/statifier/document/`. This bead creates it.

### Constraints

- `docs/architecture.md:47` fixes the contract in one line:
  `Document (typed structs, source locations, uncompiled expressions)`.
  Interning, indexing, and expression compilation belong to the compiler.
- `docs/architecture.md:33-36` (principle 4) scopes "valid by construction" to
  the **Machine**. The Document is deliberately the pre-validation type, and
  this is what lets it hold the malformed shapes st-l5k.5 must report.
- `docs/observability.md` Constraint 3 / ADR-0012: locations are born in the
  parser and can only be retained. A field that does not exist here can never
  be recovered downstream.
- ADR-0014: expression spans are relative to an expression string that lives
  inside an attribute value, so the span the Document must carry forward for an
  expression is the attribute's **value** span, not the element's.
- ADR-0005: the predicates run on the interned Machine, not here. The Document
  representation is an input to that pass; it has to be walkable and
  unambiguous, not fast.
- ADR-0004 / `docs/datamodel.md`: expressions are raw predicator source strings
  and are compiled once at Machine-build time. No `Predicator` alias belongs in
  `lib/statifier/document/`.
- `docs/testing.md`: every test asserting `lib/` behavior carries a
  `# sabotage: <mutation> -> red` line; harness plumbing states its exemption.
  Coverage floor is 90% (`coveralls.json`).

## Desired End State

`lib/statifier/document/` holds nine struct modules plus the layer's front-door
module, and:

- every node carries a `%Statifier.Parser.Location{}` in a field named
  `location`, non-nilable, reusing the parser's span rather than defining a
  second location type;
- every node that has source attributes carries `attribute_locations`, a map
  from a known attribute atom to that attribute's **value** span, holding an
  entry only for an attribute that was actually written;
- expressions (`cond`, `log`'s `expr`, `content`'s `expr`) are `String.t() | nil`
  and nothing in the directory mentions `Predicator`;
- whitespace-separated list attributes (`transition` `target` and `event`,
  `initial`) are typed as `[String.t()]`, already tokenized, so no consumer
  re-splits;
- `State` is one struct with `kind :: :state | :parallel | :final | :history`,
  and every field that is meaningful on only some kinds is named in the
  moduledoc together with the validator check that catches its misuse;
- the malformed shapes st-l5k.5's checks 4, 5, 6, and 8 exist to report are all
  representable;
- no `document_order` integer appears anywhere.

Verify with: `mix quality` green, plus the three layer-guard tests in Phase 3
(every struct carries a location, nothing references `Predicator`, no
`document_order` field).

### Key Discoveries

- `lib/statifier/parser/location.ex:13-37` - the location type is settled; this
  bead reuses it. Two location shapes meeting at a layer boundary is the exact
  outcome st-l5k.3's Decision 2 was made to avoid.
- `lib/statifier/parser/dom/attribute.ex:1-19` - `value_location` exists
  specifically for ADR-0014, and its documented entity-expansion caveat is
  inherited verbatim by any Document field that stores an expression plus its
  span.
- `lib/statifier/parser/markup.ex:32-45` - one struct, `kind: :start | :end`.
  The `kind`-atom shape is already the house pattern.
- st-l5k.5's checks 6 and 8 (`bd show st-l5k.5`) are reports about documents
  whose shape is wrong. Per-kind structs make them unrepresentable, which
  relocates the rejection into lowering - contradicting st-l5k.4's stated
  boundary ("lowering staying dumb about semantics keeps the layer boundary
  clean") and deleting checks whose acceptance criteria demand a stable error
  code and a red fixture apiece.
- `../statifier/lib/statifier/history_tracker.ex:163-170` - v1's widened kind
  atom set (`:atomic` distinct from `:final`) caused
  `collect_atomic_descendants/1` to fall through final states. v2's Document
  `kind` therefore stays equal to the element name; widening to atomic/compound
  is the compiler's business.
- `../statifier/lib/statifier/document.ex:30` - v1's `@type t` silently omits
  `binding_location` while the `defstruct` has it. Eleven hand-maintained
  location fields is what produced that; one map is what avoids it.
- `test/scxml_tests/mandatory/content/test529_test.exs:30` and
  `test/scxml_tests/mandatory/donedata/test294_test.exs:48` - every static
  `<donedata><content>` in the corpus is plain text (`21`, `foo`). The other
  corpus cases use `<content expr="...">`. No corpus case puts markup inside
  `<content>`.

## What We're NOT Doing

- **No parsing and no lowering.** Nothing in this bead reads a DOM. Fixtures are
  built literally in tests. Lowering is st-l5k.4.
- **No validation.** The Document holds whatever lowering builds, including
  shapes the spec forbids. That is the point (`docs/architecture.md` principle 4).
- **No predicator, no compiled expressions.** The
  `{:static, term()} | {:compiled, instructions, source}` sum type is a Machine
  `@type` (`docs/architecture.md:78`) and must not appear here.
- **No interning, no indexes, no `document_order`.** ADR-0005 puts all of that
  in st-wju.1.
- **No Appendix D predicate functions.** `is_compound_state/1` and friends live
  on the Machine per ADR-0002; defining them here would duplicate them in the
  layer that does not run them.
- **No Phase 3 elements.** No `datamodel`, `data`, `assign`, `script`, `send`,
  `cancel`, `invoke`, `if`/`elseif`/`else`, `foreach`, `param`.
- **No `<content>` subtree preservation.** Static content is a string; see
  Decision 5.
- **No changelog fragment.** Per `changelog.d/README.md`, the test is whether a
  caller of the public API could tell the difference. There is no public API
  reaching these structs yet; the fragment belongs to whichever bead lands
  `Statifier.parse/1`.
- **No conformance ratcheting.** Nothing can pass until an interpreter exists.

## Implementation Approach

Nine struct modules under `lib/statifier/document/`, plus `Statifier.Document`
itself as the layer's front door and root struct. Every module is data only,
following `DOM.Element`'s template exactly: `@enforce_keys`, `defstruct`,
`@type t` naming every field, a moduledoc that argues for the shape rather than
restating the field names.

```
Statifier.Document                     root: name, version, xmlns, datamodel,
  |                                    binding, initial, states, location
  |-- Document.State      kind :state | :parallel | :final | :history
  |     |-- Document.Transition
  |     |-- Document.Initial          the <initial> element form
  |     |-- Document.Block            one <onentry> or <onexit>
  |     |     |-- Document.Raise
  |     |     |-- Document.Log
  |     |-- Document.Donedata
  |           |-- Document.Content
  |-- Document.State ...
```

The eight questions the research left open are answered below, each as a
numbered decision, then phased leaves-first so no phase forward-references a
type that does not exist yet.

### Decision 0: one `State` struct with a `kind` atom

**Adopted from the research, whose case is decisive and is not re-argued here.**
`kind :: :state | :parallel | :final | :history`.

Two refinements the research did not make:

**`:initial` is not a kind.** See Decision 4. The rule the kind set follows is
that **a kind is a thing with an id that a transition can target**. `<state>`,
`<parallel>`, `<final>`, and `<history>` all qualify (id optional, but present
in the grammar and targetable). `<initial>` has no `id` attribute at all
(spec 3.6), so it is not a state, it is a slot on its parent.

**`:atomic` and `:compound` are not kinds.** v1 widened its atom set at parse
time so `isCompoundState` became a pure atom match
(`../statifier/lib/statifier/parser/scxml/state_stack.ex:194-207`). v2 does not,
for two reasons: the Document `kind` stays equal to the element name, so
lowering never has to decide anything semantic; and v1's widening is what
produced the `:final`-is-not-`:atomic` divergence that
`collect_atomic_descendants/1` fell through
(`../statifier/lib/statifier/history_tracker.ex:163-170`). The compiler is free
to stamp a widened discriminator on the compiled state - st-wju.1's `kind` field
is unconstrained by this bead - and that is the layer where the widening is
cheap and checked.

**What the single struct gives up, and where each looseness is caught.** This is
the moduledoc debt the research says a plan choosing the single struct owes. It
goes in `Statifier.Document.State`'s moduledoc as a "fields that are
kind-scoped" section:

| Field | Meaningful on | Representable misuse | Caught by |
|---|---|---|---|
| `donedata` | `:final` | donedata on a non-final state | st-l5k.5 check 8 |
| `states` | `:state`, `:parallel` | state children under a `:final` | st-l5k.5 check 6 |
| `states` | any | a `:history` child of `:final` or of another `:history` | st-l5k.5 check 5 |
| `initial` / `initial_element` | `:state` | both forms on one state | st-l5k.5 check 4 |
| `initial` / `initial_element` | `:state` | an initial on an atomic state | st-l5k.5 check 3 (target resolution and descendancy) |
| `history_type` | `:history` | `history_type` on a non-history kind | **nothing** - unbuildable from lowering, see below |
| `transitions` | `:state`, `:parallel`, `:history`, `:initial` slot | transitions on a `:final` | **nothing** - see Residual Note 1 |
| `id` | any | `nil` id | not an error; the spec makes `id` optional |

The two "nothing" rows are stated in the moduledoc rather than hidden.
`history_type` on a non-history kind is unreachable from lowering, which only
sets it from `<history type=...>`; it is a shape a *hand-built* Document
(a test fixture, or a future programmatic builder) could produce, and the
moduledoc says so rather than implying a check exists. Transitions on a final
state are reachable from lowering and are recorded as a residual note for
st-l5k.5.

`id: String.t() | nil` no longer overloads `nil`: with `<initial>` off the kind
set, `nil` means exactly one thing - the author omitted an optional `id`.

### Decision 1: `<scxml>` is a separate `Document` struct, not a `State`

**`Statifier.Document` is its own struct. There is no `kind: :scxml`.**

```elixir
%Statifier.Document{
  name: String.t() | nil,
  version: String.t() | nil,
  xmlns: String.t() | nil,
  datamodel: String.t() | nil,
  binding: :early | :late,
  initial: [String.t()],
  states: [State.t()],
  location: Location.t(),
  attribute_locations: attribute_locations()
}
```

The alternative - `%Document{root: %State{kind: :scxml}}` - was considered
because st-wju.1's design recommends interning the root as state index 0 with
`kind: :scxml`, so that LCCA and `get_transition_domain` fall out without a
special case. It is rejected here for three reasons.

First, the compiler's root state is a **synthesis**, not a copy: it needs an
index, a range, and resolved initial indexes, none of which the Document has.
Building it from `%Document{}`'s fields is one function either way, so the
`:scxml` kind costs the compiler nothing to create and buys the Document layer
nothing to carry.

Second, the split would put `<scxml>`'s attributes in two places: `initial` and
`location` on the root state, `name`/`version`/`binding`/`datamodel` on the
wrapper, because those four are not state fields on any other kind. One struct
holding all of `<scxml>`'s attributes is the honest shape.

Third, the generic-walk argument that favored the single `State` struct does not
transfer. A walk over every state is
`document.states |> Enum.flat_map(&walk/1)` - one entry clause, not a per-kind
dispatch - and `Document.states` has the same `[State.t()]` type as
`State.states`, so the recursion below the entry point is uniform either way.

Validator check 5 (`history` is not a child of `scxml`) stays representable
because `Document.states` is `[State.t()]` and a `%State{kind: :history}` is a
legal member of it.

### Decision 2: attribute locations are one map per node, keyed by atom, holding value spans

```elixir
@type attribute_locations :: %{optional(atom()) => Statifier.Parser.Location.t()}
```

Every node with source attributes carries `attribute_locations`, defaulting to
`%{}`. The key is the attribute name as an atom drawn from a **fixed, known set
per element** (`:id`, `:initial`, `:cond`, `:target`, `:event`, `:type`,
`:label`, `:expr`, `:name`, `:version`, `:binding`, `:datamodel`, `:xmlns`).
Lowering maps known source names to known atoms; `String.to_atom/1` appears
nowhere, which is what makes atom keys safe here. The value is the DOM
attribute's **`value_location`** - the span inside the quotes.

Three shapes were available (research Q2). Per-attribute flat fields
(`id_location`, `cond_location`, ...) is v1's shape and v1's documented failure:
`Document`'s `@type t` silently omits `binding_location` while the `defstruct`
has it (`../statifier/lib/statifier/document.ex:30`), which is what happens when
eleven location fields are kept in step by hand. Carrying only what a named
consumer demands would be re-litigated on every new consumer and cannot be
retrofitted, since lowering will have discarded the DOM.

The map is not the "parallel location map" st-l5k.3's Decision 3 rejected. That
rejection was about a structure kept in **index correspondence** with a list of
attribute objects that already existed. Here the attributes have been
destructured into typed fields (`target: [String.t()]`), so there is no
attribute object left for a span to live on, and the map's key is the source
attribute name, which is stable and self-describing.

Value spans only, not the full `name="value"` span. ADR-0014's arithmetic needs
the value span (`attribute_locations[:cond].start_offset + span.start`), and
st-l5k.5's errors point at the offending value; the node's own `location`
already covers the whole element for anything coarser. Widening the map's value
to a two-span struct later is additive.

Inherited caveat, restated in the moduledoc: the stored string is
entity-expanded while the span covers raw source
(`lib/statifier/parser/dom/attribute.ex:14-18`), so offsets *inside* a value
containing a reference do not map 1:1.

### Decision 3: `<onentry>` / `<onexit>` get a `Block` struct

```elixir
%Statifier.Document.Block{
  content: [Statifier.Document.content_node()],
  location: Location.t()
}
```

`State.onentry` and `State.onexit` are each `[Block.t()]`. A bare list of lists
preserves the block boundary the spec requires (3.8, 3.9: each handler is a
separate block, and section 4's error rule makes it a separate error-isolation
unit) but gives the block no location, so a diagnostic could name the failing
`<raise>` and not the `<onentry>` that contains it. Constraint 3 says locations
are retained on executable-content nodes; the `<onentry>` element **is** a node,
and one struct is the whole cost.

No `kind` field on `Block`: the field name on `State` says which it is, and
unlike `Markup`'s `:start`/`:end` the two never share a list.

A transition's executable content is `[content_node()]` directly, not a
`Block.t()` - there is no wrapping element in the source to give a block a
location of its own, and the transition's own `location` is that span.

### Decision 4: `<initial>` is a slot on its parent, not a state

```elixir
%Statifier.Document.Initial{
  transitions: [Transition.t()],
  location: Location.t()
}
```

`State.initial_element :: Initial.t() | nil`.

`<initial>` has no attributes at all (spec 3.6), so v1's synthetic
`"__initial_#{n}__"` ids (`../statifier/lib/statifier/parser/scxml/element_builder.ex:522-525`)
exist purely to fit it into an id-bearing struct - and would then have to be
excluded by hand from st-l5k.5's check 1 (unique ids) and from the compiler's id
map. Making it a slot deletes that problem instead of managing it, and it keeps
`getChildStates` (spec: `<state>`, `<final>`, `<parallel>` children only)
aligned with what `State.states` holds plus history.

`transitions` is a **list**, not a single nilable transition, even though the
spec requires exactly one. Both the zero case and the two case must survive
lowering for st-l5k.5's check 4 to report them - the same "hold the wrong shape
long enough to name it" principle that chose the single `State` struct. The
history default transition needs no special handling for the same reason: a
`%State{kind: :history}` already has `transitions: [Transition.t()]`, so its
zero and two cases are representable for free.

The `<initial>` transition's executable content, which the spec permits, is
representable in Phase 1 at no cost: `Transition.content` already holds it.

The compiler's document-order numbering is unaffected. `<initial>` is never a
numbered state (v1's synthetic ids were never real states either); its
transition gets a `t_index` from st-wju.1 like any other transition.

### Decision 5: `<donedata>` static content is a string; markup is not preserved

```elixir
%Statifier.Document.Donedata{content: Content.t() | nil, location: Location.t()}

%Statifier.Document.Content{
  expr: String.t() | nil,
  text: String.t() | nil,
  location: Location.t(),
  attribute_locations: attribute_locations()
}
```

Spec 5.6 allows `<content>` children to be "text, XML from any namespace, or a
mixture of both". Preserving non-text markup would mean holding a DOM subtree
inside a Document struct, which crosses the layer boundary the whole rewrite is
organized around. Every static `<content>` in the corpus is plain text
(`test/scxml_tests/mandatory/content/test529_test.exs:30` is `21`,
`test/scxml_tests/mandatory/donedata/test294_test.exs:48` is `foo`), so nothing
in scope needs more. Lowering errors on an element child inside `<content>`
rather than silently dropping it (st-l5k.4's rule for non-whitespace text
elsewhere, applied in reverse); recorded as Residual Note 2.

`Content` is a separate struct rather than two fields on `Donedata` because
`<content>` is an element in the source and therefore a node that owes a
location, and because `<send>` reuses it in Phase 3.

`expr` and `text` are both nilable and both representable at once, even though
spec 5.6 says a document MUST NOT specify both - the mutual exclusion is a
validator concern, and the struct holding both is what lets it be reported.
Whether st-l5k.4 accepts `<content expr="...">` in Phase 1 is that bead's call
(two of the four corpus donedata cases use it, and `expr` is a raw string here
like any other expression, so the struct does not change either way).

`text` has no span of its own. It is `DOM.text/1`'s concatenation of the direct
text children, which has no single span when an entity reference or CDATA splits
the run; the `<content>` element's own `location` is what a diagnostic points
at. Stated in the moduledoc.

### Decision 6: no `document_order` integers

**Absent, not nil-filled.** st-wju.1 assigns dense `t_index` / `c_index` itself
and derives state indexes from depth-first document order, and its design says
so explicitly. List order in the Document is the input to that numbering, and
`docs/architecture.md`'s layer diagram puts indexing in the compiler. A field
carried here would be a second source of truth for the same ordering, kept in
step by hand. A Phase 3 guard test asserts no Document struct has a
`document_order` field, so the temptation is mechanical rather than a matter of
review.

### Decision 7: defaults are applied, and `attribute_locations` records what was written

st-l5k.4 commits to applying `:external`, `:early`, and `:shallow` at lowering,
so `transition.type == :external` does not by itself say whether the author
wrote it. That distinction is not lost: **an entry exists in
`attribute_locations` only for an attribute that was actually present in the
source**, so `Map.has_key?(t.attribute_locations, :type)` is exactly the
"was it written" question, and the location a diagnostic would want is the same
lookup. This is stated in `Statifier.Document`'s moduledoc as the map's contract,
not left as an emergent property, and Phase 2's tests pin it.

The consequence for `binding`, which has a non-nil default (`:early`), is the
same: `binding: :early` with no `:binding` key means the default applied.

### Decision 8: the sabotage story for a struct-only bead

`docs/testing.md` requires a mutation a reasonable person could make and rules
out deleting a function body. A bead that adds only `defstruct`, `@enforce_keys`,
and `@type` has exactly **three** classes of real, mutable `lib/` behavior, and
every test in this plan is anchored to one of them:

1. **`@enforce_keys` membership.** Dropping `:location` from a module's
   `@enforce_keys` is a mistake a reasonable person makes; a test asserting that
   `struct!(Mod, [])` raises `ArgumentError` naming that key goes red. This is
   the primary mutation, and it is what makes "every node carries a location"
   an enforced property rather than a convention.
2. **`defstruct` defaults.** Changing `states: []` to `states: nil`, or
   `attribute_locations: %{}` to `nil`, is the classic empty-collection slip and
   is exactly what st-l5k.4's rule ("missing optional attributes become nil or
   `[]`, never empty-string sentinels") depends on. A test constructing a struct
   with only its enforced keys and pattern-matching the defaults goes red.
3. **The layer guards' predicate.** The Phase 3 guards read `lib/statifier/document/`
   and assert layer properties. Their mutation is a `lib/` edit: add
   `alias Predicator` to one Document module, or a `document_order` field, or
   drop `:location` from a struct - each reddens exactly one guard. That is a
   real mutation in the code path the guard claims to cover.

The **file-loading plumbing** inside the guard tests asserts no `lib/` behavior
and states its exemption in the required form:
`# sabotage: n/a - lists .ex files under lib/statifier/document/, no lib/ behavior`.

`@type t` correctness is not unit-testable and is not pretended to be; dialyzer
in the full gate is what checks it, and the Phase 3 guard that every struct
module defines a `location` field is the mechanical half.

## Phase 1: The layer vocabulary and its executable-content leaves

### Overview

The front-door module's shared types, and the four leaf structs nothing else
depends on. Phased first so that no later module forward-references a type that
does not exist - a forward reference would fail dialyzer and leave an
intermediate gate red.

### Changes Required:

#### 1. The front door and shared types

**File**: `lib/statifier/document.ex` (new)
**Changes**: Moduledoc for the layer plus the three shared `@type` aliases. No
`defstruct` yet; the root struct arrives in Phase 3, once the state spine it
holds exists.

```elixir
defmodule Statifier.Document do
  @moduledoc """
  The typed parse target: what lowering produces, and what the validator and
  the Machine compiler consume.

  ... states the layer contract (docs/architecture.md:47), the raw-expression
  rule (docs/datamodel.md), the attribute_locations contract including
  "an entry exists only for an attribute that was written" (Decision 7), and
  the entity-expansion caveat inherited from DOM.Attribute.
  """

  alias Statifier.Document.{Log, Raise, State}
  alias Statifier.Parser.Location

  @type attribute_locations :: %{optional(atom()) => Location.t()}
  @type content_node :: Raise.t() | Log.t()
  @type state_kind :: :state | :parallel | :final | :history
end
```

`state_kind` lives here rather than on `State` so `State`'s own `@type t` reads
against a named union, matching `DOM.Element`'s `@type child` habit.

#### 2. The executable-content leaves

**File**: `lib/statifier/document/raise.ex`, `lib/statifier/document/log.ex` (new)

```elixir
%Statifier.Document.Raise{
  event: String.t(),                       # spec 4.2: required NMTOKEN, a name not a descriptor
  location: Location.t(),
  attribute_locations: Document.attribute_locations()
}

%Statifier.Document.Log{
  label: String.t() | nil,                 # spec 4.7: both optional
  expr: String.t() | nil,                  # raw predicator source; ADR-0014 span via attribute_locations[:expr]
  location: Location.t(),
  attribute_locations: Document.attribute_locations()
}
```

`@enforce_keys [:event, :location]` on `Raise`, `[:location]` on `Log`.
`Raise`'s moduledoc states that `event` is a plain event name, not a descriptor
list, so it is deliberately not tokenized the way `Transition.event` is.

#### 3. The block

**File**: `lib/statifier/document/block.ex` (new)

```elixir
%Statifier.Document.Block{content: [Document.content_node()], location: Location.t()}
```

`@enforce_keys [:location]`, `content: []`. Moduledoc carries Decision 3: why
the block is a struct rather than a bare list, citing spec 3.8/3.9 and section
4's per-block error rule.

#### 4. Donedata and content

**File**: `lib/statifier/document/content.ex`, `lib/statifier/document/donedata.ex` (new)

Shapes as in Decision 5. `@enforce_keys [:location]` on both. `Content`'s
moduledoc states that `text` is the concatenated direct text, that non-text
markup is not preserved and why, and that `expr` and `text` are simultaneously
representable so the validator can report a document that has both.

## Testing Strategy

### Unit Tests

Under `test/statifier/document/`, plus `test/statifier/document_test.exs`.
`use ExUnit.Case, async: true`, `describe` per module or per property,
assertions by pattern match rather than a pile of `assert ==`, fixtures built
**literally** (there is no parser path into these structs until st-l5k.4), and a
`# sabotage:` line above every test.

Three properties are asserted for every struct module, which is the whole of
what a struct-only layer can assert:

1. `@enforce_keys` raises for each enforced key, `:location` always among them.
2. `defstruct` defaults are `[]` / `%{}` / `nil`, never `""`.
3. Composition: nested fixtures round-trip child order.

Plus the shape tests that encode the plan's decisions: list attributes arrive
split, `attribute_locations` presence distinguishes written from defaulted, and
each of st-l5k.5's checks 4, 5, 6, and 8 has a representable malformed fixture -
those four tests are the load-bearing consequence of choosing the single `State`
struct, and their failure would mean the validator bead has been made
impossible.

### Conformance Tests

None. No SCION or W3C test can pass until an interpreter exists; the ratchet
does not move in this bead. The corpus is read only as evidence for Decision 5.

### Manual Testing Steps

1. `iex -S mix`, build the Phase 3 fixture and inspect it - the printed tree
   should read like the XML it models.
2. Construct `%State{kind: :final, states: [%State{kind: :state, ...}]}` and
   confirm it builds without complaint. It must: st-l5k.5 check 6 depends on it.
3. Attempt `%State{kind: :state}` without a `:location` and confirm the raise
   names the key.

## Corpus/Ratchet Notes

`test/passing_tests.json`'s `internal_tests` list is globbed, so every new unit
test joins the regression ratchet the moment it is written - no manual
ratcheting and no shrinking of the file, so `mix gate.check` has nothing to
flag. No `.quality.exs`, `.credo.exs`, `coveralls.json`, or `.sobelow-conf`
change is needed, so no `docs/quality-gate-changes.md` entry is required
(ADR-0011). Struct-only modules contribute few coverable lines; if the coverage
number moves unexpectedly the answer is more tests, never a threshold edit.

## Residual Notes for Later Beads

Recorded, not blocking; none needs an answer before this bead ships.

1. **A `:final` carrying transitions is representable and no listed st-l5k.5
   check names it.** Spec 3.7 gives `<final>` no `<transition>` children, and
   check 6 names only state children. Either check 6's scope widens to
   "onentry, onexit, donedata only" or a ninth check appears; that is st-l5k.5's
   call, and this plan changes nothing either way because the struct already
   holds the shape.
2. **`<content>` with non-text markup.** Not representable by Decision 5. If a
   document ever needs it, the decision is whether the Document layer may hold a
   DOM subtree - a layer-boundary question, not a field addition. st-l5k.4
   should error on an element child inside `<content>` rather than dropping it,
   so the gap is loud.
3. **`<content expr="...">` in Phase 1.** Two of the four corpus donedata cases
   use it. The struct holds it as a raw string either way; whether lowering
   accepts it or defers it with the Phase 3 unsupported error is st-l5k.4's
   call.
4. **Widening `attribute_locations` values to two spans.** Only the value span
   is stored (Decision 2). If a diagnostic ever wants to underline the whole
   `name="value"`, the map's value becomes a two-field struct - additive, and
   the DOM still has both spans at lowering time.
5. **`history_type` on a non-history kind** is unbuildable from lowering and
   caught by nothing. If a programmatic Document builder ever ships, that is the
   field it can get wrong, and the check belongs with the builder.
