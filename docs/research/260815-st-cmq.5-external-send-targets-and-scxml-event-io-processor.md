# Research: External `<send>` targets and the SCXML Event I/O processor

**Date**: 2026-08-15T13:29:20-0600
**Git Commit**: b995d788b96979832e4df84d457f41240ff157d0
**Branch**: st-cmq.5-external-send-ioprocessor
**Bead**: st-cmq.5

## Research Question

What does the codebase look like today in every layer st-cmq.5 has to touch,
so that a plan can be written without rediscovering it: the `<send>` execution
path from document to effect, `Statifier.Session`'s effect interpretation and
the (nonexistent) session registry, `Statifier.Event`'s deliberately-absent
`origin`/`sendid` fields, how `_ioprocessors` is populated today, and how
`error.execution` and `error.communication` are raised as events. Spec clauses
6.2 and C.1 are quoted from the local cache rather than from memory.

## Summary

Everything upstream of delivery exists and is finished. `<send>` lowers,
validates, compiles, and executes end to end, producing exactly one
`{:send, %Effect.Send{}}` or `{:send_delayed, %Effect.SendDelayed{}}` per
execution with the full 6.2.2 attribute surface resolved. What does not exist
is the delivery half:

1. **Target routing is a single `nil`/not-`nil` branch.** `Session.Effects`
   plans a `nil` target as an enqueue onto the session's own external inbox
   and *every* non-`nil` target - `#_internal` included - as
   `{:unroutable, effect}`, which is forwarded to subscribers and otherwise
   dropped. There is no vocabulary of special targets anywhere in `lib/`.
2. **`type` is never inspected.** `Effect.Send.type` is carried and never
   read. No code names `http://www.w3.org/TR/scxml/#SCXMLEventProcessor`
   outside the `_ioprocessors` seed constant and one validator moduledoc
   sentence, and no short alias `"scxml"` exists anywhere.
3. **There is no registry and no supervisor.** ADR-0027 decided the shape
   (`Statifier.Supervisor` holding `Statifier.Registry` plus
   `Statifier.SessionSupervisor`, `:rest_for_one`, sessions
   `restart: :temporary`), and none of it is written: `lib/statifier/` has no
   `supervisor.ex`, and `session.ex:113` still reads
   `use GenServer, restart: :transient`.
4. **`_ioprocessors` already has the SCXML entry** - `%{"location" =>
   session_id}` keyed by the processor URI - so the "Phase 3 minimal map" is
   minimal in the *value* it puts in `location` (the bare session id), not in
   the presence of the entry.
5. **`error.communication` is never raised**, and there is no path by which a
   `Session` can put anything on `MachineState`'s internal queue. Every
   internal-queue write today happens inside a step the pure core is running.
6. **`Statifier.Event` still lacks `origin` and `sendid`**, and
   `SystemVariables.event/1` hardcodes `"sendid" => nil`, `"origin" => nil`,
   `"origintype" => nil` with a comment saying they become real "once `<send>`
   lands".

## The spec, quoted from the local cache

Read from `$(git rev-parse --path-format=absolute --git-common-dir)/spec-cache/scxml-rec.html`.

### 6.2.4 The Target of Send

> The target of the `<send>` operation specifies the destination of the
> event. The target is defined by either the 'target' or the 'targetexpr'
> attribute. In most cases, the format of the target depends on the type of
> the target (for example a SIP URL for SIP-INFO messages or a HTTP URL for
> Web Services). **If the value of the 'target' or 'targetexpr' attribute is
> not supported or invalid, the Processor MUST place the error
> error.execution on the internal event queue. If it is unable to dispatch
> the message, the Processor MUST place the error error.communication on the
> internal event queue.**

That is the split the bead's acceptance criteria restate: *invalid or
unsupported target* is `error.execution`; *cannot dispatch* (a well-formed
target naming nothing reachable) is `error.communication`.

### 6.2.5 The Type of Send

> If neither the 'type' nor the 'typeexpr' is defined, the SCXML Processor
> MUST assume the default value of
> http://www.w3.org/TR/scxml/#SCXMLEventProcessor. **If the SCXML Processor
> does not support the type that is specified, it MUST place the event
> error.execution on the internal event queue.**
>
> SCXML Processors MUST support the following type: [...]
> http://www.w3.org/TR/scxml/#SCXMLEventProcessor | Target is an SCXML
> session. The transport mechanism is platform-specific.
>
> Processors MAY support other types such as web-services, SIP or basic HTTP
> GET. When they do so, they SHOULD assign such types the URI of the
> description of the relevant Event I/O Processor. **Processors MAY define
> short form notations as an authoring convenience (e.g., "scxml" as
> equivalent to http://www.w3.org/TR/scxml/#SCXMLEventProcessor).**

Note the modality: the short alias `"scxml"` is a MAY, not a MUST. The bead's
description commits to supporting it; the spec merely permits it.

### 6.2.3 Children (the discard rule already implemented)

> The Processor MUST evaluate all arguments to `<send>` when the `<send>`
> element is evaluated, and not when the message is actually dispatched. If
> the evaluation of `<send>`'s arguments produces an error, the Processor
> MUST discard the message without attempting to deliver it. **If the SCXML
> session terminates before the delay interval has elapsed, the SCXML
> Processor MUST discard the message without attempting to deliver it.**

Both halves are already satisfied: ADR-0036 for the argument failure, and
`Session.terminate/2` for the timer discard.

### C.1 SCXML Event I/O Processor - the mapping

> The sending and receiving SCXML Processors MUST maintain the following
> mappings:
>
> The 'name' field of the event raised in the receiving session MUST match
> the value of the 'event' attribute of the `<send>` element in the sending
> session.
>
> **The 'origin' field of the event raised in the receiving session MUST
> match the value of the 'location' field inside the entry for the SCXML
> Event I/O Processor in the _ioprocessors system variable in the sending
> session.**
>
> The 'sendid' field of the event raised in the receiving session MUST match
> the sendid in the sending session, if the author of the sending session
> specifies either the 'id' or 'idlocation' attribute. **If the author does
> not specify either the 'id' or 'idlocation' attribute, the 'sendid' field
> MUST be left empty.**
>
> **The 'origintype' field of the event raised in the receiving session MUST
> have the value "scxml".**
>
> The 'data' field of the event raised in the receiving session MUST contain
> a copy of the data specified in the 'namelist' attribute or in `<param>` or
> `<content>` elements in the sending session. [...] the Processor MUST
> ensure that changes to the transmitted data in the receiving session do not
> affect the data in the sending session and vice-versa.

Two details that bite:

- `origin` is the *sender's* `_ioprocessors[...].location`, not the `target`
  attribute. 5.10.1 separately describes `origin` as "a URI, equivalent to
  the 'target' attribute on the `<send>` element ... a value which, when used
  as the value of 'target', will allow the receiver of the event to `<send>`
  a response back". The two readings agree only if `location` is itself a
  usable target string.
- `origintype` is the literal string `"scxml"`, **not** the processor URI.
  Test352 in the corpus is exactly this assertion.

### C.1 - the special targets

> When using the SCXML Event I/O Processor, SCXML Processors MUST support the
> following special targets for `<send>`:
>
> **#_internal.** If the target is the special term '#_internal', the
> Processor MUST add the event to the internal event queue of the sending
> session.
>
> **#_scxml_sessionid.** If the target is the special term
> '#_scxml_sessionid', where sessionid is the id of an SCXML session that is
> accessible to the Processor, the Processor MUST add the event to the
> external queue of that session. The set of SCXML sessions that are
> accessible to a given SCXML Processor is platform-dependent.
>
> **#_parent.** If the target is the special term '#_parent', the Processor
> MUST add the event to the external event queue of the SCXML session that
> invoked the sending session, if there is one.
>
> **#_invokeid.** If the target is the special term '#_invokeid', where
> invokeid is the invokeid of an SCXML session that the sending session has
> created by `<invoke>`, the Processor MUST add the event to the external
> queue of that session.
>
> **If neither the 'target' nor the 'targetexpr' attribute is specified, the
> SCXML Processor MUST add the event to the external event queue of the
> sending session.**
>
> **If the sending SCXML session specifies a session that does not exist or
> is inaccessible, the SCXML Processor MUST place the error
> error.communication on the internal event queue of the sending session.**
> If the receiving Processor cannot handle the data format contained in the
> message, the receiving Processor MUST place the error error.communication
> in internal queue of the session for which the message was intended and
> MUST ignore the message. The Processor SHOULD also notify the sending
> processor of the error.

### C.1.1 _ioprocessors Value

> SCXML Processors MUST maintain a
> 'http://www.w3.org/TR/scxml/#SCXMLEventProcessor' entry in the
> _ioprocessors system variable. The Processor MUST maintain a 'location'
> field inside this entry whose value holds an address that external entities
> can use to communicate with this SCXML session using the SCXML Event I/O
> Processor.

### 5.10.1 - the three event fields still missing

> **sendid.** If the sending entity has specified a value for this, the
> Processor MUST set this field to that value. Otherwise, **in the case of
> error events triggered by a failed attempt to send an event, the Processor
> MUST set this field to the send id of the triggering `<send>` element.**
> Otherwise it MUST leave it blank.
>
> **origin.** [...] For external events, the SCXML Processor SHOULD set this
> field to a value which, when used as the value of 'target', will allow the
> receiver of the event to `<send>` a response back to the originating entity
> via the Event I/O Processor specified in 'origintype'. **For internal and
> platform events, the Processor MUST leave this field blank.**
>
> **origintype.** [...] **For internal and platform events, the Processor
> MUST leave this field blank.**

The `sendid` sentence is the one that couples this bead's two halves: an
`error.communication` raised because a target could not be dispatched MUST
carry the failing `<send>`'s send id in `_event.sendid`. That is a
platform-typed event carrying a non-blank `sendid` while `origin`/`origintype`
stay blank.

## Detailed Findings

### 1. The `<send>` execution path, document to effect

**`Statifier.Document.Send`** ([`lib/statifier/document/send.ex:39-56`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/document/send.ex#L39-L56)) carries
every 6.2.2 attribute plus its `expr` sibling simultaneously, on purpose, so
the validator can report the shape rather than lowering refusing to build it.

**`Statifier.Validator.Checks.Send`** ([`lib/statifier/validator/checks/send.ex:159-232`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/validator/checks/send.ex#L159-L232))
enforces eight constraints, all pairwise mutual exclusions plus
`delay`+`target="_internal"`. Two things a plan must know:

- `delay_and_internal_target/2` ([`lib/statifier/validator/checks/send.ex:210-216`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/validator/checks/send.ex#L210-L216))
  matches the literal string `"_internal"`, following 6.2.2's own attribute
  table wording ("when the attribute 'target' has the value '_internal'"),
  **not** C.1's `#_internal`. The two clauses of the spec disagree with each
  other on the spelling; the check follows 6.2.2 verbatim because that is the
  clause it implements.
- 6.2.3's three-way "exactly one of 'event', 'eventexpr' and `<content>`" is
  deliberately unenforced, with the reasoning written into the moduledoc
  ([`lib/statifier/validator/checks/send.ex:31-71`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/validator/checks/send.ex#L31-L71)) and its own commit
  (`5889e3b`). Two W3C *mandatory* tests violate the letter, including
  `test/scxml_tests/mandatory/scxml_event_processor/test354_test.exs`.
  Nothing in this bead should reopen it.
- Nothing in the validator inspects `type` or the target *vocabulary*. An
  unknown target or an unsupported type is not a validation error, which is
  correct: 6.2.4/6.2.5 put both at execute time as events.

**`Statifier.Machine.Content.Send`** (`lib/statifier/machine/content/send.ex`)
is the compiled node plus its `ExecutableContent` impl in one file.
`execute/2` ([`lib/statifier/machine/content/send.ex:104-138`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/machine/content/send.ex#L104-L138)) resolves
`event`, `target`, `type`, `delay`, `namelist ++ params`, and `<content>`,
mints or reads the send id, writes `idlocation`, then emits exactly one
effect via `build_effect/6` ([`lib/statifier/machine/content/send.ex:289-319`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/machine/content/send.ex#L289-L319)).
Per ADR-0036 any argument failure returns `{:error, reason}` and produces no
effect at all.

Send id: ADR-0035. `generate_send_id/2`
([`lib/statifier/machine/content/send.ex:243-249`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/machine/content/send.ex#L243-L249)) uses the author's literal
`id` verbatim when present, else `"send_" <> Integer.to_string(counter + 1)`
off `machine_state.send_counter`. **`send_id` on the effect is therefore
always non-`nil`, even when the author wrote neither `id` nor `idlocation`.**
C.1 requires the delivered event's `sendid` to be *empty* in exactly that
case, so the effect alone does not carry enough information to satisfy C.1;
the node knows (`node.id == nil and node.idlocation == nil`) and the effect
does not.

**Effect shapes.** `Statifier.Effect.Send`
([`lib/statifier/effect/send.ex:27-50`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/effect/send.ex#L27-L50)): `event`, `target`, `type`, `data`,
`send_id`, `c_index`, `owner`, `macrostep`, `microstep`.
`Statifier.Effect.SendDelayed` ([`lib/statifier/effect/send_delayed.ex:21-46`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/effect/send_delayed.ex#L21-L46))
adds `delay_ms`. Both moduledocs say in as many words that the fields are the
element's own attribute names "so the not-yet-implemented session/invoke
support, which will give this effect its semantics, can extend rather than
rename them".

### 2. `Statifier.Session` and the absent registry

`Session` splits into a pure planner and an impure performer.
`Statifier.Session.Effects.plan/1` ([`lib/statifier/session/effects.ex:44-47`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session/effects.ex#L44-L47))
maps each effect to zero or more instructions from the vocabulary at
[`lib/statifier/session/effects.ex:31-37`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session/effects.ex#L31-L37): `{:notify, effect}`,
`{:enqueue_event, event}`, `{:schedule, send_id, delay_ms, event}`,
`{:cancel_timers, send_id}`, `{:unroutable, effect}`, `{:halt, reason}`.

The whole of today's target routing is four clauses
([`lib/statifier/session/effects.ex:50-65`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session/effects.ex#L50-L65)):

- `%Send{target: nil}` -> `[{:notify, e}, {:enqueue_event, Event.external(send.event, data: send.data)}]`
- `%Send{}` (any non-`nil` target) -> `[{:notify, e}, {:unroutable, e}]`
- `%SendDelayed{target: nil}` -> `[{:notify, e}, {:schedule, send_id, delay_ms, event}]`
- `%SendDelayed{}` -> `[{:notify, e}, {:unroutable, e}]`

`type` is not matched in any clause. `Session`'s own moduledoc
([`lib/statifier/session.ex:72-81`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L72-L81)) states the deferral: "Every other target -
`#_internal` included - plans as `{:unroutable, effect}` and is forwarded,
never guessed and never a crash".

`perform_instruction/3` ([`lib/statifier/session.ex:516-566`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L516-L566)) is the impure
half: `{:enqueue_event, _}` appends to `state.inbox`
([`lib/statifier/session/inbox.ex:34-37`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session/inbox.ex#L34-L37)); `{:schedule, _, _, _}`
([`lib/statifier/session.ex:537-548`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L537-L548)) is the library's only
`Process.send_after/3`, keyed by a fresh `make_ref()` recorded in both
`Timers` (by `send_id`) and `state.timer_refs` (by ref); `{:cancel_timers,
send_id}` ([`lib/statifier/session.ex:550-554`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L550-L554)) takes every ref under that id
and cancels it; `{:unroutable, effect}`
([`lib/statifier/session.ex:556-559`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L556-L559)) only notifies subscribers.

The drain loop is `handle_continue(:drain, state)`
([`lib/statifier/session.ex:358-374`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L358-L374)) feeding `Interpreter.handle_event/2`
([`lib/statifier/session.ex:489-498`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L489-L498)).

**Public API and naming.** `start_link/2`
([`lib/statifier/session.ex:200-204`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L200-L204)) splits `:name` out of `opts` and hands it
to `GenServer.start_link/3` unchanged, so a caller-supplied
`{:via, Registry, _}` works with no code in the module. The session does not
mint its own id: `init/1` reads it back from
`machine_state.datamodel["_sessionid"]` ([`lib/statifier/session.ex:331`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L331)) after
`Interpreter.initialize/2` has run. `restart: :transient` is still on
[`lib/statifier/session.ex:113`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/session.ex#L113).

**Nothing named `Statifier.Registry`, `Statifier.Supervisor`, or
`Statifier.SessionSupervisor` exists.** `lib/statifier/` has no
`supervisor.ex`. `Mix.Statifier.AdrGuard`'s exemption list is still
`@effect_interpreter_paths ["lib/statifier/session.ex"]`
([`lib/mix/statifier/adr_guard.ex:74`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/mix/statifier/adr_guard.ex#L74)), one entry.

### 3. `Statifier.Event` and its absent `origin`/`sendid`

`Statifier.Event` ([`lib/statifier/event.ex:44-56`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/event.ex#L44-L56)) is
`%{name, type, data, cause, invokeid}`. The moduledoc's "What is deliberately
absent" section ([`lib/statifier/event.ex:27-39`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/event.ex#L27-L39)) names `origin` and `sendid`
explicitly:

> `origin` and `sendid` (spec 5.10.1's remaining event fields) are left out
> rather than carried dead: they matter to `<send>` round-tripping, which the
> not-yet-implemented session support handles. They get added once that
> caller exists.

and records the precedent for adding them: `invokeid` "was in the same
position until `Statifier.Interpreter`'s finalize/autoforward pass became its
first reader". `origintype` is not named in that list at all, but
`SystemVariables.event/1` already emits a `"origintype" => nil` key, so it is
a third field in the same position.

`Event.external/2` ([`lib/statifier/event.ex:66-73`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/event.ex#L66-L73)) takes `data:` and
`invokeid:` opts today. `Event.internal/3` and `Event.platform/3`
([`lib/statifier/event.ex:84-97`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/event.ex#L84-L97)) both require a `%Cause{}`.

The doc on `Event.internal/3` ([`lib/statifier/event.ex:75-82`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/event.ex#L75-L82)) already states
the routing rule this bead implements: `type: :internal` is restricted to
`<raise>` and `<send target="#_internal">`, and a `<send>` with no target goes
to the session's *external* queue as `:external`.

### 4. `_ioprocessors` today

`Statifier.Evaluator.SystemVariables.initial/2`
([`lib/statifier/evaluator/system_variables.ex:50-60`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/evaluator/system_variables.ex#L50-L60)) is the single build
site:

```elixir
"_ioprocessors" => %{
  @scxml_event_processor => %{"location" => session_id}
}
```

with `@scxml_event_processor "http://www.w3.org/TR/scxml/#SCXMLEventProcessor"`
at [`lib/statifier/evaluator/system_variables.ex:20`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/evaluator/system_variables.ex#L20). So the SCXML processor
entry and its `location` field already exist and already satisfy C.1.1's
literal MUSTs; what is "minimal" is that `location` is the bare `sess_` UXID
rather than a string usable as a `<send target>` (C.1's `origin` mapping and
5.10.1's "when used as the value of 'target'" both want the latter, which
would be `"#_scxml_" <> session_id`).

`MachineState.new/2` ([`lib/statifier/machine_state.ex:421-445`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/machine_state.ex#L421-L445)) merges
`SystemVariables.initial/2`'s result **over** the caller's `:datamodel` option
([`lib/statifier/machine_state.ex:436`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/lib/statifier/machine_state.ex#L436)), so author data can never shadow a
system variable. It is written exactly once, at construction; `_event` alone
is rewritten, by `MachineState.put_event/2`

## Architecture Documentation

- **ADR-0027** (`docs/adr/0027-embedder-placed-session-runtime.md`, accepted
  2026-08-14) is the record this bead implements. Four decisions: no
  application callback, an embedder-placed `Statifier.Supervisor` holding
  `{Registry, keys: :unique, name: Statifier.Registry}` then
  `{DynamicSupervisor, name: Statifier.SessionSupervisor}` under
  `:rest_for_one`; registration inside `Session.init/1` (the `sess_` UXID does
  not exist before `MachineState.new/2` runs, so no `{:via, _}` tuple can name
  it); parent/child by monitors and an invocation table, not links or nesting;
  `restart: :temporary`. It also states that a bare `Session.start_link/2`
  stays legal and *unregistered*, which C.1's "accessible ... is
  platform-dependent" sanctions. It leaves the public
  start-through-the-runtime helper's name and signature explicitly to this
  bead. It requires the branch to widen
  `Mix.Statifier.AdrGuard.@effect_interpreter_paths` by exactly one path
  (`lib/statifier/supervisor.ex`) and to carry an ADR-0011 ledger entry in
  `docs/quality-gate-changes.md` with an `Approved-by:` line - **a human's
  call, not an agent's**.
- **ADR-0003** - the pure core returns effects; `session.ex` is the one exempt
  path. Any registry lookup, monitor, or `start_child` call belongs in
  `session.ex` or the new `supervisor.ex`.
- **ADR-0035** - the send id is `send_<n>` off `machine_state.send_counter`,
  not a UXID, because the core has no clock and no CSPRNG.
- **ADR-0036** - a failed `<send>` argument discards the message and produces
  no effect (6.2.2's element-level MUST).
- **ADR-0008** - `sess_` / `send_` / `inv_` UXID prefixes; the session id is
  minted outside the core.
- **ADR-0029** - `Session.interpret/2` stays public and replay records four
  inputs. Any new session-side input path (an inbound cross-session delivery,
  for instance) has to be reconciled with that recording, per
  `docs/observability.md` constraint 6.
- **ADR-0005** - state ids are strings only at the `Statifier` boundary.
  Session ids and target strings are boundary values, not interned indices.
- [`docs/architecture.md:125-139`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/docs/architecture.md#L125-L139) - the standing statement that
  "`#_parent`/`#_invokeid` routing and delivery do not exist yet - that is
  st-cmq.7". Note that the *architecture doc* attributes `#_parent`/`#_invokeid`
  to st-cmq.7 while this bead's own description reserves `#_parent`'s shape
  here and wires it fully in st-cmq.7; see Open Questions.

## Open Questions

These are recorded rather than resolved; no human was available during this
research pass.

1. **How does `error.communication` reach the sending session's *internal*
   queue?** The failure is detected in `Session` (a registry lookup miss),
   the queue lives in `%MachineState{}`, and `Session` has no write path to
   it today. Three shapes are visible and none is decided: (a) `Session`
   calls `MachineState.raise_platform/4` directly on the `machine_state` it
   holds, between drain iterations; (b) a new `Interpreter` entry point that
   injects a platform event and re-drives the loop; (c) routing moves partly
   into the core so the failure is discovered there. Option (a) is the least
   machinery but writes to the core's queue from outside a step, which is a
   question ADR-0003 has an opinion about.
2. **What `Cause.origin` arm does an `error.communication` get?** All eight
   existing arms index the compiled `%Machine{}`. The natural value is the
   originating `<send>`'s `{:content, c_index, owner}`, which
   `Effect.Send`/`Effect.SendDelayed` already carry - but a delayed send's
   failure happens long after its microstep, so the counters `Cause.new/4`
   would stamp are the *current* ones, not the ones on the effect. Whether
   the cause should carry the effect's stored counters instead is undecided.
3. **`sendid` on the error event.** 5.10.1 requires an error event triggered
   by a failed send to carry the triggering `<send>`'s send id. That means
   `raise_platform/4`'s `opts` (or `Statifier.Event` itself) has to convey a
   `sendid` that no platform event carries today.
4. **Empty `sendid` on delivered events.** `Effect.Send.send_id` is always
   non-`nil` (ADR-0035 mints one), but C.1 requires the *delivered* event's
   `sendid` to be empty when the author wrote neither `id` nor `idlocation`.
   The effect does not record which case it was. Either the effect gains a
   flag, or the delivered `sendid` is populated unconditionally (a knowing
   deviation), or the node stops minting when neither attribute is present
   (which would break `<cancel>`-by-generated-id and ADR-0035's counter).
5. **What goes in `_ioprocessors[...].location`?** C.1.1 wants "an address
   that external entities can use to communicate with this SCXML session";
   C.1 makes that same value the delivered `origin`; 5.10.1 wants `origin`
   usable as a `<send target>`. `"#_scxml_" <> session_id` satisfies all
   three; the bare `sess_` UXID satisfies only C.1.1's letter. test501 is the
   corpus test that distinguishes them. Changing it breaks three existing
   unit assertions ([`test/statifier/evaluator/system_variables_test.exs:36-50`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/test/statifier/evaluator/system_variables_test.exs#L36-L50),
   [`test/statifier/machine_state_test.exs:127-141`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/test/statifier/machine_state_test.exs#L127-L141), `:272-278`).
6. **`#_internal` vs `_internal`.** 6.2.2's attribute table says the value is
   `"_internal"`; C.1 says the special term is `'#_internal'`. The validator
   check follows 6.2.2. The router will have to decide whether it accepts one
   spelling or both, and whether `Checks.Send`'s `delay_and_internal_target/2`
   should widen to match. The corpus (test189, test495) writes `#_internal`.
7. **Ownership of `#_parent` between this bead and st-cmq.7.**
   [`docs/architecture.md:125-139`](https://github.com/riddler/statifier-ex/blob/b995d788b96979832e4df84d457f41240ff157d0/docs/architecture.md#L125-L139) says "`#_parent`/`#_invokeid` routing and
   delivery do not exist yet - that is st-cmq.7", while this bead's
   description says `#_parent` is a "reserved shape now, wired fully by the
   invoke child-session bead". `#_invokeid` is named in neither this bead's
   description nor its acceptance criteria, but C.1 makes it a MUST and
   test192 exercises it. Which of the two beads owns each is a scoping call.
8. **Unsupported `type` -> `error.execution` is detected where?** 6.2.5 puts
   it at execute time, and `Machine.Content.Send.execute/2` resolves `type`
   and could check it - but a *supported types* list is session-runtime
   knowledge, and the core has no access to it. Detecting it in `Session`
   instead means an `error.execution` raised from outside the core, which is
   open question 1 again for a different error name.
9. **Does the ADR-0027 runtime need its own ADR-0011 ledger entry written
   before the gate goes green?** ADR-0027 says the guard amendment and the
   ledger entry land with the implementing bead, `Approved-by` a human, and
   that "writing that entry is the human's call at implementation time". No
   agent may write it. This blocks a full-gate green on any branch that adds
   `lib/statifier/supervisor.ex`, and the plan should sequence around it.
