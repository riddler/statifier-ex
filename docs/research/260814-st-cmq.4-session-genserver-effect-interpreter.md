# Research: Statifier.Session, the GenServer effect interpreter

**Date**: 2026-08-14T10:11:25-0600
**Git Commit**: 3d8036fec00b38efc3e94cd4b69e9a6c2d506d3d
**Branch**: st-cmq.4-session-genserver
**Bead**: st-cmq.4

> Base note: this branch is cut from `st-af3.17-script-statement-bodies`, not
> `origin/main`, so the Phase 3 datamodel and script work described below is in
> reach here and not yet on the default branch.

## Research Question

`Statifier.Session` is the GenServer that owns the outer `while running` loop,
the external event queue, and the delayed-send timers, driving the pure core
through `Statifier.Interpreter.initialize/2` and `handle_event/2`. The module
does not exist. What exists today that it must build on: the effect vocabulary,
the interpreter's documented entry points and its ADR-0002 deviation comment in
`main_event_loop/1`, `MachineState` as a value, the observability seams, and
whatever the repo already holds for sessions, `sess_` UXIDs, `_sessionid` /
`_name` initialization, `<send>` / `<cancel>` executable content, and delayed
sends.

## Summary

The seams this bead consumes are all present, and three of them are further
along than the bead's own text assumes.

1. **The core is a pure library with no OTP anywhere, and the quality gate
   enforces it - with one hole cut in advance, at exactly this bead's file
   path.** `mix.exs` declares no `mod:` in `application/0`
   (`mix.exs:29-33`), there is no `config/` directory, and there is not one
   `GenServer`, `Supervisor`, `Registry`, `start_link`, or
   `Process.send_after` under `lib/statifier/`. `Mix.Statifier.AdrGuard`'s
   `@effect_call_pattern` (`lib/mix/statifier/adr_guard.ex:87-92`) fails the
   gate on `use GenServer`, `GenServer.`, `Process.send_after(`, `:timer.`,
   `spawn*(`, `receive do`, `Logger.*(`, `File.*(`, `:ets.`, and more,
   anywhere under `lib/statifier/` - **except** the single path in
   `@effect_interpreter_paths`:

       # ADR-0003 names `Statifier.Session` as *the* production effect interpreter,
       # so it is the one core module allowed to do I/O. Excluding it is the design,
       # not a hole in the check.
       @effect_interpreter_paths ["lib/statifier/session.ex"]

   (`lib/mix/statifier/adr_guard.ex:64-67`.) The guard's own tests already use
   that literal path (`test/mix/statifier/adr_guard_test.exs:135`, `:143`). So
   the module **must** be `Statifier.Session` at `lib/statifier/session.ex`;
   any helper module split out beside it (a timer table, a registry wrapper)
   is not exempt and cannot call `Process.send_after`. The ad-hoc-identifier
   ban (`:96-100`, `:250-259`) is *not* lifted for `session.ex` - deliberately,
   because that is where a session id would be generated ad hoc.
   `Statifier.Session` would be the first process this library ever starts,
   and introducing one means deciding whether the library gains an application
   callback module and a supervision tree at all (open question 1).

2. **`_sessionid`, `_name`, `_ioprocessors` and the `sess_` UXID are already
   wired, in the core, not in the session.** `MachineState.new/2` accepts a
   `:session_id` option and defaults it to `UXID.generate!(prefix: "sess")`
   (`lib/statifier/machine_state.ex:267`), then merges
   `Evaluator.SystemVariables.initial/2` *over* the caller's `:datamodel` so
   author data can never shadow a system variable
   (`lib/statifier/machine_state.ex:276`). `_name` comes from `machine.name`,
   the `<scxml name>` attribute
   (`lib/statifier/evaluator/system_variables.ex:54`). The session's job here is
   therefore *ownership* of the id, not creation of the mechanism: it decides
   the id, passes it as `:session_id`, and keeps its own copy for routing and
   telemetry. The bead's acceptance criterion "`sess_` UXID supplies
   `_sessionid` and `_name`" is satisfied by the core today for a
   session-generated id passed through `initialize/2`. One structural note: there
   is **no `session_id` field on `%MachineState{}`** - the id lives only inside
   `datamodel["_sessionid"]`, so a session that wants it for routing or
   telemetry keeps its own copy rather than reading it back out of a map.

3. **Four of the seven core effects exist as complete structs with no
   producer.** `Effect.Send`, `Effect.SendDelayed`, `Effect.Cancel`, and
   `Effect.Invoke` are defined, typed, in the `@type core()` union, and
   documented as unproduced (`lib/statifier/effect.ex:26-44`). Their producers
   are st-cmq.3 and st-cmq.6, not this bead. **This bead can therefore write
   the interpretation half against effect values it constructs itself in tests,
   with no `<send>` element in the document** - which matters, because
   `<send>`, `<cancel>`, and `<invoke>` have no lowering builder, no `Document`
   struct, no `Machine.Content` node, and no parser support at all today.

4. **`isCancelEvent` and the external queue are the two things Appendix D
   assigns to `mainEventLoop` that this port explicitly moved outward**, with
   the reason written at the port site
   (`lib/statifier/interpreter.ex:693-702`) and restated in `MachineState`'s
   moduledoc (`lib/statifier/machine_state.ex:21-31`). Neither has any
   implementation anywhere in the repo. `isCancelEvent` in particular has no
   even-partial answer: `Statifier.Event` has three `type` values
   (`:external | :internal | :platform`) and no notion of a cancel event.

5. **`MachineState` is a plain serializable value** with no pid, ref, port, or
   fun, so the "synchronous query of the current snapshot" API in the bead is a
   `GenServer.call` returning the struct with no copying concern beyond term
   size. The one documented caveat is that `==` on two `%MachineState{}` values
   is not a position-equality test, because `:queue`'s front/rear split is
   history-dependent (`lib/statifier/machine_state.ex:169-180`); compare
   through `internal_events/1` instead.

## Detailed Findings

### The pure core's two entry points, and what they do not do

`Statifier.Interpreter.initialize/2` (`lib/statifier/interpreter.ex:173-230`)
runs `MachineState.new/2` -> `begin_macrostep/1` -> `begin_microstep/1` ->
`Datamodel.initialize/1` -> `run_global_scripts/2` -> `enter_states/2` ->
`main_event_loop/1`, returning an untagged `{machine_state, [effect]}`. It
cannot fail, because a `%Machine{}` is valid by construction
(`lib/statifier/interpreter.ex:166-169`). `opts` passes straight through to
`MachineState.new/2` with nothing interpreted on the way
(`lib/statifier/interpreter.ex:163-164`), so the session's option surface is
exactly `MachineState.new/2`'s.

`Statifier.Interpreter.handle_event/2` (`lib/statifier/interpreter.ex:331-351`)
is the external-event tail. Its shape is the session's inner contract:

```elixir
@spec handle_event(machine_state :: MachineState.t(), event :: Event.t()) ::
        {:ok, MachineState.t(), [Effect.t()]} | {:error, :not_running}
def handle_event(%MachineState{running: false}, %Event{}), do: {:error, :not_running}
```

The `running: false` guard (`lib/statifier/interpreter.ex:333`) is Appendix D's
own loop condition, so a session that delivers an event after termination gets
`{:error, :not_running}` rather than a crash. Note this reads `running`, not
`status`: there is a documented window where `running` is already `false` and
`status` is still `:running`, spanning `exit_interpreter/1`
(`lib/statifier/machine_state.ex:77-90`). A session that has finished a call
never observes that window, since `main_event_loop/1` runs `exit_interpreter/1`
before returning (`lib/statifier/interpreter.ex:693-707`).

`handle_event/2` also carries a seam of its own: the invoke `finalize` and
`autoforward` passes over the configuration are commented out at the
pseudocode's position, immediately before `put_event/2`
(`lib/statifier/interpreter.ex:342-343`).

### The ADR-0002 deviation comment this bead is named by

`lib/statifier/interpreter.ex:693-702`, inside `main_event_loop/1` on the
`running == true` branch:

> ADR-0002 mechanical deviation, ADR-0003. Appendix D's `mainEventLoop` owns
> both queues and blocks on `externalQueue.dequeue()` at the end of every
> iteration, then checks `isCancelEvent/1` on what it dequeues. This core takes
> one external event per call, so the outer `while running` loop is driven by
> the caller (`handle_event/2`), and the waiting external events live in the
> session, not this struct. The semantics of processing one external event are
> unchanged; only the storage of the waiting ones moves outward.
> `isCancelEvent/1` moves out with them.

The Appendix D text it deviates from, quoted from the local cache at
`$(git rev-parse --path-format=absolute --git-common-dir)/spec-cache/appendix-d.txt:145-152`:

```
        # A blocking wait for an external event.  Alternatively, if we have been invoked
        # our parent session also might cancel us.  The mechanism for this is platform specific,
        # but here we assume it's a special event we receive
        externalEvent = externalQueue.dequeue()
        if isCancelEvent(externalEvent):
            running = false
            continue
        datamodel["_event"] = externalEvent
```

The spec itself calls the cancel mechanism "platform specific" and the cancel
event an assumption, so what a cancel event *is* in this engine is an open
decision, not a port (open question 4).

Three further skipped passes sit in `main_event_loop/1` in the pseudocode's own
positions (`lib/statifier/interpreter.ex:680-691`): the
`for state in statesToInvoke: invoke(state)` loop, `statesToInvoke.clear()`,
and the post-invoke `if not internalQueue.isEmpty(): continue` guard. A fourth
is per-state inside `exit_interpreter/1`: `cancelInvoke(inv) for inv in s.invoke`
(`lib/statifier/interpreter.ex:780-781`). All four belong to the invoke beads
(st-cmq.6, st-cmq.7), not to this one. `states_to_invoke` is deliberately absent
from `MachineState` until a caller exists
(`lib/statifier/machine_state.ex:33-41`).

A fifth seam is in the datamodel's late-binding path
(`lib/statifier/interpreter/datamodel.ex:250`): an invoked child's
`<param>`/`namelist` values arrive as spec 5.3.2's environment seed, and the
guard there exists so a late-bound child does not discard them. That is a
constraint on how a session seeds a child's datamodel, relevant to st-cmq.7.

### The effect vocabulary as it stands

`Statifier.Effect` (`lib/statifier/effect.ex`) is the single `@type t()` union
every consumer pattern-matches. Every effect is `{tag, payload_struct}` -
never a positional 4- or 5-tuple (`lib/statifier/effect.ex:14-20`). The
moduledoc's table (`lib/statifier/effect.ex:24-44`) names the producer of each,
and says in as many words that `:send`, `:send_delayed`, `:cancel`, and
`:invoke` "remain unproduced, because nothing in this core sends, delays,
cancels, or invokes yet."

Core effects, with what a session does with each:

| Tag | Struct | Fields the session reads | Produced today |
|---|---|---|---|
| `:log` | `Effect.Log` (`lib/statifier/effect/log.ex`) | `label`, `value`, `c_index`, `owner`, counters | yes, by `<log>` |
| `:done` | `Effect.Done` (`lib/statifier/effect/done.ex`) | `donedata`, `configuration` (full, ADR-0005), counters | yes, by `exit_interpreter/1` |
| `:budget_exhausted` | `Effect.BudgetExhausted` (`lib/statifier/effect/budget_exhausted.ex`) | `configuration`, `budget`, `pending_internal_events`, counters | yes, by `macrostep/1` (ADR-0019) |
| `:send` | `Effect.Send` (`lib/statifier/effect/send.ex`) | `event`, `target`, `type`, `data`, `send_id`, `c_index`, counters | no |
| `:send_delayed` | `Effect.SendDelayed` (`lib/statifier/effect/send_delayed.ex`) | same plus `delay_ms` | no |
| `:cancel` | `Effect.Cancel` (`lib/statifier/effect/cancel.ex`) | `send_id`, `c_index`, counters | no |
| `:invoke` | `Effect.Invoke` (`lib/statifier/effect/invoke.ex`) | `invoke_id`, `type`, `src`, `params`, `autoforward`, `state_index`, counters | no |

The four unproduced structs already say in their own moduledocs that the
session owns their semantics: `Effect.SendDelayed` - "The timer that eventually
fires this send is not yet implemented; this module only defines the shape it
schedules" (`lib/statifier/effect/send_delayed.ex:6-7`); `Effect.Cancel` -
"resolving it against the pending `SendDelayed` timers is the
not-yet-implemented session's job" (`lib/statifier/effect/cancel.ex:5-6`).

`Effect.SendDelayed` carries `macrostep`/`microstep` "as they stood when the
send was scheduled, not when the timer fires"
(`lib/statifier/effect/send_delayed.ex:10-11`), which is the seam a replay or
telemetry consumer needs to correlate a firing back to its scheduling.

`Effect.Log` carries an `owner` field -
`{:onentry, state_index, ordinal} | {:onexit, state_index, ordinal} | {:transition, t_index}`,
`Statifier.Machine.Content.owner/0` - specifically so a session-side subscriber
can correlate a line back to the block that produced it
(`lib/statifier/effect/log.ex:6-14`). The epic asks the send/invoke effects to
grow the same shape when they get a producer.

`Effect.trace?/1` (`lib/statifier/effect.ex:137-138`) is the single match that
splits the stream, which is what a session's fan-out uses to route trace
separately from core effects if it chooses to.

### The trace stream and the emission gate

Seven trace effects under `lib/statifier/effect/trace/`, one per
`docs/observability.md` constraint-2 row: `EventDequeued`,
`TransitionsSelected`, `ExitSet`, `ContentExecuted`, `EntrySet`,
`MacrostepStable`, `Done`. Every payload stamps `macrostep`/`microstep`/`round`
from the machine_state and carries constraint-3 *identities* (state index,
`t_index`, `c_index`) rather than structs, so tooling resolves through
`Machine.at/2`, `transition/2`, `content/2` (`lib/statifier/effect.ex:46-57`).

Emission is gated by the `Effect.trace/3` macro
(`lib/statifier/effect.ex:153-163`), which expands to a single boolean read and
`[]` when `machine_state.trace` is false, never evaluating the `fields`
expression. `trace` is a flat boolean on `MachineState`, set once by `new/2`
from the `:trace` option, never a level.

Two properties matter to the session:

- **Trace effects are ordinary list members, in order, on the same return
  value.** There is no side channel (`lib/statifier/effect.ex:59-63`,
  `docs/observability.md:75-76`). The bead's "subscribe to effects/trace" is
  therefore one stream with a `trace?/1` filter, not two.
- **`round` advances on rounds that run no microstep**, which is what keeps a
  livelocked fold ordered (ADR-0020). A session forwarding the stream gets a
  total order from `(macrostep, round)` with no clock of its own.

`docs/observability.md:135-147`, constraint 6, is the part of that document
addressed directly to this bead, and it is the only place the repo states what
the session must preserve:

> - **Observation**: the session forwards its effect/trace stream to
>   `:telemetry` or a subscriber pid. Live tooling attaches there; the core is
>   untouched.
> - **Replay**: because the core is pure and timers are effects, recording the
>   external inputs (delivered events, timer firings, with session timestamps)
>   at the session boundary makes a run reproducible: (machine, initial data,
>   external event log). Keep the session's input path single and capturable -
>   no side doors that inject events without crossing the recordable boundary.

The second bullet is a hard constraint on the API shape: every path by which an
event reaches `handle_event/2` - a caller's async send, a fired delayed-send
timer, a self-targeted `{:send, _}` re-enqueued from an effect - must funnel
through one recordable entry point.

### `MachineState` as the value the session holds

`lib/statifier/machine_state.ex`. Fields: `machine`, `configuration`
(`MapSet` of integer indexes, full configuration per ADR-0005),
`internal_queue` (`:queue.queue(Event.t())`), `history_values`,
`entered_states`, `datamodel` (map, holding spec 5.10's system variables
alongside author data), `running` (boolean, Appendix D's flag), `status`
(`:running | :done`), `macrostep`/`microstep`/`round`, `trace`,
`max_macrostep_rounds` (default `10_000`, or `:infinity`).

`new/2` (`lib/statifier/machine_state.ex:265-285`) accepts exactly four
options - `:trace`, `:datamodel`, `:session_id`, `:max_macrostep_rounds`. Note
that `Statifier.initialize/2`'s own `@doc` enumerates only three of them,
omitting `:session_id` (`lib/statifier.ex:82-85`); that gap is pre-existing and
was explicitly left alone once already
(`docs/plans/260812-st-sd1-macrostep-round-budget.md:137-141`).

The external queue's absence is a documented section of its own
(`lib/statifier/machine_state.ex:21-31`): Appendix D's `mainEventLoop` owns both
queues; this struct owns only the internal one, and "the session that drives it
owns queueing the waiting external events."

The counter contract (`lib/statifier/machine_state.ex:92-137`) has exactly three
writers - `begin_macrostep/1`, `begin_microstep/1`, `begin_round/1` - and the
session calls none of them. The initialization macrostep is macrostep 1; the
first external event is macrostep 2.

Serializability: every field is a plain term. No pid, ref, port, or fun appears
in the struct, which is what makes `docs/observability.md` constraint 1's
"complete, inspectable, resumable position" literally true and makes a
snapshot-returning `GenServer.call` cheap to reason about. The one caveat is
equality, not serialization: two `:queue` values holding the same events in the
same order can differ structurally, so `==` on two `%MachineState{}` values is
not a position test; use `internal_events/1`
(`lib/statifier/machine_state.ex:169-180`, `:334-335`).

### System variables: `_sessionid` and `_name` are already done

`lib/statifier/evaluator/system_variables.ex:50-60`:

```elixir
def initial(%Machine{} = machine, session_id) when is_binary(session_id) do
  %{
    "_sessionid" => session_id,
    "_name" => machine.name,
    "_event" => nil,
    "_ioprocessors" => %{
      "http://www.w3.org/TR/scxml/#SCXMLEventProcessor" => %{"location" => session_id}
    }
  }
end
```

Spec 5.10 (quoted from the cached REC) requires exactly this lifetime: "The
SCXML Processor MUST bind the variable `_sessionid` at load time to the
system-generated id for the current SCXML session... MUST keep the variable
bound to this value until the session terminates," and the same wording for
`_name` against the `<scxml>` element's `name` attribute. ADR-0008 adds that
the id is generated once at the owning entity's creation and never regenerated
- explicitly correcting v1, which regenerated `_sessionid` on every expression
evaluation.

`_ioprocessors` currently carries a minimal map whose `location` is the session
id; st-cmq.5 replaces it with the real SCXML Event I/O processor entry.

Tests already pin the behavior: `test/statifier/machine_state_test.exs:192-206`
covers a supplied `:session_id` winning and the generated default carrying the
`sess_` prefix; `:256-278` covers stability across `put_event/2` calls.

`UXID.generate!(prefix: "sess")` at `lib/statifier/machine_state.ex:267` is the
**only** `UXID.` call site in `lib/`. `send_` and `inv_` have no producer, so
ADR-0008's prefix table, not repo precedent, is the source of truth when they
arrive.

### `<send>`, `<cancel>`, `<invoke>`: nothing exists

No `Document.Send`/`Cancel`/`Invoke` struct
(`lib/statifier/document/` holds assign, block, content, data, datamodel,
donedata, foreach, if, initial, log, param, raise, script, state, transition),
no `Machine.Content.Send`/`Cancel`/`Invoke`
(`lib/statifier/machine/content/` holds assign, foreach, if, log, raise,
script), no lowering builder, no validator check. The test harness knows it:
`test/support/feature_detector.ex:106-113` marks `send_elements`,
`send_content_elements`, `send_param_elements`, `send_delay_expressions`,
`send_idlocation`, `cancel_elements`, `invoke_elements`, `finalize_elements`
all `:unsupported`, and `event_expressions`/`target_expressions` likewise
(`:80-81`). A corpus document using any of them flunks the feature gate rather
than reporting a false pass.

The consequence for this bead: **there is no document that can make the core
emit a `:send`, `:send_delayed`, or `:cancel` effect.** Every test of the
session's interpretation of those effects has to construct the effect struct
directly, or drive the session with a hand-built effect list, until st-cmq.3
lands. That is a testability fact, not a blocker - the structs are complete and
`@enforce_keys`-checked.

### Relevant spec clauses for the timer semantics

From the cached REC, 6.2 `<send>`:

> If a delay is specified via 'delay' or 'delayexpr', the SCXML Processor MUST
> interpret the character string as a time interval. It MUST dispatch the
> message only when the delay interval elapses. (Note that the evaluation of
> the send tag will return immediately.) The Processor MUST evaluate all
> arguments to `<send>` when the `<send>` element is evaluated, and not when
> the message is actually dispatched... **If the SCXML session terminates
> before the delay interval has elapsed, the SCXML Processor MUST discard the
> message without attempting to deliver it.**

The last sentence is the normative source for the bead's "delayed sends do not
survive session termination; terminating the session cancels outstanding
timers."

From 6.3 `<cancel>`:

> The SCXML Processor MUST NOT allow `<cancel>` to affect events that were not
> raised in the same session. The Processor SHOULD make its best attempt to
> cancel all delayed events with the specified id. Note, however, that it can
> not be guaranteed to succeed, for example if the event has already been
> delivered by the time the `<cancel>` tag executes.

"If multiple delayed events have this sendid, the Processor will cancel them
all" - so the timer table is keyed `send_id -> [timer_ref]`, not
`send_id -> timer_ref`, if a document can reuse a `sendid`. Note also that the
"already delivered" case is explicitly a permitted no-op, matching the bead's
"a sendid that already fired or never existed is a no-op per spec."

### What plays the session's role today

`Statifier` (`lib/statifier.ex`) is the four-function public surface:
`compile/1`, `initialize/2`, `send_event/2`, `active_leaf_states/1`. Its
moduledoc states the boundary the session inherits: "**Effects are returned,
never interpreted** (ADR-0003). Every function that can produce
`Statifier.Effect.t()` values hands them back as data; none of them is
inspected, logged, or executed here" (`lib/statifier.ex:18-21`).
`send_event/2` accepts a plain name string as a convenience over
`Event.external/2` (`lib/statifier.ex:113-117`).

The conformance harness is the only existing driver of the outer loop:
`Statifier.Case.test_scxml/4` (`test/support/case.ex:81-97`) initializes once,
then folds a list of events through `send_event/2`, asserting the configuration
after each. It flunks on `{:error, :not_running}` rather than tolerating it
(`test/support/case.ex:172-181`). This is exactly the shape the session
automates, with a queue and timers instead of a list and a fold.

The harness also already performs one piece of effect interpretation the
session would otherwise own: because a terminated chart's `configuration` is
empty by construction, `assert_configuration/3` looks for a `{:done, _}` in the
effect list and restores that effect's `configuration` onto the
`%MachineState{}` before reading leaves off it (`test/support/case.ex:23-32`).
A session that keeps a readable terminal snapshot has to make the same move.

`Statifier.Case`'s moduledoc also records that v1's `StateMachine` and its
logging helpers were deliberately not ported, so there is no v1-shaped
precedent in the test tree either.

### v1 as a comparison point

`../statifier` (read-only reference) answers only part of this. Its
`Statifier.StateMachine` (`../statifier/lib/statifier/state_machine.ex:66`) is a
GenServer holding `state_chart`, a `delayed_sends` map of
`send_id -> timer_ref`, and a snapshot timer; delayed sends schedule with
`Process.send_after(self(), {:delayed_send, send_id, event}, delay_ms)`
(`:339`) and fire in `handle_info` (`:376-390`). Cancellation exists only as an
unexposed `handle_call({:cancel_delayed_send, send_id}, ...)` (`:360-372`); the
`<cancel>` *element* does not exist in v1 at all.

The structural differences that matter here, all of which v1's design is the
argument against:

- v1 stores both queues in the `%StateChart{}` struct and stores the GenServer
  pid *inside* it (`../statifier/lib/statifier/state_chart.ex:15`) - the exact
  mixing ADR-0003 was written to prevent.
- v1's `execute_delayed_send` checks for a pid and, when there is none, **warns
  and fires immediately, ignoring the delay**
  (`../statifier/lib/statifier/actions/send_action.ex:256-268`). This is the
  "delayed send silently becomes immediate in the sync API" bug ADR-0003's
  Context names by name; effects-as-data makes it unrepresentable.
- v1 has no session identity at all: no `_sessionid`, `_name`, or
  `_ioprocessors` anywhere; the only system variable is `_event`
  (`../statifier/lib/statifier/datamodel.ex:152-200`).
- v1's target resolution is a literal string compare against `"#_internal"`,
  with everything else logged and dropped
  (`../statifier/lib/statifier/actions/send_action.ex:82-102`).
- v1 has no `isCancelEvent`, no platform event type, and no invoked-child
  session - `<invoke>` is a synchronous user-registered callback run inline
  inside the microstep (`../statifier/lib/statifier/actions/invoke_action.ex:70-79`).

## Architecture Documentation

- **ADR-0003** (pure core with effects) is the founding decision. It names
  `Statifier.Session` explicitly: "`Statifier.Session` (GenServer) is the
  production effect interpreter owning timers, invoke lifecycles, and
  parent/child session routing. Tests interpret effects directly, no processes
  required. No pids, adapters, or log buffers live in core state." Its
  Consequences list "Deterministic replay: a session is (machine, initial data,
  event log)" and "Embedders can supply their own effect interpreter (e.g.
  queue delayed sends into Oban instead of process timers)" - the second is an
  argument for keeping effect interpretation a replaceable seam rather than
  hard-wiring `Process.send_after` into the only code path.
- **ADR-0002** (literal Appendix D port) is why the deviation comment at
  `main_event_loop/1` exists at all, and why anything this bead moves outward
  needs its mechanical reason written at the port site.
- **ADR-0008** (UXID) fixes `sess_` as the session prefix, generated once and
  immutable. Its Consequences add a constraint on tests: "tests must not depend
  on their shape beyond the documented prefix."
- **ADR-0012 / `docs/observability.md`** constraint 6 is the only written spec
  of this layer's obligations (observation and replay, quoted above).
  Constraint 1 is what makes the snapshot API trivial.
- **ADR-0019 / ADR-0020** bound the inner fold. `docs/plans/260812-st-sd1-macrostep-round-budget.md:130-133`
  states plainly that what to *do* about a `:budget_exhausted` effect - "alert,
  retry with a bigger budget" - is this epic's decision and nothing handles the
  effect anywhere today. That is a live design question for the session's
  effect loop (open question 6).
- **ADR-0018** (process artifacts are not code comments) binds this bead's
  output directly and mechanically. `Mix.Statifier.AdrGuard` now flags a bead ID
  added on a comment or doc-string line, with its own dedicated escape marker
  `ADR-0018-exempt` (`lib/mix/statifier/adr_guard.ex:105-110`, `:262-283`). The
  new `Statifier.Session` moduledoc therefore cannot name `st-cmq`, and any
  edit that rewrites one of the ten existing `st-cmq` seam comments in
  `lib/statifier/interpreter.ex` and `lib/statifier/interpreter/datamodel.ex`
  must restate the fact rather than move the ID.
- **`docs/architecture.md:121-131`** is the standing description: "`Statifier.Session`
  is the GenServer effect-interpreter: it owns timers for delayed sends,
  processes `<cancel>`, and supervises child sessions." Note "supervises child
  sessions" - the supervision shape is not purely this bead's convenience, since
  st-cmq.7 needs a parent to own children, and st-cmq.5 needs a registry to
  resolve `#_scxml_<sessionid>` targets "through the registry, not raw pids."
- **Gate mechanics.** `.doctor.exs` sets 100% doc and spec coverage on every
  axis; Doctor exempts `@impl`-annotated callbacks in a module with a behaviour
  (`deps/doctor/lib/module_report.ex:106-120`), and `use GenServer` registers
  the behaviour, so `handle_call/3` and friends need no `@doc`/`@spec`. The
  public client functions do. `coveralls.json` sets `minimum_coverage: 90`.

## Open Questions

These are recorded rather than resolved; each is a plan-stage decision.

1. **Does the library gain an application callback module and a supervision
   tree?** `mix.exs` has no `mod:` today and `lib/statifier/` contains no OTP at
   all. A `DynamicSupervisor` + `Registry` (which st-cmq.5 needs anyway to
   resolve `#_scxml_<sessionid>` targets "through the registry, not raw pids",
   and st-cmq.7 needs to parent child sessions) implies both, and implies the
   library starts processes on load for every embedder whether they use
   sessions or not. The alternative - `start_link/1` returning a linked pid with
   no registry, and the embedder supplying supervision - keeps the library
   process-free by default but leaves st-cmq.5 and st-cmq.7 to introduce the
   registry later. The bead names this as the plan's call; nothing in the repo
   or the ADRs settles it.

2. **Does `:done` stop the session process or idle it?** `Effect.Done` carries
   the full configuration precisely so a consumer "can observe the terminal
   position without switching tracing on"
   (`lib/statifier/effect/done.ex:6-12`), which argues the machine_state stays
   readable after termination - i.e. idle, answering snapshot queries, with
   `status: :done`. Against that, `handle_event/2` already returns
   `{:error, :not_running}` for every subsequent event, so an idle session
   accepts nothing and only holds memory. A third shape is "stop with reason
   `:normal` after notifying the owner", which loses the post-mortem snapshot
   unless the owner captured it from the notification. Note the interaction with
   question 1: under a `DynamicSupervisor` with `restart: :transient`, stopping
   `:normal` is clean; under links, it terminates the linked owner unless the
   owner traps exits.

3. **What is the "notify owner" contract?** The bead says `:done` notifies the
   owner and that subscribers get effects/trace. Whether the owner is a distinct
   concept from a subscriber (a single `:owner` pid receiving lifecycle
   messages, versus everything going to the subscriber set) is undecided, as is
   the message shape. `docs/observability.md` constraint 6 says "`:telemetry` or
   a subscriber pid" without choosing, and st-cmq.1 builds the telemetry bridge
   *on* whatever stream this bead exposes - so the stream's shape is this bead's
   commitment and telemetry event names are not.

4. **What is a cancel event in this engine?** Appendix D's `isCancelEvent`
   explicitly says "The mechanism for this is platform specific, but here we
   assume it's a special event we receive". `Statifier.Event` has no fourth
   `type` and no cancel notion. Candidate shapes: a reserved event name, a
   fourth `Event.type`, or an out-of-band `GenServer.call(:stop)` that sets
   `running: false` without going through the queue at all - but the last one
   conflicts with constraint 6's "keep the session's input path single and
   capturable", since a cancellation that does not cross the recordable boundary
   is not replayable. Note also that `MachineState` has no public writer for
   `running`, so a cancel that sets it needs either a new `MachineState`
   function or a core-side `cancel/1` entry point alongside `handle_event/2`.

5. **Where does a self- or internal-targeted `{:send, _}` re-enter?** The bead
   says self/internal targets are "enqueued back to this session". The repo
   already draws half the line: `Statifier.Event.internal/3`'s `@doc`
   (`lib/statifier/event.ex:63-69`) says "spec 5.10.1 restricts `type: :internal`
   to `<raise>` and `<send>` with `target="#_internal"`; a `<send>` with no
   `target` goes to the sending session's *external* queue and is
   `type: :external` instead". So the absent-target case is settled - it is an
   external event the session queues like any other. The `#_internal` case is
   not: that queue lives on `MachineState` and is drained inside a macrostep,
   so an internal-target send arriving as an effect after `handle_event/2` has
   already returned cannot be put where the spec wants it without either a
   `MachineState.enqueue_internal/2` call from the session (writing core state
   from outside the core) or the core resolving `#_internal` itself before the
   effect ever escapes. st-cmq.5 owns target routing, but which side of the
   boundary `#_internal` is resolved on is a question this bead's API shape
   decides first.

6. **What does the session do with `:budget_exhausted`?** ADR-0019's plan
   explicitly deferred the policy here and nothing handles the effect today. The
   returned machine_state is a resumable position, so "forward it and keep the
   position" is available; so is "treat it as a fault and stop".

7. **Is the timer table keyed to one ref or many per `send_id`?** Spec 6.3 says
   "If multiple delayed events have this sendid, the Processor will cancel them
   all," which is only reachable if a document can produce two live delayed
   sends under one id. `<send id>` is author-supplied and `idlocation` generates
   one, so a repeated author-supplied `id` on a state entered twice is the
   reachable case. v1 used a flat `send_id -> ref` map and would silently lose
   the first ref.

8. **Does the snapshot query return the whole `%MachineState{}` or a projection?**
   The bead says "synchronous query of the current MachineState snapshot (it is
   a value - constraint 1 makes this free)". It is free of *staleness* concerns,
   but a `GenServer.call` copies the term, and `machine_state.machine` is the
   whole compiled document on every call. A projection (configuration as string
   ids, status, counters) avoids that; returning the struct preserves constraint
   1's "resumable position" property for tooling. Both may be wanted.
