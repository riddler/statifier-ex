# Research: `<script>` as predicator statement programs

**Date**: 2026-08-14T06:24:54-0600
**Git Commit**: 456d28e5d477f11ff162e52a5a6ec8e946235d1e
**Branch**: st-af3.17-script-statement-bodies
**Bead**: st-af3.17

## Research Question

ADR-0026 is accepted: `<script>` is supported, its body compiles with
`Predicator.parse_program/2` and executes with `Predicator.execute/3`, the
partial context on error is kept, `<script src>` is rejected, and a
top-level `<script>` is a load-time path. This research documents the
codebase as it stands today so an implementation plan can be written
against it: where the program path attaches to the evaluator, what the
executable-content contract requires, what the parser and lowering already
retain, where a placement or `src` rejection would live, what the load-time
seam actually looks like now, and what the corpus tooling requires.

The decisions ADR-0026 makes are settled and are not re-opened here.

## Summary

- **The element pattern is closed and mechanical.** `<assign>` (st-af3.4)
  established every seam a datamodel-mutating executable-content element
  needs, and every one of them is still open for a second occupant. Nothing
  in the protocol, the block runner, `Machine.content/2`, or the interpreter
  changes for a `<script>` node.
- **The expression path and the program path are genuinely separate
  upstream.** `Machine.expr()` is `{:static, term} | {:compiled,
  %Predicator.Compiled{}, source}` and rides `Predicator.evaluate/3`, which
  *rejects* a statement program: `Predicator.parse/2`'s expression grammar
  never produces `{:if, ...}` or `{:block, ...}`. A script body must go
  through `parse_program/2` / `compile_program_with_positions/1` /
  `execute/3`. So the program path is a **new sibling type**, not a third
  arm of `Machine.expr()` that `Statifier.Evaluator.evaluate/2` learns.
- **The parser needs no change at all.** `Statifier.Parser.Handler` already
  retains character data verbatim and untrimmed, merging split runs;
  `<script>` already produces a normal `%DOM.Element{}` with `%DOM.Text{}`
  children. It is *lowering* that rejects `<script>` today, via a
  dispatch-map miss producing `{:unsupported_element, "script"}`.
- **The ceiling is higher than the bead's Design section assumes.**
  Predicator 7.0's `if` and `while` are **fully implemented statements**,
  not merely reserved words - parsed, lowered, and loop-budgeted. What
  actually fails to parse is `var`, object literals, `typeof`, and function
  definitions. The separator is `;` and is **mandatory** (newlines are plain
  whitespace), which is a sharper constraint on ECMAScript corpus bodies
  than the reserved-word list.
- **Neither `Document` nor `Machine` has a slot for a top-level
  `<script>`.** `Document` has `datamodel_element` but nothing beside it;
  `Machine`'s nine fields are deliberately minimal and executable content is
  reachable only through the `c_index`-addressed `contents` tuple. The
  load-time path ADR-0026 decision 3 describes needs a new field on both.
- **Two `<assign>` invariants that `<script>` cannot inherit.** `<assign>`
  refuses to create a new top-level root (`check_root/3`) and refuses a
  write to a system variable (`check_system_variable/1`). Predicator's
  `store` instruction does neither check - it auto-vivifies freely. W3C
  test304 exists precisely to assert that a script-declared variable is
  readable, so root creation is required, not optional.
- **The corpus surface is larger than the bead names.** Besides the four
  SCION `:needs_script` entries, `tools/corpus/scxml_w3/exclusions.exs`
  carries `test302`/`test303`/`test304` on the same clause, and
  `conf_predicator.xsl` stubs four `conf:` templates on it. The SCION and
  W3C sources are **not vendored** - `mise run corpus:fetch` is a
  prerequisite for ADR-0026 decision 4's file-by-file determination.
- **`:partial` is a notation the feature registry supports and has never
  used.** No entry in `feature_registry/0` is `:partial` today, and
  `validate_features/1` treats it identically to `:supported`.

## Detailed Findings

### The evaluator, `Machine.expr()`, and where a program path attaches

`Machine.expr()` is declared once, at [`lib/statifier/machine.ex:90`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine.ex#L90):

```elixir
@type expr :: {:static, term()} | {:compiled, Predicator.Compiled.t(), source :: String.t()}
```

`Statifier.Evaluator` is small and has exactly two public functions
(`lib/statifier/evaluator.ex`):

- `context/1` ([`lib/statifier/evaluator.ex:97-103`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/evaluator.ex#L97-L103)) builds a
  `%Predicator.Context{}` from `machine_state.datamodel` with an `In/1` host
  function closing over `machine`/`configuration`, and `on_unbound: :error`.
  It is a **position snapshot**, deliberately never cached on
  `MachineState` ([`lib/statifier/evaluator.ex:37-73`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/evaluator.ex#L37-L73) states both reasons:
  ADR-0012 resumability, and staleness by construction).
- `evaluate/2` ([`lib/statifier/evaluator.ex:151-163`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/evaluator.ex#L151-L163)) dispatches the two
  `expr()` arms. `{:static, v}` returns `{:ok, v}` untouched; `{:compiled,
  compiled, source}` calls `Predicator.evaluate(compiled, context)` and
  wraps a failure as `{:error, Evaluator.Error.new(source, error)}`.
  `{:invalid, error}` is **never** seen here - callers intercept it first.

Compilation is `Statifier.Compiler.Expressions.compile/3`
([`lib/statifier/compiler/expressions.ex:62-73`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/compiler/expressions.ex#L62-L73)), which calls
`Predicator.compile_with_spans/1` and on failure re-parses via
`Predicator.parse/2` to recover `{line, column}` (the failure path returns
only a formatted string). Its version comment
([`lib/statifier/compiler/expressions.ex:53-60`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/compiler/expressions.ex#L53-L60)) is already current - it
cites "the installed predicator 7.0.0 dependency", refreshed by st-5ma.

**Where a program path attaches.** Not as a third arm of `expr()`.
Upstream, `Predicator.evaluate/3` takes an expression AST/instructions and
`Predicator.execute/3` takes a program; `lib/predicator.ex:213-217` records
that the expression grammar never produces statement nodes. The natural
shape by analogy is a sibling type (a `{:program, %Predicator.Compiled{},
source}` or similar) compiled by a new
`Statifier.Compiler.Expressions.compile_program/3` wrapping
`Predicator.compile_program_with_positions/1`, and executed by a new
`Statifier.Evaluator.execute/2` wrapping `Predicator.execute/3`. Nothing
in the codebase forces that shape - it is a plan decision - but the
existing pairing of `Expressions` (compile half) with `Evaluator`
(evaluate half) under ADR-0014 is the symmetry it would follow.

**The deferral asymmetry that a program body must choose a side of.**
`docs/datamodel.md` records that a non-compiling expression is rejected at
load time *everywhere except* `<data expr>` and `<assign expr>`, which
defer to runtime as `{:invalid, error}` on the compiled node
([`lib/statifier/compiler.ex:1199`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/compiler.ex#L1199) for `<data expr>`,
[`lib/statifier/compiler.ex:860-876`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/compiler.ex#L860-L876) for `<assign expr>`). The asymmetry is
deliberate and exists because two SCION fixtures assert `error.execution`
for an unparseable expression. ADR-0026 does not say which side a
`<script>` body falls on. See Open Question 1.

### The executable-content contract, as `<assign>` implements it

**The protocol** (`lib/statifier/executable_content.ex`) has one function,
`execute/2` ([`lib/statifier/executable_content.ex:83-84`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/executable_content.ex#L83-L84)), and three result
shapes ([`lib/statifier/executable_content.ex:73-76`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/executable_content.ex#L73-L76)):

```elixir
{:ok, Context.t(), [Effect.t()]}
| {:error, term()}
| {:error, Context.t(), term()}
```

The three-element error arm is the one that preserves work already done
before a failure, and today only `If` and `Foreach` use it. **A `<script>`
node keeping ADR-0026 decision 1's partial context is exactly this arm** -
the mechanism already exists and needs no protocol change. There is no
`@fallback_to_any` ([`lib/statifier/executable_content.ex:59-66`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/executable_content.ex#L59-L66)): a struct
with no `defimpl` is a compile-time bug, per "Machine is valid by
construction". A node never raises and never constructs a
`Statifier.Event`.

**The context struct** ([`lib/statifier/executable_content/context.ex:63-71`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/executable_content/context.ex#L63-L71))
has `@enforce_keys [:machine_state, :owner, :datamodel_context]` plus
`pending_errors`. `datamodel_context` is built **once per block** by the
runner, and is *not* automatically kept fresh: a node that mutates the
datamodel must rebuild it itself by calling `Evaluator.context/1` and
writing the result back in the same struct update
([`lib/statifier/executable_content/context.ex:16-31`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/executable_content/context.ex#L16-L31)). Two sites do this
today - [`lib/statifier/machine/content/assign.ex:82-89`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/assign.ex#L82-L89) and
[`lib/statifier/machine/content/foreach.ex:276-285`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/foreach.ex#L276-L285). The runner never does
([`lib/statifier/interpreter/content.ex:49-57`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/interpreter/content.ex#L49-L57)), and doing it there is the
sabotage named in [`test/statifier/interpreter/content_test.exs:316-341`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/test/statifier/interpreter/content_test.exs#L316-L341).

**The block runner** (`lib/statifier/interpreter/content.ex`) builds the
`Context` once at [`lib/statifier/interpreter/content.ex:140-145`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/interpreter/content.ex#L140-L145), folds
`run_nodes/2` ([`lib/statifier/interpreter/content.ex:172-193`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/interpreter/content.ex#L172-L193)) over the
`c_index` list, and owns the sole `error.execution` conversion in
`raise_execution_error/4` ([`lib/statifier/interpreter/content.ex:229-239`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/interpreter/content.ex#L229-L239)):

```elixir
defp raise_execution_error(machine_state, owner, c_index, reason) do
  MachineState.raise_platform(machine_state, "error.execution", {:content, c_index, owner},
    data: reason
  )
end
```

`raise_platform/4` rather than `raise_internal/4`, because spec 5.10.1
classifies `error.*` as a platform event. `run_nodes/2` treats the
three-element error arm as "keep `new_context`" and the two-element arm as
"discard back to the pre-call context" - the exact distinction ADR-0026
decision 1 needs.

**`<assign>`'s own implementation**
([`lib/statifier/machine/content/assign.ex:74-91`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/assign.ex#L74-L91)) is a five-step `with`:
evaluate the value, resolve the location via
`Predicator.context_location/3`, **reject a resolved root beginning with
`_`** ([`lib/statifier/machine/content/assign.ex:143-153`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/assign.ex#L143-L153), spec 5.10),
**require the resolved root to already be a key of
`machine_state.datamodel`**
([`lib/statifier/machine/content/assign.ex:162-173`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/assign.ex#L162-L173), returning
`{:error, {:unbound_location, location}}`), then write via
`Predicator.ContextLocation.put/3` against the raw datamodel map. On
success it returns `{:ok, context_with_rebuilt_datamodel_context, []}` - no
effect. [`docs/observability.md:57-68`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/docs/observability.md#L57-L68)'s trace vocabulary is closed and has
no datamodel-write row, so a pure datamodel mutation emits nothing;
`Trace.ContentExecuted` already covers any content node via `c_indexes`.

The other family members, for shape reference: `Log`
(`lib/statifier/machine/content/log.ex`) leaves `machine_state` alone and
emits one effect; `Raise` (`lib/statifier/machine/content/raise.ex`)
mutates `machine_state` and emits none; `If`
(`lib/statifier/machine/content/if.ex`) and `Foreach`
(`lib/statifier/machine/content/foreach.ex`) are the two composites, both
folding their own partitions directly rather than recursing through the
block runner. A `<script>` node is the `Raise`/`Assign` shape: mutate
state, emit nothing.

### The parser and the lowering path

**The parser needs no change.** `Statifier.Parser.Handler` routes both
`:characters` and `:cdata` to the same accumulator
([`lib/statifier/parser/handler.ex:110-112`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/parser/handler.ex#L110-L112)), and `add_text/2`
([`lib/statifier/parser/handler.ex:129-143`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/parser/handler.ex#L129-L143)) appends to an open `%DOM.Text{}`
sibling or creates one - **no trimming, no normalization**, raw bytes.
`text_span/1` ([`lib/statifier/parser/handler.ex:149-157`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/parser/handler.ex#L149-L157)) recomputes the
span on every event of a split run so it always covers the whole raw run.
`%DOM.Element{}` (`lib/statifier/parser/dom/element.ex`) is fully generic;
nothing under `lib/statifier/parser/` special-cases any element name.

`Statifier.Parser.DOM.text/1` ([`lib/statifier/parser/dom.ex:44-55`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/parser/dom.ex#L44-L55)) is the
shared body reader - it concatenates direct `%Text{}` children verbatim.
Three builders use it today, all treating any *element* child as a
`misplaced_element` error rather than walking it: `build_content/2`
([`lib/statifier/lowering/builders.ex:349-369`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L349-L369)), `build_data/2`
([`lib/statifier/lowering/builders.ex:414-446`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L414-L446)), and `build_assign/2`
([`lib/statifier/lowering/builders.ex:472-501`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L472-L501)). Each sets
`text: DOM.text(element)` on its `Document.*` struct. That is the exact
template a `build_script/2` follows.

**Lowering is what rejects `<script>` today.** The `@dispatch` map
([`lib/statifier/lowering.ex:53-75`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering.ex#L53-L75)) has no `"script"` key, so
`walk_child/4` falls to its miss clause
([`lib/statifier/lowering.ex:151-152`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering.ex#L151-L152)) and reports
`Error.unsupported(name, location)`. Any accumulated error makes
`lower/1` return `{:error, errors}` - so a `<script>` document is
currently unloadable, not silently ignored.

The builder contract is `build_x(element, ctx) :: {tagged_result, [Error.t()]}`
where `tagged_result` is `nil` or `{slot_tag, struct}`; the builder never
knows its parent. `place/3`
([`lib/statifier/lowering/builders.ex:769-897`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L769-L897)) is where a struct is folded
into its parent's slot, with a catch-all reporting
`{:misplaced_element, name, parent_name}`. `content_node_name/1`
([`lib/statifier/lowering/builders.ex:899-905`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L899-L905)) is private and exists
because `:content_node` is a shared tag covering five struct kinds - it
recovers the SCXML tag name from the struct for a misplacement message:

```elixir
defp content_node_name(%Raise{}), do: "raise"
defp content_node_name(%Log{}), do: "log"
defp content_node_name(%Assign{}), do: "assign"
defp content_node_name(%If{}), do: "if"
defp content_node_name(%Foreach{}), do: "foreach"
```

Note the `%Assign{}` precedent at
[`lib/statifier/lowering/builders.ex:883-885`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L883-L885): it needs a dedicated
placement clause *before* the generic `:content_node` catch-all because its
element span lives on `node_location` rather than `location`. A `Script`
node naming its span the same way inherits the same requirement.

**Compilation to `Machine.Content.*`** happens in two passes in
`lib/statifier/compiler.ex`: `assign_content_node/2`
([`lib/statifier/compiler.ex:513-561`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/compiler.ex#L513-L561)) walks `onentry`/`onexit`/transition
content assigning dense document-order `c_index` values and stashing the
raw `Document.*` nodes, and `build_content_node/2`
([`lib/statifier/compiler.ex:744-876`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/compiler.ex#L744-L876)) has one clause per raw shape. The
numbering pass is already generic. `Statifier.Machine.Content`
(`lib/statifier/machine/content.ex`) is a namespace module whose moduledoc
at [`lib/statifier/machine/content.ex:14`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content.ex#L14) already names `<script>` as a
future member getting "its own struct here too, and its own
`Statifier.ExecutableContent` implementation, never a clause added to this
module."

### The validator, placement, and where a `<script src>` rejection would live

`Statifier.Validator` ([`lib/statifier/validator.ex:83-95`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator.ex#L83-L95)) is collect-all,
never fail-fast: sixteen `&Module.check/2` captures in `@checks`
([`lib/statifier/validator.ex:51-68`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator.ex#L51-L68)), each returning `[Error.t()]`, flat-mapped
and sorted by `location.start_offset`. There is no `@behaviour` - a check is
any 2-arity function. There is **no warning concept**; `Statifier.Validator.Error`
([`lib/statifier/validator/error.ex:68-75`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator/error.ex#L68-L75)) is the only outcome shape, with a
closed tagged-tuple `reason` union and one constructor per reason.

Errors reach the caller through `Statifier.compile/1`
([`lib/statifier.ex:59-65`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier.ex#L59-L65)), a `with` chain with no `{:error, _}` clause of
its own, so `{:error, [Validator.Error.t()]}` short-circuits out unchanged.

**Element placement is mostly not a validator concern.** The primary
mechanism is structural, in `place/3`'s per-slot clauses; a missing clause
is a `misplaced_element`. The validator's own best placement example is
`Checks.Final` ([`lib/statifier/validator/checks/final.ex:34-51`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator/checks/final.ex#L34-L51)), which
enforces spec 3.7's content model and reports at the *offending child's*
location.

**The mutual-exclusion template** is
`lib/statifier/validator/checks/assign.ex` - spec 5.4.2's "either `expr` or
children, but not both". Two details from it matter for `<script>`:

1. **Whitespace-only text is not text**
   ([`lib/statifier/validator/checks/assign.ex:12-17`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator/checks/assign.ex#L12-L17), `blank?/1` at
   `:118-119`). `DOM.text/1` is untrimmed, so a pretty-printed element
   carries `"\n  "`. Firing on that would reject documents the spec allows.
   The same rule is in `Checks.Content.blank?/1` and `Checks.Data.blank?/1`.
2. **Only two checks walk executable-content nodes** -
   `Checks.Assign` and `Checks.If` - and both need the `descend/1` recursion
   through `%DIf{}` branches and `%DForeach{}` bodies
   ([`lib/statifier/validator/checks/assign.ex:97-103`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator/checks/assign.ex#L97-L103)) or a node nested
   inside a partition is invisible. The moduledoc
   ([`lib/statifier/validator/checks/assign.ex:88-96`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/validator/checks/assign.ex#L88-L96)) states this boundary
   explicitly "so the next composite element does not re-run the audit from
   scratch". A `<script>` check needs the same walk.

Critically, that walk starts from `document.states` - it reaches
`onentry`/`onexit`, transitions, and `<initial>` transitions. **It does not
reach a top-level `<script>` child of `<scxml>`**, which lives nowhere in
`Document` today.

**No existing check rejects a named, in-vocabulary, unimplemented
feature.** The two closest patterns are both in lowering:
`Error.unsupported/2` ([`lib/statifier/lowering/error.ex:39-49`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/error.ex#L39-L49)) for an
unknown element name, and `Error.unexpected_attribute/3`
([`lib/statifier/lowering/error.ex:119-135`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/error.ex#L119-L135)) for a known element carrying an
attribute it does not take - whose only user today is `build_else/2`
([`lib/statifier/lowering/builders.ex:606-628`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/builders.ex#L606-L628)), which reports the attribute
and still builds the struct. The `Lowering.Error.reason` union
([`lib/statifier/lowering/error.ex:21-28`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/error.ex#L21-L28)) is declared closed, so a new
named reason is an explicit extension of it.

**`<data src>` is not the precedent it looks like.** ADR-0024's shipped
behavior is *not* a load rejection: `src` compiles to `{:src, uri}` and
`bind_value/4` ([`lib/statifier/interpreter/datamodel.ex:195-197`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/interpreter/datamodel.ex#L195-L197)) raises
`error.execution` at binding time, leaving the id nil. ADR-0026 decision 2
calls for `<script src>` to be **rejected at load with a named unsupported
error** - a deliberately different shape. Which layer owns it is open
(Open Question 4).

**Execute.** [`deps/predicator/lib/predicator.ex:404-415`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L404-L415):

```elixir
@spec execute(
        binary() | Types.instruction_list() | Compiled.t(),
        Types.context() | Context.t(),
        keyword()
      ) :: {:ok, Context.t()} | {:error, struct(), Context.t()}
```

The partial-context contract, verbatim
([`deps/predicator/lib/predicator.ex:374-391`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L374-L391)):

> `{:error, error_struct, context}` - execution stopped at the failing
> statement. `context` is the context **as of the last successfully
> completed statement** - every earlier write survives, the failing
> statement's write does not happen, and no later statement runs. Handing
> back this partial context costs nothing (contexts are immutable) and
> commit-or-discard is left to the caller.

Two mechanical details that matter here. First, **a parse failure also
returns the three-tuple** ([`deps/predicator/lib/predicator.ex:530-539`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L530-L539)) -
`execute/3` never returns a two-element error, so a runtime-deferred
compile failure and a runtime execution failure arrive in the same shape.
Second, the returned context is `%{input_context | data: final.context}`
([`deps/predicator/lib/predicator.ex:554-564`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L554-L564)) - `functions`, `on_unbound`,
and `host` from the caller's context survive, so the `In/1` host function
`Evaluator.context/1` installs is preserved across a program run.

Options include `:loop_budget` (default 10_000 back edges; exhaustion is
`%EvaluationError{reason: "loop_budget_exceeded"}`,
[`deps/predicator/lib/predicator.ex:128-132`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L128-L132)) - relevant because `while` is
real. Passing `:positions` alongside a `%Compiled{}` raises `ArgumentError`
([`deps/predicator/lib/predicator.ex:476`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L476)), the same trap ADR-0014 item 2
already records for the expression path.

**Context.** `%Predicator.Context{data, functions, on_unbound, host}`
([`deps/predicator/lib/predicator/context.ex:64-71`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/context.ex#L64-L71)). There is **no
`to_map/1` and no `get/2,3`** - you read `context.data` directly. Since
6.0, `nil` is preserved as the null value and is distinct from the
`:undefined` sentinel ([`deps/predicator/lib/predicator/context.ex:99-100`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/context.ex#L99-L100),
[`deps/predicator/lib/predicator/undefined.ex:76-78`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/undefined.ex#L76-L78)).

**The statement grammar**, verbatim from
[`deps/predicator/lib/predicator/parser.ex:16-22`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/parser.ex#L16-L22):

```
program      → statement ( ";" statement )* ( ";" )?
statement    → if_statement | while_statement | assignment | expression
if_statement → "if" expression block ( "else" ( block | if_statement ) )?
while_statement → "while" expression block
block        → "{" ( statement ( ";" statement )* ( ";" )? )? "}"
assignment   → location "=" expression
location     → IDENTIFIER ( "." IDENTIFIER | "[" expression "]" )*
```

`if` and `while` are **fully implemented**, parsed at
[`deps/predicator/lib/predicator/parser.ex:565-575`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/parser.ex#L565-L575) and lowered at
[`deps/predicator/lib/predicator/visitors/instructions_visitor.ex:345-383`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/visitors/instructions_visitor.ex#L345-L383).
Braces are mandatory. The separator is `;` only - newlines are plain
whitespace ([`deps/predicator/lib/predicator/lexer.ex:603`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/lexer.ex#L603)) - with one
exception: a statement ending in `}` may be followed directly by the next
([`deps/predicator/lib/predicator/parser.ex:549-554`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/parser.ex#L549-L554)). Assignment LHS is any
identifier/property/bracket access chain.

Reserved words ([`deps/predicator/lib/predicator/lexer.ex:499-522`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/lexer.ex#L499-L522)):
`true`, `false`, `undefined`, `null`, `AND`/`and`, `OR`/`or`, `NOT`/`not`,
`IN`/`in`, `CONTAINS`/`contains`, `if`, `else`, `while`, `ago`, `from`,
`now`, `next`, `last`. The seven cast type names are contextual and stay
usable as variable names.

**`store` and `pop`** are ISA tier 6
([`deps/predicator/lib/predicator/instructions.ex:90-91`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/instructions.ex#L90-L91)). `["store", n]`
([`deps/predicator/lib/predicator/evaluator.ex:1491-1523`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/evaluator.ex#L1491-L1523)) pops `n + 1`
values - value on top, then `n` path segments - and writes via
`ContextLocation.put/3`, **auto-vivifying** and with no root-existence or
system-variable check. A `LocationError` from the write is wrapped into an
`EvaluationError` with `operation: :store` and a reason of
`"not_assignable"`, `"not_a_container"`, or `"invalid_index"`
([`deps/predicator/lib/predicator/evaluator.ex:1571-1582`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/evaluator.ex#L1571-L1582)). `["pop"]`
([`deps/predicator/lib/predicator/evaluator.ex:1625-1631`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/evaluator.ex#L1625-L1631)) discards the stack
top and records it as `last_value`; the emitter appends a `pop` after every
expression statement and nothing else
([`deps/predicator/lib/predicator/visitors/instructions_visitor.ex:426-454`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator/visitors/instructions_visitor.ex#L426-L454)).

**Error structs** `execute/3` can hand back: `%ParseError{message, position}`,
`%EvaluationError{message, reason, operation, position, span}`,
`%TypeMismatchError{...}`, `%UndefinedVariableError{message, variable, position, span}`.
`%LocationError{}` does **not** escape the program path - it is wrapped at
the `store`. None of these is a `Statifier.Evaluator.Error`, which is the
`{source, error, span}` wrapper the expression path produces.

Upstream, `conf:script` expands to `<script>var Var1 = 1</script>`. `var`
is not predicator, so the local stylesheet emitting `Var1 = 1` is the
minimum change - and `Var1` is undeclared in test302 and test304, so those
two require the script to *create* a top-level root (Open Question 2). The
three W3C cases test exactly the three things ADR-0026 decides:

- **test302** - a top-level `<script>` runs at load time, observed by `Var1`
  having a value in the initial state. This is decision 3's path.
- **test303** - `<script>` runs as executable content in document order,
  observed by an `<assign>` before it being overwritten. This is the
  ordinary block-runner path.
- **test304** - a variable *declared by a script* is readable like any other
  datamodel member. This is the root-creation requirement.

`conf:scriptGoodSrc`/`conf:scriptBadSrc` are referenced by no `.txml` in
the suite, so `<script src>`'s W3C exposure is nil; the SCION `script-src`
directory is the only `src` corpus pressure, and ADR-0026 decision 2
rejects it.

## Open Questions

None of these re-opens ADR-0026; each is a shape the record leaves to the
planning stage.

1. **Does a body that fails `parse_program/2` reject at load, or defer to
   runtime as `{:invalid, error}`?** `docs/datamodel.md` records load-time
   rejection everywhere except `<data expr>` and `<assign expr>`, and notes
   that if the split is ever unified it unifies *toward* deferral. ADR-0026
   is silent. The consequence is large for the corpus: load-time rejection
   makes every ECMAScript-bodied `<script>` document unloadable, whereas
   deferral loads them and produces `error.execution`. Note that
   `Predicator.execute/3` returns the same three-element error tuple for a
   parse failure as for an execution failure
   ([`deps/predicator/lib/predicator.ex:530-539`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/deps/predicator/lib/predicator.ex#L530-L539)), so deferral costs no extra
   error-shape handling.

2. **May a `<script>` create a new top-level datamodel root?** `<assign>`
   refuses ([`lib/statifier/machine/content/assign.ex:162-173`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/assign.ex#L162-L173),
   `{:unbound_location, location}`), predicator's `store` permits it freely,
   and W3C test304 exists specifically to assert that a script-declared
   variable is readable. ADR-0026 does not address the divergence. If
   `<script>` may create roots and `<assign>` may not, that asymmetry wants
   a stated reason.

3. **How is spec 5.10's system-variable protection enforced for a program?**
   `<assign>` checks the resolved root against a leading `_` before writing
   ([`lib/statifier/machine/content/assign.ex:143-153`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine/content/assign.ex#L143-L153)). A program's writes
   happen inside `Predicator.execute/3` with no hook. The candidates are a
   pre-execution scan of the parsed program's assignment targets, a
   post-execution diff of `context.data` keys against the pre-run datamodel,
   or accepting the gap. A post-execution diff cannot distinguish "the
   script wrote `_event`" from "the script wrote `_event` and then a later
   statement failed", and a pre-execution scan cannot see a computed
   bracket key. This is st-af3.4's open question 5, now with a second
   claimant.

4. **Which layer rejects `<script src>`, and under what reason?** ADR-0026
   says "rejected at load with a named unsupported error". Lowering's
   `Error.unexpected_attribute/3` is the closest existing shape but its
   semantics are "this element takes no such attribute", which is not true
   of `<script>` in the spec. The `Lowering.Error.reason` union
   ([`lib/statifier/lowering/error.ex:21-28`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/lowering/error.ex#L21-L28)) is declared closed, so a new
   named reason is an explicit extension; a validator check is the
   alternative and matches `Checks.Data`'s existing `expr`+`src` conflict
   handling. Also unsettled: whether `<script src>` plus child text is a
   distinct error from `<script src>` alone (spec 5.8.2 forbids both
   together).

5. **Where do the top-level program and its span live on `Document` and
   `Machine`?** Neither struct has a slot, and `Machine`'s moduledoc
   ([`lib/statifier/machine.ex:55-61`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/machine.ex#L55-L61)) states a deliberate reluctance to add
   fields derivable from elsewhere. The options are a new field on each
   (paralleling `datamodel_element`), or routing the top-level script
   through the existing `c_index`-addressed `contents` tuple with the index
   reachable from `states[0]`. The second keeps `Machine` at nine fields but
   puts a non-block node in a structure the block runner indexes.

6. **What does `error.execution`'s `data:` carry?** The expression path
   produces a `Statifier.Evaluator.Error` (`{source, error, span}`);
   `Predicator.execute/3` returns a bare `%EvaluationError{}`,
   `%TypeMismatchError{}`, `%UndefinedVariableError{}`, or `%ParseError{}`.
   Whether the script path wraps to match the expression path's convention
   or passes the struct through is st-af3.4's open question 7, unresolved.

7. **The `nil`/`:undefined` round trip is now unavoidable.**
   `Evaluator.context/1` runs `undefine_nils/1`
   ([`lib/statifier/evaluator.ex:105-133`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/lib/statifier/evaluator.ex#L105-L133)), rewriting every `nil` in the
   datamodel to `:undefined` so that a declared-but-unbound `<data>` keeps
   answering `:undefined` under predicator 7.x. `Predicator.execute/3`
   returns the whole context back, so writing `context.data` into
   `machine_state.datamodel` is the first code path in the engine that
   converts every `nil` in the datamodel to `:undefined` - permanently,
   and for ids the script never touched. Predicator 6.0 also made `nil` the
   null literal's own value, so `:undefined` and `nil` are no longer
   interchangeable downstream. A merge that writes back only the keys the
   program changed, or a re-`nil`ing pass, are the two obvious mitigations;
   neither exists today. This is st-af3.4's open question 2, escalated from
   hypothetical to blocking.

8. **What does `:partial` mean operationally for the detector?** It is a
   notation the registry has never used, and `validate_features/1`
   ([`test/support/feature_detector.ex:121-136`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/test/support/feature_detector.ex#L121-L136)) treats it as `:supported`,
   so flipping `script_elements` to `:partial` admits every `<script>`
   document to the suite. Since `Statifier.Case` flunks rather than skips,
   files whose bodies do not parse become red tests unless they stay
   excluded. The ordering of "flip the detector" against "resolve the
   exclusions" therefore matters, and ADR-0026 decision 4's per-file
   re-recording is what keeps the suite green.

9. **The corpus sources must be fetched before the ceiling can be
   determined.** `tools/corpus/scratch/` is empty in this checkout and the
   SCION suite is cloned, not vendored, so no `<script>` body from the four
   excluded SCION directories can be read today.
   `mise run corpus:fetch` is a prerequisite step for ADR-0026 decision 4,
   not an implementation detail.

10. **The W3C half of the corpus work is unscoped by the bead.**
    [`tools/corpus/scxml_w3/exclusions.exs:16-18`](https://github.com/riddler/statifier-ex/blob/456d28e5d477f11ff162e52a5a6ec8e946235d1e/tools/corpus/scxml_w3/exclusions.exs#L16-L18) (test302-304) and the four
    stubbed `conf:` templates in
    `tools/corpus/scxml_w3/conf_predicator.xsl` rest on the same
    now-false clause as the SCION entries. `conf:script` upstream is
    `<script>var Var1 = 1</script>`; `var` is not predicator, so the local
    stylesheet must emit its own predicator statement form, which is a
    corpus-generation decision (what exactly `conf:script` should mean under
    a predicator datamodel) rather than a mechanical un-stubbing.
