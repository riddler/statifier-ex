# Research: `<assign>` and auto-vivifying deep-path assignment

**Date**: 2026-08-13T09:32:51-0600
**Git Commit**: 6209b76b4c58ba23581e9177ec0e3bdff02b4ccf
**Branch**: st-af3.4-assign-deep-path
**Bead**: st-af3.4

## Research Question

Document the codebase as it stands today for everything st-af3.4 touches: the
end-to-end executable-content element pattern (`<raise>` and `<log>` as the two
exemplars), how the evaluator context is built and threaded through the block
runner and where a datamodel-mutating node's rebuild seam has to go, how
`machine_state.datamodel` is stored and written, the real upstream predicator
assignment API, the spec clauses governing `<assign>`, what the standing docs
and ADRs commit to, the conformance-corpus and ratchet situation, and the
existing test patterns plus the sabotage convention.

## Summary

Everything st-af3.4 needs already exists as a seam that was designed for it, and
in three places the code names the bead by number.

- **The element pattern is closed and mechanical.** The parser is entirely
  element-agnostic; the allowlist is one map in [`lib/statifier/lowering.ex:53-69`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/lowering.ex#L53-L69).
  A new element is: one `@dispatch` entry, one `Builders.build_assign/2`, one
  `Statifier.Document.Assign` struct, one arm on the `Document.content_node`
  union, one clause on `Builders.content_node_name/1`, two aliases plus a
  `build_content_node/2` clause in `lib/statifier/compiler.ex`, one arm on the
  `Machine.Content.t()` union, and one new file
  `lib/statifier/machine/content/assign.ex` holding the struct and its
  `defimpl Statifier.ExecutableContent` together. The protocol, the block
  runner, `Machine.content/2`, and the interpreter need no change at all -
  [`lib/statifier/executable_content.ex:9-12`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/executable_content.ex#L9-L12) and
  [`lib/statifier/machine/content.ex:11-15`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/machine/content.ex#L11-L15) both say so, naming `<assign>`.
- **The rebuild seam is named in the source.**
  [`lib/statifier/interpreter/content.ex:49-52`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/interpreter/content.ex#L49-L52) says in prose: "A node that
  mutates the datamodel (`<assign>`, st-af3.4) will have to rebuild or rebind
  that context before the next node in the same block reads it; this is the seam
  where that has to happen." Today `execute_block/3` builds one
  `Evaluator.context/1` at [`lib/statifier/interpreter/content.ex:105`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/interpreter/content.ex#L105) and threads
  the identical value to every node through
  `ExecutableContent.Context.datamodel_context`.
- **The upstream API is `Predicator.context_assign/4` over plain maps, but
  `Predicator.Context.assign/3` exists too and is the better-shaped fit** - it
  takes and returns the whole `%Predicator.Context{}`, preserving `functions`
  (the `In/1` closure) and `on_unbound: :error` across the write, which
  `context_assign/4` cannot do because it operates on the bare data map.
- **There is a live `nil`/`:undefined` normalization asymmetry on the round
  trip.** `machine_state.datamodel` stores `nil` for a seeded-but-unbound
  `<data>`; `Predicator.Context.new/2` deep-normalizes that `nil` to
  `:undefined`. Nothing in `lib/` reads `context.data` back out today, so
  writing an assigned context's `data` back into `machine_state.datamodel`
  would be the first code path that converts every `nil` in the datamodel into
  `:undefined`. This is an open question, recorded below.
- **Nothing guards system-variable writes at write time.** The only protection
  today is the `Map.merge/2` ordering in `MachineState.new/2`
  ([`lib/statifier/machine_state.ex:257`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/machine_state.ex#L257)), which is construction-time only. Spec
  5.10's "MUST cause any attempt to change the value of a system variable to
  fail" has no implementation and no list of protected names to check against -
  the four names exist only as literal map keys in
  `SystemVariables.initial/2`.
- **82 generated corpus files name `assign_elements`**; exactly 6 of them name
  no other unsupported feature. `conditional_transitions` is the dominant
  co-blocker and is still registered `:unsupported` even though st-af3.2 landed
  `cond` - see the open questions.
- **An existing internal test asserts the pre-af3.4 behavior directly**
  ([`test/statifier/interpreter/content_test.exs:316-341`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/test/statifier/interpreter/content_test.exs#L316-L341)): a later node in the
  same block does *not* see an earlier node's datamodel write, and the two
  recorded contexts are `==`. Its own sabotage note describes per-node rebuild
  in `run_nodes/2` as the sabotage. Whether that test stays green after st-af3.4
  depends entirely on where the rebuild goes.

#### Validator

No file under `lib/statifier/validator/checks/` enumerates executable-content
node kinds - `Raise`, `Log`, and `content_node` return zero matches across the
whole directory and across `lib/statifier/validator/context.ex`. Lowering owns
missing-attribute and misplaced-element errors already. The two files worth
reading as templates if `<assign>` needs a check of its own (for instance the
5.4.2 expr-and-children exclusion) are
`lib/statifier/validator/checks/content.ex` - which already implements exactly
that mutual-exclusion check for `<content>` and reports
`{:content_expr_and_text, expr}` - and `lib/statifier/validator/checks/enums.ex`.

### The evaluator context and the rebuild/rebind seam

`Statifier.Evaluator.context/1` ([`lib/statifier/evaluator.ex:97-103`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/evaluator.ex#L97-L103)):

```elixir
def context(%MachineState{} = machine_state) do
  Predicator.Context.new(machine_state.datamodel,
    functions: %{"In" => {1, in_function(machine_state)}},
    on_unbound: :error
  )
end
```

The returned value is a **position snapshot**: `in_function/1`
([`lib/statifier/evaluator.ex:142-151`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/evaluator.ex#L142-L151)) closes over `machine_state.machine` and
`machine_state.configuration` as they stand at the call.
[`lib/statifier/evaluator.ex:37-72`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/evaluator.ex#L37-L72) records the two independent grounds for not
caching it on `MachineState`: the closure makes it non-resumable
(`docs/observability.md` constraint 1 / ADR-0012), and it would be stale by
construction because the configuration moves every microstep. The plain map on
`MachineState.datamodel` stays the resumable truth.

`Statifier.ExecutableContent.Context`
(`lib/statifier/executable_content/context.ex`) carries three fields -
`machine_state`, `owner`, `datamodel_context` - all three `@enforce_keys`'d. Its
moduledoc records that `datamodel_context` is built once per **block**, not per
macrostep, because `_event` is rewritten every internal-event round and `In/1`
reads a configuration that moves every microstep.

`Statifier.Interpreter.Content.execute_block/3`
([`lib/statifier/interpreter/content.ex:101-123`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/interpreter/content.ex#L101-L123)) builds it once at `:105` and
`run_nodes/2` (`:131-145`) threads the fold's `context` forward untouched in the
`datamodel_context` field. **The seam has exactly two candidate homes:**

1. Inside the `<assign>` node's own `execute/2`, returning
   `%{context | machine_state: ms, datamodel_context: rebuilt}`. The protocol
   already permits this - `execute/2` returns "the (possibly updated) context"
   ([`lib/statifier/executable_content.ex:19-21`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/executable_content.ex#L19-L21)) - and no runner change is
   needed, which is what ADR-0003's "never a change to the runner"
   ([`docs/architecture.md:112-114`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/docs/architecture.md#L112-L114)) requires.
2. Inside `run_nodes/2`, rebuilding per node. [`docs/architecture.md:112-114`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/docs/architecture.md#L112-L114)
   and [`lib/statifier/executable_content.ex:9-12`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/executable_content.ex#L9-L12) both forbid this shape, and
   [`test/statifier/interpreter/content_test.exs:316-322`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/test/statifier/interpreter/content_test.exs#L316-L322)'s sabotage note names
   it as the sabotage.

Option 1 keeps the existing test green as written, because
`Statifier.ContextRecorder` ([`test/support/context_recorder.ex:12-20`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/test/support/context_recorder.ex#L12-L20))
deliberately mutates `machine_state.datamodel` *without* rebuilding
`datamodel_context` - it stands in for a node that does not rebuild, so the
"unaffected by an earlier node's datamodel write" test is asserting the runner's
behavior, not `<assign>`'s.

The cost side is recorded at [`lib/statifier/evaluator.ex:63-72`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/evaluator.ex#L63-L72):
`Predicator.Context.new/2` deep-normalizes the whole datamodel every time, where
`Predicator.Context.bind/3` is O(1) in the data's size and carries `functions`
and `on_unbound` over unchanged. `Predicator.Context.assign/3` has the same

#### The context-to-map round trip

`%Predicator.Context{}` is `defstruct data: %{}, functions: %{}, on_unbound:
:undefined, host: nil` (`deps/predicator/lib/predicator/context.ex:64-71`); the
`data` field **is** the plain map, and there is no `to_map`/unwrap function
because none is needed. `Context.new/2` (`:123-131`) calls `normalize_value/1`
(`:326-337`) on the data:

```elixir
defp normalize_value(nil), do: Undefined.value()
defp normalize_value(list) when is_list(list), do: Enum.map(list, &normalize_value/1)
defp normalize_value(%_struct{} = struct), do: struct
defp normalize_value(map) when is_map(map), do: normalize_map(map)
defp normalize_value(other), do: other
```

`nil` becomes `:undefined` recursively; `normalize_map/1` (`:351-368`) converts
atom keys to string keys. Nothing in `lib/` reads `context.data` back out today -
a grep for `context.data` across `lib/` returns no matches - so any round trip
`<assign>` performs is the first one in the codebase.

Pinned at [`mix.exs:41`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/mix.exs#L41) (`{:predicator, "~> 5.0"}`) and [`mix.lock:19`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/mix.lock#L19)

`Predicator.context_assign/4` (`deps/predicator/lib/predicator.ex:1140-1147`):

```elixir
@spec context_assign(Types.context(), binary(), term(), keyword()) ::
        {:ok, Types.context()} | {:error, struct()}
def context_assign(context, expression, value, opts \\ [])
    when is_map(context) and is_binary(expression) do
  case context_location(expression, context, opts) do
    {:ok, path} -> ContextLocation.put(context, path, value)
    {:error, _error} = error -> error
  end
end
```

`Predicator.Context.assign/3` (`deps/predicator/lib/predicator/context.ex:304-310`):

```elixir
@spec assign(t(), binary() | ContextLocation.location_path(), Types.value()) ::
        {:ok, t()} | {:error, struct()}
def assign(%__MODULE__{data: data} = context, path_or_expression, value) do
  with {:ok, path} <- resolve_path(data, path_or_expression),
       {:ok, new_data} <- ContextLocation.put(data, path, value) do
    {:ok, %{context | data: new_data}}
  end
end
```

Supporting types: `@type location_path :: [binary() | integer()]`
(`deps/predicator/lib/predicator/context_location.ex:73`);
`@type put_result :: {:ok, Types.context()} | {:error, LocationError.t()}` (`:88`);
`@spec put(Types.context(), location_path(), term()) :: put_result()` (`:206`).

**Return shapes.** `context_assign/4` returns `{:ok, plain_map}` (a
`Types.context()`, *not* a `%Context{}`) or `{:error, %LocationError{}}` from
either resolution or the write, or `{:error, %ParseError{}}` when the expression
does not parse. `Context.assign/3` returns `{:ok, %Predicator.Context{}}` with
`data` replaced and `functions`/`on_unbound`/`host` carried over, or the same two
error structs. `ContextLocation.put/3` alone never produces a `ParseError`,
since it takes an already-resolved path.

**Option keys.** There are none. `context_location/3`'s third parameter is
literally named `_opts` (`predicator.ex:1090`) and documented "currently unused,
reserved for future extensions" (`:1031-1032`); `context_assign/4` threads its
`opts` into it unchanged (`:1144`) and documents it "Reserved for future
options" (`:1118`). Nothing reads a key out of either.

**Every `LocationError` type.** The union is declared at
`deps/predicator/lib/predicator/errors/location_error.ex:49-56` and has seven
members:

| type | Condition | Source |
|---|---|---|
| `:not_assignable` | assigning to a literal, string literal, function call, arithmetic, comparison, logical and/or/not, unary, or list-literal AST node | `context_location.ex:250-303` |
| `:not_assignable` | an empty location path | `context_location.ex:209-211` |
| `:invalid_node` | unrecognized AST node (catch-all) | `context_location.ex:307-308` |
| `:undefined_variable` | a bracket key `items[i]` where `i` is unbound | `context_location.ex:336-342` |
| `:invalid_key` | a bracket key variable whose value is neither binary nor integer | `context_location.ex:344-345` |
| `:computed_key` | a bracket key that is itself a computed expression | `context_location.ex:350-355` |
| `:not_a_container` | an interior path segment holds a non-nil, non-`:undefined` scalar | `context_location.ex:395-402` |
| `:not_a_container` | a non-integer (string) key read against an existing list | `context_location.ex:418-419` |
| `:not_a_container` | a non-integer key written into a list at the leaf | `context_location.ex:436-437` |
| `:invalid_index` | a negative integer index read against a list | `context_location.ex:414-415` |
| `:invalid_index` | a negative integer index written against a list | `context_location.ex:432-433` |

Note that an index **past the end** of a list is not an error - it pads. Only a
*negative* index produces `:invalid_index`.

**Vivification rules** (`ContextLocation.put/3`'s private helpers,
`context_location.ex:358-457`):

- A missing / `nil` / `:undefined` segment is created by `vivify/3`
  (`:381-393`): `[]` when the *next* segment is an integer (`:382-385`), `%{}`
  otherwise (`:387-389`). An existing map or list is left alone (`:391-393`).
- A scalar hit mid-path is `:not_a_container` (`:395-402`) - vivification never
  destroys existing data.
- List write past the end (`write_at/4`, `:440-446`):
  `index < size` is `List.replace_at/3`; `index >= size` is
  `list ++ List.duplicate(Undefined.value(), index - size) ++ [value]` -
  padding with `:undefined` sentinels.
- An **integer segment against an existing map is allowed** and writes with the
  integer key (`fetch_in/3` at `:406-408`, `set_in/4` at `:423-425`), with the
  rationale stated at `:169-170`: "refusing would destroy data the caller put
  there."
- The **leaf is always overwritten**, whatever its current type
  (`do_put/4`, `:368-370`); the `:not_a_container` check applies only to
  interior traversal.
- `put/3` "consults string and integer keys, never atom keys" (`:172-180`).

The plan that produced this upstream API records the same six decisions in
prose at [`docs/plans/260803-st2-qjs-predicator-path-assign.md:96-114`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/docs/plans/260803-st2-qjs-predicator-path-assign.md#L96-L114), and
[`docs/plans/260803-st2-qjs-predicator-path-assign.md:130-131`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/docs/plans/260803-st2-qjs-predicator-path-assign.md#L130-L131) explicitly scopes
the statifier-side `<assign>` out of that work: "That is separate work" - it is
this bead.

### The spec clauses

Read from the local cache
(`$(git rev-parse --path-format=absolute --git-common-dir)/spec-cache/scxml-rec.html`),
quoted rather than recalled.

**Spec 5.4 `<assign>`** - the `location` attribute is `required="true"`, typed
"path expression", valid values "Any valid location expression", described as
"The location in the data model into which to insert the new value. See 5.9.2
Location Expressions for details." `expr` is `required="false"` and carries the
constraint "This attribute must not occur in an `<assign>` element that has
children."

5.4.2 Children:

> The children of the `<assign>`element provide an in-line specification of the
> legal data value (see 5.9.3 Legal Data Values and Value Expressions) to be
> inserted into the data model at the specified location.

> A conformant SCXML document MUST specify either "expr" or children of
> `<assign>`, but not both.

> Assignment to a data model is done by using a location expression to denote
> the part of the data model where the insertion is to be made. If the location
> expression does not denote a valid location in the data model or if the value
> specified (by 'expr' or children) is not a legal value for the location
> specified, the SCXML Processor MUST place the error 'error.execution' in the
> internal event queue. Otherwise, the SCXML Processor MUST place the specified
> value at the specified location. Note that the nature of the insertion and the
> definition of a legal value depends on the data model language used.

That last sentence is what licenses the vivification semantics: the nature of
the insertion is the data model language's call, and predicator's is
ECMAScript-like.

**Spec 5.9.2 Location Expressions:**

> Location expressions are used to specify a location in the data model, e.g. as
> part of the `<assign>`, `<param>`, `<send>` or `<invoke>` elements. The exact
> nature of a location depends on the data model. If a location expression
> cannot be evaluated to yield a valid location, the SCXML processor MUST place
> the error 'error.execution' in the internal event queue.

**Spec 5.9.3 Legal Data Values and Value Expressions:**

> If a value expression does not return a legal data value, the SCXML Processor
> MUST place the error 'error.execution' in the internal event queue.

**Spec 5.10 System Variables** - the opening obligation and the closing
prohibition:

> The SCXML Processor MUST maintain a protected portion of the data model
> containing information that can be useful to applications. We refer to the
> items in this special part of the data model as 'system variables'.
> Implementations MUST provide the following system variables, and MAY support
> others.

> The set of system variables may be expanded in future versions of this
> specification. Variable names beginning with '_' are reserved for system use.
> A conformant SCXML document MUST NOT contain ids beginning with '_' in the
> `<data>` element. Platforms MUST place all platform-specific system variables
> under the '_x' root.

> The concrete realization of these variables in a specific data model depends
> on the language used. The Processor MUST cause any attempt to change the value
> of a system variable to fail and MUST place the error 'error.execution' on the
> internal event queue when such an attempt is made.

Note the clause is broader than the bead's four names: it is scoped to "a system
variable", and the paragraph above reserves the whole `_` prefix and names `_x`
as a fifth root the spec requires implementations to place platform variables
under. `_x` is not currently created by
`lib/statifier/evaluator/system_variables.ex`.

**Appendix D** has no `executeContent` procedure body - the five hits at
`appendix-d.txt:173,271,296,315,319` are all call sites - so `<assign>` has no
pseudocode to port, only 5.4's prose. This is the same situation
[`lib/statifier/interpreter/datamodel.ex:6-19`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/interpreter/datamodel.ex#L6-L19) documents for
`initializeDatamodel`.

## Open Questions

No human was available during this research, so these are recorded rather than
resolved. Each is a decision for the planning stage.

1. **`context_assign/4` over a plain map, or `Context.assign/3` over the built
   context?** The bead names `Predicator.context_assign/4`, which takes and
   returns a bare `Types.context()` map. `Predicator.Context.assign/3`
   (`deps/predicator/lib/predicator/context.ex:304-310`) does the same write but
   preserves `functions` (the `In/1` closure) and `on_unbound: :error` across
   it, which is exactly the "rebuild or rebind" the seam needs. Choosing
   `context_assign/4` means rebuilding the whole context afterwards
   (`Predicator.Context.new/2` deep-normalizes the entire datamodel each time,
   per [`lib/statifier/evaluator.ex:63-72`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/evaluator.ex#L63-L72)); choosing `Context.assign/3` means
   the context and `machine_state.datamodel` have to be reconciled explicitly.
   Both are available on the current pin.

2. **The `nil` versus `:undefined` round trip.** `machine_state.datamodel`
   stores `nil` for a seeded-but-unbound `<data>`
   ([`lib/statifier/interpreter/datamodel.ex:146`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/lib/statifier/interpreter/datamodel.ex#L146)), and
   `Predicator.Context.new/2` deep-normalizes `nil` to `:undefined`
   (`deps/predicator/lib/predicator/context.ex:326-337`). Nothing in `lib/`
   reads `context.data` back out today, so if `<assign>` writes the assigned
   context's `data` back into `machine_state.datamodel`, every `nil` in the
   datamodel silently becomes `:undefined` - observable to
   `test/statifier/interpreter/datamodel_test.exs`'s
   `assert ms.datamodel["Var1"] == nil` and to any resumed position under

5. **How far spec 5.10's protection extends.** The bead names four variables
   (`_event`, `_sessionid`, `_name`, `_ioprocessors`). The clause quoted above
   is written against "a system variable" generally, reserves the whole `_`
   prefix for system use, and requires platform variables under an `_x` root
   that `lib/statifier/evaluator/system_variables.ex` does not currently create.
   Whether `<assign location="_x.foo">` or `<assign location="_anything">` is
   also `error.execution`, and whether the check is a prefix test or a
   membership test against a named list, is undecided. There is no list of the
   four names anywhere today - they exist only as literal map keys in
   `SystemVariables.initial/2` - so a membership check would have to create one.
   Related: whether the check tests the *root* segment of the resolved
   `location_path()` or the raw attribute string. Resolving first and testing
   `List.first(path)` handles `_event.name` and `_event['name']` uniformly,
   which a string test would not.

6. **Whether the `location` attribute is compiled at load time or deferred.**
   [`docs/datamodel.md:53-71`](https://github.com/riddler/statifier-ex/blob/6209b76b4c58ba23581e9177ec0e3bdff02b4ccf/docs/datamodel.md#L53-L71) records that this engine rejects
   uncompilable expressions at load time everywhere *except* `<data expr>`,
   which defers, and names the asymmetry as deliberate. A `location` is not an
   `expr` - it is resolved by `context_location/3` at runtime against a live
   context, because a bracket key like `items[index]` reads `index` from the
   pre-assignment datamodel (`deps/predicator/lib/predicator.ex:1103-1105`). So
   `location` cannot be fully resolved at compile time even in principle, but
   whether it is *parse*-checked at compile time (rejecting the document) or
   left entirely to runtime is a choice. `test286`'s
   `location="foo.bar.baz "` - with a trailing space - parses fine and must
   produce a runtime `error.execution`, which argues for deferral.

7. **What `error.execution`'s `data:` carries for a predicator
   `%LocationError{}`.** The three existing raise sites pass either a
   `%Statifier.Evaluator.Error{}` (which wraps a predicator error struct with
   the source string and span) or a bare tuple. A `LocationError` from
   `context_assign/4` is neither - it arrives without a `source` or `span`
   wrapper. Whether it is wrapped in an `Evaluator.Error` for uniformity,
   passed bare, or given a new struct is undecided.
