# Research: Defines the typed Document structs (st-l5k.2)

**Date**: 2026-08-07T16:26:18-0600
**Git Commit**: d9c9b38b9c1748a5a48c0426a1fb3176b04683a1
**Branch**: st-l5k.2-typed-document-structs
**Beads Issue**: st-l5k.2

## Research Question

From the bead: typed structs for the Document layer - the parse target that
lowering (st-l5k.4) produces and that both the validator (st-l5k.5) and the
Machine compiler (st-wju.1) consume. Scope is the Phase 1 core element set
(`scxml`, `state`, `parallel`, `final`, `initial` element form, `history`,
`transition`, `onentry`, `onexit`, `raise`, `log`, and `donedata` with static
content). Locations on every node, expressions as raw source strings, list
attributes typed as lists, and a kind representation that compiles down to
cheap Appendix D predicates.

The bead's design notes name one trade-off and decline to settle it: a single
`State` struct carrying a `kind` atom, versus per-kind structs
(`Statifier.Document.State` / `Parallel` / `Final` / `History`). This document
gathers the evidence on both sides. It does not decide.

## Summary

**The repo already has half the answer written down.** The parser layer that
landed under st-l5k.3 fixes the location type, the struct discipline, and the
moduledoc register that these structs will be read against. `Location` is a
six-field exclusive-end span with both line/column and byte offsets, one shared
struct, `@enforce_keys` on all of it. `DOM.Element`, `DOM.Text`, and
`DOM.Attribute` are the pattern: `@enforce_keys`, `defstruct`, a `@type t` with
every field spelled out, no behavior in the struct module, and a moduledoc that
argues for the shape rather than restating the field names.

**The Document layer's job is fixed by `docs/architecture.md`'s layer diagram
and nothing in this bead may widen it.** `Document (typed structs, source
locations, uncompiled expressions)` is the whole contract. Interning, indexing,
and expression compilation are the Compiler's, per ADR-0005 and ADR-0014.
`cond`, `log`'s `expr`, and every other expression field is a raw
`String.t()`; the `{:static, term()} | {:compiled, instructions, source}` sum
type is a Machine `@type` and must not appear here.

**The "cheap Appendix D predicates" criterion turns out to be nearly neutral
between the two candidates.** The predicates do not run on Document structs.
ADR-0005 flattens states into an integer-indexed array with parent pointers and
descendant ranges at Machine-build time, and st-wju.1's design already gives
every compiled state its own `kind` field. Whatever the Document layer does,
the compiler stamps a compiled discriminator, and every predicate becomes an
atom match or an integer comparison there. The Document-layer choice is
therefore about lowering ergonomics, validator expressiveness, and `@type`
honesty - not about runtime cost.

**Where the evidence does bite is the validator.** Several of st-l5k.5's
required checks exist precisely to *report* documents that per-kind structs
would make unrepresentable: `donedata` on a non-final state (check 8), state
children under `<final>` (check 6), both an `initial` attribute and an
`<initial>` element on the same state (check 4). Making those unrepresentable
does not delete the error - it relocates the rejection into lowering, which
st-l5k.4's own design note forbids ("lowering staying dumb about semantics
keeps the layer boundary clean"), and it deletes validator checks whose
acceptance criteria demand a stable error code and a red fixture apiece. That
is the single strongest piece of evidence in the file, and it points at the
single struct.

**v1 chose the single struct and its documented pain lies elsewhere.** v1's
`Statifier.State` has one `type` field over six atoms, branched on at roughly
25-30 sites, and no comment anywhere in v1 calls that field awkward. The
2108-line parser and the 73-to-79-clause `state_stack.ex` that this rewrite
exists to kill were caused by lowering inside the SAX handler, one clause per
(element x parent context) pair - a defect that st-l5k.3 has already fixed and
that neither candidate representation reintroduces.

## Detailed Findings

### 1. The existing parser layer in this repo

Six modules under `lib/statifier/parser/`, all landed by st-l5k.3 on this
branch's ancestry. They are the local convention these structs must match.

**Struct discipline.** Every struct module in the layer is data only, with no
functions except where a constructor or accessor is genuinely shared:

- `lib/statifier/parser/dom/element.ex:28-38` - `@enforce_keys [:name,
  :attributes, :children, :location]`, `defstruct` with the same list, a
  `@type child :: t() | Text.t()` alias for the heterogeneous child list, and a
  `@type t` naming every field's type. No functions in the module at all.
- `lib/statifier/parser/dom/text.ex:21-27` - same shape, two fields.
- `lib/statifier/parser/dom/attribute.ex:23-31` - `@enforce_keys [:name,
  :value]` only; `location` and `value_location` are typed
  `Location.t() | nil`, so a caller can build an attribute without spans.
- `lib/statifier/parser/markup.ex:32-45` - `@enforce_keys [:kind, :name,
  :location]`, `defstruct kind: nil, name: nil, location: nil, attributes: []`
  (keyword form, because `attributes` has a default), and
  `@type t :: %__MODULE__{kind: :start | :end, ...}`.

`Markup` is worth naming twice: **it is an in-repo precedent for the single
struct with a `kind` atom**, chosen over `Markup.Start` / `Markup.End`, for a
discriminated union whose two arms carry identical fields.

**How Location is carried.** One shared struct,
`lib/statifier/parser/location.ex:13-37`, six enforced fields:

```elixir
%Statifier.Parser.Location{
  start_line: pos_integer(), start_column: pos_integer(),
  start_offset: non_neg_integer(),
  end_line: pos_integer(), end_column: pos_integer(),
  end_offset: non_neg_integer()
}
```

1-based line/column with columns counted in Unicode codepoints, 0-based byte
offsets, exclusive end. The moduledoc states why both pairs exist: ADR-0014's
attribute-relative expression spans become document positions by plain
arithmetic, `value_location.start_offset + span.start`. Two helpers live on the
module - `at_offset/2` (a zero-width span, used by `ParseError`) and `slice/2`
(the primitive the location-accuracy sweep is built on). Nothing else.

The field is always named `location`, never `source_location` or `span`.
Non-nilable on `Element` and `Text`; nilable on `Attribute` and `ParseError`,
in each case with the moduledoc saying when nil occurs.

**Attribute-level locations.** `DOM.Attribute` carries **two** spans, per
`docs/plans/260807-st-l5k.3-sax-dom-source-locations.md` Decision 3:
`location` covers the whole `name="value"` text including quotes, and
`value_location` covers only the text inside the quotes. The documented
limitation is that `value` is Saxy's entity-expanded text while
`value_location` covers raw source, so offsets *inside* a value containing a
reference do not map 1:1 (`lib/statifier/parser/dom/attribute.ex:14-18`).
Attributes are an ordered **list** with duplicates preserved, not a map,
because a map is lossy in exactly the case the parser exists to report.

**@type / @spec style.** `@type t :: %__MODULE__{...}` per struct module, every
field named. Nested types get their own alias rather than being inlined
(`@type child`, `@type reason`, `@type attribute`, `@type cursor`,
`@type frame` in `handler.ex:39-53`). Public functions all carry `@spec` with
**named arguments**: `@spec parse(source :: binary()) :: {:ok, DOM.Element.t()}
| {:error, ParseError.t()}` (`lib/statifier/parser.ex:74`), `@spec
slice(location :: t(), source :: binary()) :: binary()`
(`lib/statifier/parser/location.ex:68`). Guards on every public entry point
(`when is_binary(source)`).

**Moduledoc style.** One-sentence opener naming what the thing is, then prose
that argues. Three habits are consistent and load-bearing:

1. **They state what the module deliberately does not do**, with the reason
   (`parser.ex:10-30` "What it does not do"; `dom.ex:10-13` "The tree is
   deliberately unvalidated").
2. **They cite the decision record inline** - `docs/architecture.md`,
   `docs/plans/260807-st-l5k.3-sax-dom-source-locations.md, Decision 1`,
   ADR-0014, and file:line into `deps/saxy` and `../statifier`.
3. **They name v1's failure mode where it explains the shape**
   (`handler.ex:6-11`, `element.ex:6-9`).

Bullet lists describe fields only when a field has a rule a reader would
otherwise get wrong; there is no field-by-field restatement of the `@type`.

**Typography.** Zero em dashes, en dashes, or other non-keyboard characters in
any file under `lib/statifier/parser/`, in `docs/research/`, or in
`docs/plans/`. Spaced hyphens do the work an em dash would. Arrows are `->`.
This document follows the same house style.

**Test conventions.** `test/statifier/parser/dom_test.exs` is the model:
`use ExUnit.Case, async: true`, a local `parse!/1` helper, `describe` blocks per
function, XML in triple-quoted heredocs at 4-space base indentation, assertions
by pattern match rather than a pile of `assert ==`, and a
`# sabotage: <mutation> -> red` comment above every test. st-l5k.2's fixtures
are built literally rather than parsed, since there is no parser path into
these structs until st-l5k.4.

### 2. The v1 reference implementation

All paths under `/Users/johnnyt/repos/github/statifier` (read-only).

**The Document/State/Transition layer.**

`Statifier.Document` (`lib/statifier/document.ex:6-55`) carries `name`,
`datamodel`, `version`, `xmlns`, `binding` (all `String.t() | nil`),
`initial: [String.t()]`, `states: [State.t()]`, `datamodel_elements`, and then
four fields that in v2 belong to the Machine: `state_lookup`,
`transitions_by_source`, `hierarchy_cache`, and a `validated: boolean()` flag.
That `validated` boolean is precisely the "validate if not already validated"
fallback that `docs/architecture.md` principle 4 exists to make
unrepresentable.

`Statifier.State` (`lib/statifier/state.ex:6-49`):

```elixir
@type state_type :: :atomic | :compound | :parallel | :history | :initial | :final
@type history_type :: :shallow | :deep

defstruct [:id, :initial, type: :atomic, states: [], transitions: [],
           onentry_actions: [], onexit_actions: [], history_type: nil,
           parent: nil, depth: 0, document_order: nil,
           source_location: nil, id_location: nil, initial_location: nil,
           history_type_location: nil]
```

`Statifier.Transition` (`lib/statifier/transition.ex:6-40`) carries `event:
String.t() | nil` (unsplit), `targets: [String.t()]` (split), `cond`,
`compiled_cond: term() | nil`, `type: String.t() | nil` (the raw string
`"internal"`/`"external"`, compared at `lib/statifier/interpreter.ex:403` as
`t.type == "internal"`), `actions: [term()]`, and `source: String.t() | nil`.

**The kind representation v1 chose: a single struct with one `type` atom over
six values.** There are no per-kind structs anywhere in v1. `<initial>` is a
`State{type: :initial}` with a synthesized id `"__initial_#{n}__"`
(`lib/statifier/parser/scxml/element_builder.ex:156-175`, `522-525`);
`<history>` is a `State{type: :history, history_type: :shallow | :deep}`
(`element_builder.ex:183-216`); `<final>` is a `State{type: :final}`
(`element_builder.ex:125-148`).

Roughly 25-30 sites branch on it, spread across seven areas:

- `lib/statifier/interpreter.ex:263-322` - `enter_state/2` has six head
  clauses matching `type:` (`:atomic`, `:final`, `:initial`, `:compound`,
  `:parallel`, `:history`), plus `:initial` filters at `343`, `351`, `354`,
  `360-361`, `368`.
- `lib/statifier/state_hierarchy.ex:247-294` - `%{type: :compound}` in LCCA
  (`253`, `263`) and `%{type: :parallel}` in region logic (`277`, `288`).
- `lib/statifier/document.ex:96`, `112`, `125-137` - `is_history_state?/2`,
  `find_history_states/2`, `get_history_default_targets/2`.
- `lib/statifier/hierarchy_cache.ex:230` -
  `Enum.filter(&(&1.type == :parallel))` at cache-build time.
- `lib/statifier/validator/initial_state_validator.ex:133,168` and
  `history_state_validator.ex:23,102,161`.
- `lib/statifier/interpreter/transition_resolver.ex:196`.
- `lib/statifier/parser/scxml/state_stack.ex:194-207` and
  `element_builder.ex:83,110,138,164,205`.

**Two things v1's `type` field does that are notable.** First, its atom set is
*wider than the element set*: `:atomic` and `:compound` are not XML element
names, they are the parse-time resolution of `<state>`. `update_state_type/1`
(`state_stack.ex:194-207`) mutates a state from `:atomic` to `:compound` as
children attach, with `:parallel` and `:final` guarded ahead of the children
test so a childless `<parallel>` does not become `:atomic`. That widening is
what makes v1's `isCompoundState` a pure atom match. Second, the widening is
also a *divergence* from the spec: the spec's "atomic state" includes
`<final>`, v1's `:atomic` does not, so every place the spec writes one
`isAtomicState` becomes two arms in v1 - and one place forgets the second arm
(`lib/statifier/history_tracker.ex:163-170`, `collect_atomic_descendants/1`
matches only `type: :atomic` and falls through a `:final` state into its empty
children list).

**Locations in v1.** Two competing shapes, chosen per target struct
(`element_builder.ex`), and no `Location` struct at all - locations are plain
maps `%{line: integer | nil, column: integer | nil}`:

1. **Flat fields** on `Document`, `State`, `Transition`, `Data`: a
   `source_location` plus one `<attr>_location` field per attribute. `Document`
   has five (`element_builder.ex:56-61`), `Transition` three
   (`element_builder.ex:253-257`).
2. **A nested map** on the action structs: one `source_location` whose
   `:source` key holds the element's own position and whose other keys hold
   per-attribute positions. `LogAction`'s is `%{source: _, label: _, expr: _}`
   (`element_builder.ex:301-305`); `SendAction`'s has twelve keys
   (`element_builder.ex:372-385`).

`Document`'s own `@type t` omits `binding_location` even though the
`defstruct` has it (`document.ex:30` vs the type block) - a field the type spec
silently does not describe, which is what happens when there are eleven
location fields to keep in step by hand.

The locations themselves are produced by re-scanning the raw XML per element
(`lib/statifier/parser/scxml/location_tracker.ex:47-67`), which the st-l5k.3
research already documented as wrong in three ways and O(n^2); v2 replaced the
mechanism outright. What matters for *this* bead is only the storage shape:
two shapes, plain maps, columns frequently `nil` (attribute lookups never
compute one, `location_tracker.ex:91`).

**Expressions in v1.** Raw strings on the struct, plus a parallel
`compiled_*` field per expression, initialized to `nil` and filled by a
separate validation-phase pass: `Transition.compiled_cond`
(`transition.ex:9,31`), `AssignAction.compiled_expr`
(`assign_action.ex:35,40`), `ForeachAction.compiled_array`
(`foreach_action.ex:52,59`), and four on `SendAction`
(`send_action.ex:39-76`). `Statifier.Validator.ExpressionCompiler.compile_document/1`
(`lib/statifier/validator/expression_compiler.ex:38-45`) walks the tree
rewriting them. Two consequences the rewrite reacted to: the compiled fields
are typed `term()`, so the document structs are coupled to whatever opaque
value `Predicator.compile/1` returns with no boundary; and because
`IfAction.execute/2` (`if_action.ex:122-140`) and `SendAction`
(`send_action.ex:387-396`) fall back to compiling at runtime when the field is
still `nil`, compilation-at-validation is an optimization rather than an
invariant. `docs/architecture.md:80-82` names this directly: "v1 carried
`x` / `x_expr` / `compiled_x_expr` triples on every action struct."

**List attributes in v1.** Split once, at parse time, for `target`
(`element_builder.ex:235-243`, `String.split(target_string, ~r/\s+/, trim:
true)`) and for the `initial` attribute (`element_builder.ex:531-539`, used by
both `build_document/4` and `build_state/4`). **Not split for `event`**:
`Transition.event` stays a single raw string and is re-split on **every match
attempt** inside `Statifier.Event.matches?/2`
(`lib/statifier/event.ex:64-79`) - `String.split(event_spec, " ")` for the
alternatives, then `String.split(_, ".")` per descriptor for the prefix walk.
`SendAction.namelist` has the same shape (`send_action.ex:373-375`). This is
exactly the re-splitting the bead's rule about list-typed attributes exists to
prevent, and st-wju.1's design already commits to pre-split descriptor token
lists at compile time.

**What v1 does not have at all.** No `donedata` support anywhere in `lib/`
(repo-wide grep finds it only in `CHANGELOG.md` and planning docs); no
`isInFinalState`; no `done.state.<id>` generation. So v1 offers no reference
shape for `Donedata`, and its `<final>` handling is a single clause treating
final as atomic (`interpreter.ex:268-271`).

**What v1's own docs call awkward.** Nothing in v1's source criticizes the
`type` field. The named pain is the parser: 2108 lines across five modules,
with `state_stack.ex` at 903 lines and 73-79 clauses depending on the counting
method (`docs/research/260807-st-l5k.3-sax-dom-source-locations.md:69-73`,
`299-300`; `lib/statifier/parser/handler.ex:6-11`). The cause is stated
precisely there: `StateStack` has no generic "append this finished child to
whatever container is on top of the stack" operation, so each executable
content element enumerates every legal parent context - `handle_log_end/1`
alone has eight head clauses (`state_stack.ex:257-317`), repeated near-verbatim
for `handle_raise_end`, `handle_assign_end`, `handle_send_end`,
`handle_foreach_end`, and `handle_invoke_end`. **That defect is a property of
lowering inside the SAX handler, not of the state-kind representation**, and
st-l5k.3 has already fixed it: `:end_element` is one clause.

### 3. The Appendix D predicates

Appendix D is *informative* and gives no pseudocode bodies for these
predicates. Only two are defined at all, in the "Preliminary definitions"
prose:

> **atomic state** - A state of type `<state>` with no child states, or a state
> of type `<final>`.
>
> **compound state** - A state of type `<state>` with at least one child state.

`isParallelState`, `isHistoryState`, `isFinalState`, and
`isCompoundStateOrScxmlElement` are never defined; they are used as bare
element-type tests. `getChildStates(state1)` is defined as "a list containing
all `<state>`, `<final>`, and `<parallel>` children" - i.e. **excluding** the
`<initial>` and `<history>` pseudo-states.

**What each predicate needs to be cheap:**

| Predicate | Kind test | Children test | Requirement |
|---|---|---|---|
| `isAtomicState` | yes | yes | `(kind == state AND children empty) OR kind == final`. The kind test cannot be skipped: a childless `<parallel>` is never atomic. |
| `isCompoundState` | yes | yes | `kind == state AND children non-empty`. `<parallel>` is explicitly **not** compound under the spec's definition. |
| `isParallelState` | yes | no | Pure kind test. |
| `isHistoryState` | yes | no | Pure kind test. |
| `isFinalState` | yes | no | Pure kind test. |
| `isCompoundStateOrScxmlElement` | yes | partly | `isCompoundState(s) OR kind == scxml`. |
| `isDescendant` | no | no | Not a kind test at all; an ancestry relation, cheap only with a precomputed descendant set or an index range. |
| `isInFinalState` | yes | yes + configuration | Composite: kind, the child list itself, and configuration membership. |

Two consequences isolate cleanly. **Only `isAtomicState` and `isCompoundState`
need anything beyond a discriminator, and what they need is emptiness of the
real-state child list, not its contents.** And if the discriminator is widened
at build time to distinguish atomic from compound, all five headline predicates
collapse to pure kind tests and the children list is never consulted at
runtime - which is exactly what v1 does at parse time, and what st-wju.1 is
positioned to do at compile time.

**Call frequency in the pseudocode** (static sites, then dynamic weight):

- `isDescendant` - 7 sites, hottest by a wide margin. `computeExitSet` calls it
  once per configuration member per transition, and
  `removeConflictingTransitions` calls `computeExitSet` O(n^2) times over the
  enabled set.
- `isAtomicState` - 3 sites, but two of them filter the *entire configuration*
  (`selectTransitions`, `selectEventlessTransitions`) once per microstep.
- `isParallelState` - 4 sites, once per state in `addDescendantStatesToEnter`
  and once per ancestor in `addAncestorStatesToEnter`, both recursive and
  per-transition.
- `isCompoundState` - 3 sites: the main recursion branch of
  `addDescendantStatesToEnter`, `getTransitionDomain` (itself called from both
  `computeExitSet` and `computeEntrySet`), and each `isInFinalState` frame.
- `isHistoryState` - 2 sites, but `getEffectiveTargetStates` is itself
  recursive through history default transitions.
- `isFinalState` - 3 sites, moderate.

**How v1 makes the checks.** Every one is an atom pattern-match on `State.type`
after an O(1) `state_lookup` hit; there is no runtime children-emptiness test
anywhere in v1. `isAtomicState` is eliminated entirely, because v1's
`Configuration` stores only leaf states
(`lib/statifier/configuration.ex:2-32`), making the spec's
`configuration.filter(isAtomicState)` a no-op - the exact storage decision
ADR-0005 reverses for v2. `isDescendant` is a `MapSet.member?` against a
precomputed `descendant_sets` map with an O(depth) parent-pointer fallback
(`lib/statifier/state_hierarchy.ex:25-49`,
`lib/statifier/hierarchy_cache.ex:40,53,178-195`) - the 376-line cache module
ADR-0005 replaces with index ranges.

**The decisive framing for this bead**: none of these predicates runs against a
Document struct. ADR-0005's decision is explicit that "the Machine compiler
interns state IDs to integers and lays states out in a flat array in document
order with parent pointers and descendant index ranges", and that "string IDs
appear only at the API boundary (parsing in, event/introspection out)".
st-wju.1's design already gives each compiled state an `index`, a `kind`, a
`parent`, and a `range`. The Document layer's representation is an *input* to
that pass. It has to be walkable and unambiguous; it does not have to be fast.

### 4. Downstream consumers

**st-l5k.4 (Lowers the DOM to Document structs)** - blocked on st-l5k.3,
sibling to this bead. What it expects:

- One builder per element, dispatched through a name-to-builder map, each
  taking `(dom_element, context)` and returning `{:ok, struct} | {:error,
  error}`. "Adding an element touches one builder, not a clause matrix - this
  is the structural fix for v1's 73-clause handler."
- **Tokenization happens there**: transition `target` and `event` are
  whitespace-split into lists; `type`, `binding`, and history `type` become
  atoms with defaults applied (`:external`, `:early`, `:shallow`). "Missing
  optional attributes become nil or `[]`, never empty-string sentinels."
- Unsupported elements (`datamodel`, `data`, `assign`, `script`, `send`,
  `cancel`, `invoke`, `if`/`elseif`/`else`, `foreach`, `param`) produce
  `{:error, unsupported}` naming the element and its location.
- "Locations are copied from DOM nodes onto every produced struct, **including
  attribute locations where the DOM has them**."
- Explicitly: "Conflicting forms (state with both initial attribute and initial
  element) are built as-is here - that is a validator check (st-l5k.5), and
  lowering staying dumb about semantics keeps the layer boundary clean."

**st-l5k.5 (Validates the Document)** - the eight checks, each with a stable
error code, a message, and "the source location of the offending node or
attribute (this is why attribute locations survive lowering)". All errors
collected in one pass. Reading them against a struct design:

1. State ids unique across the document - needs a **generic walk over every
   state of every kind**.
2. Every transition target resolves to a state id - needs a
   kind-independent id index.
3. Initial attribute / initial element targets resolve and are descendants -
   needs both forms present on the same state to compare.
4. **A state has at most one of initial attribute and initial element**, and an
   initial element contains exactly one transition, which has a target and
   carries no event and no cond.
5. `history` is a child of a compound state or parallel (not of scxml, final,
   or another history); default transition target is a descendant of the
   history state's parent; type is shallow or deep.
6. **`final` has no state children** - only onentry, onexit, donedata.
7. Compound-state initial fallback (first child in document order) is legal -
   the check is that the first child exists and is enterable.
8. **`donedata` appears only on final states.**

Checks 4, 6, and 8 are the ones that bear directly on the representation: each
is a report about a document whose shape is wrong, which means the Document
type must be able to *hold* that wrong shape long enough for the validator to
name it. The bead also states the layer boundary from the other side: the
validator builds a throwaway id-to-path index and explicitly must not share it
with the compiler.

**st-wju.1 (Compiles the Document to an interned Machine)** - what it reads out
of these structs:

- A per-state `kind` (its own suggested compiled-state field list is `index,
  id, kind, parent, range, children, initial, transitions, onentry, onexit,
  history children, history_type, donedata, location`), so the Document must
  supply enough to derive it. Its open decision "whether scxml root is state
  index 0 (recommended: yes, kind `:scxml`)" implies a `:scxml` discriminator
  may want to exist one layer up too.
- `initial` resolved to indexes at compile time "from attribute, element, or
  first-child default, so the interpreter never re-derives it" - so the
  Document must preserve *which* of the three forms was used, and the attribute
  and element forms must be separately readable.
- History children as indexes "so exit-time recording finds them without
  scanning" - the compiler needs to find history children of a state, which
  means history states must be reachable through the ordinary child list rather
  than hidden in a separate field, or else placed in a field the compiler knows
  to look at.
- Pre-split event descriptor token lists: "matching in st-wju.3 walks tokens,
  no string splitting at runtime". The Document's list-of-descriptor-strings is
  the input to that second-level split.
- `cond` as raw source: "a cond that fails to compile is a compile-time error
  of this pass (with the expression source, its location, and predicator's
  position in the message)" - so the Document must carry the cond's **source
  location**, not merely its string, or the compiler cannot produce that
  message. ADR-0014 makes this an attribute *value* location, since the
  expression span is relative to the expression string.
- Locations retained on every compiled state, transition, and executable
  content node, plus dense document-order `t_index` / `c_index` assigned **by
  the compiler**, since "SCXML transitions and executable content have no IDs".
  The Document does not need to carry document-order integers for that purpose;
  list order is the input.

### 5. Constraints from the repo's docs and ADRs

**`docs/architecture.md`** fixes the layer diagram, and the Document line is
the whole contract for this bead:

```
DOM (element name, attrs, children, location)
   |  Lowering (typed per-element builders)
   v
Document (typed structs, source locations, uncompiled expressions)
   |  Validator (structural + semantic checks)
   |  Compiler (intern IDs, index hierarchy, compile expressions)
   v
Machine (valid by construction, integer state indexes, compiled Expr values)
```

Design principle 4 is the one usually cited *for* per-kind structs, and its
actual wording scopes validity to the Machine, not the Document: "Parsing
produces a `Document`; validation produces a distinct `Machine` type (interned,
optimized, guaranteed valid). The interpreter only accepts a `Machine`, so
'validate if not already validated' fallback branches do not exist." The
Document is explicitly the *pre*-validation type.

**`docs/datamodel.md`** - the "no predicator in this layer" rule is stated as
a timing rule in the Evaluation contract: "Expressions are compiled once at
Machine-build time into `{:compiled, instructions, source}`; static attribute
values are `{:static, value}`. One evaluator function handles both." Combined
with architecture.md's "uncompiled expressions", this settles that `cond`,
`log`'s `expr`, and every other expression field on these structs is a raw
`String.t()`, and that the `expr` sum type is a Machine `@type` (declared at
`docs/architecture.md:78`), not a Document one. No `Predicator` alias belongs
in `lib/statifier/document/`.

**`docs/observability.md` Constraint 3** - "The Document layer carries source
locations and compiled expressions keep their source string. The place this is
lost by default is the compiler pass, because the runtime does not need
locations. Keep them anyway: states, transitions, and executable-content nodes
on the Machine retain their source location." Constraint 3 states the Document
layer's location-carrying as a *premise*: the compiler can only retain what
lowering produced, and lowering can only produce what these structs have a
field for. ADR-0012 makes it binding and its consequences name "a change that
drops locations in the compiler" as a violation. Constraint 4 adds that
internally raised events carry cause metadata naming "which transition or
executable-content node (by constraint-3 identity) raised them", and the
identity in question is the compiler-assigned index, not a Document field.

**ADR-0005** (accepted) - the flat array, parent pointers, descendant index
ranges, integer/range comparisons, configurations as `MapSet`s of integers,
"string IDs appear only at the API boundary". This is the ADR that removes
runtime cost from the Document-layer representation question entirely.

**ADR-0002** (accepted) - the literal Appendix D port keeps spec function names
in snake_case and treats deviations as semantic bugs unless an inline comment
cites a mechanical reason. It governs the interpreter, so it does not constrain
these structs directly, but it is the reason the predicate names in section 3
matter at all: `is_compound_state/1` and friends will exist by those names, on
the Machine.

**ADR-0003** (accepted) - pure core, effects as data. `Raise` and `Log` compile
down to effect-producing nodes, but that is a Machine and interpreter contract;
it puts no field on the Document structs.

**ADR-0014** (accepted) - exclusive-end spans, the span table travelling with
the compiled instructions. Its bearing here is twofold: it is why `Location`
has byte offsets at all, and it is why an expression's **attribute-value**
location (`value_location`, not `location`) is the span the Document must carry
forward for `cond` and `expr`. `value_location.start_offset + span.start` is
the arithmetic that turns a predicator span into a document position; without
the value span on the Document node, ADR-0014's diagnostics cannot be built.

**`docs/testing.md`** - every new test asserting `lib/` behavior gets a
`# sabotage: <what was broken> -> red` line above the `test` line, above any
`@tag`. Valid mutations are the mistakes a reasonable person could make: invert
a condition, drop a clause, off-by-one a boundary. Deleting a function body is
not sabotage. The document is silent on struct fixtures specifically; the bead
supplies the rule ("struct tests build fixtures literally"). Note the tension
worth flagging to the plan stage: a pure struct-definition bead has little
`lib/` behavior to break, so the honest sabotage story for `@enforce_keys` and
`@type` may be closer to the stated-exemption form
(`# sabotage: n/a - ...`) than to a mutation, unless the structs carry
constructor or predicate functions.

**ADRs 0001, 0004, 0006-0011, 0013, 0015** were scanned and none touches parser
structs, typing discipline, or state representation. ADR-0004 confirms
expressions are always predicator source strings, never JS or Elixir.

### 6. What st-l5k.3 already decided that constrains this bead

The sibling research (`docs/research/260807-st-l5k.3-sax-dom-source-locations.md`)
and plan (`docs/plans/260807-st-l5k.3-sax-dom-source-locations.md`) are already
implemented on this branch's ancestry, so their decisions are facts, not
proposals.

1. **Decision 2 fixes the location type.** `Statifier.Parser.Location`, a
   six-field exclusive-end span, 1-based line/column, 0-based byte offsets. The
   plan argues the point explicitly: the bead's own design note had proposed a
   bare `{line, column}` point, and "a span is a superset of that point, not a
   departure from it". st-l5k.2's design note proposes the same bare point.
   **The same reconciliation applies here: `Location` is settled, and this bead
   reuses it rather than defining a Document-layer location type.** Two
   location shapes meeting at a layer boundary is the outcome that decision was
   made to avoid.

2. **Decision 3 fixes the attribute-location story at the DOM.** Two spans per
   attribute, `location` and `value_location`, with `value_location` existing
   specifically for ADR-0014. This is what st-l5k.4 will have available to copy
   onto Document nodes, and it is the upper bound on what the Document can
   carry. It also settles the *shape* argument the Document layer will face
   next: a map keyed by attribute name is lossy in exactly the duplicate-attribute
   case the layer exists to report, and a parallel location map is the
   "bolted-on bookkeeping" shape architecture.md names as the thing to avoid.

3. **The parser deliberately preserves whitespace-only text and unknown
   names.** `DOM.elements/1` is the filter. st-l5k.4's design already states
   the consequence: whitespace-only children are ignored during lowering
   *except inside donedata content, where text is the payload*.

4. **v1's relaxed-input normalization is dropped** (plan, Residual Note 1). If
   a document omitting `xmlns` or `version` has to be accepted, that leniency
   belongs to lowering or the validator, not the parser - so `Document`'s
   `version` and `xmlns` fields will see whatever the source actually said,
   including `nil`.

5. **Comment nodes are not in the DOM** (Residual Note 2), so no Document node
   can carry a doc-comment field sourced from XML comments.

6. **Attribute values are entity-expanded while their spans cover raw source**
   (Residual Note 3). Any Document field that stores an expression string plus
   the span it came from inherits this caveat verbatim.

### 7. The scope element set, per the W3C spec

Sections and anchors from https://www.w3.org/TR/scxml/. Phase 1 needs the
attributes and children marked in bold; the rest are listed so the plan stage
knows what it is deferring rather than missing.

**`<scxml>`** ([3.2](https://www.w3.org/TR/scxml/#scxml)) - **`initial`**
(IDREFS, optional; "if not specified, the default initial state is the first
child state in document order"), **`name`** (NMTOKEN, informational),
`xmlns` (required, must be `http://www.w3.org/2005/07/scxml`), **`version`**
(required, must be `"1.0"`), **`datamodel`** (NMTOKEN), **`binding`**
(`early` | `late`, **default `early`**). Children: one or more of `<state>`,
`<parallel>`, `<final>`; plus `<datamodel>` (0-1) and `<script>` (0-1), both
Phase 3.

**`<state>`** ([3.3](https://www.w3.org/TR/scxml/#state)) - **`id`** (ID,
optional), **`initial`** (IDREFS, optional; "**MUST NOT** be specified in
conjunction with the `<initial>` element. MUST NOT occur in atomic states").
Children: `<onentry>`*, `<onexit>`*, `<transition>`*, `<initial>` (0-1),
`<state>`*, `<parallel>`*, `<final>`*, `<history>`*, plus `<datamodel>` and
`<invoke>` (Phase 3).

**`<parallel>`** ([3.4](https://www.w3.org/TR/scxml/#parallel)) - **`id`**
only. Children: `<onentry>`*, `<onexit>`*, **`<transition>`*** (parallel states
do take outgoing transitions), `<state>`*, `<parallel>`*, **`<history>`***,
plus `<datamodel>` / `<invoke>`. Note: `<parallel>` may **not** have `<final>`
children.

**`<final>`** ([3.7](https://www.w3.org/TR/scxml/#final)) - **`id`** only.
Children: **`<onentry>`***, **`<onexit>`***, **`<donedata>`** (0-1). No state
children, and no `<transition>`. Semantics that reach the compiler: entering a
`<final>` child of a `<state>` generates `done.state.<id>` after the `<onentry>`
elements complete, with the `<donedata>` result in `_event.data`.

**`<initial>`** ([3.6](https://www.w3.org/TR/scxml/#initial)) - **no
attributes at all.** Exactly one child, a `<transition>` whose `target`
specifies the default initial state(s); that transition "MUST NOT contain
'cond' or 'event' attributes, and MUST specify a non-null 'target'", and it
"MAY contain executable content". Restricted to compound states, mutually
exclusive with the `initial` attribute. **The absence of an `id` attribute is
the structural fact that bears on the struct design** - v1 synthesized
`"__initial_#{n}__"` to fit it into an id-bearing `State`.

**`<history>`** ([3.10](https://www.w3.org/TR/scxml/#history)) - **`id`** (ID,
optional), **`type`** (`shallow` | `deep`, **default `shallow`**). Exactly one
child, a `<transition>` giving the default history configuration, under the same
"no cond, no event, non-null target" constraint, and it too "MAY contain
executable content".

**`<transition>`** ([3.5](https://www.w3.org/TR/scxml/#transition)) -
**`event`** (a space-separated list of event descriptors), **`cond`** (boolean
expression, **default `true`**), **`target`** (IDREFS, a legal state
specification), **`type`** (`internal` | `external`, **default `external`**).
"A conformant SCXML document MUST specify at least one of 'event', 'cond' or
'target'." Eventless: taken whenever `cond` evaluates true. Targetless: "the
value of 'type' does not have any effect and taking the transition does not
change the state configuration" - the executable content still runs. Children:
executable content, run after all `<onexit>` and before all `<onentry>`
handlers triggered by the transition.

Event descriptor tokenization is stated normatively at
[3.12.1](https://www.w3.org/TR/scxml/#EventDescriptors): "The 'event' attribute
of a transition consists of one or more such event descriptors separated by
spaces", matching is by token prefix and case-sensitive, and a descriptor may
end in `.*`. **Note the gap:** the spec does *not* restate whitespace
tokenization for the IDREFS-typed `target` and `initial` attributes in its own
prose - that rests on the inherited XML Schema `IDREFS` datatype.
[3.11](https://www.w3.org/TR/scxml/#legalstate) instead constrains the
resulting *set* semantically ("no state is an ancestor of any other state on
the list"). The bead's rule to type them as lists is unaffected; the citation
for the split is the datatype, not SCXML prose.

**`<onentry>`** ([3.8](https://www.w3.org/TR/scxml/#onentry)) and
**`<onexit>`** ([3.9](https://www.w3.org/TR/scxml/#onexit)) - **no
attributes**; children are executable content; 0 or more of each per state.
The block rule is normative and is the reason the bead insists boundaries not
be flattened:

> The SCXML processor MUST execute the `<onentry>` handlers of a state in
> document order when the state is entered. In doing so, it MUST treat each
> handler as a separate block of executable content.

with the error rule from section 4: "If the processing of an element causes an
error to be raised, the processor MUST NOT process the remaining elements of
the block. (The execution of other blocks of executable content is not
affected.)" So each `<onentry>` *element* is its own error-isolation unit, and
a state with three `<onentry>` elements is structurally different from one with
their nine children concatenated. v1 flattened them into
`State.onentry_actions: [term()]`
(`../statifier/lib/statifier/parser/scxml/state_stack.ex:212-251`), losing the
boundary; this bead's acceptance criteria require it back.

**`<raise>`** ([4.2](https://www.w3.org/TR/scxml/#raise)) - **`event`**
required, NMTOKEN. No children. Note the attribute is a plain event *name*,
not an expression and not a descriptor list.

**`<log>`** ([4.7](https://www.w3.org/TR/scxml/#log)) - **`label`** (string,
optional, "meta-data about the log string"), **`expr`** (value expression,
optional). No children. Both optional, so both are `String.t() | nil`, and
`expr` is an expression field subject to the raw-string rule and to ADR-0014's
span needs.

**`<donedata>`** ([5.5](https://www.w3.org/TR/scxml/#donedata)) - **no
attributes.** Children: `<content>` (0-1) and `<param>` (0+), with the
constraint "A conformant SCXML document MUST specify either a single
`<content>` element or one or more `<param>` elements as children of
`<donedata>`, but not both." Phase 1 takes the `<content>` branch only;
st-l5k.4 rejects `<param>` as a Phase 3 unsupported element.

**`<content>`** ([5.6](https://www.w3.org/TR/scxml/#content)) - `expr`
(optional value expression), mutually exclusive with child content: "A
conformant SCXML document MUST NOT specify both the 'expr' attribute and child
content." **"Static content" is the `expr`-less branch**: "If the 'expr'
attribute is not present, the Processor MUST use the children of `<content>` as
the output." Those children may be "text, XML from any namespace, or a mixture
of both" - which is the open question about how faithfully Phase 1 has to
preserve non-text content (see Open Questions).

## The central trade-off: one State struct with a `kind` atom, or per-kind structs

The two candidates, stated concretely.

**A. One struct, one discriminator.**

```elixir
%Statifier.Document.State{
  kind: :state | :parallel | :final | :history | :initial,
  id: String.t() | nil, initial: [String.t()], initial_element: ... | nil,
  states: [t()], transitions: [Transition.t()],
  onentry: [Block.t()], onexit: [Block.t()],
  history_type: :shallow | :deep | nil,   # history only
  donedata: Donedata.t() | nil,           # final only
  location: Location.t()
}
```

**B. Per-kind structs.** `Document.State`, `Document.Parallel`,
`Document.Final`, `Document.History`, `Document.Initial`, each with only the
fields its element permits, and a union type
`@type any_state :: State.t() | Parallel.t() | Final.t() | History.t() | Initial.t()`
on every field that holds children.

### Axis 1: cheapness of the Appendix D predicates on the compiled Machine

**Nearly neutral, and this is the finding that most changes the shape of the
decision.** The predicates never touch a Document struct. ADR-0005 puts the
states in a flat array with integer indexes and descendant ranges, and
st-wju.1's compiled-state design already carries its own `kind` field. Whether
the compiler reads `%State{kind: :parallel}` or `%Parallel{}` while building
that array, it stamps the same compiled discriminator, and the predicate cost
at runtime is one atom match either way.

The one asymmetry worth naming is in the two composite predicates.
`isAtomicState` and `isCompoundState` need kind **and** children-emptiness, and
v1 avoided the second half by widening its discriminator at parse time to
include `:atomic` and `:compound` (`state_stack.ex:194-207`). That widening is
available to either candidate at compile time (st-wju.1's `kind` field is
unconstrained by this bead), and available to neither cleanly at the Document
layer - under candidate B it would require `Document.Atomic` and
`Document.Compound` structs that correspond to no XML element and would have to
be chosen at lowering time from a child list that lowering builds bottom-up.

Verdict on this axis: **no meaningful preference**. Both compile down. The
bead's phrasing already anticipates this - "has to compile down to something
pattern-matchable" - and both do.

### Axis 2: pattern-matchability

**Neutral at the language level, mildly favors A at the traversal level.**
`%Final{} = s` and `%State{kind: :final} = s` are both compile-time-optimized
matches on the BEAM; neither is measurably cheaper.

The difference appears in the *generic* traversals, and both the validator and
the compiler are dominated by generic traversals rather than kind-specific
ones:

- st-l5k.5's check 1 (unique ids across the document) is a walk over every
  state of every kind. Under A that is one recursive clause over
  `%State{states: children}`. Under B it is a five-clause dispatch or a
  protocol, repeated in every generic pass.
- st-wju.1's interning walk, its location-retention pass, and its
  document-order numbering are all the same shape.
- The location-accuracy sweep pattern already established for the DOM
  (`Location.slice/2` over every node) is another.

Under B, each of these needs an explicit union match. That is the "clause
matrix" smell `docs/architecture.md` names as the thing the rewrite exists to
avoid, reproduced one layer down - though at 5 clauses rather than 73, and in
consumers rather than in the parser.

Counter-evidence for B on this axis: the kind-*specific* passes get slightly
cleaner. `find_history_states` becomes `Enum.filter(children, &match?(%History{}, &1))`
rather than `&(&1.kind == :history)` - a wash - and functions that only accept
one kind get a `@spec` that says so, which A cannot express.

### Axis 3: `@type` expressiveness

**Clearly favors B, and this is B's strongest axis.** Under A,
`history_type: :shallow | :deep | nil` and `donedata: Donedata.t() | nil` are
fields that are *structurally meaningless* on four of the five kinds, and the
`nil` in each union exists only to say "not applicable here". `id` has the same
problem in reverse: `<initial>` has no `id` attribute at all
([spec 3.6](https://www.w3.org/TR/scxml/#initial)), so under A the field is
`String.t() | nil` where the `nil` means two different things (an `<initial>`
element, versus a `<state id>` the author omitted). Dialyzer cannot catch
`%State{kind: :parallel, history_type: :deep}`.

Under B, `%History{history_type: :shallow | :deep}` is non-nilable and exists
nowhere else; `%Final{donedata: Donedata.t() | nil}` has a `nil` that means
exactly one thing; `%Initial{}` simply has no `id` field. `@enforce_keys` does
real work per kind rather than being reduced to the intersection of all kinds.
This is the "make invalid states unrepresentable" argument, and on its own
terms it is correct.

The counter is that `docs/architecture.md` principle 4 scopes that goal to the
Machine, deliberately: "Parsing produces a `Document`; validation produces a
distinct `Machine` type (interned, optimized, guaranteed valid)." The Document
is the pre-validation type by design. And v1's own evidence is that the field
count, not the field nullability, is where the type discipline actually broke:
`Document`'s `@type t` silently omits `binding_location` even though the struct
has it (`../statifier/lib/statifier/document.ex:30`), which is a
hand-maintenance failure that per-kind structs would have made *more* likely,
not less, by multiplying the number of type blocks to keep in step.

### Axis 4: special-casing forced on lowering

**Neutral.** st-l5k.4's dispatch map already routes by element name, so
`build_parallel/2` exists either way; under A it returns `%State{kind:
:parallel, ...}` and under B it returns `%Parallel{...}`. Construction is
symmetric.

The one place it is not symmetric is the *collection* type. Under A,
`Document.states`, `State.states`, and the children of a parallel are all
`[State.t()]`. Under B they are all
`[State.t() | Parallel.t() | Final.t() | History.t() | Initial.t()]`, spelled
out (or aliased) on every such field, and every builder that appends a child
appends into a heterogeneous list. That is a documentation cost more than a
correctness one.

A second, subtler point favors A: v1 needed `update_state_type/1` to mutate
`:atomic` into `:compound` as children attached, which is impossible with
per-kind structs. v2 does not need that mutation, because lowering builds
bottom-up from a complete DOM tree rather than incrementally from a SAX event
stream - so this v1 pain does **not** transfer as evidence. Worth recording
precisely because it looks like it should.

### Axis 5: special-casing forced on the validator

**Clearly favors A, and this is A's strongest axis - and, on the evidence
gathered here, the strongest single argument in either direction.**

Three of st-l5k.5's eight required checks are reports about documents whose
shape is wrong in a way per-kind structs would make unrepresentable:

- **Check 8: "donedata appears only on final states."** Under B, `donedata` is
  a field on `%Final{}` and on nothing else, so a `<donedata>` under a
  `<state>` cannot be *built*. The error does not disappear; it moves into
  lowering, which must now reject it. But st-l5k.4's design note says the
  opposite in as many words: "lowering staying dumb about semantics keeps the
  layer boundary clean." And st-l5k.5's acceptance criteria require this check
  to have a stable error code and a red fixture asserting that code and its
  location line - which cannot exist if the check has been relocated.
- **Check 6: "final has no state children - only onentry, onexit, donedata."**
  Same shape. Under B, `%Final{}` has no `states` field, so the check becomes
  vacuous at the validator and a lowering error instead.
- **Check 4: "A state has at most one of initial attribute and initial
  element."** Under B this is representable either way (a `%State{}` can carry
  both an `initial` list and an `initial_element`), so it survives - but note
  that st-l5k.4's design explicitly names this case as one lowering must build
  as-is: "Conflicting forms (state with both initial attribute and initial
  element) are built as-is here - that is a validator check (st-l5k.5)."

Check 5 (`history` is a child of a compound state or parallel, not of scxml,
final, or another history) is the mirror image and cuts the same way: under B,
`%History{}` would have to be a legal member of `%Final{}`'s child list for the
validator to report it, which means B's per-kind child lists cannot actually be
narrowed to the spec's permitted-children sets without deleting the check.
Every narrowing that makes B type-expressive deletes a validator check the bead
requires.

The generic-walk cost from Axis 2 lands here too: checks 1, 2, 3, and 7 are
all id-index-and-walk passes over every state regardless of kind.

### Where the evidence leans

**Toward A: one `State` struct with a `kind` atom.** Four strands:

1. **The decisive one is the validator.** Per-kind structs relocate checks 6
   and 8 out of st-l5k.5 and into st-l5k.4, contradicting st-l5k.4's stated
   layer boundary and deleting checks whose acceptance criteria demand a code
   and a fixture apiece. Narrowing B's child lists enough to gain the type
   expressiveness is exactly what breaks the validator; leaving them wide
   enough to keep the validator whole gives up most of B's advantage. B's best
   axis and A's best axis are in direct tension, and only one of them is
   backed by an acceptance criterion.

2. **The predicate-cheapness criterion, which the bead named as the reason the
   choice matters, turns out not to discriminate.** ADR-0005 puts the
   predicates on the Machine. Both candidates compile down identically, so the
   axis the bead expected to be decisive is neutral, and the remaining axes are
   ergonomic.

3. **Both local precedents point at A.** `Statifier.Parser.Markup` in this repo
   already uses one struct with `kind :: :start | :end` for a two-arm
   discriminated union. v1 used one struct with a six-value `type` atom, and
   the pain v1 is quoted for throughout this rewrite's docs - 73-to-79 clauses
   in `state_stack.ex` - is a property of lowering inside the SAX handler, not
   of the discriminator. No comment anywhere in v1 calls the `type` field
   awkward.

4. **The generic traversals dominate.** The validator's id walk, the compiler's
   interning walk, and every location-retention pass are kind-independent, and
   there are more of them than there are kind-specific passes.

**What B genuinely wins, and what a plan choosing A owes in return:** B's
`@type` honesty is real and A does not get it for free. Under A,
`history_type` and `donedata` are fields that are meaningless on most kinds,
and `id: String.t() | nil` overloads `nil`. A plan that picks A should say in
the moduledoc which fields are kind-scoped and which validator check catches
their misuse, so the looseness is documented rather than latent - the same move
`DOM.Attribute`'s moduledoc makes for its nilable spans. The bead's design note
anticipates the middle path too: "split structs are acceptable if guards stay
one clause."

## Open Questions

Recorded here rather than blocking; none needs an answer before a plan can be
written, but each is a choice the plan stage has to make explicitly.

1. **Is the `<scxml>` root itself a state?** st-wju.1's design recommends
   interning the root as state index 0 with `kind: :scxml`, because "LCCA and
   transition domain fall out without special cases", and the spec's
   `isCompoundStateOrScxmlElement` in `findLCCA` supports that reading. If the
   Machine wants a `:scxml` kind, does the Document layer also want one - a
   `Document` struct that wraps a root `State{kind: :scxml}`, or a `Document`
   that duplicates the root's fields (v1's shape, where `Document` is not a
   `State` and `%{parent: nil}` stands in for the scxml arm at
   `../statifier/lib/statifier/state_hierarchy.ex:260-267`)?

2. **How much of the attribute-location story does the Document carry?** The
   acceptance criterion says "attribute-location story stated", and the DOM
   gives lowering two spans per attribute. Three shapes are available: v1's
   per-attribute flat fields (`id_location`, `cond_location`, ...), which cost
   one field per attribute and drifted out of sync with the `@type` in v1; a
   single map of attribute name to `Location`; or carrying spans only for the
   attributes a downstream consumer demonstrably needs (`cond`'s
   `value_location` for ADR-0014, `target` and `initial` for validator checks 2
   and 3, `id` for check 1's duplicate report). st-l5k.5's error struct wants
   "the source location of the offending node **or attribute**", which is the
   demand side of this question.

3. **Do `<onentry>` / `<onexit>` get a struct or a list of lists?** The spec
   requires each handler element to be a separate block (3.8, 3.9) and the bead
   requires boundaries preserved. A bare `[[content]]` preserves the boundary
   but gives the block no location, so a diagnostic can name the failing
   `<raise>` but not the `<onentry>` that contains it. A `%Block{content: [...],
   location: Location.t()}` costs one struct and satisfies Constraint 3 at
   block granularity. The bead's design note leaves both open.

4. **How is the `<initial>` element form represented, given it has no `id`?**
   The spec gives `<initial>` no attributes at all. v1 synthesized
   `"__initial_#{n}__"` ids to fit it into an id-bearing `State`
   (`../statifier/lib/statifier/parser/scxml/element_builder.ex:522-525`),
   which would collide with st-l5k.5's check 1 (unique ids) unless synthetic
   ids are excluded from it. The alternatives are a `kind: :initial` state with
   a nilable `id`, or a dedicated field on the parent state holding just the
   transition (which changes what "children in document order" means for the
   compiler's numbering). Related: does the `<initial>` transition's
   executable content, which the spec permits, need to be representable in
   Phase 1?

5. **What is `<donedata>`'s static content, exactly?** Spec 5.6 allows
   `<content>` children to be "text, XML from any namespace, or a mixture of
   both". Phase 1 is "static content only". Is that a plain `String.t()` taken
   from `DOM.text/1`, or does non-text child markup have to be preserved (which
   would mean holding a DOM subtree in a Document struct, crossing a layer
   boundary)? The corpus's `donedata` cases (`test/scxml_tests/mandatory/donedata/test294_test.exs`)
   would settle what is actually exercised.

6. **Does the Document layer need `document_order` integers?** v1 carried a
   `document_order` field on `Document`, `State`, `Transition`, and `Data`.
   st-wju.1 assigns dense `t_index` / `c_index` itself and derives state
   indexes from depth-first document order, so list order in the Document may
   be sufficient. If it is, the field should be absent rather than nil-filled;
   if it is not, the plan should say what reads it.

7. **Are attribute defaults applied at lowering, or preserved as absence?**
   st-l5k.4 commits to applying `:external`, `:early`, `:shallow` at lowering.
   That makes `transition.type == :external` ambiguous between "the author
   wrote it" and "the default applied" - fine for semantics, but it removes a
   distinction a diagnostic might want (an attribute location exists only for
   an attribute that was written). Worth stating explicitly in the struct docs
   either way.

8. **What is the honest sabotage story for a pure struct bead?** `docs/testing.md`
   requires a mutation that a reasonable person could make, and deleting a
   function body does not count. A bead that adds only `defstruct` /
   `@enforce_keys` / `@type` has little behavior to mutate - dropping a key
   from `@enforce_keys` is a real mutation that a construction test would
   redden, and that may be the whole of it. If the structs carry no functions,
   several tests may legitimately need the stated-exemption form
   (`# sabotage: n/a - ...`) rather than a mutation line.
