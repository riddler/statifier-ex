# Research: handler-registry invoke as an extension

**Date**: 2026-08-18T19:51:54-0600
**Git Commit**: 463fb453d27237ebf2bf329647d2518700ac847a
**Branch**: st-cmq.8-handler-registry-invoke
**Bead**: st-cmq.8

## Research Question

Where is `<invoke>` handled end to end today; which part of it is pure core and
which is Session-process concern; how are invoke ids minted and made stable
across persist/reload; what does `type`/`typeexpr` resolution do and where does
an unknown type end up; what registry and per-session configuration precedents
already exist; which ADRs constrain the work; and what is the regression net
that must survive moving the `type=scxml` mechanics behind a handler interface.

## Summary

`<invoke>` is already split across two layers with a clean instruction seam
between them, and the seam the bead's note 1 asks for mostly exists - it is just
not named as a contract.

- **The pure core** decides *that* an invocation starts, is cancelled,
  autoforwarded to, or finalized. It mints the invoke id, evaluates arguments
  and `type`/`typeexpr`, and emits `{:invoke, %Effect.Invoke{}}`,
  `{:cancel_invoke, %Effect.CancelInvoke{}}`, `{:autoforward, %Effect.Autoforward{}}`
  plus two trace effects. It never starts a process and never dereferences a URI.
- **`Statifier.Session.Effects.plan/2`** is a *pure* planner that turns those
  effects into instruction tuples - `{:start_child, invoke, effect}`,
  `{:stop_child, invoke_id}`, `{:forward, invoke_id, event}`,
  `{:raise, :platform, "error.execution", origin, opts}`.
- **`Statifier.Session.perform_instruction/3`** is one *executor* of those
  instructions; `Statifier.Replay`'s no-op performers are already a *second*
  executor of the same vocabulary ([`lib/statifier/replay.ex:453-492`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/replay.ex#L453-L492)).

So "define the behaviour against the effect vocabulary, not Session internals"
is a matter of promoting the existing planner/executor split into a named
contract, not of inventing a new layer. A host driving the pure Interpreter
directly already gets, for free and with no process: every invoke effect, the
pure planner, the pure `Statifier.Session.Invocations` table, the pure
`Statifier.Invoke.Source` resolver, and the pure inbox. What it does not get is
anything in `perform_instruction/3`'s `{:start_child, ...}`, `{:stop_child, ...}`,
`{:forward, ...}` clauses and the `:parent` / `{:invoke, _}` delivery clauses -
those are `session.ex` only, and a host today must reimplement them.

Two other findings matter for the plan:

1. **There is no clause in spec 6.4 requiring `error.execution` for an
   unsupported invoke type.** The bead says "per spec 6.4"; the cache says
   otherwise. The nearest normative clauses are 6.4.1's "Platforms MUST support
   `http://www.w3.org/TR/scxml/`" and 3.12.2's general error rule. 6.2.5 has the
   explicit sentence, but for `<send>`, not `<invoke>`. See
   [Spec 6.4, quoted](#spec-64-quoted).
2. **The current unsupported-type behavior already exists and was just hardened**
   (st-5fbw, commits `d62a2f9`, `5ff0322`, `463fb45`). An unsupported type today:
   still emits its `Effect.Invoke`, still writes `idlocation`, is **absent** from
   `machine_state.active_invocations`, absent from `Trace.InvokePass.invoke_ids`,
   emits no `Effect.CancelInvoke` on exit, and raises `error.execution` from
   `Statifier.Session.Effects.plan_invoke/2`. The bead's third acceptance
   criterion is therefore largely satisfied for the *unregistered* case already;
   what changes is that "supported" stops being a static three-way string test.

And the ADR record already names this bead as its reopen trigger: ADR-0047
decision 5 says the supported-type set stays static "so 6.2.5's check may run in
the core", with **"The named reopen trigger: an embedder-registrable
processor-type set."** That is exactly what st-cmq.8 lands.

### The seam: what a process-less host has and lacks

**Available with no process (all pure):**

| Piece | Path |
|---|---|
| Every invoke effect | `lib/statifier/effect/{invoke,cancel_invoke,autoforward}.ex` |
| The planner | `Statifier.Session.Effects.plan/2` |
| The live table | `Statifier.Session.Invocations` |
| The inbox | `Statifier.Session.Inbox` |
| Source resolution | `Statifier.Invoke.Source.resolve/2` |
| Type classification | `Statifier.Send.Target.supported_invoke_type?/1` |
| A second executor to copy | `Statifier.Replay` ([`lib/statifier/replay.ex:453-492`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/replay.ex#L453-L492)) |

**Session-only (a host must reimplement):** starting/monitoring/stopping a child
process, cross-session event delivery (`#_parent`, `#_<invokeid>`, autoforward
cast), `done.invoke.<id>` delivery, and the 6.4.3 discard bookkeeping at its own
drain point. `Statifier.Replay` already models the last of these with a plain
`MapSet` of `live_invoke_ids` (`lib/statifier/replay.ex:141,152,468-472,479-481`)
in place of `Invocations`.

`Statifier.Session.interpret/2` is public (ADR-0029), which is why
`plan_invoke/2` re-checks the type even though the core already did: an embedder
can hand the session effects no core drive produced.

### Invoke ids and persist/reload stability (note 2)

`generate_invoke_id/3` ([`lib/statifier/interpreter.ex:1491-1512`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L1491-L1512)) is the only
mint site:

- An author-written `id` is used verbatim and **does not advance the counter**
  ([`lib/statifier/interpreter.ex:1496-1497`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L1496-L1497)).
- Otherwise `machine_state.invoke_counter` is incremented and the id is
  `state.id <> "." <> "inv_" <> n` per 6.4.1's `stateid.platformid`, or bare
  `inv_<n>` when the invoking state has no author id
  ([`lib/statifier/interpreter.ex:1499-1512`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L1499-L1512)).

`invoke_counter` is a field on `%MachineState{}`
([`lib/statifier/machine_state.ex:128-167`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/machine_state.ex#L128-L167), default at `345`/`459`, type at `408`) -
a session-global sequence, not per state. ADR-0008 as amended 2026-08-15 is the
reason it is a counter rather than a UXID: an id minted inside the pure core must
be a deterministic function of `%MachineState{}` alone. **That is what makes ids
stable across persist/reload**: reloading a persisted `%MachineState{}` reloads
the counter, and re-running the same drive re-mints the same ids. Note 2's
"keep it that way" is already the accepted position and needs no change.

`machine_state.active_invocations`
([`lib/statifier/machine_state.ex:60-92`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/machine_state.ex#L60-L92), type at `407`) is
`%{{state_index, invoke_index} => invoke_id}` - the core's own liveness record,
deliberately distinct from the session's pid table
([`lib/statifier/session/invocations.ex:9-19`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session/invocations.ex#L9-L19)).

### `type` / `typeexpr` resolution, and the unknown type

Lowering stores `type` and `typeexpr` verbatim, side by side, with no
normalization ([`lib/statifier/lowering/builders.ex:813-846`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/lowering/builders.ex#L813-L846), doc comment at
`800-807`). The compiler folds the pair into one `Machine.expr()` via
`build_invoke_pair/6` ([`lib/statifier/compiler.ex:1528-1549`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/compiler.ex#L1528-L1549)) - `{:static, v}`
for `type`, `{:compiled, instrs, source}` for `typeexpr`. Still no
normalization.

The validator ([`lib/statifier/validator/checks/invoke.ex:56-105`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/validator/checks/invoke.ex#L56-L105)) enforces
6.4.1's five mutual-exclusion rules as errors and 6.5.2's forbidden
`<finalize>` content as an ADR-0033 warning. **It never inspects the value of
`type`.** An unsupported type is neither a validator error nor a warning.

Runtime resolution is `resolve_expr/2` ([`lib/statifier/interpreter.ex:1423-1426`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L1423-L1426)),
called at [`lib/statifier/interpreter.ex:1363`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L1363). The *only* place the short form
and the long URI are treated as equivalent is
`Statifier.Send.Target.supported_invoke_type?/1`
([`lib/statifier/send/target.ex:129-132`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/send/target.ex#L129-L132)):

```elixir
def supported_invoke_type?(nil), do: true
def supported_invoke_type?("scxml"), do: true
def supported_invoke_type?(type), do: type == scxml_invoke_type()
```

with `scxml_invoke_type/0` ([`lib/statifier/send/target.ex:101-102`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/send/target.ex#L101-L102)) returning
`"http://www.w3.org/TR/scxml/"` - deliberately *not* the `#SCXMLEventProcessor`
fragment URI `<send>` uses.

It has exactly two callers, and ADR-0047 decision 4 is the reason they cannot
drift:

- [`lib/statifier/interpreter.ex:1591`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L1591) (`maybe_record_active_invocation/5`,
  `1583-1596`) - bookkeeping only: an unsupported type is not recorded live.
- [`lib/statifier/session/effects.ex:210`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session/effects.ex#L210) (`plan_invoke/2`) - the actual
  rejection: `error.execution`, no `{:start_child, _}`.

So today's unknown-type path, end to end: `Effect.Invoke` emitted with the
authored `type`; `idlocation` written; no `active_invocations` entry; absent from
`Trace.InvokePass.invoke_ids`; no `Effect.CancelInvoke` on exit; never
autoforwarded to; never finalized; `error.execution` raised by the session
planner.

### `invoke_source` and ADR-0038's no-fetching posture (coexistence)

`Statifier.Invoke.Source.resolve/2` ([`lib/statifier/invoke/source.ex:76-112`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/invoke/source.ex#L76-L112)) is
the sole seam from an `%Effect.Invoke{}` to a `Statifier.Machine.t()`:

- `content` a binary -> `Statifier.compile(content, invoke_content_markup: true)`
  (the one call site setting that option, ADR-0042).
- `content: nil`, `src` a binary -> `opts[:invoke_source].(src)`, or
  `{:error, :src_not_resolved}` when no resolver is configured.
- `{:error, {:content_not_markup, content}}` / `{:error, :no_source}` otherwise.

`invoke_source` is a per-session option, a plain 1-arity function stored on
session state ([`lib/statifier/session.ex:342`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session.ex#L342), set at `733`, documented at
`447-451`), default `nil`, consumed at exactly one site
([`lib/statifier/session.ex:1313`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session.ex#L1313)).

**Coexistence constraint**: `resolve/2`'s contract is "produce a
`Machine.t()`". That is meaningful only for an SCXML-typed service. A registry
for non-scxml types is a *parallel* dispatch keyed on `type`, not an extension of
`Invoke.Source` - `Invoke.Source` becomes an implementation detail *of the
built-in scxml handler*. ADR-0038's own consequence anticipates it being
"extended, not redesigned".

### Registry and configuration precedents

- **There is no project-authored `@callback` anywhere in `lib/`.** The only two
  `@behaviour` lines implement dependency-owned behaviours:
  `Predicator.FunctionProvider` ([`lib/statifier/evaluator/functions.ex:1-28`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/evaluator/functions.ex#L1-L28)) and
  `Saxy.Handler` ([`lib/statifier/parser/handler.ex:58`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/parser/handler.ex#L58)). Both are hard-referenced
  by name, not selected at runtime.
- **There is no `Application.get_env`/`compile_env` anywhere in `lib/`, and no
  `config/` directory at all.** Every option in this codebase is threaded through
  `start_link/2` opts. Note 4's preference for per-session data over a global
  registry is therefore also the *only* precedent the repo has.
- **`start_link/2` options** ([`lib/statifier/session.ex:431-475`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session.ex#L431-L475), `693-748`):
  `:name`, `:session_id`, `:trace`, `:datamodel`, `:max_macrostep_rounds`,
  `:subscribers`, `:record`, `:invoke_source`, `:invoked_by`,
  `:inherit_observers`. Parsing is bare `Keyword.get/2,3`, `Keyword.get_lazy/3`,
  `Keyword.take/2` - no NimbleOptions or schema library.
- **`:invoke_source` is the closest existing precedent** for an embedder-supplied
  per-session handler: a function value on session state, `nil` default, no
  behaviour wrapping it, contract documented in prose and a typespec.
- **`Statifier.Registry`** ([`lib/statifier/supervisor.ex:19-26`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/supervisor.ex#L19-L26)) is an Elixir
  `Registry` for *session-id lookup*, embedder-placed per ADR-0027. It is an
  unrelated concept to an invoke-type handler registry and the name will
  collide in prose if reused.
- **`Statifier.Send.Routes`** ([`lib/statifier/send/routes.ex:1-73`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/send/routes.ex#L1-L73)) is the newest
  precedent for handing the core deployment state: a caller-stamped, point-in-time
  *value* (`%{sessions: MapSet, parent?: bool, invokes: MapSet}`) that rides on
  `%MachineState{}` and is re-stamped before every drive. ADR-0048 chose this
  shape (shape C) over a resolver function (shape D) explicitly, on three grounds:
  a value cannot perform a lookup so ADR-0003's purity stays structural; replay
  records one value per drive instead of call-by-call answers; and a resolver's
  freshness advantage is illusory. **If a registry has to be visible to the core,
  this is the shape the record already blessed.**
- **`:subscribers`** plus `subscribe/2,3` ([`lib/statifier/session.ex:620-671`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session.ex#L620-L671)) is
  the per-session host-callback precedent on the observation side;
  `Statifier.Session.Telemetry` is a fixed `:telemetry` event emitter, not
  pluggable.

### v1's handler registry (`../statifier`, read-only reference)

[`docs/architecture.md:176-178`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/docs/architecture.md#L176-L178) says v1's handler-registry invoke "is kept as an
explicit extension type - a useful, safe escape hatch, but not the definition of
`<invoke>`". The v1 shape:

- `Statifier.InvokeHandler` (`../statifier/lib/statifier/invoke_handler.ex:93`)
  defines exactly one callback:
  `@callback handle_invoke(src, params, StateChart.t()) :: handler_result()`,
  with `handler_result` being `{:ok, sc} | {:ok, data, sc} | {:error, :communication, reason} | {:error, :execution, reason}`.
- Registration is `invoke_handlers: %{type_string => &Mod.fun/3}` passed to
  `Interpreter.initialize/2` and stored on `StateChart`
  (`../statifier/lib/statifier/state_chart.ex:22,44`) - per-run data, not a
  global.
- Dispatch is `Map.get(state_chart.invoke_handlers, type)` in
  `dispatch_invoke/3` (`../statifier/lib/statifier/actions/invoke_action.ex:99-118`);
  a missing entry generates `error.execution` with the message
  `"No handler registered for invoke type '#{type}'"`.

Three properties of the v1 shape are incompatible with v2 as it stands and are
worth naming rather than inheriting: it is **synchronous** (the handler returns
its result inline, so a `done.invoke` minutes later is inexpressible); it
**rescues exceptions to an error event**
(`../statifier/lib/statifier/actions/invoke_action.ex:157-166`), which is the
rescue-to-default at a leaf this repo forbids; and it hands the handler the whole
mutable `StateChart`, which has no v2 analogue on the pure side.

### Spec 6.4, quoted

From `$(git rev-parse --path-format=absolute --git-common-dir)/spec-cache/scxml-rec.html`,
section 6.4.1:

> Platforms MUST support http://www.w3.org/TR/scxml/ as a value for the 'type'
> attribute. Platforms MAY support http://www.w3.org/TR/voicexml21/, which
> indicates a VoiceXML 2.1 interpreter, http://www.w3.org/TR/voicexml30/, which
> indicates a VoiceXML 3.x interpreter, and http://www.w3.org/TR/ccxml/, which
> indicates a CCXML 1.0 interpreter. Platforms MAY support additional values, but
> they SHOULD assign them the URI of a description of the relevant service.
> Processors MAY define short form notations as an authoring convenience (e.g.,
> "scxml" as equivalent to http://www.w3.org/TR/scxml/).

and on the `typeexpr` attribute:

> A dynamic alternative to 'type'. If this attribute is present, the SCXML
> Processor MUST evaluate it when the parent <invoke> element is evaluated and
> treat the result as if it had been entered as the value of 'type'.

and 6.4 on argument failure and starting the service:

> When the <invoke> element is executed, if the evaluation of its arguments
> produces an error, the SCXML Processor MUST terminate the processing of the
> element without further action. Otherwise the Processor MUST start a new
> logical instance of the external service specified in 'type' or 'typeexpr',
> passing it the URL specified by 'src' or the data specified by <content>,
> "namelist" or <param>.

**A full text sweep of the REC for `error.execution` finds no occurrence
anywhere in section 6.4.** The nearest explicit sentence is 6.2.5, about
`<send>`:

> If the SCXML Processor does not support the type that is specified, it MUST
> place the event error.execution on the internal event queue.

and the general rule in 3.12.2:

> Once the SCXML processor has begun executing a well-formed SCXML document, it
> MUST signal any errors that occur by raising SCXML events whose names begin
> with 'error.'.
> ... 'error.communication' and 'error.execution'. The former cover errors
> occurring while trying to communicate with external entities, such as those
> arising from <send> and <invoke>, while the latter category consists of errors
> internal to the execution of the document.

Appendix D (`spec-cache/appendix-d.txt:137-141`) declares the procedure itself
platform-specific:

```
        # Here we invoke whatever needs to be invoked. The implementation of 'invoke' is platform-specific
        for state in statesToInvoke.sort(entryOrder):
            for inv in state.invoke.sort(documentOrder):
                invoke(inv)
        statesToInvoke.clear()
```

So the existing `error.execution` behavior is a defensible platform choice built
on 3.12.2 by analogy with 6.2.5, not a 6.4 MUST. It is also worth noting that
3.12.2 lists `error.communication` as covering "errors occurring while trying to
communicate with external entities, such as those arising from `<send>` and
`<invoke>`", which is what the session already raises when
`Statifier.Invoke.Source` fails.

## Architecture Documentation

The constraints, by record:

- **ADR-0003** (pure core with effects). A registry cannot live inside the pure
  core as a lookup. The core returns `{machine_state, [effect]}`; anything that
  performs is session/host side.
- **ADR-0004** (predicator as the datamodel). This bead builds the sanctioned
  extension surface this record points hosts at. It does not reopen eval: a
  handler is embedder-supplied code, never document-authored.
- **ADR-0008** (amended 2026-08-15). Any id minted inside the core must be a
  deterministic `%MachineState{}` counter, never a UXID. `invoke_counter` already
  is; note 2 needs no change.
- **ADR-0012** (debuggability). Microsteps stay resumable and the
  `{:invoke, state_index, invoke_index}` cause identity stays stamped. If a
  registry becomes core-visible it must be part of the resumable position (which
  is precisely ADR-0048 decision 2's argument for `Routes` being a struct field).
- **ADR-0024 / ADR-0038** (never fetch a URI; `Invoke.Source` at the boundary).
  The registry must not become a back door for the library to fetch `src`. A
  handler that fetches does so as embedder code, under embedder policy.
- **ADR-0027** (embedder-placed session runtime). `Statifier.Registry` is
  session-id lookup, embedder-placed. Name collision risk for a "handler
  registry".
- **ADR-0029 / ADR-0034** (`Session.interpret/2` public; replay is catch-all-free).
  Any new instruction shape needs an explicit `Statifier.Replay` clause.
- **ADR-0031** (argument failure aborts the invocation). Handler resolution must
  happen *after* argument evaluation succeeds, per invocation.
- **ADR-0032** (round budget spans the invoke re-entry). A repeatedly-failing
  unregistered type already terminates within budget; no new work.
- **ADR-0040** (session telemetry event contract) + statifier-ui's normalizer.
  A non-additive change to `%Effect.Invoke{}` is a contract change with a live
  downstream consumer.
- **ADR-0044 / ADR-0046** (re-entry deferral; round on every core effect). Any
  new effect follows both.
- **ADR-0047 decision 5** - the direct trigger:

  > **5. The supported-type set stays static, so 6.2.5's check may run in the
  > core.** ... The named reopen trigger: an embedder-registrable processor-type
  > set. If that lands, the 6.2.5 check becomes deployment state and moves back
  > to the boundary (or into a caller-supplied capability), and this decision is
  > re-argued in that record.

  Decision 4's anti-drift property ("The two sites apply one shared classifier,
  so they cannot drift") must survive whatever replaces
  `supported_invoke_type?/1`.
- **ADR-0048** (send reachability judged against a route snapshot). The most
  recent and most directly applicable precedent: when the core needed deployment
  state, the answer was a caller-stamped point-in-time **value** on
  `%MachineState{}`, re-stamped before every drive - explicitly chosen over a
  resolver function.
- **ADR-0050** (invoked children inherit observation by opt-in). Scoped to
  `type=scxml` child sessions; a non-scxml handler has no child session, so the
  mechanism does not reach it.

## Open Questions

1. **The bead cites "spec 6.4" for the `error.execution` requirement, and 6.4
   does not contain it.** A full text sweep of `spec-cache/scxml-rec.html` finds
   no `error.execution` in 6.4 at all; 6.2.5 has the sentence for `<send>` and
   3.12.2 has the general rule, which also assigns `<invoke>` communication
   failures to `error.communication`. The behavior itself already ships and is
   defensible as a platform choice on an Appendix-D-declared platform-specific
   procedure - but the plan should cite 3.12.2 plus the 6.2.5 analogy rather than
   a 6.4 MUST, and should decide whether an *unregistered* type is
   `error.execution` (today's behavior, "the document named something this
   deployment does not implement") or `error.communication` ("failed to reach an
   external entity"). Recorded here rather than resolved: it is a direction call.

2. **Note 6's premise about the golden trace corpus does not hold.** The
   statifier-ui golden trace test uses a two-state chart chosen deliberately to
   contain **no `<invoke>`**
   (`~/repos/github/statifier-ui/test/statifier_ui/trace/golden_trace_test.exs`
   moduledoc). The real invoke regression net is this repo's own 20 ratcheted
   mandatory conformance tests plus the ~100 internal tests listed above. What
   statifier-ui *does* pin is the effect wire format
   (`statifier-ui:lib/statifier_ui/trace/normalizer.ex:279-301` reads `p.type` off
   `%Effect.Invoke{}`), so the cross-repo obligation is "keep `%Effect.Invoke{}`
   additive", not "keep the golden trace green". And nothing in *this* repo's
   suite reddens on a wire-format break - a case-insensitive sweep of `lib/`,
   `test/`, `tools/`, and fixture directories finds no "golden" anything; the
   only references are prose in `docs/adr/0049`, `docs/adr/0050`, and three
   research/plan documents. Worth a `mirrors:` note or a correction on the bead.

3. **Where does the registry live, and is it core-visible?** Three shapes the
   codebase already supports, in ascending order of core visibility:
   (a) a session-only `:invoke_handlers` opt, exactly like `:invoke_source` -
   the core keeps `supported_invoke_type?/1` unchanged and stays wrong about
   liveness for registered non-scxml types; (b) a `Statifier.Send.Routes`-shaped
   value stamped onto `%MachineState{}` per drive, so the core can gate
   `active_invocations` on the *actual* registered set (ADR-0048's blessed
   shape, and the only one that keeps ADR-0047 decision 4's anti-drift property
   honest); (c) a global/compile-time registry, which note 4 disprefers and which
   the repo has no precedent for. This is the plan's central call and it needs
   ADR-0047 decision 5 re-argued either way.

4. **What does a handler's start return, and who owns the IO?** Note 3 asks for
   at-least-once idempotency semantics or "start shaped as returned
   instructions/data so the host owns the IO and the dedup". The existing
   instruction vocabulary (`{:start_child, _}`, `{:stop_child, _}`,
   `{:forward, _, _}`) is already instruction-shaped and already has two
   executors, which argues for the returned-instruction shape - but nothing in
   the record decides it, and v1's synchronous `handle_invoke/3` is the opposite
   shape.

5. **What is the non-scxml analogue of `done.invoke.<id>` and `<donedata>`?**
   Today that event is constructed at [`lib/statifier/session.ex:1397`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/session.ex#L1397) from a
   child session's `done_effect.donedata`. A handler with no child session has no
   such source. Whether the behaviour returns the done payload, or the host feeds
   it back through a public `Statifier.Session` call, is undecided in every
   document read.

6. **Does `<finalize>` auto-assign apply to non-scxml handlers?** Spec 6.4.2
   says only scxml/ccxml/voicexml-typed services MUST interpret `<param>`/namelist
   as datamodel injection, and "for targets of other invoked service types, the
   interpretation ... is platform-specific". `auto_assign_finalize/5`
   ([`lib/statifier/interpreter.ex:728-759`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/lib/statifier/interpreter.ex#L728-L759)) is in the pure core and runs off the
   arriving event regardless of type, which is probably the right default but is
   an unexamined generalization.

7. **Where does the user-facing doc section go?** The bead asks for one. There is
   no embedder guide today: `README.md` has three headings and none is about
   usage, and `docs/` holds only architecture/datamodel/observability/testing/
   workflow. A new `docs/extending.md` or a section in `docs/architecture.md`
   are both plausible; nothing in the record picks one.

8. **Naming.** `Statifier.Registry` is taken (ADR-0027, session-id lookup). A
   handler registry needs a name that does not collide in prose or code -
   `Statifier.Invoke.Handlers`, `Statifier.Invoke.Registry`, and
   `Statifier.Invoke.Handler` (behaviour) are all unclaimed, but nothing decides
   it.

9. **Does the feature detector need an invoke-`type` flag?** Today
   `invoke_elements: :supported` keys on the element only
   ([`test/support/feature_detector.ex:162`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/test/support/feature_detector.ex#L162)), and
   [`test/statifier/feature_detector_test.exs:318`](https://github.com/riddler/statifier-ex/blob/463fb453d27237ebf2bf329647d2518700ac847a/test/statifier/feature_detector_test.exs#L318) asserts no registry entry is
   `:unsupported`. Whether a registry changes what the corpus gate should say is
   unexamined.
