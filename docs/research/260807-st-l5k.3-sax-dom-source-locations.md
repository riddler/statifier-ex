# Research: Parses XML to a generic DOM with source locations (st-l5k.3)

**Date**: 2026-08-07T08:24:23-0600
**Git Commit**: 75cee536ac97331ef1dc97e2f859acb0a8f0b723
**Branch**: st-l5k.3-sax-dom
**Beads Issue**: st-l5k.3

## Research Question

From the bead: a Saxy SAX handler producing generic DOM nodes (`name`,
`attributes`, `children`, `location`) with no typed knowledge of SCXML
elements - the layer that replaces v1's 73-clause `state_stack`. Source
locations are a property of every DOM node, not bolted-on bookkeeping. No
lowering here; the output is the generic tree only.

Acceptance criteria: any well-formed XML parses to the generic DOM; every node
has a location; malformed XML returns `{:error, reason}` with position info; no
SCXML-specific clauses in the handler.

This document maps three things: what v2 has today (nothing - `lib/` is
greenfield for parsing), what v1 does and why its shape produced the clause
matrix, and what Saxy 1.6.1 does and does not give a handler.

## Summary

**v2 state.** `lib/` contains no parser modules at all. The only non-Mix module
is `lib/statifier.ex`. Saxy is already a runtime dependency (`{:saxy, "~> 1.6"}`
in `mix.exs`, pinned to `1.6.1` in `mix.lock`) and is already vendored in
`deps/`. Nothing consumes it yet. This bead is the first `lib/statifier/parser/`
code in the repo.

**The layer contract.** `docs/architecture.md`'s "Parser: DOM first, then
lowering" section fixes the boundary: XML string -> generic DOM node
(`name`, `attributes`, `children`, `location`) -> lowering pass -> typed
`Document`. This bead is the first arrow only. The next bead, st-l5k.4 ("Lowers
the DOM to Document structs"), is blocked on it; st-l5k.2 ("Defines the typed
Document structs") is a sibling, not a dependency.

**The central technical fact.** Saxy 1.6.1 gives handler callbacks **no**
position information of any kind - no line, no column, no byte offset - and has
no option to enable it. `Saxy.Handler.handle_event/3` receives only
`(event_type, data, user_state)`, where `data` for `:start_element` is
`{name, attributes}` and nothing more (`deps/saxy/lib/saxy/handler.ex`). The
only positional data Saxy produces is on the failure path:
`%Saxy.ParseError{reason:, binary:, position:}`, where `position` is a **byte
offset** into `binary` (`deps/saxy/lib/saxy/parse_error.ex`,
`deps/saxy/lib/saxy/parser/utils.ex:6-12`).

So "every node has a location" is not something Saxy hands over; it has to be
produced alongside the event stream. v1 solved this by re-scanning the XML text
per element with a regex and an occurrence counter. That mechanism, and its
known imprecision, is documented in detail below - it is the piece of v1 whose
behavior most directly constrains what "location" can mean in v2.

**The clause matrix.** v1's `state_stack.ex` is 903 lines and 93 `def`/`defp`
heads, of which **79 are public-function clauses** across 17 `handle_*_end`
functions. The count comes from one structural decision: `StateStack` has no
generic "append this finished child to whatever container is on top of the
stack" operation. Instead each executable-content element enumerates every legal
SCXML parent context as its own function clause. Seven elements (`log`, `raise`,
`assign`, `send`, `foreach`, `invoke`, `if`) x eight contexts each = 56 clauses
on their own. A generic DOM handler collapses all of that to one `:end_element`
clause, because "attach child to parent" is a single list prepend when the
parent is a DOM node rather than a differently-shaped typed struct per context.

### What Saxy 1.6.1 provides

Verified against the vendored copy in `deps/saxy` and confirmed against upstream
docs and the GitHub tracker.

**Handler callbacks** (`deps/saxy/lib/saxy/handler.ex`):

| Event | `data` payload |
|---|---|
| `:start_document` | prolog keyword list |
| `:start_element` | `{name :: String.t(), attributes :: [{String.t(), String.t()}]}` |
| `:characters` | binary, **not trimmed**, includes all `CharData` whitespace |
| `:cdata` | binary (emitted as `:characters` by default; `cdata_as_characters: true` is the default) |
| `:end_element` | `name :: String.t()` |
| `:end_document` | arbitrary |

Return values: `{:ok, state}` continues, `{:stop, term}` and `{:halt, term}`
abort. A bad return produces `{:bad_return, {event, return}}` in the
`ParseError`.

Notable Saxy properties relevant to this layer:

- **No atoms are created during parsing.** Element and attribute names arrive as
  binaries. (This is the reason Saxy was chosen over xmerl-based options in the
  wider Elixir community, per José Valim's recommendation on Elixir Forum.)
- **No namespace processing.** `xmlns` arrives as an ordinary attribute and a
  prefixed name like `foo:bar` arrives as the literal string `"foo:bar"`. The
  corpus (`test/scion_tests/`, `test/scxml_tests/`) uses only the default
  namespace `xmlns="http://www.w3.org/2005/07/scxml"` and has no prefixed
  elements, so nothing in the corpus forces a namespace decision today.
- **DTD/Doctype is skipped**, not reported. XSD is unsupported.
- **Only UTF-8**; a non-UTF-8 encoding declaration stops the parser with
  `{:invalid_encoding, encoding}`.
- **Entity expansion**: `:expand_entity` option with `:keep` (default), `:skip`,
  `:never`, or `{m, f, a}`. Character references and the five predefined XML
  entities expand by default.

**Error shape** (`deps/saxy/lib/saxy/parse_error.ex`):

```elixir
defexception [:reason, :binary, :position]

@type reason() ::
        {:token, token :: String.t()}
        | {:wrong_closing_tag, open_tag :: String.t(), close_tag :: String.t()}
        | {:invalid_pi, pi_name :: String.t()}
        | {:invalid_encoding, encoding :: String.t()}
        | {:bad_return, {event :: atom(), return :: term()}}
```

`position` is a byte offset (`Saxy.Parser.Utils.parse_error/4` passes the
parser's buffer position straight through). `Exception.message/1` on it produces
e.g. `unexpected byte "<", expected token: "="` or `unexpected end of input,
expected token: ...`. Converting the byte offset to `{line, column}` is a
straightforward count over the prefix `binary_part(binary, 0, position)` - the
raw material for the bead's "position info" acceptance criterion is present, but
line/column is a v2-side derivation.

**Saxy.SimpleForm** is the closest existing analogue to the target: it produces
`{name, attributes, children}` 3-tuples with a stack-based handler of exactly
seven clauses (`deps/saxy/lib/saxy/simple_form/handler.ex`) and **no** location
data. It is a useful shape reference for the child-attachment idiom (build on a
stack, reverse content on `:end_element`, fold into parent), and it is what the
generic DOM would be if locations were not required.

**Saxy.Partial** feeds chunks incrementally (`new/3`, `parse/2,3`,
`terminate/1`, `get_state/1`). A caller can track cumulative bytes fed, but Saxy
never reports where inside a chunk an event fired, so this yields
chunk-granularity brackets only, not per-element offsets.

**Upstream status**: saxy is actively maintained (v1.6.1 released 2026-07-10,
v1.6.0 2024-10-22). A search of qcam/saxy issues and PRs for "line",
"position", "location", "offset", "column" found **no** open or closed request
for source-location tracking and no maintainer statement on it. No published
Elixir library or blog post builds a DOM-with-locations on top of Saxy.

**Alternatives that do carry locations** (documented, not recommended):

- `:xmerl_sax_parser` (OTP stdlib) passes an `event_location()` to every
  callback: `{CurrentLocation :: string(), EntityName :: string(), LineNo ::
  integer()}` - a line number on every event, but **no column**, and it creates
  atoms.
- `xmerl_scan` records carry a `pos` field, which is a sibling/document-order
  index, **not** a source position.
- `erlsom` carries no position data at all, including in error tuples.
- `sweet_xml` wraps `xmerl_scan` and inherits its lack of locations.

### v1's parser: module map

Four modules under `../statifier/lib/statifier/parser/scxml/` plus the entry
point. Line counts: `scxml.ex` 104, `handler.ex` 459, `state_stack.ex` 903,
`element_builder.ex` 540, `location_tracker.ex` 102 - 2108 total.

| Module | Owns |
|---|---|
| `Statifier.Parser.SCXML` (`scxml.ex`) | public `parse/2`; XML normalization; the `Saxy.parse_string/3` call |
| `...SCXML.Handler` (`handler.ex`) | `@behaviour Saxy.Handler`; the parser state struct; `:start_element` -> `dispatch_element_start/4` name switch; per-element location lookup |
| `...SCXML.StateStack` (`state_stack.ex`) | all `:end_element` semantics: fold the finished child into its parent; push/pop/peek; `:characters` |
| `...SCXML.ElementBuilder` (`element_builder.ex`) | pure `build_*` constructors producing typed structs with location metadata |
| `...SCXML.LocationTracker` (`location_tracker.ex`) | text search over the raw XML for `{line, column}` of an element and the line of an attribute |

Parser state (`handler.ex:16-31`):

```elixir
defstruct [:stack, :result, :current_element, :line, :column, :xml_string, :element_counts]
```

`:line` and `:column` are carried on the struct but are vestigial - locations
are computed by `LocationTracker` from `:xml_string` and `:element_counts` on
each `:start_element`, not advanced incrementally. `:xml_string` holds the
*normalized* document (see below), so every location is relative to the
normalized text, not the caller's input.

### v1: how source locations are computed

`Handler.prepare_element_handling/2` (`handler.ex:88-102`) increments
`element_counts[name]`, then calls
`LocationTracker.get_location_info(xml_string, name, stack, element_counts)`.

`LocationTracker.find_element_occurrence/4` (`location_tracker.ex:47-67`) splits
the whole XML into lines and walks them, matching the regex
`~r/<#{element_name}([ \/>]|$)/` per line, decrementing the target occurrence
count on each **line** that matches. Column comes from
`String.split(line, "<#{element_name}", parts: 2)` and taking
`String.length(prefix) + 1` (`location_tracker.ex:69-74`).

Consequences of this mechanism, as it exists:

- The occurrence counter is decremented **per matching line**, not per match, so
  two same-named elements on one line resolve to the same location, and the
  count desynchronizes from the SAX stream after such a line.
- The column is the position of the **first** occurrence of `<name` on the line,
  regardless of which occurrence was sought.
- The regex is built from the element name by interpolation into `~r/.../`, so
  the search is textual over the whole document and matches inside XML comments
  and character data as readily as inside real markup.
- The scan is O(document) per element, so the parse is O(n^2) in element count.
- Fallback on no match is `{1, 1}` (`location_tracker.ex:43,48`).

Attribute locations (`LocationTracker.attribute_location/3`,
`location_tracker.ex:78-101`) search forward from the element's line for any
line containing the substring `"#{attr_name}="` and return
`%{line: n, column: nil}` - **column is never computed for attributes**, and the
search does not stop at the element's closing `>`, so it can walk into a later
element. Fallback is `%{line: nil, column: nil}`.

Because `Statifier.Parser.SCXML.parse/2` normalizes the document before parsing
(`scxml.ex:47-103`: `String.trim/1`, optional `<?xml ...?>` prepend, injecting
`xmlns="..."` and `version="1.0"` into the `<scxml` tag when absent), the
locations describe the normalized text. The `:xml_declaration` option's doc
comment states this outright: setting it true "shifts line numbers by 1". The
xmlns/version injection shifts columns on the `<scxml>` line unconditionally.

### v1: where locations are stored

Two different shapes, chosen per target struct (`element_builder.ex`):

1. **Flat fields** on `Document`, `State`, `Transition`, `Data`: a
   `source_location: %{line:, column:}` plus one `<attr>_location:` field per
   attribute the struct cares about. E.g. `Document` carries `name_location`,
   `initial_location`, `datamodel_location`, `version_location`,
   `binding_location` (`element_builder.ex:56-61`); `Transition` carries
   `event_location`, `target_location`, `cond_location`
   (`element_builder.ex:253-257`).
2. **A nested map** on the action structs (`LogAction`, `RaiseAction`,
   `AssignAction`, `SendAction`, `Param`, `SendContent`, `ForeachAction`,
   `InvokeAction`): a single `source_location` map whose `:source` key holds the
   element's own `%{line, column}` and whose other keys hold per-attribute
   locations. E.g. `LogAction`'s is `%{source: location, label: label_location,
   expr: expr_location}` (`element_builder.ex:301-305`); `SendAction`'s has
   twelve keys (`element_builder.ex:372-385`).

Elements that get **no** location at all in v1: `<datamodel>`,
`<onentry>`, `<onexit>`, `<elseif>`, `<else>` (`handler.ex:214-241`,
`379-411` - each ignores the `_location` argument). `<if>` gets one, but stored
as a bare `location:` key in an ad-hoc map assembled inline in the handler
(`handler.ex:365-369`) rather than through `ElementBuilder`.

`Data`'s `child_content_location` is initialized to `nil`
(`element_builder.ex:285`) and no code path ever sets it.

This is the concrete referent of the architecture doc's phrase "bolted-on
bookkeeping": location is a per-struct, per-attribute convention that each
builder re-implements, so an element whose builder forgets it simply has none.

The "eight-context family", shown by `handle_log_end/1`
(`state_stack.ex:257-317`), matches the parent frame beneath the finished child:

```elixir
{"onentry", actions} when is_list(actions)   # subsequent child of onentry
{"onentry", :onentry_block}                  # first child of onentry
{"onexit", actions} when is_list(actions)    # subsequent child of onexit
{"onexit", :onexit_block}                    # first child of onexit
{"if", if_container}                         # inside a conditional block
{"foreach", foreach_action}                  # inside foreach
{"transition", transition}                   # directly under transition
_                                            # catch-all: pop and drop
```

The first/subsequent split exists because `<onentry>` is pushed with the marker
atom `:onentry_block` and only becomes a list once a child is folded in. Seven
executable-content elements x this context set = 56 of the 79 clauses.

**Why a generic DOM erases the matrix.** Every one of those clauses does the
same abstract thing - "attach the finished child to its parent" - and differs
only in which typed field of which typed parent struct receives it
(`onentry_actions`, `if_container.conditional_blocks[i].actions`,
`foreach_action.actions`, `transition.actions`, `send_action.params`,
`document.states`, `parent_state.states`, `parent_state.transitions`, ...).
When the parent is a DOM node with one `children` list, there is exactly one
attachment rule, so `:end_element` is one clause regardless of element or
context. That is the architecture doc's claim ("Adding an element touches one
builder, not a clause matrix") stated as a clause count.

### v1: stack mechanics

The stack is `state.stack`, a plain list of `{element_name :: String.t(),
element_data :: term()}` 2-tuples, head = innermost open element. `element_data`
is heterogeneous by design: a typed struct, `nil` (for `<datamodel>` and unknown
elements), the marker atom `:onentry_block` / `:onexit_block`, or an ad-hoc map
(the `if_container`).

- `push_element/3` (`state_stack.ex:174-177`) prepends.
- `pop_element/1` (`state_stack.ex:182-185`) is `tl/1`, used only when there is
  no attachment rule (unknown elements, catch-all clauses).
- Attachment is a **single stack rewrite**, not pop-then-mutate: each
  `handle_*_end` destructures head (finished child) and the next frame (parent),
  builds an updated parent, and returns
  `%{state | stack: [{parent_type, updated_parent} | rest]}`. The child frame is
  simply not re-pushed.

`Saxy.SimpleForm.Handler` uses the same idiom in seven clauses, which is the
minimal version of it.

### v1: what is SCXML-specific in the handler

The list below is what a generic DOM handler explicitly does **not** do (bead
acceptance criterion: "no SCXML-specific clauses in the handler"). Each of these
becomes lowering-pass work (st-l5k.4) or validator work (st-l5k.5):

- **Typed dispatch by element name** - `dispatch_element_start/4` knows all ~22
  SCXML element names and their target structs (`handler.ex:104-450`).
- **State type inference** - `update_state_type/1` flips a parent from `:atomic`
  to `:compound` as children attach (`state_stack.ex:194-207`).
- **Synthetic IDs for `<initial>`** - `"__initial_#{n}__"`
  (`element_builder.ex:157-175`, `522-525`).
- **`<history>` type defaulting** to `:shallow` (`element_builder.ex:195-200`).
- **if/elseif/else reassembly** - `<elseif>`/`<else>` are flat siblings in XML;
  v1 accumulates `conditional_blocks` with a `current_block_index` during
  parsing and collapses them into one `IfAction` on `</if>`
  (`handler.ex:357-411`, `state_stack.ex:531-570`, `776-789`). In a generic DOM
  these are three sibling children and nothing more.
- **`<param>` context retagging** - pushed as `"send_param"` or `"invoke_param"`
  by peeking the parent frame (`handler.ex:311-338`).
- **Early/late binding hoist** - a state-level `<data>` is hoisted into
  `document.datamodel_elements` only when `binding == "early"`, and silently
  dropped otherwise (`state_stack.ex:111-135`).
- **Transition source assignment** - `transition.source = parent_state.id`
  (`state_stack.ex:65`).
- **IDREFS attribute grammar** - `initial` and `target` split on whitespace into
  lists (`element_builder.ex:235-243`, `531-539`).
- **Depth computation** - `calculate_stack_depth/1` counts `"state"` frames
  below (`state_stack.ex:36`, `188-190`).
- **Document normalization** - injecting `xmlns` / `version` / `<?xml?>` before
  parsing (`scxml.ex:47-103`) is an SCXML-specific input fixup living in the
  parser entry point.

### What the corpus feeds the parser

Sampled from `test/scion_tests/` and `test/scxml_tests/` (generated corpus, XML
inlined in triple-quoted heredocs at 4-space indentation per the repo
convention):

- **XML declarations** are present (`<?xml version="1.0" encoding="UTF-8"?>` on
  line 1).
- **XML comments** are common and multi-line - e.g. the Apache license header in
  every SCION file (`test/scion_tests/parallel/test0_test.exs:11-25`). Any
  location mechanism that scans text has to skip them; any offset-tracking
  mechanism has to account for them consuming source without emitting events.
- **No CDATA sections** anywhere in the corpus.
- **No namespace-prefixed element names** anywhere in the corpus; the only
  namespace declaration is the default `xmlns="http://www.w3.org/2005/07/scxml"`.
- Significant **incidental whitespace**: leading blank lines, trailing blank
  lines, trailing spaces inside start tags (`<scxml ` with a trailing space
  before the newline), and attributes spread across multiple lines. Whitespace
  `:characters` events between elements are emitted by Saxy untrimmed.

### Constraints from repo docs

- **`docs/architecture.md`, "Parser: DOM first, then lowering"** - the DOM node
  field set (`name`, `attributes`, `children`, `location`) and the statement
  that locations are a property of every node.
- **ADR-0012 item 3 / `docs/observability.md` Constraint 3** - locations must
  survive all the way to the `Machine`, not just the `Document`; states,
  transitions, and executable-content nodes retain their source location, and
  the compiler assigns document-order indexes to transitions and
  executable-content nodes. The DOM is the origin of that data, so what the DOM
  records bounds what anything downstream can report. `docs/observability.md`'s
  implementation checklist has an unchecked "compiler retains locations on
  states, transitions, executable content" item.
- **ADR-0014** - expression-level spans are in scope for the same constraint,
  carried by the compiled-expression value from predicator. That is expression
  granularity inside an attribute value, one level finer than element locations;
  ADR-0014 governs it, not this bead. Whether the DOM records
  attribute-value start positions (which is what would let an expression span be
  translated into a document line/column) is an open question below.
- **`docs/testing.md`** - every new test asserting `lib/` behavior needs a
  sabotage line (`# sabotage: <what was broken> -> red`). New internal tests are
  automatically covered by the regression ratchet's globbed `internal_tests`
  list. Scratch dirs use `@tag :isolated_tmp_dir`.
- **CLAUDE.md conventions** - `@spec` on public functions, structs + MapSets,
  `{:ok, v} | {:error, e}` returns with no rescue-to-default at leaves, XML in
  tests as triple-quoted heredocs at 4-space base indentation.
- **`docs/workflow.md:121`** names "parser DOM" as an example of a good
  module-boundary split for parallel work.

## Architecture Documentation

The layer pipeline this bead sits in (`docs/architecture.md`):

```
XML string
   |  Parser (Saxy SAX -> generic DOM with source locations)   <- st-l5k.3
   v
DOM (element name, attrs, children, location)
   |  Lowering (typed per-element builders)                    <- st-l5k.4
   v
Document (typed structs, source locations, uncompiled expressions)
   |  Validator (structural + semantic checks)                 <- st-l5k.5
   |  Compiler (intern IDs, index hierarchy, compile expressions)
   v
Machine
```

Design principles bearing directly on this layer:

- **"Make invalid states unrepresentable"** (principle 4). The DOM is
  deliberately *not* validated - it is whatever the XML said. Validity is the
  `Document` -> `Machine` transition's job. A generic DOM that rejects unknown
  elements would be doing the validator's work in the parser.
- **"Errors are events"** (principle 3) applies to the interpreter, not the
  parser: `parse/1` returning `{:error, reason}` is the normal Elixir result
  convention, and there is no `error.execution` at parse time.
- **ADR-0002 (literal Appendix D port)** does not reach this layer - Appendix D
  starts at the interpreter.

Bead relationships (from `bd show`):

- Parent epic **st-l5k** "Phase 2: Parser - DOM first, typed lowering",
  0/4 children complete, depends on the completed st-00p (Phase 0 foundation)
  and blocks st-af3 (Phase 3: datamodel and error model).
- st-l5k.3 **blocks st-l5k.4** ("Lowers the DOM to Document structs").
- Siblings: st-l5k.2 (typed `Document` structs), st-l5k.5 (validator).

## Open Questions

These are recorded, not resolved. None blocks starting the work; each is a
decision the implementation plan has to make.

1. **How locations are obtained at all.** Saxy provides none, so the position of
   every `:start_element` must come from somewhere else. The options visible from
   here, none of which is chosen by any existing repo document: (a) an
   independent left-to-right scan of the source that records the offset of each
   markup construct in document order and is zipped against the SAX event
   sequence (needs to correctly skip comments, PIs, DOCTYPE, and CDATA to stay in
   sync); (b) `Saxy.Partial` chunk-feeding to bracket offsets; (c) v1's
   re-scan-per-element approach; (d) a different parser
   (`:xmerl_sax_parser` gives a line number per event but no column, and creates
   atoms). The bead does not name a mechanism, and picking one is the first
   design decision of the plan.

2. **What a `location` value contains.** Line and column only (v1's shape), or
   byte offset too, or a start/end span? ADR-0014 chose spans with exclusive ends
   (LSP-compatible) for *expressions*; whether DOM element locations adopt the
   same span shape for consistency, or stay points, is unsettled. A span would
   need an end position, which the SAX stream does not directly give either.

3. **Attribute-level locations.** The bead's node shape is
   `(name, attributes, children, location)` - one location per node. v1 recorded
   per-attribute locations (line only, no column). Whether v2's DOM records
   attribute positions, and if so in what shape, is not stated. This matters
   downstream: ADR-0014's expression spans are relative to an expression string
   that lives inside an attribute value, so translating a span into a document
   position requires knowing where that attribute value starts.

4. **Text nodes and comments in the DOM.** `children` is described as holding
   child elements. Whether character data becomes a node in `children` (with its
   own location), a separate field on the parent, or is dropped, is unspecified.
   The corpus needs text content at least for `<content>` and `<data>` (v1's
   `handle_characters/2` handles exactly those two). Whether comments and PIs
   appear in the DOM at all is likewise unspecified - Saxy does not emit events
   for them, so keeping them would require the location mechanism to surface
   them separately.

5. **Whitespace policy.** Saxy emits untrimmed `:characters` for every bit of
   inter-element whitespace, and the corpus is full of it. Whether the DOM
   preserves it verbatim (correct, but noisy) and lowering discards it, or the
   handler drops whitespace-only text, is a decision with a location cost either
   way.

6. **Where XML normalization lives.** v1's `normalize_xml/2` injects `xmlns` and
   `version` into `<scxml>` before parsing - both SCXML-specific, and both
   distort the locations of everything after them. A generic DOM parser cannot
   do this (it would be an SCXML-specific clause). Whether v2 needs the
   relaxed-input behavior at all, and if so whether it moves to lowering or is
   dropped, is not addressed by any bead in the epic.

7. **Error shape.** The bead requires `{:error, reason}` "with position info".
   Whether `reason` is the raw `%Saxy.ParseError{}` (byte offset), a v2 error
   struct with `{line, column}` derived from it, or a tuple, is unsettled. Note
   that a `{:bad_return, ...}` reason arrives with `binary: nil, position: nil`
   in at least some cases (observed upstream in qcam/saxy issue #32), so a
   converter has to tolerate a missing position.

8. **Namespaces.** Saxy does no namespace processing, so `xmlns` is an ordinary
   attribute and prefixed names arrive as literal strings. The corpus never
   exercises prefixes, so nothing forces a decision, but whether the generic DOM
   stores raw names (generic, matching Saxy) or resolves prefixes (which would
   require namespace machinery in the handler) is open.

9. **Malformed-input surface for tests.** The acceptance criterion "malformed
   XML returns `{:error, reason}` with position info" spans five distinct
   `Saxy.ParseError` reasons (`:token`, `:wrong_closing_tag`, `:invalid_pi`,
   `:invalid_encoding`, `:bad_return`). Which of them the internal test suite
   must cover is not specified.
