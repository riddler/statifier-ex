# Research: log expr, donedata content/param, and one event-data coercion function

**Date**: 2026-08-13T19:55:40-0600
**Git Commit**: 4558cbe71139cab6c449676b0be75f7124990faf
**Branch**: st-af3.7-log-donedata-coercion
**Bead**: st-af3.7

## Research Question

st-af3.7 covers four things. As the codebase exists today, where does each of
them sit?

1. `Log.value/1` returns `nil` for a `{:compiled, ...}` expr; it must evaluate
   against the macrostep context, and a failed evaluation must reach the block
   runner as `{:error, reason}` rather than logging a placeholder.
2. `static_donedata/2`'s `{:compiled, ...}` arm must be evaluated at both call
   sites - `raise_parent_completion/3`'s `done.state.*` data and
   `exit_interpreter/1`'s `Effect.Done` / `Trace.Done` donedata.
3. `<param>` under `<donedata>` currently lowers as
   `{:unsupported_element, "param"}`; it needs name + expr/location lowering,
   evaluation at done time, and merging into the done event data map.
4. ONE shared coercion/normalization function for event data, with defined
   rules, used by `<param>` and `<content>` here and by
   namelist / `<send>` / `<invoke>` later.

The map below covers: the evaluation-context construction seam, the block
runner's error path, both donedata call sites and their data shape, the
lowering pipeline and where a `<param>` builder would slot in, existing
normalization behavior, the normative spec text, and the corpus coverage.

## Summary

Everything st-af3.7 needs to call already exists and is exercised by four
sibling elements. `Statifier.Evaluator.context/1` and
`Statifier.Evaluator.evaluate/2` are the single evaluation seam; the
executable-content block runner already carries a fatal `{:error, reason}`
channel and a non-fatal `pending_errors` channel, both converging on one
`raise_platform(machine_state, "error.execution", origin, data: reason)` call.
Five call sites already evaluate a `{:compiled, ...}` expr through that seam
(`<data>`, `<assign>`, `<if>`, `<foreach>`, transition `cond`).

The two sites named by the bead are the only two left carrying a compiled
expr with no evaluation, and both carry a comment saying so:

- [`lib/statifier/machine/content/log.ex:54-65`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content/log.ex#L54-L65) - `value/1`'s
  `{:compiled, _, _}` clause returns `nil`. `Log.execute/2`'s `@spec` admits
  only `{:ok, Context.t(), [{:log, Effect.Log.t()}]}`; the node has no error
  arm at all today, though the protocol's `result/0` type already permits
  both `{:error, term()}` and `{:error, Context.t(), term()}`.
- [`lib/statifier/interpreter/exit_entry.ex:871-878`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/exit_entry.ex#L871-L878) - `static_donedata/2`'s
  `{:compiled, _, _}` clause returns `nil`. It is `def` rather than `defp`
  precisely because `Statifier.Interpreter.exit_interpreter/1` is its second
  caller.

The two donedata call sites differ structurally in a way that matters:
`raise_parent_completion/3` folds donedata *inside* a `MachineState`-threading
function that can enqueue an `error.execution` (it already calls
`raise_platform/4`), while `exit_interpreter/1` folds it inside an
`Enum.reduce` over the exit set with no event queue left to drain - the
machine's `status` becomes `:done` on the next line.

`<param>` is genuinely absent: no `"param"` key in the lowering `@dispatch`
map, no `Document.Param`, no `Machine` counterpart, no `place/3` clause. The
`<donedata>` document struct has a single `content` slot, not a list.

No shared event-data coercion function exists. Value handling today is a set
of narrow, spec-cited, per-site checks, and the only general normalization is
predicator's own: `Predicator.Context.new/2` deep-normalizes `nil` to
`:undefined` on the way *in*, and `Evaluator.evaluate/2`'s `{:static, v}` arm
deliberately bypasses that entirely.

## Detailed Findings

### The evaluation-context seam

`Statifier.Evaluator` is one module with two public functions.

`Evaluator.context/1` ([`lib/statifier/evaluator.ex:97-103`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/evaluator.ex#L97-L103)) builds the
context from a `MachineState`:

```elixir
def context(%MachineState{} = machine_state) do
  Predicator.Context.new(machine_state.datamodel,
    functions: %{"In" => {1, in_function(machine_state)}},
    on_unbound: :error
  )
end
```

`In/1` ([`lib/statifier/evaluator.ex:142-151`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/evaluator.ex#L142-L151)) closes over
`machine_state.machine` and `machine_state.configuration` at build time, so
the context is a position snapshot. `on_unbound: :error` makes an unbound
identifier a hard evaluation error.

`Evaluator.evaluate/2` ([`lib/statifier/evaluator.ex:121-133`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/evaluator.ex#L121-L133)) handles both
arms of `Machine.expr/0` ([`lib/statifier/machine.ex:90`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine.ex#L90)):

```elixir
def evaluate(%Predicator.Context{}, {:static, value}), do: {:ok, value}

def evaluate(
      %Predicator.Context{} = context,
      {:compiled, %Predicator.Compiled{} = compiled, source}
    ) do
  case Predicator.evaluate(compiled, context) do
    {:ok, value} -> {:ok, value}
    {:error, error} -> {:error, Error.new(source, error)}
  end
end
```

The error shape is `%Statifier.Evaluator.Error{source:, error:, span:}`
([`lib/statifier/evaluator/error.ex:42-45`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/evaluator/error.ex#L42-L45)), wrapping predicator's own error
struct verbatim and carrying a span when predicator attributes one
(ADR-0014 item 2).

**Interval**: the context is built once per evaluation site, never once per
macrostep - [`docs/datamodel.md:48-53`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/docs/datamodel.md#L48-L53) states the reason. The sites:

| Site | Where the context is built |
|---|---|
| executable-content block | [`lib/statifier/interpreter/content.ex:140-145`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/content.ex#L140-L145) |
| datamodel binding pass | [`lib/statifier/interpreter/datamodel.ex:133`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/datamodel.ex#L133) |
| late binding per state | [`lib/statifier/interpreter/datamodel.ex:292`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/datamodel.ex#L292) |
| transition `cond` | [`lib/statifier/interpreter/selection.ex:285`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/selection.ex#L285) |

`Statifier.ExecutableContent.Context`
([`lib/statifier/executable_content/context.ex:63-71`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/executable_content/context.ex#L63-L71)) carries the built
context to every node in a block:

```elixir
@enforce_keys [:machine_state, :owner, :datamodel_context]
defstruct [:machine_state, :owner, :datamodel_context, pending_errors: []]
```

`Assign.execute/2` ([`lib/statifier/machine/content/assign.ex:76-91`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content/assign.ex#L76-L91)) and
`Foreach`'s `rebuild/2` ([`lib/statifier/machine/content/foreach.ex:276-285`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content/foreach.ex#L276-L285))
both rebuild `datamodel_context` after a write so a later node in the same
block sees it.

**Important for donedata**: neither donedata call site is inside an
executable-content block, so neither has an `ExecutableContent.Context` to
borrow. Both would build their own via `Evaluator.context/1` from the
`MachineState` they already hold.

### The block runner and its error path

`Statifier.Interpreter.Content.execute_block/3`
([`lib/statifier/interpreter/content.ex:135-162`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/content.ex#L135-L162)) builds one context, runs
`run_nodes/2`, and converts a returned error.

`run_nodes/2` (`content.ex:172-193`) folds with `Enum.reduce_while/3` over
three result shapes:

- `{:ok, new_context, node_effects}` - drain pending, continue.
- `{:error, new_context, reason}` - composite-node failure; drains
  `new_context.pending_errors`, halts, keeps the produced `machine_state`.
- `{:error, reason}` - leaf failure; halts on the *pre-call* context.

The failing `c_index` is appended to `executed` in both error arms, so
`Trace.ContentExecuted` names it.

`drain_pending/2` (`content.ex:202-212`) is the non-fatal channel (spec
5.9.1): a node appends a reason to `pending_errors` instead of halting, and
the runner turns each into an `error.execution` after that node.

Both channels converge on one private function
(`content.ex:229-239`):

```elixir
defp raise_execution_error(machine_state, owner, c_index, reason) do
  MachineState.raise_platform(machine_state, "error.execution", {:content, c_index, owner},
    data: reason
  )
end
```

The protocol's result type already admits the error shapes
([`lib/statifier/executable_content.ex:73-76`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/executable_content.ex#L73-L76)):

```elixir
@type result ::
        {:ok, Context.t(), [Effect.t()]}
        | {:error, term()}
        | {:error, Context.t(), term()}
```

Per the protocol moduledoc (`executable_content.ex:28-51`), a node never
constructs a `Statifier.Event` and never raises; converting a failure into
`error.execution` is the block runner's job (ADR-0003).

`MachineState.raise_platform/4` ([`lib/statifier/machine_state.ex:398-413`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine_state.ex#L398-L413))
builds `Cause.new(origin, macrostep, microstep, round)`, wraps it in
`Event.platform(name, cause, opts)` ([`lib/statifier/event.ex:82-85`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/event.ex#L82-L85), which
reads `data:` out of `opts`), and enqueues internally. There is no `/3`
arity - `opts \\ []` is a default.

`"error.execution"` is constructed at exactly three places in `lib/`:
[`lib/statifier/interpreter/content.ex:236`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/content.ex#L236) (block runner),
[`lib/statifier/interpreter/selection.ex:529`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/selection.ex#L529) (transition `cond`), and
[`lib/statifier/interpreter/datamodel.ex:312`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/datamodel.ex#L312) (`<data>` binding failure).

`Assign.execute/2` (`assign.ex:76-91`) is the closest precedent for a node
whose evaluation can fail: a `with` chain whose implicit `else` returns the
first `{:error, reason}` unchanged. It never names `"error.execution"`.

### `<log>` today

[`lib/statifier/machine/content/log.ex:37-52`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content/log.ex#L37-L52) builds the effect
unconditionally and returns `{:ok, context, [{:log, log_effect}]}`; its
`@spec` names only that shape. `value/1` (`log.ex:62-65`):

```elixir
defp value(%Log{expr: nil}), do: nil
defp value(%Log{expr: {:static, term}}), do: term
defp value(%Log{expr: {:compiled, _compiled, _source}}), do: nil
```

The comment above it (`log.ex:54-61`) states the `nil` is "not a
rescue-to-default, nothing failed, the expression simply has not been
evaluated yet", and points at `static_donedata/2` as the matching site.

`Statifier.Effect.Log` ([`lib/statifier/effect/log.ex:23-32`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/effect/log.ex#L23-L32)) types `value`
as `term()`, so a real evaluated value needs no struct change:

```elixir
@enforce_keys [:macrostep, :microstep]
defstruct [:label, :value, :c_index, :owner, :macrostep, :microstep]
```

A test pins the current behavior explicitly:
[`test/statifier/executable_content_test.exs:163-169`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/test/statifier/executable_content_test.exs#L163-L169), "compiled expr `<log>`
carries nil (evaluation not yet implemented)", with its own sabotage note.

### The two donedata call sites

**Site 1 - `raise_parent_completion/3`**
([`lib/statifier/interpreter/exit_entry.ex:782-807`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/exit_entry.ex#L782-L807)), reached from
`raise_completion_events/2` (`exit_entry.ex:748-764`) which
`exit_states/2` (`exit_entry.ex:656`) calls per exiting state:

```elixir
MachineState.raise_platform(
  machine_state,
  "done.state." <> parent_id,
  {:state, state_index},
  data: static_donedata(machine, state_index)
)
```

The `parent == 0` (top-level final) branch of `raise_completion_events/2`
raises nothing and only sets `running: false` (`exit_entry.ex:756-757`).

`maybe_raise_grandparent_completion/3` (`exit_entry.ex:821-854`) raises
`done.state.<grandparent_id>` for a completed `:parallel` with **no `data:`
option at all** and never calls `static_donedata/2` - matching Appendix D,
where the grandparent event is `new Event("done.state." + grandparent.id)`
with no donedata argument (`appendix-d.txt:329`).

**Site 2 - `exit_interpreter/1`** ([`lib/statifier/interpreter.ex:674-719`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter.ex#L674-L719))
folds donedata inline inside the exit-order reduce:

```elixir
donedata =
  if Machine.final?(machine, state_index) and Machine.at(machine, state_index).parent == 0 do
    ExitEntry.static_donedata(machine, state_index)
  else
    donedata
  end
```

and threads that one local into both `Effect.Trace.Done` (`donedata:`,
`configuration:`) and `Effect.Done` (`donedata:`, `configuration:`,
`macrostep:`, `microstep:`), built from the same locals so they cannot
disagree (comment at `interpreter.ex:661-668`). `machine_state.status`
becomes `:done` immediately after.

**The fold** (`exit_entry.ex:871-878`):

```elixir
def static_donedata(machine, state_index) do
  case Machine.at(machine, state_index).donedata do
    nil -> nil
    %Donedata{expr: nil} -> nil
    %Donedata{expr: {:static, term}} -> term
    %Donedata{expr: {:compiled, _predicator_compiled, _source}} -> nil
  end
end
```

**Data shape.** Both effects type `donedata` as `term() | nil`
([`lib/statifier/effect/done.ex:21-29`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/effect/done.ex#L21-L29),
[`lib/statifier/effect/trace/done.ex:19-40`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/effect/trace/done.ex#L19-L40)) - the untagged value, never the
`Machine.Donedata` struct and never the `{:static, _}` tuple. For site 1 the
value lands on `%Statifier.Event{data: ...}`
([`lib/statifier/event.ex:38-51`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/event.ex#L38-L51)) and reaches the datamodel through
`MachineState.put_event/2` (`machine_state.ex:345-347`) ->
`Evaluator.SystemVariables.event/1`
([`lib/statifier/evaluator/system_variables.ex:68-79`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/evaluator/system_variables.ex#L68-L79)), which copies
`event.data` verbatim into `_event["data"]`. Site 2 never raises an event,
so its donedata never becomes `_event.data`.

**Structs.** `Statifier.Machine.Donedata`
(`lib/statifier/machine/donedata.ex`):

```elixir
@enforce_keys [:location]
defstruct [:location, expr: nil, expr_location: nil]
```

It has no `c_index`: `<donedata>`'s payload is not executable content and no
block ever runs it ([`lib/statifier/machine/content.ex:25-28`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content.ex#L25-L28)). It is compiled
by its own pass, `build_donedata_map/1` / `build_donedata/2`
([`lib/statifier/compiler.ex:998-1053`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/compiler.ex#L998-L1053)), keyed by owning `:final` state index,
and attached by `with_donedata/2` (`compiler.ex:262-269`).

`Statifier.Document.Donedata` (`lib/statifier/document/donedata.ex`) has a
single `content` slot:

```elixir
@enforce_keys [:location]
defstruct [:location, content: nil]
```

`<content>`'s fold to a `Machine.expr()` (`compiler.ex:1041-1053`):

```elixir
defp build_content_expr(%DContent{expr: nil, text: text}, _owner),
  do: {:ok, Expressions.static(text)}

defp build_content_expr(%DContent{expr: source} = content, owner) do
  Expressions.compile(source, owner, content_expr_location(content))
end
```

So `<content>foo</content>` becomes `{:static, "foo"}` - the raw, untrimmed
text, no parse attempt. Only `<content expr="...">` becomes `{:compiled, ...}`.
Note the asymmetry with `<data>`'s inline content, which *does* get a
parse-then-string-literal ladder at compile time in
`Expressions.inline_value/1` ([`lib/statifier/compiler/expressions.ex:118-126`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/compiler/expressions.ex#L118-L126)).

`Statifier.Machine.Content` is **not** the compiled `<content>` element - it
is the executable-content node family (`Raise`, `Log`, `Assign`, `If`,
`Foreach`). `<content>` under `<donedata>` has no compiled struct of its own.

### The lowering pipeline and the `<param>` slot

`Statifier.Lowering`'s `@dispatch` map ([`lib/statifier/lowering.ex:53-74`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/lowering.ex#L53-L74))
holds 20 entries; there is no `"param"` key. `walk_child/4`
(`lowering.ex:138-156`) produces `{:unsupported_element, name}` via
`Error.unsupported/2` at `lowering.ex:151` for any miss, at the child's own
location. Dispatch is context-free: a builder never knows its parent's name
(`lowering.ex:26-35`).

Tagged results are consumed only by `Builders.place_children/3`
([`lib/statifier/lowering/builders.ex:717-724`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/lowering/builders.ex#L717-L724)) and its `place/3` clauses
(`builders.ex:711-850`). Relevant clauses: `{:donedata, donedata}` onto
`%State{}` (`builders.ex:756-758`), `{:content, content}` onto `%Donedata{}`
(`builders.ex:772-774`), `{:content_node, node}` onto `%Block{}` /
`%Transition{}` / `%Foreach{}` (`builders.ex:784-790`, `825-827`). The
generic catch-all (`builders.ex:848-850`) derives the element name from the
tag atom and reports `{:misplaced_element, ...}`.

`build_donedata/2` (`builders.ex:279-288`) calls `walk_children/2` then
`place_children/3` with no `reverse_lists/1` - it has only the single
`content` slot, not a list.

`build_content/2` (`builders.ex:308-326`) is the one builder that bypasses
`walk_children/2` entirely, reading `element.children` directly because
`<content>`'s text is its payload; element children become
`{:misplaced_element, name, "content"}`.

`build_log/2` (`builders.ex:246-265`) is the simplest builder: unconditional
struct construction, no required attribute.

**Required attributes** have no helper. Every builder does the same inline
`case Attributes.value(element, "x") do nil -> ... end`. The first instance
and the one every later doc cites is `build_raise/2` (`builders.ex:217-237`);
`build_foreach/2` (`builders.ex:617-660`) shows the two-required-attributes
variant that reports both misses rather than short-circuiting.

**Mutually exclusive attribute pairs** are deliberately *not* enforced in
lowering. Both fields stay nilable and simultaneously representable so a
validator check can report the shape:

- `<data>`'s `expr`/`src`: [`lib/statifier/document/data.ex:12-19`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/document/data.ex#L12-L19) +
  `Statifier.Validator.Checks.Data.expr_and_src_errors/1`
  ([`lib/statifier/validator/checks/data.ex:84-89`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/validator/checks/data.ex#L84-L89)).
- `<content>`'s `expr`/`text`: [`lib/statifier/document/content.ex:23-29`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/document/content.ex#L23-L29) +

### Existing normalization behavior

There is no shared coercion function. What exists:

- **`nil` -> `:undefined`**: entirely inside `Predicator.Context.new/2`,
  deep and recursive. Statifier never does it itself. The comment the bead
  points at, [`lib/statifier/interpreter/datamodel.ex:55-60`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/datamodel.ex#L55-L60), verbatim:

  > Seed: `Map.put_new(datamodel, id, nil)` for every `%Machine.Data{}` in
  > `machine.data_elements`, regardless of binding - 5.3.3 makes *creation*
  > unconditional under both bindings, and `Predicator.Context.new/2`
  > normalizes `nil` to `:undefined` recursively, so a seeded-but-unbound id
  > answers `=== undefined`/`!== undefined` rather than raising
  > `UndefinedVariableError` (Decision 3).

- **`{:static, v}` bypasses normalization**: `Evaluator.evaluate/2`'s first
  clause returns `v` untouched, never through predicator. So a
  `<content>foo</content>` donedata value is the raw untrimmed source text,
  and a `<log expr>`-less static value is whatever the compiler wrapped.

- **Non-boolean `cond`** (spec 5.9.1): implemented twice, independently -
  [`lib/statifier/interpreter/selection.ex:294-311`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/interpreter/selection.ex#L294-L311)
  (`{:error, {:non_boolean_cond, other}}`) and
  [`lib/statifier/machine/content/if.ex:143-161`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content/if.ex#L143-L161) (appends to `pending_errors`).

- **`<data>` inline content**: `Expressions.inline_value/1`
  ([`lib/statifier/compiler/expressions.ex:118-126`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/compiler/expressions.ex#L118-L126)) trims, compiles and
  evaluates at compile time against an empty `on_unbound: :error` context; on
  any failure falls back to `{:static, trimmed_text}`. This is the closest
  existing thing to a B.2.1-style ladder, and it runs at compile time, not at
  event time.

- **`_event` shape**: `SystemVariables.event/1`
  ([`lib/statifier/evaluator/system_variables.ex:68-79`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/evaluator/system_variables.ex#L68-L79)) stringifies
  `event.type` and passes `event.data` through untouched;
  `sendid`/`origin`/`origintype`/`invokeid` are always `nil`.

- **`<foreach>` iterability**: `Foreach.check_iterable/1`
  ([`lib/statifier/machine/content/foreach.ex:188-190`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/machine/content/foreach.ex#L188-L190)) requires `is_list/1`.

### What the spec says normatively

Read from the local cache (`$(git rev-parse --path-format=absolute
--git-common-dir)/spec-cache/scxml-rec.html` and `appendix-d.txt`).
Section numbering in the REC is **5.5 `<donedata>`, 5.6 `<content>`, 5.7
`<param>`** - the bead's "spec 5.7" is `<param>`.

**5.5 `<donedata>` children** (normative):

> A conformant SCXML document MUST specify either a single `<content>`
> element or one or more `<param>` elements as children of `<donedata>`, but
> not both.
>
> In cases where the SCXML Processor generates a 'done' event upon entry into
> the final state, it MUST evaluate the `<donedata>` elements `<param>` or
> `<content>` children and place the resulting data in the _event.data field.
> The exact format of that data will be determined by the data model (see B
> Data Models for details). In other cases (namely when the `<final>` element
> is a child of `<scxml>` and the state machine has not been triggered by
> `<invoke>`), the SCXML Processor SHOULD return the data to the environment
> in an implementation-dependent manner.

That last sentence is exactly the split the codebase already has:
`raise_parent_completion/3` is the `_event.data` case,
`exit_interpreter/1` is the "return the data to the environment" case
(`Effect.Done`).

**5.6 `<content>`** - `expr` "must not occur with child content", and:

> When the SCXML Processor evaluates the `<content>` element, if the 'expr'
> value expression is present, the Processor MUST evaluate it and use the
> result as the output of the `<content>` element. If the evaluation of
> 'expr' produces an error, the Processor MUST place error.execution in the
> internal event queue and use the empty string as the value of the
> `<content>` element. If the 'expr' attribute is not present, the Processor
> MUST use the children of `<content>` as the output.

**5.7 `<param>`** - `name` required (NMTOKEN), `expr` "May not occur with
'location'", `location` "May not occur with 'expr'":

> A conformant SCXML document MUST specify either the 'expr' attribute of
> `<param>` or the 'location' attribute, but MUST NOT specify both. If the
> 'location' attribute does not refer to a valid location in the data model,
> or if the evaluation of the 'expr' produces an error, the SCXML Processor
> MUST place the error 'error.execution' on the internal event queue and MUST
> ignore the name and value.

**B.2.8.1 `_event.data`** - the normative source for a coercion function's
rules:

> _event.data is populated with content provided by an external event or by
> `<param>` or `<content>`. In some circumstances, the entity that generated
> the event may have indicated how the data is to be interpreted. In such
> cases, the Processor SHOULD try to format the data according to those
> indications. Otherwise, if the SCXML Processsor can interpret the content
> as key-value pairs, then for each unique key, the Processor MUST create a
> property of _event.data whose name is the name of the key-value pair and
> whose value is the value of the key-value pair. In the case of duplicate
> keys, the behavior is platform-specific. (Note that content specified by
> `<param>` or delivered as POST parameters via the BasicHTTP Event I/O
> Processor consists unambiguously of key-value pairs.) Otherwise (i.e., if
> the content does not consist of key-value pairs), if the Processor supports
> JSON and it can interpret the content as JSON, it MUST create the
> corresponding ECMAScript object(s) as the value of _event.data. Otherwise,
> if the Processor can interpret the content as a valid XML document, it MUST
> create the corresponding DOM structure and assign it as the value
> _event.data. Otherwise, the Processor MUST treat the content as a
> space-normalized string literal and assign it as the value of _event.data.

**B.2.6 `<content>`**:

> When `<content>` is a child of `<donedata>`, the Processor MUST interpret
> its value as defined in B.2.8.1 _event.data.

**5.10.1, the `data` field of an event**:

> data. This field contains whatever data the sending entity chose to include
> in this event. The receiving SCXML Processor SHOULD reformat this data to
> match its data model, but MUST NOT otherwise modify it. If the conversion
> is not possible, the Processor MUST leave the field blank and MUST place an
> error 'error.execution' in the internal event queue.

**4.7 `<log>`** - `expr` is "An expression returning the value to be logged",
and:

> The manner in which the message is displayed or logged is
> platform-dependent. The SCXML processor MUST ensure that `<log>` has no
> side-effects on document interpretation.

There is no normative text making a failed `<log expr>` special; 5.9.4's
general rule and the executable-content error model apply.

**Appendix D** - `exitInterpreter()` (`appendix-d.txt:169-178`) calls
`returnDoneEvent(s.donedata)`, and `enterStates`'s final-state branch
(`appendix-d.txt:326-330`) enqueues
`new Event("done.state." + parent.id, s.donedata)` and, for the parallel
grandparent, `new Event("done.state." + grandparent.id)` with no donedata.
Neither pseudocode block spells out *when* donedata is evaluated - the prose
in 5.5 does.

## Architecture Documentation

- **ADR-0002** (literal Appendix D port): the pseudocode names `s.donedata`
  as an argument but never says when it is evaluated, so 5.5's prose is the
  port source here, not a pseudocode block. Both existing donedata sites
  already deviate mechanically (the fold happens at the raise site rather
  than at struct-construction time) with the reason in a comment.
- **ADR-0003** (pure core with effects): `{:log, ...}` and `{:done, ...}` are
  the effect vocabulary. A node returns an error; only the block runner turns
  it into an event. `<log>` "has an effect and nothing else"
  (`log.ex:34-36`).
- **ADR-0004** (predicator as the datamodel): every expression here goes
  through `Statifier.Evaluator`, never `eval`.
- **ADR-0005** (interned indices): `<param>`'s `name` is a string key in
  event data, not an interned index - event data keys are a document-facing
  surface, like state ids at the `Statifier` boundary.
- **ADR-0012** (debuggability): `Effect.Log` and `Trace.Done` carry
  `macrostep`/`microstep` (and `round` on the trace); a real evaluated value
  changes what those effects carry, not their shape.
- **ADR-0014 item 2** (expression spans): `Evaluator.evaluate/2` already
  produces span-carrying errors; a `<log>` or `<content>` failure inherits
  that for free via `expr_location`.
- **Layer division**: lowering keeps mutually-exclusive attributes
  representable and the validator reports the shape. `docs/architecture.md`
  principle 4 makes the validator the pipeline's only gate, which is why
  `raise_parent_completion/3` keeps a defense-in-depth id guard.

## Open Questions

No human was available to resolve these; they are recorded here for the
planning step.

1. **`<content expr>` failure: empty string or no data?** The bead says "a
   failed evaluation raises error.execution and the done event carries no
   data (spec 5.7)". Spec 5.7 says that for `<param>` ("MUST ignore the name
   and value"), but spec 5.6 says the opposite for `<content>`: "use the
   empty string as the value of the `<content>` element". The two elements
   have different failure results in the normative text. Which one the done
   event carries for a failed `<content expr>` is a decision.
   `test/scxml_tests/mandatory/content/test528_test.exs` is the file that
   pins it, and its cond reads `_event.data === undefined`, not
   `_event.data == ''`. That spelling is not a rewrite artifact: it is the
   W3C `conf:emptyEventData` macro, and
   [`tools/corpus/scxml_w3/exclusions.exs:8-13`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/tools/corpus/scxml_w3/exclusions.exs#L8-L13) records the choice to emit it
   as `=== undefined` against predicator 5.0's `undefined` literal. So the
   W3C test suite itself treats a failed `<content expr>` as *empty event
   data*, which is 5.7's `<param>` rule rather than 5.6's stated "empty
   string". Following the test (empty data) contradicts 5.6's letter;
   following 5.6 reddens test528. This needs a decision with the clause
   quoted either way.

2. **What does the coercion function actually take and return?** B.2.8.1's
   ladder (indicated format -> key-value pairs -> JSON -> XML DOM ->
   space-normalized string literal) is written for the ECMAScript data model.
   Predicator has no DOM and no JSON step is present in this tree today. The
   nearest existing analogue is compile-time
   `Expressions.inline_value/1` (parse-or-string-literal), which runs in the
   compiler, not at event time. Which rungs of B.2.8.1 the one function
   implements, and whether it runs at compile time or event time, is
   undecided.

3. **Does `{:static, v}` go through the coercion function?** Today it
   deliberately bypasses predicator entirely (st-af3.1's decision), so
   `<content>foo</content>` yields the raw untrimmed `"foo"` while
   `<content>21</content>` yields the string `"21"`. **test529 asserts
   `_event.data == 21`, the integer** - so at least for inline `<content>`
   text, the corpus requires a parse step that the `{:static, v}` path does
   not perform today. `Expressions.inline_value/1` already implements exactly
   that ladder for `<data>` inline content, at compile time, and
   `build_content_expr/2` ([`lib/statifier/compiler.ex:1041-1043`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/lib/statifier/compiler.ex#L1041-L1043))
   deliberately does not call it. Whether the shared coercion function
   subsumes `inline_value/1`, whether it runs at compile or event time, and
   whether it changes the existing `{:static, v}` bypass the st-af3.1 plan
   chose on purpose, is undecided. Note this also touches
   `test/statifier/machine/content_test.exs`'s
   `"a <donedata><content>text</content></donedata> holds {:static, text}"`
   and `test/statifier/interpreter/termination_test.exs`'s
   `%Effect.Done{donedata: "42"}` assertion, both of which pin the string
   form.

4. **`<param location>` needs a location-expression read, not a value
   evaluation.** `Predicator.context_location/3` exists and `<assign>` uses
   it (`lib/statifier/machine/content/assign.ex`), but no read-only "resolve
   a location and fetch its value" path exists yet, and spec 5.7's failure
   mode is "does not refer to a valid location" rather than an evaluation
   error. Whether `<param location>` lands in this bead or with
   `<send>`/`<invoke>` is unstated - the bead says the lowering should be
   shaped for reuse but does not say whether `location` evaluates now.

5. **Multiple `<param>` merge order and duplicate keys.** B.2.8.1: "In the
   case of duplicate keys, the behavior is platform-specific." No project
   decision exists. `Document.Donedata` has a single `content` slot and would
   need a `params` list plus a `reverse_lists/1` call in `build_donedata/2`.

6. **The `<content>`-xor-`<param>` rule is a new validator check.** Spec 5.5
   makes "either one `<content>` or one-or-more `<param>`, not both" a
   conformance requirement. `Checks.Content` and `Checks.Donedata` exist but
   neither covers it. Whether it becomes a third check or an arm of
   `Checks.Donedata` is undecided.

7. **The corpus stays red regardless.** All seven donedata tests also carry
   `:conditional_transitions`, still `:unsupported` in the registry
   ([`test/support/feature_detector.ex:68`](https://github.com/riddler/statifier-ex/blob/4558cbe71139cab6c449676b0be75f7124990faf/test/support/feature_detector.ex#L68)), and the `<content>`/`<param>`
   regexes flag `send_content_elements`/`send_param_elements` regardless of
   the parent element. Whether this bead flips those registry entries,
   splits the regexes by parent, or leaves the corpus untouched and proves
   the behavior with internal tests only is a decision - and it determines
   whether the bead can move any file into `test/passing_tests.json`.

8. **Where the donedata evaluation error goes at `exit_interpreter/1`.**
   Site 1 can enqueue an `error.execution` because it is already threading a
   `MachineState` through `raise_platform/4` before the queue drains. Site 2
   runs after the event loop has stopped and sets `status: :done` on the next
   line, so an `error.execution` enqueued there would never be dequeued. Spec
   5.6/5.7 both say MUST place it on the internal queue. Whether site 2
   enqueues it anyway (observable in the final `MachineState`), emits it as
   an effect, or drops it is undecided.
