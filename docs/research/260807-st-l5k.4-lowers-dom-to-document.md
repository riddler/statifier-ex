# Research: Lowering the generic DOM to typed Document structs (st-l5k.4)

**Date**: 2026-08-07T17:38:48-0600
**Git Commit**: 0f4e97ad4d2341df08a9da9c9eb3826992001dd3
**Branch**: st-l5k.4-lowers-dom-to-document
**Beads Issue**: st-l5k.4

## Research Question

st-l5k.4 asks for a separate lowering pass from the generic DOM (st-l5k.3) to the
typed Document structs (st-l5k.2): one builder function per element, so that adding
an element touches one builder rather than a clause matrix. This document records
what the two input layers actually expose today, what each Document struct requires,
where the Phase 1 / Phase 3 element boundary falls, what error machinery exists (and
does not exist), and how the surrounding tests are written - so the plan stage has
ground truth rather than assumptions.

## Summary

Both input layers are landed on `main` and are complete for this purpose.

The **DOM** (`lib/statifier/parser/dom.ex` plus three node structs) is deliberately
unvalidated and namespace-dumb. It hands the lowering pass elements with raw
qualified names, an ordered attribute list with duplicates preserved, an ordered
child list interleaving elements and text runs, and a six-field `Location` span on
every node. Attributes carry *two* spans - `location` for `name="value"` and
`value_location` for the quoted text - and `value_location` is the one the Document
layer stores. Three accessors exist and are the only ones: `DOM.elements/1`,
`DOM.attribute/2`, `DOM.text/1`.

The **Document** layer (`lib/statifier/document.ex` plus eight structs) is
data-only: `@enforce_keys`, `defstruct`, `@type t`, no functions. It expects lowering
to do all tokenization and defaulting. `Transition.event` and `Transition.target` are
already-split `[String.t()]`; `type` defaults to `:external`, `Document.binding` to
`:early`, and `State.history_type` is `:shallow | :deep | nil`. The layer's central
contract is `attribute_locations`: a `%{atom() => Location.t()}` map holding **value
spans only**, with an entry **only for an attribute the author actually wrote** -
which is what keeps "the default applied" distinguishable from "the author wrote the
default's value" after lowering applies `:external` / `:early` / `:shallow`.

Three findings bear directly on the plan and are not obvious from the bead:

1. **The lowering module cannot live under `lib/statifier/parser/` or under
   `lib/statifier/document/`.** Two existing guard tests forbid it, in opposite
   directions. `test/statifier/parser/generic_handler_test.exs:55` fails if any file
   matching `lib/statifier/parser/**/*.ex` contains a string literal equal to any
   SCXML element name - and a per-element builder dispatch map is nothing but those
   literals. `test/statifier/document/layer_test.exs:76` fails if any file matching
   `lib/statifier/document/*.ex` is not a struct module with an enforced `:location`
   field. A third namespace is required.

2. **No error-accumulation machinery exists anywhere in `lib/`.** The only error type
   in the whole library is `Statifier.Parser.ParseError` (`defexception`, single
   error, `[:reason, :message, :location, :byte_offset]`). The docs assign "all
   errors collected in one pass" to the *validator* (st-l5k.5), not to lowering, and
   the builder signature the l5k.2 research sketches is singular:
   `(dom_element, context) -> {:ok, struct} | {:error, error}`. The bead's criterion
   "multiple unsupported elements reported in one pass" therefore requires designing
   a new multi-error mechanism in this bead - it cannot be inherited.

3. **The "library-side mirror of the FeatureDetector contract" is a conceptual
   mirror, not a shared vocabulary, and cannot be a literal one.** `FeatureDetector`
   is harness code that `lib/` is explicitly forbidden to reference
   (`test/support/feature_detector.ex:6`). Its vocabulary is feature atoms
   (`:send_elements`, `:if_elements`), not element names; it carries no locations;
   and it has no atoms at all for `<elseif>`, `<else>`, or `<param>`-under-`<invoke>`.
   What transfers is the *rule* - fail loudly, name the thing, never skip - not the
   atoms.

## Detailed Findings

### 1. What the DOM hands the lowering pass

**Node shapes.** Three structs, all under `lib/statifier/parser/dom/`.

`Element` (`lib/statifier/parser/dom/element.ex:28-38`), enforcing all four keys:

| Field | Type | Notes |
|---|---|---|
| `name` | `binary()` | Raw qualified name, **prefix included** (`"pre:root"`) |
| `attributes` | `[Attribute.t()]` | Document order, **duplicates preserved** |
| `children` | `[Element.t() \| Text.t()]` | Document order, interleaved |
| `location` | `Location.t()` | `<` of start tag to byte after `>` of end tag |

`Text` (`lib/statifier/parser/dom/text.ex:21-27`): `value` (decoded, entities
expanded, CDATA unwrapped) and `location` (spans the **raw** source). One node per
run - Saxy's split events are coalesced.

`Attribute` (`lib/statifier/parser/dom/attribute.ex:23-31`): `name`, `value`
(entity-expanded), `location` (whole `name="value"`, quotes included, nilable), and
`value_location` (the text inside the quotes, nilable). The moduledoc states the
purpose of the second span explicitly: ADR-0014's expression arithmetic needs
`value_location.start_offset` to turn a within-expression span into a document
position. Both span fields are `Location.t() | nil` because the handler joins Saxy's
attribute list against the scanner's by index and tolerates a short scan
(`lib/statifier/parser/handler.ex:162-175`).

`Location` (`lib/statifier/parser/location.ex:13-37`): six enforced fields -
`start_line`, `start_column`, `start_offset`, `end_line`, `end_column`, `end_offset`.
1-based line/column (columns in Unicode codepoints), 0-based byte offsets, exclusive
end. Two public functions: `at_offset/2` and `slice/2`.

**Attribute access.** `DOM.attribute(element, name)` returns the **first** attribute
of that name or `nil` (`lib/statifier/parser/dom.ex:40-42`). "First, not only" is
deliberate - duplicates stay in `attributes` so the validator can report them. A
lowering builder that wants to notice a duplicate must read `element.attributes`
itself.

**Text and whitespace.** Whitespace is preserved verbatim, including whitespace-only
runs between child elements (`lib/statifier/parser.ex:21-24`). The parser cannot
know which vocabulary treats whitespace as significant, so it drops nothing.
`DOM.elements/1` (`lib/statifier/parser/dom.ex:29-31`) is the documented filter -
`Enum.filter(children, &match?(%Element{}, &1))` - and `DOM.text/1`
(`lib/statifier/parser/dom.ex:51-55`) concatenates the direct text children only,
ignoring the subtree. Those two accessors are the whole story: lowering will use
`elements/1` everywhere it walks structure, and `text/1` only inside `<content>`.

The bead's "non-whitespace stray text is an error with location" therefore needs
lowering to look at the *unfiltered* `children` list, not `DOM.elements/1`, and check
each `%Text{}` for `String.trim/1 == ""`. The `%Text{}` node's own `location` is what
the error names.

**What the DOM does not give.** No namespace resolution (a prefixed element arrives
as `"pre:root"` and `xmlns` is an ordinary attribute -
`test/statifier/parser_test.exs:254-261`); no comments or PIs (Saxy emits no events
for them); nothing outside the root element. Nothing is normalized or validated.

### 2. What each Document struct requires

All nine modules are data-only. Every one enforces `:location`; none defines a
function; none may reference `Predicator` (mechanically enforced,
`test/statifier/document/layer_test.exs:93`).

| Struct | Enforced | Fields lowering must fill | Defaults already applied by the struct |
|---|---|---|---|
| `Document` (`lib/statifier/document.ex:98-109`) | `:location` | `name`, `version`, `xmlns`, `datamodel`, `binding`, `initial`, `states`, `attribute_locations` | `binding: :early`, `initial: []`, `states: []`, `attribute_locations: %{}` |
| `State` (`document/state.ex:84-98`) | `:kind`, `:location` | `id`, `initial`, `initial_element`, `states`, `transitions`, `onentry`, `onexit`, `history_type`, `donedata` | `initial: []`, `states: []`, `transitions: []`, `onentry: []`, `onexit: []`, `history_type: nil`, `donedata: nil` |
| `Transition` (`document/transition.ex:43-52`) | `:location` | `event`, `cond`, `target`, `type`, `content` | `event: []`, `target: []`, `type: :external`, `content: []` |
| `Initial` (`document/initial.ex:34-35`) | `:location` | `transitions` | `transitions: []` |
| `Block` (`document/block.ex:32-33`) | `:location` | `content` | `content: []` |
| `Raise` (`document/raise.ex:19-20`) | `:event`, `:location` | `event` | - |
| `Log` (`document/log.ex:16-17`) | `:location` | `label`, `expr` | both `nil` |
| `Donedata` (`document/donedata.ex:20-21`) | `:location` | `content` | `content: nil` |
| `Content` (`document/content.ex:32-33`) | `:location` | `expr`, `text` | both `nil` |

**Who tokenizes what.** The structs declare list types but do no splitting - the
type is the contract and lowering satisfies it:

- `Transition.event :: [String.t()]` - whitespace-split descriptors. The
  *second*-level dot split of a descriptor is explicitly **not** lowering's job; it
  is st-wju.1's, at match time (`document/transition.ex:14-18`).
- `Transition.target :: [String.t()]` - whitespace-split ids.
- `Document.initial :: [String.t()]` and `State.initial :: [String.t()]` - IDREFS,
  same split.
- `Raise.event :: String.t()` - explicitly **not** split
  (`document/raise.ex:7-13`): a raise produces one literal name, it does not match a
  pattern.
- `Content.text` - `DOM.text/1`'s concatenation, with no span of its own; the
  `Content` node's own `location` is what a diagnostic points at
  (`document/content.ex:17-21`).

**Who applies defaults.** Lowering, per the l5k.2 plan's Decision 7
(`docs/plans/260807-st-l5k.2-typed-document-structs.md:416-429`). The struct
defaults exist so a literal fixture is convenient, but the lowering pass is what
turns an absent attribute into `:external` / `:early` / `:shallow`. Missing optional
attributes become `nil` or `[]`, never `""` - v1 mapped `""` to `nil` for every
attribute (`../statifier/lib/statifier/parser/scxml/element_builder.ex:515-520`);
whether v2 does the same for an explicitly-written `label=""` is an open question
below.

**The `attribute_locations` contract** (`lib/statifier/document.ex:22-44`) is the
one rule a builder is most likely to get wrong, and the moduledoc states it in
capitals: an entry exists **only for an attribute that was actually written in the
source**, and its value is the attribute's `value_location` (value span only, not the
`name="value"` span). So `Map.has_key?(t.attribute_locations, :type)` is exactly the
"did the author write it" question. Keys are atoms drawn from a fixed known set per
element; the l5k.2 plan enumerates the set as `:id`, `:initial`, `:type`, `:event`,
`:cond`, `:target`, `:label`, `:expr`, `:name`, `:version`, `:binding`, `:datamodel`,
`:xmlns` (Decision 2, plan line 277).

**What lowering must *not* reject.** The Document is the pre-validation type
(`docs/architecture.md:33-36`, principle 4). `State`'s moduledoc carries a table of
kind-scoped fields and the st-l5k.5 check that catches each misuse
(`document/state.ex:43-51`): `donedata` on a non-final, state children under a
`:final`, both `initial` forms on one state, a `:history` child of a `:final`. All
eight are validator checks. Lowering builds the shape as written. The l5k.2 research
states the boundary in one line, quoted from the st-l5k.4 bead's own design note:
"Conflicting forms (state with both initial attribute and initial element) are built
as-is here - that is a validator check (st-l5k.5), and lowering staying dumb about
semantics keeps the layer boundary clean."

### 3. Phase 1 element set, and where Phase 3 gets rejected

The Phase 1 set with its attributes, sourced from the W3C spec by the l5k.2 research
(`docs/research/260807-st-l5k.2-typed-document-structs.md:626-742`):

| Element | Attributes lowering reads | Produces | Defaults / tokenization |
|---|---|---|---|
| `<scxml>` 3.2 | `initial`, `name`, `datamodel`, `binding`, `version`, `xmlns` | `%Document{}` | `initial` split; `binding` -> `:early` |
| `<state>` 3.3 | `id`, `initial` | `%State{kind: :state}` | `initial` split |
| `<parallel>` 3.4 | `id` | `%State{kind: :parallel}` | - |
| `<final>` 3.7 | `id` | `%State{kind: :final}` | - |
| `<history>` 3.10 | `id`, `type` | `%State{kind: :history}` | `history_type` -> `:shallow` |
| `<initial>` 3.6 | **none** | `%Initial{}` on parent's `initial_element` | one `<transition>` child expected structurally |
| `<transition>` 3.5 | `event`, `cond`, `target`, `type` | `%Transition{}` | `event`/`target` split; `type` -> `:external` |
| `<onentry>` 3.8 | none | `%Block{}` appended to `State.onentry` | boundaries preserved, never flattened |
| `<onexit>` 3.9 | none | `%Block{}` appended to `State.onexit` | as above |
| `<raise>` 4.2 | `event` (required) | `%Raise{}` | **not** split |
| `<log>` 4.7 | `label`, `expr` | `%Log{}` | both `nil` when absent |
| `<donedata>` 5.5 | none | `%Donedata{}` on `State.donedata` | `<content>` branch only |
| `<content>` 5.6 | `expr` | `%Content{}` | `text` from `DOM.text/1` |

The block rule at 3.8 is normative and is why `Block` exists: each `<onentry>`
element is a separate error-isolation unit under section 4's rule, so three
`<onentry>` elements are structurally different from one with nine concatenated
children. v1 flattened them into `State.onentry_actions: [term()]` and lost the
boundary (`../statifier/lib/statifier/parser/scxml/state_stack.ex:212-251`).

**The Phase 3 rejection set**, named identically in the bead, the l5k.2 research
(`:425-427`), and the l5k.2 plan's "What We're NOT Doing" (`:136-137`):
`datamodel`, `data`, `assign`, `script`, `send`, `cancel`, `invoke`, `if`, `elseif`,
`else`, `foreach`, `param`. Two placements are worth calling out because they are not
top-level:

- `<param>` inside `<donedata>` is rejected as Phase 3 even though `<donedata>`
  itself is Phase 1 (l5k.2 research `:733`). Corpus case
  `test/scxml_tests/mandatory/donedata/test294_test.exs:36-38` is exactly this shape.
- `<datamodel>` and `<script>` are legal `<scxml>` children per 3.2 and legal
  `<state>` children per 3.3, so the rejection fires from inside the `scxml` and
  `state` builders, not only at some notional top level.

**Error shape.** No shape is specified anywhere in docs for lowering. The available
precedent is `Statifier.Parser.ParseError`
(`lib/statifier/parser/parse_error.ex:22-35`): a `defexception` with a
pattern-matchable `reason` term, a rendered `message`, and a `Location.t()`; the
parser returns it in an `{:error, _}` tuple and never raises. The l5k.3 plan's
Decision 5 established that pattern - normalize the failure into a v2-owned struct,
never leak the underlying one, keep `reason` matchable rather than a message string.
Following it would give something like a `reason` of
`{:unsupported_element, "send"}` plus the element's `location`.

**Multiple unsupported elements in one pass.** Nothing exists to build on. A repo-wide
search for `defexception` or an error-collection type finds only `ParseError`. The
docs assign "all errors collected in one pass" to st-l5k.5 (l5k.2 research `:437`)
without specifying a shape for the collection, and the builder signature the same
research sketches is single-error. This bead has to invent the mechanism - the two
obvious candidates being a builder that returns `{:ok, struct, errors}` and threads
an accumulator, or a fail-fast build followed by a separate collecting sweep for
unsupported elements. Neither is prescribed.

### 4. The FeatureDetector contract, and what actually mirrors

`test/support/feature_detector.ex` is regex-over-raw-XML detection, deliberately
not structural: "v2 has no parsed document struct yet; when one lands, a
`detect_features/1` clause for it is added alongside the string clause"
(`feature_detector.ex:10-12`).

Public surface:

- `detect_features(xml :: String.t()) :: MapSet.t(atom())` (`:28`)
- `feature_registry() :: %{atom() => :supported | :unsupported | :partial}` (`:42`)
- `validate_features(MapSet.t(atom())) :: {:ok, MapSet.t()} | {:error, MapSet.t()}`
  (`:89-90`); a feature absent from the registry is treated as `:unsupported`
  (`:96`).

All 33 registry entries are currently `:unsupported` (`:44-78`) - the moduledoc says
this is deliberate and each phase flips its own features as they land. `Statifier.Case`
calls `validate_features!/2` first thing in `test_scxml/4`
(`test/support/case.ex:60-61`) and `flunk`s - never skips - naming the unsupported
features, all detected features, and the test description (`:84-93`).

**Where a literal mirror breaks down.** The `@element_features` regex table
(`feature_detector.ex:106-130`) has 23 entries and its atoms do not line up with the
bead's rejection set:

- There is no `elseif` or `else` regex at all - `<if>` maps to `:if_elements` and the
  other two branches are invisible to the detector.
- `<param>` maps to `:send_param_elements` regardless of whether it sits under
  `<send>`, `<invoke>`, or `<donedata>`; `<content>` maps to
  `:send_content_elements` regardless of context.
- `<datamodel>` maps to `:datamodel`, `<data>` to `:data_elements` - the atoms are
  feature-shaped, not element-shaped.
- Nothing carries a location.

And `lib/` may not reference the module at all (`feature_detector.ex:6`,
`docs/testing.md:161-162`, ADR-0006). So "the library-side mirror of the
FeatureDetector contract" is the *rule* - a document the harness would flunk must
also fail loudly here, never silently, with the offending thing named - not a shared
atom vocabulary. Keeping the two consistent is a matter of the element sets agreeing,
which is a review property, and could be made mechanical by a guard test comparing
the detector's regex table against the lowering dispatch map's key set. No such
guard exists today.

### 5. What v1 did, and what the shape is fixing

`../statifier/lib/statifier/parser/scxml/state_stack.ex` is 903 lines and 93
function-head clauses. Excluding 18 small private helpers and the 2
`handle_characters/2` clauses, **73 clauses match on an (child element, parent
element) pair** - that is the number `docs/architecture.md:62-64` and the bead both
cite. v1 has no DOM stage at all: the Saxy handler builds the final `Document`
incrementally during the SAX walk, so every element must know how to fold itself into
every container it can appear in.

The coupling is mechanical and repetitive. Each action-bearing element (`log`,
`raise`, `assign`, `if`, `send`, `foreach`, `invoke`) carries the *same six-to-eight
clause shape*: parent `"onentry"` with an accumulated list, parent `"onentry"` as the
first child (a `:onentry_block` sentinel), the same two for `"onexit"`, parent
`"if"`, parent `"foreach"`, parent `"transition"`, and a silent catch-all pop. The
per-element line ranges are `handle_log_end` 257-317, `handle_raise_end` 323-383,
`handle_assign_end` 389-449, `handle_if_end` 455-525, `handle_send_end` 581-641,
`handle_foreach_end` 688-758, `handle_invoke_end` 833-891.

Two clauses, from different elements, showing the shape is one template repeated:

```elixir
# state_stack.ex:297-303
def handle_log_end(
      %{stack: [{_element_name, log_action} | [{"foreach", foreach_action} | rest]]} = state
    ) do
  updated_foreach = %{foreach_action | actions: foreach_action.actions ++ [log_action]}
  {:ok, %{state | stack: [{"foreach", updated_foreach} | rest]}}
end

# state_stack.ex:647-653
def handle_param_end(
      %{stack: [{_element_name, param} | [{"send", send_action} | rest]]} = state
    ) do
  updated_send = %{send_action | params: send_action.params ++ [param]}
  {:ok, %{state | stack: [{"send", updated_send} | rest]}}
end
```

Adding one new action element to v1 costs roughly 6-8 new `state_stack.ex` clauses,
plus a `dispatch_element_start/4` clause and an `:end_element` clause in `handler.ex`,
plus a `build_*` function in `element_builder.ex`. The module disables Credo's
cyclomatic-complexity check for the whole file (`handler.ex:12`).

Other v1 behaviors worth contrasting, because v2's bead specifies the opposite:

- **Unknown elements are silently accepted.** `dispatch_element_start/4`'s catch-all
  pushes `{name, nil}` and discards the attributes (`handler.ex:447-450`); the
  `:end_element` catch-all just pops (`handler.ex:73-74`). `<donedata>` is one such
  element - it appears nowhere in v1's parser and is silently dropped.
- **Tokenization is inconsistent.** `target` is split at parse time
  (`element_builder.ex:235-243`) but `event` is stored raw and re-split on **every
  match attempt** in the interpreter (`../statifier/lib/statifier/event.ex:64-79`).
- **Defaults are partly missing.** `history` `type` defaults to `:shallow`
  (`element_builder.ex:195-200`), but transition `type` is left `nil` with the
  default documented only in a comment (`../statifier/lib/statifier/transition.ex:12`),
  and `binding` is compared against the literal `"early"` so a `nil` binding falls
  into the discard branch (`state_stack.ex:132-135`).
- **Whitespace text is trimmed and dropped, and repeated `:characters` events
  overwrite rather than append** (`state_stack.ex:794-828`) - only `"content"` and
  `"data"` elements consume text at all; every other element's text is silently
  discarded.
- **Locations come from re-scanning the XML string per element**
  (`location_tracker.ex:51-67`), counting the Nth occurrence of `<tag` per line;
  attribute locations get a line but `column: nil` (`location_tracker.ex:80-83`).
  v2's `lib/statifier/parser.ex:32-45` records why that approach was rejected.
- **`<initial>` got a synthetic id**, `"__initial_#{n}__"`
  (`element_builder.ex:522-525`), which then had to be excluded by hand from
  unique-id checking - the reason v2 makes `<initial>` a slot, not a kind
  (`lib/statifier/document/initial.ex:6-14`).

### 6. Where the lowering module can live

Two guard tests already constrain the namespace, and between them they rule out both
obvious homes.

`test/statifier/parser/generic_handler_test.exs` walks the AST of every file matching
`lib/statifier/parser/**/*.ex`, drops `@moduledoc`/`@doc`/`@typedoc`, and fails if any
remaining string literal is equal to one of 26 SCXML element names (`:8-12`). Its
comment states the intent directly: "the parser layer may not name an element,
because the moment it can, a clause per element follows." A dispatch map keyed by
`"state"`, `"parallel"`, `"transition"` is precisely the literal set it rejects.

`test/statifier/document/layer_test.exs` reads every file matching
`lib/statifier/document.ex` and `lib/statifier/document/*.ex` and asserts each one
compiles to a struct module that both has and `@enforce_keys` a `:location` field
(`:74-89`). A lowering module placed there would fail on the first guard, since it is
not a struct module.

So the lowering pass needs a third namespace - `Statifier.Lowering` at
`lib/statifier/lowering.ex` (plus `lib/statifier/lowering/*.ex`) is the shape that
fits both existing guards without amending either. Amending a guard to accommodate
the new module would be a gate-weakening decision, and ADR-0011 makes that a human's
call; the plan should not assume it.

### 7. How the tests are structured

**Case module.** `Statifier.Case` (`test/support/case.ex`) is for the SCION/W3C
conformance corpus only - it is `use ExUnit.CaseTemplate` and exposes exactly one
function, `test_scxml/4`. Every internal unit test in `test/statifier/` uses plain
`use ExUnit.Case, async: true` instead, verified across all 20 test files. A lowering
test module follows the latter.

**Heredoc XML.** Triple-quoted heredocs at 4-space base indentation, fed straight to
a locally-defined `parse!/1` helper each parser test module defines for itself
(`test/statifier/parser_test.exs:9-12`) rather than a shared import. Single-line
fixtures use `~s(...)` instead (`parser_test.exs:139,158`).

```elixir
# test/statifier/parser_test.exs:26-33
xml = """
<root>
    <alpha>
        <gamma/>
    </alpha>
    <beta/>
</root>
"""

root = parse!(xml)
```

**Sabotage notes.** One line, present tense, directly above `test`, above any `@tag`,
format `# sabotage: <what was broken> -> red` (`docs/testing.md:44-52`). Real
examples in this repo run longer than the canonical one-liner and wrap:

```
# sabotage: the :end_element clause skips `Enum.reverse(frame.children)`
# -> the children come back in reverse document order, reddening the
# ordered name assertion                    (parser_test.exs:22-24)

# sabotage: drop :kind from State's @enforce_keys -> struct!(State, []) stops
# raising for :kind                         (document/state_test.exs:21)

# sabotage: n/a - lists .ex files under lib/statifier/document/, no lib/ behavior
#                                            (document/layer_test.exs:66)
```

A valid mutation is one a reasonable person could make by mistake - invert a
condition, drop a clause, skip a recursive call, off-by-one a boundary. Deleting a
function body is explicitly not sabotage (`docs/testing.md:54-57`). Unlike the
struct-only l5k.2 bead - which had to work out (plan Decision 8) that its only three
mutable behaviors were `@enforce_keys` membership, `defstruct` defaults, and guard
predicates - a lowering pass has abundant real mutations available: drop a
whitespace split, invert a default, forget to copy a location, filter text instead of
erroring on it, drop an element from the dispatch map.

**Error-path assertions** pattern-match the whole tuple and rebind for follow-ups:

```elixir
# test/statifier/parser_test.exs:265-275
assert {:error, %ParseError{reason: {:wrong_closing_tag, "b", "c"}} = error} =
         Parser.parse(xml)

assert %Location{start_line: 1} = error.location
assert error.byte_offset > 0
```

Totality sweeps over a table of hostile inputs use `match?/2` with a message
(`parse_error_test.exs:116-139`).

**Location assertions** come in two styles and both are used. Literal line/column
where the number is worth pinning (`%Location{start_line: 4, start_column: 1} =
root.location`, `parser_test.exs:94`), and `Location.slice/2`-based property
assertions where the point is that the span is *correct* rather than at a particular
place (`location_accuracy_test.exs:13-37` slices every descendant's span back out of
the source and asserts it starts with that element's start tag). A lowering test can
reuse `slice/2` the same way to prove a copied location still points at the right
element.

**Structure.** Every file uses `describe` blocks, named either for the function under
test (`describe "elements/1"`) or for a scenario group (`describe "parse/1 -
locations"`, `describe "guard 2: no Predicator in this layer"`). Test names are full
sentences describing observed behavior.

## Architecture Documentation

`docs/architecture.md:38-58` places lowering between the DOM and the Document as
"typed per-element builders", and `:60-67` states the structural claim the bead
inherits: "Adding an element touches one builder, not a clause matrix."

The layer boundaries that constrain lowering:

- **Down from lowering** - nothing. The DOM is finished and unvalidated; lowering
  reads it and does not amend it.
- **Up to the validator (st-l5k.5)** - all eight semantic checks. Lowering builds
  malformed shapes rather than refusing them, because a check needs a stable error
  code and a red fixture, and cannot have one for a shape that was never
  representable (`docs/architecture.md:33-36`, principle 4).
- **Up to the compiler (st-wju.1)** - interning, indexing, `document_order`, expression
  compilation, and the second-level dot split of event descriptors. ADR-0005 puts
  indexing in the compiler; ADR-0002 puts Appendix D's predicates on the Machine;
  ADR-0004 and `docs/datamodel.md` keep `Predicator` out of this layer entirely.

**Locations.** ADR-0012 item 3 and `docs/observability.md` Constraint 3 make location
retention binding: locations are born in the parser and can only be retained
downstream, never recovered. ADR-0014 is the reason `attribute_locations` stores value
spans specifically - `value_location.start_offset + span.start` is the arithmetic that
turns a within-expression span into a document position, and it only works if lowering
copies the *value* span rather than the `name="value"` span.

**Errors.** `docs/architecture.md:28-31` ("errors are events") governs the
interpreter, not this layer. Here, per the l5k.3 precedent, errors are plain tagged
tuples carrying a v2-owned struct, and the pass never raises.

**Unsupported features.** `docs/testing.md:159-162` and ADR-0006 fix the harness rule
- fail, never skip, with the feature named. The same document is explicit that
feature detection lives in `test/support`, not `lib/`, "it is harness code, not
library surface." The bead's mirror is to that *rule*.

## Open Questions

Recorded here because no human was available; none blocks planning, but each is a
decision the plan must make explicitly rather than by accident.

1. **Where does the lowering module live?** Both obvious namespaces are ruled out by
   existing guard tests (finding 6). `Statifier.Lowering` at
   `lib/statifier/lowering.ex` fits both without amending either, but the name is not
   fixed by any doc.

2. **What is the multi-error mechanism?** The bead's criterion "multiple unsupported
   elements reported in one pass" has no existing machinery to inherit - `ParseError`
   is single-error and the docs assign error accumulation to st-l5k.5 without
   specifying a shape. Threading an accumulator through the builders and a separate
   collecting sweep are both viable; the plan has to pick and say why.

3. **Does `<content expr="...">` land in Phase 1 or defer as unsupported?** This is
   handed to st-l5k.4 explicitly by the l5k.2 plan's Residual Note 3
   (`:828-831`). The struct holds `expr` either way. Two corpus donedata cases use it
   (`test/scxml_tests/mandatory/content/test527_test.exs:30`,
   `test528_test.exs:31`), and the spec makes `expr` mutually exclusive with child
   content - which is a validator concern, so accepting it costs lowering nothing.

4. **What happens to a prefixed element name?** The DOM keeps names verbatim,
   prefix included (`test/statifier/parser_test.exs:254-261`), and l5k.3's bead text
   says foreign-namespace elements should be rejected or warned about "at lowering
   time, not here." A document written as `<s:scxml xmlns:s="...">` is legal SCXML and
   would miss every dispatch key. The bead does not mention it. Options: strip a
   prefix before dispatch, reject prefixed names outright, or resolve the declared
   namespace on the root and check it - and `Document.xmlns` exists as a field, so
   something is expected to read the declaration.

5. **Is `label=""` the same as an absent `label`?** The bead says missing optional
   attributes become `nil` or `[]`, "never empty-string sentinels", which covers the
   absent case. It does not say what an explicitly-written empty value becomes. v1
   collapsed the two (`element_builder.ex:515-520`). `Log`'s moduledoc argues the
   opposite direction for the *absent* case ("a missing `label` is not the same fact
   as an author writing `label=\"\"`"), which reads as wanting them distinguished -
   and `attribute_locations` already distinguishes them for free.

6. **Should the FeatureDetector/lowering agreement be mechanical?** The bead calls
   lowering "the library-side mirror" of the harness contract, but the two cannot
   share code (`lib/` may not reference `test/support/`) and their vocabularies do not
   line up (finding 4). A guard test comparing the detector's regex table against the
   dispatch map's key set would make the agreement mechanical the way
   `generic_handler_test.exs` and `layer_test.exs` made their beads' criteria
   mechanical. Nothing requires one.

7. **Does a duplicate attribute reach lowering as an error, or pass through?** The DOM
   preserves duplicates deliberately so "the validator gets to report" them
   (`dom/element.ex:12-14`), but `DOM.attribute/2` returns the first silently and no
   listed st-l5k.5 check names duplicates. The plan should state whether lowering
   notices.
