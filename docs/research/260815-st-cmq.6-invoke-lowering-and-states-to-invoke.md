# Research: `<invoke>` lowering and the statesToInvoke passes

**Date**: 2026-08-15T05:17:14-0600
**Git Commit**: baedffc10d695da3f682b4c9a65b188d13c78fff
**Branch**: st-cmq.6-invoke-lowering
**Bead**: st-cmq.6

## Research Question

What does the codebase look like today, at the seams st-cmq.6 will work
in? Specifically: how an SCXML element with attributes, expr-variants,
`<param>`/`<content>` children and executable-content children is parsed,
lowered, validated, compiled and evaluated; what the `Statifier.Effect`
family is and how effects are produced and consumed; what
`Statifier.MachineState` holds and what its "deliberately absent"
contract for `states_to_invoke` actually says; where each commented
invoke seam is; what Appendix D and the normative spec say about the
invoke passes, `cancelInvoke`, finalize and autoforward; which ADRs
constrain the work; and what test infrastructure and corpus material is
blocked on `<invoke>` today.

This document describes what exists. It proposes nothing.

## Summary

`<invoke>` exists in this codebase as a **vocabulary without a
producer**. The effect payload struct is written, typed, registered in
the effect union, planned for by the session, and exercised in tests -
but nothing in `lib/` constructs one, no `Document.Invoke` or
`Machine.Invoke` exists, `<invoke>` has no lowering builder (it is
rejected as `{:unsupported_element, "invoke"}`), and `states_to_invoke`
is deliberately not a field on `%MachineState{}`.

Concretely, the state of play at this commit:

- **Lowering**: `<invoke>`, `<send>` and `<cancel>` are all absent from
  the lowering dispatch table ([`lib/statifier/lowering.ex:53-76`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering.ex#L53-L76)). The
  closest complete precedent for what `<invoke>` needs is the
  `<donedata>` / `<param>` / `<content>` path, which already covers
  every ingredient except the expr-variant attribute pairs
  (`typeexpr`/`srcexpr`) and `namelist`.
- **Effects**: `Statifier.Effect.Invoke` is complete and its field is
  `state_index`, with the rename from `source` recorded in its own
  moduledoc ([`lib/statifier/effect/invoke.ex:13-15`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/effect/invoke.ex#L13-L15)). Nothing produces
  it; `Statifier.Session.Effects.plan_one/1` already has a clause that
  plans it as `{:notify, effect}, {:unroutable, effect}`
  ([`lib/statifier/session/effects.ex:69-71`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/session/effects.ex#L69-L71)). There is **no**
  cancel-invoke effect struct at all - `Statifier.Effect.Cancel` is
  spec 6.3's `<cancel sendid>` and nothing else.
- **MachineState**: `states_to_invoke` is absent by an explicit,
  documented standing rule, and this bead is named as its first caller
  ([`lib/statifier/machine_state.ex:33-41`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L33-L41)).
- **Interpreter seams**: five commented sites across two modules, each
  naming `st-cmq`, each sitting in the pseudocode's own position. The
  bead's line numbers are stale (the file has moved since it was
  written); the current locations are given below.
- **Corpus**: 35 emitted W3C mandatory tests carry
  `required_features: [:invoke_elements]` and `flunk` today through
  `Statifier.Case`'s feature gate. None is in the regression ratchet.

## Detailed Findings

### 1. The Appendix D pseudocode, read locally

Read from the spec cache at
`$(git rev-parse --path-format=absolute --git-common-dir)/spec-cache/appendix-d.txt`.
There are exactly six pseudocode sites plus one prose paragraph.

**`interpret` declares the global** (`appendix-d.txt:59`, `:96`):

```
global statesToInvoke
...
    statesToInvoke = new OrderedSet()
```

**`mainEventLoop`'s prose** for the invoke steps
(`appendix-d.txt:112`):

> ... 2) When there are no more internally enabled transitions
> available, the macrostep is done. Execute any `<invoke>` tags for
> states that we entered on the last iteration through the loop 3) If
> any internal events have been generated by the invokes, repeat step 1
> to handle any errors raised by the `<invoke>` elements. 4) When the
> internal event queue is empty, wait for an external event and then
> execute any transitions that it triggers. However special preliminary
> processing is applied to the event if the state has executed any
> `<invoke>` elements. First, if this event was generated by an invoked
> process, apply `<finalize>` processing to it. Secondly, if any
> `<invoke>` elements have autoforwarding set, forward the event to
> them. These steps apply before the transitions are taken.

**`mainEventLoop`'s invoke pass** (`appendix-d.txt:137-141`):

```
        # Here we invoke whatever needs to be invoked. The implementation of 'invoke' is platform-specific
        for state in statesToInvoke.sort(entryOrder):
            for inv in state.invoke.sort(documentOrder):
                invoke(inv)
        statesToInvoke.clear()
```

**The post-invoke internal-queue re-check** (`appendix-d.txt:142-144`):

```
        # Invoking may have raised internal error events and we iterate to handle them
        if not internalQueue.isEmpty():
            continue
```

**The finalize/autoforward pass**, sitting between
`datamodel["_event"] = externalEvent` and `selectTransitions`
(`appendix-d.txt:152-158`):

```
        datamodel["_event"] = externalEvent
        for state in configuration:
            for inv in state.invoke:
                if inv.invokeid == externalEvent.invokeid:
                    applyFinalize(inv, externalEvent)
                if inv.autoforward:
                    send(inv.id, externalEvent)
        enabledTransitions = selectTransitions(externalEvent)
```

Note two literal properties of this loop that the port has to reproduce
or deviate from explicitly: it iterates `configuration` (the **full**
configuration, not leaves), in no stated order; and the `autoforward`
test is **not** in the `else` of the invokeid test - an invocation whose
invokeid matches *and* which autoforwards does both.

**`exitInterpreter`'s cancel walk** (`appendix-d.txt:171-178`):

```
procedure exitInterpreter():
    statesToExit = configuration.toList().sort(exitOrder)
    for s in statesToExit:
        for content in s.onexit.sort(documentOrder):
            executeContent(content)
        for inv in s.invoke:
            cancelInvoke(inv)
        configuration.delete(s)
        if isFinalState(s) and isScxmlElement(s.parent):
            returnDoneEvent(s.donedata)
```

**`exitStates`' two invoke lines** (`appendix-d.txt:258-273`), with the
prose that explains the `delete` (`appendix-d.txt:253`):

> Compute the set of states to exit. Then remove all the states on
> statesToExit from the set of states that will have invoke processing
> done at the start of the next macrostep. (Suppose macrostep M1
> consists of microsteps m11 and m12. We may enter state s in m11 and
> exit it in m12. We will add s to statesToInvoke in m11, and must
> remove it in m12. In the subsequent macrostep M2, we will apply invoke
> processing to all states that were entered, and not exited, in M1.)

```
procedure exitStates(enabledTransitions):
    statesToExit = computeExitSet(enabledTransitions)
    for s in statesToExit:
        statesToInvoke.delete(s)
    statesToExit = statesToExit.toList().sort(exitOrder)
    ...
    for s in statesToExit:
        for content in s.onexit.sort(documentOrder):
            executeContent(content)
        for inv in s.invoke:
            cancelInvoke(inv)
        configuration.delete(s)
```

The `statesToInvoke.delete(s)` loop runs over the **unordered** exit set
before it is sorted, and before the history-recording pass.

**`enterStates`' add** (`appendix-d.txt:308-310`):

```
    for s in statesToEnter.toList().sort(entryOrder):
        configuration.add(s)
        statesToInvoke.add(s)
```

`statesToInvoke.add(s)` is unconditional per entered state - the
pseudocode does not test whether `s` has any `<invoke>` children.
`mainEventLoop`'s inner `for inv in state.invoke` is where a state with
no invocations costs nothing.

`exitInterpreter`'s prose also names the invoke-completion event
(`appendix-d.txt:167`):

> The implementation of returnDoneEvent is platform-dependent, but if
> this session is the result of an `<invoke>` in another SCXML session,
> returnDoneEvent will cause the event done.invoke.`<id>` to be placed
> in the external event queue of that session ...

### 2. The normative clauses, read locally

From `spec-cache/scxml-rec.html`, section 6.4 (normative).

**Attribute table (6.4.1)** - the pairs and their mutual exclusions:

- `type` (URI, no default), `typeexpr` (value expression) - "Must not
  occur with the 'type' attribute ... the SCXML Processor MUST evaluate
  it when the parent `<invoke>` element is evaluated and treat the
  result as if it had been entered as the value of 'type'."
- `src` (URI), `srcexpr` (value expression) - each "Must not occur with"
  the other **or with the `<content>` element**.
- `id` (ID), `idlocation` (location expression) - mutually exclusive.
- `namelist` - "A space-separated list of one or more data model
  locations to be passed as attribute/value pairs to the invoked
  service", and "Must not occur with the `<param>` element."
- `autoforward` - boolean, **default `false`**.

**Children (6.4.2)**: `<param>` 0..n; `<finalize>` 0..1; `<content>`
0..1 ("The SCXML Processor MUST evaluate this element when the parent
`<invoke>` element is evaluated and pass the resulting data to the
invoked service").

**The generated id format**:

> A conformant SCXML document MAY specify either the 'id' or
> 'idlocation' attribute, but MUST NOT specify both. If the
> 'idlocation' attribute is present, the SCXML Processor MUST generate
> an id automatically when the `<invoke>` element is evaluated and store
> it in the location specified by 'idlocation'. (In the rest of this
> document, we will refer to this identifier as the "invokeid",
> regardless of whether it is specified by the author or generated by
> the platform). The automatically generated identifier MUST have the
> form stateid.platformid, where stateid is the id of the state
> containing this element and platformid is automatically generated.
> platformid MUST be unique within the current session.

**When the arguments fail**:

> When the `<invoke>` element is executed, if the evaluation of its
> arguments produces an error, the SCXML Processor MUST terminate the
> processing of the element without further action.

**Autoforward**:

> When the 'autoforward' attribute is set to true, the SCXML Processor
> MUST send an exact copy of every external event it receives to the
> invoked process. All the fields specified in 5.10.1 ... MUST have the
> same values in the forwarded copy of the event. The SCXML Processor
> MUST forward the event at the point at which it removes it from the
> external event queue of the invoking session for processing.

**Finalize selection** (6.4, and again in 6.5):

> If there is a `<finalize>` handler in the instance of `<invoke>` that
> created the service that generated the event, the SCXML Processor MUST
> execute the code in that `<finalize>` handler right before it removes
> the event from the event queue for processing. It MUST NOT execute the
> `<finalize>` handler in any other instance of `<invoke>`.

**Cancellation ordering** (6.4):

> If the invoking session takes a transition out of the state containing
> the `<invoke>` before it receives the 'done.invoke.id' event, the
> SCXML Processor MUST automatically cancel the invoked component and
> stop its processing. The cancel operation MUST act as if it were the
> final `<onexit>` handler in the invoking state.

**`<finalize>` (6.5)** - no attributes; children are 0 or more elements
of executable content:

> In a conformant SCXML document, the executable content inside
> `<finalize>` MUST NOT raise events or invoke external actions. In
> particular, the `<send>` and `<raise>` elements MUST NOT occur.

> In the case of parallel states, only the finalize code in the original
> invoking state is executed.

And the **empty-finalize** rule, which is a distinct behavior from an
absent one:

> If no executable content is specified, the SCXML Processor MUST update
> the data model each time an event is received ... for each item in the
> 'namelist' attribute and each such `<param>` element, the Processor
> MUST update the corresponding location as if by `<assign>` with any
> return value that has a name that matches ... Note that the automatic
> update does not take place if the `<finalize>` element is absent as
> opposed to empty.

**`invokeid` as an event field (5.10.1)**:

> invokeid. If this event is generated from an invoked child process,
> the SCXML Processor MUST set this field to the invoke id of the
> invocation that triggered the child process. Otherwise it MUST leave
> it blank.

**3.14 IDs** - why an `<invoke>` id is generated per execution rather
than at load time:

> The ids for `<send>` and `<invoke>` are subtly different. In a
> conformant SCXML document, they MUST be unique within the session, but
> in the case where the author does not provide them, the processor MUST
> generate a new unique ID not at load time but each time the element is
> executed.

### 3. `Statifier.MachineState` and the "deliberately absent" contract

`lib/statifier/machine_state.ex` is the reified interpreter position -
"any `%MachineState{}` value is a complete, inspectable, resumable
position" (ADR-0012 constraint 1, [`lib/statifier/machine_state.ex:2-11`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L2-L11)).

Current fields ([`lib/statifier/machine_state.ex:188-205`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L188-L205)), `machine`
enforced: `configuration`, `internal_queue`, `history_values`,
`entered_states`, `datamodel`, `running`, `status`, `macrostep`,
`microstep`, `round`, `trace`, `max_macrostep_rounds`.

The verbatim contract this bead is named in
([`lib/statifier/machine_state.ex:33-41`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L33-L41)):

> ## `states_to_invoke` is deliberately absent
>
> Appendix D carries `statesToInvoke` as a global, but every read and
> write of it belongs to the invoke passes of `main_event_loop`, not yet
> implemented. Adding an unused field now would be exactly the "dead
> field nobody can test" mistake avoided for `origin`/`sendid` on
> `Statifier.Event`: the field is added deliberately, with a caller,
> once the invoke passes exist, rather than added now as a placeholder
> ahead of any caller.

The rule is quoted back from ADR-0027 as a general standing rule
("multiple named runtimes are mechanism with no caller and stay out, per
the same standing rule that kept `states_to_invoke` off `MachineState`
until st-cmq.6", [`docs/adr/0027-embedder-placed-session-runtime.md:83`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/docs/adr/0027-embedder-placed-session-runtime.md#L83)).

Adjacent contracts a new field inherits:

- **The counter contract** ([`lib/statifier/machine_state.ex:93-137`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L93-L137)):
  `begin_macrostep/1`, `begin_microstep/1`, `begin_round/1` are the only
  writers of their counters, enforced by review.
- **Sets of states are `MapSet.t(non_neg_integer())`** - interned
  indexes, never string ids (ADR-0005). `configuration`,
  `entered_states` and `history_values`' values are all that shape.
- **`entered_states` is the precedent for hoisting an Appendix D
  per-state mutable off the compiled state**
  ([`lib/statifier/machine_state.ex:43-66`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L43-L66)): `s.isFirstEntry` became a
  runtime `MapSet` keyed by `state_index`, declared an ADR-0002
  mechanical deviation, and populated unconditionally rather than
  conditionally so the field's meaning does not depend on the document.
- **`==` is not a position-equality test**
  ([`lib/statifier/machine_state.ex:169-181`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine_state.ex#L169-L181)) because `internal_queue` is
  a `:queue`.

**`Effect.Invoke` in full** ([`lib/statifier/effect/invoke.ex:1-43`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/effect/invoke.ex#L1-L43)) - the
moduledoc is the record of the `source` -> `state_index` rename:

> Payload for `{:invoke, %__MODULE__{}}` - spec 6.4's `<invoke>`. Fields
> are the element's own attribute names: `invoke_id` (`id`/`idlocation`,
> generated when the element has none), `type`, `src`, `params` (the
> resolved `<param>`/`<content>` payload), `autoforward` (the
> `autoforward` attribute).
>
> `<invoke>` is attached to a state, not to a block of executable
> content, so this payload carries `state_index` - the invoking state's
> index (constraint 3) - rather than a `c_index`; there is no content
> node to identify. `state_index` is named apart from `src` (spec 6.4's
> URI attribute) on purpose - the two fields are two letters apart with
> unrelated meanings, and the original `source` name invited confusing
> them (post-review correction).
> `macrostep`/`microstep` are the counters as they stand when the invoke
> is produced. The not-yet-implemented invoke/session support may add
> fields to this payload once it exists.

`finalize` field; and it has **no cancel counterpart**.

### 6. The lowering, validation and compilation path `<invoke>` will reuse

**`<invoke>` has no builder.** The dispatch table
([`lib/statifier/lowering.ex:53-76`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering.ex#L53-L76)) has 15 entries and contains no
`send`, `cancel` or `invoke` key; an `<invoke>` element falls through
`walk_children/2` ([`lib/statifier/lowering.ex:122-158`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering.ex#L122-L158)) to
`Statifier.Lowering.Error.unsupported/2`
([`lib/statifier/lowering/error.ex:45-51`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering/error.ex#L45-L51)) with reason
`{:unsupported_element, "invoke"}`. That rejection is asserted in
[`test/statifier/lowering/unsupported_test.exs:39-45`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/test/statifier/lowering/unsupported_test.exs#L39-L45), and `<invoke>` is
listed among `@phase_3_elements ~w(send invoke cancel)` in
[`test/statifier/lowering/coverage_test.exs:35`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/test/statifier/lowering/coverage_test.exs#L35).

**Builder shape.** Each builder is
`build_x(element, ctx) -> {tagged_result, [Error.t()]}`. The dominant
body (e.g. `build_param/2`,
[`lib/statifier/lowering/builders.ex:304-332`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering/builders.ex#L304-L332)): walk children first; read
attributes, short-circuiting on a missing required one to `{nil, errors}`;
record spans with `Attributes.put_location/4`; build the struct with
`location: element.location`; fold children in via `place_children/3`
([`lib/statifier/lowering/builders.ex:810-819`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering/builders.ex#L810-L819)); return
`{{tag, struct}, errors}`. `place/3`
([`lib/statifier/lowering/builders.ex:827-965`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering/builders.ex#L827-L965)) has one clause per
`{tag, parent-struct}` pair and a catch-all producing
`{:misplaced_element, tag, parent}`. Lists accumulate newest-first and
are restored to document order once by `reverse_lists/1`
([`lib/statifier/lowering/builders.ex:976-1031`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/lowering/builders.ex#L976-L1031)).

`Statifier.Lowering.Attributes` offers exactly four operations:
`value/2` (`:26-32`), `list/2` (whitespace-split - the shape `namelist`
needs, `:41-46`), `atom/4` (mapped onto a known atom with a default,
unknown values silently fall back rather than erroring, `:67-73`), and
`put_location/4` (`:86-98`).

**`<param>` end to end.** `Statifier.Document.Param`
([`lib/statifier/document/param.ex:47-56`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/document/param.ex#L47-L56)) enforces `location` and holds
`name`, `expr`, `param_location`, `attribute_locations` - and note the
naming inversion documented at `:6-33`: `location` is the element span,
`param_location` is the raw SCXML `location` **attribute**, which is the
opposite of `Document.Assign`'s convention. Lowering builds both `expr`
and `param_location` even though 5.7 forbids both, deliberately leaving
the violation for the validator. `Statifier.Validator.Checks.Param`
reports `{:param_expr_and_location, name}`
([`lib/statifier/validator/checks/param.ex:53-61`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/validator/checks/param.ex#L53-L61)) and
`{:param_no_value, name}` (`:49-51`); its moduledoc (`:14-18`) names
`<send>`/`<invoke>` as the future walk-growth sites - the rule is
unchanged, only the set of parents it walks grows.
`Statifier.Machine.Param` ([`lib/statifier/machine/param.ex:36-48`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/machine/param.ex#L36-L48))
enforces `name, kind, location` with `kind :: :expr | :location`, and
compiles a `<param location>`'s path string through the same expression
path as `<param expr>`. Compilation is
[`lib/statifier/compiler.ex:1140-1175`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/compiler.ex#L1140-L1175); evaluation is
`ExitEntry.evaluate_donedata_params/3`
([`lib/statifier/interpreter/exit_entry.ex:978-1026`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/interpreter/exit_entry.ex#L978-L1026)), which builds one

and on failure raises `error.execution` at a **per-param** origin

without aborting its siblings.

**`<content>` end to end - and the name collision.** Three unrelated
things are called Content in this tree:

## Architecture Documentation

Settled decisions that bind this work, cited rather than re-argued:

- **ADR-0002** (literal Appendix D port). Does not mention invoke by
  name, but governs every seam here: a deviation from the pseudocode is
  a semantic bug unless an inline comment cites a mechanical reason. The
  existing seams are all written in that style, and `main_event_loop/1`
  and `MachineState` both already carry ADR-0002 deviation notes for the
  caller-driven outer loop and the hoisted `isFirstEntry`.
- **ADR-0003** (pure core with effects). Names `{:invoke, ...}` in the
  vocabulary and assigns "timers, invoke lifecycles, and parent/child
  session routing" to `Statifier.Session`. This is the line between this
  bead (produce the effect data) and st-cmq.7 (perform it).
- **ADR-0004** (predicator as the datamodel). "Real computation reaches
  the host through `<invoke>` handlers and external `<send>`" -
  `<invoke>` is the escape hatch, restated in [`docs/datamodel.md:17`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/docs/datamodel.md#L17) and
  [`docs/architecture.md:140`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/docs/architecture.md#L140).
- **ADR-0005** (full configuration, interned indexes). `states_to_invoke`
  would be a set of integer indexes, and Appendix D's finalize pass
  iterates the **full** configuration, which is exactly what
  `MachineState.configuration` holds.
- **ADR-0008** (UXID identifiers). `inv_` is the reserved prefix for
  invocations; "Document-authored IDs ... are always respected; UXIDs
  fill the spec's 'platform-generated id' holes only"
  ([`docs/adr/0008-uxid-for-identifiers.md:19-21`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/docs/adr/0008-uxid-for-identifiers.md#L19-L21)), and "tests must not
  depend on their shape beyond the documented prefix" (`:27-29`).
- **ADR-0012** (debuggability). Constraint 1 - a `%MachineState{}` is a
  complete, inspectable, resumable position - is the argument
  `machine_state.ex` makes for `entered_states` being unconditional, and
  the same argument any new field inherits.
- **ADR-0019 / ADR-0020** (round budget and round ordinal). Appendix D's
  `if not internalQueue.isEmpty(): continue` re-enters the inner loop;
  in this port the inner loop is a bounded fold, so the seam interacts
  with the budget.
- **ADR-0021** (donedata `<content expr>` failure yields no data). Its
  scope limit is explicit
  ([`docs/adr/0021-donedata-content-expr-failure-yields-no-data.md:94-101`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/docs/adr/0021-donedata-content-expr-failure-yields-no-data.md#L94-L101),
  `:114-118`): it says nothing about `<content>` under `<send>` or
  `<invoke>`, "when they land they must answer the 5.6 question for
  their own context rather than inherit this answer, and the default
  expectation there is the opposite" - 5.6's empty-string rule, because
  B.2.6 routes those contexts to the Event I/O Processor and the
  platform, not to B.2.8.1. Deciding it either way is an explicit act;
  concluding "no data" would be an amendment to that record's scope
  limit, not a silent extension.
- **ADR-0024** (`<data src>` is never fetched). Same shape of exclusion:
  "`<content>` fetching for `<send>`/`<invoke>` payloads, if ever
  implemented, must argue its own case - those sit at the effect
  boundary where a fetch may genuinely be expressible, so they do not
  inherit this answer" ([`docs/adr/0024-data-src-is-never-fetched.md:126`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/docs/adr/0024-data-src-is-never-fetched.md#L126)).
  Relevant to `src`/`srcexpr`.
- **ADR-0026** (script as predicator statement programs).
  `Machine.program()` is a sibling of `Machine.expr()`, which is what a
  `<finalize>` body's executable content would compile through.
- **ADR-0027** (embedder-placed session runtime). The most load-bearing
  boundary record. It names st-cmq.6 as the trigger that ends the "no
  caller yet" era for `states_to_invoke` (`:83`), quotes 6.4's
  cancellation MUSTs (`:40-50`), and assigns the parent-held
  `invokeid -> {child_session_id, pid, monitor_ref}` table, the monitors,
  the parent-sequenced cancel, and the queued-event discard by invokeid
  to **st-cmq.7** (`:110-121`, `:182`). It also records that widening
  `Mix.Statifier.AdrGuard.@effect_interpreter_paths` requires an
  ADR-0011 ledger entry with a human `Approved-by:` (`:160-170`).
- **ADR-0028** (executable content blocks thread one context). The
  contract a `<finalize>` block would inherit: its own `Block.location`,
  its own `[c_index]`, one `Evaluator.context/1` built once per
  `execute_block/3` call.
- **ADR-0018** (no process jargon in code comments) and the repo's own
  convention that a ported function is described against the pseudocode
  - both visible in the style of every existing seam comment.

## Open Questions

These are recorded here rather than answered; each is a decision the
implementation plan owes, not a fact about the codebase.

1. **The generated invokeid format contradicts ADR-0008 as literally
   written.** Spec 6.4.1 says the auto-generated identifier "MUST have
   the form stateid.platformid, where stateid is the id of the state
   containing this element". ADR-0008 reserves the bare `inv_` UXID
   prefix. A composite `"<stateid>.inv_01J..."` satisfies both readings;
   a bare `inv_01J...` satisfies ADR-0008 but not 6.4.1's MUST. Nothing
   in the tree decides which. Note also that ADR-0008's "IDs are
   generated once at the owning entity's creation and are immutable"
   sits against 3.14's "not at load time but each time the element is
   executed" - a state re-entered twice invokes twice and gets two ids.
2. **`<content>` failure semantics under `<invoke>` are explicitly
   undecided.** ADR-0021's scope limit requires this bead (or its
   successor) to decide the failure value for the invoke context
   explicitly, and states the default expectation is 5.6's empty string
   rather than `nil`. Related: whether `src`/`srcexpr` may ever be
   fetched is left open by ADR-0024 with the same "must argue its own
   case" language.
3. **There is no cancel-invoke effect shape.** `Effect.Cancel` is
   `<cancel sendid>`; the bead says invoke cancellation "is its own
   thing" and leaves the shape to the plan. Open sub-questions: whether
   it carries `invoke_id`, `state_index`, or both; whether one effect
   carries a list of invocations per exiting state or one effect per
   invocation; and whether it gets a `round` field (no core effect has
   one today; all seven trace effects do).
4. **What `state.invoke` looks like on the compiled state.** Neither
   `Document.State` nor `Machine.State` has an invoke field.
   `Machine.State`'s moduledoc records that `donedata` is the sole field
   filled in after the compiler's single interning pass, so whether
   invocations join that late pass or the main one is unsettled.
5. **`states_to_invoke`'s exact type and population rule.** Appendix D's
   `enterStates` adds **every** entered state unconditionally, and its
   `mainEventLoop` sorts by entry order, which an unordered `MapSet`
   does not preserve (`Machine.document_order/2` exists and could
   re-derive it, as `enter_states/2` already does at
   [`lib/statifier/interpreter/exit_entry.ex:600`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/lib/statifier/interpreter/exit_entry.ex#L600)). Whether to store a
   `MapSet` and sort at the pass, store an ordered list, or filter to
   states that actually carry invocations at entry time - and whether
   filtering would be an ADR-0002 deviation needing a cited reason, as
   `entered_states`'s own moduledoc argues about conditional population
   - is undecided.
6. **What "core-side finalize/autoforward selection" returns.** The bead
   says the core selects and the session delivers, but there is no
   effect tag, no return shape, and no `Cause.origin()` arm for it
   today. Appendix D's pass also runs `applyFinalize` and `send` inside
   a loop over the configuration during `handle_event/2`, i.e. before
   `select_transitions`, which means finalize's executable content
   mutates the datamodel mid-`handle_event/2` - so whether finalize runs
   as `Interpreter.Content.execute_block/3` inside the core (mutating
   `machine_state`) or is deferred to the session is a real fork, and
   6.5's "MUST NOT raise events" bans `<raise>`/`<send>` inside it,
   which nothing validates today.
7. **The empty-versus-absent `<finalize>` distinction.** 6.5 requires an
   *empty* `<finalize>` to auto-assign matching returned values into
   `namelist` locations and `<param location>` targets, while an
   *absent* one does nothing. That means the lowered shape must
   distinguish `nil` from `[]` all the way to the machine struct - a
   distinction that `Document.Block`'s `content: []` default does not
   currently carry on its own.
8. **The feature-detector atoms will misreport once invoke lands.**
   [`test/support/feature_detector.ex:168-182`](https://github.com/riddler/statifier-ex/blob/baedffc10d695da3f682b4c9a65b188d13c78fff/test/support/feature_detector.ex#L168-L182) folds `<param>`/`<content>`
   under `<invoke>` into the `send_*` atoms and says so; flipping
   `invoke_elements` to `:supported` without addressing that would let
   files through the gate on a mis-scoped classification. Whether
   `invoke_elements` becomes `:partial` for this bead (core lowering,
   effects, passes) and only `:supported` after st-cmq.7 is undecided,
   and it determines how many of the 35 files this bead can move.
9. **The bead's own line numbers are stale.** It cites
   `interpreter.ex:462-473`, `:554` and `:210-212`; the seams are at
   `:760-771`, `:861-862` and `:393-396` at this commit. Worth
   correcting on the bead so a later reader does not chase them.
